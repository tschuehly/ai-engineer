# Auto-Evolving Skills Multiply Whatever Governance You Already Have

Summary: A closed loop that rewrites its own skills is not a fix for an ungoverned skill library — it writes into the same library, at higher rate. Ownership, discoverability, versioning, and access control are upstream of the loop, so automating skill improvement scales whichever regime is already in place, including the bad one. The governance question does not get easier when the authoring gets cheaper; it gets more urgent.

Use when:
- Evaluating a proposal to have agents author or continuously improve their own skills.
- Sequencing work: deciding whether a self-improvement loop or a catalog comes first.
- Explaining why a working personal skill-evolution loop does not transfer to an organization unchanged.
- Reviewing an agent-authored skill and asking what would have caught it if it were wrong.

Details:
- **The claim, as the talk's closing line.** "Auto evolving — and again, this is what everyone kind of like is the next hype right now. Like, yeah, I can create a closed loop that can evolve automatically my skills. So what, right? If you automatically start this machine, the impact will be way more than it is today, because what I shared earlier is going to be just maintaining auto-evolving skills without that governance in place that actually put the guardrails for your organization." ([Touil](../sources/20260828_M05vON8i0aI.md), 19:37-20:03) The word doing the work is *multiply*: the loop is a rate, and the sign is set elsewhere.
- **What "elsewhere" contains.** The failure modes an auto-evolving loop inherits unchanged, all named earlier in the same talk: duplication, because teams on the same stack "for sure building the same skills over and over again without sharing them"; quality decay, because skills must be validated "not against your task but also against the latest models that comes"; unknown ownership, because "if you don't have an owner then no one will be able to maintain, scale those skills"; and security, because "skills actually does have scripts because that is the deterministic part of it," so an unchecked skill is a supply-chain intake. (11:21-13:13) None of these are addressed by making authoring automatic; each is made faster.
- **The specific asymmetry with the personal case.** This wiki's self-improvement pages — [Mine Agent Conversation History to Generate Missing Skills](mine-agent-conversation-history-to-generate-missing-skills.md), [Skills Turn Procedural Feedback Into Transferable Agent Memory](skills-turn-procedural-feedback-into-transferable-agent-memory.md), [Feedback turns coding-agent loops into prompt and skill improvement cycles](feedback-turns-coding-agent-loops-into-prompt-and-skill-improvement-cycles.md) — all describe loops that work, and all of them run inside one person's or one team's context. That is exactly the property that makes them safe: the author is the reader, the library is small enough to hold in a head, and a bad revision is noticed on the next run by the person it hurts. Scale the same loop across an org and every one of those checks disappears while the write rate goes up. The loops are not wrong; their preconditions are local and go unstated.
- **The cheapest gate available today, and its ceiling.** Skill evaluation is unsettled — "there's still kind of like a discussion on what is the right approach to evaluate skills" — and the interim answer Touil reports using is structural rather than behavioural: "you static-test or evaluate your skills against the Anthropic best practices. If the skill is not invoked properly, if the skill is not structured properly, there's a high chance that it's not going to be high quality." (19:13-19:37) This is cheap, automatable, and worth wiring into an auto-evolution loop as an admission test. Its ceiling is obvious and should be stated with it: a well-formed skill can be confidently wrong, and structure correlates with quality rather than establishing it. For the behavioural half, [Evaluate agent skills with task scenarios and comparative conditions](evaluate-agent-skills-with-task-scenarios-and-comparative-conditions.md) supplies the with-skill/without-skill comparison this static check cannot.
- **The model-drift term, which is what makes a static library rot without anyone touching it.** Validating a skill against its task fixes it to the model that was current when it was written. "If you don't test and make sure that you're maintaining and you're validating your skills not against your task but also against the latest models that comes, then the quality starts degrading over time." (11:43-11:55) A skill's quality is a property of the (skill, model) pair, so a library decays under a model upgrade with no edit and no failing test — the same dynamic [A Harness Fix Becomes Overhead When the Model Outgrows It](a-harness-fix-becomes-overhead-when-the-model-outgrows-it.md) documents for harness workarounds, applied to a library that may hold hundreds of units nobody owns. An auto-evolution loop could in principle *fix* this, by re-testing on model change; without governance it more likely re-writes stale skills into new stale skills, because the loop's own reward signal is also model-dependent.
- **The sequencing this implies.** Ownership and a catalog first, then the loop — not because the loop is dangerous in itself, but because the loop's output has to land somewhere with a name on it. The minimum before switching on org-wide auto-evolution: every skill has an owner, every change is versioned and attributable, an admission gate runs on write, and the skills whose scripts touch sensitive systems are access-controlled. Each of these is a thing the loop assumes and none is a thing it provides.
- Limits. Nothing in this talk is measured, and this section in particular is forward-looking commentary rather than a report of anything deployed. No auto-evolving system is named, evaluated, or shown; the static-check-against-best-practices recommendation is offered as "the easy thing that I found so far very valuable" with no accuracy figure.
