# Make One Agent Session Reachable From Every Interface

Summary: Adding a Slack bot to a coding agent does not make the agent multiplayer; it moves the agent from trapped on one laptop to trapped in one product. The reusable move is to make a single agent session — with its accumulated context intact — addressable from every surface where the work already happens, so that a teammate joining from a different tool is joining the same run rather than starting a parallel one.

Use when:
- Designing how a team, rather than one developer, interacts with a long-running coding agent.
- Someone proposes a Slack integration, a GitHub bot, and a desktop app as three separate agent entry points.
- Deciding what a reviewer should do when they have a question about a change someone else's agent produced.

Details:
- **The starting condition and why the obvious fix is only half.** "Typically when people are working with coding agents, they're on their laptop, kind of stuck on that laptop. Nobody else can talk to that agent." The standard first response is a chat bot — "Claude has a Slack bot. Codex has a Slack bot. We have a Slack bot" — and Singh's objection is that it relocates rather than removes the constraint: "now we've taken it from trapped on somebody's laptop to kind of trapped in Slack. And a lot of work happened in Slack, so that's better than nothing, but certainly not all work happens in Slack." ([Arjun Singh](../sources/20260809_OL7kfezynJM.md), 03:04-03:36)
- **The requirement, stated as an identity claim about the session.** "What we really wanted was to be able to work with the same session from every relevant interface. Could be Slack, could be our app, could be GitHub, could be elsewhere." A demonstrated flow starts in Slack, continues "in a more engineer-focused environment in the desktop app or the mobile app," and finishes in GitHub — "and the important thing here is the exact same agent session… it's like the agent didn't forget what you did in one place in Slack when you go and talk to it from GitHub, it's the same session. It's got the same context." The interfaces are views; the session is the object. ([Arjun Singh](../sources/20260809_OL7kfezynJM.md), 03:36-04:07)
- **The concrete payoff is a review latency one, and it is the sharpest thing here.** Reviewing a teammate's change, "I can just pop in and say, 'Hey, why did you do it this way?' And again, because it's the same agent session, I don't need to wait for Sergey to kind of get my notification on GitHub and respond to me. The answer to the question is almost certainly in this thread." The second half matters as much: "I don't also don't want to read the entire thread. So I can just ask the agent." The session is both the record of why a decision was made and the interface for querying that record — which is the practical form of [capturing the coding session as the intent record](capture-the-coding-session-as-the-intent-record.md), with the author removed from the critical path. ([Arjun Singh](../sources/20260809_OL7kfezynJM.md), 04:49-05:08)
- **A shared session carries a participant roster, and the roster is provenance.** "You can kind of see at the top here all the different people that interacted with this. So I can see who's getting notified about this session, who's seen it." Singh calls this "especially important when you have work triggered by non-technical people": if "our customer support person created a ticket" and the work looks good, the question a reviewer actually needs answered is "has this been vetted by an engineer or not?" — and the roster answers it without anyone maintaining a separate field. This is a lightweight instance of [keeping human ownership on agent pull requests](human-ownership-keeps-agent-pull-requests-from-bypassing-review.md). ([Arjun Singh](../sources/20260809_OL7kfezynJM.md), 04:21-04:48)
- **Visibility travels as artifacts, not as text in whichever tool produced it.** "It doesn't matter where the work started or where it's finishing, the agent can show you the work it's doing as screenshot or video or other. And you can see it from everywhere… you don't have to worry about like, 'Oh, where is that thing? I got to go to GitHub to see the image or got to go to Slack to see the image.'" The session-as-object design is what makes an artifact addressable from every surface rather than pasted into one of them. See [dynamic artifacts make agent work reviewable and reusable](dynamic-artifacts-make-agent-work-reviewable-and-reusable.md). ([Arjun Singh](../sources/20260809_OL7kfezynJM.md), 05:09-05:31)
- **The stated cost of not doing it.** "Integrate agents into the relevant human interfaces so your team and your agents can work together and don't have to like context switch and copy context back and forth… Figure out how to make this happen because if not, the friction is just really high." The failure this prevents is human beings acting as couriers between systems that each hold part of the context. ([Arjun Singh](../sources/20260809_OL7kfezynJM.md), 17:24-17:46)
- **Relation to the cloud-workspace version of the same idea.** ACE reaches multiplayer sessions from the environment side — a sandboxed micro-VM on its own Git branch with shared terminals, dev servers, and previews, so teammates join without stashing local work ([shared cloud workspaces make agent sessions collaborative](shared-cloud-workspaces-make-agent-sessions-collaborative.md)). This page is the *addressing* half of the same problem: one shared runtime still leaves you with one place to go and look at it, and the claim here is that work does not concentrate in any one place. The two compose — Superconductor's sessions run in isolated cloud environments for exactly the ACE reasons — but they are separable, and a team that has the shared runtime can still have the trapped-in-one-product problem.
- **A second vendor reaches the same "where you live" conclusion but keeps the primary surface singular.** Resolve AI ships a UI where you "inspect all the different tasks that you have and view their reports, view previous runs," and then subordinates it deliberately: "we think the surface area being where you live, right? So, Slack… or MS Teams," with "ideally a lot of your interaction… in the places that you're already kind of doing work." That is the trapped-in-Slack position this page argues against, and the difference in workload is the likely reason — operational reports and channel questions genuinely originate in chat, whereas a coding session has to touch GitHub and an editor. The shared premise is that the vendor's own app should not be the place the work happens; the disagreement is whether one chat surface suffices. ([Justin Smith](../sources/20260809_vSx5IULvBns.md), 21:40-22:11, 24:20-24:31)
- **The same source shows the reply-in-place move applied to a standing job rather than a session.** Replying "this is too verbose. Verbose. Make it shorter" in a report's thread updates the recurring task itself, so the next firing differs — see [Amend a Recurring Agent Task by Replying to Its Output](amend-a-recurring-agent-task-by-replying-to-its-output.md). Where this page makes one session addressable from many surfaces, that one makes a persistent specification editable from wherever its output lands. ([Justin Smith](../sources/20260809_vSx5IULvBns.md), 20:26-20:58)
- **Unaddressed by the source.** Nothing is said about contention: what happens when two people push the same session in incompatible directions from different surfaces, how conflicting instructions are ordered, or whether anyone can pause a run someone else started. A single mutable session shared across a team is a concurrency design, and none of it is described.
