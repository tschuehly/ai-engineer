# The Markdown Workflow Is the Source; the YAML Is a Compiled Artifact

Summary: An agentic automation can be authored as a Markdown document — prose instructions in the body, a declarative capability manifest in the front matter — and compiled into whatever the CI runner actually executes. The rule that makes it work is that the compiled output is never edited and never read: "the markdown is the source code. The YAML is like a compiled artifact." Changing the automation's behavior means editing the English.

Use when:
- Designing how recurring agent jobs are authored, reviewed, versioned, and handed to non-engineers.
- Deciding whether an automation's definition should be a prompt, a config file, or a program.
- Someone proposes generating CI configuration with an LLM and you need to decide which artifact is canonical.
- Assessing what a team can actually review when the executable form is machine-generated.

Details:
- **The authoring experience is a message to a teammate.** Gazit's dependency-upgrade automation began as "something a lot like a Slack message that I'd send to a junior developer on my team. Like, every day I want you to check if there's a new release, look at the change log, look at the docs, come up with a plan for the upgrade, and then create a PR with the thing and here's the links to the docs" — roughly three lines, plus a "magic line up top" supplying a skill that tells Copilot how to write agentic workflows at all. ([Idan Gazit](../sources/20260808_iQ5xldZ9StU.md), 05:38-06:11)
- **Expansion is the point, and it is codebase-aware.** The three lines compiled into a full playbook with steps the author never wrote: check for new releases, review the changelog and upgrade guide, apply the upgrade, create a pull request. "Because it sees my codebase, it was able to infer what it even needs to check, and it actually found these specific dependencies." Gazit's summary: "I didn't ask for any of this explicitly, but Copilot is pretty good at sussing out my little three-line message into a full playbook." The described shape is "if GitHub Actions and Copilot had a baby together, and it ran on markdown." ([Idan Gazit](../sources/20260808_iQ5xldZ9StU.md), 06:12-06:58)
- **The compiler contract.** "It's just markdown. It's easy to iterate on that markdown. If you don't like the way that the automation works, just edit the English. It gets recompiled into an Actions workflow… You never look at it." The generated YAML is treated the way a build artifact is treated: regenerable, not a place to make changes, not the thing under review. ([Idan Gazit](../sources/20260808_iQ5xldZ9StU.md), 10:20-10:35)
- **The front matter is the part the LLM does not get to write around.** The same document carries a YAML front-matter block declaring permissions, allowed tools, allowed network destinations, and permitted writes — deliberately outside the prose, because a guardrail expressed in the prose is reachable by anything that can inject the prose. So the artifact has two halves with different trust properties: a natural-language body that is elaborated and rewritten freely, and a declarative manifest that binds the run's capabilities before the agent starts. Treating them as one file is what makes the automation portable and forkable; treating them as one *kind of text* is the mistake. See [bound what an unattended automation may emit](bound-what-an-unattended-automation-may-emit.md) and [run must-not-fail decisions in a code layer above the model](run-must-not-fail-decisions-in-code-above-the-model.md). ([Idan Gazit](../sources/20260808_iQ5xldZ9StU.md), 07:10-07:47)
- **Distribution follows from the format.** Because an automation is one readable document, a starter library becomes viable: GitHub ships an issue triager, a CI doctor, a Repo Assist "swarm of agentic workflows that work together to help you maintain your project," and daily team and repo status jobs, all offered "as a starting point to customize." GitHub used the issue triager internally as the basis for its own triager and for hunting N+1 queries in its monolith. The same property is what lets the pitch extend past engineers to product managers — you fork a document and edit sentences. ([Idan Gazit](../sources/20260808_iQ5xldZ9StU.md), 10:36-11:46)
- **The cost of "you never look at it."** An unread compiled artifact is an unreviewed one. If the executable YAML is what CI runs and nobody reads it, the review surface for a change is the diff of the English plus trust in the compiler — which is exactly the property that makes the front matter's deterministic declarations load-bearing, since they are the only part a reader can check against what will actually happen. The talk offers no account of how a compiler regression, a non-deterministic recompile, or a prompt-injected recompile would be caught. Compare [version-control and unit-test the agent permission policy](version-control-and-unit-test-the-agent-permission-policy.md), where the policy artifact is authored by hand, reviewed line by line, and covered by fixture tests: same goal, opposite bet on who writes the enforceable part.
- **Where this sits among the wiki's Markdown-as-substrate patterns.** [Repo-local Markdown tasks](repo-local-markdown-tasks-give-agents-durable-scoped-work-units.md) hold *work items* for an interactive agent to pick up; this holds a *standing job* that runs unattended on a schedule and is compiled into a runner spec. [Compiling natural-language analytics into reusable deterministic widgets](compile-natural-language-analytics-into-reusable-deterministic-widgets.md) makes the same move in a different domain — an LLM produces the artifact once, and thereafter a deterministic system executes it — and both rest on the claim that repeated execution should not re-enter the model's judgment.
- **Provenance.** A vendor lab demo of a product in public preview, presented by the lab's lead. The Astro 5→7 run on the speaker's personal site is a single successful demonstration; there is no data on compile fidelity across many workflows, no failure examples, and no report of what a bad compile looks like.
