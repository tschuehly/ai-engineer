# Contain Retry Amplification Before It Becomes a Compute Incident

Summary: Uncontrolled retries are one of the biggest risks in agentic systems: when an agent responds to a tool error by regenerating a slightly different but still-invalid request, the loop compounds — each retry consumes more compute and deeper reasoning — until a minor API error becomes a runaway compute incident. Bound retries with circuit breakers, resource quotas, and controlled recovery so infrastructure absorbs the mistake instead of amplifying it.

Use when:
- An agent can retry tool calls, model calls, or workflow steps on failure without a hard bound.
- Diagnosing unexplained GPU/cost spikes that trace back to an agent looping on a failing dependency.
- Designing recovery behavior for a long-running agent that must stay within a cost, latency, and outcome budget.

Details:
- The amplification mechanism: an agent calls a tool incorrectly, the tool returns an error, and instead of recovering the agent generates a "slightly different but still invalid request." The cycle repeats; each retry consumes more compute, reasoning depth increases, GPU consumption rises, and you get exponential resource growth — "what started as a minor API error became a compute incident."
- This is the concrete example of the broader failure class: real agent failures are usually infrastructural (retry amplification, recursive reasoning loops, workflow deadlocks, context corruption, memory poisoning, cost explosions), not hallucinations — "the model makes a mistake, but the infrastructure turns that mistake into an outage." Hallucinations are "often the least interesting failure mode."
- The fix is to reuse distributed-systems reliability primitives rather than invent new ones: retries become *controlled recovery* (bounded, backed-off, escaping the loop on repeated failure), circuit breakers become tool isolation so a failing tool fails fast instead of being hammered, and resource quotas become cost governance so a runaway loop hits a ceiling.
- Detecting these loops requires causal observability — traces of the chain of tool calls and reasoning decisions — because a retry storm looks like normal activity in aggregate logs until the compute bill spikes.
- **A quieter cousin that no circuit breaker catches, because nothing errors.** Coyle names running out of output tokens as a stop reason in its own right: the response "is based on partial when the LLM had to stop. And it's going to give you a response, but if you have run out of tokens, then you need to take action." Retry amplification is a loop that fails loudly and repeatedly; this is a loop that terminates cleanly on a half-finished answer, so quotas, backoff, and fail-fast tool isolation all report success. The detection surface is the stop reason rather than the trace ([Read the Stop Reason Before You Read the Answer](read-the-stop-reason-before-you-read-the-answer.md)). ([Coyle](../sources/20260808_Z-c11pV_uvU.md), 10:50-11:12)
- **Amplification can also be capped at the exit rather than inside the loop, by declaring how many artifacts a run may produce.** GitHub's agentic-workflow manifest lists permitted outputs with cardinality: "Pull request single… because I don't want the agent to get prompt injected to create 500 pull requests. That would be a denial of service." The cap is enforced outside the model, so it holds regardless of why the loop is spinning — a retry storm, a confused plan, or an injected instruction all hit the same ceiling. This is complementary to in-loop containment rather than a substitute: an output cap does not stop wasted tokens or wall-clock, it stops the blast radius reaching the repository and the humans watching it. The same manifest permits an empty result, so a run that cannot make progress is allowed to end silently instead of retrying into noise. See [bound what an unattended automation may emit](bound-what-an-unattended-automation-may-emit.md). ([Idan Gazit](../sources/20260808_iQ5xldZ9StU.md), 08:16-08:48)
- **Two things retry amplification costs that a compute-incident framing understates, and the one mitigation that survives the storm.** Manuja's objection to blind retries on LLM calls is that they hit three budgets at once: "retrying an LLM API eats into your latency budget really fast," and because the calls are slow and expensive, "blind retries just multiply your cost and your tail latencies." The tail-latency term is the one usually missed — amplification degrades the P99 of the requests that are *not* failing, well before any bill spikes. His containment advice is also more specific than scaling: "when you have a retry storm, it becomes really hard to just scale out. You cannot simply scale out services that is under a retry storm," so the gateway needs load shedding, bounded internal web-server queues that "cannot accept requests that are unbounded," and traffic prioritization so "under load your most important use cases get served" — rehearsed in "your runbooks, game days" rather than discovered live. ([Manuja](../sources/20260828_zrZ1amZBSPw.md), 02:24-02:58, 13:49-14:31)

- **Containment has a middle setting between "let it run" and "kill it," and it needs a different place to live.** Chawla and Koul's objection to quotas and circuit breakers as the whole answer is that both are terminal: the run dies, and the work is lost. Their enforcement layer puts steering ahead of halting — when "your context is growing very out of range… you should have in place policies which can solve that particular thing there and there instead of halting," with the cap only "after basically exhausting the list of all in place policies." Their policy catalog names loop detection and progress detection as first-class policies beside spend and context management, which is the detection surface this page's causal-observability point calls for, expressed as something that acts rather than something that reports. The catch is that steering requires a channel back into the running agent, which a gateway, a quota, or a breaker does not have.
