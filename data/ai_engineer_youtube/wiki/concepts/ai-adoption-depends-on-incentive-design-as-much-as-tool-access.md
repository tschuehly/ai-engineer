# AI adoption depends on incentive design as much as tool access

Summary: Uneven AI-tool adoption inside engineering teams can come from incentives, not only awareness, training, or tool availability. People with direct upside from output gains have stronger reasons to keep experimenting with agents and automation.

Use when:
- Diagnosing why engineers are not adopting AI coding tools despite availability.
- Designing organizational policies that should reward useful AI leverage rather than visible tool usage.
- Comparing founder, salaried employee, and equity-driven incentive structures.

Details:
- The speaker contrasts his own heavy use of many agents with an engineer still typing directly in a code editor and asks why the usage patterns differ. (03:01-03:44)
- He frames the difference as an incentive issue: founders seek every incremental efficiency gain, while a typical base-salary, annual-bonus, and equity package may not directly reward working faster with unfamiliar AI tools. (03:44-04:42)
- Hourly work can disincentivize speed because more time means more pay, and fixed project pricing can encourage padded estimates because engineers want downside protection against uncertain duration. (05:08-06:07)
- The talk's proposed remedy is to directly incentivize engineers to use AI tools well while preserving high code quality standards. (07:20-07:33)
- **Access is not the binding constraint, and the cost of assuming it is compounds.** Shenoy's version — "everyone assumes the usage just shows up… It never does" — adds a consequence beyond wasted licences: where the agent improves from production traces, non-adoption starves the improvement loop, so "the agent only improves if people actually use it. And people only use the agent if it's worth adopting." Incentive design is therefore acting on the seed of a feedback loop rather than on a one-time conversion, which is why the early period is worth disproportionate effort. ([Shenoy](../sources/20260828_B0fjR3yaZFU.md), 14:29-15:17)
