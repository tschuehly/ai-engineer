# Put an Agent Approval Gate in Front of Maintainer Attention

Summary: A repository facing more contributions than its maintainers can read has two structurally different responses: filter the inflow so less arrives, or absorb it so that what reaches a human is pre-qualified. Warp took the second — every pull request goes through an agent-managed review that iterates until an agent approves, and no human reviewer is notified before that point. The gate is not a quality control bolted onto review; it is an attention router, and the thing it protects is the maintainer's notification queue rather than the merge button.

Use when:
- A repo, monorepo, or internal platform is receiving more pull requests than its reviewers can triage, and adding reviewers is not available.
- Deciding whether an AI code review should comment alongside humans or run before them.
- An open-source project is choosing between contribution restrictions and automated intake.
- Someone proposes "AI review" without specifying what changes about who gets pinged.

Details:
- **The volume that forced it, with the only numbers the talk gives.** Warp open sourced "about 3 months ago"; GitHub stars "catapulted from around 20,000 to over 60,000"; the repo took "thousands of PRs" from "hundreds of contributors." These measure inbound pressure, not the gate's effect. ([Abdalla](../sources/20260822_L173Z8DpaJg.md), 10:30-11:13)
- **The design constraint stated before the mechanism.** "We didn't want this to be the kind of thing where agents are just writing code and firing off PRs. We want them to participate meaningfully in the structure that we use to triage issues that came into the repo, provide context around them, do implementation, do reviews, but still have the space for humans to participate in this loop." The agents are placed inside the project's existing process rather than pointed at its inputs — which is what distinguishes this from a bot that opens PRs. (11:13-11:33)
- **The gate itself, and the sentence that carries the whole idea.** "All PRs that get contributed to Warp go through an agent-managed review process. And it goes through multiple iterations, and we don't actually ping any of the human reviewers on our team until an agent has approved our PRs, which helps manage the workload a lot for the team. So all of those thousands of PRs, the things that humans actually have to manage are only the high-signal, high-quality ones." Two properties matter independently: the review *iterates* with the contributor rather than emitting one verdict, and human notification is *gated on approval* rather than merely accompanied by a bot comment. (12:25-12:45)
- **The gate is expected to improve from its own traffic.** "We improve the agent as we get more PRs in the repo and we see more examples of code… self-improvement loops are a really important way for you to enhance the overall SDLC." No mechanism is described — whether examples become rules, prompt context, or eval cases is not said — so read this as an intent rather than a technique, next to the wiki's concrete versions in [mining recurring review comments into an invariant registry](mine-recurring-review-comments-into-an-invariant-registry.md) and [turning review lessons into guardrails](use-reviewer-agents-and-lints-to-turn-review-lessons-into-guardrails.md). (12:45-13:03)
- **This is the opposite response to the same problem the wiki already documents.** Every prior source on contribution influx *narrows the channel*: Zechner auto-closes PRs pending a human-voiced issue, Zig bans AI in issues and comments, tldraw auto-closes all PRs, GitHub ships a switch to disable third-party PRs ([Gate AI-generated open-source contributions through human-effort filters](gate-ai-generated-open-source-contributions-through-human-effort-filters.md), [Closing the Contribution Channel Is Where Slop Filtering Ends](closing-the-contribution-channel-is-where-slop-filtering-ends.md)). Warp *widens* it and moves the cost to compute. The two are not interchangeable, and the deciding question is what the project believes review is for. Rizwan reports Zig's reason as an ordering of values — review is how they "grow new contributors who can become trusted over time" — and an agent gate does not do that at all; it optimizes for the patch. A project whose scarce resource is maintainer attention should read this page. A project whose scarce resource is trusted contributors should read that one.
- **What the gate cannot do, and the wiki's evidence for it.** A gate the contributor iterates against is a verifier the contributor can optimize against, and [at long horizons a weak verifier becomes an attack surface](at-long-horizons-a-weak-verifier-becomes-an-attack-surface.md). The failure mode specific to this design is not a bad merge but a *silent* one: a PR that never reaches a human because the agent approved it wrongly leaves no trace in anyone's queue, whereas a bad comment in a human-visible review at least gets read. That is the inversion of the wiki's usual review-bot concern, which is [comment volume](comment-volume-is-a-property-of-the-review-pipeline.md) — filtering for volume risks dropping true positives, and gating on approval risks dropping the whole change from view.
- **What the gate does not replace.** Humans still merge; the described role is that they see "only the high-signal, high-quality ones," not that they see none. That keeps this compatible with [human ownership on agent pull requests](human-ownership-keeps-agent-pull-requests-from-bypassing-review.md) — the accountable reviewer still exists, further downstream — and distinguishes it from [a self-verifying loop](self-verifying-agent-loops-hide-review-rather-than-remove-it.md), since the reviewing agent is not the agent that wrote the code. Where a contributor's own agent wrote the patch and the repo's agent approves it, that separation is thinner than it looks and nobody has measured it.
- **Evidence.** Entirely unmeasured. No approval rate, no false-approval rate, no reviewer-hours saved, no contributor-side report of how many iterations the gate demands before it approves, and no statement of what happens to a PR the agent never approves — whether it is closed, left open, or escalated. The star and PR counts describe demand, not the gate.
