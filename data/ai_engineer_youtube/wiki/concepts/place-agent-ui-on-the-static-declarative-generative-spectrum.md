# Place Agent UI Generation on a Static–Declarative–Generative Spectrum

Summary: How an agent produces UI sits on a spectrum defined by how much the model generates versus delegates to developer-built components — static (props into predefined components), declarative (model emits a JSON/YAML descriptor a rendering engine maps to components), or fully generative (model writes HTML/CSS/JS on demand) — and the choice trades flexibility against consistency, predictability, latency, token cost, and the trust/containment burden.

Use when:
- Designing how an agent or MCP app turns a tool call into rendered UI, and deciding whether to ship prebuilt components, a descriptor renderer, or model-written markup.
- Reasoning about why "the models write great front-end code" does not automatically mean you should let them render arbitrary code to users.

Details:
- **Static UI** — the agent is just an orchestrator. A tool call (via MCP apps or a direct tool call) passes parameters/data/props to predefined static components built by developers; the client renders them. This is the dominant pattern today and is "very similar to what we've been doing for the past 20 years" (server sends data → client renders), except the agent now generates the data and props. Examples: the AG UI protocol's SDK registers a client tool that maps to a React component (the tool call's props map to a static component); Goose's "Auto Visualizer" takes arbitrary data, matches/organizes it, and routes it to a predefined set of components the Goose team built. (06:02-07:41)
- **Declarative UI** — still developer-built design-system components, but instead of just passing props the agent emits a *descriptor* (JSON or YAML, or Python with FastMCP) that a translation/rendering engine converts into the final UI. More dynamic and personalized, but the components are still static: "the LLM is generating the JSON, not the components." Prior art: Netflix's server-driven UI personalizes the homepage while still mapping to Netflix components. Current tool: Vercel's JSON Render (JSON and recently YAML). Casas's position is that declarative UI is "probably the perfect balance today" — it preserves the design system and predictability, is faster, and is potentially cheaper because it spends far fewer tokens than generating the whole UI. (07:42-10:06)
- **Fully generative UI** — skip components entirely and let the model write HTML/CSS/JS on demand at runtime. Mechanically: instead of calling a layout rendering engine, call the same model with "reverse sampling" or call a second model to generate the markup, then pass it to the client. The Postman weather agent does this — fetch the weather API, write a joke, and emit HTML/CSS/JS "all in one tool call," yielding an imaginative UI where "everything is created by the agent — there is no component, there is no translation." (10:06-11:25)
- The decision axis is flexibility vs. consistency/predictability/latency/cost: static is cheapest and most predictable but least flexible; generative is most flexible but unpredictable and token-heavy; declarative is the practical middle that keeps a design system while letting the model personalize. (07:42-10:06)
- The hard catch on the generative end is **trust and containment**: LLM-generated code is untrusted third-party code, so "if we don't trust third-party code, we should not trust code generated by LLMs and just present it to the user." Generative UI therefore needs a distribution model with a boundary, containment, and a sandbox — which is what makes MCP apps the natural delivery mechanism (auth, tool calling, UI↔agent message passing, and sandbox-by-default double iframe), for first-party as well as third-party UI. See [Render Third-Party Generative UI Through a Double Iframe](render-third-party-generative-ui-through-a-double-iframe.md). (11:25-13:21)
- Framing: this is "still the radio era" of agent interfaces (early TV was "radio shows with cameras"); the spectrum is a snapshot of an evolving medium, not a final taxonomy, and the speaker expects the endgame to move "beyond components" toward collaborative, editable shared artifacts rather than one-shot output. See [Structured canvas outputs make agent edits inspectable and editable](structured-canvas-outputs-make-agent-edits-inspectable-and-editable.md). (13:21-16:16)
- **Figma's Code Connect is the static end of this spectrum applied to component output.** Rather than generating a rendering of a design element, the MCP server returns a reference to the consumer's own component when a mapping exists — "the small react component that just says use button component" — because "an enterprise doesn't care if it's pixel perfect if it's not using its like battle tested accessible and internationalized components." Generation is the fallback for unmapped elements, not the default. ([Lumarie](../sources/20260828_ZIYYsAzaLlA.md), 07:10-08:37)
- **A fourth axis the flexibility/consistency/latency/cost tradeoff misses: what the user has already learned.** Wang concedes the capability before qualifying it — dynamic interfaces "are amazing… technically AI can just produce a new UI for any use case that you have" — and then names the cost of using it everywhere: "there is something really nice about being able to visit the same consistent UX for the same use cases over time so that you can like learn how to use some tool." That argues for the static end on grounds unrelated to design systems or tokens: a regenerated surface has no stable affordances to accumulate familiarity with, so the criterion becomes how often the same use case recurs. His resolution keeps both — "crystallized UIs and then also arbitrarily powerful flexible chat agents are both important components of being agent first." ([Wang](../sources/20260826_6pbQgnJ9Voc.md), 10:57-11:51)
