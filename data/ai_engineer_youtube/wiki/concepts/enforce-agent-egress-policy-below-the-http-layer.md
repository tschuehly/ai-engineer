# Enforce Agent Egress Policy at the Wire Protocol, Below HTTP

Summary: Every consequential thing an agent does leaves as bytes on a socket, and the dangerous bytes are frequently not HTTP — an agent that can spawn a subprocess can speak the Postgres wire protocol through a tunnel that no MCP tool definition, HTTP proxy rule, or LLM gateway will ever see. Putting the enforcement point below HTTP, as a protocol-parsing proxy that reads every byte the agent emits, is what makes a rule like "understands SQL" possible at all.

Use when:
- An agent has shell or subprocess access and also has network reach to production databases, clusters, or cloud APIs.
- You are choosing where the agent security boundary lives: inside the harness, at the MCP tool layer, at an HTTP proxy, at an LLM gateway, or below all of them.
- Someone proposes an HTTP allow-list or method restriction as the network control for an agent that can run arbitrary commands.

Details:
- **The reframing.** "Effectively every nefarious action that an agent could take, every good action that it takes, comes in the form of some network communication, some bytes over the wire." Those bytes get formed "of course [by] call[ing] through MCP but also [by] subprocesses," and Postgres in particular "is a nonHTTP protocol that [the agent] can just spawn as a subprocess and start connecting to services." The design conclusion is to "understand what the bytes are coming out of that agent in great detail." ([Ryan Dahl](../sources/20260817_MkRYPFIMCSA.md), 04:24-05:11)
- **The case that defines the requirement.** Deno's production Postgres sits "inside a VPC that we can only reach really through an EKS endpoint," and the thing to prevent is an agent that can "somehow tunnel through this EKS server, spawn psql, and drop the users table." Dahl's own summary of what that demands is precise and is the retrieval cue for this page: "this is an outbound path the agent's host can't reach, on a protocol that isn't HTTP, that's gated by a rule that understands SQL." ([Ryan Dahl](../sources/20260817_MkRYPFIMCSA.md), 05:14-06:33)
- **What the layers above cannot see.** LLM gateways with guardrail features (OpenRouter, LiteLLM are named) inspect the traffic "going back and forth between the LLM provider" — "but, of course, that's just the LLM… we're talking to databases and stuff." HTTP proxies (httpjail's GET-but-not-POST and subpath rules; Brex's Crabtrap running an LLM judge over HTTP requests) "really sit at the HTTP layer." OS-level process sandboxes guard filesystem paths and syscalls, which is a different axis entirely. Each is a real control at its layer; none of them is looking at a Postgres startup packet. ([Ryan Dahl](../sources/20260817_MkRYPFIMCSA.md), 07:40-09:58)
- **The implementation shape (Claw Patrol, MIT-licensed).** A proxy in front of the agent that "operates not at the HTTP level but at a lower level," understanding "each and every byte flowing out of your agent," with a rule system for "what requests get transferred out of the agent and talk to the outside world." Two properties matter beyond the parsing: rules "can be applied even when tunneling through other systems," and a plug-in system extends the protocol set "when you run into a protocol that it is not yet familiar with" — so the parser inventory, not the rule language, is the thing that has to keep up with the agent's reach. ([Ryan Dahl](../sources/20260817_MkRYPFIMCSA.md), 10:00-12:16)
- **The demo is the proof of layer choice, not of the rule.** Codex is run in yolo mode and told to delete the users table; it "properly obeys and starts a psql subprocess." The subprocess's connection "goes through claw patrol where we parse each and every byte. We understand the Postgres protocol. We apply our rules and ultimately reject that." The interesting fact is that the agent's obedience, the subprocess spawn, and the network connect all succeed — the only thing that fails is the wire-level action. ([Ryan Dahl](../sources/20260817_MkRYPFIMCSA.md), 12:16-13:14)
- **"Action," not "request," is the unit.** The dashboard and rule vocabulary deliberately avoid HTTP framing: you click into "each request or action as we call it because it's more general than HTTP requests." A rule outcome is not only allow/deny — it can "ask a human for example in a Slack channel or run an LLM judge over this, or any combination thereof… maybe first get an LLM judge and then get approval in Slack," which puts the [human-approval gate](route-high-impact-agent-actions-through-explicit-human-approval-gates.md) at the wire rather than inside the harness. ([Ryan Dahl](../sources/20260817_MkRYPFIMCSA.md), 13:14-14:31)
- **The integration contract that makes it deployable.** "We treat the agent software as a black box… we don't require any changes to that software." This is what lets one policy cover OpenClaw, Codex, and whatever ships next, and it is the same reason the boundary cannot be a harness plugin. ([Ryan Dahl](../sources/20260817_MkRYPFIMCSA.md), 14:31-14:41)
- **The proxy also holds the credentials.** Because it terminates and re-forms the connection, it can inject secrets so the agent "doesn't ever actually see secret values," across "cookies… Postgres… ClickHouse… all sorts of OAuth protocols… very complex things like AWS SigV4." This is the same no-credential-in-the-box property that [network-layer access control](move-agent-access-control-to-the-network-layer.md) achieves, reached from the protocol side instead of the identity side. ([Ryan Dahl](../sources/20260817_MkRYPFIMCSA.md), 10:00-10:42, 14:41-15:11)
- **Deployment and the caveat the author volunteers.** It runs "over Tailscale or WireGuard," with agents inside a tailnet and the proxy acting as "a Tailscale exit node," and the dashboard reusing Tailscale identity "so that we don't have to layer on another authentication mechanism." The precondition is that "all of our stuff is off the internet." The cost is concentration: "Claw Patrol itself is holding all of these credentials to production systems. So you have to be very careful with it" — the chokepoint that makes the policy enforceable is also the highest-value target in the deployment. ([Ryan Dahl](../sources/20260817_MkRYPFIMCSA.md), 15:28-16:32)

- **What the common alternative looks like, and exactly where Dahl's argument bites it.** Anthropic's managed agents attach an allowed-hosts egress policy to the environment definition — the demo sandbox runs "with the networking limited and allowed hosts only being the MCP server," described as "effectively stop[ping] Claude from doing things that you didn't intend." Host allowlisting is a real and worthwhile control, and attaching it to the environment rather than the agent means every session inherits it ([Model a Managed Agent as Agent, Environment, and Session](model-a-managed-agent-as-agent-environment-session.md)). But it decides *destination*, not *content*: an agent allowed to reach a host can send that host anything the protocol permits, which is precisely the gap this page argues has to be closed by a rule that parses the bytes. The two are layers, not alternatives — and note that neither vendor account has third-party validation behind it. ([Anthropic Applied AI](../sources/20260811_K0X9QDRkIdg.md), 18:30-19:20)

- **What a destination-list sandbox gives you, and where it stops.** Superconductor ships the common shape — allowed and disallowed destinations, a prompt on anything new, scope set "on a per ticket basis or for the whole project" — with exfiltration named as the reason: "make sure they can't exfiltrate your code or your projects or your secrets or your content to somewhere they shouldn't be able to." That governs which hosts a run may reach; it does not govern what is sent to a host already on the list, which is the gap this page's wire-protocol enforcement addresses. The second limitation is procedural: prompting on each new destination is the interactive-approval pattern the same talk rejects two minutes earlier for laptop agents, and the example given for approving one is mundane enough ("maybe you're trying to integrate a new vendor and you need documentation") to train the habit of saying yes. ([Arjun Singh](../sources/20260809_OL7kfezynJM.md), 11:24-12:13)
