# Use formal specifications and proofs for critical generated code

Summary: Formal methods can make selected generated code paths more trustworthy when requirements are written as checkable specifications and verified before the code runs. They are most useful for critical components, not as a blanket guarantee over all LLM behavior.

Use when:
- Hardening a small critical algorithm, library, safety check, or boundary condition generated by an agent.
- Deciding whether type systems, model checking, theorem proving, or proof-carrying code should complement ordinary tests.

Details:
- Dafny is presented as a language that lets developers put proofs beside code, verify assertions with theorem-proving software, and emit ordinary language artifacts such as Python libraries. 20:02-21:56
- In the demo, the verifier checks array-search assertions before execution and rejects a deliberately introduced algorithm bug. 20:45-22:20
- Verification is only as good as the specification: omitted requirements leave space for bugs even when the verifier succeeds. 22:24-22:33
- The source distinguishes static verification, richer type-system checks, proof-carrying languages such as Dafny and SPARK, theorem provers such as Lean, and model checking over finite state machines. 24:39-25:46
