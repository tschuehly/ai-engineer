## Summary

Vasant Kearney (Onlay) describes an agentic execution layer for insurance claims and argues that the healthcare EDI standard X12 should be treated as part of the agent harness rather than as a file format. Because every stage of the claim lifecycle has an X12 correspondence, a phone call to a payer, a browser session on its portal, and an EDI feed are all the same transaction emitted through different channels — which gives a 50-step agentic pipeline a public, strict schema to reject against. The second half is a warning about authority: a payer's phone system, portal, X12 layer, and FHIR layer are often built by different teams or different contractors, so they can contradict each other and can also agree on the wrong answer, which means everything must normalize into an internal representation held correct only until downstream evidence disproves it. He also contrasts enterprise agent memory (database-backed, tiered, bias-aware) with coding agents' local-disk memory, and closes on being "AI pilled and AI skeptical" at once, including the cost discipline of not using an overpowered model for routine high-volume work.

## Extracted Concepts

- [Ground Agent Actions in an Existing Domain Transaction Standard](../concepts/ground-agent-actions-in-an-existing-domain-transaction-standard.md) - X12 is used as the confining schema for agent actions because it is strict, public, and already the provider-payer contract.
- [Treat Every External System of Record as Non-Authoritative](../concepts/treat-every-external-system-of-record-as-non-authoritative.md) - payer phone, portal, X12, and FHIR surfaces disagree and can jointly be wrong, so the internal representation is "correct until downstream evidence proves otherwise."
- [Give Enterprise Agents Tiered Database Memory With an Escape Hatch](../concepts/give-enterprise-agents-tiered-database-memory-with-an-escape-hatch.md) - enterprise memory lives in a database rather than local disk, is split into organization and user tiers, and must not steer users into repeating yesterday.
- [Treat Model and Prompt Upgrades as Regulated Migrations](../concepts/treat-model-and-prompt-upgrades-as-regulated-migrations.md) - a better model on benchmarks is not automatically better inside a system designed around the model it replaces.

## Notes

- The goal frame: agentic work in healthcare has to be grounded in driving overall cost down (specifically the cost of interacting with insurance) or improving the patient experience, because insurance shapes how the patient experiences the whole process. Technical excitement that grounds in neither is out of scope, 01:15-01:54.
- The lineage he draws runs neuron → convolutional nets → large-scale unsupervised learning (2011-2012) → "Attention Is All You Need"/the transformer → the modern chat interface → "the Claude codes, the Codexes," OpenClaw, Hermes agent, and their internal system — which is what introduces the *execution layer*, 01:58-03:02.
- The check-deposit analogy for harness: "we have solved the handwritten digit problem" does not mean you can deposit a check. You still have to identify all the other characters, match them against other infrastructure, and confirm the target account. "Parts of this can be thought of as the harness." Claims have the same shape — many little AI steps between an eligibility check and money landing in the provider's bank account, all of which must run inside strict confinements, 03:06-04:36.
- Multimodal flattening is a stated failure mode: reducing an image to findings (anatomy, extracted geometries, pathologies) before combining it with EHR data in a downstream model can make sense on cost and model-capability grounds, but "you lose context" — the extraction may drop something that matters to a downstream procedure the upstream model was never aware of. The same argument applies to desktop use, where buttons and shapes are "only obvious when you do this multimodal," 04:42-06:09.
- The agentic execution layer is defined by the actions available: open-ended database queries and schema discovery, querying code with respect to data, insurance transactions, phone calls, web portals, and EHR interfaces. Some of those actions have write implications; on desktop/PMS interfaces the minimum control is user logs, 06:16-07:18.
- Memory: "cloud code or codex, they use local memory, they write to your desktop. In enterprise healthcare, we can't really do this, so we do memory in a database, just so we have that logical separation," 07:23-07:38.
- Model upgrades: "you can't just replace the model and assume it's going to be better. It's different." A model that is better "on certain evals … as measured by these different metrics" is not necessarily better for the situations you need, "because of the way you've designed your system," so you "really have to redo everything from scratch" and make sure evals, testing, and validation are set up so a new model does not break the system, 07:40-08:23.
- Harness, broad definition: "all the different nuts and bolts that surround this agentic reasoning" — memory, tools, checks, permissions, handoffs, evals — "but also in the context of healthcare and claims, it's X12," 08:31-09:03.
- Why a strict standard helps: like COBOL or TypeScript, "LLMs really thrive … when they're confined, they have clear limited values that they can predict, and X12 is exactly this," providing "this contract between what you're trying to communicate and the insurance company," 09:04-09:40.
- Error propagation: a claims objective can be "like 50 steps," and mistakes at each step propagate downstream, so "it's very good to have something grounded that can be rejected to" — strict guardrails let you reject an incorrect intermediate result, 09:44-10:25.
- The balance being struck: pure agentic reasoning over 50 multimodal steps is expensive, slow ("folks might not want to wait"), and gives every step an opportunity to introduce an error; but hardcoding the whole system "limits yourself or your code can explode to be just unmanageable," requiring "a giant engineering team, which poses its own problems," 10:27-11:18.
- Memory tiers and bias: partner-level/organizational memory plus user memory. People in multi-site health organizations "tend to do the same thing day after day," so a few words plus context identify what one user probably means versus another. But persistent memory across chats and days "also introduce[s] bias" — the user may not want to do what they did yesterday and now gets steered into it — so the system must let any user break out of it, 11:19-12:33.
- Claim lifecycle, stage by stage, each with an X12 correspondence: scheduling (insurance starts before the patient shows up), treatment (which procedures the patient is a candidate for depends on insurance), documents (sometimes the x-ray itself is the document sent as proof), claim submission, and payment into the provider's bank, 12:36-13:20.
- The "obvious in retrospect" claim: calling an insurance company "boils down to a transaction, an X12 transaction" — identifying the patient is an eligibility request, a 270; a claim-status request has its own X12 grounding. So a phone call, a desktop agent, a browser agent, and an imaging attachment (275) are all the same transaction by another route; the bank/ACH leg is not X12 but is still a structured transaction, 13:29-14:26.
- The standard is public and therefore shared: "this is not my schema. If you ask agents to make a schema for you you're going to get all sorts of stuff. But now if we ground it in something standard you can look up all of these" — including a new engineer joining the team, 14:39-15:25.
- No ground truth: X12 "is a system of rules," but an X12 from a payer is not thereby true. The payer's web portal, phone system, X12 layer, and FHIR layer may each have been built by different teams or by a different contracted company. They can disagree — and "they can all actually agree on the wrong information as well": all three say the patient is covered, you treat the patient, and the claim comes back denied because the patient was not covered at that time. Over time you learn payer idiosyncrasies about which surfaces are more reliable, 15:30-16:41.
- The normalization rule: "regardless of if it originates as an X12 or not, you can boil all those transactions down to your own internal semi-correct X12. Correct until downstream evidence proves it otherwise to be incorrect" — and any payer information "any time can be wrong, it can be updated later," 16:42-17:10.
- Patient-side and evidence details: an upfront patient-cost estimate is "very important for your experience going to the doctor"; treatments performed in the clinic can themselves be the evidence a payer asks for (a CBCT and its image slices); the submitted claim is "a receipt of what you did … like the invoice," after which the ball is in the payer's court, 17:13-18:25.
- Post-submission progression: submission → a 999 acknowledging that the syntax is right → a status update confirming receipt → possibly a phone call to verify a status that never arrived → the EOB/835 recording payment, 18:28-18:55.
- Closing posture: "I'm fully AI pilled … but you should also be very AI skeptical." Models make mistakes, and "you can't even say they make mistakes — we make mistakes designing them. We might set them up to fail." They must also be used cost-effectively: an overpowered, over-expensive model on "one of these routine things that need to be done a thousand times a day" defeats the cost-reduction goal the work exists to serve, 19:00-20:02.
