## Summary

David Karam presents RAG improvement as an empirical quality-engineering ladder: start with product outcomes and query-set loss analysis, then add retrieval and ranking techniques only when observed failures justify their complexity. The ladder moves from in-memory context and BM25 through vector retrieval, cross-encoder reranking, domain-specific ranking signals, user-preference signals, query fan-out, supplementary retrieval, distillation for cost and latency, and finally product-level fallback or graceful degradation when the system cannot confidently understand the request.

## Notes

- The quality-engineering loop starts with product outcomes, a launch-quality bar, easy/medium/hard query sets, a baseline, and loss analysis before choosing retrieval techniques (01:17-03:35).
- The talk warns against starting with technique debates such as BM25 versus vector search without first knowing the query set and failure modes; "complexity adjusted impact" should favor simple fixes when they move the metric (03:05-03:49).
- In-memory retrieval or stuffing small document sets into the context window can be the simplest baseline, but it breaks when documents do not fit or the model fails to attend to all supplied context (04:10-04:49).
- BM25 is useful and cheap when query terms are explicit, while vector retrieval helps when users express the same intent in different language; the choice should follow observed query shape (04:51-06:08).
- Cross-encoder rerankers attend jointly to the query and document, making them more powerful than embedding-distance scoring, but their cost means they should rerank a smaller candidate set rather than every document (06:12-06:55).
- Standard embeddings and rerankers measure semantic similarity, but production ranking may need non-relevance signals such as price, merchant quality, popularity, PageRank-style prominence, and domain-specific vocabulary (07:02-10:56).
- User preference introduces another ranking layer because observed clicks and behavior can change which otherwise relevant result should rank first for the application (11:05-12:17).
- Ambiguous queries such as "falafel" can require fan-out across multiple backends, because the user might want restaurants, images, recipes, facts, or another intent; supplementary retrieval improves recall by searching more relevant surfaces (14:25-15:39).
- Distillation becomes worth considering when the full retrieval and generation stack is too slow or expensive; the goal is to keep the quality bar while lowering model size or latency (15:40-17:10).
- When the system cannot confidently infer intent, product design should gracefully degrade to broader choices rather than overconfidently returning one answer (17:14-19:06).
