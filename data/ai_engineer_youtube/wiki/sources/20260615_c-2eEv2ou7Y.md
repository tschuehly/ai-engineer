## Summary

Frédéric Barthelet (CTO/co-founder of Alpic, an MCP hosting company) reverse-engineers why ChatGPT renders MCP-app UI inside an iframe nested in another iframe. He frames MCP apps / ChatGPT apps as a new surface area with two properties — discoverability (store browsing plus in-chat surfacing) and an interactive UI layer rendered as "views" returned from tool calls. He then walks the security elimination chain that forces the double-iframe design: a single `srcdoc` frame shares ChatGPT's origin and content-security-policy (CSP), so app scripts are blocked by ChatGPT's per-request script nonce; relaxing the CSP lets app code read ChatGPT's origin-indexed `localStorage`/cookies; adding `sandbox` moves the frame to an opaque null origin that breaks all origin-indexed storage; adding `allow-same-origin` to restore storage is the classic sandbox escape; and pointing an iframe `src` at each app's own server would require ChatGPT to add every app domain to `frame-src`, which does not scale. A host-owned proxy domain (e.g. `openaiusercontent.com`) helps but forces the host to serve untrusted third-party code from its own domain and demands heavy dynamic-serving infrastructure. The remaining design is the double iframe: an outer frame serving one identical lightweight loader script from a controlled per-app subdomain (so origin-indexed storage never collides between apps), which injects the real app HTML into an inner `srcdoc` frame, with the app's own CSP delivered through a meta tag per the MCP spec. This is the same pattern Facebook first shipped for its app marketplace. The practical takeaway for app developers: declare every external domain your view touches (especially `connect-src` and `script-src`) in the MCP app metadata, or the host rewrites them incorrectly inside the nested frame and the app breaks or gets rejected from the store. Alpic's open-source Skybridge framework adds end-to-end type safety, host-specific polyfills, and a CSP inspector that diffs declared domains against domains the view actually calls, live in dev.

## Notes

- MCP apps / ChatGPT apps are framed as a new acquisition surface with two criteria: discoverability (browsable in the ChatGPT app store / Claude connectors and also surfaced in-chat when relevant) and an interactive UI layer added on top of text-only conversation. (00:46-01:32)
- The UI standard lineage: MCP UI was developed first (by Leat and Ido), released by OpenAI as the Apps SDK in October last year, then standardized across clients as the first official MCP extension called the "app extension." (01:43-02:02)
- Views are small HTML/JS/CSS UI snippets always rendered as the result of a tool call; tools carry metadata saying which view fits their results, views are advertised ahead of time on the `tools/list` call at conversation start, and can be cached or fetched on demand; the host creates the iframe, renders the view, and injects tool results as dynamic content. (02:02-03:31)
- Inspecting ChatGPT's DOM during MCP-app rendering shows an iframe nested inside another iframe; the same pattern appears on Claude AI. (03:31-04:31)
- CSP directives are returned as response headers on the document load; the two that matter here are `frame-src` (which sites may render iframes) and `script-src` (which scripts may run); ChatGPT requires every script to carry a per-request signed nonce. (04:31-05:30)
- Elimination chain for a single iframe: `srcdoc` shares parent origin and CSP → app scripts blocked by the nonce rule (06:22-07:42); relax CSP → same-origin app code can read ChatGPT `localStorage`/cookies and exfiltrate them (07:42-08:22); `sandbox` → opaque/null origin breaks `localStorage`, IndexedDB, and cookies (08:22-09:12); `allow-same-origin` to restore storage → classic sandbox escape back to parent DOM (09:12-09:36). (06:22-09:36)
- Using iframe `src` to each app's own endpoint would force ChatGPT to keep adding every new app's domain to `frame-src`, which is not scalable; a single host-owned proxy domain (e.g. `openaiusercontent.com`) using the subdomain prefix as a routing key avoids that, but makes the host serve untrusted third-party code on its own domain and requires heavy dynamic-serving infrastructure that non-OpenAI/Anthropic hosts may lack. (09:36-12:07)
- The double-iframe solution: load one identical lightweight script for every app in the outer frame, served from a dedicated domain different from ChatGPT; that script initiates an inner iframe with `srcdoc` holding the real app content; the outer script is served on per-app subdomains so origin-indexed `localStorage`/cookies cannot collide between apps; infra stays light because the same script content is served everywhere; and the app's own CSP is supplied via a meta tag inside the first iframe per the MCP spec. (12:07-13:39)
- This is not novel — Facebook first used the same approach for its app marketplace, which had the identical problem of rendering third-party UI inside its own app context. (13:42-14:00)
- App-developer implication: declare every domain the app depends on in the MCP app metadata so they are rewritten correctly inside the nested iframe; `connect-src` (external API calls) and `script-src` are the most important, alongside image, frame, and base directives. (14:00-14:49)
- Failure mode: OpenAI developer mode removed all CSP up to now, so missing-domain breakage only surfaced in production; the speaker reports many ChatGPT app-store rejections and production failures caused by missing CSP domains. (14:49-15:50, 19:00-19:15)
- Skybridge (Alpic's open-source framework) is a superset over the official Apps SDK: end-to-end type safety between MCP server and app widgets/views, polyfills for host-specific (ChatGPT) APIs, and dev tooling; its CSP inspector lists declared metadata domains versus domains actually called by the view and flags missing ones live as the component re-renders. (15:50-19:00)
