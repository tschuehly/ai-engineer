## Summary

Rishabh Bhargava (leads voice AI at Together AI, ex-cofounder/CEO of Refuel) walks through the production voice-agent pipeline at engineering specificity: why voice is "primarily an engineering problem today," and how to hit high quality, low latency, and reliability *at the same time* (an "and problem" across 100/1,000/10,000 concurrent calls). He frames the human-factors latency thresholds (humans respond to conversational cues in ~300 ms; users notice above 500 ms; at 1-2 s they hang up), then decomposes the dominant cascading pipeline — audio chunks → agent orchestrator (Pipecat, LiveKit, or homegrown) → speech-to-text → LLM (tool calls + text) → text-to-speech → audio back — with concrete per-component metrics and the system-level budget that ties them together. ## Notes

- Why voice / why hard: billions of human-handled phone calls a year (support, doctor's offices, being on hold) plus voice as a brand-new interface (ChatGPT advanced voice mode; people talking to Cursor and Claude Code); "this is primarily an engineering problem today." It is an "and problem": real-time latency AND baseline intelligence/tool-calling AND natural-enough pleasant voice (language, accent, name pronunciation, emotion) AND reliability across 100/1,000/10,000 concurrent calls — all at once. (01:36-04:18)
- Dominant architecture: the cascading/pipeline shape — audio chunks streamed into an agent orchestrator (Pipecat, LiveKit, or homegrown) → speech-to-text → LLM (decides tool call / output text) → text-to-speech → audio chunks streamed back. STT = "ears," LLM = "brains," TTS = "voice." (04:22-05:12)
- STT metrics: word error rate ~6% on open benchmarks for SOTA; critical that *keyword* errors (names, drug names) be right because the LLM and TTS carry the mistake forward with no way to fix it downstream. Latency metric = time to complete a transcript after the user stops speaking; Together runs models at P90 ~100 ms. (05:12-06:19)
- Turn detection: "still somewhat unsolved... could be a 20-minute talk in itself" — a pause does not reliably mean the turn ended; talking over the user is as unwelcome with AI as with humans. (06:19-07:06)
- Streaming-native STT: architectural evolution from batch to stream models. Whisper (canonical) was trained on 30-second clips — too long to wait, so people bolt on chunking, silence-padding, and multi-call stitching. A recent NVIDIA streaming encoder instead trains with variable *look-ahead* (only ~80 ms up to ~1 s of audio rather than 30 s) and caches activations so stepping forward by small audio frames only does the heavy compute once. (07:06-08:16)
- LLM metric: streaming latency / time-to-first-token; ~200-300 ms TTFT is a good target so tokens start feeding TTS fast. This budget dictates an 8-30B model sweet spot — bigger blows the latency budget, smaller breaks intelligence and tool calling. (08:40-09:13)
- TTS metrics: time-to-first-audio; real-time factor (RTF) = audio produced per second of processing (10 s audio in 5 s = RTF 0.5); keep RTF < 1 to avoid buffering. Quality is hard to measure objectively — "nothing quite beats listening to audio samples" for the voices you care about. Capabilities: naturalness across voices, exact pronunciation of names/products, emotional control (digital tags: happy/angry/sad), language coverage. (09:13-10:50)
- System budget: across the orchestrated models there is a shared latency and cost budget — the LLM takes the majority, then TTS, then STT (both latency and cost). So far the numbers are *engine* latency (model compute); *network* latency from models in different data centers adds on top. (11:08-11:55)
- Co-location: in an already-optimized pipeline (100-200 ms engine TTFT), models far from the orchestrator add ~75 ms network latency (e.g. US West↔Europe). Co-locating all models + the orchestrator in the same data center / same building drops 75 ms→5 ms = ~30% reduction. "Every 10 milliseconds matters" — needs deep observability. Q&A example: a London voice agent calling OpenAI models hosted in the US pays a trans-Atlantic round trip; running an open-source model in the same data center makes the hop intra-DC. (12:40-14:24, 17:50-19:18)
- Auto-scaling: scale up aggressively (more so than async systems) because backed-up requests are the worst outcome; scale down carefully — stateful long-lived model connections mean you can't arbitrarily kill a pod, you drain and wait for conversations to finish. Global deployments shave latency and satisfy data residency (e.g. Europe). (11:55-12:40)
- Speech-to-speech alternative: a single model does STT+LLM+TTS including function calling — simpler than orchestrating many models. Examples: OpenAI Realtime API (single model behind the scenes), NVIDIA "voice chat" (recently launched). Mostly *not* in production yet because they still struggle with instruction following and tool calling (try them → prompt-engineer → fall back to pipeline). Upside when they improve: no loss of speech nuance (tone, emotion, hesitation) that STT→text destroys, and full-duplex — produce audio while still receiving audio — enabling native backchannels ("I see," "aha") and far easier interruption/barge-in handling than the pipeline's bespoke engineering. (14:24-16:22)
- Q&A — evals: "it depends"; component-by-component evals; for tool calling, similar to general LLM tool-calling evals (was the call correct? was the output possible?) — tool-call *structure* should be near 100%, correctness is use-case dependent. To raise tool calling within the small-model budget, customers fine-tune smaller LLMs on use-case-specific data. (16:44-18:29)
- Q&A — guardrails: production pipelines grow extra models — a classifier *before* the main LLM (e.g. route to a refunds LLM vs an order-tracking LLM) and guardrails *after* LLM generation but *before* TTS. Catch violations before TTS is invoked, because spoken audio cannot be unsaid (the agent would have to awkwardly retract "sorry, I shouldn't have said that"). Each added component pressures latency; set clear per-component SLAs/budgets and scale them independently. (19:18-21:29)
- Q&A — thinker-talker pattern: a small LLM handles all conversation flow and emits an immediate filler response ("let me think about it" / "let me get back to you"), then issues a single big tool call to a much larger model (better instructions, all tools, more guardrails) whose cleaner response feeds TTS — keeping the fast path fast while still handling complex requests. (21:29-22:14)
- Q&A — speech-to-speech observability/evals: a parallel transcription model can run alongside an S2S model for auditability (read the transcript as audio is generated); evals shift from text-to-speech / text-to-text toward full-duplex *whole-conversation* metrics over longer conversations, typically layered on top of the base inference API. (22:14-24:08)
