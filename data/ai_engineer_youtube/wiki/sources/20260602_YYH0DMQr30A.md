## Summary

Kobie Crawford (developer advocate at Snorkel, the "Frontier AI Data Lab") presents a controlled experiment showing that task quality is the dominant lever in agentic RL training. Working with TerminalBench-style agentic tasks (containerized environments + a task definition, built with the Harbor framework / OpenEnv), Snorkel gates each task on four automated criteria — achievable, non-trivial, functionally correct (the logic plays as expected), and environment-reliable — calling the ones that pass "accepted" (high quality) and the rest "rejected" (low quality). Accepted tasks averaged twice as many tool calls, a lower pass rate, and more output tokens (genuinely harder), and their failures were *cleaner*: a well-specified task fails for a real reason (the model can't reach the logical conclusion), whereas rejected tasks fail for degenerate reasons — environmental problems no model could solve, spec-test mismatches (the back-end tests expect things the prompt never requested), or implicit dependencies never fed into the model's context. The headline result: holding model, compute budget, and task count fixed, an RL run on low-quality tasks improved the base model ~1% while the same run on high-quality tasks improved it ~6% — a 5x training uplift from task quality alone. The talk's frame is that "task quality and data quality are largely the same thing," and that expert-in-the-loop generation (plus rubrics and human/LLM-judge inter-annotator agreement) is what delivers quality at scale.

## Notes

- Snorkel framing: a "Frontier AI Data Lab" since 2019 whose through-line is that data quality is critical; in the agentic space "task quality and data quality are largely the same thing," and architecture/harness changes matter but data quality is still at the center. (01:07-03:11)
- Task definition = a containerized environment (reproducibility, isolation, parallel rollouts) plus a task definition; Harbor framework and OpenEnv are the cited agentic-task frameworks. (02:27-03:57)
- Four task-quality criteria verified by automated tests: achievable, non-trivial, functionally correct (logic plays as expected), environment reliable; pass all → "accepted" (usable for training/research), otherwise → "rejected." (03:30-04:54)
- To check whether the acceptance criteria correlate with real behavior, they ran the tasks with Sonnet 4.5 and Codex (auto-caption "GPT 52, 51, and sometimes 40" — likely GPT-5.2 / 5.1 / 4o; uncertain). Accepted tasks averaged 2x as many tool calls (more difficulty, more steps, more external-tool engagement), a lower pass rate (higher intrinsic difficulty), and more output tokens (more reasoning). (05:17-06:06)
- Failure-mode categorization: accepted tasks produce "cleaner failures" — failures due to genuine difficulty (logic error, incomplete task = the model not reaching the needed logical conclusion), which are useful to hill-climb on — versus degenerate failures (an environmental problem no model could solve, or a tactical context that's "just not working"), which carry no meaningful learning signal. (06:08-08:40)
- Controlled training run: same model, same compute budget, same number of tasks, trained twice (RL); low-quality tasks → ~1% improvement over the base model, high-quality → ~6%, i.e. a 5x uplift difference from task quality alone. The description states the same figures. (09:09-10:21)
- Quality at scale comes from human expertise / experts in the loop for generating RL environments and data; the platform combines human annotators with LLM judges, builds rubrics (a longer list of data points/criteria usable by both), and requires very high inter-annotator agreement both human-to-human and human-to-LLM-judge before using a signal. (10:21-10:42, 18:40-20:15)
- Benchmark-noise corollary (Q&A): unsolvable tasks that "can never be completed literally because they actually can't be" become a source of noise that *masks* whether the model actually improved — conflating task-quality issues with genuine benchmark saturation. (12:54-13:52)
- Under-specification (Q&A): a common rejected-task failure is a desired testable outcome that isn't clearly specified up front, while the back-end tests expect things "never actually requested" (spec-test mismatch), making the task only *appear* harder; or implicit dependencies in the tests that the task never specifies and never feeds into the model's context, so the model lacks what it needs. (14:19-15:17)
- Distinguish under-specified (noise) from genuinely multi-step/iterative (good): not every task is one-shot, so the fix is to make the outcome verifiable on the back end — done right, the learned skills still transfer to unverifiable or iterative settings. Verifiable domains (coding, math) are easy; "fuzzy" domains are handled via an open benchmark grants program. (15:20-16:15, 16:36-17:40)
- Snorkel publishes an "Agentic coding" leaderboard (auto-caption "genetic coding") focused on these TerminalBench-style tasks, applying the same rigor so others can see the quality difference. (11:26-11:48)
- Kobie Crawford's later, separate Snorkel talk (FinQA, [Stop Making Models Bigger, Make Them Behave](20260610_TNwJ1LMiENk.md)) shares the expert-in-the-loop + rubric-decomposition methodology and the small-model RL angle.
