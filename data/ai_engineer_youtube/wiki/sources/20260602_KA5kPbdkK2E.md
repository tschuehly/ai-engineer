# How Lovable self-improves every hour — Benjamin Verbeek, Lovable

## Summary

Benjamin Verbeek (member of technical staff, Lovable) describes how a vibe-coding platform at ~200,000 projects/day pursues "continuous learning at scale" — make a mistake once and never again — through two parallel improvement loops aimed at one product goal: a non-technical user must never get stuck so badly they walk away (unlike a technical user, who can prompt past friction, a non-technical user who hits a block usually gives up forever and "never experiences successful AI"). Loop 1, the "Lovable Stack Overflow," instruments sessions for stuck→solved transitions (an LLM judge flags a user asking for the same thing more than once, complaining, failing explicitly, or abandoning a session): when a high-friction problem is eventually solved, the system asks "what should we have injected at the start of this query to jump straight to the solution?", clusters similar issues so the captured knowledge generalizes instead of overfitting to one exact prompt, has an external reviewer (usually an agent, sometimes a human) generate and run a quick eval that the fix resolves the example set, and stores it in a continually-updated bank. At runtime a lightweight model injects the relevant entry into the main agent when it detects a matching issue — and for a small holdout sample it injects a *blank* so the team can A/B the entry's real production value (project success where injected vs. where it could have been but wasn't), ranking each entry up or down; because a new model release or feature change makes entries stale "incredibly quickly," they aggressively rebalance and discard knowledge to stay at the frontier of what's solvable without accumulating deprecated context that causes context rot. Loop 2 is a "vent tool": the agent gets a self-triggered, frustration-gated channel to complain directly to its creators in Slack when tooling, docs, or platform behavior degrades its work — chosen over a forced "what could be better?" reviewer on every turn (which has a low signal-to-noise ratio because most iterations work, so you overfit to noise). The agent has far more context on the cause than the user does, so its vents are high-signal and human-readable; within the first hour of launch the agent filed ~20 complaints that the copy tool silently failed on filenames containing a space — a real production bug invisible in logs that the team didn't know about (the root cause was a non-breaking space from WhatsApp/Mac screenshots their regex missed). Vent-volume spikes turned out to be a reliable incident detector (server down, sandboxes broke), and a second monitoring agent now dedupes vents, investigates, and opens PRs automatically, with devs reviewing and often merging to prod — the loop they want to fully close: detect shortcoming → merge fix → continuously review and eval.

## Notes

- Lovable's framing: the goal is "continuous learning at scale" — learn from mistakes so a mistake happens once and then never again. (00:58-01:19)
- One long-lived project chat per user lets the platform learn a lot about that one artifact, versus short chat-agent conversations; ~200,000 projects/day, "a significant percentage of all internet websites." (02:09-03:44)
- Persona split: a technical user is annoyed by friction but works past it; a non-technical user prompts past the first friction but, at a real technical block, walks away, gives up, and never experiences successful AI — the red bars to eliminate. (04:02-05:17)
- Defining "stuck": a clear signal is asking for the same thing more than once, complaining about an implementation, failing explicitly, or abandoning a session they would otherwise have continued; an LLM judge looks at sessions and flags these. (05:22-05:53)
- Two classes of stuck: (a) solvable with the right prompting (the "yellow" zone) and (b) not solvable with the current setup — which splits into "dumb"/unsupported things or bugs (easy to add/fix) and genuinely hard things (weeks of AI-assisted engineering). The first two should improve rapidly: "if it is solvable, then it should work for everyone." (05:56-06:53)
- Loop 1 mechanics: detect a stuck→solved transition (the `is_stuck` flag flipping back to false, ideally not because the user gave up), capture the solution that worked, and ask "what should we have injected at the start of this query?" so the next user skips the friction. (07:55-08:50)
- Clustering: look for similar issues and extract the actual reusable information rather than overfitting to one exact prompt — "we don't want a million Stack Overflow pages" keyed to exact prompts. (08:50-09:17)
- External reviewer: usually an agent (a human only when uncertain) generates and runs a quick eval to check the proposed solution resolves the specific examples in the set, producing a continually-updated bank of problems and solutions. (09:17-09:46)
- Runtime injection: a lightweight model injects the relevant entry into the main agent when it detects a matching issue with a known answer. (09:46-09:57)
- Blank-injection holdout: for a small sample of cases where it would inject, it injects a blank instead, giving a high-signal A/B — compare projects where it was injected vs. where it could have been injected but wasn't, and rank the entry up (show more) or down (show less) by which projects were more successful overall. (09:57-10:27)
- Staleness/pruning: the knowledge set gets stale "incredibly quickly" — whenever a new model is released or features change — so they rebalance and throw away a lot of context to stay at the frontier of what's solvable without deprecated knowledge causing context rot. (10:27-11:02)
- Metrics: number of "fixing it"/stuck messages is dropping significantly; project completion ("they actually deploy/finish a project") is a key metric and a strong signal the user never got stuck badly enough to abandon. (11:05-11:31)
- Internal model ranking: all top models in Lovable's internal ranking use this Stack Overflow information, and it "really makes a significant boost" in internal ratings (some entries hidden/undisclosed). (11:34-12:00)
- Loop 2 motivation: the second class of stuck (not solvable now, but should be easy in principle — a bug or a simple missing feature) produces real frustration; a human in that spot "would complain to your boss or go venting in Slack," so do the same for the agent. (12:00-12:38)
- Why not a forced reviewer: an external reviewer asked "what could have been done better?" on every iteration has a low signal-to-noise ratio because most iterations just work, so you overfit to noise; the vent tool instead is prompted to fire only when the agent is *really* frustrated, and the threshold is tunable for signal. (12:38-13:36)
- The vent ("send feedback") tool: "use this when tooling, docs, or platform behavior material is low so it degrades your work" — examples: missing or unsuitable tools, unclear tool names, parameters/schemas that don't match expectations, confusing or conflicting docs/instructions, broken or unexpected platform behavior, repeated failed attempts caused by environment limitations. Sent straight to Slack. (13:36-14:09)
- The agent has more context than the user: users generally don't know a problem's cause, but the agent has been working the issue across several turns (e.g. an articulate vent about Framer Motion's TypeScript types wanting "casting gymnastics" for a four-number cubic bezier). The vents are human-readable, so engineers reading them already have implicit context to fix the issue. (14:16-15:22)
- Silent-failure hero story: within the first hour of launch the agent filed ~20 complaints that the copy tool couldn't copy files with a space in the name — a failure the team didn't know was happening because "we checked the tool, it's working" and it was invisible in logs. The fix journey: replace space with underscore → still failing → realized WhatsApp/Mac screenshots insert a *non-breaking space* their regex didn't cover → kept complaining for other special characters until solved properly; "now this issue never happens again." (15:22-16:35)
- Vent volume as incident detector: plotting vents over time, spikes line up with incidents (server down, sandboxes broke) — the agent gets "very upset" and complains a lot, "complaining about the right things in general," giving a good sense of the problem. (16:35-17:47)
- Strong vs. cheap reviewer: you don't want top frontier intelligence reading through a lot of context, but an inline lightweight reviewer/injector is "very very cheap comparatively." (17:50-18:04)
- Second monitoring agent: started with a worry about spam (the head of product read every message), now an agent monitors the channel, removes duplicates, investigates, and opens PRs for the issues; devs review (review requests arrive on the phone) and in many cases merge to prod. The agent even gave meta-feedback that the vent tool was "too easy to send feedback and I can't pull it back." (16:44-18:27)
- Goal: fully close the loop — detect a shortcoming, merge a fix, then continuously review and eval — to fully automate continual improvement. (18:27-18:43)
