## Summary

Peter Werry frames a context engine as the reasoning and retrieval layer that gives coding agents only the organization-specific context needed for a task. The talk argues that naive RAG, more MCP servers, and larger context windows do not solve personalization, permissions, conflict resolution, stale answers, or token waste by themselves; useful context engines combine source relationships, user and team relevance, runtime retrieval, conflict surfacing, and social or expert graphs.

## Notes

- Coding agents start with no local organizational context and often spend tokens exploring the codebase before doing the task; context engineering is presented as supplying needed context while excluding irrelevant context. (01:27-02:19)
- Naive vector search or documentation RAG can lead to unsatisfied search, high token use, compaction, task-irrelevant results, unresolved data conflicts, and missing personalization. (10:51-12:12)
- A context engine should understand the user, team, collaborators, organizational experts, and prior decisions that led to the current codebase state. (15:50-16:08)
- When conflicts cannot be resolved confidently, the context engine should surface that uncertainty and learn from user input instead of pretending the conflict is resolved. (16:08-16:31, 24:04-24:39)
- Context-engine inputs can include planning tools, docs, conversations, code, and PRs; outputs can feed coding agents, MCP or CLI tools, APIs, SCM code review, and social messaging integrations. (17:42-18:19, 32:20-33:09)
- Historical PR comments can be distilled into reusable memories that tell future agents how an organization handles recurring code patterns. (19:10-19:41)
- Personalized retrieval can bias deeper search toward repositories a user contributes to frequently while searching more broadly elsewhere. (21:11-22:01)
- In one reported task comparison, the speaker says a context engine reduced time and tokens versus a run without it, but cautions that model-generated numbers in the experiment should not be trusted precisely. (22:13-23:22)
- Caching complete answers is discouraged because code, docs, and reasons change, and feeding prior bad answers back into context can pollute later outputs. (24:48-25:28)
- Context engines can be exposed through MCP, CLI, API, dashboard, and Slack surfaces; MCP is a surface into the agent flow, not the whole context engine. (32:20-33:09)
- Graph RAG-style hierarchical summarization can cross permission boundaries, so context graphs need compartmentalized pockets or equivalent access controls. (37:37-37:55)
- A context engine can combine procedural knowledge-graph construction, LLM distillation, vectorization, runtime data-fetch tools, and conflict-resolution logic rather than relying on a single retrieval method. (38:26-39:19)
- The workshop demo builds a local social graph from GitHub repository activity to identify who reviews whose PRs and which people work on which code areas. (43:31-44:36)
