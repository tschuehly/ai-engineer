## Summary

Sam Morrow describes lessons from scaling GitHub's MCP server: large tool surfaces can make agents worse, tool outputs and descriptions need token and intent discipline, remote MCP security should prefer OAuth and scope-aware access over long-lived plaintext tokens, and horizontal scale is easier when each request can rebuild the allowed tool surface from stateless infrastructure.

## Notes

- After GitHub's MCP server grew past 100 tools, agents became worse at using GitHub and exhausted context windows faster; most users stayed on defaults even when tool-set configuration existed. (02:06-04:15)
- GitHub reduced initial context by focusing default tools, grouping CRUD tools, and trimming tool outputs; one pull-request listing output lost more than 75% of its tokens after tailoring. (05:10-06:13)
- Tool descriptions should be evaluated against each other because the right description makes a tool selected at the right times and avoided at the wrong times. (07:32-08:08)
- GitHub improved tool reliability by encoding agent intent into server-side tools, accepting extra API calls inside the server to reduce client round trips, context use, and failure. (06:43-07:30)
- Plaintext MCP access tokens in local configs are often long-lived, over-privileged, and stored where agents can access them; remote HTTP with OAuth 2.1 and PKCE makes secure connection easier for users. (08:13-09:33)
- PAT-based sessions can filter exposed tools by token scope, while OAuth can return a scope challenge for step-up authorization instead of simply failing a tool call. (12:27-13:29)
- GitHub's remote MCP server is stateless, uses Redis for session storage, does not need session affinity, and builds a fresh SDK server instance with the allowed tools on every request. (13:48-15:08)
- Human-in-the-loop MCP apps can let users edit AI-generated issues before posting, which protects social and review quality for open-source workflows. (15:15-16:25)
