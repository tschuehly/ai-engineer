## Summary

Justin Schroeder (StandardAgents; creator of dmux, ArrowJS) argues that the dominant way of building agents — piling skills and MCP servers onto one large general-purpose agent's context — is an *inheritance* pattern that breaks down as context grows, and that the durable alternative is *composition*: many small, isolated, full domain-specific agents (each with its own system prompt, precise tools, message history, and agentic loop), coordinated by a top-level agent that talks to them in plain English. He reports StandardAgents sees 80%+ token efficiency per task from this shape, and that narrowing each agent's job makes very cheap small models (e.g. DeepSeek V4 Flash, ~137× cheaper than Fable 5 per task) viable, enforces strict per-agent capability limits for security, and gives excellent parallel/cloud scaling. He frames a token-cost reversal (per-token cost rising in 2026, up ~29–30% adjusted for IQ and ~76% unadjusted mid-year) as the economic pressure making this necessary, especially for customer-facing AI. The talk closes with an "ideal agent" anatomy (model, system prompt, a tool layer split into functions / prompts / full sub-agents, hooks, agent rules, a sandbox filesystem, and sandboxed code execution) and a recursive sub-agent hierarchy (coordinator → Salesforce → Workspace / asset-gen → legal → GDPR → OSHA) that keeps every context window small.

## Notes

- Agent definition offered: "deterministic software that harness the non-deterministic results produced by models in pursuit of some desired objective"; the agent/harness distinction is called pedantic and the two are conflated. 02:25-02:59
- Why everyone builds custom agents: integration — businesses want their data properly integrated into AI for competitive gains; custom agents are one of the first mechanisms teams discover. 04:47-05:15
- Why building robust agents is hard: careful agentic-loop orchestration, many provider abstractions, durable execution / fault recovery, validations and stop conditions; demos work but production doesn't. Agents are also not portable ("works on my machine" across env vars, system requirements, runtimes) and not composable (a chatbot built for one use rarely reuses). 05:15-07:32
- MCP became the de facto *tool*-distribution mechanism: on the MCP client-support matrix only the tools column is filled all the way down (resources/prompts not broadly adopted), so it moves company tools into a big general agent but "has not proven great at providing other value yet." "Tools are just not enough" — "we didn't land a man on the moon by giving one guy a ton of tools." 07:35-09:08
- Skills are markdown documentation; they help with complex tasks, but "if you use very many of these, it actually makes your agent substantially worse." 09:10-09:56
- The agent stack (model → system prompt → tools → skills → MCP → messages) is "almost all context"; people try to solve integration by working on the context or the model, which is where new tech/protocols keep appearing. 09:59-11:23
- Inheritance framing: installing more MCPs/skills inflates the context layer to give one agent more properties; it works, but 5 skills → 100 → 1000 hits diminishing returns from added context. 11:25-13:30
- Composition alternative: a tiny Figma agent whose system prompt *is* Figma expertise (APIs, clicks, mouse moves), with only the precise tools it needs and a small Figma-only message history; each domain (Gmail, travel, Sheets) is a separate isolated full agent with its own loop, coordinated by an agent above them, communicating in English like humans. 13:32-15:25
- Biomimicry / Apollo analogy: teams of experts each really good at a few tools got to the moon; the mission-control operator = LLM (brain) + dashboard (tools) + mouth (messages). 15:27-16:20
- Token efficiency: StandardAgents "regularly see over 80% token efficiency for any given task," because a sub-agent's total context is just its system message, its tools, and the single incoming message ("get that last email from Debbie") — no surrounding conversation. 16:44-18:04
- Small-model economics: DeepSeek V4 Flash vs Fable 5 is ~137× cheaper per task; small/cheap models fail if asked to do everything, but with a narrow pre-picked task and minimal context they execute faithfully. Non-language models (image generation, diffusion) can also serve as agents. 18:05-19:29
- Security/permissions: instead of bypassing permissions on a big coding agent that "can do anything," domain-specific agents can only do what is explicitly approved — a more controlled ecosystem that "puts Doug in IT's heart at ease." 19:30-20:25
- Scaling: each agent is its own small execution environment → parallelizable, easy cloud deploy without a giant VPC, thousands of instances across regions, no geographic co-location needed. 20:26-20:56
- Portability: "squeeze up" a Gmail agent and send it to someone else → an ecosystem where domains are reused rather than rebuilt per team. 16:53-17:28
- Token-cost reversal: the "cost of intelligence going down" trend reversed in 2026; tokens up ~29–30% adjusted for IQ and ~76% unadjusted mid-year (partly a memory crunch), so per-task efficiency matters. You "can't put Fable in front of a customer unless that customer has a massive lifetime value" — customer-facing AI needs efficacy plus efficiency. 22:37-24:13
- Ideal agent anatomy: model + system prompt; a tool layer split into (a) *functions* that execute effects (e.g. write a file), (b) *prompts* — smaller injectable sub-prompts, including a tool that itself calls an LLM (e.g. use Nano Banana for an image while GLM 5.2 is primary), and (c) another full domain-specific agent as a tool; *hooks* that mutate/side-effect (e.g. inject a synthetic "what time is it? / 6:45pm Pacific" tool call so the LLM knows the time); *agent rules* (max turns/steps, whether a tool call must be validated). 24:35-27:00
- Every agent should have its own sandbox filesystem and a sandboxed code-execution location (write files, run them, no exfiltration/OS interaction) as baked-in primitives — the big labs already added filesystems to make chat interfaces work. 27:01-27:56
- Recursive sub-agents: a coordinator → Salesforce agent (knows all APIs/credentials) → Google Workspace agent (spreadsheets) + an asset-generation sub-agent (Nano Banana, SVG generator, own reflection/QA) → a legal-team agent → a GDPR-compliance sub-agent (isolate ~45MB of GDPR context) → an OSHA agent; nesting keeps every context window small. 27:56-30:07
- Predictions: rest of 2026 = a rapid uptick in domain-specific-agent talk and frameworks; 2027 = "the year of multi-agent orchestration." Vercel's Eve is cited as the first framework to publicly use the "domain-specific agent" term. 21:00-22:32
