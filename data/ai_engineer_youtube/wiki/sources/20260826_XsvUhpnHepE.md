# The Missing Layer in Agentic AI — Giedrius Šteimantas, Oxylabs

Source: [The Missing Layer in Agentic AI — Giedrius Šteimantas, Oxylabs](https://www.youtube.com/watch?v=XsvUhpnHepE)
Uploaded: 2026-08-26
Transcript: `raw/20260826_XsvUhpnHepE/XsvUhpnHepE.en-orig.vtt`

## Summary

A fifteen-minute rebuild of one failing agent, told by a web-scraping vendor. A friend vibe-coded a personal shopping agent — a style chatbot that hands prompts to a second agent that finds and buys the items — and ran a browser automation framework at every stage, producing something "slow, expensive and unreliable" enough not to work. Šteimantas re-derives each of its four stages from two scraping rules: *use a browser only when you absolutely have to*, and *validate content before you spend anything on it*. Discovery drops the hardcoded retailer list for a search API returning compact JSON; the decision stage drops the browser for a scraper returning markdown that fails loudly on a block; checkout keeps Playwright MCP but swaps a hardened headless browser in behind it. The wiki already holds a dense cluster on hostile web access, and most of this corroborates it. What is new is the *unit of the decision*: existing pages escalate technique within a single page interaction, this one selects a different access primitive per pipeline stage, and it supplies the cost-side reading of a silent block — an unvalidated CAPTCHA page is not primarily a hallucination risk, it is a bill. Everything demonstrated is the speaker's employer's product line, no before/after is measured, and the headline 70% figure is arithmetic from a hypothetical, not an observation.

## Extracted Concepts

- [Assign a Web-Access Primitive Per Pipeline Stage](../concepts/assign-a-web-access-primitive-per-pipeline-stage.md) - the talk's structure is one agent's four stages, each re-solved with the cheapest primitive that works for it.
- [Validate Retrieved Content Before Spending Tokens on It](../concepts/validate-retrieved-content-before-spending-tokens-on-it.md) - "HTTP response 200 does not mean that we are good to go," and the 70%-wasted-tokens arithmetic that follows from checking status and size only.
- [Fail Loudly and Bill Only for Successful Results](../concepts/fail-loudly-and-bill-only-for-successful-results.md) - a blocked fetch returns an explicit error instead of the block page, and the vendor charges nothing for it.
- [Keep Geolocation Consistent Across Pipeline Stages](../concepts/keep-geolocation-consistent-across-pipeline-stages.md) - the discovery stage without geolocation produced items that were unavailable at checkout.
- [Keep a Protocol Boundary So the Browser Backend Stays Swappable](../concepts/keep-a-protocol-boundary-so-the-browser-backend-stays-swappable.md) - Playwright MCP stayed, and the hardened browser went in behind it as a drop-in replacement.

## Notes

- The failing system: a chatbot discusses style, picks items, and "produce[s] prompts that a shopping agent would then take and attempt to find them online and purchase them." It was built fast — "he vibe coded the whole thing while having a[n after]thought about infrastructure and underlying layers and how it should work. I didn't at all" — and "was using a browser automation framework for everything and it was slow, expensive and unreliable." The result: "a product that does not work and is expensive to run." (00:30-02:11)
- The diagnosis is a missing layer, not a missing capability: "he was missing something… an infrastructural layer that would allow this agent to operate freely on the open web." (02:11-02:32)
- The two operating rules, stated as scraping-industry principles under the heading "cost matters": "use a browser when you absolutely have to," "validate content — HTTP response 200 does not mean that we are good to go," and "lighter content is preferred" because HTML, CSS, and JavaScript carry "a lot of bites that do not deliver any value whatsoever." (02:59-03:45)
- The four stages: discovery (find product pages), decision (visit them, confirm stock, price, description fits the prompt), a user confirmation, then execution (make the purchase). "Sometimes it worked and sometimes it did not." (03:45-04:47)
- Discovery on a browser failed six ways at once: the automation tool "lacked what we call stealth" so it drew CAPTCHAs and outright access failures; retries made the flow long and costly; cost per transaction became unpredictable; the hardcoded site list meant "selection of items would only be limited to the few choices he put in"; JavaScript-heavy pages made it slow; and with no geolocation, "items ended up being unavailable at checkout" because e-commerce sites vary stock, sizes, and options by user location. (05:05-06:30)
- The replacement is a search API rather than a browser: "a compact JSON which is less than 2,000 tokens per response," "less than 700 milliseconds on average," a high success rate at a predictable low price, and reach into search engines where "all of these websites have been indexed already a long time ago." The agent then "formulates fan out queries and selects the relevant URLs from search results," and because responses are small, "there's no need for complicated models" at this stage. (06:30-07:56)
- The decision stage is where the token argument lands. Running many parallel browsers did produce results, but many came back blocked, leaving the agent "with very few choices with the majority of popular retailers being left out." The friend caught it only because "he did well with observability"; the common case is worse — "what we see when working with these types of customers is that they often fail to detect the failure. They end up checking only the content size and HTTP response code and then feeding this large HTML to an LLM." (08:19-09:22)
- The cost arithmetic, and the reason the model does not save you: "a large language model of course can distinguish between valid shop content and a capture. But we need to spend tokens in order to do that. And when we attempt to open 10 websites, but only three return valid content but feed all of the 10 to the model, it is a problem. It means that we waste 70% of the tokens." (09:22-09:44)
- The wrong fix, named explicitly: "My initial hunch was to compress the output. But then I thought — wait, the problem is not the compression. The problem is that the content is not valid. We need to make sure that the content is valid before even attempting any compression. This will lead to more options for the agent to choose from and fewer wasted tokens." (09:44-10:29)
- The rebuilt decision stage, without a browser: only valid content is returned; "in case of captures or other blocks the request would fail with an explicit error message. So I know not to include it when sending to a large language model"; it is "a lightweight REST API" so "I can run hundreds of requests in parallel"; it "supports markdown. So no need to submit raw HTML"; it "runs a full browser under the hood" when the site is dynamic; and it "supports geolocation options." (10:29-11:30)
- The billing model is presented as the best part and it is a contract, not a discount: "customers only pay for successful results… No cure or no pay. If the scraper fails, there's no cost and it fails loudly." (11:30-11:54)
- Checkout is the exception the rules are built to protect: "this time you absolutely need to use a browser. We need to process inputs and the content is highly dynamic." Both implementations use Playwright MCP with a browser and an LLM; only the browser behind it differs. (11:54-12:37)
- The swap: "I just connected Oxylabs' headless browser — since it supports Playwright MCP it's just a drop in replacement," bringing "proper stealth done at the browser source code level, a residential proxy attached to it out of the box, and… a geolocation capability. So my results are localized the same way as in the verification stage." (12:37-13:20)
- Closing lessons: "use the browser when you absolutely need to. You have to validate content before feeding it to the large language models and most importantly fill the missing layer with the proper infrastructure so you can focus on building stuff. But remember cost matters." (14:03-14:35)
- Reading caveats. Every replacement primitive is an Oxylabs product, and no measurement compares the two implementations end to end: no per-transaction cost, no success rate, no latency for the rebuilt pipeline as a whole. The 2,000-token and 700-millisecond figures are product specifications the speaker states, not results he measured on stage. The 70% figure is arithmetic over a hypothetical 10-page fetch with 3 valid responses, not an observed waste rate. The "high success rate… even for protected websites" claim carries no number at all.
