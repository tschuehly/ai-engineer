# Anthropic's Applied AI team on the Evolution of Agentic Surfaces

## Summary

Gagan Bhat and Isabella Kai He of Anthropic's Applied AI team trace the surfaces a developer can build an agent on — the Messages API ("simply tokens in and tokens out"), a hand-rolled agentic loop, the Claude Agent SDK (the Claude Code harness packaged: loop, filesystem, tools, sandboxing), and Claude managed agents, where Anthropic runs everything below the product — and use the ladder to argue about where the buy boundary should sit. The concrete form of that argument is a six-question checklist of what production forces on you regardless of surface: hosting and scaling, session management, filesystem, execution isolation, credentials, and observability.

The organizing claim of the talk is one sentence: "harnesses encode assumptions about what Claude cannot do on its own… they have to be questioned frequently because they go stale as models improve." The worked instance is the most useful thing in the talk because it has a named cost on both sides. Sonnet 4.5 "literally got anxious as it approached its context window limit," wrapping up tasks early "even when it actually had room left to spare"; the team added context-reset machinery to the harness to compensate. Opus 4.5 "no longer exhibited context anxiety," and the same machinery "became dead weight. In fact, it became pure overhead, adding things like latency and causing issues with the cache being discarded incorrectly at times." The generalization they draw — "when the model moves and the harness doesn't, it degrades the agent" — cuts in a direction worth noting: a model lab is arguing that the harness, not the model, is the binding constraint, closing with "harnesses have become the limiting factor to what models can achieve."

The architecture half is a decoupling story. The managed-agent design originally put the agent loop and the tool-execution container in one box; "the container was blocking the agent being able to start its model reasoning," and "if one part of this component went down, the entire box of the agent would go down." Splitting the brain from the hands bought three things: container setup runs in parallel with (or is skipped ahead of) first token, giving a reported "60% faster time to first token for P50" and "over 90% improvements in latency for time to first token in P95 use cases"; a dead sandbox no longer kills the run, because "the brain could just spin up a new sandbox and retry and then continue as it left off"; and a dead brain is recoverable because the session is "a durable resource persisted in the cloud." That last piece is the context-engineering contribution: "with many traditional harness implementations, the context window and the session are one in the same," so a mid-run discard loses the run, whereas a separate session log means "the harness can actually just read in slices of that context from the session log into its current window."

The primitives are agent (model, prompts, tools, skills), environment (a container definition, with each session getting "its own isolated container instance"), and session (agent + environment, with four states: idle, running, rescheduling, terminated). Security appears as two placement decisions rather than policies: credentials live in vaults "decrypted only when needed at tool execution runtime," so "the model never sees your security tokens" — which is only possible because tool execution left the model's process; and private MCP servers are reached by tunnels that "run only within their private network and only making outbound calls to the Claude agent loop," inverting which side has to be exposed. A semi-interactive SRE demo (P99 latency "10x over baseline," an environment with "networking limited and allowed hosts only being the MCP server") shows the pieces together. The frontier list closes it: scheduled deployments, self-hosted sandboxes in the customer VPC, multi-agent orchestration, **dreaming** (a periodic batch pass over session transcripts plus current memory that edits memory so "the next day's agent sessions [are] automatically much more intelligent"), and **outcomes** (a user-defined rubric plus "a separate grader agent that runs alongside your agent loop" that "will keep trying until it reaches that success criteria").

## Provenance and Caveats

- This is an Anthropic vendor talk for Claude managed agents, given by the Applied AI team. The architecture is described as Anthropic built it, and every reported benefit is a benefit of the product being announced. There is no comparison against any other hosted agent runtime, and no pricing appears anywhere in the talk.
- **The latency figures are the only numbers in the talk and they are unmethodized.** "60% faster time to first token for P50" and "over 90% improvements… in P95" are given with no workload, no baseline configuration beyond "the coupled design," no sample size, no date, and no absolute values — so a 90% P95 improvement could be seconds or minutes, and the reader cannot tell whether the comparison is against a tuned coupled implementation or a naive one.
- Context anxiety is reported anecdotally. No eval, frequency, or task distribution is given for the original behavior, no measurement is offered that the harness fix helped, and the overhead it later imposed ("latency," "cache being discarded incorrectly at times") is named but never quantified. The story is a well-shaped illustration of a real dynamic, not evidence of its magnitude.
- The specific model versions in the anxiety story are partly unreadable in the captions (see below), so the page states the dynamic rather than pinning behavior to an exact release beyond what is legible.
- **Dreaming and outcomes are announced, not evaluated.** For dreaming there is no evaluation of whether rewritten memory improves outcomes, no cost accounting for the batch pass, no conflict-resolution or rollback policy, and no statement of what happens when the rewrite is wrong. For outcomes there is no iteration cap, no cost bound, no discussion of what stops a rubric the agent cannot satisfy from looping, and no treatment of the rubric itself being wrong.
- The demo is described by the presenters as "a semi-interactive demo." The incident, the logs, the dashboard, and the deploy history are all staged, so it demonstrates the wiring rather than the agent's diagnostic ability on a real unseen incident.
- The security claims are architectural descriptions, not verified properties: "the model never sees your security tokens" holds for the described flow, but the talk offers no threat model for a compromised tool, a malicious skill, or exfiltration through an allowed host, and the egress allowlist is presented as a demo configuration rather than a default.
- The "harnesses are the limiting factor" thesis is worth recording partly *because* of who states it — a model lab arguing that the constraint is above the model — but that framing also happens to sell a hosted harness.
