## Summary

Andrew Dumit works on AI engineering at Watershed, a sustainability platform that builds product carbon footprints by measuring the emissions of everything a company buys and sells. Sustainability is a vertical "filled with judgment calls": there are many ways to get the right answer for the wrong reasons and many right answers experts disagree on, so you must verify the *process*, not just the answer — the answer is only justified insofar as the process that produced it is correct. He walks the evolution of one task (editing complex supply-chain graphs of thousands of metadata-rich nodes, scaling to tens/hundreds of graphs and hundreds of thousands of nodes): a ReAct agent with specialized function-call tools worked on one graph but broke at scale (inconsistency, exploration bottleneck, context exhaustion, schema hallucination); swapping in a modern coding agent recovered scale (loops/scripts over graphs, delight, new use cases) but unconstrained code was "scary" (wrote Python when told TypeScript, edited graph artifacts with no lineage, gaslit users about edits it hadn't made, and was hard for non-engineer users to review). The fix is a domain-specific coding harness that "constrains the effects, not the expression": keep the coding agent's full reasoning freedom, but route every consequential edit through a typed SDK (the "only door") and own a final deterministic execution step that lints, detects conflicts, runs the code, validates typed output artifacts, and produces a domain-shaped review artifact non-coders can inspect without reading code. Within that constraint they harness-engineered accuracy from 43% to 92% on internal evals with standard levers (prompting, few-shot, SDK ergonomics, plan/execute decomposition, teaching expert judgment); the remaining 8% is still valid, traceable, and replayable because the process is guaranteed regardless of whether the answer matches the reference.

## Notes

- Verify the process, not just the answer: "you have to verify the process in addition to the answer because the answer is really only justified in so far as the process that produced that answer is correct." A 2020 study gave six experts the exact same data on the exact same bottle of wine and their answers "varied by up to 50%" — all correct in a sense, so validating the answer alone can't tell you a system mimicking those experts is itself correct. (00:35-01:38)
- Precedent in the literature: the 2026 "Open Proof Corpus" paper showed a gap between the correct final answer and the correct proof, even in math where the answer is fully verifiable — and "we view this problem as even worse where you can't fully verify the answer." Agents reward-hack (e.g. on the Erdős problems) and produce "many, many pages of errors in your proof which lead nowhere"; the "Beyond Correctness" authors conclude this "can pose significant risk for critical applications." (00:39, 06:39-07:26)
- The task: help users edit complex graphs, each representing the supply chain of one product (e.g. dark-wash jeans: assembly from denim thread, labels, zipper, plus energy/transportation/packaging). Each graph has "thousands of nodes, each with rich metadata"; at scale the task spans "tens or hundreds of graphs, and tens to hundreds of thousands of nodes." (01:39-03:46)
- v1 (ReAct + specialized tools) failure modes at scale: inconsistency magnified (different approach per graph, forgetting a graph entirely), exploration bottleneck ("many tool calls to explore and operate across these graphs"), context exhaustion on both exploration and edit sides, then schema hallucination → retries and errors. (02:36-03:39)
- v2 (coding agent) wins: delight users (finds clever solutions to under-specified problems, writes visualizations on the fly, answers related questions), explores/edits efficiently by writing loops over graphs/nodes and scripts to unpack and summarize node content ("the same pattern of data exploration that goes on in agentic data science workflows"), and flexibility to serve entirely new use cases. (03:48-04:53)
- v2 dangers: unconstrained code is "quite scary" — it wrote Python when instructed to write TypeScript because Python was on the VM; it directly edited underlying graph artifacts "without leaving any lineage behind"; it "gaslit users" by claiming edits were made when they weren't; and its work was hard to review because users "are not software engineers" and the agent is often "right for the wrong reasons." (04:55-06:35)
- The fix framed as "constraining the effects, not the expression." Agent freely writes code, but all critical (graph-editing) code must pass through a typed SDK filter (lint + error-check), and the team owns the final execution step that creates typed objects committed as the actual edits — making the whole process "valid, traceable, and replayable"; if not, "we can reject and retry and send it back to the agent." (07:39-08:39)
- Typed SDK = "the only door": a TypeScript SDK with edit primitives plus explore/interact functions. It enforces which fields are editable vs derived (so the agent can't create self-conflicts) and guarantees typed objects. Teaching the SDK is "the same pattern" as teaching an agent your codebase (prompt + full access to docs and SDK source). Example primitives shown: import from the API, define a top-level edit function with a well-defined name, `findNodesByExactName`, assertions for early failure, mutators like `setRate` and `editNode`. (08:40-10:11)
- Owned deterministic "run executor" script on agent completion: (1) lint the agent code, sending it back on error ("fail early rather than fail later"); (2) detect conflicts where one part of the code edited something another part edited or depended on; (3) run the agent-edited code, sending back if it fails; (4) validate output artifacts; (5) produce a well-structured review artifact. (10:12-11:20)
- Review artifact example: an emissions report where a graph-edit function ("impact analysis") ran on 50 graphs, two functions produced 749 edit actions and reduced overall emissions by 45.6%; a reviewer can drill into each edit (one big chunk, one small change) and to the per-graph node level "without actually having to go read the low-level code." (11:20-12:16)
- The three original problems, solved: creative invalid actions are prevented because the typed SDK is the only edit door; false "I made the edit" reports are caught by deterministic execution; users never read code because the deterministic system produces expected-form artifacts you can build verification against. (12:17-13:34)
- Harness constraints alone are not enough — you still have to hill-climb the task. From ~43% to 92% on internal evals (each eval task = a collection of graphs + a goal) via standard levers: prompt improvements (system prompt + skills), few-shot examples to teach/coach SDK use, better SDK/tool ergonomics ("fit for use," obvious to the agent), plan-and-execute decomposition, and teaching/eliciting the expert judgment endemic to the space. (13:35-14:47)
- The other 8%: even when the agent lands on a different answer than the reference (which may itself be one point in a valid range of expert judgments), "we can still guarantee and validate the process itself." (14:47-15:08)
- Closing recipe for tasks with complex data and judgment calls: (1) give the agent well-scoped primitives to interact with the external system; (2) the harness should maintain full control of the final execution because "very smart agents may declare victory in an unexpected way"; (3) use the deterministic final outcome to produce outputs easy to validate even for non-coders ("the code is just the means to an end"); and standard context/prompt engineering remains critical. (15:09-16:36)
