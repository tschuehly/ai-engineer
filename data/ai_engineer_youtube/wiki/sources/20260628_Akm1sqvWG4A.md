## Summary

Abed Matini (senior backend developer, Ogilvy) live-demos a framework-free, fully local RAG chatbot (an HR FAQ assistant) built on Python/FastAPI, React, PostgreSQL, Docker, Ollama, Docling, and Langfuse, running on GitHub Codespaces with no GPU. His headline argument is the "multimodal tax": drag-and-dropping a raw PDF/Word/image into a cloud chatbot spends tokens on document processing before any question is asked and hides how the document was chunked and read (bad table extraction → hallucination). The fix is to structure documents offline first — Docling converts files to Markdown on local CPU, you control chunking, and the prompt becomes cheap (or free when run locally). The talk walks four chunking strategies chosen per document type, hybrid keyword+semantic retrieval with RRF and a reranker in Postgres, deterministic Python functions instead of LLM-agent loops for speed and testability, guardrails enforced in code before the LLM, Langfuse telemetry for the chat widget, and the finding that once data is vetted the smallest model (Qwen 2.5 0.5B) suffices and safely abstains instead of hallucinating.

## Notes

- Two problems motivate the talk: (1) uploading documents to a cloud LLM spends tokens on processing before any question, and (2) stacking vector search, keyword search, and many tools into a production chatbot becomes hard to manage. 01:07-02:35
- Stack: Python + FastAPI (backend), React (frontend), PostgreSQL (vector DB), Docker (reproducibility, runs anywhere incl. Codespaces), Ollama for local chat + embedding models (no GPU, CPU is enough on any staging server), Langfuse for telemetry. Whole codebase pulls from the repo and runs with one command on GitHub Codespaces. 05:51-06:57
- End-to-end blueprint: source documents → Docling converts raw files to Markdown → chunk into PostgreSQL (with embeddings) → user query retrieves top-ranked chunks → LLM answers in the chat widget → observe in Langfuse. 06:59-08:08
- The "multimodal tax": drag-drop upload into a cloud chatbot both spends ingest tokens up front and hides chunk quality (you don't know how a table was read → risk of low accuracy and more hallucination). Structure-first uses local CPU: Docling → Markdown → known/controllable chunking → cheaper prompt, or no cost when fully local. For 1-2 pages the cost is negligible, but 200 pages × many employees re-asking makes naive upload expensive. 08:14-10:29
- Four chunking strategies, chosen per document: heading-based (Docling finds each heading; heading+answer becomes a clean, traceable chunk — best for FAQ Q&A), paragraph-based (each paragraph is a separate chunk regardless of headings), fixed 512-character with 64-char overlap (32 + 32 across boundaries; for unorganized/random data), and sentence-based (chunk by sentence count). Naive whole-handbook upload produces meaningless chunks (acknowledgement, signature, date) that slow answers and increase hallucination. 10:46-21:40, 25:28-26:05
- Ad-hoc images/screenshots (e.g. an emailed maintenance-window notice) are handled by an image→text model → `.md` → sentence-group chunking, then indexed into the knowledge base so employees can ask about it; the answer cites the uploaded screenshot as its reference. 21:40-25:32
- Turning FAQ source data into explicit question/answer pairs makes it easiest for the system to digest and gives clean, correct references; every retrieved answer shows the exact source chunk it was generated from, so failures are debuggable (you can see which chunk was or wasn't retrieved). 11:44-17:57
- "Agents" here are plain Python functions, not LLM calls: chosen for speed on local Ollama (no 20-30s multi-agent loops that lose user interest), full control, no hallucination, and coverage by a test suite. Anything a Python function can do (current date, product calculations) is done in code; only one natural-language LLM call runs. Toggleable in settings. 26:17-29:22
- Hybrid retrieval: pgvector nearest-neighbor semantic search (cosine distance clusters similar meanings) plus BM25 keyword search for exact matches (product name, SKU, brand, medication, ID, language filter) — semantic returns "close," keyword returns "exact," and medical/product chatbots need exact. 29:22-30:37, 31:16-32:44
- Ranking: RRF fuses the vector and BM25 candidate sets and a reranker rescores to return the top-N; top-K is tuned by use case — products retrieve more (else same-brand products never surface/sell), medical retrieves fewer (accuracy and liability); default here is top-2. 30:37-34:25
- Direct RAG (fixed embed-query → hybrid-retrieve → answer pipeline) is preferred when compliance matters and keeps the path clear; agent mode adds tools (search, compare-product) that fetch more information but are slower, less controllable, and lose the clean referencing. 34:25-35:32
- Langfuse telemetry (fully local, no external calls): per-conversation IDs, model used, top-K answers, number of chunks returned, latency in ms, sessions/users, and cost estimation when external models are used. 35:32-37:15
- Guardrails live in code, not a long prompt: the system prompt stays tiny while do's/don'ts are enforced in Python, and risky queries (medical escalation, prompt injection) are blocked before ever reaching the LLM via intent rejects, term dictionaries, and an LLM classifier — giving rigid, testable, deterministic blocking ("this is what I block and why"). 37:15-40:20
- Models: only two are needed — a smallest chat model (Qwen 2.5 0.5B instruct, ~400MB; started at 7B but it was slower and too wordy) and a small embedding model (BGE). Finding: you don't need the biggest model — if you vet/clean the data before sending it, the smallest model gives good answers, less hallucination, and safely says "I don't have that information" rather than making things up, which is itself a form of guard-railing. 42:08-44:02
- Key takeaways: structure Markdown first (Docling does the heavy lifting), store everything in Postgres vector DB, use no paid framework (Ollama for chat, Langfuse for free telemetry); the pattern generalizes to product catalogs and customer-service chatbots. 44:31-45:16
