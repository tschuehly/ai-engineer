## Summary

Michal Cichra (Safe Intelligence; previously Microsoft and Red Hat, 10 years on one product) argues that humans and LLMs share the same weakness — limited context (people forget / LLMs compact; humans leave / LLMs have no memory) — so a team must *capture decisions* in durable, enforceable artifacts rather than trusting anyone to remember why the code is shaped the way it is (the five-monkeys parable: rules persist after everyone who knew the reason is gone). His method has four layers. (1) **Decision documents**: an ADR (architecture decision record) records *why* a rule exists and *how* it is enforced; a PRD (product requirements document) is a lighter per-feature note capturing why/problem/goal/the user journey; both serve agents and "you 6 weeks from now." (2) **Executable verification with BDD/Cucumber**: spec-driven development leaves a loop open — you have a markdown spec but no proof the product behaves that way, and "one thing harder than reading AI code is reading AI tests" — so readable, executable BDD scenarios linked to PRDs and critical user journeys close the gap. (3) **Structural prevention via module-import linting**: forbid the imports that would make a failure class possible (templates can't touch the database → no N+1 queries ever; the E2E suite can't import any DB-touching module) because "what you cannot find, you cannot enforce" and you must prevent problems entirely, not keep finding them. (4) **Enforcement in the loop, not the prompt**: rules live in git hooks, CI, linters, and skills, so an agent that skips them gets caught at commit, is linked back to the ADR, and iterates — which is why his sessions survive 20–50 context compacts ("I have no fear of context compacts") and run autonomously for hours.

- Framing: humans and LLMs suffer the same trait — limited context. People forget; LLMs compact. Humans leave; LLMs have no memory. So decisions must be externalized. The five-monkeys parable illustrates rules surviving without anyone remembering why. 01:27-01:36, 01:00-01:23
- After a while a team asks "why do we have this flow? why is this code shaped like that?" and the founding engineer may not be available to answer — these problems show in every org, sooner with AI. 01:40-02:00
- ADR (architecture decision record): records *why* you do something and *how* you enforce it; can cover examples by reference docs and code snippets; not a fixed format, just a concept (text). Example: split code in layers to prevent N+1 queries, enforced by linting module imports; reads from the database return plain shapes instead of ORM objects so those queries cannot be made and duplication is prevented; ~50 ADRs define the product's architecture. 02:03-02:47
- A text ADR still needs a *tool* to enforce it; the tool tells you the rule, why it exists, and how to fix it, and the agent goes and finds the document for more detail. You can scope an ADR to which files/folders it concerns and how it is enforced. 02:47-03:26
- PRD (product requirements document): lighter, for building a feature — describes why it exists, what problems it solves, and how the user journeys through the app; can be very light (capture why, the problem, the goal, and the journey that connects them); for agents *and* for you 6 weeks from now when you forget why you did it. 03:26-04:07
- BDD (behavior-driven development): spec-driven development leaves a loop open — a markdown spec describes how it should work, but how do you know it actually works like that? "One thing harder than reading an AI code is reading AI tests." An intermediate layer describes behavior in human language. 04:07-04:46
- Cucumber: "almost forgotten, suddenly useful again." Executable and readable, easier to review than your average tests; connect scenarios directly to PRDs and critical user journeys; closes the loop spec-driven development leaves open. Specs are parsed by steps and executed as code, but you can write, read, review, and understand them — the language is on you, and scenarios refer back to the docs about why things exist. 04:46-05:59
- Bonus — consistent UI with agents is "another level of hard"; design system + pattern library are the way (before AI and now): document your language (a primary button is blue, this shape/color/size), state your rules ("only one primary button visible on a page at any point in time"), define components/patterns with previews and snippets that you and the agents can see, review whether they adhere to principles/visuals, then build from small pieces, compose, and reuse — otherwise chaos like with code; enforce e.g. no inline styles anywhere else. 05:59-07:18, 12:08-12:19
- The loop: git hooks, skills, CI, and linters plus other checks. The agent's goal is to deliver a pull request, which forces it to use git, so git hooks run predefined tasks; the same tasks run on CI, so a lazy agent that skips them gets caught. Checks include linting, formatting, type checking, code duplication, architecture checks, and document linting — "everything that's possible." 07:44-08:23
- Code reviews used to be about style, tabs, and spaces; there is no space for that anymore — those are rules: enforced, automated, not for discussion. Review is now about high-level concepts. 08:23-08:43
- "What you cannot find, you cannot enforce." Enforce architecture by separating modules and their imports (what you can use from where): the E2E BDD test suite cannot access the database, so it is forbidden from importing any module that could, forcing it to iterate without the database using only the application's browser features; in the product, rendering templates cannot talk to the database, so there are no N+1 queries ever. "We just define ways to prevent these problems from happening ever. You cannot keep finding them. You need to prevent them entirely." 08:43-09:36
- When the agent tries to commit/push, it gets feedback, gets rejected, gets linked back to the document, reads it, fixes it, and iterates. 09:36-09:50
- The loop (do work → push → get feedback → iterate) is generic, but skills change its *focus*: an ADR skill that looks up ADRs and the code they affect, a PRD skill, a UI loop that skips a bunch of checks and instead forces fast iteration in a browser, a test skill that identifies which tests to run from code coverage and file changes (a focused subset, not the whole suite), and a goal-execution skill that records the decisions the model makes for later review. 09:50-11:04
- Drawback: it is very context heavy — you can burn half the context just starting the research. But "I have no fear of context compacts"; sessions run 20–50 context compacts and it's okay because the important things survive and the agent will always look them up again. The goal anyway is multi-hour autonomous sessions with a clear goal where the agent operates within the rules you define. 11:04-11:44
- Closing: capture decisions you can record, executable BDD specs you can read/review, design systems for consistent UI, and a harness to loop it all together. "May the spec be with you." 11:48-12:29
