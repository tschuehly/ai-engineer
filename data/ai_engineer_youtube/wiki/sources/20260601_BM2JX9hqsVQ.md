## Summary

Remy Guercio (Tailscale) argues that "sandbox" conflates two separate things — a boundary (execution isolation: a thing in, a thing out) and a set of permissions/identity (access control) — and that the standard way of handling the second is broken: you put the credential *inside* the box. Whether that credential is an API key (what the model labs prefer; you pay full price and even a synthetic key gets misused by a model run long enough in a loop) or an OAuth/OIDC login, the agent ends up holding something it can exfiltrate, misuse, or escalate. His alternative is to move authentication and authorization to the network layer. Tailscale (built on WireGuard) attaches verified identity — the logged-in user, SCIM-synced groups, or a tag / set of tags — to every connection, so you can govern who may even talk to a service and the receiving side learns who is calling, replacing "IP address + API key." Built on that, Aperture is an LLM gateway: a single provider key (Anthropic/OpenAI/Gemini/Vertex/Bedrock) lives on the gateway node, and the sandboxed agent gets a placeholder (a literal dash) instead of a real key — "nothing to exfiltrate," and revocation can't be routed around because there is no working credential to fail over to. Because every model call must traverse the gateway, Aperture sees every tool call, bash command, and MCP request without instrumenting inside the container, and adds cross-provider budgets, quotas, and guaranteed webhooks. The same identity primitives are open-sourced as **tsnet** (a Go library) so teams can build their own identity-aware internal MCP servers/APIs; Aperture itself was deliberately built only on public primitives so anyone could reproduce it. A key empirical aside: they chose the LLM layer over the MCP layer precisely because agents increasingly bypass structured tool calls for code/bash — and internally at Tailscale, **bash dominates** structured tool calls.

## Notes

- Sandbox has two components: a boundary ("a thing in and a thing out") and a set of permissions/identity ("a sandbox without any toys" if there are none). The usual VM-vs-container debate is about the boundary, not the access control. 00:46-01:46
- Permissions are handled one of two ways today, and both put the credential in the box. (1) API keys — "what the major model labs would really like you to do": you pay the full price, and it doesn't address authN vs authZ, it's just "here's a key, it lets you have access"; even a synthetic key gets misused because "models are very clever at doing things with keys they maybe shouldn't, especially if you run them in a loop for a very long time." (2) OAuth/OIDC — "the more cost-effective way" to handle permissions, but the agent still logs in and the account "hangs out over there in the corner" inside the box. Either way "the agent has access to its own permissions." 01:52-03:18
- Network-layer alternative: WireGuard (what Tailscale is built on) gives keys to any node on a network; Tailscale layers identity on top. On a tailnet, each direct connection (container, GPU server, laptop, phone) carries the user (if logged in), the groups (e.g. SCIM-synced engineering org), or a tag / set of tags (e.g. "the PR review bot for this project"). You can govern network access by that identity ("you can't even talk to something if you don't have a certain set of permissions") *and* the receiving side gets the full identity — replacing the old "IP address plus an API key." "The connections happen with identity." 03:18-05:30
- Aperture is an LLM gateway built on this. Put a single provider key (Anthropic/OpenAI/Gemini/Vertex/Bedrock) on Aperture, which is "just a node on this network," so it sees the identity of everything talking to it. On the other side "there's actually no key" — the runner connecting from the sandbox "has no key to accidentally exfil or share or do something with." 05:42-07:10
- GitHub Actions runner example: use GitHub's federated OIDC; when the runner spins up it gets access into the tailnet and a tag, and that tag "is what determines what it is able to do." 06:05-06:55
- Visibility demo: as a logged-in user on the corporate tailnet you see per-identity usage — tokens, models, money spent per model, and every request through the gateway including full request/response headers and bodies ("this is everything that Claude code sends at the very beginning"). Drill into a session; a "say hello" with Claude Code's full context cost 20 cents. 07:28-09:38
- PR review bot (a "dog food" tag) example: 30 days of every request; one ran "three commands at the same time" for 4 cents; you can see all the bash commands. "I have a sort of a guarantee I've seen every tool call this thing has ever made" — "not happening from inside the container... not from the harness." Example trajectory: MCP tool call to update the code review, some bash, some grep, then re-update the comment. 09:38-11:13
- Network-layer revocation: because it's enforced at the network, "the moment you say no" the agent can't fail over — it's not "the key no longer works, let me go to this other endpoint... I would want to be very helpful here"; "it's just a dash." 11:13-11:46
- Agent setup is minimal: run the agent in API-key mode with a dash (so it doesn't complain there's no key) plus the gateway base URL; works across Claude Code, Codex, Gemini CLI. (Demo: a "10-word story" prompt that was "about robots" 3 weeks ago, then dogs, then cats — an offhand model-eval signal; shown on "Opus 4.6 1 million context.") 11:46-13:27
- Cross-provider controls at the gateway: budgets that work across every provider ("not 'here's a thousand dollars for everybody'... here's just a thousand dollars and you can decide how to use it"); quotas ("$5 a day"); and webhooks fired per tool call to a third party with all the tool-call info — "guaranteed to exist and run no matter what" because everything passes through. Quota permissioning can mix team and individual budgets and can say "use as much as you want of the internal GPU... but if it's Opus 4.6 you only get this amount." 13:59-15:35, 20:25-21:28
- tsnet: the Tailscale identity primitives are available via an open-source Go library, so you can write your own program that joins the tailnet and reads the same identity. Build an internal-only MCP server or API endpoint without "thinking about OAuth or opening it up to everybody" — "who made this request?" and force that identity into whatever you're proxying. Self-imposed charter: Aperture had to be built only on public primitives (not private API endpoints), "so in theory you could go build [it] too." 15:35-16:55
- Q&A — configuring permissions in two places: (1) Aperture "grants" (who it applies to; model access and quotas, MCP access, hooks, roles; groups coming soon), and (2) the Tailscale policy/ACL file ("how you define who can access what on the network"). "Application capabilities" attach arbitrary metadata to identity, "guaranteed by the Tailscale control plane." Visual editor + JSON + API for GitOps workflows. 17:03-18:46
- Q&A — transparent base-URL interception: you set the agent's base URL to the Aperture node; they *could* capture that at the network layer transparently but chose not to because it's "not the Tailscale way" — hidden interception "can start to break and shift and move out from under you." The framing is best-of-both-worlds: easy for devs to get LLM access, easy controls + full tool-call visibility for security/IT. 18:46-20:25
- Q&A — non-tool-call / code-execution behavior: "a lot of agents are moving away from tool calls and executing code," which makes traffic harder to parse, "and it's the whole reason we chose to do this." They considered the MCP layer but the LLM layer is "way more valuable" because even with skills/code "you're still running something" through the gateway. Caveat: you could "write the thing, obfuscate the thing, then run the thing." Many customers said "I don't even know what tools people are using — forget about blocking it, just tell me what people are doing"; internally "bash dominates everything else" over MCP. Planned guardrails: e.g. block `rm -rf /`. "If you can't see everything, how valuable is it?" 21:28-23:41
