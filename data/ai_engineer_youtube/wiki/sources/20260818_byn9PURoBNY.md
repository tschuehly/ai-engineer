## Summary

Gabriel Jorge Menezes gives the infrastructure half of the Krea 2 story — the same model whose research side Sangwu Lee covered in a separate talk the same day — and it is almost entirely about operating a shared GPU cluster rather than about diffusion. Three durable arguments come out of it. First, the standard observability defaults are wrong for large-scale pre-training: GPU utilization reads 100% while the cluster is nowhere near well used, so tensor core utilization is the honest proxy, and InfiniBand counters (the fabric where most of their failures actually happened) are exported by nothing off the shelf and have to be collected by hand. Second, the response to failures at this scale is replacement and checkpoints rather than diagnosis: any GPU above 78 °C is pulled instead of debugged, and crashes are absorbed by checkpointing every 20-30 minutes against a filesystem fast enough to write a terabyte in under 30 seconds. Third, training and production share one cluster with training holding the higher priority, which works only because a virtual-kubelet fake node lets evicted inference pods spill out to external GPU providers, a taint driven by Prometheus metrics decides which side new pods land on, and a descheduler migrates them back gradually so the site never drops. The closing asymmetry is the reason the whole scheme is safe: their diffusion-transformer inference runs on a single node and tolerates hardware that would destabilize a training run.

## Notes

- Framing: Krea 2 was "pre-trained from scratch," released less than a month before the talk, with "no base checkpoint, not anything. Everything done in house." Two checkpoints are open: a raw pre-trained one "so people can post-train and do whatever they wish to do with it," and a post-trained "turbo" one that returns an image "in like less than a second." Both are on Hugging Face and GitHub; the model also serves production on krea.ai (00:23-01:48).
- Scale and topology: "trained from scratch on thousands of GPUs," on "one main cluster with a lot of GPUs, all InfiniBand connected." Work started as "small ablations on like a small number of GPUs" to test hypotheses before scaling (01:55-02:25).
- Research provenance, matching the companion talk: the goal was "to kind of bridge the gap between like LLM research and diffusion transformers," and "my AI researchers, they ported a lot of research from LLMs into into DiTs." The resulting architecture "was meant to be extremely, extremely simple… very very dumb, but like very effective" (02:26-02:51).
- Crash scaling: small experiments "would like run for days," but at 128, 256, 512 GPUs "things are crashing more. That's expected… there's more surface area for things to break." The dangerous class is the quiet one: "a lot of the times things would go wrong in silent ways… NCCL timeouts, like just crashes and… the metrics are all good" (03:02-03:34). Captioned "nickel."
- The let-it-crash lesson: "at the beginning we were like paranoid, swap node, change node, whatever… And we learned that like sometimes you just let it crash. It crashes, like it runs for like an hour, crash, runs for an hour, crash, and then runs again on the same set of machines, same code, same data for like 12 hours, 16 hours, 24 hours" (03:35-03:51).
- Failure-rate baseline: "there is this paper from Meta that kind of gives you a like rough estimate of like how many failures you should expect… we kind of saw the same pattern but like not the same numbers. Our runs would last way way less than this." The paper is not named. Why it matters: "you can imagine doing large-scale pre-training on runs that last less than 8 hours, it is a problem… You want [to keep] those GPUs fed, and if things are crashing, you are not doing progress and losing time and models are going to be late" (03:52-04:19).
- The thesis of the middle section: "metrics are everything. That's how I can support my researchers. That's how I have visibility in the system… if you're doing large-scale pre-training, I highly highly recommend for you to invest heavily on metrics. Don't go blind because you're going to go crazy." He calls the specific metrics "quite silly but like extremely effective" (04:22-04:46).
- Temperature as the first metric: a single GPU "a bit warmer than the others… is going to start throttling and slow down and… the training's going to be unstable and you have weird problems. So for us it was like if there is any GPUs above like 78°, you remove them. Don't think about it. Don't try to fix. Don't don't try to be smart. You just remove the GPU… just ask your provider… this GPU's hot. Please replace it" (04:46-05:17).
- GPU utilization: "there is GPU utilization which is a lie. Don't trust this. This is dumb… this is amount of time GPU's doing work but like not good work. Not how efficient the GPU's working. So… during our pre-training, the GPUs are 100%. This is not true. We are not fully utilizing the GPU. This is 100% a lie" (05:26-05:45).
- Tensor cores as the honest proxy: "what we would use as a proxy was tensor core utilization. This is actually how much of a tensor core you're using and like how effective they are being." The validating observation is the resolution curriculum: from pre-training through mid-training to post-training "you start like scaling the resolution of the images… pre-training we do like I think 128, 256, 512, 1024 pixels as they scale and you could see the tensor core utilization go up as we like would scale on these resolutions cuz now you're doing more work on images" (05:46-06:18).
- Fabric counters: InfiniBand and NVLink metrics "by default [are] not exported by… the NVIDIA metrics, that DCGM stuff. Some NVLink stuff, yes, but no InfiniBand… I'm telling you right now, if you're doing large-scale pre-training with a bunch of GPUs talking to each other between machines and you have no InfiniBand metrics, you're doing something wrong." These mattered most "because most of our failures were like related to like cross-node communication." Their reference dashboard carries, beyond throughput, "when a message [is] sent on the fabric… how much time the message is waiting," "number of errors and different types of errors," and packet counts. Collection was custom-built: "It was not hard. You can figure it out. It's very very easy" (06:18-07:12).
- NVLink is the single-node counterpart and NVIDIA does not export its error counters either: "sometimes a single node would have a weird failure where the GPUs seem to be fine, but like some weird error happens and then you can look at NVLink errors and like you see errors happening. And then replace that machine." His verdict on the set: "without this we would not be able to to train at all" (07:12-07:52).
- Checkpointing as the crash absorber: "our trains would crash constantly and a hacky way… to fix the problem [is] just checkpoint. Use and abuse the file system that you have." Their first attempt failed: "At the beginning we use Ceph. Ceph didn't work well. Was very annoying. It broke. We lost trust in data. So, I recommend if you have the money go with something paid… cuz you can trust your data" (07:56-08:19). Captioned "SEF."
- The filesystem numbers: "This is our worker cluster. We can do like 1.8 terabytes [per] second of reads, almost a terabyte of writes. And the file system would not choke on the training. So, we could checkpoint every like 30 minutes, 20 minutes, produce like a terabyte of data in like less than 30 seconds. So, this would not delay trainings" (08:19-08:43).
- Submission model: "I don't want my researchers to think about GPUs. I just want them to launch stuff and this goes into a queue and if we have GPUs we have GPUs. If we don't have GPUs we don't have GPUs" (08:53-09:04).
- The scheduler: "This is a[n] open source project. You can look it up. It does gang scheduling. Gang scheduling is important for trainings in general. And this gives us a semantic of like two tiers of priority where you have a workload priority… you can say like oh this training is more important than this one. So, it skips on the queue in front of the queue. And then after this we have the normal Kubernetes priority" (09:04-09:31). See Caption Artifacts on the project's name.
- The priority inversion, stated plainly: "the training pods they always have like high priority for everything. So, like once they are submitted they go on a schedule. If there's inference running on those machines, the inference gets kicked out. And you'd say, 'Oh, this is bad. Production is going to go down.' No, you can build on top of that to make production not go down" (09:31-09:47). The justification comes later: "production is lower priority. The site still needs to work. People still need to be use the website. But like the GPUs… the value that we get off the GPUs doing trainings is more like higher than than we get out of production" (10:44-11:03).
- The scheduler's rough edge: "the only… problem with [it], which is annoying — you can automate that, we have not — it's just that you specify the queues. The queues have like amount of resources, CPU, and like Nvidia GPUs, memory, whatever. But this is manually specified. And at least our cluster is quite fluid. Nodes phasing in and out of existence. They go into maintenance, whatever. You lose a few nodes here and there. This number gets out of sync. And sometimes these would break gang scheduling" (09:47-10:20).
- An alternative he has not tried: a Kubernetes release he cites by version "has gang scheduling out of the box. Something very similar to [the queue project]… so, maybe you can use [it]" (10:24-10:34). The version number is unreliable in the captions; see Caption Artifacts.
- What the users see: "there is this magical system… that allows us to flip traffic between clusters magically. And not just clusters, and like external providers, GPU rentals, whatever… the dark green is like inference running in cluster. And then someone launches a train, and then suddenly [pods] start flipping to the other cluster, and then training is done or whatever happens, it flips back. So, we stop wasting money. And this is seamless. No one needs to think about it" (11:04-11:38).
- The mechanism: "there's this very nice project called virtual kubelet, also open source… It is a very nice code base. And this works by creating a fake machine in Kubernetes… This creates a fake machine that is like up to you to control how it works. So, Kubernetes does normal scheduling as you would expect. Things would go into these nodes. For example, here all the GPUs are in the cluster in use, right? So, this pod goes into the virtual kubelet node, and in there you can do whatever" (11:56-12:24).
- The provider layer they wrote on top: "you receive the pods back, and then you find a provider… Let's say you have a deal with some provider that gives nice prices. You integrate into here. We built like some nice interfaces to… not leak things. So we just implement a provider, and there is an algo that decides which one it goes [to]. You translate this back of the pods into the provider stuff, and you deploy, and then you have something that reconciles between the both sides" (12:24-12:52).
- Free failure handling from Kubernetes: with the HPA scaling replicas, "if something fails, it is very interesting, you don't need to handle the fail. The only thing you need to handle is like, 'Oh, something failed.' You mark the pod as failed. Kubernetes… detect[s] that something has failed and create[s] a new one. You don't need to try to save the world. Let Kubernetes handle it for you… If something breaks on your side, something breaks on the other side, just mark it as failed, let Kubernetes handle it, create a new one, and things keep working" (12:53-13:41).
- Taints as the routing switch: "let's say you have GPUs on your cluster available… You don't want to waste money. This would be very, very bad. So, the system works with using… Kubernetes taints. They allow and disallow things to run. Pods have tolerations for the taints. And when we have GPUs in the cluster… this adds a taint into the node when we have a lot of GPUs. So, like a lot of GPUs in the cluster, we taint the node, nothing can schedule on it. So, we stop wasting GPUs. Like the pods, they go into the GPUs in the cluster, we don't waste money." The reverse: "imagine someone launches a training… This training is going to take all the GPUs in the cluster, it's going to hog all of the GPUs, no GPUs in the cluster. The system detects this, removes the taint, new pod schedules there" (13:41-14:37).
- The signal driving it is deliberately unremarkable: "for us, for example, we use just some Prometheus metrics. That's how we do it, very simple, but it works very, very, very well" (14:37-14:43).
- Migrating back without an outage: when the training finishes, "now we have pods running on the other side, you're wasting money… you run something else that detects the system and removes things back. In this case, a descheduler. Once the taint's added back, so like GPUs available, we add the taint, the descheduler says, 'Oh, these pods, they don't tolerate the taints. I'm going to migrate them back'" (14:56-15:17).
- Why not the obvious Kubernetes primitive: "you can ask, 'Oh, why you don't use a NoExecute taint?' NoExecute in Kubernetes would kick everything out at the same time. So, at [the] moment you put the taints, everything will be kicked out and that's bad. Production would go down. So, this system slowly migrates the pods back, so production doesn't go down and we don't waste money" (15:17-15:34).
- Operational verdict: "it is a very self-healing system. You don't need to interfere with it. It just runs. Yes, of course, there was bugs at the beginning. Nothing's perfect. But like once you calibrate it was very very well and like changed the way we do research cuz no one else needs to care about GPUs. They just launch stuff. If [we] have GPUs, we have GPUs. If not, we don't have GPUs, go into the queue. And we fully utilize the cluster for trainings. Production runs somewhere else. And the GPUs are doing like useful work" (15:34-16:02).
- The closing asymmetry, and the reason the eviction scheme is affordable: "if you're doing like diffusion transformers, they're not huge like LLMs that need like multi-node inference. Something that we learned: whatever GPU works. The GPU can be hot, falling out of the bus. It can be exploding. Inference still going to run. It is very interesting. So, like you can have very very bad GPUs for inference and everyone's going to be happy" (16:02-16:22).

## Caption Artifacts

- The company and model are captioned phonetically throughout: "Korea" is Krea and "K2" is Krea 2. "Nickel timeouts" is NCCL, and "SEF" is Ceph — all four are unambiguous from context.
- The open-source scheduler is captioned indistinguishably from the ordinary English word "queue" (and once as "Q"), so the transcript cannot settle its spelling. Everything he attributes to it — open source, Kubernetes-native gang scheduling, a workload-priority tier above normal Kubernetes pod priority, and per-queue resource quotas that are manually specified and drift out of sync as nodes come and go — matches the Kubernetes SIG project Kueue, which is almost certainly the referent. This note records the identification rather than silently substituting the spelling.
- The Kubernetes version credited with built-in gang scheduling is captioned "1.15." That release long predates the capability being described, so the digits are unreliable; the durable claim is only that a recent Kubernetes release ships something similar and that Krea has not tried it. No version is asserted here.
- The hiring email is captioned "gabriel plus hiring at cerebra.ai," which does not match the company under discussion. The address is not reproduced.
- One line reads "the training SLI is going to kick out the pods" (14:49) where the surrounding argument is about the training workload preempting inference pods; "SLI" appears to be a mis-transcription and carries no meaning here.
- The Meta failure-rate paper is referenced but never named, and no numbers from it are quoted.
