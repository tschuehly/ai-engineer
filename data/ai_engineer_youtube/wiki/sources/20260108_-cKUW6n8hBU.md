## Summary

Kevin Madura frames DSPy as a way to program with LLMs through typed signatures, modules, adapters, metrics, and optimizers instead of manually tuning prompt strings. The talk shows how that abstraction supports model swapping, document-routing pipelines, multimodal PDF boundary detection, and metric-driven optimization that can improve a program or transfer performance to smaller, lower-cost models.

## Notes

- DSPy is presented as a programming model where developers declare program intent, inputs, and outputs instead of hand-managing response parsing or prompt strings; this keeps control flow more stable as models change. 02:00-05:35
- Signatures express the task and typed fields; modules structure the program; adapters control how the prompt is formatted for the model; optimizers use metrics to improve the program. 07:40-10:00
- Adapter choice can affect token use and model behavior: the example swaps a JSON adapter for a BAML adapter while leaving the calling program intact. 21:10-21:45, 40:31-43:00
- Optimization starts from a dataset and task metrics, evaluates a base program, then iteratively generates better prompts; teacher feedback can explain why an answer was wrong, not just whether it failed. 47:24-49:28
- Metric breakdowns after optimization can reveal whether to tune a metric, decompose it, adjust the dataset, or change program structure. 62:03-63:22
- Optimizer output is a serialized or loadable DSPy module, effectively a compiled program object that can be reused later. 63:29-63:49
- DSPy is not inherently cheap or expensive; costs come from program design, call count, context size, adapter verbosity, and whether optimization transfers work to a smaller model. 70:38-72:24
