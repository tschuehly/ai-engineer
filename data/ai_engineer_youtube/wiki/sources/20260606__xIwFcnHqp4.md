## Summary

Marlene Mhangami and Liam Hampton (Microsoft / GitHub developer advocates for VS Code and GitHub Copilot) give an intro-level walkthrough of MCP Apps — the MCP extension that lets server tools return rich, interactive UI that renders directly in the chat window instead of plain text. They restate the host/client/server model (VS Code is the host, GitHub Copilot is the client holding the 1:1 connection to servers, servers are lightweight programs exposing capabilities), then frame the motivation: when MCP first shipped, tools could pretty much only return text, so READMEs overcompensated with ASCII art and emojis because diagrams and rich content were impossible. MCP Apps fix this with a concrete runtime flow — the user prompts, the LLM picks a tool, the server returns the tool result *plus a UI resource reference* (an MCP resource pointing to bundled HTML the server generated), the **host** (not the client) fetches that HTML and renders it in a **sandboxed iframe**, and the embedded app then calls back to the server so fresh data updates the UI live. The sandbox exists for the same reason "you put a hamster in a cage": to stop the app from touching VS Code settings, external APIs, or anything outside the chat window. The build side is a coding-agent workflow: Liam *borrowed a skill from the Model Context Protocol repo (Anthropic), edited it, and ran it through GitHub Copilot CLI* to scaffold several MCP apps (flame graph, markdown viewer, flight status, color picker). An MCP app has three parts — the tool, the resource (bundled HTML UI in React/Vue/Svelte/vanilla JS), and the link the server recognizes between a data response and a renderable UI — plus tool-visibility config for who may invoke the tool (model only / model + app / app only). The live demo profiles a Go program (bubble sort + Fibonacci) with Go `pprof` over 5 seconds via a localhost MCP server (TypeScript) and renders the "nasty, jumbled" profile data as an interactive React flame-graph app inside Copilot chat, eliminating the back-and-forth of pasting profiler text and re-prompting. Named adopters: Shopify (in-chat checkout that preserves brand experience), Excalidraw (interactive architecture diagrams; Claude Code uses its MCP app), and Figma (components generated on the fly).

## Notes

- MCP architecture restated: hosts are programs like VS Code that want data from MCP servers; clients maintain the 1:1 connection with servers and are sometimes (not always) the same as the host — in VS Code the recommended client is GitHub Copilot; servers are lightweight programs that expose specific capabilities/context. 01:16-02:35.
- Security framing for picking servers: use the curated server list in VS Code (search `@MCP` in the extensions tab) or GitHub rather than a random internet server, which can contain malicious stuff. 02:52-03:16.
- The text-only origin problem: when MCP first released, tools "pretty much only" returned text, so a "draw me a diagram of MCP" request failed; early MCP/LLM READMEs leaned on ASCII art and emojis because diagrams and rich text could not be generated. 03:19-04:05.
- MCP Apps definition: server tools return "rich interactive components that render directly in the chat," giving live UI elements the user interacts with in-chat. The Excalidraw MCP server now uses an MCP app to generate a *live* MCP diagram you can move and edit. 04:17-05:13.
- Runtime data flow (the mechanism): user prompt → LLM decides which tool to call via the MCP server → server returns the tool result *with a UI resource reference* (MCP resources; the reference points to a stored HTML element the server generated) → the **host** (VS Code, explicitly "not the client, it wouldn't be GitHub Copilot") fetches the HTML from that UI reference → host renders the app inside a **sandboxed iframe** → user interacts; the app calls back and forth to the server for a live interaction; the server can return fresh data and the app updates. 05:15-06:33.
- Use cases: (1) data exploration — click buttons in a UI instead of repeatedly typing new questions into chat (e.g. drill into a bar chart); (2) e-commerce — complete the buy/checkout flow in chat instead of getting links and navigating to a browser, keeping the user inside the chat. 06:37-08:05.
- Adopters: Shopify (in-chat checkout, "keeping the brand experience of a company the same as if you were on the company's website"); Excalidraw (architecture diagrams / interactive diagrams; Claude Code — transcript "Cloud Code" — has nice MCP apps using Excalidraw to generate images); Figma (components generated on the fly). 08:10-09:30.
- Build workflow: Liam borrowed a skill from the Model Context Protocol repository (from Anthropic), edited it, and ran it through **GitHub Copilot CLI** to "spit out a number of different MCP apps" — flame graph, markdown viewer, flight status, color picker as generic starters. The skill tells "Copilot CLI or Claude or whatever AI tooling" how to set up and run the app, with code examples for handlers and tool visibility. 09:35-10:14, 11:03-11:31.
- Three main parts of an MCP app (per the repo README/skill): the tool (called by the LLM, with the host i.e. VS Code), the resource (the bundled HTML UI — "could be React, could be Vue, vanilla JS, Svelte, etc."), and the link between the two — the server recognizes the link between the data response and a UI being available to render. 10:26-10:57, 10:37-10:46.
- Tool visibility / "who invokes the tool": configurable as the model only, the model and the app, or just the app. 11:10-11:31.
- Demo specifics: a Go file with a bubble-sort and a Fibonacci sequence; the MCP server profiles the app over 5 seconds using Go `pprof`, bundles up the Go program, runs it, profiles it, and spits out JSON; the MCP server runs on localhost and calls out to a TypeScript server (all written in TypeScript per the skill); the front end is a React "flame app" using React hooks that receives the tool input/results and renders the flame graph. 11:31-13:30.
- Why an iframe: "the same reason you put a hamster in a cage" — you don't want the app to interact with your VS Code settings, any APIs, or anything external; keep it all contained inside the chat window. 14:23-15:10.
