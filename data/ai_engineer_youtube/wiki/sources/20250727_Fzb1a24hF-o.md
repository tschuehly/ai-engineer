## Summary

Kyle Penfound and Jeremy Adams demonstrate using Dagger to build coding-agent workflows as portable, containerized software-delivery code: build/test functions become reusable tools, an LLM receives a typed workspace environment and prompt, traces expose tool behavior, and the same workflow can run locally or in GitHub Actions to open a pull request.

## Notes

- Dagger is described as both a container runtime and workflow engine whose CI/CD workflows run the same on a developer machine, Kubernetes, GitHub, or other CI infrastructure. (05:34-06:03)
- LLMs are treated as another Dagger component alongside containers, repositories, directories, and files, letting teams bring models into existing workflows rather than building a separate agent framework. (06:24-06:56)
- Dagger distinguishes itself from Docker by making the whole workflow portable, not only one application container; the workflow can include multiple sandboxed containers and other objects. (07:46-08:24)
- Dagger modules can be written in several languages and reused cross-language with native bindings, which lets teams package workflow functions without forcing one implementation language. (08:30-09:32)
- Dagger Cloud visualization is used to inspect prompts, tool availability, tool calls, and environment behavior so prompt and tool descriptions can be improved from observed failures. (16:05-16:54)
- The coding-agent example gives the LLM an environment and prompt, expects a `completed` workspace output, extracts the completed source directory, and runs tests again in code before proceeding. (39:12-41:17)
- The workshop connects the agent workflow to GitHub Actions with secrets and permissions so CI can run the agent and open a pull request. (58:52-61:41)
