## Summary

Dominik Tornow (founder/CEO of Resonate, a durable execution platform, and author of *Think Distributed Systems*) argues that coding agents will retire general-purpose platforms not because they are bad but because they become unnecessary: general-purpose implementations get replaced by bespoke implementations generated on demand as minimal extensions of infrastructure that is already in place. When that holds, reuse moves upstream — from reusing an implementation to reusing an abstract specification — and value moves from implementation to specification/protocol ("the prompt is the platform, the specification is the product"). The talk's core engineering contribution is how to make agents *design*, not just build and verify: naive prompting from an abstract spec straight to a concrete Rust-on-Postgres server produced happy-path code that broke on concurrency, process, and network failure, so Resonate inserted a **deterministic simulation** step. The pipeline becomes abstract specification → simulated implementation (executable design) → concrete specification → concrete implementation, with the agent as the driver and humans still in the design loop. A concrete NATS.io example (versioned KV store with optimistic concurrency and occasional stale reads) motivates the "forbidden fruit" pattern: the simulation records facts the real platform hides (whether a read was fresh or stale, and the latest value the algorithm missed) which the algorithm may not depend on but the agent may use to explain *why* its design was wrong. Enablers are minimalism and simplicity (three years shrinking the protocol to two objects — a durable promise and a durable task).

## Notes

- Thesis: in 2026 coding agents will "quietly retire their first software platform" — not because it is bad, simply because the platform is unnecessary; general-purpose implementations are increasingly replaced by bespoke implementations generated on demand, not as a new library/framework/platform but as a minimal extension of infrastructure already in place. (00:02-00:57)
- If implementations become generatable, reuse moves upstream: instead of reusing a general-purpose implementation, you reuse a *specification* and derive a bespoke implementation from it; value moves from implementation to specification. (00:57-02:05)
- Reframes Resonate itself: the product is no longer the implementation but the specification/protocol; from one protocol they derive multiple server implementations (a general-purpose reference server, and implementations built with infrastructure partners). Resonate ships a server plus SDKs for TypeScript, Python, Rust, Go, and Java. (01:33-02:40)
- The real question is not "can we build a server" but "can we repeatedly synthesize trusted servers from the same specification, and if so how." (02:40-02:52)
- Agentic engineering usually focuses attention on *verification* ("how do we know the result is correct?"); this talk focuses instead on the *specification* and on how agents can participate in specifying the system, not just building or verifying it. (02:58-03:23)
- Partner example: Synadia, the company behind NATS.io (open-source messaging for distributed systems); the rest of the talk uses Resonate on NATS.io. (03:23-03:50)
- The specification must be abstract: it must not assume a concrete DB schema/indices, not even a relational DB with tables/transactions, not a key-value store, not weak or strong consistency. Only the implementation is concrete. (03:53-05:11)
- First attempt failed: asked the agent to build a Resonate server in Rust on Postgres directly from the abstract spec; the gap was too large. It worked on the happy path and passed basic tests but was not correct — broke on concurrency, process failure, and network failure — a prototype, not a production system. (05:11-05:52)
- First fix: insert an intermediary *concrete specification* (data schema, indices, SQL queries, transaction boundaries written down explicitly). Then the agent could implement the production system, but the human was the main driver; the agent helped *build* but did not help *design*. If the specification is the reusable product, that is not enough. (05:52-06:57)
- Next step: move agents upstream. For Resonate-on-NATS they changed the question from "can the agent build the production system" to "what does the agent need in order to *design* the system first and build it second," and gave the agent a deterministic simulation environment. (07:04-07:31)
- New task: do not build the production system; build a *simulated implementation*. The simulated implementation is not the product — it is *executable design* whose purpose is to discover the correct algorithm under partial order under partial failure; once discovered/tested/verified in simulation, the agent writes the concrete specification, then the production implementation. Pipeline: abstract spec → simulation implementation → concrete spec → concrete implementation. This is the point where the agent moves upstream and becomes the driver (humans still involved). (07:31-08:29)
- Two enablers: minimalism and simplicity, which are the finish line, not the starting point. Three years shrinking the protocol by repeatedly asking "what can we take away? what abstraction can we erase? what property can we remove? what relationship can we break?" Result: a small protocol centered on two objects — a durable promise and a durable task. Even simple concurrent/distributed protocols on top of a few simple primitives have a complex state and behavior space, so implementing them is tough. (08:29-09:24)
- NATS gives a small set of primitives: queues, a key-value store, and delayed/scheduled messages — the concepts of the *target* platform, not Resonate concepts. Design question: express the Resonate protocol using only these primitives. (09:24-09:54)
- The versioned KV store: create foo, update to bar, update to baz → latest is baz at version 2. Most reads are fresh, but sometimes a read is stale (e.g. returns foo at version 0 while latest is baz at version 2). A stale read is not corruption or a bug; it is a valid read under the target's consistency model. (09:54-10:52)
- Correctness bar: the implementation must be correct when the target behaves *legally* (per its consistency model), not only when it behaves conveniently — so the simulation must expose fresh reads, stale reads, and the version information that tells you which world you are in. (10:52-11:21)
- You cannot tell a read was stale by reading; you find out later on write. Optimistic concurrency: a write against version 0 fails because the key already moved on — the moment the target tells you "the world you saw is not the current world." Building always-correct applications on a concurrency model that allows occasional stale reads is not simple, not for humans and not for agents. (11:21-12:00)
- Agents thrive on immediate, unambiguous feedback — feedback that shows *why* and *how* something went wrong (what stale value was returned, what logic was triggered, what write failed, which invariant broke), not just *that* it went wrong. (12:00-12:38)
- They built a deterministic simulation testing environment in Python simulating the parts of NATS.io they depend on. The simulated KV store keeps full version history per key; on get it usually returns the latest version but sometimes (controlled by a deterministic RNG) returns an older version; on update it enforces optimistic concurrency (write succeeds only if the read version is still latest, otherwise raises). It behaves like the real store where correctness matters, but is deterministic, repeatable, and inspectable — so a broken run can be reproduced exactly and the agent can repair the algorithm against that trace. (12:38-13:53)
- **Forbidden fruit**: simulation exposes facts the real platform hides. In production you only get the value at the version you observed; you do not learn whether the read was fresh or stale, or the latest value you missed, because real code cannot depend on it. In simulation, every get emits a trace event tagging fresh/stale plus "this is what you got and this is what the latest value was." The algorithm is forbidden to depend on this, but the agent is allowed to use it to explain why the algorithm it designed was wrong. (13:53-15:05)
- Trace-event example: production code only sees the result (e.g. "the promise was pending"), which is all the real platform would tell you; the simulation additionally records the read type (stale) and the hidden latest value (e.g. the same promise is already settled). That difference is exactly the fact an agent needs when debugging a distributed algorithm — the invariant failed *because* the algorithm made a decision from a stale view of the world. Cause and effect becomes visible; the agent learns not just that the system is wrong but *why*. (15:05-16:16)
- Outcome: from a single abstract specification the agent built a proof of concept in the deterministic simulator (verified by first testing), derived a concrete specification where the algorithm was already known correct, then derived the implementation. Deterministic simulation lets agents participate in the design, not just implementation; humans stay in the design process but the agent is the driver. (16:16-17:18)
- Closing: "The prompt is a platform and the specification is a product." (17:18-17:24)
