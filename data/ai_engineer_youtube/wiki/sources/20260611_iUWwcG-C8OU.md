# Why Can't Anyone Answer Questions About the Business?

Source: [Why Can't Anyone Answer Questions About the Business? — Garrett Galow, WorkOS](https://www.youtube.com/watch?v=iUWwcG-C8OU)
Uploaded: 2026-06-11

## Summary

Garrett Galow (Head of Product, WorkOS) demos Studio, an internal natural-language workspace where any employee can ask business questions against Snowflake, Linear, and Notion and get an answer or build a reusable "widget" without filing an engineering request. The durable engineering content is how Studio is made reliable enough to hand to a non-technical support team: an LLM (Opus) drives a LangGraph agent that, once it converges, writes a widget as declarative JavaScript calling the data sources directly, so every later run is deterministic, cheap, and LLM-free. Three techniques make the generation trustworthy — preflight sequencing with just-in-time tool-context injection to keep the window clean, a layered prompt that tells the model to distrust its own (stale) product knowledge and go to primary sources, and execution-based query validation that catches valid SQL returning zero rows. Notably, WorkOS uses no RAG vector store: LLMs read self-descriptive table schemas well, so injected context blocks describing join quirks and status-filter rules are enough.

## Notes

- The recurring pain Studio attacks: a business question needs SQL, so a non-technical person explains it, waits for an engineer, gets an answer, realizes it needs one more join, and shares a one-off in Slack that does not scale. Pre-built dashboards (e.g. Retool) are too rigid when the next question needs an extra field. (01:09-02:16)
- Architecture under the hood: a Studio dashboard or a Slack bot kicks off an API that parses the request and runs it through LangGraph, an agent tied to an LLM (Opus) plus tools and a guidance layer. An integration proxy reaches the data sources (Snowflake, Linear, Notion); the agent drives queries and returns answers or widget updates; session state is stored in Convex so it persists across sessions. (04:11-05:19)
- The guidance layer defines rules for how to query each source and the context needed to query it successfully — for sprawling Snowflake, how a customer is represented and how to join tables effectively. (04:45-05:04)
- A widget is sandboxed code bundling the UI, the APIs, and the query for a fully usable tool. Once built it is live and reusable: hitting refresh reruns the query for new time slices, the LLM is not involved, and inputs (e.g. a user email) are passed as ordinary JavaScript arguments. Widgets can mix and combine data from multiple tools in one interface. (06:15-07:01, 15:48-17:05)
- Self-serve payoff: the support team uses Studio widgets in Slack to answer per-customer questions (e.g. why Radar blocked a login, all sessions for a customer) themselves. One-off questions get answered directly; recurring ones become shared widgets, so no platform or data team has to keep building and modifying dashboards. (07:07-09:51)
- Three reliability techniques (10:00-12:24):
  - Sequencing: run many preflight checks (are tools connected, is there enough context, otherwise ask clarifying questions) and a checklist of which tools to use; inject the non-trivial, schema-heavy tool context only at the moment a tool is invoked — explicitly to avoid preloading all tool context and blowing out the context window. (10:07-11:13)
  - Layering: a base Studio prompt with defaults, plus org rules and per-tool context that is maintained when someone edits a tool, plus an instruction to distrust the model's own knowledge of WorkOS (training data is outdated, the product moves fast) and instead look up primary sources such as docs. (11:14-11:58)
  - Validation: always run a generated Snowflake query and confirm it returns data before hardcoding it into a widget, because a valid SQL query that returns zero rows is a real and useless failure mode; the agent pre-validates its work before deploying. (11:59-12:24)
- Evals are used while developing the product and run in both staging and production instances, treated the same so developers get the same experience as teammates. (12:25-12:43)
- No RAG store: WorkOS does not maintain a RAG database. LLMs are "surprisingly good" at interpreting table schemas, especially with self-descriptive column names, so they "just invoke tools with context on top." A messy data estate (e.g. a customer-to-user relationship four joins deep) is handled by telling Studio the join block once in the context, rather than cleaning up Snowflake. (12:57-14:12)
- Governance / trust-but-verify: the audience worry is that a wrong generated query becomes accepted truth nobody re-checks. Galow reports a very high hit rate and protects against the common miss — forgetting filter columns like active-status or non-deleted entities — by embedding those data-consistency rules into the tool context; remaining errors tend to be large and obvious. (14:26-15:43)
- Permissioning today is per-user (each employee connects their own Snowflake/Linear/Notion), which is annoying; WorkOS is moving to org connectors (built on its own Pipes integration product) where one person sets up a connection and sets a default access level plus role-based overrides (e.g. read-only by default, edit/admin for certain Studio roles). (17:03-18:09)
- Cost stance: widgets are declarative so there is no per-run LLM cost; for generation WorkOS is willing to pay because Opus outperforms cheaper models enough that trading cost for quality would be unacceptable. (18:10-18:43)
