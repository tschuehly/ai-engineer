## Summary

Vaidas Razgaitis, a senior research engineer on Higharc's labs (R&D) team — Higharc works in home building and spatial reasoning, so it uses computer vision to parse hand-sketched floor plans into an internal data model, reasoning agents, custom transformers, and diffusion models for image gen — treats the research-to-production gap as a **systems-and-process problem** rather than a modeling problem. The core friction is a handoff between two populations: platform/infrastructure/back-end engineers who build robust production-grade code but do not know CV or LLM-training methodology, and ML researchers who track the latest papers and combine concepts creatively but have not owned production-grade APIs. He offers three levers to raise the velocity of turning research into customer-ready features. (1) **Research legibility** via a "research prototype taxonomy" (RPT) document — a software-engineering technical design doc / RFC adapted for ML, with ML-specific sections up front (domain context and novel data representations, business goal) followed by conventional TDD sections (type contract between repos, persistence, system architecture, merge/decompose plan). (2) **Code structure**: a separate Python ML mono repo of cleanly isolated, fully decoupled microservices at roughly a one-researcher-to-one-microservice ratio, fronted by a gateway on one Docker bridge network, each microservice a standalone layered FastAPI app, with agent-navigable specs and shared CI/GPU tooling underneath. (3) **Decomposition and PR review**: slice a proven monolithic prototype along a dependency graph and land it as stacked diffs (Graphite) for asynchronous, subject-matter-expert review. He closes with diagnostic questions for each lever to tell whether a team should invest more in legibility, repo structure, or decomposition.

## Notes

- The team is a multidisciplinary AI/ML shop: CV to scan hand-sketched floor plans into the internal data model, reasoning agents for agentic user experiences, custom transformers, diffusion models for image gen (00:26-01:06).
- The problem is framed as a two-sided handoff: production engineers unfamiliar with CV/LLM-training research vs. paper-fluent researchers who have not built production-grade APIs — "this baton pass… how do we facilitate that" — treated as a systems-and-process problem (01:16-02:40).
- Three levers to improve the velocity of bringing research into production: research legibility, code-base structure, and decomposition/PR review (02:42-03:36).
- Lever 1 — research legibility: the RPT document is "just a technical design document from software engineering with some specific twists" for ML, kept in Notion. Cites a Pragmatic Engineer blog on the importance of technical design docs / RFCs / specs before building to align scaling teams. Sections: (a) **domain context** and novel data representations (a party diagram, a graph for a home's circulation, embedding models / latent-space representations) — framed as "picture a software engineer we just hired from JP Morgan; what lingo and data representations do they need"; (b) **business goal** (why the problem matters, the value of the ML tool); then conventional TDD parts — (c) **type contract** between the core product repo and the ML repo and how types stay in sync; (d) **persistence layer** (deliberately *not* where the researcher should spend much time — mapping how far they got is a good first entry point for software-engineering help); (e) **system architecture / anatomy** (is it a workflow, a chaining of workflows, external LLM calls?); (f) **merge/decompose plan** (03:37-06:38).
- Lever 2 — code structure: a separate repo from the core product repo, all Python, a mono repo of "cleanly isolated and fully decoupled microservices," roughly a one-to-one researcher-to-microservice ratio (e.g. "data-driven entity prediction" is the custom transformer model), so each initiative iterates independently. A gateway guards requests, everything on one Docker bridge network; web-app clients call the gateway, which routes to the appropriate microservice (06:38-08:00).
- Each microservice uses a simple layered architecture — API layer, business logic, data layer. Core business logic sits at the services layer (may make external LLM calls to foundation models, or pull the team's own model weights in CI/CD), wrapped by controllers, then API routers exposed as standalone FastAPI applications. Each microservice root holds metadata, build instructions, a Dockerfile, project dependencies, and poetry/UV lock files; three microservices in production share a consistent "skeletal backbone." Beneath the services: GitHub Actions for build/deploy, automated test suites, linting/formatting/type checks; Jupyter notebooks running on Modal for GPU compute; ML studies; and a tooling layer plus a CLI. Specs are "really cleanly documented… so that agents can navigate these repositories and help accelerate our ML researchers" (08:00-10:32).
- Lever 3 — decomposition and PR review: treated as a design problem — study which axes to slice a large monolithic prototype on and what the dependency graph looks like, then use **Graphite** stacked diffs to decompose it and get the right reviewers. Graphite is favored for **asynchronous review** ("I could be working on a PR up here while a domain specialist is still reviewing a different PR"), letting the team tap subject-matter experts on specific tightly-decomposed slices. The RPT document's mapped layers, architecture, persistence, and types "informs your decomposition strategy" (10:32-12:31).
- Wrap-up diagnostics per lever: (1) legibility — as product/software/AI engineers staff a research initiative, "is it obvious where they should concentrate their efforts" and clear which tasks to pluck off? ambiguity means revisit the process; (2) repo — clear buckets for new code, with templates/frameworks/patterns to mimic, or have you outgrown the architecture and keep "fighting these old abstractions"? (3) decomposition — can you consistently estimate timelines/delivery dates and know which SMEs to tap? trouble here points upstream to handoff coordination or the hosting code base (12:31-14:35).
