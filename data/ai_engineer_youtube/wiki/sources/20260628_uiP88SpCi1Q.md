## Summary

A ~6-minute lightning talk from Erik Hanchett (senior developer advocate, AWS) giving five code-level levers to cut agent token cost after a production agent's bill was "not good… because it was doing too much" — not because the model was bad. All five operate on the agent loop's per-request message assembly, using AWS **Strands** agents (the mechanisms are framework-agnostic), and none require changing prompts or switching models: (1) cache the system prompt (and optionally tool prompts and messages) so the static prefix is sent in full only once; (2) route messages to a cheaper or more expensive model by task difficulty instead of using the most expensive model for everything; (3) offload large tool results out of the message stream (store locally/in the cloud, keep a summary) so a big result isn't re-added on every loop; (4) cap the tool loop with a max-iterations ceiling so a repeating or infinite tool loop doesn't burn tokens, and use observability before deploy to see how many times each tool loops and how long it runs; (5) trim multi-turn conversation history with a sliding window (Strands' `SlidingWindowConversationManager`, e.g. last 10 messages) so the whole transcript isn't re-sent each turn, mitigating the lost-early-context tradeoff with summarization. The unifying model: in an agent loop the system prompt, tool results, and conversation history are re-transmitted on every iteration, so token spend compounds with loop length unless each re-sent part is shrunk and the loop count is bounded.

## Notes

- Framing: "I deployed an agent to production and the bill was not good. Not because the model was bad, but because it was doing too much" — the cost was in re-sent context, expensive-model overuse, and over-long tool loops, each fixable in "a few lines of code." (00:00-00:18, description)
- Lever 1 — cache the system prompt: in Strands, `cache_prompt = default` sends the full system prompt on the first call and a "much reduced" reference on every subsequent call; tool prompts and messages can be cached too. (00:18-01:01)
- Lever 2 — route by difficulty: use a newer frontier model for a very difficult task and a cheaper model (e.g. Claude Haiku) for something simple, Claude Sonnet for something in between, via an `if` statement — "you can even have another model that's very cheap decide which model to use." Recommendation: "don't use the most expensive model for everything… use multiple different models based on the use case… route to it inside your agent." (01:01-01:51)
- Lever 3 — offload the tool result: for a large tool result, "store it locally or in the cloud and then use some kind of summarization that saves on tokens," so the result "isn't added into the context every time the tool loops or every time the agent loops." Strands offers APIs for this beyond the manual approach. (01:51-02:47)
- Lever 4 — cap tool loops: an agent can call a tool "over and over and over again"; without a cap "it might run 10, 20 times… might get into an infinite loop, which would be very bad for your token usage," so "always set a max iterations." Before deploying, "run some observability tools" to inspect each tool's call count and run duration and "get an idea of how efficient the tool call is." (02:47-03:37, 05:16-05:27)
- Lever 5 — trim the history: in a multi-turn agent, the whole conversation history is re-sent to the model on every call and "can eat through hundreds, if not thousands, of tokens." Strands' `SlidingWindowConversationManager` "looks back at the last 10 messages and only sends those back" (window size configurable). Tradeoff: "you will lose the message history from the beginning" — mitigate by summarizing the older history into the context window. (03:37-04:50)
