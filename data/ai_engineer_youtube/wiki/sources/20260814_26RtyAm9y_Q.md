## Summary

Corey Gallon builds agents that drive a real Chrome through the Chrome DevTools Protocol, and his premise is that this makes an agent indistinguishable from a person at the input layer: "a CDP browser is just like a meat bag with a mouse," because the agent's clicks and keystrokes travel the same path inside Chrome that a human's do. The engineering is a method rather than a trick. Give the agent a shell CLI instead of an MCP server, because capability is a wash (~83% task success either way in an Arize AI study) while the CLI wins on reuse, latency, and token cost (7 turns and under a minute versus 71 round trips and 8 minutes; Anthropic reports up to 75× cheaper). Drive the browser through a small subset of CDP's 57 domains, organized as digital senses — see (DOM, accessibility tree, screenshot), hear (network, console), operate (clicks, keystrokes, navigation). Run sense → act → verify, where verification deliberately uses a different channel than the action. When the loop will not close, climb a three-rung "meatbag ladder" — synthetic JavaScript click, then a real CDP input event, then a human mouse path with jitter and a deliberate overshoot — only as high as the page forces, then write the working path down as code or an agent skill so it never has to be rediscovered. The demonstrations are CAPTCHAs (Cloudflare Turnstile, MTCaptcha, a Lemon drag puzzle, and reCAPTCHA v2), chosen as adversarial tests of the method; the reCAPTCHA solution is the architectural payoff, splitting a deterministic code "solver" that drives and re-arms the challenge from an agent "operator" called in only to look at the tile grid, because the challenge expires on a clock that a model-per-click design cannot beat. Everything demonstrated ran on infrastructure and accounts Gallon owns, after OpenAI threatened to ban his account for the work and then rescinded the threat.

## Notes

- Framing and the legal/ToS reality: preparing the talk earned a message from OpenAI threatening to ban his account "for cyber abuse with a web browser"; the offending work was an agent clearing CAPTCHAs with no human in the loop. After "a quiet word" the threat was rescinded. On advice of counsel, everything demonstrated runs "only on infrastructure that I own and accounts that I operate" (00:01-01:09, 08:26-08:48, 20:22-20:43).
- The premise in one line: "if you have a browser an agent driver browser using the Chrome DevTools protocol, your agent's clicks and keystrokes travel the exact same path inside Chrome that yours do" — as far as Google, Cloudflare "and the rest can tell," it is a meat bag with a mouse (01:35-02:22).
- Three requirements follow from the premise: a CLI rather than an MCP server, CDP as the driving protocol, and "a loop run on a ladder" (02:00-02:22).
- CLI versus MCP, with numbers. Capability is a wash: an Arize AI study found both cleared the same tasks successfully "roughly 83% of the time." The CLI wins on three other axes — **reuse** ("a CLI sequence can be programmed. You write it once and you run it a thousand times without a model in the loop," whereas MCP "hits the model on every single turn"), **speed** (same task: MCP 71 round trips and 8 minutes; CLI 7 turns and under 1 minute), and **token cost** (Anthropic reported the CLI "can be as much as 75 times cheaper") (02:22-04:07).
- CDP surface: "you already know this protocol, even if you don't know its name" — it is what the F12 DevTools panel speaks. It is large (57 domains as of the talk, hundreds of methods and events) and changes frequently, but human-like interaction needs only a small subset, best held in mind as **digital senses**: *see* the page (DOM structure, accessibility-tree semantics, or a screenshot for pixels), *hear* the page (network traffic to and from, console/logs), *operate* the page (clicks, keystrokes, navigation) (04:07-05:39).
- His tool, Chrome Agent, is an installable Python-ecosystem CLI that drives CDP and "makes it really easy for your agents to write code to replay CDP interactions." He explicitly disclaims selling it: "build your own, right? Like I'm not here shilling a product" (04:28-04:40, 20:43-21:04).
- The loop: sense (perceive through one or more channels), act (do exactly one thing), verify (sense again through a *different* channel), repeat "until the page gives in." "If you've clicked something, don't ask the click if it was successful. Check the network or check the screen" (05:39-06:38).
- The ladder, climbed only when the loop will not close: rung one, don't act human at all — use an in-page API or a synthetic JavaScript click, "easy, free, instant, and the right default"; rung two, a real click via the CDP input domain that "the page cannot tell apart from your own"; rung three, human input and behavior — a real mouse path with dwell and jitter, or vision to see and interpret. "Climb only as high as the page forces you… climb to the lowest rung that actually works." Loop on each rung (06:38-08:01).
- The explore-then-automate arc: "first, you explore, you run the loop by hand, you climb rungs until the thing actually works, and then you automate. You write the solution down so you never have to figure it out again… as code or as an agent skill or very often as both" (08:01-08:26).
- Rung one in practice — batch personalized email from the Outlook web client. The compose box "has nothing for us to defeat," so a synthetic click opens compose, fields are filled programmatically, another synthetic click sends. Capture the sequence once and loop it "whether it's 20 emails or 200," with the agent riffing on content for personalization while a program drives every interaction (08:48-09:57).
- Why drive the web UI at all instead of the API: in corporate environments the Office 365 tenant API "requires an app registration, and it also requires admin approval, which as an employee you can't often get," whereas the web login the employee already has is sufficient. "In this pattern the web UI itself kind of becomes a universal API… a permissionless API" (09:57-10:43).
- Rung two in practice — the same JavaScript click aimed at a mega-retailer's add-to-cart button produces "literally nothing. There's no failure, there's no error, just nothing happens." The page is checking whether the click came from a human source; Chrome stamps every event trusted or untrusted, and untrusted input is quietly dropped. Switching to Chrome's input domain uses the same path as a physical mouse, the event is stamped trusted, and the item drops into the cart. In the page's own logs, "every one of the untrusted clicks fails, but the trusted ones go through." (The visible cursor in the demo is drawn programmatically to show the agent's inputs; the physical mouse is not moving.) (10:43-12:41)
- Rung three, target one — **Cloudflare Turnstile**, "the hardest target that we've hit yet," not because the check is hard but because the checkbox is unreachable: encapsulated beneath a *closed* shadow root, inside a cross-origin iframe, which itself contains another shadow root. "There's no element to grab." The solution stops trying to grab it: ask the browser where the iframe sits on screen, compute where the checkbox is, and fire a trusted click at that screen position — "a real click lands right in the checkbox" (12:41-14:12).
- Rung three, target two — **MTCaptcha** (distorted-text image CAPTCHA). The agent does what a person does: screenshot the challenge, use its own vision to pick characters out of the noise, then type the answer with real trusted keystrokes routed into the widget's cross-origin iframe one character at a time (14:12-15:00).
- Rung three, target three — a **Lemon** jigsaw/drag puzzle, representative of "an entire class of CAPTCHAs." No shadow root, no cross-origin iframe; the piece is in the page. The difficulty is the drag itself, because these challenges "sample the mouse movement into a trail of points the whole way," including jitter and changing speeds. The agent eases in gently, curves slightly, deliberately overshoots the target and eases back in — vision to identify the gap, human-like motion to cross it (15:00-16:30).
- Final target — **reCAPTCHA v2**, solved as one system in two halves. The **solver** is pure code, no model: trusted click on the checkbox, pierce into the challenge iframe, screenshot the grid every round, and re-arm itself if a round expires — "deterministic, fast, and free." The one step code cannot do is look at fuzzy tiles and decide what is in them; that is given to the agent, the **operator**, which takes one look per round, names the matching tiles, hands the answer back, and idles until the next lap (16:30-18:23).
- Why the split is forced rather than elegant: "this big bad boss is on a clock. Every round expires, and one challenge can be multiple rounds back-to-back. An agent that round-trips a model on every click and on every look burns that clock and loses. The challenge expires well before it ever finishes." The only working shape found was "deterministic code running at machine speed with one quick AI look per round" — which is also why it had to be a CLI rather than a model sitting in the middle of every interaction. He notes the result is repeatable and reliable, not a fluke (18:23-19:36).
- Closing takeaway, stated explicitly as the point of the talk: "the big takeaway is the methodology… the CAPTCHAs themselves were just tricksy little tests that demonstrate the methodology. This came down to careful, disciplined engineering, and the engineering enabled the agent to do something that it could not do at all off the shelf." The method restated: give the agent a CLI so you can program it; drive a whole browser through CDP using its digital senses; run the loop on the meatbag ladder and climb only as high as forced; explore until you solve it and write the solution down (19:36-20:22).
