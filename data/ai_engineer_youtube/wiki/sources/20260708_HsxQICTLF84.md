## Summary

Bennet Fenner (Zed, the Rust-based AI code editor) live-codes a minimal coding agent into an ACP-compatible one in ~15 minutes to demonstrate the Agent Client Protocol (ACP). ACP is a JSON-RPC protocol — an LSP/MCP analog for the *editor↔agent* boundary — that lets any client (editor) drive any agent through a unified interface, so users can bring their agent of choice to their tool and get one consistent UI across all of them. The talk shows the two durable halves: (1) the protocol shape — four minimal methods (initialize, authenticate, newSession, prompt, plus cancel), a session lifecycle keyed by a server-generated session ID, capability negotiation, and stdio transport; and (2) how agent work is surfaced to the client through session-update *notifications* rather than request/response — streaming `agent_message_chunk` for tokens, a two-phase `tool_call`→`tool_call_update` for tool visibility, a diff content type the client renders, a proxied file system so the agent sees unsaved editor-buffer changes, and a client-advertised terminal capability. The demo ends by bootstrapping the agent to add a terminal tool to itself.

## Notes

- Motivation: 2025 saw every major provider ship a terminal coding agent (Claude Code, Codex, Gemini CLI); Zed wanted users to bring any agent and get one unified interface, so it defined ACP, "similar to MCP or LSP… a JSON-RPC based protocol" where agents and clients talk through a unified interface. (00:14-01:06)
- Open source at agentclientprotocol.com; ~40 clients implement it (JetBrains, Obsidian, open claw — itself both a client and an agent). Agents support it either via an adapter that translates the agent's native language to ACP, or with a native ACP mode built into the CLI agent (opencode, cursor). (01:07-01:54)
- The base agent loop being wrapped: model APIs are stateless, so you attach the conversation, call the endpoint (Anthropic), get either an end-turn text message or a tool call, run the tool locally, append the result, and loop. Bare-minimum tools were read-file and edit-file (path + old_text→new_text replacement). (02:56-04:04)
- Minimal ACP agent = implement the SDK's agent interface with four methods: `initialize` (respond with supported protocol version + capabilities), `authenticate` (skipped — API key from env var), `newSession`, and `prompt`; `cancel` added as a nice-to-have. (04:16-04:33, 06:33-06:46)
- `initialize` responds with the latest protocol version; both client and agent advertise capabilities, and a minimal agent advertises nothing extra. (04:37-04:57)
- Session lifecycle: `newSession` generates a random ID, instantiates a coding agent bound to the client-provided current working directory, stores it in an internal map, and returns the ID; `prompt` carries the session ID plus an array of content blocks (text/images), looks up the agent, and runs the tool-calling loop (this minimal agent ignores non-text blocks). (05:04-06:30)
- Registering the agent in Zed needs no special code — you just tell Zed there is an ACP-compatible agent runnable as `node <path>/agent.js`. (06:46-07:00)
- Before wiring updates, the debug view showed Zed sending a `session/new` request, getting a session ID back, then a prompt returning only a stop reason with no visible tokens — the loop ran but nothing surfaced, motivating session updates. (07:37-08:11)
- Streaming: the coding agent is given the ACP connection + session ID; reacting to the Anthropic SDK stream's text event, each chunk is sent as a session update of type `agent_message_chunk` (a notification associated with the session ID). (08:17-09:38)
- Tool visibility is two-phase: emit an initial `tool_call` session update (title, kind/data for icons, status `in_progress`, associated locations), then at completion emit a `tool_call_update` (status + returned content) for that tool call. (10:51-12:16)
- ACP proxies the file system: if the client advertises a file-system capability, the agent calls `read_text_file` (and writes) over ACP instead of native `fs`, so an editor's unsaved buffer changes are visible to the agent rather than only what is on disk. (12:23-13:04)
- Diffs are an ACP content type: the agent sends old_text + new_text and the client (Zed) does the diffing/rendering. (17:27-17:38)
- Terminal capability: a client can advertise that it creates and manages terminals for the agent; the demo asked the running agent to add a terminal tool to itself (self-bootstrap), then ran `sleep 5; ls` and saw the live terminal + output in Zed. (15:08-16:30)
- Transport is stdio today; remote transport (JetBrains) is in progress. Caveat: the demo code is entirely agent-generated and "please don't use it in production." (17:51-18:03, 16:40-17:12)
