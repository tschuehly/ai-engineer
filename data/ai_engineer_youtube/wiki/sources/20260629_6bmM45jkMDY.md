# You Can't Prompt the Room: The Last Skill AI Won't Replace

Source: [You Can't Prompt the Room: The Last Skill AI Won't Replace - Balázs Horváth, VisualLabs](https://www.youtube.com/watch?v=6bmM45jkMDY)

## Summary

Balázs Horváth (founder of VisualLabs, a Budapest Microsoft partner, 13 years bridging business and IT on ERP/CRM programs) argues that once AI makes code, specs, tests, and implementations cheap to produce, the software-delivery bottleneck moves upstream to "people work": getting the right stakeholders in the room, eliciting the real requirements, and naming what is actually worth building. You can prompt your AI, your spec, your code — but "you can't prompt the room." He grounds this in a VisualLabs internal hackathon where 21 agent ideas were generated and 17 were abandoned (no data access, no clear business owner, or no measurable value); the 4 survivors run in production. Because AI is "coded to give you the most common answer," using it naively replicates what exists (a faster horse), so a human must read the room and name the problem to reach a car. The talk resurfaces the analyst/business-analyst toolkit as the newly scarce skill: story mapping (process backbone + user stories at the right altitude), the AI-native user-story structure (persona / what / need / why + acceptance criteria → test cases) that models were trained on, the VAD thinking path (Value → Architecture → Design) that separates production agents from demos, and the 4-question value framework. It closes with a measurement shift: stop counting features shipped, count features used more than twice, and move your smartest people upstream toward customers because deciding what to build is now the expensive part.

## Notes

- "Writing code is no longer the bottleneck… the real bottleneck is getting your people, your stakeholders, your decision-makers into the room… you can prompt your AI, you can prompt your whole specification, but you can't prompt your room." (00:32, 02:15-03:00)
- VisualLabs internal hackathon: ~21 agent ideas, 17 abandoned "because they actually created no business value" — either no data access or it just didn't make sense to build; the 4 survivors "had a very big impact on how we work today." (00:37-01:30)
- Henry Ford framing: asked what they wanted, users say "more horses"; AI "by definition is coded to give you the most common answers," so naive use replicates what exists — the job is to move AI "away from that average" to a car "a magnitude shift better." (03:10-04:20)
- The newly scarce skill is the analysis toolkit — story mapping, business model canvas, value canvas, design thinking — "those good old things that we are so used to using as functional consultants, business analysts." (04:24-04:43)
- Story map example (support system): backbone stages contact → triage → resolve → close; slice release one (capture intent, classify urgency, draft a grounded answer, log to system of record) as the MVP / first four user stories; second-row stories (read sentiment, route to a team, suggest next action, check satisfaction) become the backlog. Kept high-level so you can see the big picture and pick what to build. (05:09-07:00)
- User stories are a means to elicit stakeholder discussion, and should be written in the trained structure — persona / the what / the actual need / the why — plus acceptance criteria "based on which you can derive the test cases," because "AI is really good at pattern recognition and it was actually trained on the user story structure." Daisy-chain stories into a coherent system → specification → code. (06:30-07:50)
- 4-question value framework: (1) Whose problem is this? (name a direct persona) (2) What does winning look like for them? (the right outcome, quick/smooth/safe) (3) What would make them refuse to use it? (not on their platform, cumbersome, data-security) (4) Would it change a decision, and which one? Track all four in "a good old markdown file in your repository so that AI can access it… get way more context out of it." (08:08-09:40)
- VAD thinking path — Value → Architecture → Design: understand how value is created and what value the customer wants, then the underlying process/architecture that supports it, then design a system around it (and what process changes are needed). A generic prompt ("build us an agent that handles support") "will not get the answer you want." (09:40-10:50)
- "Isn't this just good old product management?" — yes; "old skill, but new economics." Everyone has the same models/tools, so the differentiator is who understands the business need better. (10:50-11:40)
- Building-the-wrong-thing signals: high shipping velocity with poor adoption; people log in to the newest thing but don't reuse it — "don't look at time of usage and time spent on site… look at the frequency of a certain activity." Anti-patterns: "the demo is the deliverable" (a demo system is not a live system) and a PRD with no real user testers. (11:40-12:35)
- "Everything needs to be moving upstream" — pre-boom the smartest people wrote code; now shift them toward customers and business problems and spend more time deciding what to build "because that's the expensive part. Building it has actually become very cheap." (12:35-13:20)
- Monday-morning actions: audit the wrong things you track; replace "number of features shipped last quarter" with "number of features shipped that is actually used more than twice"; move subject-matter experts into customer-facing / decision-making roles; run a mapping session (user story map or business model canvas) before you build. Personal takeaway: comparing wibe-coding with vs. without user stories was the "big shift" — "we can build the right thing and not just the next thing." (13:20-15:20)
