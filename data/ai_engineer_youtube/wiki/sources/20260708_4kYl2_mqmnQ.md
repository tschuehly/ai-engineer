# I Run a Fleet of AI Agents Across Three Machines. Here's What Broke.

Source: [I Run a Fleet of AI Agents Across Three Machines. Here's What Broke. - Kyle Jaejun Lee, KRAFTON](https://www.youtube.com/watch?v=4kYl2_mqmnQ)
Uploaded: 2026-07-08
Transcript: `raw/20260708_4kYl2_mqmnQ/4kYl2_mqmnQ.en-orig.vtt`

## Summary

Kyle Jaejun Lee (AI Platform Engineer, KRAFTON) gives an honest field report from a personal fleet of coding agents he runs as a daily driver across three machines (a MacBook for heavy coding, two always-on headless Linux boxes) under one control plane. The first thing that broke was him: a wall of tmux panes made him "the scheduler, the memory, and the reviewer" for six live contexts, which does not scale. His fixes are concrete and reusable: (1) structure agents as a real org hierarchy — CEO/VP/manager/worker as actual entity types, each with its own scoped context and approval boundary, so context flows down, results flow up, and the human holds exactly one context instead of six; (2) move state out of the model onto disk (per-entity workspaces with `shared/`, `machines/`, and a mission/status/handoff layout) and — "the single most practical thing I learned all year" — *reset instead of compact*, clearing the context completely and letting the agent re-read its own handoff/history files so work survives context wipes and machine crashes; (3) a blocking review gateway where any layer submits a plan and waits, and an approval hook fires the work automatically, collapsing many panes into one web inbox. Scaling from one machine to three surfaced five failures (agents doing work instead of delegating; worker panes too crowded for `tmux capture-pane` to read; OOM from stacked Claude/MCP processes; credential collisions across workspaces; a laptop dying and losing in-flight jobs), each fixed operationally, and cross-machine coordination brought git-based context transfer, per-machine vs. shared-via-PR directories, one collapsed always-on gateway, and a Discord phone router. The talk's punchline: an agent should declare *what* it needs, not *where* it runs — and those are exactly the compute/secrets/scheduling questions Kubernetes already answers, so he's building his orchestration/review/context layer on top of a cluster scheduler rather than reinventing it.

## Notes

- The fleet: MacBook (heavy coding + personal projects, sleeps because it's a laptop), Linux A (long-running coding tasks), Linux B (short-lived personal side projects), both headless and always-on, "two operating systems, one control plane." Not a demo — "this is what I actually use all day, every day." (00:05-00:45)
- The human breaks first: a few tmux panes become four/five/six live contexts; "I'm not running agents anymore. I've become the scheduler… I'm the memory… and I'm the reviewer… One human, three roles, six contexts. It does not scale." "My own attention was the bottleneck." (00:45-01:28)
- Org-hierarchy unlock (from "how does a handful of executives run a company of thousands?" — they separate context, each person sees only their slice): CEO/VP/manager/worker as "real entity types in the system. It is not a cute metaphor." Each is its own agent with scoped context and its own approval boundary; context flows down (each layer gets only the slice it needs), results flow up, "I only review what reaches the very top… instead of holding six contexts in my head, I hold exactly one." (01:28-02:12)
- State on disk: every entity gets its own workspace; shared context everyone must honor lives in `shared`, machine-bound state under `machines`, and inside each workspace the mission, current status, and a `handoff` folder (the actual work product passed along). "The state lives in files. It is not trapped inside one model." (02:12-02:42)
- Reset, don't compact: when the window fills, the built-in move is compact (summarize history). "I stopped doing it. It's slow. I can't choose what survives. And whatever it throws away is just gone." Instead, inside Claude he clears the context completely, then it reads back the handoff and history files it wrote for itself and "picks up exactly where it left off. The context can get wiped, the machine can even crash, and the work still survives because it was never only in the model." (02:42-03:20)
- Review gateway for alignment/drift: plans flow down but drift, and he used to catch it only by walking into each pane by hand. Any layer that wants to act submits its plan and blocks — "Nothing runs until I approve. And the second I approve, a hook fires the work off automatically. One web inbox, one control point, I never walk into the work windows anymore." He didn't build it by hand — "an infra team inside the fleet built it. Agents building the tools that run the agents… that's kind of the whole point." (03:20-04:11)
- Five single-machine failures: (1) agents did the work themselves instead of dispatching down to a worker — fixed by forcing the orchestrator's hand with "a CLI harness with skills that call those CLIs. So dispatching becomes the only path it can take." (2) Managers kept spinning up more worker panes inside one window until panes were too small to read and even `tmux capture-pane` couldn't pull anything meaningful. (3) Out of memory — activity monitor buried under Claude Code and MCP processes, swap almost full, sessions stacked until "the machine couldn't breathe." (4) Credentials collided and bound to the wrong workspaces — fixed with a clean, fully separated environment per workspace. (5) The laptop lost power/network and every in-progress job died; it had restarted itself with everything in flight gone — fixed with a boot command (`overlord boot`) that brings the whole fleet back "because all the state was sitting in files." (04:08-06:04)
- Multi-machine coordination: offload heavy long-running work off the laptop to always-on Linux A/B, one control plane over all. Move context between machines with git — commit and push context files, then `tmux send-keys` over SSH to tell the other machine to pull; the agent there reads the files and resumes. Conflicts (two machines editing the same directory) fixed with per-machine directories for machine-specific state and shared state changed only through a pull request — "boring is what stops the two machines from silently disagreeing." (06:04-07:04)
- Collapse the gateways: one gateway per machine meant multiple inboxes again, so every machine sends review requests over SSH into one main gateway on an always-on Linux box — "Your one point of control can't be a thing that falls asleep" (the Mac sleeps). A Discord router (one bot per machine: Mac, Linux A, Linux B) makes his phone the remote control for the whole fleet, after he once couldn't remember which machine he'd built a feature on. (07:04-07:53)
- Four unsolved problems (consistency across machines, abstracting local-only tools stuck on the Mac — MCP servers, the browser — secure credential handoff between instances, and resource management) all reduce to: "An agent should just declare what it needs, not where it runs. Above it sits the orchestrator, the review gate, the logical hierarchy. Below it, compute, secrets, tools. A scheduler places it, and the machines just disappear underneath. These are the exact questions Kubernetes already answers." He's stacking Kubernetes underneath for compute/secrets/tools and building task orchestration, review flow, and context management on top — "reuse what exists, build the new part on top." (07:53-08:52)
- Honest state: "One machine, I solved. Across machines, still rough, still building… this is the part nobody has figured out yet." (08:52-09:09)
