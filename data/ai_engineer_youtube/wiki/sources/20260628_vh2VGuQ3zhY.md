# The 100-Tool Agent Is a Trap

Source: [The 100-Tool Agent Is a Trap - Sohail Shaikh & Ankush Rastogi, Prosodica](https://www.youtube.com/watch?v=vh2VGuQ3zhY)
Uploaded: 2026-06-28
Transcript: `raw/20260628_vh2VGuQ3zhY/vh2VGuQ3zhY.en-orig.vtt`

## Summary

Sohail Shaikh and Ankush Rastogi (Prosodica) diagnose the "Fat Agent" anti-pattern — loading every tool's name, description, and JSON schema into the system prompt on every request — and show with benchmarks that it collapses as the catalog grows: tool-selection accuracy falls from ~78% at 10 tools to 13.6% at 741 tools while a 741-tool catalog costs ~127,000 tokens per request before the user's question is even read, and time-to-first-token past 500 tools can exceed 5 seconds. Their fix is a **Semantic Tool Router** — "RAG for tools": embed each tool description offline into a vector index, then at runtime embed the user query, retrieve the top-K (K≈3–5) closest tool descriptions, and inject only those schemas into the model call (**Just-in-Time Context Injection**). The routed agent stays above ~83% accuracy across the same catalog sizes with roughly flat latency and ~99% fewer tool-context tokens, echoing Anthropic's reported 150k→2k token drop from on-demand MCP tool loading. The talk closes with an evaluation-and-tuning discipline (four metrics, a K-sweep, three named failure modes) and a production checklist.

## Notes

- Fat Agent definition: give the model every tool definition on every request — every function name, description, and JSON schema goes into the prompt whether the user needs it or not. Works in a demo and at ~10 tools, but breaks as the catalog grows to 30, 100, or more. (02:19-03:00)
- Root cause is structural, not per-tool: "the design does not fail because one tool is badly written. It fails because every request is forced to carry the entire catalog." (03:31-03:47)
- Token cost: 741 tools ≈ 127,000 tokens just for tool descriptions/schemas, paid on every request before the user's question is considered; at 100,000 requests/day this is billions of tokens/day just to describe tools. (06:00-06:30)
- Accuracy collapse (fat agent): ~78% correct tool at 10 tools, ~40% at ~100 tools, 13.6% at 741 tools (≈1 correct in 8). Semantic router stays above 83% across the same catalog sizes because the model chooses from a small relevant set, not hundreds. (04:31-05:20, 26:10-27:20)
- Lost-in-the-middle explanation: models attend more strongly to the beginning and end of long context, so hundreds of tool schemas packed into the middle are used unreliably — "we end up paying for a huge prompt, and that prompt makes the decisions even harder." (05:24-05:55)
- Latency: with the fat agent, time-to-first-token grows with the catalog because the model must process a larger prompt first; ~500 tools can push first-token latency past 5 seconds. Router TTFT stays almost flat because prompt size is bounded. Core lesson: "the catalog can grow, but the model's working set should stay small." (06:50-07:25, 15:00-15:20)
- Token reduction: JIT routing injects only ~3–5 relevant schemas, closer to ~1,000 tokens — roughly a 99% reduction in tool-context tokens. (06:30-06:50)
- Semantic routing = "RAG for tools": (1) each tool has a clear description; (2) embed descriptions offline into a vector index when the catalog is created/updated; (3) at runtime embed the user query with the same embedding model, nearest-neighbor / cosine search the index, return top-K (K=3 or 5), inject only those schemas. If you already have an embedding model and vector DB, the infrastructure is familiar. (09:20-12:00)
- Just-in-time context injection is the context-management strategy paired with the router (the retrieval layer): don't load everything before the query is understood — wait until the query is known, then inject only what's needed. Not a new idea: lazy loading, JIT compilation, on-demand resource loading applied to LLM context. (11:30-12:10)
- The router doesn't just add the right tool — it also *removes* the wrong tools from the model's choice set, which reduces cross-tool confusion. Example: "find me a flight to New York" surfaces search-flights/book-flight/calendar-check; hotels/weather/email tools are "simply not available at this request." (18:30-20:00)
- Anthropic community signal: on-demand tool loading via MCP reported token usage dropping from 150k to 2,000 (98.7% reduction). Cited as the signal that large tool catalogs should be retrieved when needed, not dumped into every prompt. (12:10-12:40, 22:00-22:30)
- Evaluation methodology: measure four things — tool-selection accuracy, time-to-first-token, input tokens per request, estimated cost per 1,000 calls. Datasets: Berkeley Function Calling Leaderboard, Skills-bench-style scenarios, and synthetic tool pools scaled to 10/50/100/200/1041 tools. Run identical queries fat vs. routed (same model, answer key, catalog). (13:14-14:00)
- K trade-off: smaller K is faster and cheaper; larger K recovers more edge cases. K=5 is a strong default starting point; sweep K at 3/5/10 and pick the smallest K that meets the accuracy target. (14:00-14:20, 21:20-21:40)
- Threshold guidance: fewer than 20 tools, a router may be unnecessary — load directly (static loading fine for 10–15). Past ~50 tools in production, a router-based schema makes sense. But tool confusion can appear with only a few tools, long before 100. (08:40-09:10, 22:40-23:00)
- Implementation pattern (3 steps): (1) offline — build catalog (name, description, schema), embed description, store in a vector DB (Chroma DB, Pinecone, Qdrant); (2) every request — embed query, nearest-neighbor search, return top-K; (3) every request — fetch schemas for selected tools, pass only those into the model call, and log which tool was selected. Runtime overhead is small: one embedding call + one vector search. (15:20-16:40)
- Production checklist: lock tools in one place (name, description, schema, owner, version); build the index; write the router (embed query → search → top-K → fetch schema); wire it into the agent loop so the model's tool list comes from the router, not a hard-coded full catalog; evaluate at K=3/5/10 and pick the smallest K meeting the accuracy target; monitor production (log selected tools, final tool calls, failures, fallback usage) and re-embed tools when descriptions/schema change. "Not a 6-month platform rewrite… for most teams it is a focused sprint." (20:40-22:00)
- Trade-offs / failure modes: (1) router miss — router fails to retrieve a needed tool; handle with a fallback (widen K, run a second retrieval pass, or route to a broader tool group). (2) weak tool descriptions → weak embeddings; write descriptions in the words users actually use, encoding intent, action, and key entities. (3) rare tools — some never score high unless their descriptions include the right language; monitor misses and rewrite. (24:20-25:40)
- Ecosystem: Aurelio Labs open-source semantic-router project; Toolbench; Berkeley Function Calling Leaderboard; the Anthropic MCP on-demand-tool-loading write-up; MCP Zero (open-source, routing at thousands of tools across many servers); vector stores Pinecone, Qdrant, Chroma. "You don't need to invent the ecosystem from scratch." (23:30-26:20)
- Closing: "If your agent starts failing as tools are added, it doesn't automatically mean your prompts are bad. It may mean the architecture is asking the model to solve the wrong problem." The goal is not more complicated agents — it's to stop forcing the model to reason over irrelevant tools. (26:20-27:00)
