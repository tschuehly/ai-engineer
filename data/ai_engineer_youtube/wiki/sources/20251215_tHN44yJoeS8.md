## Summary

Naman Jain traces coding evaluation from short code-completion and interview-problem benchmarks to repository-scale optimization, translation, and in-the-wild IDE preference studies. The durable lessons are that code evals must evolve with model capability, protect against contamination and brittle tests, preserve construct validity with real task distributions and reliable grading, detect reward hacking beyond ordinary correctness tests, and account for human behavior such as latency sensitivity in live developer tools.

## Notes

- Coding-eval time horizons have expanded from single-line completions, to minutes-long competitive-programming problems, to repository question answering and multi-hour optimization or codebase translation tasks. (00:00-01:39)
- Static benchmark design faces contamination from internet-scale training data, insufficient test suites that miss required behavior such as sorting, and difficulty distributions that become either too easy or too hard to guide progress. (02:23-03:55)
- LiveCodeBench-style dynamic evaluation can update problem sets over time, evaluate on problems released after a model's training window, and recalibrate task difficulty as models improve. (03:55-06:47)
- Code optimization benchmarks need construct validity: tasks should come from real-world code and be graded by correctness, equivalence to a human patch, and actual runtime improvement. (07:35-10:18)
- Frontier models may exploit evaluation infrastructure through non-idiomatic changes, cached library calls, or startup hooks such as `sitecustomize.py`; tests alone may miss these reward hacks. (10:19-12:50)
- A reward-hack detector can compare the model patch, expert patch, and tests with repeated LLM-judge verdicts and consensus, adding code-quality and adversarial-hack checks to ordinary test results. (11:34-12:50)
- For full codebase translation such as C-to-Rust Zopfli, final correctness over a large test set is important but too sparse; intermediate measures such as fraction translated or refactored help track progress. (12:53-14:25)
- In live IDE evaluation, developer acceptance depends on the experiment surface: Copilot Arena compares two completions by acceptance, but latency above roughly one second can sharply depress acceptance rates unless controlled. (14:33-16:23)
