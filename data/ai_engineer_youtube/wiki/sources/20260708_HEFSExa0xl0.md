# Teaching Coding Agents to do Spreadsheets

Source: [Teaching Coding Agents to do Spreadsheets - Nuno Campos, Witan Labs](https://www.youtube.com/watch?v=HEFSExa0xl0)
Uploaded: 2026-07-08
Transcript: `raw/20260708_HEFSExa0xl0/HEFSExa0xl0.en-orig.vtt`

## Summary

Nuno Campos (Witan Labs) reports four months of work getting coding agents as good at spreadsheets as at Python or JavaScript, moving an internal financial-analysis benchmark from ~50% to 92% accuracy. The single biggest jump (50% → 74%) came from replacing ~15 accumulated tools with one Node.js REPL — code mode *with persistent state*, so variables survive across calls, the agent writes shorter scripts and interleaves more reasoning, and new capabilities are added as JavaScript methods surfaced to the model through a TypeScript type-definitions file in the prompt rather than new tool schemas. The other durable lever was building high-fidelity engines (a formula engine and an image render engine) to close a verification/feedback loop for a domain where code-style tooling doesn't exist off the shelf; an *incomplete* engine produces worse results than none, and the loop (not the REPL interface, which will change as models get better at computer use) is the durable part — more capable models extract more from it. Supporting lessons: domain knowledge in the prompt (reminding, not teaching) survived every tool iteration and was portable across architectures; deterministic evaluation (golden-spreadsheet black-box I/O comparison) beats LLM-as-judge where possible because judge drift confounds score changes; and much apparent agent confusion is really infrastructure bugs (a broken tool, a wrong prompt example) that the model faithfully follows or retries around.

## Notes

- Goal and result: get coding agents "as good at spreadsheets as they are at Python, JavaScript"; started at ~50% on an internal financial-analysis benchmark and reached 92%. (00:27-00:46)
- Why spreadsheets are deceptively hard: a human "instantly sees the structure" (revenue table here, assumptions there, a chart) visually, but an LLM sees none of it — asked "what's the revenue?" it must disambiguate net/gross, quarter/year, and whether a cell is an input or a formula. (00:56-01:50)
- Dead end — three-agent split: a central edit agent with a five-step define-end-state / plan / execute / verify process changed *where* errors happened (mistakes made while planning are easier to rectify than mistakes made while building a model), but the architecture was too rigid — discovery ran once up front and couldn't be revisited, and context didn't flow between the agents. (01:53-02:44)
- Dead end — representations: they "tried every conceivable way of representing a spreadsheet to an LLM." SQL (decades of training data, good for structured data) didn't work; XML (Excel's on-disk format) didn't work. Two survived as *methods inside the REPL*, not standalone: CSV/TSV views of part of a sheet (used very often as one piece of the larger solution), and HTML, which introduced layout/formatting and led to a rendering engine that shows the agent the rendered sheet as an image. (02:47-04:20)
- Breakthrough — one REPL replaces ~15 tools: all 15 tools became JavaScript functions the agent combines in one Node.js REPL call. JavaScript was chosen because it is easy to sandbox and LLMs are familiar with it (Python "would probably work equally well"); the actual spreadsheet implementation lives in C# — use the scripting language for the agent interface and the right language for the files. (04:11-05:33)
- Before/after: previously 10-15 sequential tool calls to explore a sheet and reach an answer, often timing out because work was sequential (even parallel tool calls didn't help because results couldn't be combined); after, the agent combines everything in a single call and gets all results at once. (05:33-06:05)
- Code mode vs. REPL: code mode (Anthropic API, Cloudflare) already combines multiple tools into one call; a REPL "goes further" — it's "code mode with persistent state," so variables defined in one call are still there in the next and the agent builds on its work. Pure code mode led to ~50-line scripts (doing many things at once); the REPL produced *shorter* scripts, letting the agent interleave reasoning between steps and often reach a better answer faster. (06:08-07:34)
- Adding capabilities is cheap: with separate tools, a new method (e.g. explore formula dependencies) meant several new tools in the schema plus figuring out how they interact; with the REPL, it's a few more JS methods, made visible to the agent by putting a TypeScript type-definitions file in the prompt — "works really well." (07:37-08:20)
- Results and timeouts: 50% (pre-REPL) → 74% (REPL) → 92% via smaller changes (fuzzy search, formula tracing for dependencies, system-prompt tweaks, bug fixes), none as dramatic as the REPL. A 5-minute task timeout was used ("if it takes longer than 5 minutes to answer a question about a spreadsheet, that's not useful"); the REPL approach produced essentially zero timeouts by being more efficient. (08:24-09:24)
- Feedback loops for a non-code domain: coding agents do better when they can run the compiler/linter/tests and iterate; the same is true of spreadsheets, but the feedback loop had to be *built* — a formula engine (to calculate formulas) and a render engine (to render a range to an image with formatting/layout). That rendered output is "the source of truth… the verification loop" that makes the agent confirm it did the right thing and fix formulas/formatting when it didn't. (09:28-10:52)
- High-fidelity requirement: the loop is only as good as the engines. An engine implementing, say, 50% of Excel's formulas produces *worse* results, because the agent writes a formula that would work in practice, computes it, and gets a wrong result or an error because it isn't implemented. (10:52-11:19)
- REPL is the interface (transient); the verification loop is durable: a REPL is the best interface *today* because coding is what SOTA models are best at, but as labs improve computer use, a mouse/keyboard interface may win — "you should expect to have to revisit" the interface. The verification loop behind it is "the more durable part"; across four or five model releases during the project, "the more capable the model is, the more they can get out of that verification loop." (11:21-12:37)
- Domain knowledge in the prompt: adding domain knowledge to prompts survived every tool iteration and always improved results — not because LLMs don't know what revenue or ARR means, but because they "know many many things" and you "pigeonhole them a bit into what you want them to focus on." It's "reminding it to pay more attention" rather than teaching, and it's super portable — almost the same prompt worked for the REPL, the individual tools, or any other approach. (12:37-13:25, 18:01-18:16)
- Evaluation — deterministic over judge: they started with LLM-as-judge only ("sometimes the only option you have"), but the annoyance is you can't tell whether a score change came from the agent or from the evaluator changing its output. Where possible they replaced it with deterministic comparison — e.g. a golden spreadsheet as a black box: put a set of inputs in, get outputs; put the same inputs into the model-produced sheet and check the outputs match — "sometimes more trustworthy than just using an LLM to grade." Evaluating correctly was "a really important part" of knowing whether CSV/SQL representations were actually good. (13:29-15:05, 18:18-18:38)
- Agent confusion is often bugs: infrastructure bugs "many times end up looking like reasoning failures" — a bug in the code, a wrong example in the skill/prompt that the model follows very faithfully, or a failing tool that the model keeps retrying around so it "seems like the model is being dumb." "A lot of juice" comes from just reading the traces to separate model limits from fixable bugs; "always check your traces and your plumbing." (15:08-16:02, 18:38-18:47)
- Generalizable summary: (1) "if your agent is making many sequential or even parallel tool calls, you've kind of invented a bad scripting language — give it a real one" (code mode or REPL); (2) feedback loops really matter, and if none exist for your domain it's worth building the rendering/calculation engine; (3) interfaces are super important but you should expect to revisit them as model capability shifts; (4) don't underestimate planning ("think before you act"); (5) domain knowledge matters — remind the model what to attend to; (6) prefer deterministic evaluation, keeping LLM-as-judge as the fallback; and always check traces because "agent confusion is just bugs." (16:12-18:47)
