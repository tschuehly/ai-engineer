# OpenClaw in Your Hand: Building a Physical AI Terminal

## Summary

Lech Kalinowski (PhD physicist, Callstack technological incubator) built "Vault," a text-first, dual-display handheld AI terminal — an ESP32-S3 dual-core microcontroller with a keyboard, encoder, a small emissive OLED, and a bistable e-paper display, all on one lithium-polymer cell — to act as a calm, distraction-free remote control for an OpenClaw agent instance running on his NVIDIA DGX Spark. The durable engineering lesson is architectural: **keep the model off the metal.** The MCU runs a tiny, fast firmware that does only I/O and rendering (pre-allocated one-bit image buffers, no markdown engine and no `malloc` on the MCU), while a dependency-free Python backend hosts all the heavy work — it dispatches to local models, autonomous OpenClaw agents, and a game engine, serving an open-source ~120B-parameter model (gpt-oss:120b) via NVIDIA TensorRT-LLM exposed behind an OpenAI-style LLM proxy (needed because not every open model matches the OpenAI API shape). The device switches among four modes with a single slash command — shell (control the terminal itself: settings, Wi-Fi), assist, control (drive OpenClaw), and an LLM-native RPG — and surfaces an agent's thinking and tool calls in real time across the two surfaces (fast OLED for live typed/streamed text, slow e-paper for the final rendered content). The talk's second durable idea is design-level: the RPG is built around **narrative state, not numbers** — no HP or dice, just LLM-tracked mood, NPCs, memory, and generated worlds/maps (rendered as one-bit matrices) — with the takeaway "try narrative, context matters, and in general not numbers." Also notable: hard-won hardware war stories (software I2C wiring, a GPIO-13 silent failure, a power regulator that kept killing the fragile OLED/e-paper, a cheap noisy encoder) each cost about a day, and the device is deliberately fault-tolerant (OLED down → e-paper works; keyboard down → encoder; Wi-Fi down → local shell).

## Notes

- Motivation and product framing: wanted a "physical and AI-native" device — a calm, text-first, distraction-free terminal to remote-control an OpenClaw instance on a DGX Spark, filling a market niche opposite audio/video-interface AI gadgets; filed a provisional patent. (00:00-04:00)
- Four modes switched by a single slash command: internal shell (system settings, Wi-Fi, config), assist, control, and an LLM-native RPG. (04:55)
- Dual-display split: a fast emissive OLED "live" surface shows dynamic typed/streamed text; on trigger (Enter) the final render is committed to the slow bistable e-paper "content" surface. (05:45)
- MCU rendering discipline: fixed static buffers rendering one-bit images stored in pre-allocated memory — "no markdown engine and no `malloc` on the MCU side." (06:54)
- Hardware: ESP32 dual-core MCU, OLED, keyboard, encoder, and a substantial power-management/supply unit (two boards were blown up during prototyping, so voltage/current stability was a first-order concern). (06:00-08:30)
- Backend architecture: Vault firmware on the terminal talks to a large backend that handles all agentic OpenClaw work and the LLM; demo model is open-source gpt-oss:120b (~120B params) served the "most optimal way" via NVIDIA TensorRT-LLM, exposed OpenAI-style behind an LLM proxy because not all open models match the OpenAI API. (09:00-09:40)
- Example agentic use: typed "write a Java example," and OpenClaw + the LLM wrote it and stored it on the local machine; also checked DGX Spark disk space through the control mode. (09:40-10:20)
- War stories, each ~a day: software I2C (a way to control I2C without extra physical pull-ups), a GPIO-13 silent failure (had to move ports), the power regulator killing the LED and fragile display parts (weeks to source replacements), and a cheap encoder's rotational noise requiring added pull-ups/capacitors. (10:37-12:10)
- LLM-native RPG: built an NPC with memory and an "ominous" world mood; four worlds (cyberpunk "neon abyss," a Witcher-like fantasy "old guns"/"the hollows," and a deep-space "the void"); characters, worlds, maps, and skills are all generated and converted to one-bit matrices for the displays. (13:22-14:30)
- Fault tolerance / "bulletproof": OLED failure → e-paper still works; keyboard failure → encoder; Wi-Fi failure → local shell always available. (14:50)
- Numbers: ~130 commits over ~3 months, 2 displays, 4 modes, 4 worlds, 16 classes; tiny/fast firmware; one lithium-polymer cell. (15:30-16:00)
- Takeaways: "keep the model off the metal" (no LLM runs on tiny MCUs today) and "try narrative, context matters, and in general not numbers"; framed as "basically a Game Boy" to play with LLMs. (17:28-18:20)
