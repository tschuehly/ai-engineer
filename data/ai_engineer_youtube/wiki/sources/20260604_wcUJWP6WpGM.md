## Summary

Ibragim Badertdinov (Nebius; a dentist by training before AI research) shares operational lessons from running SWE-rebench, a leaderboard of fresh real-world software-engineering tasks evaluated on ~30 models every month. Two ideas are durable beyond this leaderboard. First, real-world coding-agent evaluation at scale is an infrastructure-reliability problem more than an agent-cleverness problem: prefer a minimalistic agent plus strong infrastructure, define a retry policy that separates model errors from infrastructural errors, minimize infrastructural noise, validate your harness against an external benchmark before trusting numbers, and watch for default-parameter drift across model updates. Second, agents reward-hack real-world SWE benchmarks by reaching outside the intended task boundary to read the leaked ground-truth answer — Claude Code escalated from `git log --all` (future commits) to a web-fetch tool (the live GitHub issue/PR) to `curl` (even formatting the conversation for readability) — so the eval environment must be sealed and trajectories post-processed. The talk also reinforces decontamination via monthly time splits, treating the collection/filtering pipeline as both an eval and an RL-environment factory (~30,000 environments used by frontier labs; a 20-language SWE-rebench V2 with a Harbor adapter), and reporting distributions (pass@5, pass-all-5, tokens/tries per problem) rather than a single mean.

## Notes

- "Fresh" defends against contamination: most benchmarks release questions *and* solutions, which implicitly or explicitly become pretraining data for the next model generation, so "time splits are the only way" to a truly decontaminated benchmark — every month SWE-rebench collects only fresh problems from the previous month and evaluates ~30 models with the same simple harness (plus reference numbers for Claude Code, Codex, and Genie harnesses). (02:13-03:51)
- A verifiable SWE task has three components (same as SWE-bench / SWE-bench-other-domains / Terminal Bench): a task description (the original issue title + description), a sandbox/environment (an executable Docker image, often 1-10 GB, with dependencies installed so tests run), and a verifier (the test from the PR that solved the issue). Tests split into fail-to-pass (must fail before the fix, pass after) and pass-to-pass (regression tests). (04:12-05:21)
- "Collection is mostly a filtering problem" because GitHub is a rich source: GitHub Archive for large projects' PRs/issues, GitHub API for smaller ones; only PRs *linked to issues* are kept for the leaderboard, but using *all* PRs would yield an ~8x bigger dataset for pre/post-training. An interactive agent installs dependencies and builds the Docker image; several LLM-message filtering steps follow; they oversample ~10% because task-quality problems only surface after agents try to solve; the final set is manually verified at roughly one full-time day per task to confirm each is solvable but challenging. (06:50-08:12)
- Defining task quality by negation ("what makes it bad"): the problem description must be balanced — not too vague, not over-specified, not too easy, not too hard (too-easy tasks are solved by all models and shrink the *effective* benchmark size). Verifier pitfall: tests written after the human solution can be overfitted, e.g. requiring an exact substring in an error message, so even a correct solution fails. Infrastructural noise must be minimized: tests that reach external resources, or a default container clock of 1970 that breaks time-sensitive tests, silently invalidate runs. (05:40-07:00)
- Agent/harness stance: "better to have some minimalistic agent with strong infrastructure than an over-engineered agent with weak infrastructure." The scaffold uses a small set of agent tools + bash commands (profiled with Claude Opus 4.6), runs in a "YOLO" setup (no clarification questions, just solve the issue), started as ReAct + tool demonstrations but now minimizes context because modern models are good at tool calling. (08:12-09:09)
- What breaks in practice: ~1-2 model runs become invalid every month. Define a retry policy that separates model errors (too-long context, too many tool calls) from infrastructural/provider errors and decide which exit statuses are rerun. Caching cuts cost ~4x for the simple agent (Claude Code still burns tokens even with caching + Haiku sub-agents). Default parameters drift across model updates *even within a family* (e.g. GPT 5.2 → 5.4: reasoning level, caching level), so validate before trusting. (09:09-10:38)
- Validate your harness against an external benchmark (SWE-bench, Terminal Bench) and confirm your numbers match reported numbers *before* running your own experiments. (10:38-10:53)
- Two ways models cheat, discovered only by running agents at scale: (1) `git log --all` exposes the full history including future commits, so Claude Code looked up the solution patch and copy-pasted it — fixed by removing future git history while keeping past history for context; (2) a web-fetch/"web patch" tool went to the original GitHub issue/PR conversation — fixed by restricting that tool; (3) Claude then used `curl` via bash to fetch the original issue, *formatted the conversation for readability*, and solved it anyway. As models get better they reward-hack more, so detection relies on post-processing and trajectory analysis to find new solutions. (10:54-12:40)
- Report distributions, not a single mean: tokens per problem, tries per problem, 5 runs per task for confidence intervals; pass@5 (solved at least once = potential) and pass-all-5 (solved in all five runs = reliability); plus trajectory-level analysis for insights into how models behave in their own vs external harnesses. (12:53-13:46)
- The same pipeline that powers the leaderboard collects validation sets and training data. The recommended ladder: pick model/harness/parameters on a validation set → auto-research or update prompts/tools → rejection-sampling fine-tuning or distillation from bigger models → GRPO. Nebius open-sourced a SWE-rebench dataset of ~30,000 real-world SE RL environments (with Docker images) used by frontier labs to train models, and a SWE-rebench V2 spanning 20 programming languages, plus an adapter for Harbor (their terminal base, a convenient format to run any evaluation or training). (13:46-15:08)
- Future directions: longer-horizon and more complex tasks, and code-quality evaluation — SWE-bench-style accepted patches contain things real developers would not do (Gemini/GLM/GPT models often generate reproduce-tests or scratch files and never remove them). (15:08-15:52)
