## Summary

Garrett Galow explains how repeated OAuth consent across many MCP servers creates both user friction and enterprise visibility gaps, then presents Cross-App Access as an identity-provider-mediated trust bridge between MCP clients and MCP servers. The talk is useful for AI engineering agents because it frames agent tool authentication as enterprise infrastructure: MCP clients, MCP servers, authorization servers, and identity providers need shared policy, short-lived tokens, and explicit limits around what authentication does and does not authorize.

## Notes

- Repeated MCP OAuth consent screens do not scale across teams because each user may connect a half dozen or dozen servers, and those connections multiply across many developers. 01:19-02:39
- The enterprise risk is not just annoyance: IT may lack visibility into arbitrary MCP clients and servers, cannot centrally determine which agents should access sensitive systems, and may miss local API keys or credentials outside the identity provider. 03:49-05:40
- Cross-App Access lets an identity provider act as the trust bridge between an MCP client such as Cursor or Claude Code and an MCP server such as Figma, allowing credentials to be issued without repeated human consent screens after the user signs in through SSO. 06:37-09:20
- The described flow has four systems: MCP client, identity provider, resource authorization server, and resource server. The client uses an identity JWT authorization grant token from the IdP, exchanges it with the resource authorization server, then proceeds with a normal OAuth access token to the MCP server. 09:34-11:49
- XAA can improve revocation posture because access tokens can be short lived, around five minutes in the example, and refreshed only while the user's SSO session remains valid. 12:20-13:06
- MCP server implementers need to advertise and accept the JWT bearer flow, verify signed JWTs with the identity provider, and then issue normal access tokens. 15:41-16:19
- In Q&A, Galow clarifies that XAA is authentication by default, not full authorization; users still receive their normal Figma permissions, while future scoped access caveats are not part of the spec as described in the talk. 17:00-17:56
