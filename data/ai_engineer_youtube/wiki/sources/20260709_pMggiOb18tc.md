# The Golden Age of AI Engineering

Source: [The Golden Age of AI Engineering — Alexander Embiricos & Romain Huet & Peter Steinberger, OpenAI](https://www.youtube.com/watch?v=pMggiOb18tc)
Uploaded: 2026-07-09
Transcript: `raw/20260709_pMggiOb18tc/pMggiOb18tc.en-orig.vtt`

## Summary

An OpenAI Codex keynote in two halves. Alexander Embiricos and Romain Huet argue engineering is returning to its roots (problem-solving over code-writing) as model cadence accelerates from every ~15 months to ~6 weeks and the build-and-test loop moves inside the model (Dev Day 2024's o1-preview could not run or verify its own code; a year later the model tests its own work live). Their core product claim is a single-stack dogfooding philosophy — Codex is built on the same responses API, open-source harness, `AGENTS.md` format, and app server that ship to every developer, "not a first system for OpenAI and a second simplified one for developers" — plus a chat-first-with-a-hands-on-surface product shape and a "value maxing" (not token maxing) framing backed by cost ($1/M input, $6/M output) and speed (750 tokens/sec on Cerebras → a real PR in ~10 seconds). Peter Steinberger then narrates the shift from hand-polling ~10 terminals to managing a single long-lived manager-of-agents, enabled by server-side compaction, coordination/delegation, and triggers ("there's your loop"), where the bottleneck keeps moving from tokens to compute to human attention.

## Extracted Concepts

- [Dogfood the Same Stack You Ship to Developers](../concepts/dogfood-the-same-stack-you-ship-to-developers.md) - Codex is built on the same responses API, open-source harness, AGENTS.md, and app server given to developers, with new needs baked into the API first.
- [Manage an Agent Manager Instead of Polling Parallel Agents](../concepts/manage-an-agent-manager-instead-of-polling-parallel-agents.md) - the shift from hand-scheduling many terminals to managing one long-lived manager-of-agents via persistence, delegation, and triggers.
- [Shape Agent Products as Chat-First With a Hands-On Surface](../concepts/shape-agent-products-as-chat-first-with-a-hands-on-surface.md) - a single entity you can ask anywhere plus a collaborative UI to dig in, because IDE-order-first and CLI-only both miss the "talk, then dig in" workflow.
- [Treat Token Spend as a Strategic Axis](../concepts/treat-token-spend-as-a-strategic-axis.md) - "value maxing, not token maxing": convert cost efficiency and inference speed into value rather than maximizing tokens.
- [Treat Human Attention as the Bottleneck for Agentic Work](../concepts/treat-human-attention-as-the-agentic-bottleneck.md) - the bottleneck moves tokens → compute → attention, and stronger models understanding intent mean staring at the agent is now a waste.

## Notes

- Engineering framing: "engineering was never about writing code… it's about solving problems"; "software ate the world, then AI ate software, and now AI engineers are eating the world" — not the end of engineering but a return to its roots. (00:43-02:08)
- Model cadence: ships went from every ~15 months to roughly every 6 weeks; the 5.6 series was previewed the prior week. (02:15-02:28)
- Build-test loop evolution: completion → inline prediction → command-K (change but no test) → models test their own work → models taking on long, hard goals until done. (02:42-03:07)
- Demo-god provenance: at Dev Day 2024, o1-preview built a drone interface but "could not actually run the code or verify its own work," so Huet had to cross his fingers; by Dev Day 2025 the model could test its own work and drive an entire camera + lighting rig live. (03:10-03:51)
- Connect the agent before and after coding: agents can do any task on your computer, so wiring them to *why* the work must be done begins more work, and wiring them to review/deploy afterward lands more work. (04:26-04:54)
- Product mission framing: the goal is "squarely not to automate engineers" but to "maximally empower" them; two questions are what agents can do / where they run, and how we use them. (06:07-06:34)
- Chat-first modality: "some people think chat is dead. I think chat is underrated" — two modalities are a single entity you ask anywhere plus a collaborative UI to inspect/steer/shape. (06:43-07:11)
- Team analogy: mostly you talk and "let them cook"; every now and then you dig all the way to the weeds; the product should "retain this feeling of mastery." (07:23-07:57)
- Surface critique: you "can't really build that collaborative interface… in a CLI, it's mostly chat," and in an IDE "the order is wrong" (you start with code); Codex app starts with chat and digs in when needed. (08:59-09:11)
- Single-stack dogfooding: developers use the models through the responses API and "this is how we built the Codex app"; new Codex needs (e.g. compaction for long-running tasks) get baked "into the API first so you can benefit as well." (09:44-10:33)
- Open harness + AGENTS.md: the Codex harness is open source (inspect/fork/adapt); models are the default but "not hard coded" so you can swap an open model and keep the same agent loop; the harness is also used in model post-training so models learn to call tools in an open-source environment; `AGENTS.md` was named so other agents can use it too. (10:37-11:16)
- Reference implementation: the Open Code team could inspect how OpenAI did ChatGPT sign-in and reuse/replace parts — "better than having developers reverse engineering." (11:17-11:43)
- App server: built open source because OpenAI itself needed a unified way to control the harness for a VS Code extension and the Codex app — "not a community adapter, it's really the path that we use for our own products." (11:44-12:16); "Toma" (aka Demilyan) built native Codex Monitor and Codex for iOS on the app server. (12:16-12:33)
- Extensibility: in-app browser and plugins are extension points; browser-use and computer-use were built as plugins on the same points developers get; role-specific plugins (data science, design) are open source; subscription usable across Open Code, Pi, Droids, Open Claw, Xcode, JetBrains. (12:37-13:33)
- Single-stack thesis (payoff line): "we're not building one system for OpenAI and a second system that's simplified for developers. At every layer, we actually use the thing that we give to you." (13:39-13:56)
- Value maxing: getting value out of agents "is not token maxing… value maxing"; cost efficiency (GPT 5.6 Terra = 5.5-level intelligence at half cost; Luna at $1/M input, $6/M output — "insane value") and speed. (14:20-15:41)
- Speed unlocks parallelism: GPT 5.6 Soul on Cerebras at 750 tokens/sec ≈ "a pretty substantial PR written in like 10 seconds"; enough to run 5–6 approaches in parallel and pick the best in the time it takes to generate one, feeling "like a coworker that's already showing you the results as it goes." (15:48-16:50)
- Remove the local/cloud distinction: run many tasks in parallel isolated on their own box and shut the laptop; the future shouldn't force you to decide local vs. cloud — "just have an agent… and it should figure out which environment is right." (16:51-17:54)
- Steinberger — polling vs. managing: juggling 10+ terminals felt like peak productivity but "I thought I was orchestrating. Really, I was polling. I was the scheduler, the router, and the memory"; 10 terminals = "managing 10 direct reports." (18:56-19:41)
- Manage the manager: now he "mostly talk[s] to a long-running manager, which delegates work to a team," dropping down to pair on tricky work — "I manage the manager of a small company of agents." (19:46-20:02)
- Three enablers = the loop: (1) server-side compaction makes long-running tasks reliable; (2) coordination lets one thread create and steer projects; (3) automation/triggers wake the same manager — "persistent context, delegation, and triggers. There's your loop." (20:04-20:34)
- Bottleneck keeps moving: last year constrained by tokens; then by compute ("my MacBook starts sounding like a jet engine," fixed by running tests on separate test boxes); now by attention, "and unlike tokens or compute, I can't simply add more of it," so "the most important skill… is deciding where to spend it." (20:37-21:36)
- Stop staring: escape-and-steer was necessary with earlier models, but "the latest generation of models is so good at understanding intent that it's a little bit of a waste of time to" keep watching. (21:37-22:03)
- Outer-loop workflow: an issue is filed → the manager wakes, reads it against the project's goals/notes/vision, decides fit, creates a worker; the worker investigates/implements/runs tests; another agent reviews; when it needs you it returns a PR + the original issue + the proposed diff + maybe a video or a running build to VNC into; you review once, leave a note, approve, and it lands after checks pass. The agent runs the inner execution loop; the human sets direction in the outer loop. (22:08-23:16); Paul's pinned "chief of staff" wakes every 10 minutes and coordinates GitHub work in sidebar threads. (23:16-23:28)
- Location independence: once the manager is long-lived, "tying it to a laptop just feels wrong" — Codex can move work between hosts, Open Claw has a gateway and nodes, but "neither feels like the final form"; the manager should connect to any machine, know which work is cloud vs. local, and be steerable from Slack. (23:38-24:29)
- Closing: "models are advancing faster than the harnesses and organizations around them… that's the next engineering problem"; "the future is not 20 terminals. It's better loops." (24:37-24:57)
