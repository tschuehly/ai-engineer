## Summary

Harshil Agrawal frames AI-generated code as untrusted internet code that may fail through hallucination, over-helpfulness, or prompt injection, then shows how capability-based sandboxing, V8 isolates, and containers map to different generated-code workloads. The source adds concrete threat-model questions and an operational checklist: default-deny network access, grant minimal capabilities, isolate per user, set resource limits, keep secrets outside sandboxes, clean up idle runtimes, log execution, and validate code before running it.

## Notes

- The talk reframes LLM-generated code as untrusted code from the internet because the model is a black box that returns code humans often do not fully audit before running with local or production credentials. (01:45-02:59)
- The threat model includes hallucinated code that crashes or loops, over-helpful code that reads environment variables and secrets, and prompt-injected code that exfiltrates data through generated behavior. (03:08-06:48)
- Capability-based security should enumerate what generated code may do, not every dangerous operation it must not do; if a capability is not granted, it should not exist in the sandbox. (08:13-09:57)
- Isolates fit short-lived functions, tool calls, plugins, skills, data transformations, and code interpreters that need fast startup and constrained side effects; they lack ordinary filesystem and process capabilities. (10:28-11:29, 19:52-21:05)
- Containers fit generated applications that must clone repositories, install packages, run builds, start dev servers, expose preview URLs, and use real filesystem, process, and networking features. (21:12-26:13)
- For multi-tenant systems, one user should get one sandbox because shared filesystems or execution contexts create data-leak paths that are hard to undo after the architecture is baked in. (25:20-27:12)
- Secrets should stay in the trusted worker or application environment; generated code should call a proxy endpoint that adds credentials, forwards the request, and returns the response without putting API keys into the sandbox. (27:13-28:37)
- Universal controls include default-deny networking, explicit capabilities, per-user isolation, CPU and memory limits, proxying secrets, cleanup with maximum lifetimes, execution logs, and input/code validation before execution. (33:00-35:24)
