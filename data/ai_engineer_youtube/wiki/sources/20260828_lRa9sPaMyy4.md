Uploaded: 2026-08-28

## Summary

Varun Pant, who leads formal-verification teams building AI products at AWS, opens on a throughput mismatch rather than on mathematics. "Coding agents are generating more code than ever. Builders are generating hundreds and thousands of PRs every week. How do you know that this is correct?" He then disqualifies the three checks a team would normally reach for, each for a different reason: LLM-as-a-judge on the code is "probabilistic"; tests "only check some inputs, not all"; and "human code review doesn't scale to match agent speed." The summary line is the one worth carrying — "none of these can say for all inputs the code is correct" — and it is what formal verification is offered to supply: "mathematical proof that code is correct for all inputs," where a human writes what correct means and a tool proves the code satisfies it (00:12-01:08).

The division of labour is the memorable claim: "humans own the specification and machines own the code and proof" (02:04-02:10). That puts all remaining risk in one artifact, which is why the workflow he sketches — spec-driven development, "for example, with Kiro" — inserts an explicit validation step before anything downstream runs. You either write the specification formally in Lean or write it in natural language and "let the AI auto formalize it," and then "you validate the specification. So, either the human reviews it, or you test that it holds on some inputs." His reason is positional: "the specification is upstream. It's a living, breathing artifact that the builder interacts with. You want this to be correct. Everything else is downstream from this" (01:11-01:52). Note what survives here: testing does not disappear under proof, it changes target — from checking the implementation to checking the specification.

Lean itself is presented through two properties an engineer can act on. It is "a programming language and a proof assistant… the same language for the definitions and proofs. There's no translation layer," and it is implemented in Lean, hence extensible. And it "has a small trusted kernel. Proofs can be exported and independently checked" (02:10-02:30). The chess analogy carries the search: tactics are moves, the theorem is checkmate, you traverse a tree and backtrack when a branch will not close, and at the end "that small independent kernel confirms and checks it" (03:16-04:03). The consequence he draws is the trust-base argument: an incorrect proof "is rejected immediately. And you only need to trust the small kernel," of which multiple independent implementations exist in C++, Rust, and Lean — "you yourself can actually go write one. It's completely open source" (04:03-04:30). The scaling property follows from the asymmetry: an AI converted zlib, a C compression library, to Lean "over a week or so," starting from the natural-language specification that decompressing the output of compress returns the original data, generating the formal spec, writing the Lean code, generating "helper lemma subgoals," and assembling them into a final theorem — "32,000 lines of proof" — while the thing that checks it stays small enough to reimplement (04:41-05:56).

The rest of the talk is a route map for code that is not going to be rewritten in Lean. If the code is in Rust, write "the functional specification of it or the model in Lean": Cedar, the open-source authorization policy language behind AWS Verified Permissions and Verified Access, has its specification in Lean while "the production code runs in Rust," with a property such as forbid-trumps-permit ("for any forbid policy being satisfied, the request is always denied") proved on the model side, and the two artifacts reconciled by "differential random testing to check that both of those for the same inputs give the same output" — "about 100 million differential random tests run nightly. No version ships until this is satisfied" (05:58-06:58). If instead you want deductive verification in place, a solver is "a calculator, a very powerful one. You feed in a formula and it returns… satisfiable or unsatisfiable"; Verus is the open-source example, built on Z3, where specifications live inline in the Rust source as `requires` and `ensures` pre- and post-conditions, "a static check… enforced by the verifier and erased at runtime. So, almost like ghost code" (06:59-08:07). Aeneas takes a third route, consuming Rust's mid-level intermediate representation and doing "a functional translation to Lean," after which the same theorem prover applies (08:09-08:22). And for "any programming language," AWS is building the open-source, work-in-progress Strata: you author a dialect, and "think of this like a compiler. You have a high-level intermediate representation and you lower it down to a low-level intermediate representation, which is what Strata core is. Now, this is written in Lean." Once programs speak Strata core they can be dispatched "to any of the engines… the Lean proof… or the very powerful calculator, SMT solvers, or model checkers" (08:26-09:12). The closing instruction is scoped rather than universal — open Lean in the browser, "pick your most critical code, write what correct means," let the coding agent implement and the verification tool prove it — ending on the pun the talk is built around: software that is "not probably correct, but provably correct" (09:17-09:46).

## Provenance and Limits

- Nothing in the talk is measured against a baseline. There is no defect-reduction figure, no adoption number, no cost or latency figure, and no comparison of formal verification against the three alternatives it disqualifies in the first forty seconds.
- The disqualification of tests, LLM judges, and human review is argued from first principles ("only some inputs," "probabilistic," "doesn't scale"), not from any observed failure at AWS or elsewhere. It is a correct statement about what each technique can guarantee, not evidence about what each one catches.
- The zlib result is reported as an outcome with two numbers — "over a week or so" and "32,000 lines of proof" — and nothing else. No compute cost, human intervention, failure or retry rate, proof-maintenance cost, or statement of whether the proved Lean version is used anywhere. The organization credited for it is unrecoverable from the captions.
- Proof maintenance under change — the standard objection to formal methods, since a proof breaks when the code or spec moves — is not raised anywhere in the talk.
- The Cedar example proves properties on the Lean side and reconciles the shipping Rust binary by *sampled* differential testing, not by proof. The talk presents both inside one formal-verification narrative without marking the boundary; the correspondence between the model and the shipped code is tested at high volume, not established for all inputs.
- The distribution of the 100 million random inputs is unspecified, which is the thing that determines what differential testing is worth. Cedar is also an unusually friendly target — a deterministic policy evaluator with a small, total input space — and the talk does not say where the pattern stops being practical.
- The step everything else depends on gets one sentence. "Either the human reviews it, or you test that it holds on some inputs" is the entire method offered for validating a specification, with no criterion for when a spec has been validated enough, and no discussion of how a human reviews an auto-formalized spec they did not write.
- Three of the five named artifacts are the speaker's employer's — Kiro, Cedar, and Strata are AWS; Verus and Aeneas are not. Strata is explicitly "work in progress," so the "any programming language" answer is a plan rather than a shipped path.
- The scoping advice is honest but thin: "pick your most critical code" is the only guidance on what fraction of a codebase is worth specifying, and no cost of writing specifications is given.
- Caption artifacts resolved: "back driven development" → spec-driven development (01:14); "LM as a judge" → LLM as a judge (00:24); "this theorem prover approves a property" → proves (02:53); "forbid Trump's permit" → forbid trumps permit (06:25); "Eneus" → Aeneas (08:11); "ensure keywords" → `ensures` (07:51); "AWS verified permissions and access" → AWS Verified Permissions and Verified Access (06:12); and the closing "not probably correct, but probably correct" → provably correct (09:43), which is the talk's title pun and is certainly a transcription error. Left unresolved: "open source Andreo. AI," the organization credited with the zlib-to-Lean conversion (04:43), and "the Arena Lang," the site said to host independent kernel implementations you can contribute to (04:25).

## Extracted Concepts

- [Ship a Proof a Small Kernel Can Recheck, Not a Claim You Must Trust](../concepts/ship-a-proof-a-small-kernel-can-recheck.md) - the trust base stays a small independently reimplementable kernel while the checked artifact grows to 32,000 lines, which is the only property in the talk that scales with agent throughput.
- [Validate the Specification, Because the Proof Cannot](../concepts/validate-the-specification-because-the-proof-cannot.md) - "humans own the specification and machines own the code and proof" moves all residual risk upstream, and auto-formalization adds a second unproved gap between the sentence and the formal spec.
- [Gate Releases on Agreement Between an Executable Spec and the Shipping Code](../concepts/gate-releases-on-agreement-between-an-executable-spec-and-the-shipping-code.md) - Cedar keeps its semantics in Lean and its production code in Rust, reconciled by about 100 million nightly differential random tests, with shipping blocked until they agree.
- [Pick a Verification Route by Which Translation You Can Afford](../concepts/pick-a-verification-route-by-which-translation-you-can-afford.md) - five routes into the same core differ in who translates your program into the prover's logic: rewrite in Lean, model plus differential testing, inline `requires`/`ensures` discharged by Z3, automatic translation from Rust MIR, or a dialect lowered to a shared verification IR.
