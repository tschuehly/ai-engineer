# Why More Context Makes Your Agent Dumber and What to Do About It — Nupur Sharma, Qodo

## Summary

Nupur Sharma (Qodo, agentic code reviews, ex-DevSecOps) argues that growing the context window did not fix agent reliability: current models attend to the start and end of a prompt and drop the middle, a "U curve" Qodo observes when benchmarking which provided context the agent actually uses. Dumping the whole codebase therefore makes results worse, not better. The fix is strategic context selection, and she compares five supply strategies by developer-input cost and scaling: a ranking context engine, hierarchical per-file/folder summarization, a knowledge graph, iterative retrieval (her default for non-product teams), and self-correction with a critic node. The second half covers an "orchestration paradox" — capable models burn most of their tokens deciding *how* to solve a task rather than solving it — fixed with an 80/20 split of high-reasoning discovery models and lighter deterministic validation models plus loop-breaking counters and timeouts. She closes on the single-agent-overload failure (one agent given four tasks silently drops two), the mixture-of-experts + judge-agent remedy, and Qodo's live code-review architecture: a context collector bifurcates context to specialist agents (security, code-diff, Jira), a judge node recombines and weighs results against PR history and uploaded architecture/compliance guidelines, and every accepted or rejected suggestion shifts the weights for the next run, all plumbed on LangChain.

## Notes

- The U curve: models take the initial inputs and the last inputs but the in-between context is "basically removed"; agents look at the start and end point and the middle is "not taken up". (02:57-03:30)
- Qodo knows this from benchmarking: they provide context to agents and measure whether it is taken into effect in the result. Mid-prompt inputs such as "I have Jira, I have MCPs, can you look into that" get purged so the model can "make sense by themselves." (03:33-04:31)
- Context engine = a "bouncer" that creates a search pattern and ranking logic so it can tell the model "this is more important." Worth it for a large messy codebase; indexing is moderate effort but **scaling is the challenge** — at 600-700 repositories the mapping and indexing slow down and become unpredictable unless you are dedicated to building a context engine. (05:00-06:01)
- Hierarchical summarization: a summary per file and folder so agents read summaries to decide relevance; cost is high upfront LLM processing and re-mapping every time a file is created or changed. (06:09-06:43)
- Knowledge graph: complex but "works wonders" for logical dependencies (file A impacts B impacts C) and dependencies across multiple repos; initial developer input/time to build is very high; graph DB hosting. (06:44-07:13)
- Iterative retrieval: instead of a summary it builds an index, "a library card you give your agents" — this is the topic, if relatable look deeper into the code. Has cost impact but low developer energy/input; her recommended default if you are building agents for yourself rather than as a product company. (07:14-07:53)
- Self-correction: a critic node checks output relevance to the initial goal and triggers a retry when context is lost; adds latency but low initial developer input. (07:57-08:30)
- Orchestration paradox: smarter models, given a task, "look for the method to solve the problem" and hop from one method to another; most API tokens are wasted "finding a way to do it rather than doing it." Opus latest-and-greatest will keep challenging itself ("maybe not this, another way") in a loop of trying to do something rather than doing something. (08:34-09:34)
- 80/20 hybrid: give the latest/greatest models power to research 80% of the time (open-ended discovery); the 20% that needs final validation is restricted with hard gates ("if I get X results I want Y") so the research from the 80% is "lowered down." (09:39-10:36)
- Loop guards on the 80%: some orgs use a counter mechanism (after 4-5 counters, work with the last result), others a 5-minute timeout (use the last tool/decision and go back if results are bad). (10:36-10:59)
- You don't need a high-reasoning model for the 20% because those tasks are deterministic — you tell them what is needed; e.g. the critic node only checks goal vs result and how to summarize. Next-possible-action planning fits the 80% dynamic models; "what is the proper result the user is looking for" fits the 20%. (11:22-12:24)
- Single-agent overload: as context grows, teams try one agent for everything (testing + review + …); the agent gets overwhelmed and loses the original task — give it four tasks and it focuses on two while the other two "get lost in the middle." (12:25-13:16)
- Mixture of agents: instead of one big agent, create small expert agents each strong at a specific task. (13:16-14:05)
- Judge agent: when each specialist returns its own result, a judge agent combines them and checks they make sense together — vacation example: hotel in Greece, flight Amsterdam→Portugal don't cohere until a judge reconciles them; it also refines by relevance ("out of the 10 things, how many make sense for you"). (14:05-15:56)
- Qodo's code-review architecture: a context collector gathers from PRs, the context engine, and tools, then bifurcates the context to specialist agents (security flaws, code differences, Jira issues); a judge agent recombines and checks relevance against PR history. (14:44-15:56)
- Plumbing: LangChain at the bottom for inter-agent communication; it collects responses and stuffs them into the next agent's prompt, and an extra agent collects results and writes a refined prompt for the next agent. (16:32-17:08)
- Calibration via PR history: index all PRs; when code changes, find similar past changes and how reviewers/developers commented; context fed twice (to sub-agents and to the judge) so the judge can weigh ~15 recommendations against past reviewer behavior. (17:32-19:06)
- Calibration via guidelines portal: architects upload architecture guidelines and compliance people upload compliance guidelines through a web portal; an agent validates code against them — mapping the old senior-engineer/security-expert/auditor roles onto specialist agents. (21:04-22:35)
- Weighted feedback loop: feedback is segmented (error vs recommendation); every accepted suggestion gets more weight for the next run, every rejection less — "it's all about indexing and managing weights." Two signals: developer accept/reject, and whether similar past-PR issues were actually implemented. (22:50-25:00)
- Rules vs bugs caveat (raised by the audience that "it happened in history doesn't mean it's good," e.g. hard-coded API keys): a "rule" is highlighted regardless of want; a "bug" is the agent flagging something wrong, weighted by whether reviewers repeatedly agree but don't implement. (25:44-26:08)
- Per-agent scoped context tradeoff (audience pushback): each specialist only gets its slice and runs autonomously without the full picture, which works for simple checks (linting, tests) but the audience questioned holistic architecture decisions where "everything is a balance"; Qodo's answer is the judge plus multi-angle weighting (PR history + guideline severity). (19:45-20:26, 23:10-24:13)
