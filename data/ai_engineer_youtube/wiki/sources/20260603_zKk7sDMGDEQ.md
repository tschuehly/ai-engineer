## Summary

Kuba Rogut (Turbopuffer, a serverless full-text + vector search database on object storage) ran a 50-task benchmark to test whether adding semantic code search to Claude Code actually improves how it finds context. This is an earlier, benchmark-heavy companion to his later "RAG is dead, right??" talk: the cached-compute framing (Claude Code re-greps every session; Cursor pays a one-time index cost) and the Cursor production numbers (≈24% answer-accuracy on the composer model, ≈12.5–13% across models, +2.6% code retention, −2.2% dissatisfied requests) are the same, but the new contribution is the measurement methodology and what it revealed. He used ContextBench (Cursor's internal context benchmark; a public ContextBench paper exists), which scores the *process* — did the agent read the right files, lines, and symbols along its trajectory — rather than whether it solved the task. Three conditions were compared: raw Claude Code, Claude Code with reads capped at 50 lines (windowed grep), and windowed grep plus a Turbopuffer-backed semantic-search tool ("Turbo Grep": tree-sitter chunking → Voyage code-3 embeddings → Turbopuffer; V1 open-sourced, V2 coming). File precision rose from 65% baseline → 87% with windowed grep + semantic search, i.e. wasted reads dropped from 1-in-3 → 1-in-5 (windowed) → 1-in-8 (+ semantic). The deeper findings: grep and semantic search win *different* task types (semantic wins behavior-adjacent tasks where related files share no keywords; grep wins import tracing where the keyword is present), and Kuba's gains were smaller than Cursor's because Claude Code has semantic search as "just another tool in the list" while Cursor's Composer is trained to know *when and why* to call it. Q&A: semantic search here was plain vector search; it works best with good inline comments/docs, Cursor injects synthetic comments before embedding to lift recall, and vector DBs earn their keep for multiplayer/shared and multimodal data you cannot grep.

## Notes

- Claude Code does not use semantic search by default; per a Boris (founding father of Claude Code) tweet, early versions used a local vector DB but they "found agentic search" (grepping the filesystem) worked better and simpler. (00:44-01:04)
- Cursor (a Turbopuffer customer, and one of its first) indexes codebases into Turbopuffer and sees real gains: ≈24% relative improvement in answer accuracy on the composer model, ≈12.5–13% across all models (measured before composer-2), plus a +2.6% code-retention increase in large codebases and −2.2% dissatisfied user requests from an online A/B test allowing/disallowing semantic search. (01:23-02:09)
- The A/B deltas look small because not every query benefits from semantic search — a simple tool call or simple query may never use it. (02:14-02:31)
- Why semantic search wins: embeddings are *cached compute*. Claude Code re-does the grep→read→assess exploration on every session and every agent for the same codebase (one sub-step ≈6,000 tokens), and people now run ~3 agents at once, so per-session savings compound. Cursor pays a one-time chunk/embed/index cost and then queries the cache cheaply. (02:34-04:08)
- Turbo Grep CLI: a tree-sitter ("tree splitter") library parses and chunks the codebase, embeds with the Voyage code-3 model, and uploads to Turbopuffer; V1 is open-sourced, V2 coming soon. (04:09-04:38, 11:14-11:34)
- ContextBench (Cursor's internal context bench; public ContextBench paper) tests "not whether the coding agent solved the problem" but, in the process of solving, whether it found certain files, lines, and symbols — "the process really matters." It is a human-labeled dataset of golden files/lines/symbols the agent should have looked at. (05:10-05:53)
- Three conditions across 50 tasks: raw Claude Code; Claude Code with 50-line max windowed reads; windowed reads + the Turbopuffer semantic-search tool. The 50-line cap exists because reading whole long files becomes noisy fast and makes the conditions hard to differentiate in the numbers. (05:53-06:24)
- Precision (of files read, how many were golden): baseline 65% file / 33% line / 43% symbol; windowed grep + semantic search reached 87% file precision. In plain terms: Claude Code wastes 1-in-3 file reads, windowed grep cuts it to 1-in-5, semantic search to 1-in-8. Claude Code is "really exploratory" and "loves to read everything," which shows up as the low 65% precision. (06:26-07:30)
- Recall (of golden files, how many were found): raw Claude Code actually *wins* file recall because it explores every file it can — but line recall drops a lot, because it read many files without golden context lines; it "explored a lot" but "explored the wrong things a lot." Windowed grep and windowed grep + semantic search have similar recall to each other. (07:33-08:25)
- Grep vs semantic win different task types: semantic search won on behavior-adjacent tasks where related files share no keywords (e.g. handling many different ORMs across libraries — keyword search missed them, semantic search understood they were related); grep won on import tracing, where the keyword is present and it finds the right files in the first or second tool call. "Certain tasks require different types of tools." (08:39-09:43)
- Why Kuba's gains were smaller than Cursor's: Claude Code is built for grepping (Anthropic's focus), and semantic search is added as "just another tool in the list" — "you probably should use it sometimes" — so the model has no true understanding of when/why to call it. Cursor's Composer treats it as a built-in tool it knows when and how to use, which is why they saw ~23.5% gains. (09:55-10:36)
- Long-term thesis: "long-term winners provide lightweight tools to find the right context in various different ways"; you can't just grep through everything — the people who provide easy tools to shrink "billion-token context windows into the right million" win. (10:36-11:01)
- "Semantic search" here meant plain vector search: embed query (Voyage code-3) and the indexed code, similarity-search Turbopuffer. (11:08-11:38)
- It works best when code has good inline comments/docstrings, which give the embedding model semantic meaning to find; "the embedding is not the hard part, it's figuring out what the meaning really is of that chunk." In this benchmark it embedded raw code only. (12:00-13:00, 13:30-13:48)
- Audience/speaker: Cursor reportedly injects synthetic "fake comments" on top of code, then embeds code-with-comments — that's how it gets high recall; a parent-child relationship (parent = natural-language query-ish like "authentication flow", child = raw code) can also bridge the query↔document format gap, since "semantic search is just similarity search" and a query format mismatch creates innate distance. (13:48-14:38, 15:40-16:00)
- Vector DBs earn their keep beyond code for "multiplayer" shared use, complex relationships across lots of data (e.g. a Notion knowledge base), and multimodal data — you can't grep a video, audio, or image file. (14:48-15:44)
