## Summary

Benedikt Sanftl (Bene, CEO/co-founder) and Burak (CTO) of Mutagent argue that the coding-agent loop should be turned on the task of building AI agents themselves: an "Agentic AI Engineer" is a multi-agent team steered by an orchestrator that runs the full agent lifecycle — spec, build, evaluate, ship, monitor, diagnose, optimize — as two connected loops. The **offline loop** (spec → build → evaluate → ship) iterates before deployment; the **online loop** (monitor → diagnose → optimize → feed back) uses production traces to keep improving. Done by hand the loop is slow because human review and build time are the bottleneck, which doesn't scale once an org runs tens or hundreds of agents; doing each stage agentically fits many more cycles into the same window. Building splits into a cold-start path (spec from scratch) and an existing-feature path (optimize an agent that already runs). The talk frames eval-driven development (EDD) as the TDD-equivalent that supplies the agent's termination gate ("when is an agent good enough?"), stresses that a complete eval suite is a product of discovery rather than something you can pre-guess, describes agent evaluation over the trajectory (context completeness + chain-checking every tool output), and argues useful evals give actionable feedback (prefer binary/criteria over score-based unless the rubric is very well defined) with a calibrated LLM-as-judge to control run-to-run variance. Diagnosis groups production failures by root cause via a recursive why-chain and, over time, distills code-checkable indicators per failure mode so you can triage millions of traces by representative sampling instead of reading them all (reading every trace costs more than the execution itself). The optimization loop varies the agent and runs auto-research-style experiments until the eval suite goes green, then auto-ships. A live demo shows Mutagent's diagnostics agent (in research preview alongside an evaluator agent): connectors pull traces from Langfuse / local Claude transcripts / exported JSONL, incidents from a ticketing system or Slack, and the run produces an HTML artifact with per-failure-mode tabs, why-chains, remedies, an assumptions block, and a decisions page that emits a Markdown task definition for the coding agent (targets: a raised GitHub PR, edits to agent `.md` files, or a managed deployment).

## Notes

- Two connected loops: an offline build loop (iterate, test, evaluate, improve) and an online loop where a deployed agent's traces are monitored, diagnosed, and fed back into optimization to produce multiple agent versions. 00:43-01:12
- The manual loop is slow: issue → implement (maybe vibe-code the change with a coding agent) → generate samples for the feature/issue → read traces → ship / AB-test, all reviewed by hand, so "the bottleneck basically becomes the human review and the human building time," which can't scale to rolling out hundreds of agents. 01:18-02:12
- Doing the loop agentically is the key to throughput once you pass a certain number of agents/AI features, because you can fit many more cycles into the same time window. 02:33-02:59
- The stages: spec (define responsibilities, functions, decisions/conditions) → build (realize the spec in a harness/framework, e.g. a Claude Code or codex agent) → evaluate (define clear evaluations = "unit tests for coding," how you verify the agent works) → ship (deploy: a code update, an agent-platform update, or a local harness) → monitor (continuous, trigger conditions from trace volume or daily/weekly jobs) → diagnose (collect failures, structured root-cause analysis) → optimize (specific changes/"mutations" for the found failure modes) → repeat. 02:33-05:52
- Two paths: cold start (design from scratch via spec + conceptualization) vs an existing feature (the agent already runs, so you optimize over something that exists). 06:00-07:07
- Spec-driven development captures the agent's requirements and especially its success criteria; because non-coding agents handle company-specific processes, the spec must define context requirements, integrations/tools, jobs-to-be-done (and what the agent will *not* do), and constraints/boundaries — becoming a blueprint the implementation is held against. 07:16-08:46
- The spec is isolated from implementation details, so the target platform choice is yours and portable; the agent framework space changes rapidly and a harness sometimes lacks capabilities or hits a roadblock you must wait on the underlying framework to fix, so stay flexible and pick the best harness — new "agent loop run-time" harnesses like Hermes and deep agents keep shipping. 08:53-11:08
- Eval-driven development is the TDD-equivalent for agents: the agent needs a termination condition (when is it good enough?). The eval suite has two parts — evals (metrics/criteria) and datasets (the cases to satisfy). 11:16-11:59
- You cannot pre-guess the entire evaluation suite; seed it with domain experts writing metrics/criteria or with historical/synthesized data, but the real, complete suite is "a product of discovery" — metrics, criteria, and edge/hard-case dataset items accumulate over time from user feedback and production failures. 12:06-13:37
- The evaluator agent removes the human bottleneck of eye-balling a 200-item dataset by scrolling an observability dashboard; "you design loops for your agent so they can autonomously work… your job becomes designing these loops with a clear eval or termination gate." 13:41-15:12
- Agent evaluation centers on the trajectory: check whether context was complete (did the agent have all required context end-to-end?) and chain-check every tool output (any wrong tool output can become the wrong final output); the harness itself drastically affects behavior and is another optimization vector, so evaluate all of these together, not in isolation. 15:15-16:53
- A useful eval provides actionable feedback: score-based evals don't tell you what to fix unless the rubric is very well defined, so binary/criteria evals are preferred because a failing criterion is a call to action. Calibrate the LLM-as-judge to control scoring noise, because LLMs are non-deterministic and the same judge can score a problem differently each run — otherwise you can't conclusively say an improved version beats the baseline. 16:58-18:54
- Diagnosis identifies the failure mode, groups occurrences by root cause and origin (a section in the agent prompt, missing/malfunctioning tools) via a recursive "why" chain, then generates new evals to detect the problem and generates remedies/improvements. 18:57-20:23
- Learned failure modes accumulate as historical data each agent checks against; there's an upfront cost to deep-reading traces, but over time you collect code-checkable indicators per failure mode (specific content or a specific tool-call sequence) that let you diagnose problems in traces without reading them all. 20:24-21:27
- At millions of traces, reading them all costs more than the execution itself, so pick a representative sample via intelligent segmentation strategies plus the learned indicators. 21:28-22:12
- The autonomous optimization loop varies the feature and runs auto-research-style experiments to reach target eval scores; as long as the eval suite is green it auto-ships to production, and every diagnostics-found issue in the outer loop yields an improvement/remedy that is optimized and re-deployed once green. 22:14-23:16
- New eval criteria derived from diagnosed production failures become part of the spec and part of the agent, so the spec and agent continuously grow with production usage and the agent scores better as it sees more production data. 23:16-24:38
- Mutagent runs in your environment (cloud + local, managed service later); two agents are in research preview — an **evaluator agent** (builds the eval set / dataset, the core of the EDD loop) and a **diagnostics agent** (analyzes production traces so users don't hand-read them) — connected through an orchestrator that runs in your coding environment. 24:58-26:07
- Connectors bring in traces and incidents from sources like a ticketing system or Slack (where people report agent failures); target platforms include an auto-raised GitHub PR, adjustments to agent `.md` files across frameworks, or deployment to a managed service. 26:07-26:52
- Diagnostics demo (in Claude Code): the orchestrator dispatches sub-agents; boot shows a dashboard of stages plus existing agents/configs; `diagnose` starts the root-cause stage scoped to an agent or a skill (diagnose all invocations of one skill); it retrieves traces from the configured source (Langfuse, local Claude transcripts, or exported JSONL from an observability platform). 27:05-28:52
- The run selects primary signals/failure modes by frequency using multi-tier filtering/segmentation (read a portion of traces first to spot obvious problems, then focus), or a guided search when you specify a known/user-reported issue so it finds all occurrences of that problem. 29:08-31:32
- The generated HTML artifact shows agent details/tools, the detected harness/framework, an overview of detected issues with frequency over a time frame, per-failure-mode tabs with a recursive why-chain, offered remedies/fixes, and an assumptions block (the diagnostics agent may make incorrect assumptions when it lacks code access, which you can see and correct). 29:12-33:00
- The decisions page lets you pick recommended or multiple remedies (multi-choice), offers a Whisper-Flow voice feedback box, and finally emits a Markdown task definition for your coding agent so the fixes apply directly back in your terminal. 33:00-34:11
