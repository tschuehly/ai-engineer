# The Pipeline Is Dead

Source: [The Pipeline Is Dead - Iris ten Teije, Sky Valley Ambient Computing](https://www.youtube.com/watch?v=bRnoEpoK5m4)
Uploaded: 2026-07-07
Transcript: `raw/20260707_bRnoEpoK5m4/bRnoEpoK5m4.en-orig.vtt`

## Summary

Iris ten Teije (co-founder of Differ, building "infrastructure for adaptive software"; co-founder Noam was the first engineer at JFrog) argues that the entire software distribution stack — CI pipelines, packagers, registries, container images, app-store reviews — exists to solve exactly one problem: move a *frozen artifact* from the machine where it was built to the machine where it runs, safely and reproducibly, once. Baked into that stack is an assumption so old "we stopped seeing it as a choice": one version of your software for everyone. That was never a fact about software "like gravity"; it was a consequence of cost, because producing a correct, scoped change took skilled humans hours or days, so you did it rarely, verified it, froze it, and shipped the frozen thing to everyone. The frozen artifact bought reproducibility, previewability, and rollback — every guarantee flows from "there is one artifact and it doesn't change after we ship it" — but the price was that software "couldn't really be for anyone in particular," and a per-user version was never rejected in a meeting, it just "wasn't an option" (forking and hand-maintaining a code base per user doesn't scale). That cost is now collapsing toward zero, and — just as importantly — production no longer has to happen once, up front, in one place: parts can run on the server, on the client, or in the user's live session. When the agent *is* the runtime and the thing that runs your software can also modify it, development and distribution stop being two phases and the boundary dissolves. Differ's bet is a **stem plus per-user divergences** architecture: deploy one canonical stem and let every user run her own bounded, immutable, individually reversible divergence of it — "the best version for anyone" instead of "the least-worst version for everyone." The talk then walks the hard parts (source of truth, correctness, desirability, autonomy-vs-control, coordination) and insists that generation is the easy 80%; observability, validation, provenance, and coordination "are the entire business."

## Notes

- The distribution stack "exists to solve exactly one problem": get a frozen artifact from where it was built to where it runs, safely, reproducibly, once (00:07-00:30). The hidden choice underneath it is "one version of your software for everyone," so old that "almost nobody asks why anymore" (00:36-00:51).
- The one-way pipeline "is not arbitrary; it's the direct consequence of production of software being expensive and risky" (01:52-02:15). Because a correct change took skilled humans hours or days, "you did it rarely… verified it and froze it… and shipped that frozen thing to everyone" (00:54-01:00 of that argument, 01:55-02:06).
- The frozen artifact's advantages are reproducibility, previewability, and rollback, and "every guarantee that we lean on in production flows from one fact: there is one artifact and it doesn't change after we ship it" (02:15-02:36). The price: "the software couldn't really be for anyone in particular" (02:47).
- One-version-for-everyone "never had to win an argument"; a version per user "meant forking the code base and hand-maintaining both… wasn't really a viable option," so it was treated "as a fact about software like gravity" when it was actually "a fact about cost and budget and the economics" (02:59-03:39).
- The interesting shift is not just AI-written code ("table stakes"); it is *where and how cheap*: "the cost of producing a correct and scoped change is collapsing towards zero," and "the production of the software no longer has to happen in one place up front before anyone runs it" — part on the server, part on the client, part in the user's live session (03:49-04:33).
- Demand for per-user software is decades old and was only gated by cost: the forward-deployed engineer / professional-services industry ("an engineer living in your Slack channel" for big Salesforce clients; smaller customers couldn't justify it financially "until today," 05:26-06:04); developer dotfiles/editor config rebuilt by hand on every machine (06:04-06:26); and Excel — "millions of people that all build their own programs on top of it" (06:26-06:47). Feature flags, segmentation, and A/B testing were forced predecessors that only let software diverge into "buckets and segments that you declare in advance" (06:47-07:39).
- Thesis restatement: "when the agent is the runtime, when the thing that runs your software can also modify it, development and distribution stop being two phases… the boundary blurs and it's gone" (07:39-08:00). Differ's shape: "one canonical stem and every user runs her own divergence of it. Same origin, but individually adapted live" — "from the least[-worst] first version for everyone to the best version for anyone" (08:02-08:25).
- The CTO objection: "I can already barely reason about one AI-generated code base. And you want me to run millions of these? …You're describing my worst problem multiplied" (08:47-09:07). The rebuttal: the brittleness you picture "is a specific type of failure mode — unmanaged divergence inside a single artifact" (thousand-line files, "everything can touch everything else, no boundaries"), and that is brittle "because there's no structure separating things," not because it's AI-generated (09:13-09:38).
- The stem+divergences answer: divergences are "bounded, isolated, and individually reversible," so "the blast radius of a change in the system is one context," and "any single divergence can roll back live with no deploy" (09:38-10:07). "The thing that you're afraid of is the thing that this architecture exists to prevent" (10:30-10:35).
- The developer sets adaptation boundaries — "what can and cannot be adapted": a form can be adapted to improve conversion, but specific fields "can never be dropped," and areas like auth or payments "should always be off limits for any sort of adaptation" (10:37-11:14).
- Concrete adaptation example: an investor using a salesperson-built CRM; the system observes that she always logs founder intros (creates an intro path), always skips certain fields (stops surfacing them), and reprioritizes deals/founders she actually checks; she can also *proactively request* changes, and as long as they stay "within the boundaries the developer sets" and "within the spirit / purpose of the software," they can be implemented "without having to go back to the developer" — letting a horizontal SaaS "address a much wider number of customer personas without increasing your R&D spend" (11:14-13:10).
- Hard part 1 — source of truth: with no single artifact, "the software" is "the stem plus all the immutable divergences," which "creates a lineage problem… what is this user running and why? That now becomes more of a graph query versus a version number"; a bug report "describes a program that exists for that specific user," so every divergence must be "immutable, inspectable, attributable" and traceable back to "the signal… this exact adaptation" (13:40-14:40).
- Hard part 2 — correctness: testing "at a much larger scale of users means that you need to reason about the stem and also every possible divergence of it" (14:44-15:09). Hard part 3 — desirability: a change can be "perfectly correct and working" but you still must know "whether this was desirable… an improvement, an uplift," measured against the goals that matter (retention, churn, support tickets) since "anyone can make a code change now, but the hard part is knowing whether you actually found an improvement" (15:09-16:11).
- Hard part 4 — autonomy vs control: the conservative answer is "start with just recommendations," but Differ's vision is "a system that understands the user well enough to act without asking the developer for permission every time"; "the challenge isn't building more control, it's winning enough trust that you don't have to" — making the system "good enough, legible enough, reliable enough that humans in the loop choose to step back" (16:11-17:06).
- Hard part 5 — coordination: pushing updates to "a million different versions"; the answer they keep coming back to is "don't merge code, merge intent, merge outcome" — "everyone converges on the same goal through their own path," not the same commit (17:06-17:41).
- Punchline on where the value is: "Generation has become easy… that's actually the easy 80%. Calling a model to write some code is something that everyone can do. The other part — observability, validation, coordination — that is the entire business… the substrate is stem plus divergences, provenance, validation… the hard part" (17:46-18:25).
- Framing close: a bank with no branches once "sounded reckless," and "a decade later the branch is the weird part"; Noam "used to fight with engineers about why you need builds and CI." "The pipeline didn't fail because it didn't work anymore, but the constraint it was built for went away" — software being expensive enough to freeze and ship once "stopped being true" (18:25-19:19). "The next 20 years are about shipping the right version to anyone with the isolation and provenance that makes it safe instead of terrifying" (19:30-19:43).
