## Summary

Two Uber platform engineers describe what they call a "managed software factory": six infrastructure building blocks, then one feature walked end to end through them. The framing numbers are that "more than 70% of our PRs [are] now either by local or cloud agents," that this produced "twice the number of lines of code per engineer year-over-year," and that toil automation has handled "more than 250 automated migrations, 9 million lines of code" (00:36-01:04). The precondition is stated once and is easy to miss: "all the investments we made over the last six years on moving to monorepos, moving to Bazel, all of that also laid a really solid foundation for us to accelerate this" (01:04-01:18). Everything after that is platform work for a few thousand engineers across 12 global tech sites.

The first block is a mandatory model gateway, and it is specified as three invariants rather than as a feature list: no PII ever leaves the perimeter to any vendor by default, "any guardrail that we add here the latency of that is strictly bounded," and every request must be attributable per user, per project, and per team (01:48-02:16). The implementation is one OpenAI/Anthropic-compatible endpoint fronting a middleware chain — Spire identity and authentication, a data anonymizer redacting "20 plus PII types," and an "AI guard that has five specialized models" for safety and policy — with the whole chain held under 100 milliseconds (02:16-02:43). Attribution lands both in real time and in the data lake, which is what makes portfolio-wide spend tiers possible, and audit logs and session traces from the same layer feed benchmarking and self-improvement loops (02:43-03:27). It carries 800-plus internal projects and more than 100 million model requests a day across frontier and open-source models (03:27-03:39).

The second block is an MCP gateway, and most of its story is about token cost rather than access. Uber had "thousands of internal APIs" and none were agent-accessible, plus SaaS tools each with their own auth, and "once you end up with enough MCPs they'll all add up to and have a massive token tax" (03:39-04:05). An automated crawler projects internal APIs into MCP servers "with one single config change," SaaS MCPs are hosted centrally with token exchange, and everyone installs through one entry point (04:05-04:37). The token work then proceeds in four stages: the original direct-MCP pattern, then Omni MCP — "one single MCP that you install which can discover and invoke any MCPs within the gateway" — then projecting all MCPs into a CLI pattern "so that even the response doesn't eat up in your context," then an auto-installed code-mode skill that "on the fly creates Python scripts to hyper optimize some of the top MCP token consuming use cases." The reported result across 1,000-plus tools is "more than 40% fleetwide savings" (04:51-05:41). Blocks three through six are pre-provisioned Kubernetes "balloon pods" with repositories snapshotted and search indexes prebuilt so agents "can start working within a matter of seconds," plus a single mega dev pod holding all repositories because "the roles of engineers are getting blurred" and agents work across repos (05:41-07:03); a managed skills marketplace of 2,500 skills behind lint checks and automated review, with persona-based auto-install and 20,000 executions a day (07:03-08:44); a context graph of 150 node and edge types and 40 million entries, built because execution traces showed agents burning tokens crawling "20 to 30 different systems" for ownership, dependency, and pattern facts (08:44-10:21); and Cortana, one assistant reachable from Slack, CLI, and web, personalizable into team-scoped personas (300 created in a month, 20,000 sessions a day) (10:21-11:30).

Adam Huda then takes a single feature — a better stadium pickup location during the World Cup — from a Slack thread through Cortana business research, product requirements, Figma mock-ups with two A/B string variants, and a code-change plan, into Minion, Uber's cloud coding agent (11:34-13:42). The design decision worth the most here is where Minion stops: it creates a draft PR and deliberately does not push to CI, because the pattern "was great for doing like toil sort of workloads but to build more advanced end-to-end features we really need to be able to validate the feature first and we want to prevent a lot of extra load coming on to CI" (13:42-14:07). Validation is therefore shifted into the inner loop — static analysis with automatic fixes, visual validation that launches a simulator through a skill and compares a screenshot against the Figma specs, and a staged backend brought up to check front-end/back-end integration (14:07-14:56). The outer loop keeps self-healing CI and a deeper code review "with a powerful model use reasoning [and] a skill," while the inner loop runs a smaller or medium model faster (14:56-15:33). Autonomous diffs carry a table on the PR listing every check they passed, screenshots included, so a human reviewer can see the self-improvement that already happened (15:33-15:54). Maintenance is then run as a managed loop: services enroll into maintenance skills such as feature-flag cleanup, scheduled deliberately for Sunday "when we know we have better CI capacity" and to control how many diffs engineers face on Monday, with the explicit constraint that "we don't want thousands of loops being set up across the company without any bounds"; whether each diff lands is treated as label data for improving the skill, and incident reviews are mined monthly for new maintenance skills (15:54-17:10). The closing observation is where the constraints moved: CI capacity, the number of experiments that can feasibly run, and finally "it's not about can we build — we know we can probably build it now — it's more of a question of should we build it" (17:10-17:52).

## Provenance and Limits

This is a platform-team experience report from inside one very large engineering organization, not a vendor pitch — nothing is being sold — but every number in it is self-reported with no methodology, baseline, or denominator, and no cost, failure mode, incident, or regression is mentioned anywhere in eighteen minutes.

- **The headline metrics are output volume.** "More than 70% of our PRs" being agent-authored says nothing about the size, risk, or reviewer cost of those PRs, and "twice the number of lines of code per engineer year-over-year" is presented as an achievement in a talk that also describes shifting review left and controlling Monday diff volume — the same code volume the rest of the talk is designed to absorb. The wiki's own pages argue against reading output volume as productivity; this source is evidence of the metric being used, not of its validity.
- **The 40% figure has no stated baseline.** "More than 40% fleetwide savings" is attributed to the combination of Omni MCP, CLI projection, and code mode, with no split between them, no definition of the fleet or the window, and no report of what the four-stage migration cost to build or whether task success changed.
- **The context-graph comparison is a slide.** "With and without graph we see massive improvement in tokens, turns and latency" is shown against one SQL question about cash trips in India; no absolute numbers, no eval set description, and no discussion of how a 40-million-entry graph is kept current.
- **Nothing is finished.** Medisetty states plainly that the blocks "are in various stages of maturity and rollout within Uber. But we want to give everyone a sneak peek of what we are up to" (01:18-01:48). The end-to-end feature walkthrough is a scripted demo, not a case study of a shipped feature with measured outcomes.
- **The precondition may not transfer.** Six years of monorepo and Bazel migration is named as the foundation, which means the parts of this architecture that assume one snapshottable repo set and a uniform build (mega dev pod, prebuilt search indexes, cross-repo agent runs) are not directly portable to a polyrepo estate with heterogeneous builds.
