## Summary

Zapier's Scout work shows how agentic code generation can turn high-volume integration-support tickets into reviewable merge requests when the workflow is embedded where support and engineers already work. The useful pattern is not just code generation: Scout gathers context, categorizes tickets, assesses fixability, runs plan/execute/validate stages through GitLab CI, lets support iterate inside GitLab, and evaluates separate failure modes so the agent can improve from real ticket feedback.

## Notes

- Zapier's 8,000-plus third-party integrations experience ongoing "app erosion" as APIs change or deprecate, creating support backlog, reliability issues, poor customer experience, and churn. (01:22-02:18)
- The first support-shipping experiment used guardrails: four target apps, engineering review on support-originated merge requests, and a focus on app fixes. (03:14-03:29)
- Discovery found that much of the app-fix process was context gathering from third-party API docs, internet searches, internal context, and logs before implementation could begin. (03:48-04:42)
- A separate Autocode playground had poor adoption because it added another window and was not embedded in engineer workflows; diagnosis gained traction only after support embedded it into the ticket creation process. (05:40-07:22)
- MCP tools brought Scout APIs into engineers' Cursor workflow, but the high-value diagnosis tool was still too slow for synchronous IDE work, pushing the team toward asynchronous agent orchestration. (07:28-09:19)
- Scout Agent sequences diagnosis, ticket categorization, fixability assessment, merge-request generation, support review and test, GitLab-based iteration, and engineering review. (10:09-11:05)
- The implementation is kicked off by Zaps, posts diagnosis and routing context to Jira, runs plan/execute/validate phases in GitLab CI/CD using Scout MCP and the Cursor SDK, then attaches the merge request back to Jira. (11:05-12:04)
- Zapier tracks Scout with three separate questions: whether the issue was categorized correctly, whether it was actually fixable, and whether the generated code fix was accurate; more processed tickets become future test cases. (12:39-13:04)
- Scout reportedly generated 40% of support's app fixes and helped some support team members move from one or two fixes per week to three or four. (13:07-13:43)
- Support is a strong validation surface because its tickets are fresh, logs may still exist, and support understands the customer-specific behavior that should be preserved. (14:24-15:10)
