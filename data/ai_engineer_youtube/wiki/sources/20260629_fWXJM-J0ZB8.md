## Summary

Rachel Lee Nabors (Arize, formerly React/Mozilla/W3C/Microsoft Edge) argues most frontier-model calls are wasteful and can be replaced by small local models measured your way to the answer instead of guessing. She lays out the cost of one-size-fits-all cloud inference (security/trust, latency, uncontrollable business cost, offline unavailability, productivity outages), the vocabulary to reason about model performance (task-specific vs small language models, quantization, golden datasets, capability evals, LLM-as-judge, P50/P95 latency), and a repeatable right-sizing framework built with Google (web.dev): **prototype big, deploy small** — prove the task is possible on the largest model, set success criteria as input/output pairs, test from small model up, then select the SAGE ("small and good enough") model. She walks a concrete case from her side project Mima (a social client): a thread-summarization feature prototyped on Claude Sonnet, exported into a 14-thread / 28-example golden dataset scored in Arize's open-source Phoenix, benchmarked against Qwen 2.5/3, Llama 3.2, and Gemma 4, where Llama 3.2 3B won on accuracy-vs-latency. She then closes the ~10% gap with one-variable-at-a-time prompt-variant testing (few-shot beat strict-rules and chain-of-thought) plus deterministic harness post-processing, surfaces an LLM-judge self-preference bias (Claude judging its own family too strictly against Llama), and ends on regression evals run like CI/CD and on-device APIs already shipping (Chrome's prompt API → Gemini Nano, Pixel 10 Pro).

## Notes

- Costs of one-size-fits-all cloud inference: security costs trust (data leaves the stack, risk of exposure/interception/retention/breach), latency costs UX (research puts ~4 seconds as the believability limit for AI responses, and many frontier calls exceed it), third-party inference cost is uncontrollable and compounds as agentic reasoning consumes tokens faster than prices fall, and remote models simply fail offline or in secure/no-Wi-Fi environments (productivity). 01:17-02:48
- Model taxonomy cheat sheet by input modality: camera/vision → MobileNet, YOLO, MediaPipe; microphone/audio → Whisper, Wav2Vec2; chat/translation/analysis → small language models like Gemma or Qwen. SLMs are for when you need GPT-style language power but not the "sum total of human knowledge" or multimodal breadth. 03:02-03:36
- Size framing: SLMs hold millions to billions of parameters; LLMs hold billions to trillions — even the smallest LLM dwarfs the largest SLM, driving a large difference in required machine. Most production jobs (summarize a thread, detect if someone's being a jerk) need far fewer parameters than a frontier model carries. 04:05-05:01
- Deployment: most mobile/web SLMs ship quantized (8-bit, 4-bit), roughly quartering disk and memory; ~1B params fits ~2GB in FP16. On-device models already ship (Pixel 10 Pro), and Chrome's prompt API exposes Gemini Nano natively so you ship no model to browser users. 05:14-05:51, 28:55-29:20
- Energy: research shows SLMs consume the same or less energy for correct responses; an SLM uses ~25% of an LLM's task energy and a task-specific model ~half of that again. Nvidia's 2025 paper called SLMs "the future of agentic AI," sufficiently powerful for agentic task loads. 05:59-06:48
- Local demo: Goose (open agent harness) running Gemma answered a reasoning-heavy biology question (ichthyosaur echolocation) correctly — "no fossil evidence of a melon or the specialized bones dolphins use for conduction" — where Claude hedged ~1/3 of the time. 07:03-08:28
- Right-sizing framework (built with Google, on web.dev), "prototype big, deploy small": (1) prove the task is possible at all on the largest/most-capable model (foundation model like Gemini or a tough task-specific model); (2) set success criteria by collecting input/output pairs — a **golden dataset**, a curated, high-quality, preferably human-labeled collection used as ground truth to evaluate/validate/benchmark; (3) test from small model up, comparing against the big-model baseline (a **capability eval**: what can this agent do well?); (4) select the **SAGE model** — "small and good enough," the smallest model that gives acceptable responses for your inputs. 08:43-09:46, 10:30-11:02, 13:34-13:58, 18:34-19:24
- Mima case: thread-summarization feature prototyped on Claude, exported to a JSONL golden dataset of 14 threads × 2 outputs (short summary, summary-with-references) = 28 examples. Success measures: JSON validity (via `JSON.parse`), reference structural validity (do the cited thread parts exist?), factual consistency (LLM-as-judge — cheaper than humans), length compliance (word count), and latency P50 (median) / P95 (worst case). 09:46-11:43, 11:59-12:56
- Benchmark in Phoenix (Arize's open-source eval tool). Baseline Claude Sonnet: ~2.9s avg latency, ~$0.22 for 14 tasks (~$1/day of inference for Mima). Local models' total cost is "zilch" because inference is pushed to the consumer's device/battery (a future eval axis: don't drain the battery). 13:00-15:02
- Contestants: Qwen 2.5 Instruct (1.5B, ~1GB), Qwen 3 (1.7B), Llama 3.2 (3B, ~2GB), Gemma 4 E2B (5B, ~3.1GB — the one engineers "told her to use"). Qwen 2.5 was fastest (~1s P50) but least accurate; Gemma 4 was slow (~8s); Llama 3.2 3B won on accuracy (~90%) while staying fast. Going with peer recommendation (Gemma 4) would have shipped a worse experience — the point of measuring. 15:07-17:43
- Llama 3.2's responses were often "indistinguishable" from Claude's; plausible reason is Meta's interest in models that summarize human/social content well. Run each model 3× and average. 17:43-18:34
- Closing the gap with prompt engineering (matters when you can't control the model — e.g. a mobile app where shipping a new distilled model per capability eats users' data plans, or a team committed to Gemma 3 until evals clear): isolate one variable per prompt variant. Five prompts (baseline + numbered-message input, few-shot, strict-rules/"house of no" negative constraints, chain-of-thought). Results on Llama 3.2: reformatted input ~no change; strict rules made it worse ("responded very negatively to being told what it couldn't do," "a naughty child"); CoT improved length slightly but added ~600ms; **few-shot won** — better length/accuracy, closer to Claude, only ~200ms added. Latency cutoffs: P50 1.5s, P95 3.5s (from the ~4s believability limit). 19:24-24:36
- LLM-judge caveat: with Claude Opus judging Claude Sonnet vs Llama 3.2, the factual-consistency gap was mostly Claude "favoring its little sister" / being a strict judge ("angsty" vs "cross" nitpicks) — a reason to crack open the eval and read the raw responses rather than trust the score. Structural validity and length are better handled deterministically inside the harness (post-process: check ref count vs thread length, truncate over-long summaries), which closed the gap to 100% JSON/structural validity and beat Claude on latency. 25:39-27:45
- Lock in gains with regression evals run like CI/CD tests so a future prompt tweak or model upgrade doesn't silently blow up summaries or start hallucinating — "how you keep your CTO from blowing away your agentic experience by accident one morning." 27:47-28:38
- Takeaway challenge: audit what you send to LLMs and ask "how many Claude calls could be Llama calls?"; watch for SLMs/specialized models already on-device (Chrome prompt API → Gemini Nano). 28:38-30:04
