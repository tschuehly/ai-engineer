## Summary

Paul Iusztin (Decoding AI) and Louis-François Bouchard (Towards AI) demo an "AI Research OS": a personal memory layer that sits between a "second brain" (10,000+ notes across Obsidian, Readwise, Notion, Google Drive) and any agent harness (Codex, Claude Code). Rather than a vector or graph database, the system is built entirely from plain Markdown files plus a reference index. It layers a **deep-research loop** (aimed at both the public web and the personal second brain) over a **three-layer store** — immutable raw files, an `index.yaml` catalog of summaries/metadata, and an LLM-generated *wiki* of derivatives (source executive-summaries, concepts, entities, comparisons, notes, open questions). Retrieval is hierarchical: the agent reads the index, then a source's executive summary, then wiki derivatives, and only falls through to a raw source when nothing cheaper answers. The wiki is "alive" — every question the user asks leaves a trace (a new concept/note/comparison file, logged). The talk also frames a tool-selection ladder (Google/ChatGPT → Codex/Claude Code → NotebookLM/RAG → build your own file wiki) keyed on how durable and how owned the research must be. Code is open-source at `github.com/iusztinpaul/ai-research-os-workshop`, packaged as a Claude Code plugin.

## Notes

- The problem: saved links are "a graveyard"; when starting an article, project, or feature the authors want to pull high-signal notes but never recall what's in their second brain and burn time hunting for them. They also want the system anchored in *personal* notes/values, not generic web results. (00:00-01:32)
- Why not just Codex Cloud or NotebookLM? You need a system that *sits between* those harnesses and your second brain. (00:37-00:50)
- Tool-selection ladder: fast one-off answer → Google/ChatGPT (but you depend on OpenAI's architecture and lose context each session); one-off change or single article → Codex/Claude Code; research that must stick and be revisited → durable memory; production/scale → RAG + vector DB (powerful at scale but needs infra and is not human-inspectable); a personalized, inspectable, compounding "Wikipedia" you own → build your own file-based research OS (more setup than opening Claude Code). (03:33-07:57)
- NotebookLM tradeoffs: powerful for digesting/revisiting content, but you don't own it, can't fully personalize, it's not agent-native, and it's weak for coding since it's browser-based. (05:32-06:05)
- The real bottleneck is not how much context you feed the model, but how you *reuse* it later: with an agent "the context window becomes everything — the database, the file system, the memory, the reasoning space… and when you stop the conversation, it loses everything." The fix is memory + context management, not more context. (08:39-09:16)
- Migrate scattered inputs into one local store: Louis-François used Codex to auto-pipe Granola meeting recaps, Apple Notes, and saved Chrome tabs into Obsidian (a local Markdown file system, nice UI, cross-device) so agents can leverage it. (10:14-11:01)
- The repo `ai-research-os-workshop` ships Claude Code / Codex skills+plugins for deep research, simpler search, and distillation; connectors: Obsidian, Readwise, NotebookLM, GitHub repos, YouTube/GitHub/web links, documents. Bright Data is used to parse SPAs / arbitrary pages. (11:01-12:28, 18:38-19:06)
- **V1** (course-lesson scope): input = topic + hand-picked "golden links"; scrape the golden links first as *seed context* for framing questions; classic deep-research loop — one orchestrator agent generates questions, each sub-agent owns a question and uses Gemini grounded in Google to gather links + executive summaries, orchestrator aggregates without exploding context; 3 rounds × 6 queries → ~40-50 links; a ranking algorithm scores each source against the topic, fully scrapes only top-K, keeps summaries for the rest; compile into one flat `research.md`. Generated 35 lessons fast. (12:58-15:27)
- **V2**: aim the same loop at the second brain (Obsidian, Readwise, NotebookLM, GitHub) plus the public web, so input is just the topic — the golden links are now an organic reflection of the second brain. (15:27-18:24)
- **V3**: add a wiki layer because `research.md` is a static pile — you always want a follow-up, or some info goes stale, and re-running the loop is token- and time-expensive. Sources in → wiki out: store each source as its own raw file, build an index over them, generate a wiki on top; query the wiki + index. (18:24-19:37)
- "Forget the infrastructure you think you need" — vector DBs, knowledge graphs, semantic/text search add complexity for a lightly-used personal wiki. Build on files + references only: an agent reads an `index.yaml` (catalog of all data + per-source summaries + metadata like origin/title/authors/date). Example index had 10 sources and 38 wiki pages as derivatives. (19:37-21:26)
- Wiki structure: `raw/` (immutable copies you never touch), `index`, `wiki/` (LLM derivatives: comparisons, concepts, entities, sources, notes, open questions). Obsidian renders the index as a subgraph connecting entities (opencode, closed code, MCP) and concepts (tool registry, context compaction, sandboxing). (21:26-22:16)
- Progressive-disclosure read path: index summary/metadata → the *source wiki page* (an expanded executive summary computed once at ingestion) → wiki derivatives (concepts/entities/notes/comparisons) → only if still unanswered, read the whole raw source. Pure referencing + a simple hierarchy makes retrieval token-efficient. (22:49-24:04)
- The wiki is alive: every question can spawn a new concept/note/comparison file and is tracked in a log, so the wiki evolves from *use*, not only from ingestion — a true reflection of what you asked and haven't understood. It's never frozen: ingest a custom link or run a new deep-research round any time. (24:04-25:01)
- The wiki does *not* sit over the entire second brain. The authors use the PARA method (Tiago Forte: Projects/Areas/Resources/Archive); the Obsidian vault is an immutable snapshot the LLM never touches, and work is scoped per-project via the deep-research loop. "The project is the work, and your second brain is the research." (25:01-27:04)
- Demo depth control: the research skill asks how deep — light (1 round × 3 queries), fast (2 rounds × 3 queries), deep — because deep runs consume a lot of tokens and take ~10-20 min crawling Obsidian/Readwise/NotebookLM; pick deep only for large surveys. (29:02-30:05)
- Demos: (1) build a wiki on "agentic harness engineering" from a brain-dump file + references; (2) ingest three harness repos (opencode, "Pi", Hermes) with no web research and produce per-repo notes + cross-repo architecture comparisons — "super useful if you want to write your own harness"; (3) ingest three arbitrary links with zero external setup (only git + curl); then ask a follow-up ("how remote sandboxing plugs into the harness") that queries the wiki and updates it. (27:04-36:49)
- Roadmap/weaknesses (by design a builder workflow, not a product): needs more connectors (Google Drive, Notion, Slack); hard to know which sources are outdated/weak/strong (source provenance + ranking is the next priority); next improvements are stronger linting and better memory compaction — "it's just very complicated to manage memory correctly, and the state of the art is always progressing." (36:49-39:16)
