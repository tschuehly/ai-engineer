## Summary

Jonathan Mortensen explains Apple Private Cloud Compute as a privacy-preserving remote inference architecture for sending sensitive AI requests to untrusted servers. The reusable pattern combines stateless computation, code-enforced operational limits, non-targetability, no privileged runtime access, remote attestation, transparency logs, hardware key protection, and confidential GPU/VM trends, while surfacing practical tradeoffs around trust concentration, latency, observability, cost attribution, and operational debugging.

## Notes

- PCC's motivating problem is that AI workloads may need more compute than a phone can provide, but sending private data to a remote server normally reduces privacy; the talk frames PCC as an attempt to make the remote server less opaque to the client. (02:23-03:29)
- Apple PCC requirements are stateless computation, enforceable guarantees, non-targetability, no privileged runtime access, and verifiable transparency. (04:02-05:14)
- The conceptual design removes operational escape hatches such as SSH and disk persistence, then has the client verify what code is running before sending data. (07:28-07:58)
- The named technical components include Oblivious HTTP, blind signatures, secure enclave or TPM-like hardware, secure boot, hardened OS, remote attestation, transparency logs, confidential VMs, and confidential H100/H200 GPU memory. (08:12-10:17, 17:37-18:52)
- Remote attestation returns signed claims plus a public key; the client decides whether to trust the claims, then uses the public key so later decryption depends on the server still matching the attested claims. (10:32-11:45)
- Transparency logs record signed hashes of software releases or components so reviewers can inspect public binaries and clients can compare attestation results to the log. (11:52-13:14)
- The talk calls out tradeoffs: trust still shifts to Apple's supply-chain and key-management behavior; the system is limited to official Apple paths; remote privacy layers add latency and encryption cost; no SSH, no logs, and weak per-user usage tracking complicate operations and billing. (15:06-17:32)
