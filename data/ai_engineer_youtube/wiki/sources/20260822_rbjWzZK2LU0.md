# Give the Agent a Budget, Not a Token — Sachin Malhotra, Anthropic

## Summary

A twenty-minute talk from an engineer on Anthropic's CI team — "everything from test quarantining to merge automation to CI autoscaling to merge cues," described as "the plumbing that allows a few thousand engineers every day to ship code safely" (00:25-00:45). It is an operator's talk rather than a vendor pitch: one production incident opens it, three enforcement primitives and one sizing question follow, and each primitive is illustrated by a control that team or an adjacent one actually shipped. The argument is that a token is the wrong data type. It is "a boolean… a static list of scopes. You either have it or you don't have it," so "if the token list is too tight, then your agent is effectively useless. If the token list is too wide, then you're maybe writing a postmortem" (04:57-05:18). A budget has four dimensions instead — how much, how fast, what can be undone, and who notices (05:18-05:45) — which becomes three things you enforce (asymmetric verbs, rate limits, trip wires) and one question you ask about all of them (the undo test) (02:37-03:02).

The evidence base is one narrated incident, three deployed controls, and one recurring caveat that the talk is honest about: no rates, no before-and-after numbers, and one self-reported effectiveness figure ("about 80%") for the text layer with no measurement method behind it.

## Notes

- **The demo shape the talk is arguing against.** "Someone gives an agent a god token… and gives it an access to some sort of tool list and just watch as it goes," a coffee website built and deployed "in 3 seconds," and "someone will ship it into production." The talk is explicitly about "what happens after that, after the demo ships, once the agent is starting to do some real work in production." (00:54-01:26)
- **The incident, in full.** The agent was cleaning up after itself, listing workloads it no longer needed and deleting them — "completely reasonable except one stage in the pipeline basically evaluated to nothing and the filter dropped out and now the selector matched everything." About 200 workloads, roughly 20 engineers' worth of work, gone in 90 seconds; some were long-running training jobs, "maybe some of these were not even checkpointed," so "hours of progress that was gone poof in like 90 seconds." (01:28-02:21)
- **The diagnosis that reframes it.** "The agent technically hadn't done anything that I couldn't have done. It was using my token after all. The failure wasn't the model itself. The failure was that I was giving the agent unbounded amount of power to do something that I wasn't watching super intently." (03:06-03:26)
- **The junior-engineer analogy is used precisely, not decoratively.** "We don't basically sit around watching every engineer… type out every keystroke," there is always an escalation path, and "the catastrophic stuff is just structurally out of reach for them." The disanalogy is stated too: agents "never get tired. They never sleep. And every so often they're just like very confidently wrong. Um, and if I'm being honest, that's maybe most of us on the first month of our jobs anyways." The talk closes the loop at the end — the four controls are "some sort of onboarding checklist for your engineers… We just wrote it for people. It's now the same checklist that we want for agents." (03:30-04:21, 15:11-15:28)
- **Why scope-narrowing is rejected as the fix.** "The standard fix for an incident like that is basically that you narrow the token scope… you just take the deletes away effectively. You would technically never do that for a new hire… And it also doesn't work for an agent either. Maybe it works for about a week, maybe two, but then you eventually end up in a situation where the agent is genuinely trying to delete something… and you will just be there sitting and pressing enter by hand all over again." (04:23-04:57)
- **Asymmetric verbs, with the CI instance.** Verbs are "operations or actions that an agent can take… API calls… CLI commands"; they are asymmetric because "the same sized action even though it looks same size… can have very different blast radius in actuality depending on which direction it goes" (05:47-06:11). Unskipping a test wrongly turns CI red and "a human can actually put them back very cheaply"; paging a human wrongly is "a nuisance for the on call. But there's always a human to correct it"; skipping a test wrongly means "nothing technically turns red. A real bug can actually walk into production with green checks and nobody would notice it until much later." The quarantining service holds the currently-skipped tests, an on-call break-glass list the agent may re-enable from but not add to. (06:21-08:07)
- **Provenance is not the agent's job.** "The agent itself is not responsible for writing the row or the audit trail itself. There is a proxy in the middle… responsible for stamping the caller's main identity on every call, whether it's a skip or an unskip… the agent technically never holds the pen on its own provenance." (08:07-08:24)
- **Rate limits, and the bypass flag that will not fire for an agent.** "Every caller gets a small amount of disruptive actions per time window… there's no approval, there's no waiting. And if you cross the line, the request simply bounces back with a count… You wait a bit and then the limit essentially refills" (08:34-08:53). "Every write effectively gets a rate limit. There are no exceptions to that. What changes is the size" — larger in your own namespace, smaller in a shared one (09:01-09:16). The team next to his built "an admission web hook of sorts whose sole job is to cap the number of deletes at a fixed number per hour per resource kind per name space," with a bypass flag that "inside a cloud code session or inside an agent session… simply refuses to do anything. All it's going to do is tell the agent to ask the human to run the command itself. So the agent effectively gets the rate limit and the human keeps the override and nobody effectively has to file a ticket for the limit because it just refills." (09:19-10:03)
- **Trip wires versus allow lists.** "An allow list is effectively a guess that you're making up front about what the agent needs or about model behavior… you write it up front before you have any data on how the agent is behaving. A trip wire on the other hand is how you get that data after the fact." Rate limits are the enforcement, trip wires are the observation; "you effectively watch the aggregate and not individual calls"; "usually when a trip wire goes off the fix is like maybe one or two lines in the agent's context and not really a big code change"; "allow lists don't really get better over time. They can get stale but trip wires do get better over time." (10:05-11:03)
- **The trip wire that fired.** They track one number: investigation threads launched per hour for a given test job failure. One morning it was far above baseline and paged on-call — "a trip wire that nobody sees is practically useless" — and "it pages after the write has already happened, after the limit has been crossed, not before. It's effectively the smoke detector not the lock on the door." The agent had opened threads for dozens of jobs sharing one error signature: "each thread effectively looked reasonable on its own, but if you took them in aggregate, you would realize that it was actually an infrastructure failure." The fix was one instruction — correlate related failures before launching a separate investigation — and "the next time when this happened, it did exactly that." (11:04-12:10)
- **The undo test, and how it differs from asymmetric verbs.** Two questions: "can the agent put it back by itself? and how bad would the impact be if it actually got it wrong." The distinction is stated explicitly: "the verbs ask whether you would notice the failure and undo asks whether you can recover from it." If the agent can roll back and the blast radius is acceptable, "you log it and you let it go"; if either answer is no, "you need a second key, and the second key is not something that the agent holds itself. It has to be someone else," plus an audit record of why the second key was involved. (12:12-13:06)
- **The second key can be an existing scope split.** On the feature-flag service the agent "has the full dial" over canary — staging traffic and dogfooding customers — and can ramp a flag zero to 100 and toggle it back off on a filed bug, but its key is not scoped to promote a flag to production; "the best that an agent can do for now… is that it can propose that someone actually promote the feature flag." "The second key in this scenario is not necessarily a new auth system. It's a scoped key for production and a scoped key for canary." Day to day he asks Claude in Slack to own the whole rollout loop, it asks a clarifying question about which audience, "and the important part is that I'm not in the middle of any of these things." (13:07-14:14)
- **The four controls replayed against the opening incident.** "The rate limit itself would have capped it at a few couple of tens of workloads. The undo test… will basically tell you that you can't un-delete a running job in someone else's namespace. So anything past the cap basically needs a human with a second key." He also notes "you don't need all the checks in every write scenario." (14:44-15:11)
- **Where policy lives.** Two places, both required. Text — "prompts… context files, markdown the agent reads before it can act" — is "where you can explain your why, the intent," and "we got exactly the same sentence that I was showing earlier written down in a markdown file. It works about 80% of the time." Upside: cheap to change, explains reasoning. Downside: "you have to garden it because the files can grow over time, and at the end of the day it's just advice… there is no enforcement anywhere." Infrastructure — the proxy — "is not reading the prompt. It doesn't know why the agent wants to do something and it doesn't really care. It will see a delete… it'll see a budget being crossed and it'll simply return a 403 and that's the whole conversation really. It's narrow. It's deterministic… What it can't do is explain the why, and a clever prompt injection cannot really talk it out of the rule itself." The summary line: "the text shapes what an agent is trying to do and infra is bounding how wrong can it go." (15:30-16:40)
- **The deployment shape.** "Every agent session has its own proxy running right next to it. The agent starts off by reading its own context file… that's the text layer, and every outbound call goes through the proxy after that point, which is the infrastructure layer." The proxy does not follow the work — for jobs launched into a Kubernetes cluster, "what is following is the stamp itself, the identity itself. So the cluster would write the stamp onto the job as a label, and every child job or anything that's happening afterwards simply inherits the same identity," and "every safeguard that is there in the rest of our systems… whether it's ownership, whether it's quotas, rate limits, approvals, trip wires, whatever it is, they're all keyed on the same stamp and the agent never got to touch it." (16:42-17:42)
- **Why the proxy stamps and not the caller.** If the agent can set its identity in a header, then on hitting a limit "what's the easiest fix from an agent's point of view? It'll just change the header… instead of sachin, sachin2, and voila, you just have a fresh budget to work with. Now, in this case, you technically don't have a rate limit. You just have a suggestion." With the proxy in the path "the agent never gets to say who it is. The proxy already knows. It's the thing that's holding real credentials and it stamps every call with the identity that it already knows, not the one that agent claims." A per-session ID falls out of the same stamping, "so that you're able to differentiate different sessions… and see which one's overreacting." The closing rule: "identity… has to come from the infrastructure, not from the request. If you get that one rule right, everything else is just tuning." (17:45-19:32)
- **Evidence limits, and they are broad.** Everything is one team's operational experience, reported without measurement. The incident has counts (200 workloads, 20 engineers, 90 seconds) but there is no rate for how often such incidents occur, before or after. None of the three primitives is reported with a number: no count of rate-limit rejections, no false-positive rate for the trip wire, no measure of whether the corrected investigation-correlation instruction held beyond the one repetition described. The "about 80%" for the text layer has no denominator, no task definition, and no stated method. The bypass-flag behavior is described as refusing inside an agent session but the detection mechanism is never named, which matters because it is an in-band check of the same kind the talk elsewhere argues cannot be trusted. The proxy is described only as a per-session sidecar holding real credentials; nothing is said about how it authenticates the agent process, what happens if the agent bypasses it, or how it is prevented from becoming a single point of failure for every agent session.
