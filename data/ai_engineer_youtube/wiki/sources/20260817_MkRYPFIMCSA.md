## Summary

Ryan Dahl (CEO, Deno; creator of Node.js) reports a working deployment — incident-response agents with read *and write* access to production Postgres, Kubernetes, ClickHouse, AWS, GitHub, and Slack, closing incidents that previously required a human in the loop — and then argues the security question that deployment raises. He grants that Opus refuses over and over when pushed to drop the users table, and rejects that as a control: "security can't just be wishful thinking that Opus will always obey your wishes." Because the agents are wired into the support system, they can be prompt injected from outside, so the agent is untrusted software and the guard cannot live inside it. The reframing that carries the rest of the talk is that every action an agent takes, good or bad, is bytes on the wire — and the dangerous bytes are frequently not HTTP, because the agent can spawn `psql` as a subprocess and tunnel to a production database through an EKS endpoint, a path no MCP tool definition or HTTP rule can see. Deno's answer is Claw Patrol, an MIT-licensed proxy that sits in front of the agent and parses every byte below the HTTP layer, with protocol plugins, rules written in HCL and checked into git (Deno's own file runs about a thousand lines, with fixture-request unit tests), credentials held by the proxy so the agent never sees a secret, and rule outcomes that can reject, ask an LLM judge, ask a human in Slack, or combine them. The demo is Codex in yolo mode obeying an order to delete the users table and the proxy killing it at the Postgres wire protocol.

## Notes

- The deployment, stated first and without hedging. Deno Deploy "has incidences… we've got a pager duty that fires," and "recently we've been playing around with using agents to automatically service these incidences. Um, in particular, OpenClaw, but other other agents as well." The access list is explicit: "Postgress, Kubernetes, Clickhouse, AWS, GitHub, Slack… all sorts of things. And we we do actually give them uh rewrite [read/write] access to these systems." (00:36-01:35)
- Why the access is broad on purpose: "the agents can actually get all of the context. They can see traces in ClickHouse. They can look in the production Postgress database at… what projects a user owns. They they can look through Slack for uh communications uh GitHub logs etc." The result: "this actually works quite well. Uh the the agents are actually able to solve quite a lot of incidences where we previously would have a human [SRE] in the loop." (01:36-02:16)
- The danger, in the same operational vocabulary: "they could start a psql subprocess and issue a delete users table… they could call [kubectl] delete namespace prod… they they could decide somehow that solving the incident it means you know removing all of the users." (02:16-02:47)
- Alignment is granted and then declined as a boundary. "We use Opus and Opus is remarkably well aligned. You can really… try very hard to to get it to delete the user's table and it will refuse over and over again. But this is not sufficient, right? Security can't just be wishful thinking that Opus will always obey your wishes." (02:47-03:12)
- The injection path is the support system, not the open web. "These S[RE] agents that we have are connected to the support system and thus can be prompt injected from the outside and that means that they can be manipulated somehow. Like who knows… what sort of uh string of characters could send opus into some bad state that allows it to think that it's taking the right action by doing something very undesirable." (03:16-03:44)
- The stance that follows: "the agents themselves have to be untrusted software. You can't rely on the agent itself to guard what it's doing. You can't put the guard inside the agent." (03:44-03:58)
- Threat-model scoping — why the filesystem is not the concern. "We run agents and I assume many of you do the same on standalone VMs. So we're not very concerned about agents touching files on the file system… they're properly isolated at the system level." (04:01-04:22)
- The reframing everything else rests on: "effectively every nefarious action that that an agent could take, every good action that it takes, comes in the form of some network communication, some bytes over the wire." Those bytes are formed in various ways: "You can of course call through MCP but also subprocesses and if you think of Postgress for example this is a nonHTTP protocol that uh open cl[aw] can just spawn as a subprocess and start connecting to services… so we take the stance that we really want to understand what the bytes are coming out of that agent in great detail." (04:24-05:11)
- The hard case, given concretely. "We have a production Postgress database in AWS um that is inside a VPC that we can only reach really through uh an EKS endpoint. And what we'd really like to do is ensure that our agent, which we want to give access to everything essentially, can't somehow tunnel through this EKS server, spawn psql, and drop the users table." Summarized as: "this is an outbound path the agent's host can't reach on a protocol that isn't HTTP that's gated by a rule that understands SQL. These are what human S[RE]s would do." (05:14-06:33)
- Why per-system credentials are not the answer. "You might say, well, you know, there's ACL's, there's permissions, you can issue readonly uh Postgress credentials… and yeah, that's true up to a point… you can do careful credential provisioning and you should. Um, but this this really requires uh working across many different systems, provisioning credentials in in incredibly careful ways. And as I just demonstrated, the composition of access can lead to holes when you can access one system and then another system." (06:34-07:12)
- Why MCP tool permissions are not the answer either. "MCP, you know, you can structure all of this as uh very careful MCP uh tools that uh have the proper permissions. But, you know, then then you can't spawn subprocesses, right?… as soon as the [OpenClaw] spawns the the PSQL, uh you're… broken through the the security boundary." (07:12-07:40)
- The landscape Dahl places Claw Patrol against, with the limitation he assigns to each. LLM gateways ("Open Router, Light LLM, for example. These often have a guard rails feature that can… guard against prompt injection… scan for various expressions… going back and forth between the LLM provider. But, of course, that's just the LLM. uh you know we're we're talking to databases and stuff"). HTTP proxies ("systems like HTTP jail and Crabtrap that are HTTP proxies that really sit at at the HTTP layer" — httpjail letting you "write rules that say well you can make get requests but not post requests or you can access this HTTP subpath"; "Crabt[rap] is a project from Brex that has a LLM as judge that operates on the HTTP requests flowing back and forth"). Credential-injecting proxies ("agent vault uh being a popular one where the the agent itself never actually sees the credentials of the system that it's talking to but passes some placeholder out and the proxy itself injects those credentials. This is an important part of the problem but not a complete solution"). Process sandboxes ("Nvidia's OpenShell" — "OS system level uh guards against say accessing different file system paths… accessing different S[YS] calls," which Deno does not need because agents get standalone VMs). (07:40-09:58)
- Claw Patrol itself. "It's an open- source MIT license project and this is a proxy that sits in front of your agents. Um it operates not at the HT[T]P level but at a lower level. It understands each and every b[y]te flowing… out of your agent. It holds credentials like agent vault and can inject those credentials so that your… agent software… doesn't ever actually see secret values. And… it has a very advanced rule system that allows you to say in in precise details how and what requests get transferred out of the agent and talk to the outside world." (10:00-11:02)
- The rules are the system. "These rules are… kind of the key piece of the system and we write them in a configuration file using a language called HCL… This is like the Terraform… configuration language. Uh it actually works really well here. So we have a file that we check into git and we manage very carefully that essentially defines the permissions for all of our services at [Deno]… it's a big long file. It's like a thousand lines and… we manage each and every change to that in kind of precise detail." The shown example "blocks certain Postgress functions from being… called." (11:02-11:52)
- Two properties of the rule engine. Rules survive indirection: "again Postgress being a nonHT[T]P protocol and these rules can be applied even when tunneling through other systems." And the protocol set is extensible: "it supports uh a number of different protocols and has a plug-in system to extend it when you run into a protocol that it is not yet familiar with." (11:52-12:16)
- The demo (recorded, not live). "We call claw patrol run code[x] in y[o]lo mode so that it just does what you say it should do. And you tell Codex, hey, delete the users table from Postgress and Cod[ex]… properly obeys and starts a Psql subprocess where it deletes the… users table. That… Psql subprocess opens a network connection to… the Postgress server that goes through claw patrol where we pars[e] each and every b[y]te. We understand the Postgress protocol. We apply our rules and ultimately reject that what we call an action from… doing something destructive." (12:16-13:14)
- The dashboard, and the vocabulary choice inside it. It shows "a couple of different uh devices or agents and the the various requests that are flowing through. Some of them being denied, some of them need approval… And you can click into to each request or uh action as we call it because it's more general than HTTP requests." Purpose is stated modestly: "it's very uh utilitarian driven. It's like what what we need to understand our own agents." (13:14-13:56)
- Approvals as a rule outcome, composable. "You can define rules that don't just reject requests or actions but uh ask a human for example in a slack channel or run an LLM judge over this um or any combination thereof, right? Maybe first get an LLM judge and then get approval in Slack. uh so that you can have again very precise control over what your agents are doing outside of the agent software itself." (13:56-14:31)
- The integration contract: "we treat the agent software as a black box, right? We… don't require any changes to to that software." (14:31-14:41)
- Credential injection is broader than bearer tokens. "Credentials come in many different forms, they're not just uh bearer uh headers… it handles cookies, it handles Postgress as I mentioned, uh click house, supports all sorts of uh [OAuth] protocols, supports very complex things like AWS SIG v4." (14:41-15:11)
- Deployment shape. "This system works over tail scale or wire guard… we ourselves run claw patrol, run our agents inside of tail scale inside of a tail net, and claw patrol acts as a tail scale exit node. Um we also lean on tail scale for authentication to the dashboard. So your… tail scale identity actually allows you access to the dashboard so that we don't have to layer on another authentication mechanism. But we also have this wire guard for people who have not bought into the wonderful tail scale ecosystem." The reason it works: "we know that all of our stuff is off the internet and all of these very security sensitive things are tightly controlled." (15:28-16:12)
- The caveat Dahl volunteers about his own design: "Claw Patrol itself is holding all of these credentials to production systems. So you have to be very careful with it." (16:12-16:32)
- The thesis, restated at the end. "Agents can't be trusted to police themselves. That includes security plugins or modifications to the agent software itself. The security boundary has to be elsewhere. And that's not to say that alignment is not a good thing, but… for real world security systems, we really do need to control this at a higher level." (16:32-17:08)
- Q&A — how the rules are tested. "This rule file actually has a test system along with it where you can provide uh fixtures, action like fixture requests that can flow through the rules and then you can uh essentially create unit tests to make sure that… that request it will always be blocked by your set of rules. And then of course for the claw patrol software itself we have a large suite of testing." (17:26-18:04)
- Q&A — does this get easier as models improve? "I think we will never be able to fully trust uh AIs. I think it becomes less and less of a problem as they are smarter, have better context, know that they're working with a company, know that they shouldn't be doing bad things. Opus is more aligned than previous models, but I think we're always going to have to have uh backstop security mechanisms." (18:10-18:42)
