# Building Agent Interfaces: Lessons from Chrome DevTools (MCP) for Agents

Source: [Building Agent Interfaces: Lessons from Chrome DevTools (MCP) for Agents — Michael Hablich, Google](https://www.youtube.com/watch?v=_B4Pv9ttFgY)
Uploaded: 2026-06-05

## Summary

Michael Hablich, product manager for Chrome DevTools, gives an honest "we built the same thing wrong three times" account of designing Chrome DevTools MCP for agents (works in any MCP client — Gemini CLI, Claude Code, Codex, Open Claw). The unifying frame is that an agent is a separate user class: it shares the human's intent (find and fix page errors) but has different cognitive bottlenecks (humans need visual layout/color; agents need semantic structure and small context), so the interface needs its own non-functional requirements (efficiency, discoverability, security, stability). Four durable lessons follow: (1) return semantic markdown summaries instead of dumping a 50,000-line JSON performance trace that blows the context window — "point it at the right sentence, not the whole book"; (2) measure the fuel efficiency of the interface with **tokens per successful outcome** (effectiveness × efficiency, conditioned on completing the journey, measured per user journey not globally); (3) turn errors into recovery so the agent self-heals without a human — actionable error messages, proactive detours that counteract training-data priors, and diagnostic-playbook skills; and (4) never compromise trust for convenience — the team kept the per-use "autoconnect" friction by design because a local browsing agent sits in Simon Willison's lethal trifecta, and reasoned about three tiers of browsing-agent exposure. Token-burn reduction has three concrete levers (tool categorization, a 3-tool "slim mode", and a CLI that chains commands so post-processing like grep stays on the local machine), and tool decomposition went from one monolithic `debug_webpage` → 25 tools (a discoverability problem) because "the schema is the UI for the agent" and ~97% of MCP tool descriptions have quality smells.

## Notes

- Chrome DevTools MCP shipped one tool, `debug_webpage`; agents failed silently because they could not compose behaviors, so the team decomposed it into 25 focused tools — which only traded the problem: agents now had 25 tools and no reliable way to pick the right one. 15:28-16:10
- The first performance-tracing endpoint returned the raw trace file: ~50,000 lines / multiple megabytes of JSON thrown at the agent, which blew through the context window (Hablich cites "the dump zone"). The fix was to return markdown + semantic summaries (LCP, INP, CLS and key metrics): "we didn't force the agent to read the entire book, the trace; we pointed it at the right sentence." Raw output is still available for post-processing with other tools. 03:58-05:20
- "Agents are a different/separate user class" — they share the goal with humans but think differently, so the interface needs its own non-functional requirements. 05:25-06:05, 21:32-21:50
- **Tokens per successful outcome** = fuel efficiency of the interface. Effectiveness = does the agent complete the entire user journey / is the functional intent fulfilled (yes/no); efficiency = token cost, tool calls, duration. It is "successful outcome" not just "outcome" because fuel economy is worthless if you can't reach the destination. Measure per user journey / task class, not globally (web scraping is cheap; debugging a broken responsive layout is intricate and uses more tokens — and that's fine). A per-use-case bar chart shows the shorter bars as where to focus optimization next; even an imperfect measurement beats gut-driven decisions. 08:18-11:03
- Three token-burn levers: (1) **tool categorization** — hide niche tools (e.g. Chrome-extension debugging) behind command-line parameters instead of the default context; (2) **slim mode** — push categorization to the limit, exposing only ~3 tools (select page, navigate page, evaluate script), great for context but a trade-off (the agent may take extra turns or lack the right tool, e.g. can't get network requests with evaluate-script); (3) **CLI interface** — a command line alongside the MCP server with nearly the same functionality so the agent chains commands and does post-processing locally (extract accessibility tree with grep, pipe the control ID into a click), keeping tokens off the model. 11:10-13:12
- Error recovery is a spectrum: actionable error messages enable self-heal — adding "no previous page in history to navigate" to "Unable to navigate back in currently selected page" let the agent fix itself without a human; proactive detours counteract training-data priors (route performance profiling to the start-performance-trace tool, not the Lighthouse audit); a `troubleshooting` skill (diagnostic playbook) kicks in to fix common MCP-setup mistakes. Every error costs retry/reasoning tokens, so efficiency is useless if the agent gets stuck. 13:14-15:16
- "The schema is the UI for the agent" — a cited paper says ~97% of MCP tool descriptions have quality smells. Better descriptions help selection but increase context-window size, and smaller models in particular get biased into calling tools they shouldn't. Uncontroversial guidance: define purpose (clear core function) and usage guidelines (clear activation criteria); e.g. "used to find front-end performance issues and core web vitals, LCP, INP, CLS." It's an "endless quest for minimum viable description" because models and harnesses keep changing. Skills can supercharge intricate workflows but are not a free lunch — too many shifts the problem (agents call skills they shouldn't; context grows): "the trade-off is shifting, not disappearing." 16:12-18:33
- Trust: the **autoconnect** feature lets a human share the browser/screen with a coding agent. Users asked to remove the per-use "allow" click ("remember my choice"), which in traditional UX is a clear win — but the team kept the friction by design, because a tier-1 local browsing agent sits in Simon Willison's **lethal trifecta** (private data + untrusted web content + ability to act/exfiltrate). Three tiers: (1) local dev — human-in-loop, time-bound grant of the default Chrome profile; (2) CI — controlled but separated, use data separation (containers, separate Chrome profiles) and connect via the remote debugging port; (3) full internet access = "YOLO mode" — every webpage can prompt-inject, so require a domain allow-list plus prompt-injection mitigations. A tier-1 local agent and a tier-3 browsing fleet may share a tool but should share nothing else of the security model: "never compromise trust for convenience." 18:33-21:30
- Closing takeaways: measure fuel efficiency with tokens per successful outcome; turn errors into recovery playbooks; audit descriptions for intent; never compromise trust for convenience — "agents are our next users; let's help them help us." 21:32-22:15
