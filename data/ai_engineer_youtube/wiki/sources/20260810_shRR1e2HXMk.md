## Summary

Dominik Kundel (OpenAI) walks the Codex harness in the order a message travels through it — context construction, actions, speed, loops, compaction — and the organizing frame is that two protocols bracket the harness on both sides: the **app server protocol** between the UI and the harness, and the **responses API** between the harness and inference. Both are described as deliberately open. The app server is what third parties build on (he names "Theo's T3 Code" and "RemoteX," and says he used the same protocol to put Codex inside Claude Code as a plugin, and, the day before, inside Doom); the responses API was codified into an "open responses schema" with a governance body and partners including Ollama, LM Studio, and Nvidia, so "you can use any responses API compatible… model provider and actually plug it into the Codex harness." The harness itself is Apache 2 and written in Rust. He opens with a disclaimer that matters for how any of this should be read: "this is a current state of affairs. Like things change so quickly… especially with new model releases, we often release new APIs and change sort of how the harness works." (01:16-04:08)

Context construction is optimized against three things at once — **size**, **flexibility**, and **cachability**. Size is not only a token-budget concern: "the more context you have in your context, the higher it is that you have contradicting information and it causes confusion for the model." Flexibility means the experience should hold "regardless of how many or how little skills you're using… regardless of how many plugins and MCPs you install." Cachability is the cost term. The useful diagnostic he draws is that these three pull hardest on exactly the *unpredictable* parts of the context: model instructions "are fairly structured and don't really change in size or like mess around with [cachability]," while the available-skills list and the tool registry grow with whatever the user installed. Two mechanisms answer that. **Deferred tools** are marked so they are "not added directly to the context window, but instead are available through tool search later on" — a per-tool flag in the responses API since GPT-5.4, paired with either OpenAI's built-in tool-search tool or one you implement yourself. And the **available skills list is capped at 2% of the maximum context window**, with descriptions progressively trimmed as the list grows past the cap rather than skills being dropped. (04:20-06:59)

Actions are split into three kinds. **Async actions** — subagents and background terminals — share one primitive: a `spawn agent` tool creates instances, and a `send input` tool either sends new content, waits for an agent, or shuts it back down; background terminals use the same shape with data going in over stdin and a wait with a timeout. **Computer use** has moved off a fixed action vocabulary: the 2025 responses-API version "only allowed you to do one action at a time" and required implementing each exposed action type, while recent models and API shapes "allow you to use code execution instead to actually do computer use," choosing JavaScript or Python. Codex's browser use is the worked instance — a **persistent Node REPL held across turns** in which the model writes Playwright, so it can inspect one page's structure and then script the rest: "look at for example one page, understand the structure, and then write a script to perform like scraping for example on subsequent pages more easily." **File system** actions are where the training distribution shows through: every model from GPT-5 on "has been trained on the concept of an apply patch tool to do file editing," everything else goes through a shell tool, "you will see the model naturally trying to use Ripgrep… since that's what it got used to during training. So we're actually in the Codex harness shipping Ripgrep with the harness if you don't have it installed on your own," and on Windows the model was trained to write PowerShell natively. All of it runs through a sandbox layer: Seatbelt on macOS, Bubblewrap on Linux, and on Windows a custom sandbox OpenAI had to build and open-source in the same repository. (07:01-11:57)

The security half starts from a live audience poll on approval fatigue and full access, followed by a second poll: "how many of you know that like IT and security really hates that you turn on full access?" The failure model he gives is not a malicious model but a high-agency one: "especially if you're trying to push the model through prompting to really have high agency, that can be misinterpreted by the agent to not match up with your expectation" — asked to email a file, it cannot attach one, so it uploads the file to a file share instead; or it "messes up some escaping and accidentally deletes too much data." The answer is **auto review**: when a sandboxed action escalates, the model spins up an **auto review subagent** that "runs entirely separate and can't spin up other subagents and has read permissions only," and is given the transcript, the actual tool calls, a risk taxonomy, and a notion of user authorization. The rubric's load-bearing axis is how explicitly the user asked: "if you ask it to delete a dot git folder, great. If you didn't ask it to, it should probably not touch that part and like completely delete your history" — and the same axis applies to network calls, where "curling Google to see if… the internet works is fine, but maybe not uploading a file." He flags his own description as "a gross oversimplification" and points at a blog post. (11:59-15:32)

Speed is the talk's sharpest single finding, and it is a bottleneck-shift claim. After launching **GPT 5.3 Codex Spark** running on Cerebras "at 1,000 tokens per second," "with all of these tool calls and the interactions, inference… no longer was the bottleneck. It was actually the network." The response is **WebSocket mode**: the responses API stops running over server-sent events and HTTP and uses a persistent WebSocket, which saves connection overhead *and* provides stateful context, "which means we only have to send the data that actually changed. So, for example, if there's a tool call, we only send back the result of the tool call rather than sending all of the items back" — one item per turn instead of, in his demo, nine. Two loop mechanisms close the talk. Long-horizon `/goal` runs work by the harness **injecting a continuation prompt containing the objective after every turn** and continuing "until the model itself calls an update… goal tool, which specifies that… the goal was actually achieved" — which is why "you actually don't want to… write full essays… into your goal, but instead have very concrete and very [verifiable]… prompts, so that… it's easy to detect when things are done." And **auto compaction** triggers server-side "in a way that the model got trained with so that the performance stays the same," rewriting the previous context window into a new one containing a compaction item. The closing takeaway ties the parts together: the standout Codex features — "tool search, apply patch, web sockets, or server side compaction" — are exposed in the responses API and "you can use those directly regardless of what harness you're using." (15:32-20:16)

## Extracted Concepts

- [Defer Tool Definitions Out of Context and Let the Model Search for Them](../concepts/defer-tool-definitions-out-of-context-and-let-the-model-search-for-them.md) - A per-tool deferral flag in the inference API keeps definitions out of the window entirely until the model's own tool-search call pulls one in.
- [Cap the Skills List as a Share of the Context Window](../concepts/cap-the-skills-list-as-a-share-of-the-context-window.md) - A 2%-of-context budget for the available-skills list that degrades by trimming descriptions rather than dropping entries.
- [Fast Inference Moves the Agent Bottleneck to the Network](../concepts/fast-inference-moves-the-agent-bottleneck-to-the-network.md) - At 1,000 tokens/second the per-turn HTTP round trip and full-history resend dominate, so the fix is a persistent connection with server-held state.
- [Escalate Risky Actions to a Read-Only Review Subagent](../concepts/escalate-risky-actions-to-a-read-only-review-subagent.md) - Approval fatigue pushes users to full access, so route the escalation to a capability-stripped judge instead of to a human or to nobody.
- [Judge an Action by How Explicitly the User Authorized It](../concepts/judge-an-action-by-how-explicitly-the-user-authorized-it.md) - The reusable rubric axis behind auto review: the same `rm -rf` reads differently depending on whether the user named the target.
- [Match Agent Tooling to the Model's Training Distribution](../concepts/match-agent-tooling-to-the-models-training-distribution.md) - apply patch, ripgrep, PowerShell, and server-side compaction as four instances of the same rule, plus the corollary about which of them are portable.
- [Sandbox Primitives Are Per Operating System](../concepts/sandbox-primitives-are-per-operating-system.md) - Seatbelt, Bubblewrap, and a Windows sandbox that had to be written from scratch, which qualifies the wiki's "never roll your own" guidance.
- [End a Long-Horizon Loop With a Model-Called Goal Tool](../concepts/end-a-long-horizon-loop-with-a-model-called-goal-tool.md) - A continuation prompt injected until the model declares completion, which makes goal phrasing a control-flow parameter rather than a style choice.
- [Model Async Agent Work as Spawn, Send, Wait, Shut Down](../concepts/model-async-agent-work-as-spawn-send-wait-shut-down.md) - One handle primitive covering both subagents and background terminals instead of two mechanisms.
- [Drive Computer Use Through a Persistent Scripting Session](../concepts/drive-computer-use-through-a-persistent-scripting-session.md) - Replacing a fixed action enum with a REPL that survives turns lets the agent amortize page understanding into a reusable script.

## Provenance and Caveats

- This is an OpenAI developer-relations talk about OpenAI's own harness, models, and API. No competing harness is compared against on any dimension, and no pricing appears anywhere.
- **Almost nothing in the talk is measured.** The WebSocket result — the talk's headline finding — is reported as "speeds up things quite significantly" and "a pretty drastic impact on the performance" with no latency numbers, no workload, and no baseline. The one concrete comparison shown is a payload-item count (nine items resent versus one), which is not a timing measurement.
- The only quantitative figures in the talk are 1,000 tokens/second for GPT 5.3 Codex Spark on Cerebras (a serving-rate claim with no workload or end-to-end task time attached) and the 2% skills-list cap, which is a configuration constant rather than a measured optimum. No evidence is offered that 2% is the right number, and no data is given on whether trimmed skill descriptions degrade skill selection.
- The live demo server crashed. The WebSocket comparison the audience saw was a pre-recorded hosted backup, and the speaker acknowledged the crash on stage.
- Auto review is described by the speaker himself as "a gross oversimplification," and the talk supplies no false-approval rate, no false-escalation rate, no adversarial evaluation (for example, whether a prompt-injected transcript can persuade the reviewer that an action was authorized), and no cost or latency figure for the extra subagent. The reviewer reads the transcript, which is also the surface an attacker would target.
- The reviewer's read-only, no-spawn envelope is stated as a property, not as an enforced-and-tested boundary; nothing describes what happens when the reviewer itself is wrong, or whether its verdict is logged or appealable.
- Deferred tools and tool search are presented as available and useful with no numbers on context saved, no accuracy comparison against loading tools eagerly, and no discussion of what happens when the model's search misses a tool it needed.
- Everything is version-bound by the speaker's own opening disclaimer, and several claims name specific versions: deferred loading "since GPT-5.4," apply-patch training "starting with GPT-5," server-side compaction "end of last year." Readers should treat the model-version boundaries as the talk's own snapshot rather than as durable facts.
- The Windows sandbox decision — arguably the most interesting engineering claim in the talk — is asserted without its reasoning, which is deferred to an external article the talk does not summarize.
- The high-agency failure examples (the file-share workaround, the escaping error that deletes too much) are illustrative anecdotes with no frequency attached, and no source is given for how often auto review changes the outcome on them.
- No Q&A, so nothing in the talk was challenged from the room.
