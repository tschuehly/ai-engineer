## Summary

A three-part workshop in which Towards AI surveys the 2026 compaction toolkit, then measures it against their own open-source AI tutor and reports that the survey's recommendations mostly lost. Across 11 presets run on real student questions and multi-turn sessions, doing nothing to the context beat every compaction technique — and beat their own shipped production defaults — on fact recall, cost, and latency simultaneously. Prompt caching is the mechanism: with 97% of tokens served from cache and cached tokens up to 50 times cheaper on some APIs, a compaction pass has to shrink the context by more than 50x before it pays for itself, because rewriting the context invalidates the cache. Two further measured results cut the other way: an agentic knowledge-base browsing tool they built returned identical recall while running 50% slower, and going local (a 32k window on a MacBook) makes "keep everything" impossible, at which point retrieval becomes the answer again — with dense retrieval collapsing to 0% recall on facts buried at 400k tokens where BM25 still found them every time. The rule they land on is to name the constraint you actually have before reaching for compaction.

## Notes

### The system under test

- Towards AI runs an academy with technical courses for AI engineers, and ships an AI tutor that answers student questions from the lesson content. The tutor is the baseline for every experiment, so results are measured on a real product with real users rather than on a benchmark. (01:23-02:26, 03:57-04:10)
- Five product requirements: answers grounded in their content rather than the model's own knowledge; scoped to the current course and lesson because there are multiple courses; able to hold long help sessions while a student debugs; able to handle code; and low enough latency not to be frustrating. (03:57-05:01)
- Everything is open source — the tutor repo (`github.com/towardsai/ai-tutor-app`) plus a Hugging Face space where the experiments and the live tutor can be inspected. (02:08-02:26)
- Architecture: a single ReAct agent built with LangChain's `create_agent` and an in-memory saver (no cross-session persistence), customized through LangChain *middleware* — the runtime hooks that summarize, clear tool outputs, and apply the user's source preference. A FastAPI app wraps it and a Next.js UI serves students. (21:56-23:38)
- They deliberately do not use subagents: "the tutor works really well with just one main [agent], so we don't need to add complexity for that." Delta summarization is named as the technique that matters *if* you do use subagents. (11:20-11:53)

### The two root problems, and where context actually goes

- Two root problems produce everything else: the context window is finite, and the model is stateless, so a returning student starts from zero unless you build something. These split into context management (within one session) and memory (across sessions); the workshop covers only the first, on the argument that "you cannot have multiple sessions if one session is [bad]." (05:13-06:19)
- What the tutor's window holds: system prompt, tool definitions, chat history, old tool outputs (retrieved course chunks and tool call/result pairs), and the user question — which is "typically the smallest part" but can be large when a student pastes code or error logs. (06:23-07:05)
- The scaling bottleneck is old tool outputs: retrieved chunks and accumulated tool call/result pairs across turns, not the user's own text. (07:05-07:44)
- Three costs of an unmanaged window, stated separately: quality degrades through context rot; every follow-up resends and re-pays for all previous tokens; and time-to-first-token rises, which is the user-visible failure. (07:44-08:36)

### The compaction toolkit as surveyed

- Non-LLM techniques come first and are cheap: truncate outlier tool outputs to head and tail with an explicit "truncated" marker *so the model can re-call the tool if it later needs the middle*; use a sliding window or trim to the last N turns; and hard-clear the outputs of specific tools that never need to persist. (09:13-10:16)
- LLM-based techniques spend tokens to save tokens, and can run on small or local models. The two with the most impact in their experiments were selective retention (the model decides what to keep and discard as the discussion moves) and continuous summarization, with the Claude Code pattern — summarize everything at the limit and reset onto the summary — as the endpoint. (10:16-11:20)
- Offloading: memory files, skills, and RAG. As a side note they also compared GraphRAG against plain RAG and found it "way costlier to set up and just tie on the results" on their real-user evaluations, so they do not use it — with the caveat that a large dataset of interconnected topics might justify it. (11:55-12:58)
- The file-offload design is Karpathy's LLM-wiki idea: chunks cross-linked with pointers, chunks linked back to the raw files they came from, and one index (~450 tokens) that the agent actually sees. The agent scans the index, opens a chunk, and escalates to the raw file only if the chunk is not enough — "the best way to pull context according to the task complexity." (13:01-14:52)
- A client-work aside on skills: everyone is converging on *more and smaller* skills that reference each other, loaded one at a time, so that a subagent can be spawned with one dedicated skill context. Progressive disclosure — "load what you need right now." (14:54-15:30)

### Prompt caching, and why the survey's advice backfires

- Providers cache the prefill for already-sent tokens; re-used tokens "can go up to 50 times cheaper with some API like DeepSeek," and typically save around 90% of cost. Cached tokens are also already computed, so time-to-first-token drops. (15:55-16:45, 17:37-18:10)
- The break-even argument: any compaction, summarization, or transformation produces a *new* context the provider cannot match against the cache, so those tokens are charged at full price. "You need to compress by more than 50 times the context" for compaction to be worthwhile. (16:45-17:37)
- Hence: "summarization is potentially a trap. You may not want to use it at all, or you may want to just use it very specifically — which is what the most serious harnesses do nowadays." Claude Code and Codex both use context caching alongside a different compaction method. (18:10-18:52)
- The surviving guidance list: clear the session when the user changes topic; use progressive disclosure when scoping files; clear old tool outputs that are no longer useful; compact only in some cases; optimize for cache hits; and use a model router for cost. (18:55-19:52)
- The operational item they call out as the thing most people skip: log everything, per turn. Cache-hit rate, user frustration signals, abnormally long outputs, and any weird behavior a small model could detect. Their tutor logs input tokens, output tokens, how many were cached, cost, time to first token, tool-call count, and whether summarization fired. (19:52-20:31, 35:19-35:50)
- Their working definition: context engineering is deciding what the model sees every time you call it — for the tutor, what to keep in the window to optimize caching, what to drop or compact, and when. (20:31-21:00)

### Retrieval and the browse tool

- Corpus: their own lessons from two years of courses plus public documentation (LangChain, LlamaIndex, OpenAI, Codex, Claude Code) — over 8 million tokens, far past any window. (24:43-25:30)
- Tool 1, `retrieve_tutor_context`: user-selected source filter, then hybrid search with a Cohere embedding model plus a BM25 keyword index to top 30, merge the two result sets, rerank to top 5, with a hard 100,000-token cap that drops trailing chunks. The numbers "are not random" — they came from a separate retrieval sweep optimized on recall (did it retrieve the correct page). (25:30-27:05)
- Tool 2, knowledge-base browsing: three folders built offline — `raw` (all markdown lessons and docs), `generated` (an automatic title index), and `wiki` (topic and framework files that Claude Code wrote by reading the raw folder, e.g. a fine-tuning topic that points at every related raw file). Regenerated when a course is added. (28:00-29:20, 30:33-30:57)
- The browse sandbox is the reusable part: read-only bash commands only (nothing that can modify the filesystem), sandboxed to the knowledge-base folder, an 8-second per-command timeout that returns an error so the agent can try something else, tool output capped at 40,000 characters with the agent expected to issue a follow-up command for the rest, and a 20-command-per-turn ceiling they have never seen hit. (29:20-30:33)
- With the current system prompt the agent uses the browse tool on ~90% of turns; they did not tune that. (30:57-31:14)
- The measured result: turning the tool off gave the *same* recall, and having it on was 50% slower because it produced more tool calls. "It was fun to add but we didn't see any benefit." (31:15-32:01)
- His explanation is that the test set is real student questions, which may not be hard enough to need multi-document browsing. (Caption artifact: the audio as transcribed reads "those questions were complex enough … to actually benefit," where the argument requires "were *not* complex enough.") (31:58-32:18)

### The experiment

- The pre-experiment production defaults, described as "unproven": clear tool outputs after 5,000 tokens but keep the last 5; summarize after 30,000 tokens but keep the last 20 messages; plus the source-preference filter. Chosen because "it looked fast, it looked good — we didn't actually measure anything." (32:19-33:30)
- Vocabulary: a **preset** is one tutor configuration; a **task** is a dataset shape (single-turn or session); a **run** is one preset on one task; a **bundle** is the resulting JSON of metrics written to disk. (36:23-37:20)
- Single-turn dataset: not synthetic. Codex scraped real question/answer pairs from the site where students ask staff, then they cleaned it to 60 pairs, dropping questions about superseded library versions and duplicates. Measured on retrieval correctness (a code check: was the right lesson retrieved) and answer correctness (an LLM judge). (37:24-38:53)
- Session dataset: a planted fact at turn one ("I want to learn about RAG evaluation"), filler messages to grow the transcript, then a probe ("what topic should I learn about today") whose correct answer requires recalling the planted fact. (38:53-40:57)
- A **gate** check verifies the technique under test actually fired — e.g. did summarization happen at all — so a run is only saved if the configuration really engaged. (40:57-41:15, 41:38-42:05)
- Harness: a `run_battery` entry point, grading by code check or LLM judge, `check_triggers` for the gates, and a generated report with latency, time to first token, and every other metric. Runs and grading are separable: run once, grade afterwards. (41:18-42:25)
- 11 presets with model, prompt, tools, and dataset held fixed: full history (touch nothing), production (the shipped defaults), and six techniques including sliding window, prompt compression, and selective retention. (42:25-43:20)
- Cost: "I didn't expect this to get over $500, but it did" — later stated as almost $600 — which is itself why the follow-up experiments moved to cheaper models. (43:19-43:29, 47:10-47:35)
- For LLM-as-judge grading they recommend using a Claude Code or Codex *subscription* rather than the APIs, because it is cheaper. (38:53-39:10)

### Results

- Full history won on fact recall over multiple turns, and the shipped production defaults scored *worse than doing nothing*. They ran one trial and two trials; the numbers are not statistically strong, so the signal they trust is the ordering of the techniques. (43:40-44:42)
- Production cost was ~50 cents for a single turn and ~24 cents per turn multi-turn. In single-turn tasks nearly every technique scored high on recall, because a single turn never accumulates enough tokens to fire the thresholds — the presets are indistinguishable there. Multi-turn quality degraded to 38%. (44:49-45:27)
- Against full history, doing nothing was cheaper, faster, *and* had better recall — winning on all three fronts at once. (45:27-45:57)
- The mechanism for the latency and cost result: if you consistently remove tool outputs, the agent has to re-retrieve information it already had, so you cause more tool calls, more tokens, and worse recall. (45:57-46:41)
- Caveat stated by the presenter: this was Gemini 3.5 Flash on an 11-13 turn dataset, which "is not huge." (46:41-46:58)

### Extended experiments: cheaper model, longer conversations, scale

- Moving to DeepSeek V4 Flash produced a drastic cost drop, attributed mainly to the cache discount — "the cache discount on DeepSeek was 50x as compared to Gemini." Keeping everything still won on that model, so the finding is not a Gemini artifact. (49:12-50:30, 53:07-53:20)
- Memory probe on real student chats (setup details, errors seen, what they had already tried): asking for specific details back, the model returned the exact detail 95% of the time when everything was kept, against 32% when the context had been summarized or compacted first — "when you summarize you remove all of the necessary details." (50:53-51:56)
- On DeepSeek, "the setup that was sending the most tokens is actually the cheapest to run," because 97% of the tokens were cached and cached tokens are charged separately. Tested on a 36-turn conversation of about 1.78 million tokens. (52:10-53:07)
- Long-context durability: distinctive facts were still recovered consistently at 800k tokens with no visible rot; ambiguous facts dropped to about half that performance. (53:16-54:33, 60:45-61:03)
- Scale arithmetic: at 100,000 to 1,000,000 turns per day, DeepSeek costs roughly $18,000 to $180,000 per month. Separately, for ~1,000 students, Gemini was about $40,000/month against ~$1,900/month for DeepSeek. (54:38-55:37, 61:17-61:34)

### Going local changes the answer

- Hardware limits were tested on a MacBook, where the maximum context window they could run was 32k. Their lessons alone exceed 32k, and once the conversation does not fit the window, caching stops helping — so the context must be made smaller by compressing or by retrieving only what is needed. (55:37-56:31)
- The parameter-count trap, stated directly: going 7B → 8B → 32B does not increase the context window. "You cannot repair that part; you have to make a choice there." (56:31-57:22)
- Local documents plus retrieval worked well: ~100% accuracy on retrieving from a pasted large document, with 25-65 seconds of processing. Overstuffing the window instead took ~340 seconds to produce a *single token*. (57:22-58:25)
- Dense (semantic) retrieval held ~80% recall from 50k to 200k tokens, but at 400k tokens it could not find facts buried in the middle and returned 0% recall, where BM25 "still got 100% every time." This is why the tutor runs hybrid search rather than semantic search alone. (58:31-59:30)
- Cloud versus local on chat: keeping everything scores 92-95% on the cloud setup and 33% locally, with the context window as the limiting factor. Local has no marginal token cost since you own the hardware, but has a throughput limit — and retrieval restores good accuracy on the local setup. (59:30-60:33)

### What they chose, and the rule

- "Do not compact by default. You have to name the constraint that you have and then look for a better alternative." (61:34-61:47)
- Final configuration: DeepSeek V4 Flash on the cloud (chosen because of their hardware limits and because it is cheapest at their current student volume), hybrid retrieval on top, and for memory, keep everything with a default compaction threshold at 30k tokens. (61:48-62:33)
