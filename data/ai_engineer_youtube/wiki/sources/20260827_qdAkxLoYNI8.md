# How to Generate Mergeable Code with a Context Engine — Peter Werry, Unblocked

Source: [How to Generate Mergeable Code with a Context Engine — Peter Werry, Unblocked](https://www.youtube.com/watch?v=qdAkxLoYNI8)
Uploaded: 2026-08-27
Transcript: `raw/20260827_qdAkxLoYNI8/qdAkxLoYNI8.en-orig.vtt`

## Summary

Peter Werry gives the eighteen-minute conference version of the Unblocked context-engine argument the wiki already holds in workshop form (`5ID22ACI7IM`, May 2026). The definition is unchanged — "a context engine delivers organizational context to both your human workers and now increasingly your agents" (00:22-00:29) — but this talk contributes three things the earlier one did not: a named failure mode for agentic search, a live with/without cost comparison on a real repository, and a debugging story in which the cause of a metric regression lived only in a Slack thread.

The framing is a role transfer. "For years you were the context layer" — trawling data sources and discussions and the codebase to build tribal knowledge, while the organization accumulated "battle scars" from incidents and architecture decisions (00:58-01:42). Agents inherit every one of those challenges plus one of their own: "agents are like new employees. They reset their knowledge every time you start a new task… you can think of an agent like an expert software engineer who's a new employee onboarding for the first time. Every time they have to rediscover your codebase, how your organization builds tests and how they deploy software with each and every task" (01:52-02:18). The distinction that matters for design is *expert* but *new*: the deficit is organizational, not capability, so a better model does not close it.

The talk's most transferable idea is a borrowed diagnosis. "Access to information doesn't equal understanding" (04:09-04:16): attaching a wiki or a `claude.md` "still doesn't tell the agent where the information is that it needs. It can search for things in the wiki, but then what happens is it'll suffer from something that radiologists call satisfaction of search" — the error in which a reader finds one indicator on an X-ray, stops looking, and misses the others that would have changed the diagnosis. "This is what happens with agents. They find something that they think is correct and then they stop" (04:16-05:12). The second half of the same failure is that "they don't distill understanding. They can look around, they can find information, but they don't understand how all the pieces fit together… without doing that leg work ahead of time" — specifically how dependencies interact and how architecture and future planning scope the work the agent does next (05:12-05:52).

The obvious escape is refused with two reasons, not one. Slamming the whole codebase and all architecture documents into the window fails "not just because you've got way more organizational context than can fit into a context window, even one that's a million tokens in size. But it causes the agent to get distracted. When you're working on a task, you want task-specific flow… it'll just waste tokens and time" (05:34-06:20). What the agent cannot see is drawn as an iceberg: the code is above the waterline and operable; intent, team conventions, past decisions, Slack discussions, and architecture rationale are below it (06:30-06:53).

The demo has three parts. First, a question about an internal component ("the source mark engine") returns an architecture explanation with a diagram that "doesn't exist. It just figures it out based on the way the code operates today," plus proposals for future architecture, and — the part Werry emphasizes — attached sources: "you show your work. This is a trust-building thing more than anything, but it allows people to see if the answer is maybe not entirely correct, then you can look into the knowledge base that you have and make corrections" (07:53-08:52). Second, the same optimization plan is generated twice in Claude Code, with and without the context engine. Without it, Claude "happily went and searched through the code and tried to figure out how the algorithm works" and "reached a conclusion that's great… but could do a little bit better"; with it, the plan "nails the nuances because it picks up on the PRs where we discussed future possibilities for improvement, some Slack conversations, and of course Notion and architecture documents," and the sources come back with the answer so "Claude knows exactly where to jump to next if it needs to elaborate on that context" (09:55-11:13). The usage panel shows sub-dollar cost and about a minute with the engine against about two minutes and more cost without (11:13-11:52).

The argument attached to that measurement is more careful than the measurement itself. "The reason that happens is because it has to do more work. It has to look around, has to discover things. And this compounds — not only does it have to do more work to discover things, it doesn't discover the right things. So when you get further down in your execution, it may be operating on the wrong plan or the wrong assumptions. And then you have to go back and loop over and over again. So the real value of a context engine is not the upfront cost on these short tasks. It's the compounding effect" (11:52-12:27). The talk therefore names the wrong metric and the right one, and then reports only the wrong one.

The third demo turns to review. Unblocked "looks at pull request data — and there are other data sources for this — and it generates a series of best practices that help align agents to your codebase," surfaced to a review agent as well as to coding agents (12:44-13:10). The surfaced comments are ranked by who said them: a senior engineer's reaction to a bot comment was "Oh, that's cool. That's something I would say" — "and that's because that actually was something he said… we use the sort of seniority or expertise as a signal to boost comments that are important" (13:10-13:40). The same engineer then noticed that "the number of code review issues that were being surfaced dropped precipitously," debugged it with Unblocked, and asked it to fix what he found. A cloud agent generated a PR that explained itself with the org record: "After this PR, we switched to Claude 4.8 and it dropped a ton in issues because the behavior is quite a bit different" — and the citation behind that sentence was a Slack conversation (13:40-15:08).

Two open-source pieces close the talk. A document query engine "runs over your GitHub repository, ingests your historical pull requests, and then synthesizes a schema based on the documents that it can sample," after which arbitrary queries can be issued through agent chat (15:10-16:04). An engineering social graph derives team structure from review relationships — "these lines show we review each other's code" — then clusters it, generates team labels, and maps coverage "so you can see where the holes are, where you might be lacking expert coverage. And that's exactly what we use within the context engine itself" (16:04-16:44). For evaluation without signup, a "context engine simulator" builds context per task and runs the task both with and without it "so that you can see what the differences might be" (16:44-17:26).

## Provenance and Limits

- This is a vendor demo of the speaker's own product, live on the vendor's own repository. Every favourable result is self-reported and self-selected.
- The with/without comparison is a single unreplicated pair of runs on one task. No token counts, no repeat trials, no description of what each run's context actually contained, and no check that the two plans were equivalently correct — the without-engine plan is judged "great… but could do a little bit better" by the speaker, not by a rubric.
- The speaker discounts his own timing number as he presents it: "Ignore the wall clock time because I've had this open for about an hour" (11:24-11:30). The "about a minute" versus "about 2 minutes" figures are read off the same panel he just told the audience not to trust for wall clock.
- The compounding claim — that the payoff is downstream re-planning avoided rather than first-task cost — is the talk's central argument and is asserted rather than measured. No multi-step task is run to completion in either condition.
- The customer quote that closes the talk, "50% fewer tokens, faster triage, better answers" (17:35-17:45), carries no methodology, baseline, or workload description.
- The cloud agent that produced the self-explaining PR is described as internal and experimental — "something that we have internally that we're experimenting with" (13:58-14:10).
- The maturity curve (02:25-03:37) is a borrowed slide, and the attribution as spoken ("this slide before by Vim") does not resolve to a name from the audio; the stage numbering is recounted here without endorsing it. Stage positions the speaker states: autocomplete at the far left (Copilot, GPT-3.5 era), then Cursor, then organizational wikis, then MCP and skills, with "most people… at the sort of stage four to five level," and software factories at eight.
- Seniority-weighted comment surfacing is demonstrated by one reaction from one engineer. Nothing measures whether boosted comments are more often correct or more often acted on.
- The model-swap regression is a single incident narrated after the fact. The magnitude of the drop, the previous model, and whether the drop was actually undesirable (fewer flagged issues could be better precision) are not established.
- Caption artifacts resolved: "Unblocks"/"unblock" → Unblocked (00:12 and throughout); "trolled all over" → trawled (01:09); "GBT35" → GPT-3.5 (02:37); "co-pilot" → Copilot; "claw code" → Claude Code (10:11); "Claude 48" → Claude 4.8 (14:31); "notion" → Notion (11:03). The demo component is transcribed as "source mark engine" and is spelled as heard.
- Unresolved: the speaker credits two different keynote speakers with similar-sounding names — "Tariq from Claude Code mentioned unknown unknowns" (06:20-06:27) and "the other Tariq from Sonar mentioned this in the keynote this morning" (12:14-12:20). Both are recorded as heard rather than merged. A sentence at 09:04-09:10 is cut off by a display mishap ("when it provides a high degree of…"), most plausibly confidence, and is not relied on here.

- [Distillation Is a Separate Step From Retrieval, and the Task Agent Will Not Do It](../concepts/distillation-is-a-separate-step-from-retrieval.md) - agents can find the pieces and still not know how they fit, because nobody did the legwork ahead of the task.
- [An Agent Is an Expert Who Onboards Again on Every Task](../concepts/an-agent-is-an-expert-who-onboards-again-on-every-task.md) - the deficit is organizational rather than capability-shaped, and the cost is paid per task instead of once per hire.
- [Measure a Context Layer on Compounding, Not on the First Task](../concepts/measure-a-context-layer-on-compounding-not-the-first-task.md) - the talk names the right metric (downstream re-planning avoided) and reports the wrong one (first-task cost).
- [Attach Sources as Both a Correction Surface and a Continuation Pointer](../concepts/attach-sources-as-a-correction-surface-and-a-continuation-pointer.md) - citations let a human fix the knowledge base and let the agent know where to dig next.
- [Weight Mined Review Guidance by the Author's Expertise](../concepts/weight-mined-review-guidance-by-the-authors-expertise.md) - PR history mined into best practices, ranked by who said it, using the same expert graph that maps review coverage.
