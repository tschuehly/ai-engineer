## Summary

Luis Romero-Sevilla (VP of AI, Orbis Operations) walks a retrieval-architecture decision for a hard corpus shape: a large collection of documents where every document is relevant to answer a set of global questions, the documents are deeply interconnected, and the whole collection becomes obsolete and is replaced with new information very fast. He shows why each standard approach breaks on this shape and arrives at Extended Cache Augmented Generation (ECAG). Simple RAG (vector DB + embedding model) inserts fast, so replacing an obsolete collection is cheap — but top-k similarity retrieval cannot select a subset when *all* documents are needed. GraphRAG (LLM reads every document, extracts entities and relationships, builds a knowledge graph, navigates it to synthesize a cross-collection answer) is excellent when the collection rarely changes, but recomputing the graph on every replacement is computationally expensive and slow. Cache Augmented Generation (CAG) instead loads all documents into a large-context model and caches the context by storing the model's KV matrix — but a limited context window means overfilling it degrades answer quality. ECAG fixes that by running many CAG caches in parallel: documents are sharded across "context buckets," each cache answers questions about its own content, and a smarter *supervisor* model interrogates the buckets, progressively builds understanding, and asks buckets follow-up questions before synthesizing an answer. Because caches load in parallel, the knowledge-building process is significantly faster than GraphRAG while more accurate than simple RAG. A key implementation detail: distributing documents by domain tempts, but with dense inter-document relationships the supervisor ignores domains that look irrelevant at first glance, so documents are distributed in no particular order, balancing only the count. KV cache cost is real; it is reduced by optimizing how long each cache lives. There is no one-size-fits-all — each retrieval strategy trades compute, cost, and speed.

## Notes

- Problem shape: a large document collection where every document is relevant to a set of global questions, documents are deeply interconnected, and the collection becomes obsolete and is fully replaced very fast. 00:24-00:44, 02:51-03:01
- Simple RAG (vector DB + embedding model): embed documents into learned vectors, store in a vector-optimized DB, embed the query, retrieve vectors within a similarity threshold, pass to the LLM. Insertion is relatively fast, so an obsolete collection can just be replaced with a new one. 00:46-01:36
- Simple RAG limitation on this shape: because all documents are relevant, you cannot take a top-k similarity subset, and you also cannot just pass the entire collection to the LLM. 01:36-01:54
- GraphRAG: an LLM reads all documents, extracts key entities and relationships, constructs a knowledge graph, then navigates it to synthesize a complete answer drawn across the entire collection; excellent when the collection isn't changed often. 01:55-02:51
- GraphRAG limitation on this shape: recomputing the knowledge graph every time the data is replaced is computationally very expensive and takes a relatively long time. 02:51-03:08
- CAG (Cache Augmented Generation): each document has to pass through an LLM for entity/relationship structure anyway, so instead throw all documents into a large-context-window model and cache the context by storing the model's KV matrix. 03:08-03:38 (transcript ASR says "KB matrix"; this is the attention KV cache)
- CAG limitation: the context window is limited, and filling it too much degrades answer quality. 03:38-03:46
- ECAG solution: run multiple CAGs in parallel, distributing documents across different context buckets so each cache can answer questions about its content; a smarter supervisor model asks the right questions to the right buckets and synthesizes an answer. 03:46-04:11
- Document distribution: organizing by domains and handing the supervisor categories is tempting, but with very dense relationships between documents the supervisor tends to ignore domains that at first glance seem irrelevant, so documents are distributed in no particular order and only balanced so the least amount of documents are needed. 04:11-04:40
- Supervisor loop: it explores buckets, progressively builds internal understanding, and when it finds something interesting can ask a specific bucket follow-up questions; because caches load in parallel, knowledge building is significantly faster than GraphRAG while providing more accurate answers than simple RAG. 04:40-05:06
- Cost: KV cache can be pretty expensive, but cost is reduced by optimizing how long each cache lives. 05:06-05:17
- No one-solution-fits-all: many retrieval strategies exist, each with compute/cost/speed trade-offs, so the type must fit the specific problem. 05:17-05:34
