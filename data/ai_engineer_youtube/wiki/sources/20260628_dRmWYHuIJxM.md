# We Cut 94% of AI Coding Tokens With a Local Code Index

Source: [We Cut 94% of AI Coding Tokens With a Local Code Index - Rajkumar Sakthivel, Tesco](https://www.youtube.com/watch?v=dRmWYHuIJxM)
Uploaded: 2026-06-28
Transcript: `raw/20260628_dRmWYHuIJxM/dRmWYHuIJxM.en-orig.vtt`

## Summary

Rajkumar Sakthivel (LLM-infrastructure engineer at Tesco) recounts how his and a collaborator's AI-coding bill jumped from ~£15 to ~£200 in a month with no change in usage, and how the diagnosis reframed the whole problem: the money was not in "AI thinking" (output) but in oversized context (input). A typical query on their project sent ~45,000 tokens of context when only ~5,000 mattered, so they paid for ~40,000 useless tokens every query ("like ordering a pizza and paying for extra nine pizzas you don't eat"). Three fixes were tried before finding the real lever — shorter prompts ("only show relevant code") do nothing because the 45K tokens are already charged before the model reads the instruction; model settings (max tokens, temperature) change the output, not the input; and output compression works but is capped because output is only ~10% of cost. The "most important slide": ~90% of AI-coding cost is input and ~10% is output, so cutting output 75% saves only ~8% of the total while cutting input 94% saves ~61% — "fix the input." Their fix is a local retrieval layer (open-sourced as Code Context Engine / CCE) that sits between the codebase and the coding agent and returns only the small relevant code pieces instead of whole files, via a five-step pipeline: AST-aware chunking (functions/classes/methods, not random chunks), parallel hybrid search (semantic-by-meaning + keyword-by-exact-name), result compression (function name + description, 50 lines → 5), a call-graph relationship layer, and a relevance gate that scores every result and drops low-scoring ones. The hardest part was relevance gating — knowing when retrieval was wrong — where an LLM self-judge was too slow (+2-3s) and a fixed score threshold too crude; a simple weighted formula (50% semantic + 30% keyword + 20% recency) with an adaptive limit ran in 0.4 ms with no extra AI calls and "beats the complex model most of the time." Everything runs locally (nothing leaves the machine), one shared index serves multiple tools (Claude Code, Cursor, Copilot) plus a memory layer so knowledge persists across tools/sessions. Benchmarks and caveats are given honestly: on FastAPI (53 files, 20 questions) tokens fell 83K→4.9K/question (94%, or 523/question with compression) at ~90% right-code accuracy, but 94% is the worst case against a full-file baseline (real tools are already smarter, so real savings are lower), and on a 396-file mixed codebase recall dropped near zero — the approach works when files each do one thing and struggles when files do many.

## Notes

- Cost diagnosis: the bill went from "fine" to "huge" with "same project, same tools, just more of it"; most of the money "was not the AI thinking… it was sending too much context" (00:15-00:42). A typical query sent 45,000 tokens of context when only ~5,000 mattered, so ~40,000 tokens were paid for every query (01:22-01:35).
- Three failed/partial fixes (01:49-02:46): (1) prompt tweaks ("be short, only show relevant code") fail because "the model already got 45,000 tokens before it read the prompt — cost already happened"; (2) model settings (max token, temperature) "change the output, not the input… money is in the input"; (3) output compression works — telling the model to write short answers cut output 75% — but output is only ~10% of cost, so 75% of a small number is still small.
- The "most important slide" (02:46-03:20): "90% of your AI cost is input… only 10% is output," so cutting output 75% ≈ 8% total savings, while cutting input 94% ≈ 61% total savings — "same math, but different result. Fix the input." Restated at the end: models "may be 30% of the cost, but the other 70% is what you feed it" (10:16-10:29).
- Five-step local search layer (03:20-04:40): (1) break code into small meaningful pieces — functions, classes, methods, "not random chunks"; (2) run two searches in parallel, one by meaning and one by exact words, then combine — "this is where the big saving comes from"; (3) compress results, keeping only function name + description, cutting a 50-line function to five lines; (4) track the call graph (which function calls which) so finding one piece surfaces everything connected across files; (5) score every result and don't send low-scoring ones ("no bad context"). "Everything runs on your machine. Nothing goes to the cloud."
- Why two searches (04:40-05:31): meaning-based search finds related ideas but misses exact names (searching "authenticate user function" may surface a different auth function); word-based search nails exact names but misses related ideas ("login flow" misses "sign in"). Alone each misses ~1 in 4 results; together ~1 in 10 — "they fix each other's weakness spots."
- Relevance gating is "the hard part Foss and I spent most of the time on" (05:31-06:33): bad results give a "confident wrong answer… worse than no answer." An LLM judging its own results was "too slow" (+2-3 s each); a fixed score limit was "too simple" (short queries score low even when the match is perfect). What worked: a simple formula — 50% meaning score, 30% keyword score, 20% recency — with a limit that adjusts based on the current results, running in 0.4 ms with no extra AI calls. "Simple formula beats the complex model most of the time."
- Benchmarks (06:33-07:22): tested on FastAPI (open-source, 53 files, 20 real developer questions). Without the tool ~83K tokens/question; with it ~4.9K/question = 94% less; with extra compression on top, 523 tokens/question; accuracy still finds the right code ~90% of the time. The test is public and runnable.
- Honest caveats (07:22-08:35): the 94% is the worst case (reading full files every time); real tools like Claude Code are "already smarter than that," so real savings are lower — full-file baseline is used only because it can be measured the same way every time. Big mixed codebases are hard: on a 396-file project recall "dropped almost zero" — it works well if files each do one thing and struggles if files do many things. They use a small fast embedding model (re-index under a second), choosing "speed over perfection."
- One shared index + memory (08:35-09:29): each tool (Claude Code for hard problems, Cursor for quick edits, Copilot for completions) "starts fresh every time" and shares nothing, forcing you to re-explain the codebase; CCE builds one shared index all tools connect to, plus a memory layer so a lesson one tool learns persists for the next session/tool — "explain the code base once."
- Real savings report (09:29-10:05): across 247 queries, 12.4 million tokens saved, "nearly [$]186 not spent"; 84% of savings came from the search layer and the rest from compression. The tool tracks every query, compares would-have-been-sent vs sent, and multiplies by model price — "not an estimate."
- Framing (10:05-10:40): "the answer was not a better model. The answer was sending less… fix the input, the model choice matters less than you think." The tool (`CCE`, "Code Context Engine") is free and open source.
