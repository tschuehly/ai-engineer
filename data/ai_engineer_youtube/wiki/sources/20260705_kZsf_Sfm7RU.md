## Summary

Raphael Kalandadze (co-founder/CTO of Wandero AI, an agent-native operating system for travel and hospitality; also co-founder of Tbilisi AI Lab) argues that shipping an agent is now the *easy* part — you can build a whole product in days and spend a lot of tokens — and the real work is the "missing layer" of operating it after launch, a discipline "only a few people are talking about." Operating an agent product is unlike operating classical software: coverage is endless (like Claude Code or Codex, an agent can do a giant range of things you cannot enumerate or pre-test), LLMs are non-deterministic (the same input takes a different path), and the failure mode is *silent* — "nothing crashes and no log lights up; the failure is in the conversation, not the stack trace." An agent can struggle mid-task, get lucky, find a workaround, and finish looking green while having actually failed the customer (built the itinerary but used the wrong service and mispriced it — "technically successful but still failing the task"), and reliable agents "shouldn't depend on luck." Normal safety nets (unit tests, regex, rule-based checks, simulated-customer scripts) cover only "one slice"; "green CI means nothing for a non-deterministic agent," and production is where you learn what to test in the first place. So Wandero put *agents on the operations* — a "meta harness" where the team that keeps the product healthy is itself made of agents: a **log-monitoring agent** (fastest loop, runs every 15 min–1 hr over a rolling window of logs/trajectories with code-base access, diagnoses stuck users / root cause vs symptom, and drafts a PR or Slack alert), a separate fresh-context **review agent** that criticizes and scores each PR against one question — root cause or just the symptom? — and can request changes or close it, a **session analyzer** that scores *every* conversation (not a sample) into a system-health dashboard with connect-the-dots AI insights, and a **computer-use agent** that logs in and simulates the customer to catch UI-level failures logs can't see. Humans stay at merge/approval boundaries (the PR + review agents produce ~10× the three-person team's daily PRs). The durable rule: close the loop first, give each operating agent all the context a human would need (trajectories, metrics, DB, UI), and remember "it's not the model alone" — you must build the harness around it that watches, understands, and improves itself.

## Notes

- Framing: "shipping is the moment when the real work begins," and only a few people talk about it — Kalandadze calls it "the missing layer." You need to close the loop as soon as possible; the loop is "at least as important as the product itself, sometimes even more." (00:31-01:26)
- Why agent ops is a *new* problem: an agent is not normal software with a few features/buttons and a predefined, pre-testable flow — coverage is endless (like Claude Code/Codex), and "you cannot write all the conversations in advance." LLMs are non-deterministic: the same input can take a different path, and slight input changes cause a different trajectory. (01:50-03:00)
- The scariest failure mode is silent: a long-running agent struggles mid-task but "was lucky," recovers with workarounds/other tool calls, and gives "no red alerts, no problems on a dashboard" — yet that hidden problem "lives in your code base" and is an early warning; reliable agents "shouldn't depend on the luck." Cites an Anthropic blog point that "sometimes the agent loves to make [mark] features as complete without checking they actually worked." (03:44-04:36)
- Huge tool surface: long-running tasks need hundreds/thousands of tools, mid-run summarizations, sub-agents, a terminal, third-party services — "you don't know what you're looking for." (04:38-05:07)
- Finished ≠ helpful: their agent built a trip itinerary and the answer "looks good / successful," but it took the wrong service and mispriced it, so the user is unhappy — "technically successful but still failing the task." Unit tests don't save you; "production is the place where you learn what you need to test in the first place." (05:07-05:48)
- Logs are the source of truth and machines explore them far better/faster than humans, but handing logs to an agent "is not as easy as you imagine" — it needs reasoning to tell a real bug from noise and a symptom from a root cause. "The operating agent itself is an agent problem." (05:48-06:50)
- End-to-end fast loop: traces/trajectories + code-base access → the agent diagnoses and opens a PR; a *separate* agent with fresh context (agents are "pretty eager to send the PR" and biased toward their own fix) checks the PR from a different angle, runs focused tests, and requests changes or closes it — "not biased of the problem itself." Then human-in-the-loop (sometimes not). (06:50-07:42)
- People underappreciate this obvious pattern: you must spend time to calibrate it and make it reliable enough to "trust the loop." It is "the fastest loop we ever had" — detect a problem and have a PR ready in ~half an hour. (07:59-08:38)
- Log-monitoring agent: runs every hour (or ~15 min) over a one-hour window of logs/trajectories with code-base access, checks whether the user got stuck, and sends a PR or a Slack alert for critical problems. (09:07-09:47)
- The PR includes a short description, metadata, mermaid/ASCII diagrams, and sometimes HTML artifacts to give an at-a-glance view; a static-analysis pass gives quick feedback flagging critical problems vs heads-up warnings. (09:47-10:31)
- Review agent is "pretty critical": it criticizes and scores the problem from a different angle, then sends the PR to the human. In their case the PR agent + review agent "send 10 times more PRs than the three of us every day," so you need a clean system so the human isn't the bottleneck. On the human-in-the-loop debate: "close the loop first" — make yourself the bottleneck, then you can remove yourself easily. (10:31-11:52)
- Review-agent feedback looks like requested changes with a summary, diagrams, risks, and edge cases; after a few code-in-the-loop iterations the key is ready and the human jumps in. (11:52-12:22)
- Session analyzer (the zoom-out / high-level loop): the fast loop only sees a one-hour window with no high-level understanding, so a second system scores *every* conversation (running many state agents and spending a lot of tokens) to detect patterns, connect the dots, surface logical problems, count tool calls / sub-agents / summaries, and produce AI insights/entities and a system health score. Visibility "was impossible before the agent." (12:22-13:12)
- Health dashboard (built in-house on purpose — "I know what I'm looking for"): sessions analyzed, cost, average score, success rate, trends, AI insights (with per-insight description, why it matters, root cause, sessions affected, recommended fix), score distribution, sentiment analysis, tool-call analytics, rejection reasons, and per-session ranked detail. Its goal is not to fix a specific bug but high-level understanding; run it once or twice a week. (13:12-16:12)
- Computer-use agent (user perspective): logs and code work from the *system's* angle, but you also need the user's angle, so a computer-use agent opens a browser, logs in, and simulates the customer to catch UI problems. Codex driving a generic browser is slow; they built a product-specific skill that knows their DOM/website so it can open the site, log in, open sessions, send messages, and inspect artifacts much faster — but it "spends a lot of tokens." (16:12-17:43)
- Meta harness principle: give every operating agent the full context a human would need — trajectories, metrics, database, UI — e.g. the computer-use agent, on detecting a problem, should analyze trajectories and check the database to understand what happened. "It's not the model alone; you need to build the agent/system/harness around it, which watches itself, understands, improves." (17:43-19:00)
- Close: "shipping is the easiest part today"; to build a production agent you must close the loop first. Everyone can have the same model/agent/harness — the differentiator is the internal operations system that detects problems, gives you a sense of what's happening, and makes the product better. (19:00-19:31)
