# What if the harness mattered more than the model?

Source: [What if the harness mattered more than the model? - Aditya Bhargava, Etsy](https://www.youtube.com/watch?v=2e9ANoOEn28)
Uploaded: 2026-07-07
Transcript: `raw/20260707_2e9ANoOEn28/2e9ANoOEn28.en-orig.vtt`

## Summary

Aditya Bhargava (staff engineer and IC initiative lead for Agentic Commerce at Etsy; author of *Grokking Algorithms*, ducktyped.org) argues against the industry wisdom that "the models are so good you can keep the harness simple — just give the model a few tools and a loop." His counter-thesis: that direction makes us reliant on fancy proprietary models that can't run locally, so we should instead invest in harness expertise good enough to get cutting-edge performance out of local open-source models. Evidence: a "Harness Bench" benchmark (106 tasks, same model, same evaluation, only the harness varying) shows scores ranging 52.4%→76.2% — a >20-point swing from the harness alone — and the harness matters *more* for weaker models. His second controversial take is that a good harness needs language-level support, so he spent ~6 months building **Agency** (agencylang.com), a TypeScript-inspired (with Python syntax) language for building agents. The bulk of the talk walks one coding agent (fix a bug in `median.py`) up a harness capability ladder across seven examples — bare model → tools → safety via interrupts/handlers → autonomy via partial function application → a ReAct feedback loop → sub-agents → self-optimization (a built-in GEPA optimizer) — showing the harness improve the same model's performance at each rung.

## Notes

- Central thesis and controversial framing: "models are so good, keep the harness simple" is "moving in the wrong direction because that is making us reliant on fancy proprietary models that can't be run locally"; instead focus on "a harness that is so good that we can get the performance of a cutting-edge model through a local open-source model." (00:48-01:42)
- Harness Bench: a benchmark *for harnesses* ("something we haven't seen a lot of yet"), 106 tasks, same model and evaluation, only the harness changing; scores 52.4%→76.2% (">20-point difference, and only the harness changed"); "for weaker models, the harness matters more." (01:47-02:47)
- Democratization argument: if the model matters more, "we're dependent on a handful of companies who are able to build and train these models"; if a good harness can compensate and make a weaker model perform better, "you can build your own harnesses… and we don't have to depend on paid models." (02:47-03:12)
- Language-level take: none of the existing tools/frameworks did what he wanted; "building a good harness actually requires language-level support," so he built **Agency** (agencylang.com), TypeScript-inspired with some Python syntax. Alan Kay quote as design north star: "Simple things should be simple, complex things should be possible." (03:31-05:44)
- Terminology: an *agent* = harness + model; e.g. Claude Code is an agent, Opus is the model, "everything else is the harness." Agency is for building agents but the thing it provides is the harness. (04:16-04:44)
- The demo task: fix a bug in a `median.py` function (even-length lists must average the middle two elements); there's a failing test. The same model and task run through all seven examples; only the harness improves. (06:01-08:26)
- Example 1 — bare model: just passes the prompt to the LLM; "it can't read or write to this file," so it asks to see the code. Very little harness → can't do anything. (08:33-09:37)
- Tools in Agency: every function is automatically usable as a tool — Agency generates a JSON schema from the function signature and the docstring becomes the tool description; "nothing else to do." Built-in `read`/`write` functions can be passed straight to the LLM. Built-in log viewer shows tool calls, parameters, and responses. (09:40-11:23)
- Safety via interrupts + handlers: giving raw `read`/`write` on the file system is unsafe, so by default Agency won't allow it — the tool raises an *interrupt* ("Are you sure you want to read this file?") and crashes if unhandled. A `handle` block with a handler function catches the interrupt, prints its info, asks the user for approval via the built-in `input`, and approves the tool call. All standard-library functions that mutate, do something destructive, or read sensitive data "throw an interrupt first." Safe but slow (manual approval every action). (11:43-15:17)
- Autonomy via partial function application (PFA): borrowed from functional programming — call `partial` on `read`, locking its `directory` argument to `demo`. The LLM can't change it and "won't even know that argument exists" — it sees only the `file_name` parameter. This constrains capability (agent can only read/write within that directory) so no human input is needed but it's still safe. (15:44-17:08)
- Feedback loop via ReAct (Reason + Act): reason → act → observe consequences → decide next, looped until tests pass. Concretely: read the two files, run the tests, observe failure, read the error, reason again, write the fix, re-run, confirm success. "A really key pattern to making the agent better" — this is the first rung where the agent actually fixes the code and confirms the fix. (18:04-20:48)
- Sub-agents: everything before made the *same task* better; sub-agents make the agent do *more things*. A sub-agent is "just another function" you call like a tool (no special framework concept), each with its own LLM call and its own set of tools. The main agent is given two sub-agents (a coding agent + a Wikipedia-search agent from the standard library) as its tools instead of raw read/write; they run in parallel. Benefit: add capabilities without bloating context — agents fail when context is bloated *and* when they have too many unrelated tools and can't pick the right one; grouping tools under sub-agents makes tool selection cleaner ("pick the sub-agent you want to call"). (21:29-25:21)
- Self-optimization via a built-in GEPA optimizer ("Japa" is ASR): mark variables with an `optimize` modifier, run the optimizer with a goal ("Fix the bug in median.py using TDD"). It establishes a baseline objective (0.2) and improves on it — "we're no longer doing trial and error… now we have a way to systematically measure and improve performance" instead of guess-and-check. (25:22-28:00)
- Language-level payoff recap: simple tool syntax (every function is a tool), tools for safety (interrupts, handlers, PFA), and true pause/resume execution — raising an interrupt pauses execution, returns control to the user, and can be resumed later at that exact point even inside a for loop, a tool call, or a sub-agent; execution is serializable ("come back a week later" with no code changes). "Very few languages allow you to do something like this." Plus built-in optimizers. (29:29-31:10)
- Main takeaways: an agent is a model + a harness; a better harness = better performance, "especially for weaker models"; and to build a better harness — give it tools, make it safe, make it autonomous, make it reason, give it sub-agents, and have it self-optimize. Install via package manager + an API key. (31:29-31:52)

"Japa optimizer" ≈ **GEPA** (Genetic-Pareto prompt optimizer). "PM install" ≈ a package-manager install (e.g. `pip install`).
