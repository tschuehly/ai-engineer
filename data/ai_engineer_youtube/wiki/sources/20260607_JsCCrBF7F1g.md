## Summary

Dat Ngo, an AI architect at Arize AI, frames "making AI work" as three connected pillars — observability, evaluation, and experimentation/improvement — and insists the whole thing is engineering, not magic. Observability is OpenTelemetry-first: a one-line auto-instrumenter turns a framework or SDK into traces and spans, because code does not audit agents or harnesses — the telemetry does. Beyond single traces, teams need sessions (conversational state) and distributional views across all runs of an agent (paths, branches, loops) to answer questions like "what percentage of traffic takes this branch, and which component there added latency?" Evaluation is presented along two orthogonal axes: five flavors of signal (LLM-as-judge, human feedback, golden datasets, deterministic checks, business metrics) and four scopes (single span, multispan, trajectory, session), with the caveat that you should run the minimal eval set that gives signal because evals cost. Experimentation means running changes (prompts, models, orchestration, configurations) against datasets — pulled from traces or uploaded directly — to avoid the trap where a "fix" silently introduces regressions. The forward-looking pitch is automation: expose all primitives via CLI + tools + skills so coding agents drive the loop, and ship an AI layer ("Alex") that, with full trace and hook access, scans for high latency and errors and authors evals on the fly — the stated goal is to automate the human out of the observability loop entirely. Products: Arize Phoenix (open source, single container, no Kubernetes) and Arize AX (enterprise, used by Uber, Booking, Reddit).

## Notes

- The three pillars: observability ("what's happening in the thing I built"), evals ("how do I derive signal from my systems"), experimentation/improvement; "AI is software reimagined," same patterns, new flavor, "all just engineering." 02:06-02:18, 13:24-13:32.
- OTel-first: everything is OpenTelemetry; an auto-instrumenter adds one line of code to see what a framework/SDK does, creating traces and spans. "Code doesn't audit agents or harnesses — the telemetry does." A trace/span is "the audit record of what my agent did." 02:47-03:41, 03:10-03:36.
- Beyond traces/spans: sessions capture conversational state and back-and-forth runs (references the Anthropic managed-agents paper). 03:47-04:34.
- Distributional / aggregate views: don't treat the agent as a single non-deterministic call — look across all instantiations to see paths, branches, and loops, and answer "what % of traffic goes down one branch vs another?" and "which component in that branch caused latency?" 05:00-05:45.
- The trajectory failure example: "I did B before A, and B has a dependency on A" — telemetry catches the out-of-order tool calls the LLM chose; the fix is adding context to enforce ordering. 06:01-06:22.
- Five flavors of signal: (1) LLM-as-judge (seems simple, gets complex); (2) human feedback (end users; valuable to technical and non-technical roles); (3) golden datasets (labeled by a trusted domain expert; used to tune the judge so the LLM approximates the trusted labeler); (4) deterministic checks (logic/code — valid JSON? right schema? non-null fields? — cheap, no LLM/human cost); (5) business metrics (make money / save money / save time). 07:06-08:44.
- Two personas: technical users (AI engineers/developers who frame and automate) and subject-matter experts / PMs (less technical, know the domain, define the prompt engineering and the evals they care about). Platform lets non-technical users run out-of-the-box eval templates and technical users attach evals programmatically. 08:46-09:46.
- Eval scope/depth (orthogonal to flavor): single span (one input/output, e.g. one part of an LLM call — simplest); multispan (eval needs data across many components, e.g. how well agents pass data back and forth); trajectory (over all spans — "did we call things in the right trajectory to finish the business process?"); session (zoom out and evaluate the state machine — "was the user ever frustrated? did we answer all their questions?"). 10:08-11:42.
- Caveat: "just because you can eval something doesn't mean you always should" — find the minimal set of evals that tells you whether the app works, because evals cost. 11:52-12:11.
- Experimentation: not everyone starts with traces; if you have them, find the bad/missing signal and collect it into a dataset; if not, upload input-output pairs directly. Then run experiments = changes to prompts, models, orchestration, or configurations, in a UI or programmatically. 12:16-13:11.
- Automation trajectory: most people don't want to live in dashboards/buttons; software will compress. Expose all primitives via CLI + a set of tools and skills so coding agents (Claude Code, Codex) drive observability. An AI layer ("Alex"), with all trace data and hooks, can be asked "do you see any issues with my application?" and plans+runs tasks, surfacing high latency and errors detected. 13:24-15:23.
- "You shouldn't even have to choose your evals" — the AI has context of the traces, creates evals on the fly, and knows when something changed and a new eval is needed; ultimate company goal is to "automate you out of" the whole observability/eval/experiment/improvement flywheel. 14:33-15:12.
- Products: Arize Phoenix is open source, a single container, deployable locally with no Kubernetes layer (engineering-first); Arize AX is the enterprise product (Uber, Booking, Reddit) and hosts Alex. 15:33-15:57.
