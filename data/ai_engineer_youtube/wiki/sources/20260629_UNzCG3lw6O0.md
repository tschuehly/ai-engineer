# Building Great Agent Skills: The Missing Manual

## Summary

Matt Pocock (author of the popular `mattpocock/skills` repo) gives a pre-recorded talk offering a shared rubric — a "skill checklist" — for distinguishing good agent skills from bad ones and escaping "skill hell" (having lots of downloadable skills but no way to tell which are effective or how they compose). The checklist has four axes. **Trigger**: decide whether a skill is user-invoked or model-invoked, trading the agent's *context load* (each model-invoked skill adds a description to every request and introduces unpredictability that forces you to eval whether it fires) against the pilot's *cognitive load* (user-invoked skills are deterministic but the human must remember them). **Structure**: compose a skill from two units — steps (procedure) and reference (supporting material) — and keep `SKILL.md` as small as possible by hiding branch-specific reference material behind context pointers to external files. **Steering**: use "leading words" (dense-meaning phrases like *vertical slice* repeated in the skill that the agent echoes into its reasoning traces and thereby changes its behavior), and force more "leg work" per step by splitting a skill so the agent sees only the current step and cannot rush toward a visible future goal. **Pruning**: keep skills small via a single source of truth (DRY), removing "sediment" (stale accreted material in shared docs) and "no-ops" (instructions that don't actually change behavior, found via a deletion test). He has packaged the whole framework into a `writing great skills` skill in his repo.

## Notes

- Framing: developers keep finding "forms of hell" — tutorial hell, framework hell, now "skill hell," where freely downloadable skills exist but there's no shared rubric to tell a good skill from a bad one, so people can't get the results the skills promise; the same gap exists at organization level (turning operating procedures into agent-runnable skills). 00:36-02:11
- The checklist: (1) Trigger — how the skill is invoked; (2) Structure — internal layout; (3) Steering — how the skill tells the agent what to do; (4) Pruning — make the skill as small as possible. 02:12-03:15
- Trigger: any skill can always be user-invoked (the file sits on the filesystem; you point the agent at it, e.g. via a `/` command depending on the harness). A skill is *model-invoked* when its description is placed in the agent's context — the description acts as a "context pointer" the agent can choose to follow to read `SKILL.md`. 03:16-05:30
- `disable model invocation: true` keeps a skill's description out of the agent's context so it shows only to the user (his `grill me` skill); his `codebase design` skill is model-invocable. 05:00-06:00
- The trigger tradeoff: model-invoked seems more flexible, but each one adds a description costing tokens on *every* request plus "a different thing for the agent to think about" (100 skills = 100 descriptions in context) — the *context load*. Pure user-invoked skills avoid that but raise *cognitive load* on the pilot, who must understand the skills deeply. Comparison: superpowers is primarily model-invoked ("gives the agent superpowers"); Matt's own skills prefer user-invoked to stay in full control. 06:00-07:25
- Model-invoked skills also carry a "cost in unpredictability": even a perfectly-matched skill may just not be invoked, and that unpredictability is what forces people to *eval their skills* to confirm they fire at the right time — "a really nasty problem I prefer to avoid." Neither choice is easy; both have symmetric costs. 06:30-07:28
- Structure: think of a skill as two units — **steps** (the step-by-step procedure) and **reference** (supporting info). A skill can be all-reference or all-steps. Example `to PRD` has three steps (find relevant context; confirm test seams with the user as a human-in-the-loop checkpoint; write the PRD) plus two reference pieces ("what is a test seam" and a PRD Markdown template). 07:29-09:00
- Keep `SKILL.md` as small as possible (tip 3): smaller skills are easier to maintain/audit and every word shaved is a token shaved off every use. Technique: look at the skill's *branches* — reference material used on only one branch is a candidate to move out. `to PRD` has one branch (always needs both reference pieces) so they stay inline; `domain modeling` has 2-3 branches (update a `context.md` glossary, create ADRs, or neither), so its ADR template and context.md template move behind context pointers into separate Markdown files ("external references") that the agent pulls in only when needed. 09:00-11:53
- Steering — leading words: the core technique. Certain words pack a lot of meaning into a small space; put the leading word in the skill text and the agent repeats it back in its thinking tokens and output, which changes behavior. Example: instead of "don't code layer by layer, build a small slice first," use the leading word *vertical slice* (a known dev term), which triggers the agent's prior. You can verify it worked by watching the reasoning traces for the phrase ("we're going to do this as a thin vertical slice"). Make leading words consistent, more powerful, and hunt for more — "English is a pretty wide API," and agents are good at helping brainstorm leading-word candidates. 11:54-14:55
- Steering — leg work: sometimes the agent doesn't do *enough* of a step (e.g. explore the codebase, ask clarifying questions). Classic case: plan mode's two steps (ask clarifying questions → create a plan) — the agent sees the ultimate goal is the plan, so it rushes the questions and eagerly writes the plan. Fix: split into separate skills so the agent sees only one step at a time. Matt's `grill with docs` skill *is* the clarifying-questions phase as its own skill; only after it completes does `to PRD` run. Hiding the future step forces an extra chunk of leg work on the current one — "there's no technique like it," though not always necessary. 14:56-16:47
- Pruning: massive skills are usually a *symptom* of other failure modes. (a) DRY — every part of the skill (including reference material like the PRD template or "what is a test seam") should have a single source of truth, not repeated across steps/places. (b) Sediment — shared docs accrete material as many people add and nobody feels brave enough to delete; fix with structure (move added material into the correct branch, or kill it if irrelevant or stale). (c) No-ops — instructions that appear to do something but don't change the agent's behavior in context (e.g. a paragraph telling the agent to write a long commit message it would write anyway); find them with a "deletion test" — delete it and see if behavior changes. 16:48-19:05
- Final sweep restates the four axes; the framework is packaged as the `writing great skills` skill in `github.com/mattpocock/skills`, usable to improve your own skills or audit community-authored ones. Newsletter at aihero.dev; upcoming "AI coding crash course." 19:06-20:00
