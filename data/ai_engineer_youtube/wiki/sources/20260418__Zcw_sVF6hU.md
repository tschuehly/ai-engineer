## Summary

Armin Ronacher and Cristina Poncela Cubeiro argue that coding agents make code production cheap enough to overwhelm human review, increase codebase entropy, and hide the moments where engineering judgment is needed. They recommend making codebases more agent-legible with modular flow, simple cores, explicit interfaces, and lint-enforced constraints, while deliberately reintroducing friction for risky changes such as database migrations, permissions, dependencies, and system architecture.

## Notes

- The speakers frame the psychological failure mode as a shift from useful extra time to pressure: once AI tools become expected, teams feel pushed to ship faster and review more generated code than they can responsibly inspect. (03:35-05:08)
- Agent-generated pull requests can be large enough that the exact moment that needs careful thinking is also the moment reviewers are most likely to tap out or rubber-stamp. (05:32-07:10)
- Coding agents are optimized to make runnable progress, so they may add forgiving fallbacks, local recovery behavior, duplicate files, or hidden state that passes immediate checks while increasing later failure conditions. (07:13-09:08)
- Libraries are easier for agents than products because their problems, APIs, and constraints are more explicit; product code combines UI, API responses, permissions, feature flags, billing, and other context that may not fit into the agent's working context. (09:16-10:24)
- Agent-legible codebases use modular components, modularized flow steps, simple cores, no hidden magic, centralized query and UI primitives, no dynamic imports, unique function names, and TypeScript modes that keep one source of truth between source and compiler. (10:52-14:08)
- Mechanical review should route fixable issues back to agents, but database migrations, permission changes, new dependencies, and other under-documented or high-impact changes should wake up human judgment instead of being auto-fixed. (14:28-15:45)
- Agents are useful for reproducing customer issues and exploring product directions, but the speakers caution that system architecture and reliability work still need slower human-led review because technical debt can now accumulate in days or weeks. (16:01-17:24)
