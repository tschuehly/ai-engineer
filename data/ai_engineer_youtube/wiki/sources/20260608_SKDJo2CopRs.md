## Summary

A fireside-style Q&A by Sunil Pai and Matt Carey of Cloudflare's agents team, framed as a teaser for their dedicated afternoon talks (Code Mode and "MCP = Mega Context Problem"). Two durable ideas anchor it. First, Durable Objects are the compute unit they bet on for AI agents: "stateful serverless" where, for a given ID, a class spins up once and every later request and websocket lands in the same addressable, persistent, hibernating instance, with ~15ms edge latency (inside a 60fps/16ms animation frame). Building agents on this — via the Agents SDK, which is an execution environment more than a library and a first-class backend for Vercel's AI SDK — makes resumable streaming, multi-tab/multi-device sync, and background scheduling emergent properties rather than userland distributed-systems work; the same primitive powers TLDraw and motivates an "AI should be multiplayer" stance and a persistent coding-agent backend reachable from terminal, chat, phone, iOS, or web. Second, Dynamic Workers ("eval++") run a string of LLM-/user-generated code in a fresh isolate that starts with zero authority — no fetch, no APIs, no environment variables — and receives only explicitly granted capabilities, the inverse of wrapping a VM/container in security; they frame it as reclaiming 30 years of avoided `eval`. Supporting points: code mode collapses Cloudflare's 2,600 API endpoints into ~1,000 tokens; generative UI should render generated React/HTML in a sandbox instead of generating JSON to render ("Jason Bender"); `@cloudflare/shell` layers a virtual filesystem on Durable Object SQLite + R2; JS/Python are first-class with everything else WASM (they are experimenting with Zig for tiny bundles); and Cloudflare's low cost comes from ISP-adjacent hardware and bulk bandwidth rather than mega data centers.

## Notes

- Durable Objects framed as "stateful serverless": a naive serverless hit-counter (`let counter = 0; counter++`) fails because each invocation spins up, runs, and disappears with no state; instead, for a given ID a class spins up once and every future request and websocket connection lands in the same instance, so state lives in the compute unit rather than an external database. (02:20-03:24)
- The instance scales across the planet on Cloudflare's edge network, giving ~15ms latency in London — just under the 16ms of a 60fps animation frame — which is why the same tech powers real-time collaborative sync like TLDraw (open the same shared canvas on many phones and drawing syncs in near-perfect real time). (03:27-03:52)
- "It turns out that's the perfect compute unit for building AI agents": Durable Objects are addressable, can run long-running and background work even with no inbound requests, hibernate/sleep, have persistence, and connect out to everything else. (03:56-04:15)
- Cloudflare's Agents SDK builds on this (`import` from `agents`, extend a class, register scheduled work and callables) and ships full-stack: React hooks plus plain-JavaScript clients, client-callable methods, and background execution; scheduling is the favorite feature (e.g., "every Friday at 9pm, look through my entire git history, wiki, and Notion, compile it, and send it to my manager"). It spins up to "millions, trillions." (04:32-05:24)
- The SDK is a first-class backend for Vercel's AI SDK; the AI SDK is great, but making it production-ready (tool calls, synchronize, resumability, things across tabs) is a lot more work — "we have the world's best backend for the AI SDK." (05:33-05:55)
- Durable Objects are also a great way to host MCP servers because MCP originally needed a stateful client-server connection that is annoying to deploy to the cloud, and Durable Objects maintain that stateful connection easily; Cloudflare hosted some of the first MCP servers (PayPal, Sentry, Linear, Intercom). (06:03-06:35)
- Workers are described as a serverless function-as-a-service "like a lambda designed 10-20 years later." (06:57-07:08)
- Dynamic Workers are a new primitive: instead of deploying a worker to the cloud, you take a string of code (sent by a customer or user, or generated by an LLM) and run it in its own isolated worker — "from a string, you can run the code." (07:11-07:34)
- They are a sandbox but not a VM: no full filesystem, none of the VM heaviness, but an isolate you can spin up billions of on demand. (07:55-08:18)
- Uses: anywhere you want user-generated code, or where you previously would have built a DSL (a JSON file generated from a big form, then converted to code) — now just write code. (08:19-08:36)
- Inverted sandbox model: ordinary sandboxes start from a VM/container and add security around it; Dynamic Workers start the opposite way — the only thing runnable is JavaScript, with no access to fetch, no APIs, nothing, and from the outside you grant explicit capabilities (e.g., outgoing fetches only to `github.com`), recommended default being to block outgoing fetches and expose no environment variables to the code. (08:55-09:36)
- "For the last 30 years they've told you never to use `eval`... Cloudflare Workers don't even have `eval`. It's dangerous. But Dynamic Workers are like `eval++`" — an entire branch of the tech tree unexplored for 30 years, now offered as a fast, secure, cheap way to run generated code; it lets you reconsider how you build interfaces "in a world where all your users can write code." (10:31-11:18)
- Code mode teaser: using this, "we fixed MCP not once, maybe twice"; one talk shows using code mode in an MCP server to give access to all 2,600 Cloudflare API endpoints in just ~1,000 tokens. (09:44-10:22)
- Generative UI argument: people generate JSON that they then render ("Jason Bender") because some platforms lack a primitive to render untrusted code; instead, have users/customers/clients/cloud agents generate HTML or React and render that directly (like Claude Artifacts, which is HTML rendered in the browser). The hard part is rendering untrusted generated code on *your servers* — a safe sandbox makes that viable, so "you don't need JSON anymore, you could render React." (12:14-13:11)
- Resumable streaming for free: ask an LLM for a long story and hit refresh mid-stream — in a serverless world you would need a database, replication, and sticky sessions, but in the Durable Objects / Agents SDK world the client just reconnects to the instance, which replays the beginning of the stream and continues sending bytes. (13:34-14:05)
- Multi-tab and multi-browser/device sync come out of the box (phone and laptop on the same session at once); the original killer use case for Durable Objects was real-time collaborative sync. (14:05-14:19)
- "AI should be a multiplayer game" — most chat products can't share a link so two people work in the same conversation; with primitives like this you don't have to patch sync/streaming in userland and become a distributed-systems engineer — it becomes the platform's problem. (14:22-14:53)
- A persistent agent loop running in the Agents SDK can be the backend of a Cloud Code-style coding agent: a persistent server reachable from any client (terminal, chat, phone, iOS app, web app) where everything is synced, resumable, and stateful; they are shipping a Workers-native coding-agent harness imminently. (15:39-16:30)
- "Open cloud" framing for that harness: a thing with a heartbeat, a virtual filesystem, connections to services, and extensions — extensions meaning generate code that runs in a safe sandboxed environment. (18:11-18:30)
- Storage: SQLite directly inside the Durable Object plus R2 for bigger files; `@cloudflare/shell` layers a full virtual filesystem on top of Durable Object SQLite and R2 and is usable today. (17:53-18:02, 20:50-21:04)
- Language support: JavaScript and Python are first-class (Dynamic Workers and Workers support Python); everything else is WASM. They are experimenting with Zig because its WASM bundles are tiny compared to Go and Rust; if you need native execution, spin up a container instead — and since the LLM is writing the code, the language matters less. (19:09-19:56)
- A "worker bundler" runs inside a Worker: it pulls dependencies from NPM, strips types/JSX/TypeScript, and uses the Cloudflare cache for dependencies instead of depending on NPM uptime. (20:15-20:34)
- M-, a new CMS launched the prior week, runs fully on Workers/Durable Objects and builds its plugin system entirely on Dynamic Workers — locking down where plugins run avoids WordPress-style plugin security incidents; M- can deploy on any platform, and Cloudflare is working on other-platform support for the Dynamic Workers piece. (21:31-22:06)
- Cost framing: Cloudflare is cheap because of architecture decisions made ~10 years ago — no massive data centers, hardware installed near ISPs, bandwidth bought in bulk from top-level ISPs, and peering agreements where cross-boundary bytes are cheap — so free accounts are how the business is constructed, not marketing spend ($5/month otherwise). (22:57-23:42)
