## Summary

Ara Khan (Cline) argues the truth about evals is "inconveniently in the middle" between two wrong camps: the objective-metrics camp that reads leaderboard numbers as gospel (and benchmark-maxes), and the taste/vibes camp that anthropomorphizes models and dismisses evals entirely. His practical framework has three levels — leverage other people's evals, use evals to improve your own agent, and build your own evals — and the talk covers the first two. For interpreting others' evals: don't believe a lab's launch number (they are approximations), stay current but let a new model "settle for a couple weeks" before switching rather than being the earliest adopter, and seek *new and precise* evals because standardized benchmarks go stale (OpenAI said SWE-bench Verified "no longer measures frontier coding capabilities"). For improving your own agent, Cline went from ignoring evals (the same initial stance as the Codex team) to paying opted-in users for real coding sessions and hand-building a from-scratch eval set; agent evals are far harder to grade than single-turn LLM evals because you grade an end state after the agent reads files, installs an environment, runs scripts, and runs tests. The core operational contribution is to **portfolio-allocate failures**: run a *second agent* over the failure traces (every LLM call the agent made) to categorize why each task failed and find the small levers that move the score, then sort fixes into three zones — obvious harness bugs, nuance/model-family-specific tuning, and the overfitting "danger zone." Every eval run is simultaneously testing three things — the model, the harness, and the problem set — and Cline's own Terminal Bench run went from 43% via container CPU/memory, raised timeouts, thinking-budget tuning, and Anthropic-specific prompt engineering that does *not* transfer to Codex or Gemini — not by switching to a better model. The closing rule: hill-climb a real benchmark *and* pass the vibe check; supporting a new model family unlocks the swath of users who love it.

## Notes

- Two wrong camps: objective-metrics (treats similar leaderboard numbers as model equivalence, "GPT 5.4 ≈ Gemini 3.1 Pro preview" — they're not; classic benchmark-maxing like a Meta launch that doesn't hold up to real-world evidence) and taste/vibes (anthropomorphizes, dismisses eval numbers as not to be taken seriously). Truth is in the middle: evals aren't the end-all-be-all but aren't useless. (01:33-03:11)
- Three levels of using evals: (1) leverage others' evals, (2) use evals to improve your own agent, (3) build your own evals for specific use cases; talk covers levels 1-2. (03:13-03:36)
- Interpretation heuristics: don't believe a lab's launch number (approximations, sometimes good/sometimes not; cites a Nikunj tweet that researchers routinely dismiss eval numbers); stay current but don't be the earliest adopter — let a model "settle for a couple weeks" and switch only if it stands the test of time ("I do this for a living and you don't have to"); look for *very new and very precise* evals because standardized ones are old (OpenAI: SWE-bench Verified no longer measures frontier coding — Fibonacci/matrix-multiply problems don't reflect real software engineering). (03:38-06:18)
- Evals are both an engineering problem and a philosophy problem: you can't exactly approximate the search space of where a problem could fail; coding problems have an infinite search space, so build evals that are a more approximate representation of the real thing. (06:27-07:12)
- Cline's eval origin: started rudimentary and ignored evals (same as the Codex team early on — "completely unnecessary"), then "upped the ante" and built evals from scratch; got a massive dataset by paying users who opted in to share their Cline coding usage, then did hard manual labor to clean it into decent solvable real-world problems. (07:13-08:46)
- Why agent evals are hard: a single-turn LLM eval ("how many toes does a cat have") has a binary answer / limited search space and is easy to grade; an agent reads files, searches docs, installs the environment, runs Python, runs tests, and you must grade the end state (did it work? did it work but break other things?). (09:05-10:14)
- Terminal Bench (Stanford): 89 coding problems (race conditions, database issues, infra issues) — an approximate but decent representation of real-world programming, runnable with any coding-agent CLI; tasks take up to 30-40 minutes, "that's how you know they're legit." (10:14-11:07)
- Running the suite: give each task an isolated environment (VM/container) with the full repo and setup, install whatever agent (Cline, Claude Code, Codex). Harbor (from the institute the speaker credits — transcript garbles the name as "Loda"/"Luddite") runs the 89 tasks in parallel with a standardized infra config (proper Linux machine, RAM/CPU per task) so the limiting factor is the slowest task. Infra options: Daytona, your own Docker machine, or Modal (Cline uses Modal). (11:07-13:00)
- Portfolio-allocate failures: run on the 89 tasks → get a score → say 50 failures → run *another agent* over the traces (a massive file of every LLM call) to categorize ("this failed because it didn't pass tests," "this failed because the retry tool was broken"); proper allocation reveals the small levers, and pulling them makes massive improvements. (13:03-13:51)
- Every eval run tests three things at once: (1) the model itself (a strong model can overshoot and score well even with a horrible harness), (2) the harness (is it leveraging the best of the model — Anthropic models work much better with Claude Code than with other agents for some harnesses), (3) the problem set (scoring 100% on stupid problems is worthless). (13:53-15:00)
- Three zones of improvement after an original score: Zone 1 obvious flaws/bugs (a bug that crashes the harness, rate limits — fix them); Zone 2 nuance improvements (the most critical — prompt-engineering techniques for Anthropic model families that straight up do NOT apply to Codex or Gemini families; the essence of hill-climbing — tweaking prompts, larger/smaller); Zone 3 the danger zone (overfitting / cheating to top a benchmark so you can tweet about it — don't). (15:43-16:53)
- Cline's concrete numbers: original 43%; gains from container CPU/memory changes, raised timeouts, and thinking-budget tuning (asking the model to think MORE sometimes *interferes* — it loops "I am a model. I am a model." for ~2,000 tokens). Cline keeps a large internal benchmark across many models including open-source. (14:51-15:40)
- Final synthesis: regardless of the problem, find a benchmark, build the eval, and hill-climb — but do BOTH; you can't just have a good number and stop, you must pass the vibe check (does it feel good to use this model/product) and have a decent score. Cline was very decent on Anthropic families, not on Gemini/Kimi families; hill-climbing to support those families unlocks the swaths of people who love them. (16:54-18:00)
