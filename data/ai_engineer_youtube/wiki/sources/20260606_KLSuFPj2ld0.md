## Summary

Stripe principal engineer Steve Kaliski lays out how to let agents spend money safely. The framing thesis: discovery and exploration benefit from LLM non-determinism, but credentials, payments, and checkout *require* determinism, so the system should isolate "how do I find things" from "how do I transact." Four agent-payment failure modes (wrong place, wrong thing, wrong amount, wrong credential) motivate three primitives Stripe built with partners: Shared Payment Tokens, which share a token carrying a processor-enforced mandate (currency, amount, time, seller) instead of a raw card across hundreds of payment methods; the Machine Payments Protocol (with Tempo), which makes ephemeral tool calls payable via an HTTP 402 status plus an encoded pay payload settled on-chain; and the Agentic Commerce Protocol (with OpenAI), a structured agent↔seller↔PSP back-and-forth that relays product-catalog JSON and cart state each turn so checkout details are not mis-relayed. The takeaway: keep discovery non-deterministic, shift payments/checkout/credentials to exclusively deterministic flows with verifiable parties, and make businesses agent-friendly by exposing programmatic flows rather than only web UIs.

## Notes

- Agents are already economic actors: using Claude Code, Codex, or any harness already spends money, proxied through a subscription or converted from input/output tokens, just not yet with arbitrary businesses beyond the LLM provider. (01:35-02:02)
- Crudely, an agent is calling an LLM and calling tools, and it spends on both; the tools of concern are search, credential management, and payment. (02:25-02:41)
- The critical separation is discovery ("how do I find things / what should I do") from transaction ("how am I going to transact"); discovery benefits from non-determinism, payments/credentials/checkout require it. (00:50-01:22)
- Four failure modes: wrong place (a fake look-alike domain such as amazon.*), wrong thing (an item 10× more expensive or the wrong variant), wrong amount (prices drift across regions/currencies/taxes so a page-parsed number may not be the real charge), wrong credential (card pasted to the wrong place; some payment methods are hard/impossible for an agent to relay). (02:42-04:02)
- Naive baselines are both bad: a raw card number has no spend controls, and operating the browser like a human is finicky, slow, and hard to observe — the same monetary-risk problem any web app has, which is why APIs exist ("dashboard is for a human; robots prefer code"). (02:52-04:31)
- Target shape: bind to a merchant, enforce spend policies, drive by API, use verifiable identities → a non-deterministic planner plus constraints with verifiable parties and structured negotiation = a small radius of risk. (04:31-04:50, 15:36-15:55)
- Shared Payment Tokens: an agent collects a credential and shares a token across hundreds of payment methods, encoding a mandate (like a smart contract) limiting the credential by currency, amount, time, and seller, enforced by Stripe and auditable. (04:51-06:01)
- SPT demo: a $25 / 30-day / seller-scoped token rejects a $50 charge because the request exceeds the mandate; lowering within the limit succeeds; brand, last-four, and credit type still flow to the seller for its own risk analysis (minimized blast radius, not secrecy). (06:38-08:39)
- Machine Payments Protocol (with Tempo): tool calls are HTTP requests that should be payable; an HTTP 402 returns an encoded payload of what/who/how to pay, then the credential is supplied; demo settles a one-cent charge in USD on the Tempo blockchain. (08:54-11:14)
- Agentic Commerce Protocol (with OpenAI): a standard set of APIs/objects for the agent↔seller↔PSP exchange — product catalog as JSON, then per-turn cart-state relay (line items, base price, tax, fulfillment) on each create-checkout / update-quantity / pick-shipping, ending in payment via a shared payment token. (11:18-14:33)
- The seller stays in control across all three primitives: keeps the customer relationship and receives risk signals, supporting crypto, cards, or any of hundreds of payment methods. (14:33-14:54)
- Q&A: recurring budgets work like a periodic-spend card on the same credential via an OAuth-style access/refresh flow; for larger budgets raise the number or mint many seller-scoped tokens. Stripe supports multiple networks (Base, Tempo) and replicates a product view of on-chain data. Stripe Projects is built on shared payment tokens plus product expression and the recurring layer. (16:15-18:00)
