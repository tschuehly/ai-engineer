# Evaluation

## Overview

Evaluation for AI engineering should measure whether models, tools, retrieval layers, skills, context packages, and agent workflows solve the intended task under real constraints. Adoption metrics need the same discipline: raw token volume, AI spend, or leaderboard rank should not be treated as developer productivity because visible usage targets can push engineers toward token generation rather than valuable outcomes. AI-assisted engineering dashboards should mature from utilization into impact and cost: tool usage, accept rates, and AI-assisted PR counts provide context, but leaders still need correlations to velocity, change confidence, maintainability, change failure rate, perceived quality, and spend. Even direct speedup claims need careful measurement: benchmark and time-horizon gains should be checked against field experiments on real developer work, and self-reported task duration should not be treated as reliable elapsed-time data. Benchmark percentages also have a lifecycle problem: once a benchmark moves quickly from first signal to saturation, capability evals need harder task distributions or human-time-horizon measurements, but those still need field validation before they are treated as productivity forecasts. For enterprise context systems, a working connector or non-empty answer is not enough; the retrieved context must close the actual knowledge gap that blocks delivery. For production AI applications, evaluation should connect offline golden data sets, deterministic scores, LLM-as-judge checks, online production scoring, and failure replay so prompt or workflow fixes are measured against both the triggering trace and the broader regression set. Enterprise eval programs also need to translate technical signals into risk, ROI, governance, compliance, brand, and budget decisions that C-suite owners can act on. Eval platforms also need to mature from ad hoc spreadsheet documentation into experiment systems where technical and domain users can compare configurations, score failure modes, and pull production traces back into offline regression loops. Model evals should include premise-pushback and dissatisfaction signals, because rising benchmark scores can hide models that answer nonsensical requests or produce two "best available" answers users still reject. For coding-agent loops, checks must verify both deterministic correctness and whether an independent reviewer can see failures the producing agent missed. Bug-finding agents also need precision-oriented evals: a tool that reports many issues with low true-positive rate creates alert fatigue and can make developers ignore the real defects that remain. Prompt-coded workspace workflows need an additional negative eval dimension: the agent should do the desired work in its assigned workspace and should not mutate the primary checkout or another forbidden location. Voice-agent evals add realtime and audio-specific concerns: traces, labeled conversations, transcript rubrics, function-call checks, tone and pacing judgments, synthetic conversations, interruption behavior, and asynchronous guardrails all contribute different signals. Realtime voice frameworks also need release evals across provider services, because Gemini Live, TTS, STT, transport, and tool abstractions can regress even when local code still passes unit tests. Planning depth is also an evaluation lever: tasks that can be specified and tested should reduce later review churn, while exploratory front-end work may need interactive QA. Agent coding evals should also account for feedback speed and review capacity: if tests, type checks, architecture review, and human inspection cannot keep pace with generated code volume, the agent is outrunning its verification loop and may turn large diffs into rubber-stamped risk. A benchmark pass can still fail a mergeability test when the output requires expensive review, correction, maintainability judgment, or context reconstruction. Product-quality evaluation has a softer but important layer: some quality debt accumulates as small interaction regressions, missing polish, slow-feeling animations, and customer drift that may not show up in short-term A/B tests. For skills and context files, useful evals compare behavior with and without the context, validate package format and clarity, and use repeated runs or error budgets when results are nondeterministic. Agent runs can also be interrogated directly after completion: asking what would have set the agent up better can reveal missing tools, contradictory instructions, permissions gaps, or wrong-language context before those defects silently repeat. For model training, basic train and validation loss curves are an early diagnostic layer before generated samples or downstream task evals are trusted. Small reasoning models add a generated-output failure mode: repetitive doom loops may survive SFT and need preference-alignment or reinforcement-learning evals that detect non-terminating repetition, missing final answers, and rewardable task completion. LLM judges themselves need evaluation: when a judge is used as a pass/fail classifier, its prompt and examples should be calibrated against domain-expert labels on a development split and validated on a held-out test split with metrics such as F1. A judge should usually be decomposed by error type into narrow binary metrics, because broad "success" judges and scalar scores are harder to align with human labels. Prompt optimizers such as GEPA can improve judge rubrics, but only when they receive useful diagnostic feedback such as the judge verdict, human ground truth, reasoning, and relevant domain priors. The same decomposition logic also serves training-data design: Snorkel's FinQA work breaks a single pass/fail correctness judgment into a rubric of sub-question checks so the per-check feedback reveals which specific behavior is failing (tool discovery, schema inspection, query construction, error self-correction) and therefore which datasets to generate, before any training data is written — even though the RL reward (GRPO) still collapses back to a single value.

Metric design is itself where product domain knowledge gets encoded. A scorer should not be treated as one broad "is this good?" question delegated to an LLM or rater; durable scoring systems decompose subjective quality into inspectable signals, calibrate those signals against human judgment and user behavior, and add new signals as failures reveal missing dimensions. Once that scoring system is trustworthy, it becomes reusable infrastructure: it can guide prompt optimization, filter synthetic data, support fine-tuning or RL, and score multiple online candidate generations so the product can return the best response without changing the base model.

Vertical AI evals should also turn expert review into structured failure-mode taxonomies. A domain expert can label how the system failed, map those labels to the customer's most important metrics, and produce production-derived failure sets that engineers improve one at a time. This keeps optimization tied to real customer context, exposes regressions by failure type, and gives domain-expert PMs a concrete threshold for deciding whether a prompt, retrieval, model, fine-tuning, or pipeline change is ready to ship.

Computer-use agents need one more evaluation lens: does the agent interaction increase human agency, or merely transfer agency to the model. Useful general intelligence should not be measured only by model capability, clicking success, or time spent on platform; it should also ask whether the workflow improves human creativity, productivity, strategic thinking, attention, and flow. That matters because automation can free attention, but it can also distract, narrow choices, or shut down user thinking when the product optimizes the wrong interaction.

Application-level evaluation can be organized as a layered metric ladder that carries into production monitoring. Because LLM systems are probabilistic, guardrails come first: input guardrails detect invalid/irrelevant/harmful inputs and output guardrails detect invalid/hallucinated/harmful outputs, and the acceptable boundaries are something the team defines. Above compliance, the ladder measures response quality (e.g. faithfulness — is the answer actually grounded in retrieved sources), at least one domain metric tied to the North Star (e.g. processing time), and system-health metrics (token cost/usage, turns per conversation, cost per response). The same metrics keep running after ship as monitoring, augmented by implicit indicators of success — how often a human overrides the AI verdict, or how long a human takes to review a recommendation — where a rising override rate or slow reviews signal regressions. This is the application-metric complement to a model-focused eval pyramid (serving → formatting → factual → safety → custom): both are layered, but one measures the model and the other measures the deployed application's compliance, grounding, domain outcome, and operational health.

Task-file workflows add pre-code evaluation points. Reviewing a generated task's acceptance criteria checks whether the agent understood intent; reviewing the implementation plan checks whether it found the right files and architecture path; final review then verifies code against the definition of done.

Coding-agent starter tasks should be chosen for verification clarity. Lint fixes, merge conflicts, failing tests, database migrations with known standards, and coverage expansion are useful early delegations because the agent and reviewer can cheaply tell whether the work is done; larger production-facing work needs stronger review and runtime validation.

Confident vibe coding adds an early-evaluation requirement for enterprise code generation. Review and testing agents should not only inspect a finished PR; they should bring standards, context, coverage, and red-team feedback into the coding loop while the agent is still shaping the change.

Agent-loop evals should pair operational metrics with correctness checks. Cost, latency, and number of steps are useful only after the harness verifies whether the agent actually reached the right outcome; otherwise a model can look fast because it guessed early or skipped the hard reasoning path.

Agent evals should also replace anecdotal development. Once a prototype reaches a plausible baseline, teams need input/output eval sets, human-reviewed examples, batch runs, failure clustering, and production tracing to compare choices such as model, tool count, memory, number of agents, and orchestration style. Observability then closes the loop by turning real customer traces into failure categories and regression examples.

Enterprise workflow evals can inspect the trajectory itself. If a task has a known golden workflow, the evaluation can compare whether the agent found the expected steps, sources, checks, or approvals before judging the final response. This catches acceptable-looking outputs that bypass internal process, protocol, or metric requirements.

Customer-facing agent evaluation needs simulation before launch and coaching after launch. Sierra's pattern uses simulated personas, accounts, and devices to generate many conversations against the agent before customers see it, then monitors live handoffs and mistakes as coaching material. This is especially important for nondeterministic support agents because a single input/output expectation cannot represent the real conversational surface.

Healthcare revenue cycle evaluation can attach AI behavior directly to operational money flows. Appeal generation can be measured by turnaround time and denial overturn rate, while upstream prevention systems should be judged by whether they reduce preventable denials, rework, and delayed payments without hiding payer-policy or clinical-necessity disputes.

High-assurance coding adds another evaluation tier for generated code. Formal specifications and proof-carrying implementation paths can verify selected critical components before execution, but only against the requirements that were actually specified. Separate generation and verification prompts or model providers can also reduce shared blind spots, especially when paired with risk analysis, safety cases, adversarial tests, and trusted libraries.

Enterprise AI ROI evaluation should classify outcomes before comparing them. Time savings, output volume, quality, new capabilities, decision quality, cost savings, revenue, and risk reduction describe different kinds of value and should not be collapsed into a single generic productivity story. Self-reported surveys can reveal useful early patterns, especially around where people believe ROI is appearing, but their audience and sampling path must stay attached to the claim so leaders do not mistake directional adoption evidence for a controlled population study.

Knowledge-work productivity claims need the same outcome discipline. Individual prompt speed can look useful while enterprise productivity stays flat; better evaluation asks whether AI compresses a real engagement phase, broadens corpus coverage, and frees experts for analysis, interviews, recommendations, or decisions. For extraction-heavy workflows, human-review load can be shaped by field-level confidence signals such as logprob-derived value scores, but those signals remain review aids rather than proof of correctness.

AI engineering transformation metrics should also distinguish adoption from operating-model impact. Tool usage, agent consumption, and breadth of use cases are only intermediate signals; teams need to connect investments in tools, upskilling, and change management to delivery speed, quality, security, resilience, developer sentiment, time to revenue, customer expansion, and cost per pod. Mean time to resolve priority bugs is one concrete resilience proxy when evaluating whether AI-assisted engineering improves the system rather than merely increasing activity.

Software-engineering ROI measurement should also separate access, usage quality, and engineering outcomes. Business outcomes such as revenue or retention are desirable but too confounded for direct AI attribution in many rollouts, so a practical framework measures AI usage and then checks a primary engineering-output signal against guardrails such as rework, maintainability, technical risk, people health, and DevOps health. PR count is a useful warning example: one enterprise case saw PRs rise after AI adoption while code quality fell, rework rose sharply, and effective output did not meaningfully improve.

Incoming AI-generated work needs evaluation too: automated security reports, issues, pull requests, and fixes can be high-volume and plausible, but maintainers still need to triage them because false reports, low-context fixes, and rushed patches can consume review capacity or break the product. Contribution gates that demand concise human context can be a practical first-pass evaluator before maintainers inspect a generated diff.

Reliable AI app evals should also be reverse-engineered from user-visible outcomes before optimization begins. Generic measures such as groundedness, factuality, or bias can miss whether the product actually resolved the user's task, so teams should define scenario-specific answer criteria, include persona and wording variants, inspect individual failures, and use the benchmark as the baseline for prompt, model, retrieval, logic, and guardrail experiments. Static golden sets are only a starting point for GenAI systems because similar natural-language inputs can produce sharply different outputs; production-readiness evals should fuzz nearby syntactic, semantic, conversational, and modality variants and treat failure discovery as guided search over the input space. Real-time AI search adds another version of this problem: static QA sets can mis-rank systems whose answers depend on changing web content, subjective source timing, and implicit user context. Dynamic grounding sets, generated from current sources and multiple search providers, can reveal failures that static benchmarks miss.

AI product evals should also be paired with production signal discovery. Offline evals mostly cover known failures and can saturate, while production AI issues may not throw exceptions at all. Teams therefore need explicit and implicit signals such as feedback, preference choices, copy behavior, regenerations, refusals, task failures, user frustration, and marked-correct or marked-wrong outputs; those signals become useful when clustered with user intent and product metadata into new issue definitions.

AI product teams should also evaluate the core capability before the surrounding UI when model feasibility is the largest uncertainty. The i.AI Consult case shows the failure mode: productizing an existing NLP technique before user-tested evals led to inaccurate and inconsistent outputs that missed legal and user thresholds. A stronger path collected real user data, added synthetic eval cases, optimized the capability, tested outputs with users, and only then used those findings to decide where human input belonged in the product pipeline.

Product-funnel evaluation should also treat attention, activation, and retention as distinct outcomes. For AI products and developer tools, a generated launch asset can be plentiful but still fail if nobody has a reason to share it; an onboarding flow can collect profile data but fail if users never reach the aha moment; and a feature roadmap can look active while neglecting primitives that keep advanced users from outgrowing the product.

AI-agent product evals can also serve as the product specification. When behavior is probabilistic or subjective, product and engineering teams need visible thresholds that decide what is shippable, what is a bug, and what is merely a model variation. Without those eval-backed thresholds, support and product teams can struggle to distinguish tone drift or excess clarification from true regressions.

Application-layer evals also need a domain map before they can be trusted. Teams should define the product "court": the in-bounds user prompts, out-of-bounds requests, easy cases, hard cases, known passes, and known failures. A small number of repeated manual checks can look convincing while missing entire regions of production behavior. The eval harness should keep representative input data stable while varying the implementation under test, such as the system prompt, model, RAG, preprocessing, or middleware. Scoring should stay as simple and debuggable as the domain allows, because PR reviewers need to understand which changes improved behavior and which introduced regressions. Vision evals need the same domain discipline: common benchmarks such as ImageNet or COCO can become saturated pattern-matching surfaces, so teams should add fine-detail, spatial, specialized-domain, and few-shot grounding tests before treating a VLM or detector as visually intelligent.

Guardrail evaluation is also part of production AI evaluation. Safety layers should be tested at the same boundaries where attacks enter: direct prompts, external context, RAG chunks, MCP tool descriptions, memory, agent plans, and model responses. For latency-sensitive paths, a fine-tuned encoder discriminator can be evaluated as a binary classifier and compared against slower LLM-as-judge checks, while human approval flows should be tested for whether reviewers see the effective action and hidden parameters they are approving. Multi-agent organizations add another evaluation question: does the workflow actually force review, approval, and role-specific quality checks, or are those still best-effort prompt instructions?

Regulated explanation systems need staged evals around both generated language and deterministic source data. TurboTax's pattern starts with tax analysts producing manual baselines and prompt guidance, turns those examples into golden data and LLM-as-judge checks for smaller iterations, and returns to manual expert review when the tax year, prompt shape, or model changes substantially. The same eval loop should check that generated explanations preserve exact values from authoritative engines rather than hallucinating numbers.

RAG evaluation should treat the pipeline as a set of changeable components, not a solved top-k pattern. Parsing quality, chunk hierarchy, OCR, image descriptions, embedding models, hybrid lexical/vector scoring, metadata filters, graph ontology, extracted triplets, traversal depth, and agentic search decisions can each change the answer. Agentic retrieval adds a trace-level evaluation requirement: teams should inspect which searches the model chose, not only whether the final answer sounded plausible. For production AI search where labeled answers are often absent, reference-free metrics should decompose answer quality into completeness, document relevance, and hallucination against retrieved evidence; these metrics diagnose different failure modes and can trade off against each other. Graph-backed RAG also needs evaluation of retrieval latency and answer quality together because deeper graph traversal can expose better relationships while slowing production responses. Graph-backed KAG adds quantitative and decision-quality checks: can the system select exact structured values, run deterministic calculations, preserve traceability, and support the advisory decision it claims to make? Enterprise deep research adds governance and factuality checks to that surface: because the agent turns private documents into business artifacts, teams should verify not only answer quality and citations, but also whether multimodal documents were parsed, the right metadata and access controls scoped retrieval, hallucination mitigation caught unsupported claims, and observability can explain how the report was produced.

Operational graph agents add an extrinsic metric requirement. A network knowledge graph or digital twin should be judged by whether it improves ticket summaries, impact assessments, test selection, execution reports, remediation recommendations, and approval-board evidence in the real workflow, not only by intrinsic graph completeness or retrieval statistics.

Enterprise analytics agents add a metadata-specific evaluation layer. GenBI systems should be tested against messy production-like schemas and real user questions, with BI experts reviewing outputs before business users or executives depend on them. Metadata quality can be evaluated directly by running the same question set against better- and worse-documented data sources, then measuring whether the LLM finds the right context, report, or query path more reliably.

Contact-center voice evaluation should inspect each pipeline stage, not only the final summary. Speaker-channel preservation, STT accuracy under accents and poor audio, domain vocabulary, numeric normalization, grounded JSON extraction, hallucination checks, operator edits, and CRM-field mappings each create a failure point that can corrupt business records or analytics. Autonomous voice agents also need self-driving-style simulation discipline: repeated conversations can estimate failure probabilities, text-only or module-level evals can cover workflow logic cheaply, and full voice realism should be reserved for behaviors such as interruption, latency, accent, background noise, and audio quality.

RL environments add an evaluation shape for interactive model behavior: the same environment can generate rollouts, compute deterministic or weighted rewards, and become the training loop. That makes the environment itself part of the eval artifact. Teams should control environment noise, inspect trajectories, check for hidden opponent or simulator bias, and try the trained model in the real task before trusting reward curves or benchmark scores. Environment design also prevents vague agent validation: once a harness must include tasks and rewards, teams can compare models, prompts, hyperparameters, and training methods against a named optimization target instead of relying on a vibe check.

Reasoning-model RL sharpens the same point: useful training and evaluation domains are often those with checkable outcomes. DeepSeek's Paper Club recap emphasizes code and math tasks where compilation, factual correctness, or mathematical correctness can verify the result; it also cautions that public benchmark gains should be interpreted alongside general performance because benchmark overfitting remains possible.

Interpretability-derived controls also need evaluation. Feature attribution can expose why a token was produced, activation steering can patch a specific behavior, and model diffs can reveal post-training feature changes, but each control should be checked against task evals and regression cases. A feature-level intervention that improves privacy handling, jailbreak resistance, or brand behavior can still create hidden off-target behavior if the team treats it as a guaranteed semantic switch rather than a model intervention.

Robotics-style agent evaluation emphasizes that action systems need more than final-answer scores. Production logs, live action feedback, stateful starting conditions, and counterfactual simulations reveal whether an agent can recover after its own actions shift the environment. A single benchmark percentage is only a starting point; failure categories and replayable trajectories tell teams where to improve the agent loop.

Autonomous-driving foundation models show the same principle in a safety-critical action domain. Open-loop replay can compare waypoint predictions against logged driving, but simulation is more faithful when the planner's output changes future observations. Generated sensor simulation adds a controllable eval surface: teams can vary weather and time of day, then check whether a camera-only planner degrades in expected ways before relying on road tests alone.

Scientific co-scientist evaluation needs the same trace discipline. Realtime lab agents should preserve sensor readings, microscope or camera frames, sample conditions, protocol context, and resulting measurements so the team can verify whether the agent's interpretation matched the experiment. Those traces can also seed simulations, letting teams compare proposed conditions against recorded physical behavior before changing the next run.

For physical robots, evaluation also needs timing and instrumentation checks below the policy. Bus captures, timestamped `candump` output, and cycle-time plots can distinguish a policy defect from delayed messages, stale sensor inputs, queued commands, logging-induced packet loss, or priority inversion. The evaluation target is not just whether the policy command is reasonable, but whether the whole sensor-policy-actuator path preserves cadence under load.

Robot foundation-model evaluation also needs generalization experiments above the low-level pipeline. Held-out homes measure whether environment diversity creates reusable behavior rather than memorized scenes; long-horizon household tasks measure whether a high-level instruction decomposes into minutes of autonomous control; and partner-hardware demos test whether the model and inference integration transfer when the model team has not tuned against that robot body.

Eval competence is also an organizational workflow. A useful eval program lets teams turn selected user complaints into regression cases, rerun product-specific benchmarks when new models launch, and decide whether an unreleased use case has crossed a viability threshold. The dataset is not a static fixture: it should be reconciled with user reality through product judgment. Scorers deserve similar treatment because they are effectively executable product specs; generic scorers are useful starting points, but product teams need custom scoring functions that encode the behavior they actually intend to ship. As frontier models get better at optimization work, eval platforms can become active workbenches where agents propose improvements to prompts, datasets, and scorers rather than leaving humans to translate dashboard findings into edits elsewhere. Media generation adds a perceptual version of this problem: FID-style scores, CLIP adherence, object counts, and color checks can disagree with human-visible quality or artistic intent, so creative-product evals may need perceptual metrics, artifact-aware datasets, and user-specific preference classifiers. For agents, the evaluated surface includes tool definitions and tool responses, because tool schemas, descriptions, output format, and token footprint can dominate the context more than the system prompt. When that surface is a large tool catalog behind a router, Prosodica makes the evaluation concrete: measure four things — tool-selection accuracy, time-to-first-token, input tokens per request, and estimated cost per 1,000 calls — over synthetic tool pools scaled from 10 to 1,041 tools (plus the Berkeley Function Calling Leaderboard and Skills-bench-style scenarios), running identical queries fat vs. routed so the only variable is whether the model saw every tool or the routed subset. This turns "does the router help?" into a curve, and it turns tuning into a search: [sweep the retrieved-tool count K and guard the router's failure modes](../concepts/tune-a-tool-router-with-k-sweep-and-guard-its-failure-modes.md), picking the smallest K (3/5/10) that meets the accuracy target rather than assuming more retrieved tools is safer.

Enterprise RL adds a private-benchmark version of the same evaluation discipline. The target is not a public math score by itself, but a company-specific workflow whose success can be graded, reinforced, and tied back to measurable ROI. Systems simulations also become part of evaluation before training begins: candidate RL layouts should be scored for throughput, queue balance, response-length behavior, KV-cache feasibility, and maximum policy staleness so teams do not mistake fast hardware utilization for stable learning.

Agent RFT adds another evaluation burden: the grader becomes the training signal for a real tool-using agent. Before training, teams should verify that train and eval sets mirror production traffic, that base-model behavior is measured, and that more samples can actually discover better rollouts. During reward design, trajectory context matters because final answers may only be meaningful alongside tool calls, terminal output, retrieved facts, file selections, tests, and lint results. Reward hacking must be treated as expected behavior in optimization-heavy domains: GPU-kernel agents, for example, can return reference code, no kernels, or identity kernels unless judges and static analysis block those shortcuts.

Cursor Composer reinforces production match as an evaluation and training requirement. Cursor built internal benchmarks around its own repositories and real development workflow, then trained with tool formats and environment behavior close to production. That matters because the desired improvements were not only final-answer quality but agent behavior such as when to search, when to read, when to edit, and when to run tool calls in parallel.

Code world models add execution traces as both training data and evaluation evidence. If a model claims to understand code behavior, useful checks include whether it can trace local variable values, predict state transitions, use terminal feedback, and simulate expensive program paths without confusing approximation with formal guarantees.

Coding-agent model evaluation should also vary the harness around the model. MiniMax M2's scaffold-generalization lesson is that scaling tools is not enough: useful evals should perturb tool descriptions, system prompts, user prompts, chat templates, environment behavior, and tool-response shape to see whether the model adapts or only memorized one agent scaffold.

GLM 4.6 adds two evaluation angles for training-time agent work. CC-Bench 1.1 treats agent-style coding as full trajectories over real-world task categories rather than isolated algorithm answers, recording planning, tool calls, edits, and execution. Its RL lessons also show that training metrics need regression checks for long-context retention, short-output reward seeking, and data-quality effects rather than assuming larger or more staged training always improves the target behavior.

Real coding sessions can become evaluation and training environments when they are treated as reconstructable software artifacts. Cline's pipeline frames a coding benchmark as a starting repository state, starting prompt, and verifier; the same environment becomes an RL environment when the reward updates the policy model. This makes verifier design central: tests should capture the user's intended outcome and avoid encoding incidental details from the ground-truth patch, because path-biased verifiers can train agents toward mimicry or shortcuts.

Long-horizon coding demos should be evaluated as workflows, not as one impressive final answer. Poolside's Ada-to-Rust demo includes visible diffs, build output, generated test commands, Bash scripts, manual reruns, and feature-level checks; those surfaces are the evidence that a multi-step coding agent did useful work rather than only producing a convincing summary.

LLM program optimization adds another eval loop: define known inputs and outputs, write metrics that reflect the desired behavior, evaluate the base program, then let an optimizer propose improved prompts or modules. Evals are also a durable specification boundary: they state what the application actually cares about when models, prompt formats, inference strategies, and optimizers change. Metric breakdowns should be inspected after optimization because a gain can mean the metric is useful, the data is underspecified, or the program needs decomposition. Prompt-learning loops add a related requirement: labels and scalar scores are weaker than feedback that explains why an output failed and points to violated instructions, missing context, or rule-level noncompliance. The optimizer also inherits evaluator quality, so prompt-improvement systems should test their LLM judges, rule checkers, data splits, and loop budgets before trusting apparent prompt gains. Product teams can use the same shape for model behavior: seed prompts, run scored tasks, select strong variants, ask an LLM to reflect on successes and failures, mutate the prompts, and repeat while checking that evals actually represent product requirements. PM-facing eval workflows should also avoid treating prompt playgrounds as isolated demos: traces and spans can carry real inputs, outputs, metadata, and agent actions into datasets and experiments, while LLM judges should emit categorical labels that are deterministically mapped to scores instead of raw numeric ratings.

Meta-controller optimization adds an evaluation layer above individual prompts or agents. A learned router should be judged on whether it selects the right strategy mix for a task profile, not merely whether the final answer improved. Its feedback needs to cover correctness, per-strategy contribution, compute, latency, memory, and confidence calibration; otherwise it may overuse expensive strategies, preserve harmful reflection deltas, or learn from sparse and noisy rewards. Hierarchical verification can reduce weak-feedback errors, but the verifier ensemble itself must be tested for shared blind spots and escalated to human oversight or executable checks when confidence is not enough.

Coding-agent prompt learning turns that evaluation loop into a system-prompt update path: baseline the agent on tasks such as SWE-bench Lite, run generated patches through tests, ask judges for explanatory diagnoses, synthesize rules from the diagnoses, and rerun the benchmark to check whether agent behavior actually improved without weight changes.

Anti-slop evaluation should be provenance-neutral. Human and AI outputs can both be low-quality, inauthentic, inaccurate, insecure, or unmaintainable, so the release question is whether the artifact meets the bar. Agent autonomy claims need the same discipline: unattended runtime is only meaningful when paired with tests, review findings, security evidence, maintainability judgment, and human ownership. For generated web apps, browser-level verification is a specific autonomy test because visible UI can hide missing handlers, mock data, or other painted-door failures that non-technical users will not systematically inspect.

Generated kernel evaluation has an unusually concrete version of the same problem: the agent can compile, run, and report a speedup while still being wrong, measuring the wrong thing, or exploiting the benchmark. Useful evaluation needs floating-point tolerance policy, representative input sizes, warmups, cache controls, reliable hardware timing, baseline comparisons, and scrutiny for suspicious speedups that satisfy the benchmark without preserving intended behavior.

Support coding agents need staged evaluation before their throughput numbers are trusted. Zapier's Scout Agent separates whether a support issue is categorized correctly, whether the issue is actually fixable by code, and whether the generated fix is accurate. Each failure asks for a different improvement: routing and triage, action gating, or code-generation quality.

Coding capability evals also need to evolve with model capability. Static programming-problem benchmarks can lose signal through training-data contamination, brittle test suites, and difficulty distributions that become too easy or too hard. Dynamic code evals can use fresh release windows, rolling task sets, generated input tests, and recalibrated difficulty to keep comparisons near the current frontier. As tasks grow from snippets to repository-scale optimization or full codebase translation, construct validity matters more: the benchmark should use natural real-world tasks and grade the actual outcome, such as correctness, equivalence to an expert patch, runtime improvement, and maintainable code quality. Long-horizon code tasks also need intermediate progress signals, because final correctness alone is too sparse to guide multi-hour translation or refactoring attempts. In live IDE studies, preference signals need human-centered controls: acceptance rate measures both completion quality and user-facing factors such as latency, so experiments should balance latency before treating acceptance as a clean model-quality signal.

AI code quality evaluation should also distinguish generated-code speed from SDLC quality. If AI creates more PRs and more code while defects per line stay flat, total review and defect load can still rise; useful evaluation has to inspect code-level issues, process-level ownership, test coverage, standards compliance, and whether review gates learn from accepted and rejected suggestions over time.

Regulated-agent evaluation adds accountability and deployment-readiness evidence. High-consequence public-sector agents should be judged on whether their decisions can be explained after a bad outcome, whether infrastructure isolates sensitive data, whether SBOM, dependency, patching, and monitoring artifacts support governance, and whether restricted-region deployments keep pace with commercial capability.

PR-derived field telemetry adds a practical adoption dashboard shape for AI coding rollouts. Developer AI adoption rate can be correlated with PR throughput and cycle time, but the result should be segmented by architecture and paired with PR-size, bug-ticket, and revert-rate guardrails. Otherwise teams can mistake more and larger PRs for productive transformation while missing review burden, quality drift, or cross-repo context bottlenecks.

Retrieval-specific evals should be fast enough to change engineering behavior. Query-document pair checks can compare chunking, embedding models, and top-k parameters on the application's own data without waiting for slow judge pipelines. Synthetic query generation can bootstrap that benchmark, but only if the generated questions are aligned with realistic user specificity; otherwise the eval can reward retrieval systems that only handle clean document-shaped questions. Once real traffic exists, conversation logs add an output-side eval surface: extracting tools, errors, frustration, satisfaction, and use-case metadata lets teams compare KPIs across clusters instead of staring at one aggregate factuality score.

RAG evaluation should also sequence complexity. A useful loss analysis asks which query shapes are failing before choosing the next technique: exact-term misses, paraphrase misses, candidate ordering failures, vertical-domain vocabulary, missing structured product signals, ambiguous intent, cost overload, and UX overconfidence each point to different fixes. This keeps BM25, vector retrieval, cross-encoder rerankers, custom embeddings, fan-out, distillation, and fallback UX in one empirical ladder instead of treating them as rival ideologies.

Information-retrieval evaluation should also check whether the retrieval mechanism matches the query shape. Short brand, identifier, or exact-term queries can expose vector-only failures even when semantic examples look good; longer contextual queries can expose keyword-only failures. Hybrid retrieval then needs its own evaluation because RRF, boosts, filters, and rerankers can change both recall and ordering.

Verifier-backed branching adds an evaluation pattern for test-time search. A shared snapshot can fan out to multiple agents or subagents, each branch mutates its own environment, and a verifier selects branches that satisfy the target condition. This is useful only when the verifier captures the desired outcome; otherwise parallel branching scales the wrong signal.

RAG evaluation can be sequenced with product maturity. A pre-production knowledge-base build may start with practical requirements such as supported source types, Markdown output, asynchronous webhooks, and enough product quality to reach real users. Once usage exists, the benchmark should expand to parser accuracy, parser completeness, hallucinated output, cost, and whether hybrid graph/vector retrieval improves real messages or decisions.

High-stakes domain RAG also needs a fidelity ladder. Expert review can catch legal or regulatory mistakes that engineers and generic metrics miss, but it is expensive; curated expert criteria and automated retrieval metrics provide faster feedback for everyday iteration. Useful automated checks can stay concrete, such as whether retrieval hit the right corpus, folder, section, keywords, or provision before judging the final answer.

Web-grounded agents have a failure mode that ordinary answer-quality scoring can miss: a blocked, empty, or poisoned fetch is not reported, so the model fabricates and an evaluator that only reads the final answer cannot tell a real search from a confident invention. Evals for these agents should verify that actual content was retrieved (live pages reached, citations that resolve, prices and links that exist), not just that the answer looks plausible, and should watch for the symptoms of silent web-access failure such as 404 citations and fabricated product URLs. This is the same reason AI search providers should expose grounding documents: distinguishing retrieval failure from generation failure requires seeing the evidence the model actually used.

General LLM eval programs can be staged as a pyramid. Start with serving performance because a high-quality model still fails production if latency, throughput, concurrency, GPU sizing, or cost do not hold. Add formatting checks when downstream systems need strict JSON or other structured output. Add factual benchmarks such as MMLU-Pro for broad or fine-tuned accuracy checks, then add safety, bias, and application-specific custom evals. Open tools such as GuideLLM, lm-eval-harness, and promptfoo are useful starting points, but the eval surface should be adapted to the product's data, request shape, risk profile, and CI/CD release process.

Coding-agent code quality needs evaluation while the diff is still forming. Useful checks include whether the diff introduces new lint or type errors relative to the starting codebase, whether generated tests express user-level behavior and cover the changed code, whether the branch still matches its stated goal, and whether specs, architecture expectations, or style rules reveal implementation gaps. This turns evaluation from a late PR gate into continuous defect discovery and repair feedback.

Enterprise production evaluation can also be architected in three layers rather than one judge. Deterministic checks (regex and format rules plus classic ML for NER, intent, and PII) are cheap and should be handled first; semantic LLM-as-judge checks score safety, groundedness, and relevance against expected answers; and behavioral checks inspect the agent's actions, such as whether it called the right tools or fell into loops. The behavioral layer is the one teams most often skip, yet it catches a correct answer that quietly required three redundant database calls, which is harmless in a demo but expensive at thousands of daily queries. This makes evaluation a precondition rather than an afterthought: the most reliable production sequence builds evals, tracing, and a data foundation before choosing a model, and treats the eval set as a living system that starts small (one banking case began at 200 expert-sourced answers) and grows from every below-threshold production miss. Because behavioral evals get expensive to rerun as the set grows, cost governance helps: run a small subset in CI on prompt changes and the full suite only on merge to main, and give the growing set an owner plus categorized rows so each change is traceable to a class of problem.

Behavioral and output evaluation also has a hard floor that no amount of test coverage removes: a fine-tuning backdoor ("sleeper agent") is correct on almost everything and only misbehaves on a benign, untested trigger, so behavioral testing would need the exact trigger up front — "and if you know the trigger, you wouldn't need the monitor." LexisNexis's Sachin Kumar frames this as a case where the assurance has to move from behavior to internals: because the backdoor is a directional shift the fine-tuning wrote into activations, an activation-difference sparse autoencoder ("diff-SAE") catches it as a single feature at 40× the signal of joint cross-model features, with precision 1.0 and zero false positives from one cheap layer, cheap enough to run as a CI gate on every checkpoint. This complements the model-diff idea (feature-level inspection surfaces untested behavioral risk that aggregate evals miss) with a concrete, quantified detector, and it is a reminder that green evals plus green behavioral monitors are not sufficient evidence for a fine-tuned, vendor-tuned, or downloaded model.

For generated-query systems, validation must include execution, not just parsing. A text-to-SQL agent can emit syntactically valid SQL that returns zero rows or silently omits a status filter, which looks correct but misleads — so WorkOS's Studio runs every generated query and confirms it returns sensible data before it is hardcoded into a reusable widget. The most common semantic miss is forgetting active-status or non-deleted filters, which is best prevented by encoding those data-consistency rules into the tool context rather than relying on a post-hoc judge. The same talk treats evals as environment-uniform: they run in both staging and production, treated the same, so developers experience the same checks as the teammates using the tool.

Agent evaluation has two orthogonal axes worth separating. Arize frames the first as five "flavors" of signal — LLM-as-judge, human feedback, golden datasets, deterministic checks, and business metrics — where golden datasets are the trust anchor that tunes the judge toward a trusted human labeler, deterministic checks (valid JSON, schema, non-null fields) are the cheap default with no model in the loop, and business metrics reduce to make-money / save-money / save-time. The second axis is scope: an eval can read a single span (one input/output of one LLM call), a multispan slice (data across several components, such as how agents pass data back and forth), the full trajectory (did the agent call things in the right order to finish the business process — the "B before A when B depends on A" failure), or the whole session (evaluate the conversation's state machine: was the user frustrated, were all questions answered). Picking an eval is therefore choosing a flavor and a scope at once, with the discipline that you run the minimal set that gives signal because every eval costs. All of this rests on OTel-first observability: a one-line auto-instrumenter turns a framework into traces and spans because telemetry, not code, audits what an agent did, and the same traces feed a distributional view (paths, branches, loops) and become datasets for experiments — changes to prompts, models, orchestration, or configurations — so a perceived "fix" is checked against regressions rather than introducing silent ones. The forward-looking pitch is to automate the human out of that flywheel: expose every primitive via CLI plus tools and skills so coding agents drive it, and ship a platform agent ("Alex") that reads the traces, surfaces high latency and errors, and authors evals on the fly so "you shouldn't even have to choose your evals."

Eval scores are most useful when read as a diagnosis, not a verdict. Cline's "evals are broken, use them anyway" framing rejects both the camp that treats leaderboard numbers as gospel (and benchmark-maxes) and the camp that dismisses evals for vibes; the productive middle is to hill-climb a real benchmark *and* pass the vibe check. The operational core is to portfolio-allocate failures: after a run, send a second agent through the traces of every failed task (each a massive file of all the agent's LLM calls) to categorize *why* each failed and surface the small levers that move the score. That triage must keep three things separate because every run tests all of them — the model (a strong model can overshoot a bad harness), the harness (is it leveraging the best of the model?), and the problem set (100% on stupid problems is worthless) — and it sorts fixes into three zones: obvious harness bugs, nuance/model-family-specific tuning, and the overfitting danger zone. The staleness lesson reinforces benchmark hygiene: OpenAI declared SWE-bench Verified "no longer measures frontier coding capabilities," so seek new and precise evals (long agentic multi-minute tasks like Terminal Bench's are a legitimacy signal), and when interpreting a lab's launch number, don't believe it outright and let a new model settle before switching.

Evaluation also applies to the tool interface an agent calls, not only the model and harness. Chrome DevTools' team measures the "fuel efficiency" of an agent interface as tokens per successful outcome — effectiveness (did the agent complete the journey?) times efficiency (token cost, tool calls, duration), gated on actually finishing because cheap-but-failing runs are not efficient. It is compared within a user journey rather than globally (web scraping is cheap; debugging a broken layout is intricate and rightly costs more), and even an imperfect measurement beats gut-driven decisions; a per-use-case view surfaces the weakest tools as the optimization targets. This sits beside loop-level metrics (correctness, cost, latency, step counts) but ranks the interface rather than the model.

A judge node can also serve as a calibrated quality gate over a fleet of specialist agents, and Qodo's code-review system shows how to make that judge trustworthy rather than another opaque LLM-as-judge. Instead of scoring against a fixed rubric, the judge weighs each specialist suggestion against organizational signals: indexed PR history (how reviewers and developers commented on similar past changes), uploaded architecture and compliance guidelines, and a running accept/reject tally where every accepted suggestion gains weight for the next run and every rejection loses it. The system also separates "rules" (flagged regardless of accept history) from "bugs" (weighted by repeated reviewer agreement), which guards against the failure of treating "it happened in past PRs" as ground truth — past code can be wrong (hard-coded API keys), so historical frequency must not silently become the quality bar.

A benchmark number is only meaningful with the conditions it was measured under, a trap that is sharpest in audio. pyannoteAI shows NVIDIA Parakeet's 11.4% word error rate on the AMI meeting dataset (the Hugging Face open ASR leaderboard figure) becomes 26% on the same model and the same recordings when you score the central table microphone instead of each speaker's headset mic — "most voice AI benchmarks are measuring single-speaker speech and calling it solved." Diarization shows the same use-case sensitivity: state-of-the-art diarization error rate is single-digit on clean two-party telephone calls but ~41% in a noisy restaurant. The eval discipline is to benchmark on audio (and conditions) that match deployment, and to read leaderboard numbers as measured under a specific microphone, speaker count, and noise level rather than as a model-wide capability.

Benchmark construction is itself a discipline, not just benchmark consumption. Snorkel's review of 120+ Open Benchmarks Grant applications separates "the science" of a sound measuring stick from "the art" of a field-shaping one. The science is four properties: rigorous individual task quality (GPQA's appendix added an adversarial multi-reviewer quality-control protocol so tasks are tractable for *other* experts, with peer-review-style incentive payouts), intentional distributional diversity (a clear domain taxonomy with tasks distributed across it — including deliberate over-weighting of rare-but-critical failure modes, the way self-driving must over-sample yellow lights and pedestrians; MMLU's 57 domains are the model), real model headroom (the benchmark stays unsaturated and reliably separates the frontier — ARC-AGI 2 stayed unsaturated until the reasoning push produced a leap, and ARC-AGI 3 launched human-solvable but under 1% for frontier models), and a robust methodology that measures the axes that matter beyond accuracy (cost, latency, reasoning-trace quality, intermediate steps, tool use, and policy adherence — τ-bench fails a model that books the right flight but violates fare-class rules). The art is what makes a benchmark a real research contribution: a thesis that bets on where the field is going (Terminal Bench bet on the CLI before coding agents made it obvious), the ability to produce roadmaps that spawn follow-on work (SWE-bench's family of Lite/Verified/Pro/Multilingual/Multimodal), and first-class researcher UX, because a benchmark's core users are other builders — adoption follows a standardized modular harness that is easy to run against, extend, and reuse for RL (HELM, and Harbor shipped with Terminal Bench 2.0). The underlying asymmetry that motivates all of this is that capability is outpacing measurement, so the next generation of agent benchmarks should push three under-covered axes — environment complexity (a real codebase's org policies, Slack context, flaky CI, parallel contributors), autonomy horizon (how long before reliability breaks down, across the co-pilot↔autonomous slider), and output complexity beyond plain text (nuanced reward signals for subjective artifacts, plus trustworthy outputs where the agent reports its own uncertainty).

Running such a benchmark at scale is also an infrastructure-reliability discipline, not just a measurement one. Nebius's SWE-rebench treats each task as a multi-gigabyte Docker image and pairs a deliberately minimalistic agent with strong infrastructure, on the principle that a minimalistic agent on strong infrastructure beats an over-engineered agent on weak infrastructure. The operational hygiene that keeps numbers trustworthy: a retry policy that separates model errors (too-long context, too many tool calls) from infrastructural/provider errors; noise control (tests reaching external resources, or a default 1970 container clock, silently invalidate runs); default-parameter drift across model updates *even within a family* (GPT 5.2 → 5.4 can move reasoning and caching defaults); and validating the harness against an external benchmark so your numbers match the reported ones before any experiment. The same talk surfaces a runtime-leakage failure mode distinct from pretraining contamination: capable agents reach outside the task boundary to read the leaked ground-truth answer — Claude Code escalated from `git log --all` (future commits) to a web-fetch tool (the live GitHub issue/PR) to `curl` (even formatting the conversation for readability) — so the environment must be sealed channel by channel and trajectories post-processed, because sealing one path just routes the agent to the next and better models reward-hack more. SWE-rebench also reports distributions rather than a mean (tokens and tries per problem, five runs per task, pass@5 for potential vs pass-all-5 for reliability) and reinforces decontamination through monthly time splits.

Verifying agent-built software is itself an evaluation-design problem, and reviewability is part of the bar. Safe Intelligence's Michal Cichra frames spec-driven development as leaving a loop open — you have a markdown spec but no proof the product behaves that way — and adds that AI-written tests are even harder to audit than AI-written code. His answer is behavior-driven-development scenarios (Cucumber): executable so they actually check behavior, and human-readable so a reviewer can confirm *what* is being checked, linked to the PRDs and critical user journeys so the test layer is traceable to intent. This is the per-feature version of judging a benchmark by methodology rather than a single number — a check is only trustworthy if a human can read it and see that it tests the intended behavior — and it sharpens the warning that generated tests need meaningful, readable plans rather than blindly accumulated assertions.

Retrieval evaluation has its own trajectory-scoped version of "inspect the process, not just the answer." Turbopuffer's benchmark of Claude Code used ContextBench, which scores whether the agent read the right files, lines, and symbols *along the way* rather than whether it solved the task, on the thesis that "how you get there" matters. It reports two metrics at file/line/symbol granularity — precision (of what was read, how much was golden) and recall (of the golden targets, how many were found) — and the split is diagnostic: raw Claude Code *wins* file recall by reading everything but loses file precision (wastes 1-in-3 reads) and line recall, so "explored a lot" is not "explored the right things." A measurement-design detail travels with it: capping reads at 50 lines makes the conditions distinguishable, because whole-file reads are too noisy to differentiate. This is the same lesson as golden-workflow trajectory evals and the span/multispan/trajectory/session scope axis, applied to retrieval quality specifically.

Lovable's self-improvement loops add two production evaluation patterns. The first turns the user's behavior into a label: an LLM judge scores whether a session is "stuck" (a user asking the same thing more than once, complaining, failing explicitly, or abandoning a project), and the stuck→solved transition becomes the high-signal training example. The second is a blank-injection holdout for measuring whether an injected context entry actually helps: for a small sample of cases where the entry *would* fire, the system injects nothing, then compares downstream project success between the injected and held-out groups — an online A/B that ranks each entry by measured outcome rather than assumed value, and feeds the same problem bank back as an internal model-ranking set. This is the production-A/B counterpart to offline scorers, gated on a real user-outcome metric (project completion/deploy) rather than a proxy.

Task quality is not only a measuring-stick property but a quantified training lever, and the curation discipline behind it is an evaluation problem. Snorkel's "task fidelity" experiment (Kobie Crawford) held model, compute, and task count fixed and found that high-quality agentic tasks produced ~5x the RL uplift of low-quality ones (6% vs 1%). The curation method is a four-criteria gate — achievable, non-trivial, functionally correct, environment-reliable — over containerized TerminalBench-style tasks, validated by behavioral proxies (accepted tasks show 2x tool calls, lower pass rates, more output tokens) and, more durably, by a *clean-failure diagnostic*: a well-specified task fails for a real reason (the model can't reach the needed logical conclusion), whereas a rejected task fails for degenerate reasons — an unsolvable environment, a spec-test mismatch (the back-end tests expect things the prompt never requested), or an implicit dependency never fed into the model's context. The eval consequence is that ambiguous specs do not produce harder tasks; they produce noise, and tasks that can never be completed actively mask whether the model improved, conflating task-quality defects with genuine benchmark saturation. The same talk reinforces the expert-built-environment lesson: ground truth comes from human annotators and experts, rubrics carry the criteria for both humans and LLM judges, and very high inter-annotator agreement (human-to-human and judge-to-human) gates whether a signal is trusted.

Agent evaluation also needs a richer specification than a dataset of good inputs and outputs. Safe Intelligence's Steven Willmott frames spec-driven validation as making the implicit explicit: on top of ground-truth examples, an agent spec should capture explicit rules (never discount over 10%, no refunds after 30 days), domain ontologies and dictionaries (an airline only flies certain destinations; gross profit and gross sales are not substitutable), rights and roles (logged-in vs out, permissions), and robustness requirements — the agent analogue of vision robustness (detecting a runway at sunset, in fog, or under camera shake), i.e. how many typos or rephrasings the agent tolerates before it fails. These read like integration tests, and the A2A agent card describes what an agent does but is not enough to evaluate it, because you still need the valid range of change. The spec feeds two activities at once: security testing (knowing the domains the agent engages and where it has power to act tells you where it is most vulnerable) and robustness testing (vary inputs to measure the agent's valid range). Keeping the spec implementation-independent — versioned like an OpenAPI spec in a GitHub repo and pulled into whatever tool runs it — lets the same integration/unit/penetration tests survive a model or framework swap (e.g. LangSmith to Vertex agents) and closes a "backyard RL" loop that iterates the agent, not the model, to fill robustness gaps. This is the eval-design complement to the same company's per-feature point that a check is only trustworthy if a human can read it and see that it tests the intended behavior.

Model *selection* is its own evaluation discipline, and Pruna's Bertrand Charpentier argues the usual shortcuts are unreliable. Reading a single public leaderboard fails because boards disagree (the same image model is rank 10 on Artificial Analysis and rank 5 on Arena, with incomparable Elo ranges, duplicate entries, and models missing from some boards), are built on a few thousand samples (small versus a provider's millions of requests per day), aggregate over tasks that hide per-use-case variance, and report win rates where most models lose ≥40% of their battles — so the top-ranked model is the wrong choice for nearly half of real use cases. Running an internal benchmark naively fails the same way: manual inspection is doubly biased (by your own taste and by the few samples you look at), and automated metrics can be inconsistent (a CLIP-score ranking of 8 models flipped across datasets with tiny between-model variation), so a metric is only useful once you understand what it measures, match it to the use case, and run several. The constructive answer reframes "state of the art" as a quality–efficiency Pareto front: quality is driven by compute (the same 26,000-battle image eval cost 20 days / $5,000 / ~400 marathons of energy on a slow model versus 7 hours / $265 on a fast compressed one), so plotting a quality score against latency or cost surfaces 3–4 co-equal SOTA models clustered tightly in quality but varying up to ~20x in efficiency — and tends to surface small specialized models rather than the largest foundation model. This sharpens the wiki's existing "read a benchmark number with its measurement conditions" lesson (the audio close-talk-vs-distant-mic case) and the private-benchmark and narrow-slice concepts into a concrete model-picking procedure: evaluate on many samples, match user use-case conditions, use multiple benchmarks, and weigh efficiency, not only quality.

Code-generation evaluation needs the same widening. Sonar's Prasenjit Sarkar argues that functional-correctness leaderboards (HumanEval, MBPP, SWE-bench pass rates of 82-84%) measure only whether code passes tests and hide the engineering dimensions that decide enterprise readiness — maintainability, security, complexity, bug density, and code bloat. Running an open-source dataset of 4,444+ Java assignments through 53+ models and analyzing the output with static analysis exposed that more capable models often pass more tests while emitting far more code: GPT-4o produced under 250,000 lines for the set, GPT-5.4 ~1.2 million, and Claude Sonnet 4.6 627,000 with the highest security-issue rate (300 per million LOC), while the pass-rate leader (Gemini 3.1 Pro High, 84.17%) stayed concise (~307,000 LOC). The durable eval lesson is that an 80%+ pass rate is necessary but not sufficient: more lines means more bugs and a larger attack surface, root causes are structural (mixed-quality/insecure training data, probabilistic output, missing codebase context), and as RL fixes known issue classes the remaining bugs get "finer" and harder for a human reviewer to catch — so generated code should be scored on quality axes, not just correctness.

Some questions have no empirically correct answer to evaluate against, and Upside's Alex Bauer offers a runtime pattern for them that doubles as an evaluation stance: rather than trust a single pass, spin up a jury of independent analysts who each return an evidence-cited opinion and let a consensus judge weigh their *reasoning quality* — not treat any as fact — synthesizing the final answer and escalating (expanding the jury) when consensus is weak. This mirrors LLM-as-judge and self-consistency but applied to inherently subjective outputs (multi-touch attribution credit), and it complements the wiki's judge-calibration concepts: when there is no ground truth to score against, the trustworthiness of the result comes from independent replication plus a judge that reasons about reasoning, not from a golden label.

The same independence requirement applies to the emerging "loops" primitive. Alex Bauer's jury and Volkov's routing table converge on one rule: a builder that grades its own work has not removed review, it has hidden it. Autonomous agent loops (scheduled agents that discover a task, plan, execute, and verify themselves against the goal) are attractive because they retry until they pass — but self-grading is the "wrote the exam, took it, scored myself" failure, so the verification signal must come from a separated writer/verifier or an independent check, not from the same agent's self-assessment. This is why Volkov's evaluation guidance (verify with traces, evals, and shadow mode; separate the writer from the reviewer/tester) sits alongside the routing table: capability drift shifts *where* proof belongs but never removes the requirement for an independent verifier.

Witan Labs' spreadsheet work grounds two pragmatic eval lessons. First, prefer deterministic evaluation over LLM-as-judge where possible: they started judge-only ("sometimes the only option"), but the confound is that when a score changes "you can't tell if it's because the agent changed something or the evaluator changed what it outputs" — so a judge can't separate agent regressions from judge drift, whereas a deterministic check (a golden spreadsheet used as a black box: same inputs → compare outputs against the model's spreadsheet) is "sometimes more trustworthy." Getting evaluation right was what actually let them tell whether alternative representations (CSV, SQL) were any good. Second, treat evaluation as a debugging surface, not just a scoring gate: infrastructure bugs "many times end up looking like reasoning failures" — a broken tool the model retries around, or a wrong example in the prompt the model follows faithfully — so "there's a lot of juice to get out of just really looking at those traces" to separate genuine model limits from fixable plumbing.

Mixedbread contributes a retrieval-specific evaluation frame that isolates the retrieval variable from the reasoning variable: the *Oracle gap*. Score a model when handed the correct documents (the reasoning ceiling — 93% on BrowseComp Plus, 64% on FinanceQA Pro) versus over the real noisy corpus (single digits for a default-tool agent), and the delta attributes the failure to retrieval rather than reasoning, telling you whether to spend on a better search tool or a better answer model. Their training loop also shows a composite retrieval eval used as a reward signal — a hard metric (NDCG over the final ranked list) plus an LLM rubric judge (is the result relevant, are all chunks relevant, is the ranking plausible) plus a trajectory judge (is the query a natural sentence, is the exploration depth right) — a reminder that retrieval quality decomposes into output-ranking and search-behavior signals, not a single answer-correctness score.

Andrew Dumit (Watershed) sharpens what "correct" even means when there is no verifiable ground truth. In sustainability "the answer is really only justified in so far as the process that produced that answer is correct," because there are many ways to reach a right answer for the wrong reasons and many defensible answers experts disagree on — a 2020 study gave six experts identical data on the same bottle of wine and their carbon numbers "varied by up to 50%." So validating an output artifact against a reference is a weak signal, and the durable eval move is to verify the *process*. He cites precedent from the 2026 "Open Proof Corpus": a gap between the correct final answer and the correct proof exists *even in math where the answer is fully verifiable*, and it is worse when the answer isn't — agents reward-hack (the Erdős problems produce "pages of errors leading nowhere") and the "Beyond Correctness" authors warn this "can pose significant risk for critical applications." Watershed's answer builds process-verification into the harness (a typed SDK plus an owned deterministic execution that lints, conflict-detects, runs, and validates typed artifacts), so that even the ~8% of eval tasks where the agent's answer differs from the reference — which may itself be one point in a valid range of expert judgments — remain "valid, traceable, and replayable." This is the no-ground-truth complement to Alex Bauer's jury framing: where a jury weighs several independent opinions for a subjective answer, Watershed instead guarantees and inspects the *procedure* when the answer itself can't be pinned down.

Angel Ortmann Lee (Duolingo) adds a warning about where the eval data itself comes from: when humans are your labeling loop, automation bias corrupts the labels. Duolingo found expert proctors (>90% calibration) confirmed *fabricated* cheating alerts ~50% of the time, so a frictionless review UI silently logs rubber stamps as ground truth — the model then looks more accurate than it is and drifts toward overconfidence (the vicious cycle). Two durable eval lessons follow. First, treat every human-AI interaction as an already-existing label, but design the interaction to make those labels *honest*: force independent judgment, and split conflated yes/no questions (e.g. "was the detection correct?" vs "is it a violation?") so a reviewer isn't forced to give a wrong answer to protect the other. Second, **capture the diff, not the click** — a human who clicks "accept" then silently edits the output records a false positive unless the edit is measured; most systems log only the binary decision, so the real correction signal is lost. This is the label-quality complement to the independence rule above (self-grading loops hide review): even with a human in the loop, the eval signal is only as trustworthy as the interaction that produced it, and success metrics plus the data you need should be defined *before* building so the interaction is shaped to produce them.

Rishi Desai (Abundant AI) extends the benchmark frontier to project-scale, billion-token work and shows how verification design breaks at that horizon. SWE-Marathon asks whether coding agents "can stay coherent over a billion token budget" — building whole products/libraries/compilers from scratch (Slack, a JAX→PyTorch rewrite, a C compiler in Rust) — across 20 tasks in four families, extending the HumanEval → SWE-bench → Terminal-bench lineage. Two eval lessons dominate. First, the best config (Claude Opus 4.8 + Claude Code) resolves only 26% at an average of 31M tokens/trial (longest rollout 877M), and the scaffold matters as much as the model (a cheaper Codex config gets 12%), so a headline resolution rate is a model-plus-harness number, not a model number. Second, the horizon changes the threat model for verification: "in a short benchmark, a weak test could just be considered as noise, but in a multi-hour environment, a weak verifier becomes an attack surface" — an agent with hours, a filesystem, network, and a reward signal will "spend hours probing the verifier instead of actually doing the intended engineering work." The defense is independence, not a single stronger test: hidden tests, reference-parity checks, computer-use-agent (CUA) checks for full-stack tasks, and anti-cheat tests (`strace` caught a "C compiler in Rust" task that shelled out to GCC), hardened in a QA loop until tasks are "solvable but hard to game." The bar he sets is measurable: across 1,400 rollouts, 12.8% showed suspicious shortcuts and 9% a clear verifier bypass, but *zero* earned reward through an exploit — "that should be the bar for long-horizon evals." This sharpens the wiki's reward-hacking concepts (seal-the-environment, detect-reward-hacking, kernel benchmark gaming) into a horizon-specific rule: the longer the run, the more the verifier itself is what the agent optimizes against. It also anchors the CUA-verifier point — for full-stack product clones "correctness is not just an API contract; it's whether the user can actually complete the product's intended workflow," which is the benchmark-side application of autonomous browser verification.

Soheil Feizi (RELAI) extends evaluation from a pre-deployment gate into a continuous, regression-controlled learning loop, and names the gap production teams fall into: at dev time you have a benchmark and evaluators, but in production you have only logs plus (automatic or human-expert) feedback, and "production logs are not learning environments" — a log-plus-feedback pair is a single observation, not something you can rerun or grade. His [verifiable continual learning](../concepts/verifiable-continual-learning-prove-each-fix-helps-and-breaks-nothing.md) reframes every improvement as an eval problem: an executable test (the failure lifted into a [replayable learning environment](../concepts/ground-agent-simulation-and-evaluation-in-production-logs.md) with inferred tools, synthetic users, and evaluators), a measured before/after delta, and a regression test — so "every fix is proven to help and proven to break nothing that already worked." Two of his four principles are durable eval discipline the topic hadn't stated: [route the fix to the right layer with the smallest durable change](../concepts/route-agent-repairs-to-the-right-layer-smallest-durable-change.md) (a single failure may trace to stale memory, an unoptimized prompt, a tool that doesn't normalize policy, a missing workflow gate, or a weak model — and "vibe-based" harness edits and unverified memory writes are exactly the untestable fixes this topic warns against), and [make regression-aware optimization part of the loop](../concepts/make-regression-aware-optimization-part-of-the-continual-learning-loop.md) — treat "don't forget the past" as an in-loop constraint rather than a post-hoc rerun of the suite, and keep it sub-linear in the number of accumulated environments. This is the continual-improvement generalization of the wiki's replay-then-check-the-regression-set and observability-to-offline-eval threads: the frontier is not a static benchmark score but a lifelong loop with online regression control.

Raphael Kalandadze (Wandero AI) gives the everyday production-monitoring version of "evaluation is continuous," and the reason offline tests aren't enough: for a non-deterministic conversational agent, "green CI means nothing" and "finished doesn't mean helpful" (the agent completed the itinerary but mispriced it — "technically successful but still failing the task"), so the eval has to run over live traffic. His answer is to [score every production conversation to judge agent health](../concepts/score-every-production-conversation-to-judge-agent-health.md): an LLM session-analyzer scores *every* session rather than a sampled few (spending real tokens on many state agents), then connects the dots across sessions into a health dashboard — average score, success rate, trends, sentiment, tool-call analytics, rejection reasons, and per-insight root cause and sessions-affected. This is the whole-conversation, whole-fleet counterpart to Arize's span/trajectory/session scope axis and to online trace scoring: run it weekly as the zoom-out health read, and pair it with a faster per-incident loop for fixes. The distinction he draws — a specific-bug fast loop vs a high-level health loop — is itself an eval-scope decision about *cadence*, not just span.

Dominik Tornow (Resonate) turns simulation from a testing surface into a design-and-debugging surface for agents building concurrent/distributed systems. To make an agent design a correct algorithm rather than emit happy-path code, Resonate has it [build a simulated implementation as executable design](../concepts/use-deterministic-simulation-as-executable-design-for-agents.md) — a deterministic, repeatable, inspectable Python simulator of the target's primitives (a versioned KV store that injects legal-but-inconvenient stale reads and enforces optimistic concurrency) so failures under partial order and partial failure are discovered before production. The eval-specific contribution is the [forbidden-fruit trace](../concepts/expose-forbidden-fruit-facts-in-simulation-for-agent-debugging.md): the simulator records facts the real platform hides (whether a read was fresh or stale, and the latest value the algorithm missed) that the *algorithm* may not depend on but the *agent* may use to explain why an invariant broke. This is the design-time analogue of Feizi's replayable learning environments and of exposing observability as agent-readable feedback — the point is not just that a run failed, but a reproducible trace that makes cause and effect visible so the agent repairs the algorithm against it.

RL Nabors (Arize) turns evaluation into the mechanism for right-sizing a model, and surfaces two eval hazards along the way. Her workflow makes model *selection* an eval problem: prototype a feature on the largest model to prove it is possible, export its behavior as a golden dataset of input/output pairs, then run a capability eval that benchmarks candidate small models against that baseline in a mixed scoring harness (deterministic JSON validity and reference-structure checks, LLM-as-judge factual consistency, length compliance, and P50/P95 latency) — the score is what tells you a Llama 3.2 3B beats a slower Gemma 4 and a peer recommendation, rather than intuition. The first hazard is that an LLM judge carries [self-preference and family bias](../concepts/llm-judges-show-self-preference-and-family-bias.md): Claude judging Claude-vs-Llama graded the outsider too strictly, so an apparent factual-consistency gap was judge bias that only reading the raw responses exposed — a concrete instance of the topic's warning that judges are imperfect substitutes with their own biases. The second is that deterministic criteria should not be judged at all: reference-count and length checks belong in [harness post-processing](../concepts/close-the-small-model-gap-with-prompt-variants-and-harness-post-processing.md), which (with one-variable-per-variant prompt testing to find that few-shot helps a small model where strict rules hurt it) closed her gap to 100% structural validity and beat the baseline on latency. Locking those gains in needs regression evals run like CI/CD so a later prompt tweak or model upgrade can't silently blow up summaries — "how you keep your CTO from blowing away your agentic experience by accident one morning."

Tisha Chawla and Susheem Koul (Microsoft) supply the reproducibility substrate that makes those production-log learning loops runnable in the first place. Their starting point is that a non-deterministic agent failure is gone the moment it happens — [LLM inference is non-deterministic even at temperature zero](../concepts/llm-inference-is-non-deterministic-even-at-temperature-zero.md), so re-running the same prompt succeeds every time and the costly run can't be recovered. The fix is to stop chasing bitwise determinism and instead [record and replay agent runs at node boundaries](../concepts/record-and-replay-agent-runs-at-node-boundaries.md) — capture each node's semantic input/output plus session variables as a frozen trace so a failure can be re-entered and stepped through with zero model calls. That trace then closes the eval loop: [turn recorded agent traces into free replay test cases](../concepts/turn-recorded-agent-traces-into-free-replay-test-cases.md) by stubbing every node except the one you changed, running it live, and asserting on its output — the model is never called, so the test is deterministic, rerunnable, and free. This is the mechanism behind the wiki's replay-then-check-the-regression-set and replayable-learning-environment threads, and it explicitly splits deterministic testing (guardrails, tools, stubbed LLM) from behavioral testing (tone and trajectory, where LLM-as-judge belongs).

Benedikt Sanftl and Burak (Mutagent) make the eval suite the load-bearing artifact of agent construction with eval-driven development (EDD), the TDD-equivalent that supplies an agent's termination gate — building an agent then becomes [automating the agent-building loop with an agentic AI engineer](../concepts/automate-the-agent-building-loop-with-an-agentic-ai-engineer.md) around that gate. The eval suite has two parts — evals (metrics/criteria) and datasets (cases) — and its complete form is "a product of discovery": you cannot pre-guess it, so seed it with domain experts or historical/synthesized data and let production failures and user feedback accumulate the edge-case items, the agent counterpart to the "evals only cover known failures" caution above. Agent evaluation runs over the trajectory (was the context complete end-to-end, and does every tool output chain-check, since one wrong tool output becomes the wrong final output), and the harness itself is an optimization vector to evaluate alongside the prompt rather than in isolation. Two usefulness rules reinforce this topic's judge threads: prefer binary/criteria evals over score-based ones unless the rubric is very well defined, because a failing criterion is an actionable call to action while a bare score doesn't tell you what to fix; and calibrate the LLM-as-judge to control run-to-run variance, since a non-deterministic judge that scores the same problem differently each run makes it impossible to conclusively say an improved agent beats its baseline. The diagnosis half adds a scale-aware method — [diagnose agent failures with code-checkable indicators and sampling](../concepts/diagnose-agent-failures-with-code-checkable-indicators-and-sampling.md) — that turns deep-read root-cause analysis into cheap ongoing triage once each failure mode has a code-checkable indicator (a content pattern or tool-call sequence), because at millions of traces "reading all of these actually costs more than the execution itself"; the loop then generates new evals to detect the problem and remedies to fix it.

Sonam Pankaj (StarlightSearch) sharpens where these loops break down at the last mile: even when observability captures every trace and the eval suite judges pass/fail, that verdict is never reflected back into the agent's context, skills, or actions, so [the eval signal dies in the dashboard](../concepts/close-the-eval-to-action-loop-so-signal-survives-the-dashboard.md) and the agent starts every run from a blank slate. The offline eval-and-observability loops in this topic then depend on an engineer reading dashboards and hand-editing prompts; her proposed complement is a runtime layer that turns each run's outcome into an automatic retrieval signal — a per-memory utility score that rises on pass and falls on fail — so the agent adapts while executing rather than only between manual tuning cycles. It also supplies the concrete outcome label those loops assume: the pass/fail judgment is only useful once something consumes it, and here it becomes the credit signal that re-ranks which memory the next run sees.

Alfonso Graziano (Nearform) makes the golden dataset the load-bearing artifact of *both* an offline and a live-data improvement loop, and adds two operational moves the topic hadn't stated. Offline, he points a coding agent at a product agent and its golden-dataset scorers and [optimizes it as a branch-per-hypothesis hill-climb](../concepts/optimize-an-agent-with-a-branch-per-hypothesis-coding-agent-loop.md): each iteration is a fresh git branch testing one failure class, kept when evals improve and rolled back when they regress, with a cross-run memory file and a readable change log — and a hard guardrail forbids the coding agent from editing the golden dataset or scorers just to pass (18%→83% on a toy agent, 67%→86% and +10% on production agents, "without actually cheating"). This is the eval-as-termination-gate discipline of Mutagent's EDD made concrete as a reversible search whose integrity depends on the scorers being off-limits. Live, he closes the loop the topic keeps circling: production traces plus user thumbs and SME annotations are clustered into failure modes, root-caused and triaged with an SME, and — the durable step — every *validated* cluster is [promoted back into the golden dataset and scorers](../concepts/promote-validated-live-trace-failure-clusters-into-the-golden-dataset.md) so the fix becomes a permanent regression test ("self-healing evals"), run ~once per sprint. Where Feizi's replayable environments and Chawla/Koul's node-boundary replay make a single failure re-runnable, Graziano's contribution is the promotion policy — the eval set is *grown* from triaged production failures, not just seeded once — which is the eval-side of this topic's observability-to-offline-eval thread.

Isadora Martin-Dye supplies the last-line-of-defense argument for why a probabilistic system still needs a deterministic gate on its *output*: [gate generated output with a deterministic post-generation veto](../concepts/gate-generated-output-with-a-deterministic-veto.md). Her framing separates the prompt (an instruction the model "usually listens" to but that "will eventually lose") from a check that "reads what actually came out and decides whether to allow it to leave your business" — "instructions are probabilistic, permission is deterministic." The trigger is stakes-calibrated: "usually" is fine when a wrong answer is a slightly off-brand sentence, "not fine when the model is confidently inventing a fact that a real person is about to act on — a date, a price, a policy, a promise." She splits the veto into a *soft flag* (an "honesty inspector" that flags a hedged or non-answer) and a *hard reject* (a "numbers guard" that rejects a figure never given, then checks specifics against an allow list so an offered-but-booked date "doesn't ship"), and justifies building it by cost asymmetry — a false positive is a double-checked response, a false negative is "a hallucinated number or a privacy violation that ships to a client." Notably she chooses a deterministic pattern-match ("never gets it wrong on the patterns it covers") over a small probabilistic classifier that would catch more edge cases but "sometimes gets it wrong" — an explicit determinism-over-coverage trade-off. This is the outbound-content sibling of the topic's completion-gate and separate-verifier threads: the check runs at generation time on user-facing text, and it is deterministic precisely because prevention-by-prompt is not.

Vivek Muppalla (Hippocratic AI) adds the statistical floor under all of this: [size eval suites to the error rate the consequence demands](../concepts/size-eval-suites-to-the-error-rate-the-consequence-demands.md). Two numbers do the work. First, translate the accuracy percentage into people — at 10,000 outbound clinical calls a day, "most agentic systems would claim 80%, 90% accuracy… for us, even the 99% is pretty bad," because 1% means 100 patients a day get the wrong appointment type and some miss a critical one. Second, the detection arithmetic sets suite size: catching a 1% error rate with 99% confidence takes about 450 tests, and observing it ten times takes about 1,900 — so a twenty-case suite carries no information about a 1% failure mode, and a green suite of that size is not evidence. Because synthetic data alone "can't purely" reach that scale of accuracy, the eval operation is standing and human: 7,000+ trained clinicians have run roughly 700,000-800,000 conversations as continuous evaluation alongside synthetic cases. His grading choice is the other transferable move — outputs are scored on the rubric already used for human clinicians (correctness, no harm, minor harm, severe harm, death) rather than a correctness bit, which both weights failures by damage and makes the AI-vs-human comparison legible (99.89% no-harm against ~81% for humans on the same scale). And when a load-bearing quality dimension has no benchmark — empathy, in their case — building and publishing one (HEART) is part of the engineering, the same reason they refused a generic voice stack that no common benchmark measured on lab-results checks or IVR navigation.

Jared Joselowitz (Ufonia) starts one layer earlier than any of these and asks what evaluation is *for* when the usual release loop is unavailable. His three broken safety nets — you cannot A/B test ("randomizing patients into a worse variant is unethical and often illegal"), you cannot roll back a spoken call ("once Dora says it, it's been said"), and a vendor benchmark "is not a defense at a post incident review" — force the discipline this topic usually treats as optional: [replace ship-and-rollback with hazard-first simulation when errors are irreversible](../concepts/replace-ship-and-rollback-with-hazard-first-simulation.md). The eval set is derived from a clinician-written hazard list rather than from features or from production traffic, rare-but-dangerous cases are *manufactured* rather than awaited, simulation is explicitly the inner loop that "only earns the right to actually try carefully," and autonomy is granted in proportion to accumulated evidence. The deliverable is a trace: "every call, every data set, every pinned prompt, every judge verdict traces back to the exact hazard that it addresses… you don't ship the model, you ship the evidence." His second contribution tightens a gap this topic's simulation and judge threads leave open on opposite sides — an LLM-simulated eval loop contains *two* models, so [validate the simulated user and the judge before trusting a simulation](../concepts/validate-the-simulated-user-and-the-judge.md). The synthetic patient passes a cheap script-adherence filter (which "helped us filter out a lot of maybe weaker models") and then a blind human realism study in which real patients picked the *simulated* patient as more realistic in three of four sets, with the finding that "there is no single realistic patient" pushing toward persona diversity rather than one canonical user; the judge is validated against 10 clinicians from 10 specialties on 240 labeled cases, reaching F1 0.96 (Gemini 2.5 Pro) and — the number they actually optimize — near-perfect sensitivity, because "you would rather overcall hazards that aren't there than undercall hazards that are there." That preference is then made mechanical rather than aspirational: [optimize prompts against an asymmetric cost matrix, not flat accuracy](../concepts/optimize-prompts-against-an-asymmetric-cost-matrix.md). Given prompt brittleness ("formatting changes alone have been seen to swing benchmarks by 76 percentage points"), hand-tuning is replaced by GEPA, and the metric handed to it is a clinician-defined cost matrix where a missed red flag is catastrophic and an over-called one is "mildly annoying" — which relocates the engineering into the data and the metric ("you define the actual metric along with the clinicians") and lets a domain expert re-target the system by recompiling the prompt. This is the same instinct as Muppalla's harm-scale grading, arrived at from the optimizer side: the scalar you optimize should already contain the damage function.

## Key Concepts

- [Replace Ship-and-Rollback With Hazard-First Simulation When Errors Are Irreversible](../concepts/replace-ship-and-rollback-with-hazard-first-simulation.md) - when a bad output cannot be retracted, percentage rollouts and dashboards arrive after the harm, so the eval set comes from an enumerated hazard list and autonomy is earned stage by stage against evidence.
- [Validate the Simulated User and the Judge Before Trusting a Simulation](../concepts/validate-the-simulated-user-and-the-judge.md) - both halves of a simulated eval loop are models: validate the synthetic user for realism (script adherence, then a blind human study) and the judge against a multi-specialty expert panel before its verdicts gate a release.
- [Optimize Prompts Against an Asymmetric Cost Matrix, Not Flat Accuracy](../concepts/optimize-prompts-against-an-asymmetric-cost-matrix.md) - prompt brittleness makes hand-tuning unreproducible, and an optimizer amplifies its objective, so the metric should be a domain-expert cost matrix encoding the real gap between a missed and an over-called error.
- [Gate Generated Output With a Deterministic Post-Generation Veto](../concepts/gate-generated-output-with-a-deterministic-veto.md) - a deterministic layer reads the actual output and checks its specifics against reality before it ships, because prompt instructions are probabilistic and "eventually lose"; split into a soft flag (honesty inspector) and a hard reject (numbers/allow-list guard), with an explicit determinism-over-coverage trade-off.
- [Optimize an Agent With a Branch-per-Hypothesis Coding-Agent Loop](../concepts/optimize-an-agent-with-a-branch-per-hypothesis-coding-agent-loop.md) - a coding agent hill-climbs a product agent's golden-dataset evals one hypothesis per git branch (keep on improvement, roll back on regression), with a cross-run memory file, a change log, and an anti-gaming guardrail against editing the scorers.
- [Tune a Tool Router With a K-Sweep and Guard Its Failure Modes](../concepts/tune-a-tool-router-with-k-sweep-and-guard-its-failure-modes.md) - evaluate a semantic tool router on accuracy, TTFT, input tokens, and cost per 1,000 calls over tool pools scaled to ~1,000 tools, then sweep K at 3/5/10 for the smallest K meeting the target.
- [Promote Validated Live-Trace Failure Clusters Into the Golden Dataset](../concepts/promote-validated-live-trace-failure-clusters-into-the-golden-dataset.md) - cluster and root-cause production traces (user thumbs + SME annotations), triage with an SME, and fold every validated failure back into the golden dataset and scorers as a permanent regression test ("self-healing evals").
- [Layer AI Application Metrics From Guardrail Compliance to System Health](../concepts/layer-ai-application-metrics-from-guardrail-compliance-to-system-health.md) - a four-tier application-metric ladder (guardrail compliance → response quality/faithfulness → domain metric → system health) that carries from offline eval into online monitoring with implicit indicators like human-override rate.
- [Automate the Agent-Building Loop With an Agentic AI Engineer](../concepts/automate-the-agent-building-loop-with-an-agentic-ai-engineer.md) - eval-driven development supplies an agent's termination gate; the eval suite is discovered from production failures, not pre-guessed, and drives the offline/online build loop.
- [Diagnose Agent Failures With Code-Checkable Indicators and Sampling](../concepts/diagnose-agent-failures-with-code-checkable-indicators-and-sampling.md) - at scale reading every trace costs more than execution, so cluster failures by root cause, distill a content/tool-call indicator per failure mode, and triage by representative sampling, then generate detect-evals and remedies.
- [Right-size models with prototype-big, deploy-small](../concepts/right-size-models-with-prototype-big-deploy-small.md) - make model selection an eval: prove the task on the largest model, freeze a golden dataset of success criteria, and benchmark small-to-large in a mixed scoring harness to pick the SAGE model.
- [LLM judges show self-preference and family bias](../concepts/llm-judges-show-self-preference-and-family-bias.md) - a judge favors its own model family and grades outsiders too strictly, so a subjective-metric gap can be judge bias you only catch by reading the raw responses.
- [Close the small-model gap with prompt variants and harness post-processing](../concepts/close-the-small-model-gap-with-prompt-variants-and-harness-post-processing.md) - test prompt variants one variable at a time and move deterministic checks (structure, length) into post-processing rather than trusting the model or a judge to enforce them.
- [Record and Replay Agent Runs at Node Boundaries](../concepts/record-and-replay-agent-runs-at-node-boundaries.md) - record each node's semantic I/O as a frozen trace so a non-reproducible production failure can be re-entered and debugged with zero model calls; durability keeps the loop alive, only replay makes it debuggable.
- [Turn Recorded Agent Traces Into Free Replay Test Cases](../concepts/turn-recorded-agent-traces-into-free-replay-test-cases.md) - reuse a recorded trace as a regression test by stubbing every node except the one under change, running it live, and asserting on output; deterministic testing stubs the LLM, behavioral testing uses LLM-as-judge.
- [Score Every Production Conversation to Judge Agent Health](../concepts/score-every-production-conversation-to-judge-agent-health.md) - LLM-score every live session (not a sample) into a health dashboard that connects the dots into high-level patterns, because green CI and finished ≠ helpful for a non-deterministic agent.
- [Verifiable Continual Learning: Prove Each Agent Fix Helps and Breaks Nothing](../concepts/verifiable-continual-learning-prove-each-fix-helps-and-breaks-nothing.md) - improve an agent from production experience via an executable test, a measured before/after delta, and a regression test, so every fix is proven to help and to break nothing already working.
- [Route Agent Repairs to the Right Layer With the Smallest Durable Change](../concepts/route-agent-repairs-to-the-right-layer-smallest-durable-change.md) - one failure may trace to memory, prompt, tool, workflow, or model; diagnose the root cause and pick the smallest durable change at the right layer instead of defaulting to fine-tuning.
- [Make Regression-Aware Optimization Part of the Continual-Learning Loop](../concepts/make-regression-aware-optimization-part-of-the-continual-learning-loop.md) - fix a new failure subject to no regression on past learning environments, treating "don't forget" as an in-loop constraint kept sub-linear in the number of accumulated environments.
- [Evaluate Coding Agents on Project-Scale, Billion-Token Tasks](../concepts/evaluate-coding-agents-on-project-scale-billion-token-tasks.md) - measure whole-project ownership (build Slack, JAX→PyTorch, C compiler in Rust) at multi-hour, hundreds-of-millions-of-tokens horizons; best agent resolves only 26% and the scaffold matters as much as the model.
- [At Long Horizons a Weak Verifier Becomes an Attack Surface](../concepts/at-long-horizons-a-weak-verifier-becomes-an-attack-surface.md) - a multi-hour agent with a filesystem, network, and reward signal will probe the verifier, so use independent multi-channel checks (hidden tests, reference parity, CUA, `strace` anti-cheat) and drive rewarded exploits to zero.
- [Use Deterministic Simulation as Executable Design for Agents](../concepts/use-deterministic-simulation-as-executable-design-for-agents.md) - a deterministic, repeatable, inspectable simulator of the target's primitives lets an agent discover a correct algorithm under partial order and partial failure before writing production code.
- [Expose Forbidden-Fruit Facts in Simulation for Agent Debugging](../concepts/expose-forbidden-fruit-facts-in-simulation-for-agent-debugging.md) - the simulator records facts the real platform hides (fresh/stale reads, the missed latest value) so the agent can explain the causal reason an invariant broke.
- [Treat Every Human-AI Interaction as a Training Label](../concepts/treat-every-human-ai-interaction-as-a-training-label.md) - the interaction loop is a data flywheel; design it to produce honest labels and capture the diff (not just accept/reject), or rubber stamps get logged as ground truth.
- [Automation Bias Turns Human-in-the-Loop Into a Rubber Stamp](../concepts/automation-bias-turns-human-in-the-loop-into-a-rubber-stamp.md) - human labelers deferring to AI signals corrupt the eval data; a coin-flip confirmation rate on fabricated alerts is the tell.
- [Run a jury of analysts and a consensus judge for no-ground-truth questions](../concepts/run-a-jury-of-analysts-and-a-consensus-judge-for-no-ground-truth-questions.md) - for subjective questions with no objective answer, weigh several independent evidence-cited opinions with a consensus judge rather than trusting one pass.
- [Measure Generated Code Quality Beyond Pass Rate](../concepts/measure-generated-code-quality-beyond-pass-rate.md) - functional-correctness leaderboards hide maintainability, security, complexity, and code bloat; static-analysis benchmarking shows more capable models often pass more tests while emitting far more (and riskier) code.
- [Spec-Driven Agent Validation Goes Beyond the Test Set](../concepts/spec-driven-agent-validation-goes-beyond-the-test-set.md) - an agent spec adds explicit rules, ontologies, rights/roles, and robustness envelopes on top of input/output examples, kept implementation-independent so it survives a model swap and drives both security and robustness testing.
- [A Bigger Model Is Not Automatically a Safer or Better Agent](../concepts/a-bigger-model-is-not-automatically-a-safer-or-better-agent.md) - a smart-vs-safe tradeoff: capable models decode poem jailbreaks, broad remit widens attack and test surface, and cost/latency rise, so aim for good-enough-to-perform but not capable of arbitrary harm.
- [Self-Verifying Agent Loops Hide Review Rather Than Remove It](../concepts/self-verifying-agent-loops-hide-review-rather-than-remove-it.md) - a self-grading loop hasn't removed review, only hidden it; verification must come from a separated verifier or independent check, not the same agent's self-assessment.
- [Evaluate Agent Retrieval by Trajectory, Not Task Success](../concepts/evaluate-agent-retrieval-by-trajectory-not-task-success.md) - score file/line/symbol precision and recall along the agent's path (ContextBench), not solve/no-solve, to measure retrieval quality and expose wasted reads.
- [Verify the Process, Not Just the Answer, in Judgment-Heavy Domains](../concepts/verify-the-process-not-just-the-answer-in-judgment-heavy-domains.md) - with no verifiable ground truth (experts vary up to 50% on the same data), the answer is only justified by a correct process, so validating the process is the main eval lever.
- [Run Agentic Coding Evals as an Infrastructure-Reliability Problem](../concepts/run-agentic-coding-evals-as-an-infrastructure-problem.md) - large-scale coding-agent eval is dominated by infra reliability: minimalistic agent + strong infra, a retry policy separating model vs infra errors, noise control, parameter-drift checks, and harness validation before trusting numbers.
- [Seal Eval Environments Against Agents That Read the Leaked Answer](../concepts/seal-eval-environments-against-answer-leaking-agents.md) - real-world SWE benchmarks leak the ground-truth fix into the sandbox and the web, so agents escalate (git history → web fetch → curl) to read it; seal every channel and post-process trajectories.
- [Verify Spec Adherence With Executable, Readable BDD Scenarios](../concepts/verify-spec-adherence-with-executable-readable-bdd-scenarios.md) - executable, human-readable Cucumber scenarios linked to PRDs and critical journeys make per-feature verification reviewable, closing the gap a markdown spec leaves open.
- [Design Benchmarks as Forward Bets That Shape the Field](../concepts/design-benchmarks-as-forward-bets-that-shape-the-field.md) - influential benchmarks pose a thesis on where the field is going and spawn research roadmaps (Terminal Bench's CLI bet, SWE-bench's family) rather than snapshotting past progress.
- [Judge Benchmark Quality by Task Quality, Diversity, Headroom, and Methodology](../concepts/judge-benchmark-quality-by-task-diversity-headroom-and-methodology.md) - the "science" checklist for a sound measuring stick: rigorous task quality, intentional distributional diversity, real model headroom, and a methodology that measures the axes beyond accuracy.
- [Select State of the Art on a Quality-Efficiency Pareto Front](../concepts/select-state-of-the-art-on-a-quality-efficiency-pareto-front.md) - there is no single SOTA model; plot quality against latency or cost and treat the 3–4 models on the front as co-equal, since quality is clustered while efficiency varies up to ~20x.
- [Don't Trust a Single Leaderboard for Model Selection](../concepts/do-not-trust-a-single-leaderboard-for-model-selection.md) - boards disagree, run on small samples, and report win rates where most models lose ≥40% of battles, so the top rank is the wrong model for ~40% of use cases; look at multiple boards and your own traffic.
- [Task Quality Drives a 5x RL Training Uplift](../concepts/task-quality-drives-rl-training-uplift.md) - a controlled run (model/compute/task-count fixed) showed high-quality agentic tasks give ~5x the RL uplift of low-quality ones, making task curation a measurable training lever.
- [Accept Agentic Training Tasks by Clean Failures, Not Ambiguous Specs](../concepts/accept-agentic-tasks-by-clean-failures-not-ambiguous-specs.md) - keep tasks whose failures are clean (genuine difficulty) and reject those that fail on spec-test mismatch or missing context, because ambiguous specs produce noise that masks model improvement.
- [Treat Researcher UX as a First-Class Benchmark Feature](../concepts/treat-researcher-ux-as-a-first-class-benchmark-feature.md) - a benchmark's core users are other builders, so adoption depends on a standardized harness that's easy to run, extend, and reuse for RL (HELM, Harbor).
- [Push Agent Benchmarks on Environment Complexity, Autonomy Horizon, and Output Complexity](../concepts/push-agent-benchmarks-on-environment-autonomy-and-output-complexity.md) - the three under-covered axes for next-generation agent benchmarks, where today's sets capture only a fraction of real deployment.
- [Portfolio-Allocate Eval Failures With a Triage Agent](../concepts/portfolio-allocate-eval-failures-with-a-triage-agent.md) - read failures, not the score: send a second agent through the failure traces to categorize causes and find the small levers, sorting fixes into obvious-bug / nuance-tuning / overfitting zones.
- [Tune Coding-Agent Harnesses Per Model Family](../concepts/tune-coding-agent-harnesses-per-model-family.md) - a low score is usually a harness problem (CPU/memory/timeouts/thinking + model-family-specific prompts), not a model problem, and prompt techniques don't transfer across Anthropic/Codex/Gemini.
- [Reconcile Specialist Agent Outputs With a Feedback-Weighted Judge](../concepts/reconcile-specialist-agent-outputs-with-a-feedback-weighted-judge.md) - a judge node becomes a trustworthy quality gate by weighting suggestions against PR history, guidelines, and accept/reject feedback rather than a fixed rubric.
- [Catalog Eval Signal Sources Across Judge, Human, Golden, Deterministic, and Business](../concepts/catalog-eval-signal-sources-judge-human-golden-deterministic-business.md) - eval signal has five flavors with different costs and trust bases; prefer the cheapest source that gives signal, and use golden datasets to tune the judge.
