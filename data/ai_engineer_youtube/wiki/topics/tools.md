# Tools

## Overview

Personal-agent tools need visible orchestration controls. Users should be able to see and collapse tool calls, stop runs, inspect scheduled messages, switch workspaces, attach exact context, and adjust the active agent's capabilities without relying on generic chat commands or hidden execution state. For read-only observers, the tool surface should make source mutability explicit: source connectors can feed an analysis workspace and reviewable outputs without granting write-back authority.

Agent tools are most useful when their execution surface is paired with clear context about when and how to use them. MCP can expose service-backed integrations and remote actions, while skills can package the workflow guidance, domain instructions, references, and scripts that help an agent choose and use those integrations correctly. Visual automation tools can expose service nodes such as Gmail or calendar actions directly as agent tools, but the tool names and descriptions become part of the prompt surface and need the same care as any other instruction. Tool loops also need a strict runtime contract: when a model requests a function call, the client should validate that the tool exists, execute it, return the structured result, and continue only until final text. Tool design should also narrow sensitive authority: if an agent needs to update a secret-bearing file, a purpose-built operation such as key existence and key write is safer than raw file reads that may send secrets through inference or logs. Skill-like command prompts can function as product surfaces: they are loaded only when invoked, can be updated server-side, and can encode advanced workflows that would otherwise require heavy UI and orchestration code. API-focused skills should avoid embedding every volatile detail; stable guidance plus links to current Markdown docs gives agents a better chance of avoiding stale model names or outdated method signatures. Browser runtimes are becoming tool surfaces too: Chrome DevTools MCP can expose navigation, screenshots, console errors, network requests, Lighthouse, network throttling, and performance traces to coding agents, while DevTools AI can analyze selected runtime evidence and apply browser-tested CSS changes back to source. Canvas tools add a different surface: agents can use structured editor objects as prompt context and produce editor-native shapes, diagrams, and UI elements that remain inspectable and editable. Voice agents are another place where tool restraint matters: a realtime conversational agent should start with a small tool surface and delegate complex work through specialist handoffs that preserve conversation state. Realtime multimodal APIs can expose audio buffers, visual frames, transcriptions, and grounding tools over a single stateful stream, which makes tool timing and latency part of the UX. Pipecat adds a provider-abstraction layer for tools and model services: function schemas can be translated across LLM providers, and pipeline processors can expose transport, context aggregation, TTS text frames, recording, and observer events as explicit runtime tools. Some workflows should bypass LLM judgment entirely: deterministic scripts, explicit approval gates, and subworkflows are a better fit for known conditional actions, while the LLM handles judgment-heavy interpretation and connection-making. On edge devices, guidance must be especially compact: a skill registry can expose short descriptions first, then load full instructions, JavaScript, native intents, or API calls only when needed. Context packages can also be distributed through libraries and registries, which makes tool guidance reusable across projects but requires evaluation, provenance, dependency management, and context filtering before installation. A context engine can be exposed through MCP, CLI, API, dashboard, or messaging surfaces; the tool surface is the access path, while the engine still needs source relationships, personalization, permissions, and conflict handling behind it. Runtime and browser/editor APIs can turn an agent into a much more capable tool user, but direct code execution against a live app should be treated as executable authority with sandboxing, local/offline constraints, or explicit permission boundaries. Product teams should also treat APIs, CLIs, and MCP servers as first-class user interfaces when agents or bots are the callers; dashboards alone are insufficient for agent experience. That agent experience should be tested by autonomous task completion, not only API existence: machine-readable docs, authentication handoff, and APIs still fail when agents need humans to bridge ordinary operations. AI-product teams need internal behavior tools as well: prompt, context, model, tool, parameter, memory, and computer-use controls are more useful when they live in the product's real working context rather than an engineer-only sandbox. Agent-readable web conventions extend that rule to public sites: `llms.txt` can guide agents to relevant documentation, and WebMCP-style tools can expose intended app operations rather than forcing browser agents to infer buttons from screenshots, DOM text, and coordinates. Enterprise MCP tools add an authentication layer: Cross-App Access can reduce repeated OAuth consent by letting the identity provider mediate trust between an MCP client and server, but authorization scopes still need their own policy design. A gateway can generalize that control plane by placing auth, authorization, observability, secure connectivity, routing, deployment, and credential primitives between MCP clients and many servers, so domain teams focus on tool workflow while security teams bless one root of trust. At production scale, the tool catalog itself becomes an operational surface: defaults, output payloads, descriptions, and scope filters should be tuned so agents see enough capability to act without burning context or selecting hazardous tools. Very large APIs should use progressive discovery rather than eager endpoint dumps; CLIs, tool search, and typed code-mode surfaces each reduce upfront context in different ways. Code mode is especially useful when generated SDK types can make thousands of endpoints available through model-written code, but that moves safety work into capability-based sandboxes, network policy, secret isolation, observability, and API rate limits. The safest shape starts with no ambient authority and grants only the APIs or network access required for the current task. Cloudflare frames the two halves together: code mode collapsed its 2,600 API endpoints to ~1,000 tokens of tool interface, while Dynamic Workers ("eval++") run that generated code in a zero-authority isolate that only receives explicitly granted capabilities — reclaiming a branch of the tech tree that 30 years of "never use eval" advice had closed off. Treat generated code as an untrusted tool implementation: short-lived tool calls and transformations can run in isolate-style runtimes, while generated apps that install packages or start servers need container sandboxes with tenant isolation and cleanup. OAuth tool access should preserve the split between the agent client, the MCP resource server, and the authorization server: tool servers should verify tokens, while identity infrastructure handles login, consent, refresh, policy, and client identity. Enterprise MCP tools also need operational controls around the tool surface itself: dynamic client registration can create management noise, public endpoints need abuse and input controls, and background agents need enforceable scope propagation rather than prompt-level instructions about what they may do. Agent-facing tool systems also need verifiable client identity, transaction-scoped authorization for high-impact tools, and chain-of-custody when a tool server calls another API or agent.

Raw backend APIs are usually too low-level for direct agent exposure. A better production surface groups semantically related capabilities into fewer, clearly named tools that represent human-facing actions, then leaves fixed conditions and state transitions in deterministic code. This reduces model confusion, keeps high-impact gates enforceable, and gives the LLM the parts of the job where flexible interpretation is actually useful.

Domain skills can act as node-level controls by supplying expert handling for specific work-tree contingencies after the agent discovers them. Persistent artifacts such as documents, comments, and tables can also be tool surfaces because they let the user scope an instruction to the exact clause, row, or review finding instead of relying on a linear chat correction. Research agents especially need tool and artifact discipline: source gathering, YouTube analysis, compilation, and writing can be split into explicit tools or files so downstream workflows consume grounded evidence instead of hidden conversation state.

Typed tool surfaces can make the runtime contract stricter. Pydantic AI's tool examples register functions against an agent, pass a typed run context into those functions, and validate final structured output before downstream code receives it. Validation errors can also become tool responses that the model sees during a retry, turning schema failures into a narrow repair loop rather than untyped downstream exceptions.

Customer-facing agent platforms need both code-facing and nontechnical behavior tools. Sierra's "agent iceberg" warns that the obvious tool choices, such as model, framework, embeddings, vector store, and integrations, miss the platform surfaces needed for regression testing, model upgrades, voice edge cases, and CX-led coaching. A production platform may therefore pair in-code journey modeling with no-code tools for agent architects to build, refine, edit, coach, and update the agent.

Agent-facing products should treat APIs and CLIs as primary interfaces once agents become meaningful users. Dashboards still matter for humans, but agent experience asks whether a feature can be automated, called from a CLI, or used through a stable machine surface. Open model families add a model-tooling version of the same rule: release success depends on meeting developers in their existing runtimes, fine-tuning libraries, quantization paths, and product integrations. Environment tooling applies the same lesson to research workflows: shared Python environment projects, registries, rubrics, async tool definitions, and managed execution make evals and RL artifacts reusable instead of one-off lab infrastructure. Snorkel's self-contained FinQA environment is one such artifact — a fixed tool set (`get_table_names`, `get_table_info`, query) packaged with two benchmarks and published to Prime Intellect, the OpenEnv GitHub repo, and Hugging Face spaces — and it makes a tool-design point: well-named discovery and inspection tools matter only if the model uses them with discipline (discover schema, inspect before querying, self-correct on errors), and that discipline is a trainable behavior rather than a property of model size. For Apple local apps, MLX Swift LM and Hugging Face model IDs form a compact tooling path, while curated app model catalogs prevent users from selecting weights that are available but poor on the target phone.

Enterprise AI product surfaces may need to decouple custom clients from the underlying tool and data layer. i.AI's Redbox remained useful as a secure chat client, but Microsoft Copilot Chat's enterprise availability and MCP's tool/data standardization changed the distribution strategy: government-specific tools and data became more valuable when reachable from multiple enterprise clients rather than only one bespoke UI.

Browser UI control is the fallback tool surface when a workflow has no suitable API, CLI, or MCP path. Nova Act's SDK treats a natural-language `act` call as a screen-action primitive, then lets developers combine it with structured JSON extraction, Pydantic schemas, Python helper functions, parallel browser sessions, and pandas post-processing. That makes browser automation less like one giant autonomous prompt and more like a programmable tool layer around small model-grounded UI actions.

MCP is one part of the agent connectivity stack, not a universal replacement for every surface. Skills carry reusable domain knowledge, CLIs and computer use fit local sandboxed environments, and MCP fits remote semantics, authorization, governance, resources, long-running tasks, and cross-client application surfaces. MCP applications and skills over MCP point to a richer server-authored surface where an integration can ship UI, tools, and current usage guidance together.

The UI half of MCP applications has its own rendering architecture, and it is a security boundary rather than a styling detail. App UI is delivered as "views" — small HTML/JS/CSS snippets rendered as the result of a tool call and advertised ahead of time on the `tools/list` call so the host can cache or fetch them and inject tool results. Hosts such as ChatGPT and Claude do not drop those views into one iframe; they nest an inner `srcdoc` frame inside an outer loader frame served from a host-controlled per-app subdomain, because every simpler option fails an origin/CSP elimination chain (shared-origin `srcdoc` blocks app scripts under the host's nonce rule, relaxing CSP exposes host storage and cookies, `sandbox` breaks origin-indexed storage, and `allow-same-origin` is a sandbox escape). The practical tool-design consequence falls on app builders: because the host rewrites the app's content-security-policy from declared metadata inside that nested frame, every external domain a view touches must be declared — `connect-src` and `script-src` especially — or the app is blocked in production or rejected from the store. Host developer modes that strip CSP hide this until production, so live CSP-diff tooling (such as Alpic's Skybridge inspector, which compares declared domains against domains the view actually calls) is part of the app-developer tool surface. GitHub's intro framing fills in the runtime contract and the build path: at runtime the server returns the tool result *plus a UI resource reference* (an MCP resource pointing to bundled HTML), the host — VS Code, explicitly not the GitHub Copilot client — fetches that HTML and renders it in a sandboxed iframe, and the app then calls back to the server so fresh data updates the view live; the sandbox is a containment boundary ("the same reason you put a hamster in a cage") that keeps the app away from host settings, external APIs, and anything outside the chat. The build itself is a coding-agent workflow rather than a framework setup: borrow the official skill from the Model Context Protocol repo, edit it, and run it through a coding-agent CLI (GitHub Copilot CLI, Claude) to scaffold the three-part app — a tool, a bundled HTML resource (React/Vue/Svelte/vanilla), and the server-recognized data↔UI link — with tool-visibility config deciding who invokes the tool (model only / model + app / app only).

Above that rendering architecture sits a design choice about *how much of the UI the model itself produces*, and it falls on a spectrum from static to declarative to fully generative. In the static pattern (the dominant one today, and essentially 20-year-old server-data-→-client-render) the agent is just an orchestrator: a tool call passes data/props to developer-built predefined components that the client renders — AG UI's SDK maps a registered client tool to a React component, and Goose's "Auto Visualizer" routes arbitrary data to a fixed component set. Declarative UI keeps the design-system components but has the agent emit a descriptor (JSON or YAML, or Python via FastMCP) that a rendering engine maps to those components, so the LLM generates the JSON rather than the components (Vercel's JSON Render; Netflix server-driven personalization is the prior art); Postman's Casas argues this is the practical balance today because it preserves consistency and predictability while spending far fewer tokens than generating the whole UI. Fully generative UI skips components and lets the model write HTML/CSS/JS on demand (one tool call emitting markup), which is the most flexible but also the reason the sandbox matters: model-written UI is untrusted third-party code, so it needs containment — and MCP apps' auth, message passing, and sandbox-by-default double iframe make them the natural delivery mechanism for it, first-party as well as third-party (Anthropic's visualizer uses MCP apps rather than a bespoke renderer). The same source points past one-shot output toward collaborative, editable shared artifacts (the Excalidraw MCP app's shared canvas a human can both prompt and click-edit) as the likely next form.

Rendering the widget is only the first move; the deeper point (Manufact's `mcp-use`) is that an MCP App is a stateful, bidirectional interaction layer built from a handful of primitives. The widget can push its live state into the model's context without a user message (set-state / update-model-context), send a follow-up message back into the conversation unprompted (with Claude prefilling the chat input while OpenAI auto-sends and streams), call other tools, and receive the model's tool-call arguments streamed in *incrementally* so the UI draws as tokens arrive (Excalidraw mermaid-to-canvas, a Remotion video rendering live). A privacy primitive matters for tool design: a tool returns a *list* of outputs, so you can send rich structured data into the widget while returning a separate redacted output — or nothing but "the user is seeing their private information above" — to the model, enabling agent UX where sharing raw data with the model provider is disallowed. Display modes (inline, full-screen with the chat input overlaid, picture-in-picture), external-link opening, and host-theme syncing round out the surface, and because the client is known from exchanged metadata a server can return a widget only to hosts that render it and a plain output otherwise. Distribution is the other half of the thesis: the client stores (ChatGPT apps at chatgpt.com/apps, Claude connectors, Cursor directory) opened for self-serve submission of both plain servers and Apps, replacing shared JSON config with one-click install URLs, and Claude already does *dynamic discovery* — searching the MCP registry for the right connector when a task has no matching tool — so store presence becomes a high-intent organic acquisition channel rather than a directory listing.

Remote MCP also changes client strategy. A single stateful MCP server can be exposed through existing clients such as Cursor, Claude, and ChatGPT, then later through a custom app or voice client when the product needs tighter control over modality and workflow. The server-side tool surface should therefore own resources, prompts, tools, memory, and side-effect state rather than assuming one chat UI owns the whole agent.

Task-management tools need the same product shape. Backlog.md uses MCP resources to teach agents the task lifecycle and MCP tools to let them search, view, create, update, and complete repo-local Markdown tasks; the resource/tool split keeps workflow guidance explicit while preserving a constrained operation surface.

RAG stacks are another tool surface when their internals are inspectable and editable. OpenRAG's LangFlow layer exposes ingestion, retrieval, guardrails, parsers, URL ingestion, calculators, prompt templates, and OpenSearch tools as flow components; its API keys and MCP server let other applications or agents call the same retrieval system instead of duplicating it.

Enterprise RAG tools can also expose proprietary API access when source data lives outside the indexed document store. A practical pattern is to make API specifications model-accessible so the LLM can call licensed databases directly, replacing manual web UI exports and spreadsheet handoffs with a controlled tool path.

LLM programming frameworks can make prompt format itself a tool layer. DSPy signatures and modules describe the workflow intent, while adapters choose how that intent is rendered to the model, so teams can compare JSON, BAML, compressed formats, or model-specific formatting without rewriting the program. This matters because prompt strings otherwise become a low-level tool surface that entangles durable task intent with model-specific wording, examples, output-format instructions, parsing assumptions, and inference-strategy choices.

Open-source agent tools need extension points as well as integrations. Plugin architecture can keep memory, wiki, dreaming, and other experimental capabilities installable without forcing every idea into core or overloading maintainers with unrelated pull requests. Ordinary package-manager distribution can be enough for harness extensions when extensions are just code modules that add tools, commands, events, providers, or compaction behavior. Routine systems are another tool layer: they package repeated prompts as scheduled or manually parameterized workflows, often invoking skills for specialized domain guidance while keeping the trigger, variables, and project or agent ownership explicit.

Tool metadata is also a security boundary. MCP and function-calling systems should treat full tool descriptions, hidden parameters, and approval summaries as prompt and policy surfaces, because a model may act on instructions the reviewer never saw. High-risk tools need approval UI that exposes the effective action and guardrails that inspect the full model-visible metadata. Tools that fetch object IDs, repository URLs, schemas, or arbitrary files also need requester-scoped authorization and allowlisted network behavior; otherwise the tool layer can become an IDOR or SSRF channel even when the model prompt looks harmless.

Tools are also how you bridge an LLM to a domain it is weak at. When a field already has a superhuman-but-inarticulate solver (a game engine, simulator, optimizer, or verifier) and you want natural-language explanation, the durable shape is an agent whose tools expose the solver's ground truth so the LLM narrates rather than computes — TNG's chess-explainer channel pairs Gemini 3.1 Pro with a legal-moves tool (constraining the action space so it never reasons about an illegal move), a playable board it can explore variations on, an on-demand chess engine, and web search, because "engines can't explain chess and LLMs can't play chess, so we combine them." The same source makes a tool-design point that runs against intuition: feeding the agent *conflicting* signals is beneficial. Rather than only the engine's single best move, the agent also gets a beginner heuristic ("checks, captures and threats," which surfaces reasonable-looking-but-losing moves) and a rating-conditioned human-move model (Maia), so it can explore the alternatives a human would actually consider and explain why the bad ones fail — because the deliverable is the reasoning across options, not one committed action. This complements the payment-style rule of collapsing to a deterministic path: when the output is explanation, keep the disagreement visible; when the output is an irreversible action, remove it.

Durable workflow tools add another tool boundary: LLM calls, sandbox operations, and external API calls should be wrapped as steps so the tool run has cached inputs and outputs, retry behavior, spans, and event logs. The workflow engine gives observability and resumability, but sandboxing and permission control still belong to the agent's underlying tool and VM boundaries.

Production MCP servers should be designed as agent-facing interfaces, not as dumps of existing API endpoints. Fewer outcome-oriented tools, constrained schemas, unambiguous descriptions, minimal response payloads, read-only annotations, and resource-level scoping all reduce prompt-injection and oversharing risk before OAuth enters the picture. Remote MCP also changes tool authorization: long-lived API keys in config files or headers are weak production credentials, while OAuth 2.1 flows, PKCE, token exchange, and CIMD-based client identity give shared MCP servers a path toward short-lived scoped access. Governance still needs per-tool policy and traces that show which agent called which tool, which parameters were used, and what data came back. Public MCP servers often need an adaptation layer before they fit a production agent workflow: filter irrelevant tools, rewrite descriptions for the local task, validate sensitive arguments before invocation, compose intent-specific tools from generic ones, and call mandatory brittle setup steps directly when no agent decision is needed. Tool outputs need the same model-facing design: a verbose API-native payload can be worse agent context than a compact serialization shaped for analysis.

Agent-native MCP design is product design, not endpoint publishing. A useful server starts from the workflow outcome an agent should achieve, then curates tools around agent discovery, iteration, and context limits. Auto-generated REST mirrors can bootstrap experiments, but they should be reduced into agent stories before production: known multi-call choreography belongs behind a server-side tool, while the model should be reserved for judgment-heavy steps where the algorithm is not already known.

Commerce agents add a domain-specific tool-design case. Product feeds and scraped product pages can bootstrap shopping experiences, but they scale poorly when many chat clients and agents need current merchant data. A stronger tool surface abstracts product catalogs, inventory representations, brand context, and checkout operations into cohesive APIs or MCP servers, then lets chat clients render generated product components or execute transaction flows without forcing every agent through brittle website automation.

Enterprise tool ecosystems also need registry metadata once many teams publish MCP servers and A2A agents. A private registry can start from public MCP catalog conventions, add approved internal and public servers, and enrich each entry with owner, environment, authentication, cost attribution, and use-case links. A paired A2A registry can use agent cards as the discoverable contract for agent identity, endpoint, capabilities, modalities, and auth requirements. These registries should be connected to DevOps pipelines so publishing an MCP server or agent updates both the runtime artifact and the governance catalog.

Internal platform tools should be designed so agents can call the same intended paths humans use. APIs are the base layer, while CLIs or MCP servers can wrap those APIs for agent use; logs, metrics, traces, and relevant documentation should also be exposed through machine-friendly surfaces instead of only dashboards or full HTML pages.

For coding agents, tool boundaries should be chosen by what needs hard semantics. Read tools can control token load, grep/glob can support exact codebase search, edit tools can enforce read-before-write and diff-shaped changes, Bash can compose project commands inside a sandbox, and brittle edge cases can be moved into versioned tools that are easier to evaluate than broad prompt guidance. When an action can be exposed as a CLI or API, that text-native surface is usually a better agent tool than browser automation, especially when accuracy matters. CLI surfaces are also workflow composition tools: they can run in the background, emit logs, accept pipes, call specialist agents, and chain generation, coverage, and review stages in a way that is awkward for IDE-only plugins.

Managed agent platforms should be evaluated as tool bundles, not only as model wrappers. Connector coverage, permissioning, compliance, audit trails, observability, email or notification support, token accounting, and infrastructure ownership determine whether the tool surface lets teams focus on business logic or forces them to rebuild platform plumbing.

Agent-first IDEs show how browser and editor tools can be combined without hiding their authority. Antigravity gives the agent a Chrome browser for authenticated context retrieval, UI interaction, JavaScript execution, DOM inspection, and screen recording, while keeping terminal-command approvals and editor handoff visible in the agent manager.

The post-IDE direction adds another tool-design constraint: putting every request through one all-purpose coding agent wastes context and model budget. A better tool surface can route trivial checks, product exploration, implementation, review, tests, and merges through narrower roles and interfaces, while the human sees orchestration state and evidence instead of a raw terminal transcript.

Amp Code adds that generic integration availability is not the same as a good core tool surface. A coding agent may need custom search, reasoning, dependency-lookup, and codemod tools tuned to the exact feedback loops it must close; otherwise tool descriptions and calls become context overhead and irrelevant choices become failure modes.

Zapier's Scout work reinforces that useful tools still need to live where the work happens. A separate API playground added another window and saw weak engagement, while the same capabilities gained traction when embedded into support ticket creation, Cursor through MCP, Jira, GitLab CI/CD, and GitLab comment-based iteration.

Prompt-to-app builders are also tool surfaces. AI Studio shows a compact version: model and API feature chips can attach Search grounding, Maps grounding, Live API, and model choices to a generated app, while one-shot builders can clone UI screenshots or explore export flows before a team commits to production implementation. Full-stack app builders extend that surface by inferring packages, backend services, storage, payments, and first- or third-party API integrations from application intent.

Coding agents can also become programmable tools inside other products. Codex is described as callable through SDKs, GitHub Actions, CI/CD, and MCP-connected product agents, which lets an outer product delegate code-writing, connector creation, merge-conflict handling, or bug fixing without rebuilding the full coding-agent harness. The tool-design burden then shifts to the product boundary: expose the coding agent where the work already happens and reserve the surrounding UI, policy, and workflow decisions for the product.

Shell wrappers can also act as local harness tools. A wrapper around Codex CLI can accept file-backed task inputs, launch a child `codex exec`, and print the child output to stdout so the parent agent receives a compact result. This uses Bash as a composable tool surface, but it also turns command shape, sandbox mode, credentials, rollout logging, output files, and timeouts into explicit tool-design concerns.

Model-client wrappers are another tool-surface pattern. When a compiled local model can be invoked through the same `embeddings.create`-style call shape as a hosted model, application and agent code can stay stable while runtime-specific resolution, FFI loading, and output shaping move behind the client boundary.

AI coworker products add tool surfaces that are neither plain chat nor backend APIs. A tool can be invisible background work, ambient affordances in a workspace, inline transformation controls, or a conversational builder. When an agent acts inline, the tool UX should show what it is doing, ask for alignment at meaningful checkpoints, keep snapshots and rollback paths visible, and hand control back to the user when the model cannot safely complete the work. Coding IDEs add another tool-policy layer: repository instructions, custom modes, MCP servers, browser previews, selected-element context, and auto-approval settings shape what the agent sees and may do. Terminal approvals remain especially sensitive because command chaining can make a simple allow-list less precise than it looks.

At cloud scale, tool discovery itself becomes a tool. AWS's Strands example keeps the agent shape simple by connecting a model to code-defined tools, but the large-catalog variant stores thousands of tool descriptions in a knowledge base and retrieves the relevant subset before exposing tools to the model. The same source shows how MCP tools can move from a local stdio server into a remote serverless endpoint with authorization and session storage, keeping the agent-facing tool contract while changing the deployment boundary.

Prosodica benchmarks why that retrieval move is necessary and not just tidy. Their "Fat Agent" — every tool's name, description, and JSON schema loaded into every prompt — collapses as the catalog grows: tool-selection accuracy falls from ~78% at 10 tools to ~40% at ~100 to 13.6% at 741 tools, a 741-tool catalog costs ~127,000 tokens per request before the user's question is read, and time-to-first-token past ~500 tools can exceed 5 seconds. The failure is structural (every request carries the whole catalog) and rooted in lost-in-the-middle: models attend to the beginning and end of long context, so schemas packed in the middle are used unreliably. Their fix is a Semantic Tool Router — "RAG for tools": embed each tool description offline into a vector index, then at runtime embed the query, retrieve the top-K (K≈3–5) closest tools, and inject only those schemas (just-in-time context injection). The routed agent stays above ~83% accuracy across the same catalog sizes with near-flat latency and ~99% fewer tool-context tokens, echoing Anthropic's reported 150k→2k token drop from on-demand MCP tool loading — and the router also *removes* the wrong tools from the model's choice set, not only adds the right one. The threshold is practical: below ~20 tools a router may be unnecessary (static loading is fine), but past ~50 tools in production it pays off. Tuning is an eval discipline — measure accuracy, TTFT, input tokens per request, and cost per 1,000 calls; sweep K at 3/5/10 and pick the smallest K meeting the target (K=5 default); and guard three failure modes (router miss → widen K or run a second pass; weak descriptions → weak embeddings, so write intent/action/entities in users' words; rare tools → monitor misses and rewrite).

Workflow composition adds another tool-design rule: a workflow can be exposed as an agent tool, and an agent can be exposed as a workflow step or tool. This is useful only when the exposed primitive is small enough to understand, because broad tool sets and graph-shaped APIs can create selection and maintenance failures. Dynamic tool injection is the tool-surface version of this pattern: provide the agent only the tools that fit the current task segment. Collaboration tools add another tool boundary: agents should be OAuth-installed platform users with GraphQL or API access, granular scopes, mention and assignment webhooks, and admin-managed access rather than anonymous background automations.

Mechanistic interpretability can become a tool surface when feature attribution, activation steering, dynamic prompting, and concept palettes are exposed through product controls. These tools differ from ordinary prompts because they operate against model-internal features during generation or post-training inspection. That makes them useful for debugging, targeted steering, and creative control, but also means product UIs and review workflows need to disclose and evaluate the effective intervention rather than hiding it as invisible model magic.

Third-party MCP tools also need ordinary integration hardening. A protocol-level success response can still hide a business failure, such as a Slack tool returning empty content because the configured channel does not exist. Wrappers should validate returned content, convert ambiguous empty results into explicit errors, and decide whether a remote MCP or A2A endpoint is acceptable under the product's security boundary. In regulated workflows, provider agreements, encrypted transport, mutual TLS, IP allowlisting, endpoint controls, and private-network deployment may matter as much as the MCP or A2A contract itself.

GitHub Copilot's MCP integration reinforces that external tool access is not passive context. An MCP server can let Copilot create GitHub issues, search external systems, or inspect database schemas and data; because those servers can also perform tasks on the user's behalf, third-party MCP servers need trust review and scope discipline before they are added to developer workflows.

Anthropic's remote-MCP experience adds two practical tool-surface lessons. First, a gateway should create a pit of success: one `connect to MCP` call can route to internal or external servers, retrieve stored credentials, return a normal MCP SDK client session, and keep product teams from reimplementing OAuth and tool plumbing. Second, MCP's JSON-RPC messages can travel over internal websockets, gRPC, Unix sockets, or other stream carriers while preserving the standard SDK boundary; external interoperability and internal routing do not have to be the same design problem.

Web access is itself a tool surface that the default `fetch` does much worse than a managed MCP. Bright Data's web-access MCP bundles a real search-engine tool (Google, Bing, DuckDuckGo), scrape-to-markdown that avoids spending tokens on HTML, batch search, per-site APIs, and a remote scraping browser that solves CAPTCHA and runs parallel sessions without getting blocked, because a raw fetch silently fails on the roughly 20% of the web that blocks AI crawling. The same surface shows the tool-budget discipline concretely: it exposes 66-69 tools but the speaker loads only the two a task needs (scrape-markdown plus search) so the agent is not flooded with irrelevant tool context. A follow-on talk fleshes out the primitives — a "web unlocker" that curls any URL and returns HTML with the right headers/cookies and a solved-CAPTCHA token, ~500 pre-built per-site APIs returning structured JSON (more token-efficient than markdown), and a geo-targetable remote browser that fills forms and clicks (everything but login) while mimicking human mouse movement and typing, so even a low-cost model like Claude Haiku is enough for browsing. The bigger tool-surface lesson there is that the agent should not be the per-page parser at all: it uses these tools to build a reusable scraper script once and then runs that deterministic script for pennies, and — because it can build the scraper — it can also maintain it on a schedule when a site breaks.

The publisher side of that web-access problem has its own emerging tool standard. WebMCP is a proposed standard that lets a site declare its capabilities as named, typed tools for in-browser agents, replacing the scrape-the-DOM-then-guess-coordinates chain with direct tool calls; the Chrome team frames it as the client-side implementation of the tools part of MCP — complementary to server-side MCP rather than a replacement, since the tools live in the browser and the page must be open. Tools are page-scoped (each page advertises its own action set), and there are two authoring paths: a declarative API that annotates existing HTML forms so the browser auto-generates the JSON schema (with extra attributes such as an `agent-invoked` boolean), and an imperative `registerTool` API with a hand-authored schema and an `execute` block of JavaScript for complex multi-step flows. As with server-side agent tools, descriptions are the operational prompt, the UI should stay in sync with each tool call so users can see what happened, and high-impact steps such as final checkout for real money are best left to the user. The same lesson as agent-readable web conventions applies first, though: good semantic HTML, accessibility, and performance already get a site most of the way to agent-ready before any new standard is added. The tooling is early (Chrome 146+ experimental preview) but already includes a Model Context Tool Inspector extension that lists a page's tools and an eval CLI for testing them.

Tool connections can also be wired as an inbound attention filter rather than only as outbound actions. WorkOS's sustainability talk gives Claude Code read/write access to Slack plus Linear via MCP and runs it on a loop as a "signal layer": the agent watches @-mentions, DMs, and high-priority asks, deduplicates them against Linear tickets, and surfaces only the real work, so the developer never opens those apps and loses focus to an unrelated thread. The reusable point is that the same MCP surfaces used to act (firing a status update into a Slack channel) can also be used to triage, keeping the human's attention on the work only they can do.

How tool context is loaded is itself a tool-surface decision. WorkOS's Studio shows the runtime, single-agent version of the tool-budget problem: rather than choosing which of many tools to expose, it injects each tool's heavy schema/usage context only at the moment that tool is invoked, after a preflight checklist decides which tools to use — explicitly to avoid preloading every tool's instructions and blowing out the window. The per-tool context block is also where data-consistency guardrails live: encoding join quirks and active-status/non-deleted filters in the tool's context is what makes a generated query against a sprawling Snowflake schema reliable, and removes the need for any RAG store because LLMs read self-descriptive schemas well.

Observability platforms are reshaping their tool surface the same way. Arize's bet is that most people do not want to live in dashboards or buttons, so it exposes all of its primitives — observability, evals, experiments — through a CLI plus a set of tools and skills, so a coding agent (Claude Code, Codex) can drive the platform programmatically rather than a human clicking. It also ships a platform agent ("Alex") reachable from those same surfaces that, with access to all the trace data and hooks, can be asked "do you see any issues with my application?" and then plans and runs the work itself.

Payment is becoming a tool surface too. Stripe's framing is that tool calls are just HTTP requests and HTTP requests should be payable, so rather than pre-provisioning an API key for every ephemeral interaction, a protected endpoint can answer with an HTTP 402 ("payment required") plus an encoded payload of what is being bought, who is being paid, and the mechanism — the agent then pays (the Machine Payments Protocol demo settles a one-cent charge on the Tempo blockchain) and retries. For richer commerce where tax, quantity, and shipping must be exact, the Agentic Commerce Protocol replaces browser stumbling with a structured agent/seller/PSP exchange: the seller exposes a product catalog as JSON and relays cart state on each create-checkout, update-quantity, or pick-shipping call, like any other tool-call response. Both keep the deterministic-tool discipline already seen elsewhere — descriptions and structured payloads carry the contract, and the seller stays in control with the risk signals it needs.

Chrome DevTools MCP turns these tool-design choices into measurable engineering, treating an agent as a separate user class with its own non-functional requirements (efficiency, discoverability, security, stability). The headline metric is the fuel efficiency of the interface — tokens per successful outcome, conditioned on completing the user journey and compared within a task class rather than globally — so optimization targets the interface, not just the model. The same discipline shapes outputs and errors: a performance tool returns a markdown semantic summary instead of a ~50,000-line JSON trace ("point the agent at the right sentence, not the whole book"), error messages are rewritten so the agent self-heals without a human, and token burn is cut through tool categorization, a 3-tool "slim mode," and a CLI that keeps post-processing like grep on the local machine. The arc from one monolithic `debug_webpage` tool to 25 tools showed that decomposition only trades the context-budget problem for a discoverability one, because the schema is the UI for the agent and most MCP tool descriptions carry quality smells.

Shipping a good tool is necessary but not sufficient — the model also has to know when to reach for it. Turbopuffer's code-retrieval benchmark found that the *same* semantic-search tool delivered ~24% answer-accuracy gains inside Cursor's Composer, which is trained to know when and how to call it, but much smaller gains bolted onto Claude Code, where it is "just another tool in the list" and the model has "no true understanding of when to use it, why to use it." Tool availability does not equal tool effectiveness: a model that has not learned to gate a tool under-calls it, over-calls it, or fires it on the wrong task. This is the upstream counterpart to the FinQA lesson that tool-use *discipline* (discover → inspect → self-correct) is trainable — here the trainable competence is the *decision to invoke the tool at all*, so durable wins come from pairing lightweight context-finding tools with a model that is competent at wielding them.

The endpoint of this "tool descriptions are a prompt surface" arc is to question whether many tools should be tools at all. Witan Labs, teaching coding agents to master spreadsheets, replaced ~15 accumulated tools with a single Node.js REPL — the tools became JavaScript functions the agent composes in one call — and this was their biggest single benchmark jump (~50% → 74%). The reframing: "if your agent is making many sequential tool calls or even parallel tool calls, you've kind of invented a bad scripting language, so you might as well give the agent a real one." A REPL goes beyond code mode by adding *persistent state* — variables survive across calls, so the agent builds on its own work, writes *shorter* scripts, and interleaves more reasoning — and new capabilities are added not as schema entries but as JavaScript methods surfaced through a TypeScript type-definitions file in the prompt. The interface language (JavaScript, easy to sandbox and familiar to models) is deliberately split from the implementation language (C#, which handles the files), and the caveat is that a code REPL is only the best interface *for now* — as labs improve computer use, the best interface may change, so expect to revisit it. To make that REPL trustworthy for a domain with no off-the-shelf compiler/linter, Witan built high-fidelity engines (a formula engine and an image render engine) that close a verification loop — the durable part of the system while the interface churns — with the sharp caveat that a partial engine (say, 50% of Excel's formulas) yields *worse* results than none.

Where you instrument tool calls is itself a tool-surface decision. Tailscale's Aperture argues for the LLM-call layer over the MCP layer: because every model call must traverse the gateway node, it captures every tool call, bash command, and MCP request without instrumenting inside the container or the harness — "a guarantee I've seen every tool call this thing has ever made." The reason to prefer the LLM layer is empirical: "a lot of agents are moving away from tool calls and executing code," so MCP-layer traffic no longer represents what agents actually do — and internally "bash dominates everything else." Even pure visibility is valuable ("forget about blocking it, just tell me what people are doing"), and the same chokepoint enforces cross-provider budgets, quotas, and webhooks guaranteed to fire on each tool call. The honest limit is that an agent can write, obfuscate, then run code, and the deliberate ergonomics choice is to set the agent's base URL explicitly rather than intercept transparently, so the control surface doesn't "move out from under you."

Protocols are also standardizing the boundary *above* tools — the editor↔agent boundary. Zed's Agent Client Protocol (ACP) is a JSON-RPC protocol positioned as an LSP/MCP analog for that boundary: where MCP standardizes agent↔tools and A2A standardizes agent↔agent, ACP lets any client (editor) drive any agent through one unified interface so users can bring their agent of choice. A minimal agent implements four methods (initialize, authenticate, newSession, prompt, plus cancel) and negotiates capabilities in `initialize`; the client provides the working directory and can advertise file-system and terminal capabilities the agent then uses. Two design choices from the live build generalize to any agent-to-client channel. First, agent work reaches the UI as session-update *notifications*, not request/response: text streams as `agent_message_chunk`, tool calls are announced with an initial `tool_call` and then completed with a `tool_call_update` (two-phase, so the client learns about a call before receiving updates for it), and edits are sent as a diff content type the editor renders — pushing rendering to the client and keeping the agent thin. Second, side effects route through client-advertised capabilities so the UI reflects true state: reading over a proxied file system (`read_text_file`) lets the agent see unsaved editor-buffer changes rather than only disk, and a client-managed terminal surfaces a live terminal in the UI. Transport is stdio today, with remote transport in progress; ~40 clients (JetBrains, Obsidian, opencode, cursor) support ACP via native mode or an adapter.

Hooks are the tool-surface hinge for a different control: turning the agent's completion into a checkpoint. Talha Sheikh (Checkout.com) wires a deterministic verification gate to Claude's Stop hook so that when the agent claims it is "done," the hook automatically runs a config of test cases and loops "try again" feedback back into the agent until they pass — extending the "use hooks for deterministic verification" pattern from mid-session tool checks to an end-of-session enforcement gate. His broader point is a tool-architecture one: enforcement should be a language-agnostic, bring-your-own contract that can fire at any level (in-conversation, conversation-end, pre-commit, multi-agent, async, or an optional LLM-as-judge), because instructions given through prompts and tools are not the same as a check that the work was actually done.

Some of the highest-leverage tools are the ones you build so the agent can *see* your specific product. Johan Lajili (Poolside) argues a coding agent is "blindfolded" without an observe-and-control surface tailored to the product's runtime — and that off-the-shelf tooling only fits web apps. Because Poolside's product is a VS Code extension, generic screenshot/browser tools do not reach it, so they built an internal CLI that takes screenshots, produces a token-compressed UI snapshot, extracts front-end/back-end service logs, restarts services, and issues stackable high-level UI commands (open a menu, navigate, send a message, wait for a reply, upload an image). The reusable point is meta rather than about any one tool: the form (CLI vs skill vs MCP) and the representation should vary by product — an ASCII view of a Unity 3D world, easy logins for a multi-permission app — and building that surface so the agent can self-serve and reproduce bugs is the engineer's new ("AIX") job, worth investing in before features because it compounds once agents run overnight and in parallel.

Aditya Bhargava (Etsy) adds two tool-surface techniques from his Agency language. First, ergonomics: every function can be auto-exposed as a tool — the framework generates the JSON schema from the function signature and uses the docstring as the tool description — so defining a tool costs nothing extra. Second, safety by *pre-binding* arguments: rather than approving each call or trusting the model to stay in bounds, apply partial function application to lock a tool's sensitive argument (e.g. lock a `read`/`write` tool's directory) before exposing it, so the model neither sees nor can change it and the tool's blast radius is confined declaratively. This is the same "narrow sensitive authority" instinct as purpose-built key-write operations, but achieved by currying a general tool into a scoped one, and it complements interrupt-based approval — pre-binding grants unattended autonomy while interrupts gate the actions that still need a human.

Andrew Dumit (Watershed) shows the tool-surface pattern for letting a coding agent operate on high-stakes structured data without free-form code corrupting it. Rather than a set of enumerated function-call tools (which broke at scale — "editing across [100k's of nodes] takes loops and filters, not enumerated tool calls"), the agent gets full code freedom but every consequential mutation must pass through a typed TypeScript SDK that is "the only door" to the graph. The SDK is a designed *edit-primitive* surface: it exposes explore/interact and mutator functions (`findNodesByExactName`, `setRate`, `editNode`), enforces which fields are editable versus derived so the agent can't create self-conflicts, provides assertions for early failure, and guarantees typed output objects — turning a general coding environment into a scoped, lintable interface. The guarantee is completed by owning the final deterministic execution (lint → conflict-detect → run → validate typed artifacts), which is the tool-layer version of Talha Sheikh's completion gate but keyed to a domain SDK rather than a generic test config. The reusable tool-design lesson: constrain the *effects* the agent can have on the external system, not the *expression* of its code, and teach the SDK exactly as you would teach an agent your codebase (prompt plus full access to the SDK's docs and source).

Protocols are a tool surface too, and the choice of *which* protocol and *why* is not only about crossing ownership boundaries. OpenGov adopted Google's A2A spec internally as the contract between its own front-end and back-end — modeling agent routes and schema on the agent card (name, description, capabilities) that both sides consume and produce — purely because "this rigorous spec really helped drive our development and drive alignment." That qualifies the usual A2A-versus-MCP-by-ownership-boundary heuristic: a rigorous open protocol can earn its place as an internal API contract for spec discipline alone, with extensions (metadata, A2UI) letting it grow with the product. On the tool-definition side, the same team keeps the surface minimal ("tools and skills are really all you need"): a tool is defined, added to a tool kit (a collection of tools), and the tool kit is registered with the language model, so product teams each contribute tools/skills to power one shared agent button.

Skills are themselves a tool surface, and Matt Pocock's authoring rubric makes one tool-design decision explicit: a skill's *trigger*. Whether a skill is [user-invoked or model-invoked](../concepts/choose-skill-trigger-by-trading-context-load-against-cognitive-load.md) is the same "expose this to the model or not" choice as advertising a tool — model-invocation puts a description in context on every request and lets the model decide (flexibility bought with token cost and firing unpredictability that forces evals), while user-invocation keeps the surface deterministic but moves the burden onto the pilot. It's the skill-layer counterpart to just-in-time tool-context injection: control how much of your tool/skill surface the model must reason over on every turn.

Amol Kapoor (Nori) generalizes the "text-native surface beats spatial automation" rule from CLIs to *artifact-authoring* tools. When agents produce garbage graphics, the fault is the tool's medium, not the model: canvas tools (PowerPoint, Figma, Canva, Figma MCPs, PowerPoint CLIs, screenshot-and-replace loops) are built for human hands and eyes and force the model to place coordinates in "a wall of numbers," which is as foreign to a model as handwriting SVG is to a person. So [match the agent's output medium to its native representation](../concepts/match-agent-output-medium-to-its-native-representation.md) — give it a language/structure tool where it reasons about semantic elements (heading, chart, grid) and the renderer places pixels, so "the model never actually places a coordinate." Concretely, [author visual artifacts as HTML and decouple the editing format from delivery](../concepts/author-visual-artifacts-as-html-decoupled-from-delivery-format.md): HTML/CSS is the editing substrate agents already handle well (slides, docs, video), and the delivery format (a PowerPoint deck, a PDF) is a separate downstream render. This is the same lesson as "prefer a CLI/API over browser automation," applied to the tool an agent uses to *make* graphics rather than to act on a system.

Most of this topic is about the tools an agent uses; the mirror question is which tool an AI feature should live inside when its users already have one. Todd Fisher's answer for audio is to [ship AI audio features as plugins inside the host DAW](../concepts/ship-ai-audio-features-as-plugins-inside-the-host-daw.md): a JUCE plugin dropped into Logic Pro "just like any other plugin… where you just plop it in there," chained with the session's existing effects, on the reasoning that "your DAW is effectively your IDE but for musicians and music producers." The host then supplies live input, routing, monitoring, and the backing track, and the plugin's own UI carries only the genuinely new decisions — in his case a clarity dial mixing synthesized tone against generated voice, and a drag-to-edit word-boundary editor. The tradeoff is that the feature now runs inside someone else's real-time audio thread, which is part of why the heaviest processing had to move off the live path.

Kapoor's medium argument has a vocabulary counterpart. Arturo Nunez's account of why agents reinvent the same game-engine camera on every request is that the only nouns available are implementation primitives — mesh, renderer, animator, rigid body, collider, audio source — so a domain intent has nothing to bind to and must be re-derived from parts. His prescription is to [expose the domain's vocabulary to agents rather than the platform's primitives](../concepts/expose-domain-vocabulary-to-agents-not-platform-primitives.md), and the source of that vocabulary is a useful detail: not invented, but taken from the words that already teach the domain ("press A to jump and press A again while you're in the air to do a double jump"). That is the same instinct as grouping raw backend endpoints into fewer human-facing tools and as encoding agent intent server-side, stated as a design rule about *whose* words the tool surface uses. The action side is stricter than most tool surfaces here: Nereu [makes every agent edit a declarative tag rather than generated code](../concepts/make-agent-edits-declarative-tags-instead-of-generated-code.md), with built-in systems querying by tag and no scripting layer at all "on purpose," so the tool catalog is a closed vocabulary the assistant is handed as it grows and the worst outcome of a bad call is a wrong tag a user can delete. Where this topic's code-mode material buys expressiveness and then spends the savings on sandboxes and capability grants, this trades expressiveness away and gets containment for free — and pays for it in the platform team's obligation to decompose everything users might mean into tags and systems.

Corey Gallon's browser-automation talk lands on this topic's oldest open argument — CLI versus MCP — and is the first source here to bring numbers to it. Capability is a wash: an Arize AI study he cites had both surfaces clearing the same tasks "roughly 83% of the time." The difference is everywhere else. Reuse: "a CLI sequence can be programmed. You write it once and you run it a thousand times without a model in the loop," where MCP "hits the model on every single turn." Latency: the same task took 71 round trips and 8 minutes over MCP against 7 turns and under a minute over a CLI. Cost: Anthropic's reported figure of up to 75× cheaper in tokens. None of those matter for a task with no deadline, which is why the argument only becomes decisive in his last demo — a challenge whose rounds expire on a clock, where [deterministic code has to drive the loop with one model call per round](../concepts/let-code-drive-the-timed-loop-and-call-the-model-only-for-perception.md). Read alongside this topic's connectivity-stack material, the useful framing is not "CLI beats MCP" but that per-turn model round trips are the price of the surface, and the tasks that cannot pay it are the ones with a timer. His tool surface itself is a good illustration of the topic's medium argument: rather than a bespoke tool per interaction, a Python-ecosystem CLI (Chrome Agent) exposes the Chrome DevTools Protocol and lets the agent write code to replay CDP interactions — a small subset of CDP's 57 domains, organized as senses (DOM, accessibility tree, screenshot / network, console / clicks, keystrokes, navigation) rather than as an API listing.

Paul Klein IV (Browserbase) extends that argument from *which* surface to *when the surface is learned*. His position is that a browser agent should arrive at a site already knowing what it can do there: [per-site skills published ahead of the visit](../concepts/publish-per-site-skills-so-agents-do-not-rediscover-a-website.md) — Browserbase's `browser.sh` registry "publishes skills for websites. So before your agent even goes to the website, it can observe what types of tasks it can do" — with [WebMCP](../concepts/expose-site-capabilities-to-in-browser-agents-with-webmcp.md) treated as the same knowledge supplied by the site rather than by a third party, and available "without pre-installing the actual MCP" because the tool surface ships with the page. Skills attach to whichever action layer is in use, including a CLI: "if your agent is using CLIs to control websites like the Playwright CLI, you could actually give it skills and context to be more effective there." The constraint he attaches is about token *quality*, not only cost — "if you're throwing everything on the page to a model, you're going to get sub-par results and it's going to cost you a lot. The right harness should not only present the right tools, but present an optimized amount of tokens that are compressed." And the action side of his account is a direct extension of this topic's code-over-tools material into the browser: the most reliable production agents [intercept the network request and replay it from a generated script](../concepts/pair-clicking-with-generated-code-and-replayed-network-requests.md) rather than clicking through the same flow every run, which is the same economics as a built parser beating per-page LLM parsing.

Dhruv Batra (Yutori) supplies this topic's sharpest limit on tool surfaces in general: most of them presume a cooperating publisher, and [the long tail of the web will not publish anything](../concepts/the-long-tail-of-the-web-will-not-ship-apis.md). His reading of the proliferation this topic tracks is that it is churn rather than convergence — "it was initially supposed to be MCP servers, then WebMCP, and for payments there are 20 different competing protocols… every single company wants to introduce their own protocol" — and his scale claim is that ~200 million active sites sit behind institutions that will not expose an endpoint even once generating one is trivial, because "you're not going to get unfettered access." That does not retire this topic's MCP, WebMCP, and `llms.txt` material; it scopes it to the head of the distribution and tells you what to build for the rest. The second limit lands on the cheapest substitute, the one this topic's code-mode pages make attractive: having a coding agent read the HTML fails where the page's own state is computed, since [rendered state is not in the HTML](../concepts/rendered-state-is-not-in-the-html.md) — "sold out" is a fetched `quantity` of zero plus a rendering script, not a string, so a document-derived tool returns a confident wrong answer rather than an error. His own action space is nevertheless not pixels-only: the model writes JavaScript in the page when that is faster, with the screenshot as the check on what the code did, which is this topic's code-over-tools argument with a verification channel attached rather than a rejection of it.

One more limit, from Bright Data's Omer Primor, applies to the search tools this topic hands agents by default. Search is a tool for *locating* a source, and giving it a job where the source is already known is a routing mistake: "you use search when you don't know the source. But if you know the source, then you should just go to the source." His worked example is a company-research task where the fields live on LinkedIn company pages, LinkedIn jobs, and Crunchbase, so the pipeline scrapes those three directly — [go straight to the known source instead of searching for it](../concepts/go-straight-to-the-known-source-instead-of-searching-for-it.md). The payoff is not only accuracy but the disappearance of a cost line, since a built scraper carries no per-call model spend: "zero AI cost involved. There's no tokens." Two things bound it. Knowing the source is itself a design-time judgment that has to be right, and the built path only pays back for a query shape you will run repeatedly — for genuinely open questions, an AI search API is still the tool, and "it's very tempting to throw AI search at all of them, but maybe that's not optimal."

A quieter shift in this topic is that some tools no longer need to be adopted at all. Ben Holmes wanted a force-graph over his own notes and did not evaluate a graph-view product: "this is not a tool that you have to install. By the way, I told an agent, build this for me." He then restyled it into a star constellation on a whim and generated a GitHub-style habit chart beside it — [disposable visualizations over your own corpus](../concepts/generate-disposable-visualizations-to-find-gaps-in-your-own-corpus.md), whose value is diagnostic ("where you have gaps in your thinking") rather than navigational. This is the fully generative end of the [agent-UI spectrum](../concepts/place-agent-ui-on-the-static-declarative-generative-spectrum.md), and it is safe here for a specific reason worth naming: the output is a personal view over local files rendered for its author, not third-party UI shipped to users, so the trust and containment problem that governs that end of the spectrum does not bind. The build-vs-adopt line for read-only views over data you already own has moved; the line for anything you ship has not.

Two of this topic's patterns move outward in Ben Hylak's talk. The first is code mode, which the wiki has carried as a way to [expose a large API through generated types](../concepts/expose-large-apis-through-typed-code-mode.md) instead of endpoint-by-endpoint tool schemas. Hylak transplants it off tool calling entirely: "you've heard about code mode in the context of MCPs… I highly recommend just uh trying to apply this to traces. Like you can just write uh these classifiers and you can run them in a sandbox and you can run them at production scale" ([Run Trace Classifiers as Code Mode in a Sandbox](../concepts/run-trace-classifiers-as-code-mode-in-a-sandbox.md)). The invariant that carries is the one that motivates typed code mode here — the model authors a program against a described surface and the runtime executes it over the data, so the model's context holds the question rather than the payload — and it applies to any corpus too large to load, not just to APIs too large to enumerate. The second is a tooling-category claim: the hosted prompt playground is losing its subject matter, because "the prompt is actually like the whole thing now. It's like all the code. It's your whole harness," so the assertion belongs in the repository beside it as an ordinary test ([Keep Evals in the Repo as Tests, Not in a Prompt Playground](../concepts/keep-evals-in-the-repo-as-tests-not-in-a-prompt-playground.md)). He names Sentry's Vitest evals and OpenAI's "macro evals" as existence proofs without evaluating either. Both claims come from an observability vendor and neither is measured; the market observation in particular ("I actually don't know many companies that use some sort of like managed prompt like in the cloud anymore") is an impression from a self-selected customer base.

Where an MCP server can *run* is a tooling question this topic has mostly treated as an operational detail, and Anthropic's Applied AI team makes it a design one. Their answer for tools that must live inside a customer's network is to invert the connection: the MCP server "run[s] only within their private network and only making outbound calls to the Claude agent loop" ([Reach Private MCP Servers With Outbound-Only Tunnels](../concepts/reach-private-mcp-servers-with-outbound-only-tunnels.md)). Nothing listens, so there is no endpoint to publish, authenticate, patch, or justify to a security review — the tool's reachability becomes a property of the customer's egress rules rather than of their perimeter. That is a materially different deployment story from the remote-MCP hosting this topic already documents, and it is the one that unblocks internal tools a hosted agent otherwise cannot touch. What it does not change is authority: once the tunnel is up, every tool the server exposes is callable, and the direction of the connection has no bearing on whether a prompt injection can invoke a destructive one. The account is a vendor's, delivered in about forty seconds, with no protocol detail, no authentication description for the tunnel itself, and no discussion of what happens to a session when it drops.

Skills are the tooling format this topic tracks that has no size discipline attached to it, and Aditya Khandelwal reports one team's answer: "even in your [SKILL.md] files, don't overload it. Like, we've kind of set a hard limit for like 100 lines in your [SKILL.md] cuz your skill is really a folder," paired with the same rule one level up for the repository context file, which should be "a thin index that can point through the right files" ([Keep the Repo Context File a Thin Index and Cap Skill Files](../concepts/keep-the-repo-context-file-a-thin-index-and-cap-skill-files.md)). The reasoning is the one Pocock already gives for keeping the top-level file small, but a stated cap is a different kind of artifact from a principle: it makes every addition a trade against an existing line and gives review something to point at, which is what the format needs once more than one person is writing skills. The number itself is soft — line count is a crude proxy for tokens, no derivation is offered for 100, and a talk about one team of about ten is not evidence that it generalizes — but the accompanying verification is portable regardless of the threshold: read the token burn at the first prompt and see whether the folder is deferring anything.

The Codex harness answers the same size problem twice, with two different mechanisms, and the split is the useful part. For the tool registry — the term OpenAI names as the one that grows without bound, "especially if you install MCPs" — the answer is [deferring tool definitions out of context entirely and giving the model a tool-search tool](../concepts/defer-tool-definitions-out-of-context-and-let-the-model-search-for-them.md), so a definition is paid for only when the model asks for it. For skills, where the list has to stay visible or nothing would trigger, the answer is a budget: [2% of the maximum context window](../concepts/cap-the-skills-list-as-a-share-of-the-context-window.md), with the harness trimming individual descriptions as the catalog grows rather than dropping entries. Both are worth reading against the retrieval-based routing this topic already documents. A router selects ahead of the model on the user's first message; Codex lets the model select mid-trajectory once it knows what it needs, at the cost of a round trip and with no published accuracy comparison either way. Two of the other tooling decisions are argued from the weights rather than from ergonomics — the diff format, the search binary, and the shell dialect are chosen because the model was trained on them ([Match Agent Tooling to the Model's Training Distribution](../concepts/match-agent-tooling-to-the-models-training-distribution.md)) — which is a real constraint on tool design that this topic's usual "write better descriptions" advice does not cover. And computer use is recast from a fixed action enum into [a persistent scripting session](../concepts/drive-computer-use-through-a-persistent-scripting-session.md), which moves the capability ceiling from the harness author to whatever library the sandbox can import.

Almost everything above concerns which tools the model can see. Frank Coyle's reading of Anthropic's certification blueprint supplies the piece underneath that — how the harness knows a tool call was requested at all, and whether the response containing it is even complete. The API returns a `stop_reason`, and the loop branches on it rather than on the text: `tool_use` means run the requested tool and feed the result back, `end_turn` means stop, and `max_tokens` means the model hit its output ceiling and the response is cut mid-sentence ([Read the Stop Reason Before You Read the Answer](../concepts/read-the-stop-reason-before-you-read-the-answer.md)). The third case is the one that bites tool authors, because a truncated response carries no marker in its body — a half-written tool-call argument, a JSON object missing its closing brace, or a summary that simply stops are all indistinguishable from short-and-finished if you only read the content. Coyle says it "happens more often than you might think" and gives no rate; the wiki has no other source that reports one. He also puts a tighter bound on tool count per agent than anything else here — a subagent should do one thing "with maybe one or two tools available to it," argued from single-purpose functions rather than from measurement — which is a design bias worth naming alongside this topic's registry-size mechanisms, since deferring, budgeting, and searching all assume the catalog is large in the first place.

Imad Touil (QuantumBlack) supplies an authorship cut through the tool layer that this topic has mostly described functionally. Asking which of a workflow's four components an organization actually writes, he answers only one: hooks are triggers, sub agents manage the context window, and MCP servers are overwhelmingly installed rather than authored — "we just use MCP tools that is actually provided by the tool that we used to use before… so we don't really own." That leaves skills as the residual where org-specific knowledge accumulates, which reframes the skills-versus-MCP split this topic already holds: integrations are commodities across companies and get shipped by whoever owns the system, while the knowledge of how your company uses them is not a commodity and nobody will ship it to you. The catalog that makes such a library usable owes specific mechanics — searchable metadata, an MCP over the catalog plus a CLI that pulls a skill into an IDE or sandbox, inter-skill dependencies, versioning so a harness pulls the current release, access control, and evaluation — but not composability, which has to be decided by a domain carve before anyone authors. The security note belongs here too, and cuts against the convenience of public skills: "skills actually does have scripts because that is the deterministic part of it," so an unvetted skill is an action-capable extension arriving through a lighter channel than an MCP server, with no server to register and no credential to issue. Nothing in the talk is measured, and the cross-harness portability claim ("a skill on Claude Code… move it to Cursor, it's going to just work") is asserted rather than demonstrated.

Jesse Lumarie's account of building Figma's first MCP server adds the constraint most of this topic's tool-design advice assumes away: the client. Figma maintained "the client compatibility matrix from March 2025" as a real artifact, because "many clients only implemented a subset of the spec, and many features were very experimental," so "it was hard to kind of understand what you were building towards." Three spec features they needed — server instructions, elicitation, and sampling — were unimplemented, hollow, or deprecated, and all three were reimplemented through the one primitive everyone had built. Instructions were appended to every tool result; a consent step became a returned prompt; a codebase scan became a second returned prompt asking for matches "in a specified format… in bulk." The sharpest observation is that presence is not sufficiency: "for sampling even when VS code supported it you could only really query it as a general agent not specific to the codebase," so the primitive existed but was not wired to the context that made the workflow worth doing. The talk also contributes a representation rule one level below this topic's existing text-over-pixels argument — among three serializations of Figma's own scene graph, the winner was chosen by pretraining mass rather than by fidelity to the domain — and a compression rule that avoids the usual trade, returning a pointer to the consumer's own component rather than a generated copy of it. Nothing in the talk is measured: there is an eval, but no score, and the one outcome claim is the unquantified "one of the fastest growing products that they've ever had."

The verification tool landscape organizes cleanly around one question this topic can reuse: who translates your program into the prover's logic, and what does that translation cost you. Lean sits at one end as "a programming language and a proof assistant… the same language for the definitions and proofs. There's no translation layer" — nothing to lose in translation, at the price of the shipping artifact being Lean. Verus, open-source and built on the Z3 solver, takes annotations in place: `requires` and `ensures` pre- and post-conditions inline in the Rust source, "a static check… enforced by the verifier and erased at runtime." Aeneas automates the translation instead, consuming Rust's mid-level intermediate representation and producing a functional model in Lean. AWS's work-in-progress Strata generalizes it once for many languages — author a dialect, lower it to Strata core, then "dispatch it to any of the engines." Underneath the tool names is a distinction worth carrying: a proof assistant is interactive tree search with backtracking, while "a solver is a calculator, a very powerful one. You feed in a formula and it returns an output. In this case, satisfiable or unsatisfiable" — so the solver route answers by itself but wants annotations, and the prover route wants a search someone has to drive, which is the labour a coding agent can now take over. The tooling claim that most deserves scrutiny is the trust one: Lean's kernel is small enough that "you yourself can actually go write one," with open-source implementations "in C++, Rust, Lean." Three of the five artifacts named (Kiro, Cedar, Strata) are the speaker's employer's, and none of the five arrives with adoption or cost data.

A gateway is the enforcement point this topic keeps arriving at, and Manuja supplies the argument against making it one deployment. His observation is that most organizations asking for a single company-wide LLM gateway have misdiagnosed their own requirement — "it's not the central gateway that they want. They want centralized governance" — so the recommendation is to [decentralize the gateway and centralize the governance](../concepts/decentralize-the-gateway-centralize-the-governance.md): "do not try to centralize your traffic, but you can have plugins, you can have custom code that can centralize your governance," where governance means cost tracking and rate-limit management. Organizational ownership and topological centralization are separable — it "can be managed by a single team," but he "wouldn't recommend deploying it as a single deployment for the entire company" — and only the second creates a failure domain shared by every team in the request path. That is a direct tension with this wiki's case for a gateway as a complete observability chokepoint and as an enterprise root of trust, both of which draw their guarantee precisely from all traffic passing one place. The reconciliation on offer is that the governance plane can be central while the data plane is not, at the unpriced cost of policy-version drift across many deployments; the talk asserts the plugin path rather than demonstrating it, and names no product or reference architecture.

Agentic commerce is the clearest current case of a domain deciding that generic tool-calling is necessary and not sufficient. Ahnaf Prio (Best Buy) places the five relevant specifications on separate layers — MCP names a merchant's capabilities, A2A carries messages between two organizations' agents, ACP and UCP supply the commerce vocabulary, AP2 carries payment authority — so the practical question is not which to pick but which layer a given problem sits on ([Map the Agentic Commerce Protocol Stack by Layer](../concepts/map-the-agentic-commerce-protocol-stack-by-layer.md)). What MCP cannot supply, and what the commerce specs exist to fix, is agreement about meaning: an `add_to_cart` tool with a quantity argument is expressible in MCP, but whether a second unit is a quantity change or a second line item is a merchant-side distinction the buyer's interface deletes. The most counterintuitive tool-surface finding here inverts the usual advice about exposing APIs to agents: both ACP and UCP decline to offer a catalog-search call and instead require merchants to push a product feed the aggregator indexes ahead of time, for a query-time fan-out reason ("if you have M number of merchants and N number of products, now it has to call that many") and a ranking-economics reason ([Push a Product Feed, Because Per-Merchant Catalog Search Does Not Scale](../concepts/push-a-product-feed-because-catalog-search-does-not-scale.md)). The cost lands on the merchant as a schema tax and a sync loop — ACP, UCP, and Meta's feeds are "similar, but still different," and inventory sync in the demo runs "every couple of seconds" — which is strictly more work than publishing one API and is worth weighing against this wiki's general preference for agent-native APIs over feeds. It also marks where in-page tool surfaces stop: agentic shopping reached WebMCP's conclusion about DOM-guessing and then went further, moving the transaction off the page entirely, because an in-page tool still runs inside a browser session the merchant's fraud stack is trying to identify. The talk carries no measurement, and its support matrix is a dated snapshot.

Tool and surface proliferation has a cost that shows up in the user rather than in the architecture diagram. When a vendor ships a coding CLI, a general workspace, and a chat app that cannot delegate to each other, the user becomes the transport between them — and the diagnostic Krieger offers is a copy-paste handoff the product asks for: "can you please create a paragraph that I can paste into Claude Code? That is some 2020 kind of workflow that really shouldn't exist anymore." The companion test is explicability, since surfaces split along implementation boundaries are also the ones an ordinary user cannot tell apart. The same argument applies to tool primitives over time: a more general primitive is grounds for retiring the specific one it subsumes, which is how prescriptive styles gave way to skills.

The buying side of tool design gets a sharp criterion from a company that kept its CRM rather than replacing it: choose systems that are arbitrarily customizable, which in practice means the vendor ships a programmatic surface an agent can drive. Salesforce survives at an agent-first company because "it exposes MCP. So all of our agents have access to Salesforce MCP," and because the domain decisions embedded in it are ones the buyer did not want to make. That reframes an MCP server from an integration nicety into a procurement requirement, and it applies inward as well: a company's own internal data needs the same treatment before an internal agent fleet can do anything, with the interface itself left deliberately unspecified — MCP, CLI, or plain API, as long as it is programmatic.

A tool description is not only guidance about when to call something; it also has to contradict what the model already believes. Jarmak's Sourcegraph trace is the clean case: the model expected a parameter name from its training data, "there's nothing in our description that would have led it to believe otherwise," and it called a read tool with `read line` instead of `start line`. The tool behaved correctly, the description was merely silent, and silence let the prior win. What makes this worth instrumenting rather than shrugging at is the cost model — the agent recovered from its own error text and still burned a full turn, so the defect is invisible in a success rate and visible only as tokens and latency, which is exactly what organizations evaluating a third-party agent tool now count. The way to find these is to manufacture the traces: run a representative task set with and without your tool and read what the agent did. And once the tool is good, it still has to be reachable — present in the marketplaces and MCP registries an agent would search, with an adoption path the agent can hand to its user without a sales conversation attached.

A skill library serving a non-engineering organization needs an intake point before it needs a package manager. Cloudflare distributes go-to-market skills through a central alias where they are submitted, reviewed jointly by the business team and the operations team, and curated toward "an expert-level knowledge skill at every level" — no install step, no version pin, no dependency resolution, with named humans performing the discovery and quality functions a registry would. The stated purpose is to prevent proliferation during what the speaker calls a Cambrian stage of agentic systems, and the risk being managed is not oversized skills but divergent ones, since independently authored definitions of the same metric make source-of-truth alignment across systems fail. Two reviewers rather than one is the part worth copying: the business owner checks that the encoded procedure is what an expert would actually do, and the data owner checks that the query underneath is right, and either can approve something fluent and wrong in the other dimension. The honest limit is that human review at an alias is the first thing to break when authoring rate rises, which is exactly what an auto-authoring loop would do to it.

An orchestration layer built for many external systems suggests a small tool vocabulary rather than a large connector catalog. Clay converged on five general-purpose node types — agent, tool call, conditional, code, and a map-reduce fan-out — with the claim that this is the right shape whether you buy the layer or build it. Two things follow. The map-reduce node, not the agent node, is what gives the graph its scale, because enrichment, scoring, and messaging are all per-record operations over a list and fan-out is the only primitive that changes cardinality. And a small primitive set is a good execution model without being a good authoring model: the graph is what runs, not necessarily what anyone writes by hand.

## Open Questions

- How is a conformance test written against a specification that is still moving? Protocol compliance is offered as an eval axis with real teeth — non-conforming feeds mean "they will not support it" — but ACP-versus-UCP convergence and identity-consent standards are simultaneously listed as unsettled. No source in this wiki describes how a merchant detects that a spec changed under it before the channel does, which is the difference between a conformance eval and a post-mortem.

- Can a root of trust survive a distributed data plane? Enterprise gateway arguments in this topic derive their guarantee from every request passing one place, and the counter-argument derives its safety from no request having to. Nobody here works through the hybrid — a central policy and audit plane with distributed enforcement — well enough to say which guarantees survive it and which quietly become best-effort. ([Manuja](../sources/20260828_zrZ1amZBSPw.md), 14:34-15:42)
- Does a shared verification IR pay off across languages, or does each dialect end up carrying the hard part? Strata's premise is that lowering many languages to one core lets a single set of proof, SMT, and model-checking back ends serve all of them, but it is explicitly "work in progress" with no adopters, no dialect other than the demo path, and no account of how much language-specific semantics a dialect author has to get right. ([Pant](../sources/20260828_lRa9sPaMyy4.md), 08:26-09:12)
- When a server emulates a protocol primitive through tool results, what fraction of the time does the agent actually honour it? Figma reconstructed consent and delegated search out of returned prompts, and the guarantees the primitives existed to provide — a client-rendered dialog, a typed response, an enforced result format — are replaced by model compliance. No source in this wiki reports a compliance rate for an emulated primitive, and the answer determines whether emulation is a workaround or a liability.
- What actually breaks when a skill moves between harnesses? Portability across harnesses is claimed as a property of the open standard, but a skill carrying scripts also carries assumptions about the sandbox, available tools, and permission model, and no source here reports a cross-harness failure mode.
- How often does output truncation corrupt a tool call, and what should the harness do about it? Coyle warns that `max_tokens` stops are more common than expected, but names no rate, no detection strategy beyond reading the field, and no recovery policy — retry with a larger budget, ask for continuation, or fail the step. Nothing else in this wiki reports the frequency either, so a failure mode that produces malformed arguments rather than error responses is currently unquantified.
- How does a model learn that a deferred tool exists? Marking a tool as deferred keeps its definition out of the registry, and the model is expected to find it with tool search — but a search only returns what the query matches, and no source describes what signal tells the model to look for a capability it has never seen listed.
- Is model-timed tool search more accurate than query-timed retrieval, or just later? The two approaches are now both documented here, with measurements on only one of them: a semantic router holds above 83% correct-tool selection across catalog sizes, while the deferred-loading side reports no accuracy figure at all.
- Should a context budget be a percentage of the window or an absolute token count? A 2% share automatically grows with context length, which is convenient and also assumes the useful skill-list size scales with the window — an assumption nobody has tested, and one that quietly enlarges the always-loaded surface with every model release.
- What is a skill file's size limit actually a limit on? A 100-line cap is a proxy for the tokens a folder charges at load time, but a line can hold a sentence or a table, and no source reports what the cap costs in rejected content or how often material pushed into reference files then goes unread.
- What does an agent see when a tunneled MCP server's connection drops mid-session? An outbound-only tunnel makes the tool set a live dependency on a long-lived connection, and no source describes whether the tools disappear from the agent's inventory, fail on call, or block — each of which produces very different agent behavior.
- If code mode generalizes to any large corpus, what is the boundary of the pattern? Hylak's trace-classifier transplant carries no cost comparison, no coverage figure, and no example classifier, so there is nothing here to tell you when writing a program over the data beats sampling it into a model's context.
- Batra's rendered-state examples are all cases where the DOM lacks the answer, but the accessibility tree sometimes carries it (`aria-disabled` on the grayed-out option). No source measures how often a page's semantic markup preserves state that the raw DOM drops — which would decide whether accessibility-tree reading is a cheap substitute for pixels or merely a cheaper way to be wrong.
- Which AI features belong inside the user's existing host application as a plugin, and which need their own runtime because the host's real-time or process constraints would break them?
- When a closed tag or descriptor vocabulary is the whole action surface, how should the platform team discover what the vocabulary is missing — from failed agent calls, from user complaints, or from the assistant proposing new tags it wishes existed?
- When should a workflow be encoded as an MCP tool description, a skill, a local script, or a combination of these?
- When is server-controlled command prompting a better product surface than visible UI controls?
- What telemetry is needed to decide that a skill or tool is unused, stale, or actively harmful?
- When should a context engine expose the same capability through MCP, CLI, API, or a messaging integration?
- What security checks should run before a registry skill or context package is loaded by an agent?
- Which agent operations should be implemented as deterministic scripts rather than LLM tool calls?
- Which personal-agent tool calls need visible progress, cancellation, or capability toggles before users will trust them?
