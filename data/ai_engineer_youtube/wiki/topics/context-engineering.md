# Context Engineering

## Overview

Personal-agent context can be made visible through nested topic descriptions and explicit attachments rather than only opaque memory. When a workspace lets the user attach the relevant document, knowledge base, password, or skill to the current task, the context contract is easier to inspect and debug than a hidden retrieval decision.

Context engineering treats prompts, skills, memory, retrieval, and documentation as an engineered substrate for agent work. It needs a lifecycle similar to software delivery: generate context, evaluate it, distribute it, observe its use, and adapt it from feedback. Demand-driven context adds a practical enterprise workflow: rather than predicting every context need upfront, assign real work to agents, observe failures, and convert missing institutional knowledge into reusable context blocks. Personal knowledge bases show the same pattern at individual scale: Markdown notes, bookmarks, project records, search, and memory become useful agent context when ingestion flows add tags, connections, and surfacing rather than merely storing links. Read-only personal intelligence adds a useful variant: emails, journals, tasks, browser history, notes, and relationship data can be synthesized into reflection artifacts without mutating source systems. A context engine is the selection and reasoning layer for this substrate: it should combine task relevance, user and team signals, source relationships, permissions, and conflict handling rather than relying on generic RAG, many MCP servers, or larger context windows alone. For productized codegen, current Markdown docs, shared domain glossaries, and compact exemplar projects can offset stale model knowledge and weak architectural priors; context can be generated from a service into skill references and loaded only when the task requires it. Conversational-agent state adds a related context-management concern: server-side interaction IDs can simplify continuation and branching, but retention, retrieval, and compaction limits remain part of the application design. Small-model preprocessing can further manage context by filtering, classifying, extracting, or reranking data before it reaches the agent. Skills and context packages distribute reusable workflow guidance, but package-like reuse also creates versioning, dependency, quality, and security concerns; volatile API facts should often stay in current documentation that skills point to rather than being copied into every skill.

Product engineering adds a customer-context layer to this problem. If AI handles more of the mechanical implementation, engineers need searchable customer conversations, tagged feedback, recorded calls, and direct customer channels so product judgment is grounded in real needs rather than abstract feature requests.

Prompt-learning workflows show a narrower context loop: when traces or datasets include explanatory feedback from subject-matter experts or evaluators, that text becomes context for improving the next system prompt. Bare labels are less reusable because they do not identify the missed instruction, missing context, or rule violation that future prompts should address.

Agentic context optimization should not be treated as one universal loop. Meta-adaptive context engineering frames context reflection as one strategy among several: a task profile can choose minimal context for simple work, AC-style reflection for incremental context updates, structured memory retrieval for hard tasks, or verification and extra compute when feedback is weak. That framing challenges a context-only optimization instinct: sometimes the right fix is less context, more execution checking, or a different resource allocation.

For coding agents, the same loop can target repository or agent rule files directly: benchmark traces, unit-test results, and judge explanations can be fed into a meta-prompt that writes learned instructions for the next run. AI-native company workflows add a team-level version of the context loop. Lessons from delegated agent work can be codified into `CLAUDE.md`-style files, subagents, slash commands, prompt libraries, and onboarding guidance so tacit conventions become reusable agent-readable context rather than private memory.

Long context should be treated as temporary working memory, not durable knowledge. Large prompts can keep a model from outright lacking a document, but attention cost, latency, and context-rot behavior mean "fits in the window" is weaker than "the model can reason over it reliably." For stable long-tail knowledge, the design choice may move from prompt stuffing to retrieval, contextual embeddings, or model adaptation.

Paul Iusztin and Louis-François Bouchard push that "durable knowledge lives outside the window" idea into a concrete personal-memory architecture: a [file-based research wiki with progressive-disclosure retrieval](../concepts/file-based-research-wiki-with-progressive-disclosure-retrieval.md). The premise is that with an agent "the context window becomes everything… and when you stop the conversation, it loses everything," so the bottleneck is not how much context you feed but how you *reuse* it — which calls for a memory layer sitting between a "second brain" (10,000+ notes across Obsidian, Readwise, Notion) and any harness (Codex, Claude Code). Their build deliberately "forgets the infrastructure you think you need" (vector DBs, knowledge graphs, semantic search) in favor of plain Markdown plus a reference index, structured in three tiers — immutable raw sources, an `index.yaml` catalog of summaries/metadata, and an LLM-generated wiki of derivatives (per-source executive summaries, concepts, entities, comparisons, notes, open questions). The retrieval discipline is the reusable part: read cheapest-first — index → source executive summary → wiki derivatives → raw source only as a last resort — so an agent rarely loads a whole raw document. The wiki is "alive": every question the user asks spawns a derivative file and is logged, so the store compounds from *use*, not only from ingestion, while the raw personal vault stays an immutable snapshot the LLM never edits. This is the personal-scale counterpart to Augment's team knowledge infrastructure and to the reset-from-files patterns above.

Context platform engineering adds an inference-side complement to context selection. Agentic coding sessions often resend system prompts, tool calls, and tool responses far more than direct user text, so context engineering should consider which repeated regions become KV-cache working sets and how cache time-to-live interacts with human pauses and fast tool loops.

Tool-heavy agent sessions also need active cleanup inside the working window. Memory can keep durable patterns and preferences outside the prompt until they are relevant, while context editing removes stale tool outputs that otherwise crowd out current task context. Knowledge graphs add a structured memory option when relationships matter: semantic and procedural learnings can become nodes, relationships, properties, embeddings, and access overlays that agents can traverse and humans can inspect. Expert advisory systems add a decision-taxonomy variant: knowledge, experience, insight, current situation, and decision-making relationships can become graph context that guides recommendations rather than only retrieval. Tool definitions and responses should be treated as first-class context artifacts: in agent loops, tool schemas and outputs can dominate the token budget more than the system prompt, so context engineering includes how tools are named, described, scoped, and serialized. The same discipline applies to a browser agent's observation of a web page: a raw DOM dump (~20k tokens) or a single screenshot (~1,100 tokens but only one viewport) is a poor context artifact, whereas a compact markdown representation (~1,800 tokens) captures the *whole* page and can be paired with a screenshot for cheap visual grounding.

Coding-agent subagents are another context-management lever. Instead of forcing one agent to spend its main window on broad repository search, deep reasoning, dependency lookup, or codemod planning, a specialist can consume context in a separate window and return only the useful result.

Context compression for coding agents is not just about fitting files into a smaller prompt. Nations' Netflix example shows that a multi-million-token codebase can be reduced into a research document and implementation plan only after humans select relevant architecture, diagrams, interfaces, requirements, and sometimes a manual migration seed. The goal is to distinguish intended design constraints from accidental local patterns before generation preserves both as if they were requirements.

Proactive agents add a timing constraint to context engineering. A background coding agent needs current project observation, personalized preferences, repository and environment knowledge, editable memory, and just-in-time task context so it can consult the right guidance before interrupting the user. Context that arrives too soon becomes noise, while context that arrives too late misses the intervention window.

AI code review turns context quality into a trust issue. Review and generation tools need access to the relevant standards, best practices, version history, PR history, organizational logs, and current code context; otherwise developers can distrust the LLM's judgment even when the model is capable.

Taste models turn repeated code edits into another context source. Instead of asking developers to encode every convention in `AGENTS.md`, `CLAUDE.md`, or prompt files, a system can infer preferences from how generated code is corrected, expose the learned taste as a transparent artifact, and inject it only when the current task matches the relevant domain, project, or team scope.

Augment's adoption path treats knowledge infrastructure as the team-scale context substrate for coding agents. Map existing docs, repositories, task trackers, and meeting outputs; capture decision knowledge that would otherwise disappear; connect sources through MCP or native integrations; and share successful memories or task lists so one engineer's agent workflow becomes reusable context for others.

Frequent intentional compaction is a coding-specific context-engineering workflow. It treats the active context window as a limited, trajectory-sensitive working area: preserve correct current facts and intent in reviewed Markdown artifacts, start fresh sessions from those artifacts, and prefer on-demand compressed context from current code over broad static onboarding docs that grow stale. Per-feature context packaging adds a planning-artifact variant of the same idea: after a master specification, feature inventory, specifications, dependencies, and implementation plan exist, the implementation agent should receive only the sections relevant to the current atomic feature plus its dependencies and validation strategy.

Repo-local task files are a smaller-grained version of this context packaging. A Markdown task with acceptance criteria and status can define what one agent run should do, what it should not do, and how completion will be checked; because it is versioned in Git, it remains available after chat context is compacted or discarded.

Architecture copilots add a system-map version of context engineering. Instead of relying on stale architecture docs, they normalize current cloud, Kubernetes, service, logging, dependency, drift, business-objective, and standards context into a live model that an AI can use for architecture recommendations.

Repository architecture can turn context engineering into the adoption bottleneck for coding agents. In PR telemetry, highly distributed codebases did not show the same AI-adoption-to-throughput lift as centralized or balanced codebases, plausibly because tools and agents operate best inside one repository while product, service, and ownership relationships span many repositories and remain undocumented.

Production AI coding adds a low-level context hygiene requirement: the agent needs current standards, package choices, development setup, task boundaries, and implementation direction in explicit files rather than in tribal memory. Rules files and Markdown plans can become reusable prompt context when they describe the intended workflow and stack, but they should be paired with tests, linters, and review because the model's fluent statements about what it did are not reliable evidence by themselves.

Devin 2.0 adds a codebase-intelligence layer to this context problem. Raw source text is not enough for broader bug and feature work; agents and humans need structural and historical representations such as call hierarchies, language-server output, commit history, lint feedback, and generated codebase explanations before they can plan consistent cross-file changes.

Stored agent conversations are themselves a context source worth engineering. WorkOS's sustainability talk treats locally saved JSONL session logs as "gold": a scheduled pass over them finds where the human and agent spent many thinking tokens or went back and forth to remove ambiguity, then converts that delta into the skills, MCP servers, or rules that were missing — so the harness improves its own future context from real usage rather than from speculative upfront curation. The caveat is that raw JSONL is not built for AI consumption, so a session-end or PR-merge hook can extract the key bits (especially the struggles) into a cleaner store before the analysis runs.

Data-and-tool agents add a just-in-time injection discipline at the level of individual tools. WorkOS's Studio runs a preflight checklist (are tools connected, is there enough context, otherwise ask) and then injects each tool's heavy schema/usage context only at the moment that tool is invoked, explicitly to avoid preloading every tool's instructions and blowing out the window — the single-agent runtime counterpart to MCP tool-budget discipline. The prompt is layered (base defaults, org rules, per-tool context preserved across edits) and includes a primary-source rule: distrust the model's own knowledge of a fast-moving product because training data is stale, and look up docs instead. Notably this needs no RAG store; LLMs read self-descriptive table schemas well, so a hand-written context block encoding join quirks is enough to "just invoke tools with context on top."

Qodo's "more context makes your agent dumber" framing supplies the failure mode behind all of this curation work. Current models attend to the start and end of a prompt and quietly drop the middle — a "U curve" Qodo observes when benchmarking which provided context actually shows up in the result — so growing the window does not help and dumping a whole codebase makes results worse, with mid-prompt additions ("I have Jira, I have MCPs") purged so the model can make sense of the task by itself. The corrective is to pick a context-supply strategy by developer-input cost and scaling rather than asking the model to be smart enough: a ranking context engine (good for messy codebases but unpredictable past ~600-700 repositories), per-file/folder hierarchical summarization (high upfront and re-map-on-change cost), a knowledge graph (very high setup, wins on cross-repo logical dependencies), iterative retrieval (a low-setup "library card" index, the recommended default for non-product teams), or self-correction with a critic node (adds latency, low setup). This corroborates the long-context-is-not-memory and keep-context-small concepts with a positional, not just volumetric, account of why curation matters.

Safe Intelligence's "capturing decisions" practice adds a context-engineering corollary: decide what *must not* depend on the context window at all. Because humans and LLMs share the same weakness — people forget and LLMs compact, humans leave and LLMs have no memory — Michal Cichra externalizes the rules and their rationale into git hooks, CI, linters, and ADRs so that surviving a context compact is not a problem. His sessions run 20–50 compacts with "no fear of context compacts" precisely because the important rules live outside the prompt and the agent re-looks-them-up on demand; the prompt then carries task-specific working context while the durable policy stays in the harness. This is the complement to frequent intentional compaction (which compresses useful state into reviewed artifacts) and to repo-local task files (which survive a compact because they are versioned in Git): all three move what the agent must not lose out of the volatile context window.

Kyle Jaejun Lee (KRAFTON) adds the most operational version of "decide what must not live in the window." Running a personal agent fleet, he treats each entity's state as files on disk (a mission/status/handoff layout per workspace) and, when the window fills, *resets instead of compacting* — clearing the context completely and letting the agent re-read its own handoff and history files — because compaction is slow, lossy, and gives you no control over what survives. Externalizing state that way makes the model's context disposable: work survives not just a compact but a full wipe or a machine crash (a single boot command rebuilds the fleet from files). This is the file-backed, reset-based cousin of Cichra's rules-in-the-harness and of frequent intentional compaction — all three keep the important thing out of the volatile window, but Lee's is a standing self-authored state store the agent re-reads after a clean clear, not a curated summary or an external policy check.

Lovable turns the demand-driven loop into a continuously-running context store. At ~200,000 projects/day, an LLM judge detects "stuck → solved" transitions, the system asks "what should we have injected at the start of this query?", clusters similar cases so the captured fix generalizes instead of overfitting to one prompt, eval-verifies it, and a lightweight model injects the matching entry into future runs just-in-time. Two engineering disciplines make this safe rather than bloating. First, each entry's real value is measured with a blank-injection holdout — for a small sample the system injects nothing and compares project success — so entries are ranked up or down by measured outcome, not assumed usefulness. Second, the bank is pruned aggressively: entries go stale "incredibly quickly" whenever a model or feature changes, so rebalancing and discarding deprecated knowledge is a standing maintenance task that keeps context rot from creeping back in — the store-level version of keeping a single session's context small and fresh.

Matt Pocock's "missing manual" for agent skills turns skill authoring into a concrete context-engineering rubric with four axes. The **trigger** axis makes the [user-invoked vs model-invoked choice](../concepts/choose-skill-trigger-by-trading-context-load-against-cognitive-load.md) a load-balancing decision: each model-invoked skill adds a description to every request and introduces the unpredictability that forces skill evals (context load), while user-invoked skills stay deterministic but push the burden of remembering them onto the pilot (cognitive load) — so, contra the instinct that model-invoked is "more flexible," both have symmetric costs. **Structure** operationalizes progressive disclosure: decompose a skill into steps and reference, keep `SKILL.md` as small as possible, and hide branch-specific reference behind context pointers to external files, because every word shaved is a token shaved off every use. **Steering** adds two behavior levers that are about phrasing rather than volume: [leading words](../concepts/steer-agents-with-leading-words-that-surface-in-reasoning-traces.md) (dense phrases like *vertical slice* that the agent echoes into its reasoning traces, letting you verify the steer worked by reading the traces), and [splitting skills to hide future steps](../concepts/split-skills-to-hide-future-steps-and-force-leg-work.md) so the agent does more leg work on the current phase instead of rushing a visible goal. **Pruning** keeps the whole thing small through a [single source of truth, sediment removal, and no-op deletion tests](../concepts/prune-skills-with-single-source-of-truth-sediment-and-no-op-deletion-tests.md). Together these give the previously-generic "keep `SKILL.md` minimal" advice an actionable checklist, and answer the open question of what belongs in `SKILL.md` versus referenced files: whatever is used on every branch stays inline, and everything else moves behind a context pointer.

Rajkumar Sakthivel (Tesco) supplies the cost argument under all of this curation work. After an AI-coding bill jumped ~£15→£200 in a month with no usage change, the diagnosis was that the money was in context, not "AI thinking": a typical query sent ~45,000 tokens when only ~5,000 mattered, and [~90% of AI-coding cost is input, not output](../concepts/cut-coding-agent-cost-by-fixing-the-input-not-the-model-or-output.md) — so cutting output 75% saves only ~8% of the total while cutting input 94% saves ~61% ("fix the input"). This reframes "keep context small" from a quality concern (context rot, the U-curve, attention limits) into an economic one: you pay for every irrelevant token on every query, and prompt tweaks ("be short, only show relevant code") change nothing because the oversized context is already charged before the model reads the instruction. His mechanism is a [local code-index retrieval layer between the codebase and the agent](../concepts/insert-a-local-code-index-retrieval-layer-between-codebase-and-agent.md) that returns only the relevant pieces, with one shared index and a memory layer across tools (Claude Code, Cursor, Copilot) so the codebase is "explained once" instead of re-discovered per tool — the shared-index counterpart to Cursor's Merkle-tree diffing and to demand-driven context capture.

Thariq Shihipar (Anthropic) adds a system-prompt corollary that inverts as models improve: [shrink the system prompt and drop examples as models get more capable](../concepts/shrink-the-system-prompt-and-drop-examples-as-models-improve.md). Claude Code "removed 80% of the system prompt" for its newest model class because "the examples tend to constrain it — it's more imaginative than the examples we give it," and the guidance flipped to "give it context and not just constraints… avoid being like 'do not do this'." The best-practice arc runs small-prompt-few-tools-many-examples (Sonnet 3.5-new) → large-prompt-many-tools-many-examples (mid-generation) → *smaller* prompt with *fewer* examples (newest class), so a prompt inherited from an older model is itself stale context that overconstrains a stronger one — the same lesson as prompting around learned model habits, applied to the system prompt's size and example density rather than to individual instructions. His second-half message reframes the *human's* map (plan/prompt/spec) as context that must match the *territory* (real codebase): every gap becomes an "unknown" the model guesses at, so [use the agent to surface your own unknowns](../concepts/use-the-agent-to-surface-your-own-unknowns.md) — a blind-spot pass, an interview, a reference codebase or HTML mock-up passed in as "another map" — is a context-gathering move that fills the spec before generation rather than after.

Erik Hanchett (AWS) supplies the loop-mechanics reason all of this curation pays off repeatedly: in an agent loop the system prompt, tool results, and conversation history are re-transmitted to the model on *every* iteration, so token spend compounds with loop length unless you [shrink the per-step payload the loop re-sends](../concepts/shrink-the-per-step-payload-the-agent-loop-re-sends.md). His three payload levers are the code-level, framework-agnostic form of threads already in this topic: cache the static prefix (system + tool prompts, e.g. Strands' `cache_prompt`) so it is sent full only once — the application-side counterpart to engineering KV-cache working sets; offload a large tool result out of the message stream and keep only a summary so it isn't re-added every loop — the cost-side version of context-window editing that clears stale tool results; and window the conversation history (Strands' `SlidingWindowConversationManager`, e.g. last 10 messages) so a long multi-turn transcript isn't re-sent each turn, with the lost-early-context tradeoff recovered by summarizing older turns into the window — the cheap, mechanical cousin of frequent intentional compaction. The framing complements Sakthivel's input-dominates-cost argument (which attacks the size of the *retrieved* context) by attacking the *repetition* of context across loop steps: even a well-curated context is charged again on every iteration, so making each re-sent part small multiplies through the whole run.

Isadora Martin-Dye pushes prompt composition itself into an architecture discipline: [layer brand voice into four composable prompt tiers](../concepts/layer-brand-voice-into-composable-prompt-tiers.md) instead of writing one "write in our brand's voice" system prompt that "works for the happy path" but breaks on the first uncovered turn. A single prompt is being asked to do four incompatible jobs — be inviolable, be situational, be expressive, and check itself — and her fix decomposes those into ordered tiers assembled through one function: immutable identity (hard constraints nothing below can override), situational mode (real-time who/what-they're-going-through signals injected *before* generation), example-anchored voice (the tone guide, "where most teams start and stop"), and a post-generation veto. Two of her rules are directly context-engineering moves. First, *order is load-bearing*: the assembly renders soft-context tone notes *before* numeric constraints so the model sets tone first and then satisfies the numbers, because reversing it "makes the prose feel mechanically slotted" — the intra-prompt ordering counterpart to the lost-in-the-middle positional findings above, applied to a hand-composed prompt rather than retrieved chunks. Second, in a multi-tenant system *identity must never default*: silently-defaulted brand-identity fields leaked one venue's persona into others ("every venue shipped as sage@hawthornemanner.com… a white label leak"), so "a missing brand identity is a crash, not a fallback. It must fail loud" — a fail-loud discipline for the shared vs per-tenant split of a composed prompt. The deeper lesson generalizes past voice: her fourth tier is not a prompt at all but a deterministic gate, and [the first three layers being probabilistic instructions while the fourth is deterministic permission](../concepts/gate-generated-output-with-a-deterministic-veto.md) reframes where context engineering ends — "everything before layer four is prompt engineering, asking nicely and hoping," so the parts that must not fail belong in a check that reads the output, not in more instruction (the outbound-content cousin of Cichra's rules-in-the-harness and Talha Sheikh's completion gate).

Vasant Kearney (Onlay) adds the enterprise constraint on where the memory half of this substrate can physically live, and a warning about what well-working memory costs. Coding agents keep memory as files the operator owns — "cloud code or codex, they use local memory, they write to your desktop" — which "in enterprise healthcare, we can't really do," so the pattern becomes [tiered database memory with an escape hatch](../concepts/give-enterprise-agents-tiered-database-memory-with-an-escape-hatch.md): memory in a database "just so we have that logical separation," split into partner/organizational and user tiers. The tiers earn their keep on repetitive enterprise work, where people "tend to do the same thing day after day," so a few words plus the user's history resolve what one person means and another does not. The warning is the part this topic has not owned: persistent memory across chats and days "also introduce[s] bias" — the user may not want to repeat yesterday, "and now you steer them to do the exact same thing they did yesterday" — so the required mitigation is an escape hatch ("any user can break out of this"), not better retrieval. That is a different failure than the ones already catalogued here: explicit attachments address *not knowing* which context was used and utility ranking addresses retrieving the *wrong* memory, while this is a correctly retrieved memory quietly narrowing the user's options. Kearney's other context caution runs upstream of retrieval entirely: flattening a multimodal record before a downstream model — reducing an image to findings, anatomy, and geometries and then combining it with EHR data — can be right on cost and capability grounds but loses whatever mattered "to some downstream procedure that the upstream model wasn't aware of," the same premature-summarization risk this topic notes for text.

Arturo Nunez (Nereu) contributes the cleanest statement this topic has of a graded middle between "send the whole state" and "retrieve on demand," and it comes from a field that solved the same problem for pixels. His agent edits a live 3D scene, and serializing it does not scale: a demo scene holds roughly a hundred assets, "but most of them are like grass that we could ignore. It doesn't really make sense." So he borrows level of detail from rendering — a near object gets a high-quality mesh and texture while "something that's too far away from the camera, I'm just going to maybe just put a cube and the user won't be able to tell" — and [assembles context by level of detail around the edit focus](../concepts/assemble-scene-context-by-level-of-detail-around-the-edit-focus.md). With the user clicking on a knight, nearby assets arrive with their full tag values and settings, mid-distance ones collapse to "there's something that's a player here at this position," and the grass is omitted; the grading recomputes as the user moves. Two properties distinguish this from the filtering and compression patterns already in this topic. The middle tier is a *stub*, not a deletion, so a demoted object can still be referred to and asked about, which is the analogue of the distant cube rather than of a dropped chunk. And the anchor is the user's current selection rather than the query — the same distinction the browser-agent whole-page representation draws when it keeps every actionable element visible while spending detail only where it matters. Nereu pairs the spatial grading with two non-spatial inputs, a cheap summary of what *kind* of assets the project contains ("if you're using robots, if you're using something like medieval") and the user's own description of what they are making, so global character comes from a summary and local fidelity comes from proximity. The source reports no token measurements and no analysis of instructions that referenced something demoted, which is exactly where the technique would fail.

Towards AI supplies the measurement this topic had been missing, and it goes against much of the advice above. Running their production AI tutor as a testbed, they [benchmarked 11 context-management presets against a do-nothing baseline](../concepts/benchmark-context-management-presets-against-a-do-nothing-baseline.md) — full history, their own shipped defaults, and six techniques including sliding window, prompt compression, and selective retention — with model, prompt, tools, and dataset held fixed. Untouched full history won on fact recall, cost, *and* latency at the same time, and their shipped defaults (clear tool outputs after 5,000 tokens, summarize after 30,000) scored worse than doing nothing at all. The mechanism is [prompt caching setting the break-even bar for compaction](../concepts/prompt-caching-sets-the-break-even-bar-for-compaction.md): cached tokens can be up to 50 times cheaper, but any rewrite of the context produces a prefix the provider cannot match, so a compaction pass has to compress by more than the cache discount before it saves a cent. In their winning configuration 97% of tokens came from cache, which is how "the setup sending the most tokens is the cheapest to run" stops being a paradox. There is a second-order cost too: clearing tool outputs makes the agent re-retrieve what it already had, so the deleted tokens come back as extra tool calls.

This does not overturn the curation arguments in this topic so much as split them by constraint. The quality case for small context — the U-curve, poisoned history, stale tool results — is untouched, and Towards AI's own [95%-versus-32% detail-recall result](../concepts/full-history-recalls-details-that-summaries-delete.md) is a quality argument *for* keeping the transcript, since a summarizer commits to discarding details before knowing which one the next turn will need. What changed is the cost case: "every extra token is charged again every turn" holds for context that is newly added or rewritten, not for a stable history that keeps hitting the cache. Their long-context probe also refines the context-rot claim rather than denying it — distinctive facts stayed recoverable out to 800k tokens with no visible rot, while ambiguous facts degraded to about half, so fact distinctiveness predicted the failure better than length did. And the whole result is conditional on the window: [going local inverts the strategy](../concepts/local-deployment-inverts-the-keep-everything-context-strategy.md), because a 32k MacBook window cannot hold the transcript, caching stops helping the moment it overflows, and a larger parameter count buys no extra window. Their closing rule is the portable part: do not compact by default — name the constraint you actually have (price, window size, or latency), because each one has a different answer.

Most of this topic treats context as something you assemble inside a run. Bright Data's Omer Primor adds the layer underneath — where web-sourced context comes from, and what it costs to keep having it — under the name "web context engineering." The premise is decay: his team's measurements put social content stale inside a day and news, finance, and retail mostly irrelevant after 30, so "extracting context from the web… is not a snapshot. It's not a one-time effort. It's not even a monthly effort." That converts the scaling question from window size to cadence — [frequency, not volume, drives web-context cost](../concepts/frequency-not-volume-drives-web-context-cost.md), since a million is not a million rows in one prompt but the same entities re-asked over time, and "every repeated query costs the same as the first. Even if it brought back the exact same answers." The second-order effect is the one worth carrying into design reviews: metered context reshapes the work silently, because [cost pressure shrinks research scope](../concepts/cost-pressure-silently-shrinks-research-scope.md) into weekly-instead-of-daily checks, top-10-instead-of-all result sets, and questions nobody submits. Removing the meter by owning the pipeline is what the same talk sells, and the benefit he rates highest is behavioral rather than financial — "no more fear, no more cutting corners." The routing discipline he draws from this belongs beside the topic's existing per-task context choices: different teams have different needs, and "it's very tempting to throw AI search at all of them, but maybe that's not optimal."

## Key Concepts

- [Frequency, Not Volume, Drives Web-Context Cost](../concepts/frequency-not-volume-drives-web-context-cost.md) - web context decays, so cadence rather than row count is the cost multiplier and repeats never amortize.
- [Cost Pressure Silently Shrinks Research Scope](../concepts/cost-pressure-silently-shrinks-research-scope.md) - metered context degrades the workload through cadence, truncation, and unasked questions, none of which a conventional eval sees.
- [Prompt Caching Sets the Break-Even Bar for Compaction](../concepts/prompt-caching-sets-the-break-even-bar-for-compaction.md) - compaction invalidates the cache, so it must compress by more than the cache discount (up to 50x) before it saves anything; the cheapest measured run was the one sending the most tokens.

## Open Questions

- At what transcript length or turn count does keeping the full history stop winning on a cache-discounted API? Towards AI's bake-off ran 11-13 turns and their long-context probe reached 800k tokens on single-fact retrieval, but neither tested reasoning that requires synthesis across the whole transcript.
- Which compaction technique is right once the cache can no longer help — a full window, a genuine topic change, or local hardware? The bake-off measured techniques where compaction was optional and lost; it did not rank them under the constraint where compaction is mandatory.
- When a graded context representation demotes an object to a bare stub, how often does the user's next instruction refer to it, and is a "promote this on request" round trip cheaper than sending more detail upfront?
- What minimum metadata should each context block include so retrieval systems can select it reliably for future tasks?
- How often should teams rescan or revalidate context blocks when source systems change?
- Which context-management tasks should be implemented with deterministic code, retrieval, or small-model inference?
- How should teams decide what belongs in `SKILL.md` versus referenced files or tool descriptions?
- Which parts of a context engine can be cached safely as source-backed structure, and which generated answers must be recomputed from current sources?
- What metadata should context packages expose so teams can evaluate provenance, version compatibility, dependencies, and security risk before installation?
- How should personal knowledge-base agents avoid amplifying stale notes or noisy bookmarks into future context?
- Which personal-agent context should be injected from explicit topic hierarchy versus retrieved from memory?
- When should operational content be moved from a CMS into code so agents can manage it with diffs and review?
- What conversation state should be summarized into durable memory before server-side interaction records expire?
- How should context services decide which examples belong in a generated skill reference versus separate documentation?
- Which team conversations are durable enough to preserve as agent context rather than transient chat?
- Which customer conversations are durable enough to become agent-visible product context without overfitting to one account?
- How should repositories distinguish current implementation guidance from historical planning artifacts?
- Which non-functional requirements are durable enough to become default context for every coding-agent run?
- Which failure explanations should become durable prompt context instead of staying as one-off annotations?
- When should stable long-tail knowledge move from context or retrieval into model weights?
- Which architectural seams require human-written context because raw code makes technical debt look like intended convention?
- When should codebase onboarding context be prewritten, generated on demand, or avoided because source code is the better source of truth?
- Which repeated prompt, tool-call, and tool-response regions should be engineered for KV-cache reuse rather than summarized or regenerated?
- Which expert taxonomies are stable enough to encode as graph context instead of leaving them in prompts or interviews?
