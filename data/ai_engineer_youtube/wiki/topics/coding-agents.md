# Coding Agents

## Overview

Coding agents work best when their autonomy is constrained by small work items, visible checks, isolated workspaces, explicit handoff rules, and codebases whose structure is easy to understand and test. AI coding is a central applied-AI problem because code is where model capability turns into software systems, products, workflows, and organizational leverage; this makes the surrounding patterns, systems, and products part of the engineering problem, not just the model. The Ralph loop pattern favors a simple repeated cycle over elaborate orchestration: pick one ticket, implement it, validate it, update status, and let the next run continue with the improved prompt, skill, or work queue. This reduces the coordination burden that appears when many agents attempt a large dependency graph at once. Claude Code-style harnesses push the same lesson down into architecture: a single master loop can let the model call tools, observe results, and continue until it is done, while todos provide prompt-enforced lightweight state rather than a hard workflow engine. As agents write more of the implementation, human effort shifts toward planning, reviewing, QA, and shepherding changes, while the engineering role also expands toward product, operations, testing, business context, and agent orchestration. Harness engineering pushes that shift further: when code production is abundant, human leverage moves to control surfaces such as task framing, durable non-functional requirements, prompts, rules, lints, reviewer agents, and CI checks that make agent output acceptable. That shift can overwhelm teams when generated-code output grows faster than review capacity: large PRs, non-engineer code contributions, and agent-produced diffs can make the exact moment that needs judgment feel too large to inspect. AI-assisted speed also raises the cost of weak product taste: when implementation is cheap, teams can ship every request and erode coherence unless engineers preserve judgment about root problems, customer value, interaction quality, and whether an agent contribution is pulling the product in a plausible but wrong direction. Claims about coding-agent speedups need the same discipline as the workflow itself: public benchmarks and long-task curves should be tested against field experiments on experienced developers working in existing repositories, with observed timing or assignment traces rather than recalled task duration. The right balance depends on task shape: specifiable back-end, refactor, migration, maintenance, and bug work can be plan-heavy and test-driven, while exploratory front-end work may require tighter human review loops because agents can produce functional UI without the timing and feel that make interactions natural. For web work, that review loop can be encoded directly into the repository: skills and AGENTS.md can require issue discovery, Playwright evidence, preview tunnels, smartphone review URLs, and human confirmation before closing the task. Productized codegen agents also need protection against model rot and runaway variation: serve fresh documentation, provide small exemplar projects that show the desired architecture, maintain shared domain language, and breadcrumb the agent through discovery, event planning, and implementation rather than asking for the final integration in one jump. Even a minimal coding agent still needs a disciplined tool loop: file and shell tools should be explicitly declared, model-required actions should be checked against the available tool map, and destructive or unsupported operations should not be executed just because the model or user suggests them. Parallel coding can be made more useful when project worktrees isolate feature or bugfix threads, when custom subagents receive task-appropriate models, tools, and permissions, and when a parent agent compares or synthesizes outputs. Prompt-enforced workspace isolation still needs explicit evals because a model can drift back into the primary checkout. Large refactors add another orchestration pattern: use shared migration context, dependency graphs, and directory structure to split a sprawling codebase change into PR-sized batches that a single agent can complete and a human can understand; then run verifier and fixer loops in dependency order so reviewed merges unblock later batches. Parallel orchestration also needs observability beyond terminal logs: spatial maps can show which files each agent touches, heat maps can surface collisions, quest queues can keep background work flowing, and review bundles can attach task summaries plus screenshots or videos to each output. Hooks add another workflow layer for setup, logging, and continuation rituals, while privilege approval gates keep sensitive filesystem, server, or network-exposure actions from becoming all-access defaults. Context engines add another reliability layer by giving the agent system-specific decisions, reviewers, owners, and expert signals before it spends tokens rediscovering them from the repository. Browser-integrated tools add another reliability layer for front-end agents: DevTools MCP can let the agent inspect live runtime errors, network requests, screenshots, and performance traces instead of inferring everything from source. Org-chart control planes add a related pattern: worker agents can be routed through QA reviewers and manager approvers, while repeated release, PR, and review prompts become routines with variables and skill references instead of one-off chat instructions. Software design remains a control surface: specs-to-code loops that ignore code can compound entropy, while TDD, fast feedback, ubiquitous language, deep module interfaces, and agent-legible codebase structure let humans retain strategic design control while agents handle bounded implementation work. Agent-legible codebases make paths, primitives, and source-of-truth decisions visible through modular flow, centralized query and UI interfaces, lint rules, unique function names, reduced hidden magic, and repeated quality lessons encoded as automatic checks. Teams also need explicit AI fluency practice: repeated workflow experimentation matters more than theory-only understanding of model internals.

High-consequence coding environments make permissions and verification part of the product, not an add-on. A coding agent can translate legacy Ada into Rust and add features, but defense, government, satellite, or critical-infrastructure contexts still require narrowed access, visible diffs, generated and human-run tests, and reviewable command output before the work is trusted.

## Open Questions

- What ticket sizes and dependency patterns are small enough for unattended coding-agent loops?
- Which validation responsibilities should stay in deterministic tests versus independent review agents?
- Which workspace boundaries must be enforced by the runtime rather than by prompt instructions?
- Which integration examples are thin enough to remain token-efficient while still giving agents the right architectural shape?
- What repository activity signals are reliable enough to infer code ownership or expertise for agent context?
- Which front-end QA capabilities are strong enough to move visual and interaction review out of human back-and-forth?
- Which file or shell operations should a minimal coding-agent runtime refuse even when the user prompt asks for them?
- Which session hooks are useful enough to automate, and which create hidden agent behavior that should remain explicit?
- Which repository-readiness checks predict whether a cloud agent can run without human setup intervention?
- What shared planning artifact is sufficient before multiple teammates or agents start related work?
- How should agent-suggested work queues be prioritized so they create useful leverage rather than review backlog?
- Which completed planning artifacts should be closed, deleted, archived, or converted into durable documentation?
- Which parts of a codebase need deeper human implementation review rather than interface-level validation?
- Which AI-tool practice routines help skeptical experienced engineers find real leverage on existing codebases?
- Which experienced-developer tasks are most likely to show positive field-study speedups rather than benchmark-only gains?
- Which product-taste checks can be made explicit enough for agents to assist without reducing design judgment to shallow style rules?
- Which non-functional requirements should become documentation, lints, reviewer agents, or hard CI gates?
- Which refactor-batching strategy best balances semantic cohesion, dependency ordering, agent success rate, and human PR review size?
- Which agent todo rules are safe to keep prompt-enforced, and which need runtime enforcement or workflow state?
- Which trajectory metrics reliably indicate agent confusion rather than harmless exploration?
