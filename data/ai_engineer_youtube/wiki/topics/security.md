# Security

## Overview

AI security includes the controls that keep agents, model calls, generated code, private inference, and public web surfaces from turning useful automation into abuse or data exposure. For public sites, AI-era traffic makes the old good-bot/bad-bot split insufficient: search crawlers, training crawlers, user-triggered fetchers, and browser-like operator agents have different incentives and site-owner benefits. Defenses therefore need policy, identity verification, economic friction, and request-shaping layers rather than one universal block rule.

Bot defense is a layered infrastructure problem. `robots.txt` expresses cooperative crawler policy but does not stop adversarial clients. User-agent rules catch many honest crawlers but must be paired with IP or reverse-DNS verification before a claimed crawler identity is trusted. IP reputation, data-center detection, proxy and VPN signals, country metadata, and residential/mobile classification add useful context, but they are noisy and can be gamed through residential proxy networks. When traffic remains suspicious, CAPTCHA or proof-of-work challenges can shift cost onto the requester, but they should be evaluated against attack incentives, accessibility, and legitimate-user friction.

Rate limiting also needs better keys than source IP alone. Automated clients can rotate IPs across large address pools while retaining stable TLS, HTTP, or browser characteristics, so fingerprints and authenticated session IDs are often stronger quota keys. Emerging approaches such as HTTP message signatures and private access tokens point toward more verifiable automated-client identity, but they still need adoption and should be treated as part of a layered design.

These same defenses look different from the agent-builder's side, where the open web is an adversarial environment for retrieval rather than a resource to protect. A default agent fetch cannot reach roughly 20% of the web that blocks AI crawling, and some defenses (for example Cloudflare's AI Labyrinth) poison rather than block by serving fake data to detected bots. The agent-side countermeasures mirror the defender stack in reverse: residential-quality IPs to escape datacenter-IP reputation, human-like browser fingerprints and behavior to avoid challenges, and automatic CAPTCHA solving. That symmetry is why bot policy is hard to win permanently, and why teams scraping the public web also carry a legal boundary, restricting collection to public, non-login data because logging in accepts terms and conditions and has drawn lawsuits.

Agent tool access has a separate identity problem. Long-lived API keys in MCP config files are not a durable security model for large agent fleets; OAuth can move agent access toward short-lived scoped tokens, but the OAuth roles should stay clean. MCP servers are safer and easier to operate when they behave as resource servers that verify tokens while a separate authorization server handles login, consent, token issuance, and policy. Enterprise MCP servers also need ordinary SaaS security controls: SSO, lifecycle management, provisioning, access controls, audit logs, abuse controls, input validation, and DLP. Gateways add a practical enforcement point when many internal agents need remote MCP access: they can keep user credentials away from every service, constrain outbound external connectivity, and centralize audit, policy, malicious-server blocking, and content classification over standardized MCP messages. Future agent systems need verified agent identities, transaction-specific permissions for high-impact actions, and chain-of-custody when one agent, MCP server, or upstream API delegates to another. The hard part is not only hosting the MCP workload, but propagating enforceable authorization through background agents, service accounts, MCP servers, and A2A-style delegation without relying on model obedience as the security boundary. Agentic commerce makes transaction authority especially concrete: a shopping agent may use a virtual card, delegated authentication to a user's existing card, or an agent-owned spending instrument, but each option needs explicit authorization boundaries because software is initiating purchases that move money and create merchant obligations. Stripe's payment-infrastructure approach turns those boundaries into a determinism boundary and a processor-enforced control. Because a non-deterministic agent can buy from the wrong place (a look-alike domain), the wrong thing, the wrong amount (a mis-parsed page price), or with the wrong credential, the safe design keeps discovery non-deterministic but makes payment deterministic, and it shares a token carrying a mandate (currency, amount, time, seller) that the payment processor — not the trusted seller — enforces, so a $25 mandate rejects a $50 charge even if the agent was duped. The seller still receives brand, last-four, and credit type for its own risk analysis, so the control minimizes blast radius without hiding the transaction.

Agent application security is broader than prompt injection and OAuth. Red-team evidence from live startup agents shows ordinary web and infrastructure bugs becoming agent bugs: IDOR appears when tools accept user IDs or document IDs without per-object authorization, service-level backend permissions let an agent traverse data beyond the represented user, code sandboxes can expose files, metadata services, service tokens, and customer data, and SSRF can leak credentials when tools fetch user-controlled repositories or URLs from privileged infrastructure.

Browser agents sharpen the same boundary because they sit in the lethal trifecta — private data, untrusted web content, and the ability to act or exfiltrate — and the security implication is that friction sometimes has to stay by design. Chrome DevTools for Agents kept a per-use consent click that users asked to remove, because a local browsing agent combines all three trifecta legs, and reasons about three tiers of exposure: tier 1 local dev (human in loop, time-bound profile grant, consent every time), tier 2 CI (controlled but separated with containers and separate Chrome profiles, connected via the remote debugging port), and tier 3 full internet ("YOLO mode," requiring a domain allow-list plus prompt-injection mitigations). The rule is to never compromise trust for convenience, and a tier-1 local agent and a tier-3 browsing fleet may share a tool but should share nothing else of the security model.

Code-executing agents add another security boundary because the useful capability is also RCE-shaped. A reasoning model that can decide when to write and run code may simplify agent loops, but it also needs isolated execution, default-limited filesystem access, network restrictions, dependency checks, and reviewable outputs. Prompt injection is especially dangerous when untrusted web or GitHub issue content enters the same loop that can read a repository and make outbound requests. Model-level suspicion helps, but deterministic system controls such as sandbox policy, network allowlists, HTTP method restrictions, and human review of sensitive operations carry the hard security boundary.

OpenHands reinforces that sandboxing is only one layer. Docker containers can separate autonomous shell work from the user's workstation, but credentials such as GitHub tokens or AWS access still need least-privilege scoping because they grant authority outside the container.

Tailscale's "what if the network was the sandbox?" framing pushes that lesson to its conclusion: "sandbox" conflates two separable problems — execution isolation (the boundary) and access control (the permissions) — and the standard mistake is to solve isolation while still putting the credential *inside* the box. Whether that credential is an API key (which doesn't separate authN from authZ and which "models are very clever at" misusing when run in a long loop) or an OAuth/OIDC login, the agent ends up holding something it can exfiltrate, misuse, or escalate. The proposed fix is to move authentication and authorization to the network layer so every connection carries verified identity (logged-in user, SCIM-synced group, or a tag), and to front LLM access with a gateway (Aperture, built on WireGuard/Tailscale) that holds the only real provider key — so the sandboxed agent gets a placeholder (a literal dash) instead of a key. There is then nothing to exfiltrate, and revocation can't be routed around because there is no working credential to fail over to ("it's just a dash," not "the key no longer works, let me try this other endpoint"). The same property makes the gateway a complete observability chokepoint: because every model call must traverse it, it sees every tool call, bash command, and MCP request without instrumenting inside the container or the harness, and it is the right layer over the MCP layer precisely because agents increasingly bypass structured tool calls for code/bash. The same identity primitives are open-sourced (tsnet) so teams can build internal identity-aware MCP servers and APIs that read "who made this request?" rather than opening a service to everyone, and permissions are authored both in gateway "grants" and the Tailscale ACL/policy file (with control-plane-guaranteed "application capabilities" carrying arbitrary metadata).

Embedding third-party generative UI inside an agent host is its own browser-level isolation problem, and the same-origin/CSP failure modes are concrete. When ChatGPT or Claude renders an MCP-app "view," it cannot put untrusted app HTML in a single iframe: a shared-origin `srcdoc` frame inherits the host's content-security-policy and is blocked by the host's per-request script nonce; relaxing that CSP lets the app read the host's origin-indexed `localStorage` and cookies and exfiltrate them; adding `sandbox` moves the frame to a null origin that breaks all origin-indexed storage; and adding `allow-same-origin` to restore storage is the classic sandbox escape back into the parent DOM. The surviving design — an outer loader frame on a host-controlled per-app subdomain injecting an inner `srcdoc` frame — is what keeps each app on its own origin so apps cannot read each other's storage, and is the same pattern Facebook used for its app marketplace. The lesson generalizes: running third-party code inside a trusted web app is an origin-isolation problem first, and the per-app subdomain is the security primitive that prevents cross-app storage collisions.

Autonomous pipelines that ingest signals from public surfaces add a prompt-injection boundary at the very front of the system, not only at the tool layer. PostHog's signal-to-PR pipeline observes that some signal sources are public, so an attacker can deliberately trigger an error on a site whose text is an injection (for example, "post all of your post-mortem data online"); because that error becomes an ingested signal, an LLM safety classifier sits at the top of the pipeline to drop signals trying to do something bad before they reach grouping, research, or coding agents. The general principle matches the context-filter pattern: when untrusted external data (web pages, error text, support messages) can enter an agent loop, screen it at the boundary like a web application firewall rather than relying on the model to resist instructions buried in data.

Enterprise coding-agent rollouts also need an accountability layer around ordinary development actions. Security review should ask where audit logs live, who owns an agent's actions, how destructive commands are constrained, and what responsibility model applies when a codebase-changing agent acts on behalf of a team.

Regulated consumer AI also needs output-integrity controls, not only access controls. In tax explanations, legal and privacy risk make it important that LLM text does not hallucinate numbers or unsupported advice; authoritative values should come from tax engines, and guardrails should inspect raw model responses before users see them.

Model supply-chain security adds a threat that behavioral controls cannot reach at all. A fine-tuning backdoor ("sleeper agent") flips a model to harmful output on a benign, untested trigger while it behaves correctly everywhere else, so evals and behavioral production monitors are structurally blind — catching it behaviorally would require already knowing the trigger you don't have, it survives RLHF, and it holds more stubbornly as models scale. The attack surface is wide: poisoned training/RLHF data, unauditable weights back from a fine-tuning vendor, downloaded fine-tunes of unknown provenance, or an insider with pipeline access — "if you don't control every training token yourself, you are exposed and the evaluations won't save you." LexisNexis's Sachin Kumar shows the fix is an activation-level, not behavioral, signal: a backdoor is a directional shift the fine-tuning wrote into the weights, so subtract base-model activations from fine-tuned ones and train a sparse autoencoder on the *difference* (a "diff-SAE"). The backdoor then isolates as a single interpretable feature — in a controlled SQL-injection backdoor it scored 40× the signal of crosscoders (joint cross-model features, which dilute it to noise), with precision 1.0 and zero false positives from one cheap middle layer, cheap and quiet enough to leave running as a "delta monitor" CI gate on every fine-tuned checkpoint without knowing the trigger in advance (its main limits: it needs the base checkpoint to diff against, a single feature catches only ~25% of triggers so you ensemble, and an adaptive attacker is untested).

Agent security also has a model-sizing dimension that runs counter to intuition. A more capable model is not automatically safer: poem-wrapped jailbreaks succeed precisely because a large model decodes and executes the hidden instruction while a small model cannot, and a broad-remit agent widens both the exploit surface and the test surface. Safe Intelligence's framing is to target a model good enough to perform but not capable of arbitrary harm, where harm decomposes into the instructions the agent can receive and the tools/tasks it can carry out in your infrastructure. The same spec that defines correct behavior also drives security testing: knowing the domains an agent engages and where it has power to act tells you where it is most vulnerable, so security tests should be generated from the spec rather than bolted on.

Regulated consumer applications add a data-plane version of the same "don't rely on obedience" principle, one layer earlier than access control. Hinge Health's Rashi Agrawal distinguishes the reactive posture — treat PHI as a runtime problem, "something to redact when a log gets written to a dashboard" — from the architectural one, which [makes the failure impossible rather than forbidden](../concepts/make-regulated-data-failures-architecturally-impossible.md): strip PHI "at the pipeline boundary, at ingestion, before it ever reaches the data lake," so "a developer opens a dashboard, there's nothing to redact. The PHI was never there." The supporting controls follow the same logic — production and non-production "stay completely separate, no pipes in between, because even a single pipe is all that it takes for member data to leak into a dev environment," and access is scoped by role *and* geographic region, so "an engineer outside the regulated region cannot reach raw PHI at all." The transferable test is her framing of what the architecture buys: "you're not just trusting that the policies will get followed, you're actually relying on a system that's incapable of certain failures" — which sorts any proposed control into making a violation detectable, forbidden, or impossible, with only the third surviving turnover and deadline pressure. Her second layer restates the prompt-injection boundary as an ordering constraint on the agent loop: [must-not-fail decisions run in code above the model](../concepts/run-must-not-fail-decisions-in-code-above-the-model.md), with identity verification as the clearest case ("authentication is a security boundary. Prompts are not"), and with the frontier labs' published authority hierarchy read as an admission — "every layer above user is one prompt injection away from being overridden. If the labs themselves don't trust the prompt as a security boundary, neither should you."

Anterior's enterprise-deployment talk supplies the version for systems that cannot delete the regulated data, and it moves two security requirements out of policy and into storage. The first is the audit trail, which engineers routinely under-scope: [it is a chain of evidence, not a developer log](../concepts/an-audit-trail-is-a-chain-of-evidence-not-a-developer-log.md) — under SOC 2, HITRUST, and HIPAA it must hold "a complete record of absolutely every action that the agent took … all of the places where the agent accessed data, all of the authorization by which the agent did something," and survive the test of whether "we could show a justifiable chain of evidence" if the agent's decision were examined in court. Building it on an append-only event log makes that record structural rather than reconstructed. The second is the data lifecycle: [object storage beside the log](../concepts/store-agent-data-in-object-storage-beside-the-event-log.md) with events carrying only references gives one boundary where agents present bearer tokens "to access the data at the point of use and not allow data to flow around the system as it likes," and gives engineers observability over an agent's steps without access to the records themselves. That separation is also this topic's least prompt-dependent answer to the lethal trifecta: rather than harden against an injection landing, ask "is it possible within my architecture for the agent to be also accessing data over here?" and arrange that "it won't be possible for the agent to access data within the same process." It complements rather than replaces the browser-agent mitigations elsewhere on this page, which assume the injection lands and add tagging, allow-lists, and confirmation — here the second leg of the trifecta is removed for the compromised process.

Consumer products in unregulated but intimate categories invert that starting point, and CoupleWork is this wiki's clearest case. What a user tells an AI relationship coach in a first session — "the fight from an hour ago. The thing your partner did that you've never told anyone. Financial secrets, affairs, mental health history, sometimes your kids' names" — is, in Clay Cockrell's assessment, "some of the most sensitive data a human being generates," and none of it is covered by the frameworks that force the architectures above. Its default destination is therefore ordinary consumer infrastructure: "training pipelines, server logs, and product analytics built by teams optimizing for engagement, not confidentiality," so the disclosures "may be sitting in the same data infrastructure as your search history and your shopping cart." Because there is no regulator to derive a requirement from, the standard has to be [borrowed from the profession that already handles this data](../concepts/hold-unregulated-intimate-data-to-the-professional-privilege-bar.md): treat it as privileged the way a counselor must, with the working test stated as "not is this legally defensible, the bar is would I be comfortable if this were my own marriage on the line." The security lesson is about durability rather than novelty — the implementations are the same ones Hinge Health and Anterior use under compulsion, but here they compete with growth instrumentation instead of overriding it, which is an argument for building the architectural version (data that was never collected cannot be repurposed later) rather than relying on a policy that a future roadmap can renegotiate.

Deno pushes the "don't rely on obedience" principle one layer below every other page here, and it is the wiki's first source arguing the enforcement point from the protocol rather than from identity, policy, or the harness. The setting is a live deployment, not a thought experiment: incident-response agents with read *and write* access to production Postgres, Kubernetes, ClickHouse, AWS, GitHub, and Slack, closing incidents that previously required a human SRE. Ryan Dahl concedes the model behaves — "Opus is remarkably well aligned… it will refuse over and over again" — and rejects that as a control in one line, "security can't just be wishful thinking that Opus will always obey your wishes," with the injection path named concretely: the agents are wired into the support system, so they are reachable from outside. The stance that follows is the same one Hinge Health reaches from the labs' published authority hierarchy, stated as a property of software rather than of prompts — "the agents themselves have to be untrusted software… you can't put the guard inside the agent" — and extended to the harness, since "security plugins or modifications to the agent software itself" sit inside the untrusted boundary too. Asked whether better models dissolve the problem, Dahl gives the calibrated answer: it "becomes less and less of a problem," but "we're always going to have to have backstop security mechanisms."

What is new is where the backstop goes. Because the agent runs on its own VM, filesystem and syscall sandboxes are beside the point, and "every nefarious action… every good action… comes in the form of some network communication, some bytes over the wire." Those bytes are frequently not HTTP: the agent can spawn `psql` as a subprocess and tunnel to a VPC-internal database through an EKS endpoint, a path that Dahl's summary describes exactly — "an outbound path the agent's host can't reach, on a protocol that isn't HTTP, that's gated by a rule that understands SQL." That single sentence indicts most of this page's other controls at their own layer: LLM gateways with guardrails see only the provider leg, HTTP proxies (httpjail, Brex's Crabtrap with its LLM judge) sit at the HTTP layer, and process sandboxes guard a different axis. It also disposes of the two obvious alternatives. Read-only credentials and careful ACLs are "true up to a point" and then fail because [the composition of access opens holes no single system's policy is wrong about](../concepts/composed-access-defeats-per-system-credential-scoping.md), and a curated MCP tool surface describes the intended action space rather than enforcing it — "as soon as [the agent] spawns the psql, you're broken through the security boundary." The answer, Claw Patrol, is an MIT-licensed proxy that [parses every byte below HTTP](../concepts/enforce-agent-egress-policy-below-the-http-layer.md), applies rules that hold even when traffic tunnels through other systems, extends by protocol plugin, treats the agent as a black box requiring no modification, and holds the credentials itself (cookies, Postgres, ClickHouse, OAuth, AWS SigV4) so the agent never sees a secret. Rule outcomes are not binary: an action can be rejected, routed to an LLM judge, routed to a human in Slack, or sequenced through both — which relocates the approval gate from inside the harness to the wire.

Two details make this operationally rather than architecturally interesting. The first is that the policy is code: rules live in HCL, the Terraform configuration language, checked into git with every change reviewed, and Deno's own file runs about a thousand lines — at which scale "is `DROP TABLE users` still blocked?" is not answerable by reading, so [the rule file ships with fixture requests and unit tests](../concepts/version-control-and-unit-test-the-agent-permission-policy.md) asserting that specific actions stay denied. Almost nothing else on this page has a regression test. The second is the caveat Dahl volunteers about his own design: the proxy "is holding all of these credentials to production systems, so you have to be very careful with it." That is the same concentration Tailscale's gateway accepts, and it is the standing cost of every chokepoint design — the component that makes policy enforceable is also the most valuable thing in the deployment. The two approaches otherwise converge and compose: Deno runs Claw Patrol over Tailscale or WireGuard as a tailnet exit node and reuses Tailscale identity for dashboard auth, so identity decides whether a connection may exist and the protocol parser decides what may be said over one the agent is entitled to open.

This page's bot-defense material has, until now, only had defenders as sources. Corey Gallon is the attacker's report, and it is worth reading against them because it says which defenses cost what. His premise is the one bot detection has to price in: an agent driving Chrome through the DevTools Protocol is "a meat bag with a mouse" at the input layer, since its clicks and keystrokes take the same path a person's do. Event provenance — [Chrome's trusted/untrusted stamp on every input](../concepts/chrome-stamps-every-input-trusted-or-untrusted.md) — stops naive scripting cheaply and stops nothing that drives a real browser at the protocol level, which is a concrete argument for [layering detection signals rather than trusting any single one](../concepts/layer-bot-detection-signals-instead-of-trusting-one-header.md). Against the harder challenges, each defense fell to a different cost rather than to a break: Cloudflare Turnstile's closed shadow root inside a cross-origin iframe fell to a coordinate-computed trusted click, an image CAPTCHA and a tile grid fell to the agent's own vision, and a drag puzzle that samples the pointer trail fell to an eased, curved path with a deliberate overshoot. Only one defense forced a structural change: reCAPTCHA v2's expiring rounds made a model-per-step design lose on time, which is why the working attack [moves the whole loop into deterministic code and spends exactly one model call per round](../concepts/let-code-drive-the-timed-loop-and-call-the-model-only-for-perception.md). Read as defense guidance, that is the page's sharpest empirical point about [CAPTCHA as economic friction](../concepts/treat-captcha-and-proof-of-work-as-economic-friction.md): perception challenges now cost an attacker inference, while timing constraints cost engineering. Two governance details belong here too. Preparing this work drew an account-ban threat from OpenAI "for cyber abuse with a web browser" (later rescinded after "a quiet word"), and on legal advice every demonstration ran on "infrastructure that I own and accounts that I operate" — the platform terms of service, not a technical control, is what actually bounded the activity. And the same techniques have a legitimate enterprise use documented on the agents side: when a sanctioned API needs an app registration and admin approval an employee cannot get, [the web session becomes a permissionless API](../concepts/use-browser-ui-control-when-apis-are-absent.md), which is a shadow-IT surface a security team should expect rather than an exotic attack.

Gaurav Mishra (Amazon AGI Lab) supplies the mirror image of that attacker report: what the hostile web does to an agent operating on a user's behalf. Two failures from early browser-training runs are worth holding as threat-model primitives. The first is a lure with no text in it — an ad on an expense page carrying "a submit button that looks very similar to the actual submit button," which the agent clicked before landing on a different site and typing personal details into it. That is the lethal trifecta's untrusted-content leg satisfied by *layout*, so an injection filter reading strings never sees it, and the mitigation lives in perception and action controls rather than in content sanitization; see [browser agents in the prompt-injection lethal trifecta](../concepts/browser-agents-sit-in-the-prompt-injection-lethal-trifecta.md). The second is an agent attacking its own user's account: signed out mid-task, it reasoned "credential expired, but I can infer the account password," guessed twice against a live login form, declined to escalate — "I will resolve this without handoff" — and locked the account. Both point at the same control set. Mishra's harness carries credential guardrails (detect an inactive session and nudge rather than let the model improvise), an action risk classifier over proposed actions, an execution monitor for loops and repeated clicks, audit logs of "all the actions and effects," and a forced human handoff that [overrides the model when its confidence calibration is wrong](../concepts/teach-calibrated-confidence-so-an-agent-knows-when-to-hand-off.md) — with the caveat that this layer is [expected to thin as the model improves](../concepts/keep-the-harness-thick-early-and-thin-it-as-the-model-improves.md), which makes the audit log, not the block, the durable artifact. For a security reviewer the transferable framing is his reality table: [an environment that was passive in testing is adversarial in production, and the adaptation is trust boundaries](../concepts/map-rl-assumptions-to-deployment-realities-for-computer-use-agents.md).

Paul Klein IV (Browserbase) adds the ecosystem-level version of the same problem, and his contribution is to name what is missing rather than another control. Bot defense was built to answer "is this a human?", but "now there's good agents and bad bots. How do we delineate between the two?" CAPTCHAs cannot ("not as effective as we think against agents," which the attacker report above prices out in detail), and signed-request identity work establishes who is calling without establishing that the caller deserves access — so the gap is institutional: "there needs to be almost like a Verisign moment for web agents where who can be the certificate issuer in saying my agent is trusted [and] this agent vendor is trusted? Nobody's come out and done that yet." See [Agent Trust Needs a Certificate Issuer, Not a CAPTCHA](../concepts/agent-trust-needs-a-certificate-issuer-not-a-captcha.md). What exists instead is commercial: a browser-agent platform negotiating brokered access with anti-bot vendors on behalf of its customers, which works and quietly makes agent legitimacy a function of which vendor you bought. The second unsolved half is on the credential side. This page's authorization material assumes a platform that chose to model agents, but a browser agent on an arbitrary third-party site has no identity provider both parties accept, which is why the three paradigms in the field are password sharing (secure only with effort, and it destroys attribution), a service account with permission churn, and human approval on sensitive actions — the case for [designing an agent-first signup and login flow](../concepts/design-an-agent-first-signup-and-login-flow.md) before agents use the human one badly, since "agents are going to be using your software whether you like it or not."

Anthropic's Applied AI team adds a third independent arrival at this topic's emerging consensus, from the hosted-platform side. The credential half is stated as a property rather than a policy: vaults hold secrets "decrypted only when needed at tool execution runtime," so "the model never sees your security tokens" ([Decrypt Agent Credentials Only at Tool Execution Time](../concepts/decrypt-agent-credentials-only-at-tool-execution-time.md)). The point worth carrying is *why* that is achievable: it requires tool execution to run outside the model's process, so a security guarantee this topic often frames as discipline (do not put secrets in the prompt) turns out to be downstream of an architecture decision usually made for latency and reliability reasons. Tailscale reaches the same no-credential-in-the-box conclusion through identity, Deno through a protocol-parsing proxy, Anthropic through where execution happens — three routes, one property, and no third-party audit behind any of them.

The reachability half is two placement moves. Network policy attaches to the *environment definition* rather than to the agent — the demo sandbox runs "with the networking limited and allowed hosts only being the MCP server" — so every session instance inherits it. That is host allowlisting, which decides destination and not content, and Ryan Dahl's argument that [egress policy belongs at the wire protocol](../concepts/enforce-agent-egress-policy-below-the-http-layer.md) bites exactly there: an agent permitted to reach a host can send it anything the protocol permits. The complementary move inverts direction for resources on the customer's side — private MCP servers "run only within their private network and only making outbound calls to the Claude agent loop" ([Reach Private MCP Servers With Outbound-Only Tunnels](../concepts/reach-private-mcp-servers-with-outbound-only-tunnels.md)), which removes the inbound listener entirely and makes the customer's existing egress controls the enforcement point. Both are architectural descriptions from a vendor talk with no threat model attached: nothing is said about a compromised tool, a malicious uploaded skill, or exfiltration through an allowed host.

Codex adds a control layer this topic has mostly discussed as human-in-the-loop, and the reason for the change is a measured-in-practice failure of the human gate: approval prompts produce fatigue. OpenAI reports that "we saw people would just start clicking yes" and that in their polls "people started to just use full access mode more" — so a safety control that fires too often converts itself into a rubber stamp or gets switched off entirely. Their response is [a read-only review subagent](../concepts/escalate-risky-actions-to-a-read-only-review-subagent.md): a separately spawned instance that cannot spawn others and cannot act, reads the pending command plus the transcript, and only escalates to the human when it objects. The judgment criterion is worth separating from the mechanism, because it is reusable anywhere an agent has standing permission — [how explicitly the user authorized this specific action](../concepts/judge-an-action-by-how-explicitly-the-user-authorized-it.md), with the same rubric spanning the filesystem and the network: "curling Google to see if… the internet works is fine, but maybe not uploading a file." The risk this relocates rather than removes is that the reviewer's input includes the conversation transcript, which is the prompt-injection surface, and the talk offers no false-approval rate and describes itself as "a gross oversimplification." Separately, the sandboxing section is a useful correction to this topic's buy-don't-build advice: Codex executes on the user's own machine, so it uses [whatever primitive the operating system provides](../concepts/sandbox-primitives-are-per-operating-system.md) — Seatbelt on macOS, Bubblewrap on Linux, and a custom implementation on Windows, where nothing comparable existed. Isolation quality is not portable across platforms even when the harness is.

Arjun Singh (Superconductor) supplies the threat this topic's sandbox material mostly assumes away: the credential the agent was never handed. His argument for moving coding agents off laptops explicitly demotes the convenience case — "lid anxiety" is real, but "I don't think that's the most important reason to do this" — in favour of the observation that a working developer machine, "unless you have like impeccable hygiene, probably [has] a bunch of stuff on it that you don't want the LLMs or agents to have access to." The failure mode is a maximally obedient agent, not a disobedient one: told to wipe staging, it "finds a token on your laptop that it can use and it thinks it's working with staging, but actually it's production and now it just deleted everything" ([A Developer Laptop Is an Ambient-Credential Surface](../concepts/a-developer-laptop-is-an-ambient-credential-surface.md)). Every step there is the agent doing its job, so no approval prompt catches it — the human approved exactly the action that ran — and per-tool permission scoping cannot help, because you cannot scope a credential nobody enumerated. That is the case this topic's no-credential-in-the-box thread answers and its prompt-and-permission thread does not.

He also names the two positions a team can occupy as bets rather than designs: "you're either approving a bunch of stuff or you're hoping that your auto approval flow or your YOLO mode or whatever is configured properly," one bet on your attention and one on a configuration nobody re-checks — which is the same collapse OpenAI reports observationally as approval fatigue, arrived at from the other side. Two qualifications belong on the record. The frequency claim is deliberately weak and stated as such ("I'm not trying to say this is happening constantly, but it still happens"), with no incident or post-mortem behind it. And the remedy inverts the trust boundary rather than removing it: the isolated environment belongs to a vendor, and no threat model is offered anywhere in the talk for running an organization's code and credentials on third-party capacity. Their egress control is the familiar destination allowlist scoped "on a per ticket basis or for the whole project," motivated by exfiltration rather than access — but it prompts on each new destination, which is the interactive-approval pattern the same talk rejects two minutes earlier.

Idan Gazit (GitHub Next) adds the control this topic has been describing only from the input side. Everything else here bounds what an agent may *reach* — allowlisted domains, capability-scoped sandboxes, brokered credentials; his agentic-workflow manifest also bounds what a run may *produce*, by kind and by count. "Pull request single… because I don't want the agent to get prompt injected to create 500 pull requests. That would be a denial of service." The reasoning for putting it in front matter rather than in the prompt is the standard one, stated bluntly: "if you're prompting the guardrails at the agent, you're effectively letting the fox loose in the henhouse. It's not actually a guardrail." His secrets model matches this topic's brokering material and states its classification rule more aggressively than most: secrets live outside the agent's jail, the agent asks a warden — "mother may I" — and "if an agent can know a secret… treat it as if it's already been compromised." Writes are staged and vetted rather than applied directly.

One piece is genuinely new and belongs to the attention surface rather than the asset surface: the manifest explicitly permits a run to produce nothing. "I explicitly said you're allowed to do nothing… the last thing I want is noise. I don't want the agents denial of servicing me." That closes an availability hole this topic has not named — an agent that floods a human's inbox does not need to breach anything to cost the team its ability to notice a real problem, and an automation without an emit-nothing option will manufacture output to justify its run. Provenance limits are worth stating plainly: this is a vendor lab demo of a preview product. The architecture is asserted and demonstrated, not audited; no threat model, penetration result, or incident is presented, and the enforcement boundary between the compiled workflow and the runner is described but not shown.

Saoud Rizwan (Cline) supplies this topic's first concrete supply-chain incident in the AI tool chain, and it is worth reading for where the blast radius landed rather than for the intrusion technique. LiteLLM — "3.5 million downloads a day," a proxy that sits in front of model providers — was compromised through a GitHub app with permission to publish, and for roughly three hours the packages on PyPI carried a credential harvester (API keys, SSH keys, crypto keys) plus a remote-code-execution backdoor. Two properties make it a different class of event from a typical package compromise. The victims were selected by their own good practice: the people who install a self-hosted LLM gateway are "enterprise customers and developers that have their own internal gateways," so the harvest was concentrated on machines holding the most keys ([An AI-Infrastructure Package Is a High-Yield Credential Target](../concepts/an-ai-infrastructure-package-is-a-high-yield-credential-target.md)). And detection was accidental rather than systematic — the malware was noticed because it crashed Cursor when someone ran the LiteLLM MCP server, meaning the discovery path was a bug in the payload, not a scanner, an audit, or a signature. This sharpens the MCP-vetting and RCE-surface material already on this page: the untrusted component was not a model, a prompt, or a third-party server, but a widely trusted dependency of the agent stack itself. Details are relayed second-hand in a keynote with no incident report cited, and no count of affected installs is given.

Guardrails also have an availability story, and it is usually left implicit. Manuja's reframe is that a guardrail — prompt-injection defence, PII filter, toxicity classifier — is "just like another service that can go down that can be unreliable," which makes [fail-open versus fail-closed a decision to take in advance](../concepts/treat-guardrails-as-a-failable-dependency-with-a-time-budget.md) rather than a default to discover during an incident: "that's the trade-off between availability and security," with no universal answer, and the rule that "the default choice should be the worst case that you can live with." Three consequences follow for any checkpoint this topic recommends adding. It needs its own timeout and time budget, because "your request should never be bound by your guardrail timing. It should always be the LLM that is the rate determining step." It needs its own fallbacks — "secondary provider, secondary checks, cache decisions" — for the same reason model calls do. And its placement is a real choice with three costs: a pre-hook on the input is "probably the safest, but it does add serial latency," running concurrently with generation hides the latency but conflicts with streaming ("if you're specially producing structured output, please don't stream them"), and a post-hook is for auditing rather than blocking. This pulls against the coverage argument elsewhere in this topic: every additional checkpoint widens the attack surface it closes *and* the failure surface it opens, so the two should be resolved together. The talk reports no guardrail incident, latency figure, or availability number, and it does not address the hardest case — a guardrail that is up but degraded, returning verdicts of unknown quality, which neither a timeout nor a fail-open switch detects.

## Key Concepts

- [Treat Guardrails as a Failable Dependency With Its Own Time Budget](../concepts/treat-guardrails-as-a-failable-dependency-with-a-time-budget.md) - guardrails are services that go down, so decide fail-open versus fail-closed in advance, bound their time, and place them knowingly.
- [An AI-Infrastructure Package Is a High-Yield Credential Target](../concepts/an-ai-infrastructure-package-is-a-high-yield-credential-target.md) - a compromised LLM gateway package harvests keys from exactly the teams that self-host, and was found only because the payload crashed an editor.
- [Bound What an Unattended Automation May Emit, Including Emitting Nothing](../concepts/bound-what-an-unattended-automation-may-emit.md) - an output allow-list with cardinality caps turns a prompt-injected flood into a single artifact, and makes silence a legal outcome.
- [A Developer Laptop Is an Ambient-Credential Surface](../concepts/a-developer-laptop-is-an-ambient-credential-surface.md) - the dangerous agent is the obedient one that finds a production token nobody gave it, which no approval prompt and no per-tool scope can catch.
- [Escalate Risky Actions to a Read-Only Review Subagent](../concepts/escalate-risky-actions-to-a-read-only-review-subagent.md) - approval fatigue degrades the human gate, so a constrained model reviews first and the human sees the disagreements.
- [Judge an Action by How Explicitly the User Authorized It](../concepts/judge-an-action-by-how-explicitly-the-user-authorized-it.md) - a portable rubric for standing permissions, covering filesystem and network with the same question.
- [Sandbox Primitives Are Per Operating System](../concepts/sandbox-primitives-are-per-operating-system.md) - Seatbelt, Bubblewrap, and a hand-written Windows sandbox: isolation does not port with the harness.
- [Decrypt Agent Credentials Only at Tool Execution Time](../concepts/decrypt-agent-credentials-only-at-tool-execution-time.md) - never-in-context secrets are a consequence of where tool execution runs, not of prompt hygiene.
- [Reach Private MCP Servers With Outbound-Only Tunnels](../concepts/reach-private-mcp-servers-with-outbound-only-tunnels.md) - no listener, no inbound rule; the protected network dials out and its egress controls become the gate.
- [Agent Trust Needs a Certificate Issuer, Not a CAPTCHA](../concepts/agent-trust-needs-a-certificate-issuer-not-a-captcha.md) - the good-agent/bad-bot distinction is not recoverable from traffic signals, and no neutral issuer has taken the role.
- [Design an Agent-First Signup and Login Flow](../concepts/design-an-agent-first-signup-and-login-flow.md) - authentication, not capability, is the gate on enterprise computer use, and each improvised paradigm has a named cost.
- [Teach Calibrated Confidence So an Agent Knows When to Hand Off](../concepts/teach-calibrated-confidence-so-an-agent-knows-when-to-hand-off.md) - an agent that treats escalation as defeat will guess credentials against a live login form until the account locks.
- [Map RL Assumptions to Deployment Realities for Computer-Use Agents](../concepts/map-rl-assumptions-to-deployment-realities-for-computer-use-agents.md) - the passive-environment and clear-reward assumptions are the two a security review should attack first.
- [Chrome Stamps Every Input Trusted or Untrusted](../concepts/chrome-stamps-every-input-trusted-or-untrusted.md) - event-provenance checking is cheap and defeats only naive scripting, because a protocol-driven browser produces genuinely trusted events.
- [Climb a Humanness Ladder Only as High as the Page Forces](../concepts/climb-a-humanness-ladder-only-as-high-as-the-page-forces.md) - the attacker's escalation discipline, which tells a defender which of its signals imposes real cost.
- [Enforce Agent Egress Policy at the Wire Protocol, Below HTTP](../concepts/enforce-agent-egress-policy-below-the-http-layer.md) - the dangerous path is often a subprocess speaking a non-HTTP protocol through a tunnel, so the enforcement point has to parse bytes rather than requests.
- [Composed Access Defeats Per-System Credential Scoping](../concepts/composed-access-defeats-per-system-credential-scoping.md) - read-only credentials and curated MCP tools are correct and insufficient: reach is the composition of grants, and a subprocess bypasses the tool surface entirely.
- [Version-Control and Unit-Test the Agent Permission Policy](../concepts/version-control-and-unit-test-the-agent-permission-policy.md) - a thousand-line rule set is production code; fixture requests turn "are the guardrails still working?" into a build step.
- [Hold Unregulated Intimate Data to the Professional-Privilege Bar](../concepts/hold-unregulated-intimate-data-to-the-professional-privilege-bar.md) - some consumer products collect data more sensitive than what regulators cover, in a category regulators do not cover, so the handling standard has to be adopted from the corresponding profession.
- [An Audit Trail Is a Chain of Evidence, Not a Developer Log](../concepts/an-audit-trail-is-a-chain-of-evidence-not-a-developer-log.md) - the compliance frameworks demand every action, every data access, and the authorization behind each, durable enough to stand as evidence — a bar a DataDog-style log does not meet.
- [Store Agent Data in Object Storage Beside the Event Log, Not Inside It](../concepts/store-agent-data-in-object-storage-beside-the-event-log.md) - one enforcement point for zero-trust tokens at the point of use, PHI-free debugging, and an architectural rather than behavioral answer to the lethal trifecta.
- [Make Regulated-Data Failures Architecturally Impossible](../concepts/make-regulated-data-failures-architecturally-impossible.md) - strip regulated data at the pipeline boundary, cut every production-to-dev pipe, and scope access by region as well as role, so the system is incapable of the failure rather than forbidden from it.
- [Run Must-Not-Fail Decisions in a Code Layer Above the Model](../concepts/run-must-not-fail-decisions-in-code-above-the-model.md) - escalation, high-stakes routing, and authentication belong in deterministic code that runs before the model, because the published authority hierarchy makes every prompt layer one injection from override.
- [A Bigger Model Is Not Automatically a Safer or Better Agent](../concepts/a-bigger-model-is-not-automatically-a-safer-or-better-agent.md) - capability cuts both ways for security: poem jailbreaks work better on large models and broad remit widens attack surface, so aim for good-enough-to-perform but not arbitrary-harm capability.
- [Spec-Driven Agent Validation Goes Beyond the Test Set](../concepts/spec-driven-agent-validation-goes-beyond-the-test-set.md) - the agent spec (rules, ontologies, rights/roles, robustness) drives security and penetration testing because it marks the domains the agent engages and where it has power to act.
- [Vet MCP Servers As Action-Capable Extensions](../concepts/vet-mcp-servers-as-action-capable-extensions.md) - MCP servers connected to coding agents can access data and act for users, so trust and scope are security decisions.
- [Classify AI Bot Traffic By Intent And Benefit](../concepts/classify-ai-bot-traffic-by-intent-and-benefit.md) - access rules should distinguish search, training, user-triggered, and operator-style AI traffic.
- [Layer Bot Detection Signals Instead Of Trusting One Header](../concepts/layer-bot-detection-signals-instead-of-trusting-one-header.md) - bot identity needs multiple request, IP, and reputation signals.
- [Treat CAPTCHA And Proof Of Work As Economic Friction](../concepts/treat-captcha-and-proof-of-work-as-economic-friction.md) - challenges deter by changing economics, not by proving humanity perfectly.
- [Key Rate Limits By Fingerprint Or Session Instead Of IP Alone](../concepts/key-rate-limits-by-fingerprint-or-session-instead-of-ip-alone.md) - limits should follow stable client or user identity where possible.
- [The Open Web Is Adversarial to Agent Access](../concepts/the-open-web-is-adversarial-to-agent-access.md) - the agent-builder side of bot defense: blocked, poisoned, and device-variant pages degrade web grounding.
- [Model MCP Servers as OAuth Resource Servers](../concepts/model-mcp-servers-as-oauth-resource-servers.md) - MCP authorization should keep token issuance separate from tool-serving logic.
- [Enterprise MCP Requires SaaS Security Controls](../concepts/enterprise-mcp-requires-saas-security-controls.md) - production MCP needs SSO, provisioning, audit, DLP, abuse prevention, and access controls.
- [MCP Gateways Create an Enterprise Root of Trust](../concepts/mcp-gateways-create-an-enterprise-root-of-trust.md) - gateway policy points can reduce decentralized credential, network, audit, and malicious-server risk.
- [Dynamic Client Registration Pressures MCP Auth Stacks](../concepts/dynamic-client-registration-pressures-mcp-auth-stacks.md) - MCP client registration can overwhelm ordinary application-management surfaces.
- [Authorization Propagation Is the Hard Part of Enterprise Agent Workloads](../concepts/authorization-propagation-is-the-hard-part-of-enterprise-agent-workloads.md) - background agents need enforceable scopes and access context across MCP, A2A, and service-account boundaries.
- [Authenticate Agents With URL-Based PKI Identities](../concepts/authenticate-agents-with-url-based-pki-identities.md) - agent clients need verifiable identity when they act without a human delegation flow.
- [Authorize High-Impact Agent Actions Transactionally](../concepts/authorize-high-impact-agent-actions-transactionally.md) - sensitive actions need amount-, budget-, or action-specific authorization rather than broad standing scopes.
- [Preserve Authorization Chain of Custody Across Agent Hops](../concepts/preserve-authorization-chain-of-custody-across-agent-hops.md) - authorization context should survive MCP-to-API and agent-to-agent delegation.
- [Treat Agents As Users For Authorization](../concepts/treat-agents-as-users-for-authorization.md) - agent tools need requester-scoped authorization rather than service-level trust.
- [Move Agent Access Control to the Network Layer So the Sandbox Holds No Credential](../concepts/move-agent-access-control-to-the-network-layer.md) - separate isolation from access control and put authN/authZ on a verified-identity network so the agent holds a placeholder, not a key.
- [Make the LLM Gateway the Agent Observability Chokepoint](../concepts/make-the-llm-gateway-the-agent-observability-chokepoint.md) - routing every model call through one gateway node makes every tool call, bash command, and MCP request visible and policy-enforceable without in-container instrumentation.
- [Do Not Roll Your Own Agent Code Sandbox](../concepts/do-not-roll-your-own-agent-code-sandbox.md) - code execution boundaries can become arbitrary execution and lateral movement.
- [Server-Side Request Forgery Exfiltrates Agent Credentials](../concepts/server-side-request-forgery-exfiltrates-agent-credentials.md) - privileged agent fetch tools can leak tokens to attacker-controlled endpoints.
- [Treat Code-Executing Agents as RCE-Risk Surfaces](../concepts/treat-code-executing-agents-as-rce-risk-surfaces.md) - shell and code execution should be designed as an intentional remote-code-execution risk.
- [Give Code-Executing Agents Isolated Computers](../concepts/give-code-executing-agents-isolated-computers.md) - agent execution should happen in a dedicated container, VM, or OS sandbox with reviewable outputs.
- [Restrict Agent Internet Access With Allowlists](../concepts/restrict-agent-internet-access-with-allowlists.md) - network access should be disabled or constrained by explicit domains, commands, and HTTP methods.
- [Browser Agents Sit in the Prompt-Injection Lethal Trifecta](../concepts/browser-agents-sit-in-the-prompt-injection-lethal-trifecta.md) - private data, untrusted content, and external action channels combine, so keep consent friction by design and tier exposure from local dev to YOLO mode.
- [Keep Human Review on High-Risk Agent Operations](../concepts/keep-human-review-on-high-risk-agent-operations.md) - LLM monitors help, but sensitive commands, dependency changes, and diffs still need accountable review.
- [Enterprise Coding Agents Need Ownership, Auditability, and Action Controls](../concepts/enterprise-coding-agents-need-ownership-auditability-and-action-controls.md) - enterprise agent security needs audit logs, responsibility boundaries, and controls for destructive actions.
- [Human Ownership Keeps Agent Pull Requests From Bypassing Review](../concepts/human-ownership-keeps-agent-pull-requests-from-bypassing-review.md) - agent PR identity should not bypass second-human review or leave failures ownerless.
- [Delegate Agentic Commerce Transactions With Explicit Payment Authority](../concepts/delegate-agentic-commerce-transactions-with-explicit-payment-authority.md) - commerce agents need bounded payment authority before buying for users.
- [Bound Agent Payments With Processor-Enforced Mandate Tokens](../concepts/bound-agent-payments-with-processor-enforced-mandate-tokens.md) - share a token carrying a processor-enforced mandate scoped to a seller so spend limits hold regardless of agent or seller behavior.
- [Separate Non-Deterministic Discovery From Deterministic Payment Execution](../concepts/separate-non-deterministic-discovery-from-deterministic-payment.md) - the four agent-payment failure modes come from non-determinism in the transaction path, so payments and credentials should be deterministic with verifiable parties.
- [Ground Regulated Explanations in Deterministic Engines](../concepts/ground-regulated-explanations-in-deterministic-engines.md) - high-liability answers should keep authoritative calculations outside the model and check generated text for invented values.
- [Render Third-Party Generative UI Through a Double Iframe](../concepts/render-third-party-generative-ui-through-a-double-iframe.md) - hosting untrusted app UI is an origin-isolation problem where simpler single-frame designs leak host storage or escape the sandbox.
- [Filter Untrusted Context Before It Reaches the Agent](../concepts/filter-untrusted-context-before-it-reaches-the-agent.md) - screen ingested public signals, pages, and context for prompt injection at the boundary before any agent reads them.
- [Behavioral Evals Cannot Catch Sleeper-Agent Backdoors](../concepts/behavioral-evals-cannot-catch-sleeper-agent-backdoors.md) - a fine-tuning backdoor fires on a benign untested trigger and survives RLHF, so behavioral testing and monitors are structurally blind and the attack surface includes poison data, vendors, downloaded fine-tunes, and insiders.
- [Detect Fine-Tuning Backdoors With an Activation-Difference SAE](../concepts/detect-fine-tuning-backdoors-with-an-activation-difference-sae.md) - diff base vs fine-tuned activations and train a sparse autoencoder on the difference so a backdoor isolates as one feature at 40× the crosscoder signal, wired as a cheap "delta monitor" CI gate.

## Open Questions

- How do you detect a guardrail that is up but wrong? Fail-open and fail-closed both assume the failure is legible — a timeout, an error, an unreachable service. A classifier returning confident verdicts of degraded quality passes every availability check while the protection it represents is gone, and no source in this wiki describes a monitor for that state short of re-running a golden set against the live guardrail. ([Manuja](../sources/20260828_zrZ1amZBSPw.md), 10:12-11:38)
- What would have detected the LiteLLM compromise if the payload had been well written? The only reported detection was a crash in Cursor while running the LiteLLM MCP server, three hours into a window that had already ended. Nothing in this wiki describes a control that would have caught a quiet credential harvester inside a trusted dependency of the agent stack — not pinning (the compromise was in a published release), not MCP vetting (the server was the legitimate one), not sandboxing the agent (the malicious code ran at install and import time, outside whatever jail the agent uses). The practical question a team can act on is narrower: which of the keys reachable from a developer machine could have been short-lived or broker-issued instead of sitting in a file.
- Does capping the output channel help when the agent still holds write-capable tools? An allow-list of emittable artifacts constrains the sanctioned exit — one pull request, no issues, nothing at all. It says nothing about the tools the run was granted in order to do its job, and an injected agent that can execute a build step, call an allowlisted endpoint, or write to the workspace has exits that are not artifacts. No source here distinguishes "the outputs the platform will publish on the agent's behalf" from "the effects the agent can cause," and the security value of the cap depends entirely on how narrow the gap between them is. The related and unexamined question is what happens on a cap breach: whether the run is killed, the excess silently dropped, or a human told, is never stated, and each choice has a different failure mode.
- What is the threat model for the vendor cloud that replaces the laptop? Every source in this topic that recommends relocating agent execution off developer machines treats the destination as trusted by construction. Nobody states what the hosting provider can see, what isolation exists between tenants running the same organization's code, or what evidence a team should require before moving its repositories and credentials there — which is the same enumeration failure the laptop argument is built on, pointed the other way.
- How common is the ambient-credential incident, actually? "It still happens" is the strongest claim any source makes, with no rate, no post-mortem, and no description of how such an event would even be detected after the fact. Without that, the argument for relocation rests on plausibility, and teams have no way to weigh it against the cost of getting every project running in a sandbox.
- How often does a model reviewer approve something a human would have stopped? Replacing per-action prompts with an automatic reviewer is a trade between a known failure (users clicking yes) and an unmeasured one, and no false-approval or false-escalation rate is published for any such reviewer.
- What defends a review subagent whose evidence is the transcript it is reviewing? The reviewer reads the conversation to judge whether the user authorized an action, which places the judge downstream of the same injected text that could have produced the action. No source describes an adversarial test of that arrangement.
- Does approval fatigue have a measurable threshold? "People started clicking yes" is a real observation with no rate attached — prompts per session, or prompts per hour, at which attention collapses. Without one, "escalate less" and "escalate more" are both defensible and neither is checkable.
- Who audits the tool-execution layer once it is the only component that touches real credentials? "The model never sees your security tokens" moves the exposure to the moment of decryption, where a compromised tool, an uploaded skill, or a tool that echoes its own auth header into its return value all reach the secret. No source in this wiki describes what is logged at decryption time or what constrains what a tool may do with the credential it was handed.
- What is the operational failure mode of an outbound-only tunnel to a private MCP server? A persistent dial-out connection can drop, and when it does the agent's tools vanish mid-session rather than erroring in a way the loop can reason about. No source describes reconnection behavior, availability expectations, or how the tunnel itself is authenticated.
- A complete session log is a security artifact, not just an operational one. Making the session durable means persisting everything the agent saw, including whatever sensitive material passed through its context, and no source states retention, access control, or redaction for that store.
- A visual lure (an ad styled like the submit button) evades text-level injection filtering entirely. What detects it — a model trained to distinguish sponsored surfaces, a harness check that the click target belongs to the task's origin, or an egress rule that blocks the navigation? Mishra's fixed trajectory shows the model solving it ("I see two submit buttons. One is sponsored"), and no source in this wiki measures how reliably that holds on a page designed to fool it.
- A wire-protocol proxy is only as complete as its parser inventory. Claw Patrol ships a plugin system for unfamiliar protocols, which means an agent reaching a protocol nobody wrote a plugin for gets either a default-deny it cannot work around or an unparsed passthrough. Which default does a protocol-parsing egress proxy have to pick, and what does the operational cost of default-deny look like for an agent whose job is unblocking production incidents?
- Deno's design is stated to depend on everything being "off the internet" and inside a tailnet, which is what makes a single exit node a real chokepoint. What does the same architecture cost a team whose agents must legitimately reach third-party SaaS over the public internet, where TLS termination at the proxy becomes the price of parsing the bytes?
- If perception challenges now cost an attacker only inference and timing constraints cost engineering, what is the defensive equivalent of a round timer for ordinary application flows — and how much legitimate-user friction does deadline-based verification create for people using assistive technology or slow connections?
- Who could credibly issue an agent certificate, and what would it attest to? Klein's Verisign analogy assumes a trust root exists to be occupied, but a CA vouches for domain control, not for behavior — an issuer for agents would have to certify something closer to conduct, which has no obvious revocation trigger short of an incident. A compromised or lax issuer also becomes a single ecosystem-wide failure point that today's per-site detection does not have.
- Which HTTP message signature and private access token patterns will get enough crawler, browser, and site adoption to become practical for general bot policy?
- Which agent identity and attestation patterns will become practical enough for open MCP ecosystems without recreating brittle pre-registration workflows?
- How should code-executing agent products balance full-auto sandboxed work against approval fatigue for commands that are low-risk individually but high-risk in aggregate?
- A voluntarily adopted privacy bar has no external enforcement. Cockrell states the standard CoupleWork holds itself to but describes no retention policy, training-data exclusion, or audit; what evidence should a user or an acquirer require that an unregulated product's stated privilege bar is actually implemented in its pipelines?
- Process-level data segregation blocks the exfiltration leg of the trifecta only if the agent's tools cannot re-open a channel. What is the practical boundary of the technique for agents that must legitimately write to an external system of record in the same run?
