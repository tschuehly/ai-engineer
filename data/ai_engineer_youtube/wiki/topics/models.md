# Models

## Overview

Model work in this wiki covers how AI engineers choose, train, adapt, and deploy model architectures under real constraints. The current sources show complementary views: small or edge models make deployment practical when memory, latency, privacy, and accelerator access matter; from-scratch local training exposes the tokenizer, architecture, training-loop, and inference choices that are often hidden behind high-level APIs; generative-media models need data curation, learned latent representations, denoising architectures, sampling controls, artifact-aware data, and perceptual evals suited to image and video topology; and non-language frontier models can be optimized for retrieval, weather, or interactive environments. Edge-scale and local workstation models should be treated as deployment-constrained systems: target hardware, memory capacity, memory bandwidth, runtime support, and quantization format can matter as much as parameter count. Edge-scale models should be profiled on target hardware, quantized to the device envelope, and post-trained for narrow capabilities rather than judged as miniature general-purpose chatbots. Model choice should also account for behavioral reliability: some models improve on public leaderboards while still accepting nonsensical premises, overusing reasoning, or underperforming on fuzzy expert work. Gemma 4 adds a concrete routing pattern inside one open-weight family: effective on-device variants, sparse MoE efficiency, and dense long-context reasoning variants serve different deployment and workflow shapes. Gemma also shows that open model families need ecosystem compatibility: permissive licensing, common runtimes, fine-tuning tools, multilingual tokenizers, quantized Hugging Face distribution, domain variants, and familiar client APIs can matter as much as the base model when teams adapt models for local, low-resource, safety, or medical workflows. Enterprise open-model adoption adds a task-pressure lens: hosted frontier APIs remain easy defaults, but open or in-house models become attractive when a narrow workload has proprietary labeled data, strict latency needs, exploding agentic call volume, or a strategic need for AI-layer differentiation. Open-weight ownership adds a sovereignty lens on top of that task pressure: owning the weights removes loss-of-service risk, keeps proprietary data inside owned infrastructure, and lets teams customize freely, while a permissive license (Gemma 4 moved from a custom Gemma license to Apache 2.0) clears the ~18-month procurement and legal review that previously blocked sovereign and regulated adoption. The same family also argues for intelligence-per-size: a 31B dense model that ranks near the top of open-model leaderboards while running on a single GPU shifts the build/own calculation when comparable quality otherwise needs four or five GPUs. Tiny models add another pattern: specialize and fine-tune narrow components, then compose them into a product workflow.

Encoder models add a guardrail-specific model pattern. When the job is to classify whether an input, retrieved chunk, tool description, model response, or agent plan is safe, a bidirectional encoder with a classification head can be a better production fit than a generative judge because it can inspect the full sequence in one forward pass and return a compact binary or policy label. Agent organizations add a model-routing layer: not every role needs frontier-model cost, so teams should choose models by role intelligence needs, quality bar, budget, and latency.

Long-tail knowledge adaptation adds a memory-oriented model pattern. When a domain is too private, too new, or too underrepresented for a base model, teams can choose between spending at inference time through context, RAG, or deep-research loops and spending at training time by turning source facts into a model update. The source-backed caveat is that naive fine-tuning can memorize and damage general behavior; useful weight updates need curated data generation, selective update strategies, and regression evaluation.

Long-horizon agent models add a post-training pressure: fluent next-token continuation is not the same as sustained task completion. Poolside's public demo frames reinforcement learning as the missing ingredient for moving from completions and chat toward autonomous software-development and knowledge-work agents, especially when the target behavior spans codebase inspection, translation, testing, feature addition, and iterative verification.

DeepSeek R1/V3 adds a reasoning-model version of that post-training lesson. The Paper Club recap frames the May 28 update as better RL on the same model family, not a wholly new base model: more post-training made the model spend more test-time reasoning tokens on hard math/coding prompts and improved benchmarked reasoning, JSON output, and function calling. The same source also highlights reasoning-trace distillation as a small-model lever: an improved reasoning teacher can generate traces that transfer surprising capability into an 8B-class student.

Code world models add an execution-aware variant of model training for software. Instead of treating code only as syntax, CWM trains around program execution traces: local variables, memory, line-by-line state, repository-level test and CI traces, and state/action/state transitions. This makes code a constrained world-modeling substrate where a model can learn to simulate program behavior, support neural-debugger interfaces, and reason about expensive execution paths before every real-world action is run.

Coding-model evaluation needs model-family progress to be measured against fresh and appropriately difficult tasks. Dynamic code benchmarks can use post-training-window problem releases and changing difficulty distributions to avoid confusing memorized or saturated task sets with genuine model improvement. As coding models move from completions to repository optimization and translation, evals should also measure whether the model's apparent improvement survives real task distributions, runtime checks, and reward-hack detection. Sonar's cross-model code-quality benchmark adds a model-selection caveat for code generation: capability and conciseness diverge. Running 4,444+ Java assignments through 53+ models showed newer/larger models bloat output (GPT-4o < 250,000 lines; GPT-5.4 ~1.2 million; Claude Sonnet 4.6 627,000 with the highest security-issue rate at 300 per million LOC) while the pass-rate leader (Gemini 3.1 Pro High, 84.17%) stayed concise, so picking a code model on pass rate alone ignores the bug density, complexity, and security cost that scales with the lines emitted.

Coding and workplace-agent models also need training signals that look like the work they will do. MiniMax M2 adds a compact open-weight model pattern: train against scaled coding environments and verifiable goals, use expert developers as a reward/evaluation source, teach repeated reasoning-tool loops for noisy environments, perturb scaffolds so the behavior is not tied to one harness, and exploit small active-parameter cost when many parallel agent copies are useful.

Cline's RL environment factory adds a data-production pattern for that training pressure: real coding-agent sessions can be converted into portable environments with start states, prompts, solved end states, traces, and outcome verifiers. In that framing, the agent product is not only an interface around current models; it is also a source of hard tasks that can shape future model capability. Prime Intellect generalizes this environment pattern beyond RL: a product harness with tasks and rewards can become an eval, synthetic-data generator, SFT or distillation source, RL training loop, and model-customization substrate.

Applied Compute adds the enterprise specialization and systems-efficiency layer for RL. In that framing, RL turns private customer workflows into private benchmarks, then improves a specialized model through repeated use and data flywheels. Because those runs serve customer delivery rather than open-ended lab research, speed, cost, and low-variance runtime are product requirements. Asynchronous pipeline RL can improve GPU utilization by decoupling sampling from training, but it introduces stale-policy tokens and a throughput/stability tradeoff that has to be modeled before launch.

OpenAI's Agent RFT talk adds a hosted, tool-using version of that post-training pattern. It treats reinforcement fine-tuning as a late-stage lever for multi-step agents after teams have matched training and eval data to production, measured a base-model baseline, and optimized prompts, tools, and task shape. The model learns from sampled trajectories that call real tool endpoints and receive custom reward signals, so useful gains depend on objective task definitions, enough exploration variance, and graders that capture production success rather than easy-to-game proxy behavior.

Cursor Composer adds a product-owned coding-model example: reinforcement learning can specialize a model for a concrete IDE agent workflow when the training loop uses high-quality data, enough compute, and the same tools and environment the model will see at inference time. Its reported improvements are behavioral as much as benchmark-oriented: the model learned to use semantic search, read files before editing, and call tools in parallel.

Snorkel's FinQA result sharpens the behavior-versus-knowledge framing for the build/own decision. A 4B model RL-finetuned with GRPO on a financial-analysis tool task outperformed Qwen 3 235B, because the failing behavior was tool discipline (discover tables, inspect the schema before querying, self-correct on tool errors), not reasoning depth — the large model queried a non-existent table and hallucinated, while the small model used the tools correctly. RL is positioned here as a behavior-changing lever rather than a knowledge-changing one, and the run was cheap (~21 hours, under $500), making self-hosted small-model specialization tractable. Two training-data lessons reinforce the small-model case: single-table-only training beat both a multi-table mix and curriculum learning and still generalized to the harder multi-table benchmark (13.9% → 26.6%), and rubric-decomposed evals were used to find the specific behavior to fix before any training data was generated.

Snorkel's "task fidelity" experiment (also Kobie Crawford) makes the data-quality lever quantitative for agentic RL: holding the model, compute budget, and task count fixed, an RL run on high-quality (accepted) tasks improved the base model ~6% while the same run on low-quality (rejected) tasks improved it only ~1% — a 5x training uplift from task quality alone, on the premise that for agentic work "task quality and data quality are largely the same thing." Quality is operationalized as a four-criteria gate (achievable, non-trivial, functionally correct, environment-reliable) over containerized TerminalBench-style tasks; accepted tasks measurably show 2x tool calls, lower pass rates, and more output tokens, and their *failures are cleaner* — a well-specified task fails for a real reason, whereas an ambiguous one fails on a spec-test mismatch or a missing implicit dependency and produces noise, not a harder problem. This complements the small-model RL concepts above: with model and compute fixed, curating tasks for quality returns more than adding low-quality tasks, which can even add noise that masks real model improvement, and expert-in-the-loop generation (plus rubrics and high human/LLM-judge inter-annotator agreement) is what delivers that quality at scale.

Modal's "what lies beneath the API" framing turns the build/own question into a timing decision with concrete signals. As a product matures and specializes, fine-tuning becomes the destination rather than the exception — because the frontier labs want their models to win at everything while you want yours to win at your business logic (the Decagon framing, with Intercom beating its frontier API at roughly one-fifth the cost and Pinterest claiming orders of magnitude). Three signals say the moment is near: you pay more for the API than your customers pay you (even after token-cutting tricks like "caveman mode"), your evals have plateaued, and your latency/throughput needs exceed a shared endpoint — gated by a garbage-in-garbage-out prerequisite that you must already be collecting data and have mature evals. This complements the enterprise-open-model-adoption and ownership-threshold concepts (which frame leaving the hosted API by task pressure and a four-axis cost call) and the readiness lesson sharpened here: if you've already built an agent harness and are collecting eval data, you have what you need to start RL, because the harness is the environment and the eval data is the training signal. The accessibility claim is that supervised fine-tuning (and RL) now fit in ~300 lines of Python via open-source libraries, so the work that remains is data and evals, not hand-taping gradients or owning a cluster.

GLM 4.6 adds a staged open-model training recipe for long-context coding and agent behavior. The useful pattern is not just more tokens: general pretraining is followed by code and reasoning continuation, repo-level code contexts, synthetic reasoning traces, long-context agent data, and RL systems that treat short reasoning tasks differently from slow software-engineering trajectories. Its reported post-training details also expose concrete failure modes: multistage short-to-long RL can erode long-context ability, sequence-mean loss can encourage short reward-seeking coding outputs, and mixed-quality scientific reasoning data can underperform smaller expert-verified datasets.

Brockman's research-engineering framing keeps model progress tied to executable systems. The AlexNet example combines an idea with fast GPU kernels, and current frontier work adds 100,000-GPU systems plus complex RL orchestration. Model capability should therefore be understood as the product of research direction, data, training method, runtime systems, and infrastructure rather than a research paper or parameter count alone.

Morph's Magi 1 framing pushes that idea toward branch-aware reasoning models: the model is intended to be trained from the ground up to use a branchable cloud substrate, delegate to subagents, run verified environment searches, and call external verification software. The reusable model lesson is that some capabilities may require co-designing the model objective with the execution environment rather than adding a tool after training.

Computer-vision models add a visual-fidelity caveat to multimodal model selection. Caption-aligned VLMs can look semantically competent while missing fine details that captions never supervised, such as object part pose, direction, clock hands, or domain-specific visual classes. Vision-only self-supervised backbones such as DINOv2 can preserve richer visual feature structure, but the useful engineering target is aligning those features with language and object-detection heads without reducing them to caption-level semantics.

Robot foundation models add action as another model output modality. GR00T N1's vision-language-action framing combines image observations, robot state, and language prompts, then outputs action trajectories through a dual-system architecture and embodiment-specific decoder. Physical Intelligence adds a complementary VLA architecture: start from a pretrained VLM-like backbone, train it on robot data and multimodal annotations for scene understanding and high-level task subdivision, then add an action expert transformer that attends to the backbone and emits continuous robot actions through diffusion flow matching. The model lesson is that physical AI needs scarce action data, sim-to-real strategy, realtime control, held-out-environment evaluation, and body-specific output adaptation in addition to ordinary foundation-model pretraining.

Autonomous driving adds a route-conditioned multimodal planning variant. Waymo's EMMA exploration uses a Gemini-based model with route text and eight-camera video as input, then predicts future waypoints. The model lesson is that foundation models can be adapted to action domains by converting existing operational logs into self-supervised future-state targets, but end-to-end action models need intermediate reasoning outputs and simulation-based evals before raw benchmark quality is persuasive.

Mechanistic interpretability adds a model-internal engineering surface. Instead of treating the model as only a prompt-response box, feature attribution can show which learned concepts contributed to a token, activation steering can adjust a behavior at inference time, dynamic prompting can trigger instructions when internal features fire, and model diffs can inspect post-training changes. These controls should be evaluated like any other model intervention because they can be powerful, hidden from users, and narrower than ordinary prompt or fine-tuning changes. Model diffs sharpen into a concrete safety monitor when the diff is taken over *activations* rather than features: subtracting base-model activations from a fine-tuned model's and training a sparse autoencoder on the difference isolates a fine-tuning backdoor as a single interpretable feature at 40× the signal of joint cross-model features (crosscoders), cheap enough to run as a CI gate — a reminder that comparing checkpoints at the internal level can surface risk that aggregate evals cannot.

Hosted model upgrades should be treated as production migrations when prompts and domain rules carry business meaning. Intuit's TurboTax experience shows that long-term contracts, prompt dependence, fine-tuned variants, and even same-vendor model changes can create migration work; the practical release gate is whether the new model preserves quality, latency, and regulated-domain correctness against established evals.

Model-tier selection should also track how deterministic a step is, not only its difficulty. Qodo's 80/20 framing pairs frontier high-reasoning models with the open-ended discovery 80% of a task, but deliberately uses lighter, cheaper models for the deterministic validation 20% — a critic node that checks goal versus result needs no research, so spending frontier reasoning on it is waste. This sharpens the role-routing concepts in this topic (choose a model by role intelligence needs, quality bar, budget, and latency): a "needs reasoning" axis and a "needs determinism" axis can point to different model tiers within the same multi-agent workflow. A hard real-time latency budget can pin model size directly: in Together AI's voice-agent pipeline the LLM dominates the latency/cost budget (over TTS, then STT), and a ~200-300 ms time-to-first-token target forces an ~8-30B sweet spot — larger blows the budget, smaller breaks tool calling — with use-case fine-tuning the lever to recover tool-calling quality in a model small enough to stay inside the budget. The "thinker-talker" pattern then lets a small conversation model keep the fast path fast while delegating hard requests to a bigger model via a single tool call.

Extending a model's context is also a training-systems problem, not only an architecture choice. Together AI's "road to 5M tokens" work frames long-context training as incremental memory engineering: a standard LLaMA 3B at a 3M-token context out-of-memories on an 8×H100 node before any activations exist, and no single trick fixes it. The reusable lesson is to layer FSDP, DeepSpeed Ulysses context parallelism, activation checkpointing, CPU offloading of transformer-block inputs, and Arctic-style chunked sequence training until 3M tokens fits, then go deeper into context parallelism with "Untied Ulysses" — chunking attention heads and reusing one smaller buffer across iterations because one head-group already saturates GPU compute — to reach 5M while matching the most memory-optimized training baselines at 8B and 32B. This complements the local-training and long-context-RL concepts in this topic: where local from-scratch training exposes the tokenizer/architecture/loop pieces and single-stage RL preserves long-context ability, the memory stack is what makes a multi-million-token training run physically fit on the hardware at all, and bottlenecks (per the talk) appear where you least expect, so profiling memory comes before optimizing it.

Choosing and switching models is itself a disciplined process, not a leaderboard reflex. Cline's eval framing warns against reading similar benchmark numbers as model equivalence ("GPT 5.4 ≈ Gemini 3.1 Pro" — they're not), against believing a lab's launch number, and against being the earliest adopter: let a new model settle for a couple weeks and switch only if it stands the test of time. Just as important, a model that underperforms in your product is often a harness gap, not a model gap — prompt-engineering techniques are model-family-specific (Anthropic ≠ Codex ≠ Gemini), so adopting a new family means hill-climbing its own harness tuning, which then unlocks the users who prefer that family. This complements the role-routing concepts above: model selection has to account for how a model interacts with your harness, not only its raw capability.

Audio models add a specialist-vs-generalist composition choice. Speaker diarization ("who speaks when") is a distinct model class from speech-to-text, with its own pipeline (voice activity detection → segmentation/overlap → speaker assignment) and its own error metric (diarization error rate), and it stays unsolved precisely where production audio lives: the number of speakers is unknown a priori, labels are permutation-invariant, and overlap, short backchannels, and distant mics break naive systems. Building "who said what" by composing a diarization model with a single-speaker-trained STT is therefore not a timestamp join — pyannoteAI reconciles the two with an STT-agnostic orchestration layer, the architectural alternative to collapsing diarization and transcription into one frontier multimodal call. This is also a benchmarking caution that generalizes beyond audio: a leaderboard number is only meaningful with its measurement conditions, since NVIDIA Parakeet's 11.4% AMI word error rate (close-talk headset mic) becomes 26% on the same model and data through the distant table mic.

Text diffusion adds a non-autoregressive generation paradigm to the model menu. Instead of predicting one token at a time, a diffusion language model initializes the whole output to noise and iteratively denoises it over a few passes, attending bidirectionally so every token sees the full canvas — the language analogue of the image/video diffusion that this topic already covers (DeepMind's Gemini Diffusion, a Gemini 2.0 Flash-Lite variant, reached comparable quality at much lower latency). Two capabilities follow from the bidirectional, iterative process and are hard for autoregressive models: it can self-correct by revising an early answer after finishing reasoning it had not yet committed to — a small Gemini Diffusion model fixed a wrong first guess (39) where much larger GPT-4o corrected only after the fact and Gemini 2.5 Flash locked the error in — and it exposes denoising-step count as an adaptive test-time compute knob, where quality rises roughly monotonically with more passes and the model decides for itself how many steps each prompt needs. The serving economics are the catch and belong to the Inference topic: low latency per request comes with low big-batch throughput, which is why frontier production models remain autoregressive and text diffusion fits on-device first.

Model selection should also resist the "pick the biggest model at the top of the leaderboard" reflex on efficiency grounds, not only behavior grounds. Pruna's Bertrand Charpentier argues that "state of the art" is not a single model but a quality–efficiency Pareto front: because quality is driven by compute, the leaderboard winner is usually the most expensive option, yet quality scores tend to cluster (3–4 image models within ~1,100–1,200 Elo) while efficiency varies up to ~20x, so the marginal quality gain is often not worth the cost. Plotting a quality score against latency or cost, ideally with a metric specific to the target use case (e.g. text rendering), tends to surface small specialized "performance models" rather than large foundation models — the same intelligence-per-size and small-specialized-model conclusions this topic reaches from the open-weight and tiny-model angles, arrived at here from the evaluation side. This complements the routing concepts (compare models by task, thinking budget, cost, and latency) by adding efficiency as a first-class state-of-the-art dimension rather than a deployment afterthought, and pairs with the efficiency-company view that the same diffusion model can be compressed (per-module quantization, pruning, denoiser-step reduction via distillation/caching) far down the cost axis while staying on the quality front.

Model-size selection for agents also has a safety axis that cuts against "bigger is better." Safe Intelligence's Steven Willmott notes that a more capable model can be *easier* to jailbreak — a malicious instruction wrapped in a poem is decoded and acted on by a large model but is opaque to a small one — and that a broad-remit agent widens both the exploit and the test surface, on top of the usual cost and latency penalty of using a large model for simple work. For automated deployment this is a smart-vs-safe tradeoff, and the target is a model good enough to perform the task but not capable of arbitrary harm. This sharpens the efficiency and small-specialized-model conclusions above with a security-driven reason to right-size: the smallest sufficient model is often safer as well as cheaper.

The small-specialized-model conclusion extends to purpose-trained agents, not only single-call inference. Mixedbread distills a *retrieval agent* into a small fast LLM (for latency) via supervised fine-tuning from a larger teacher, then tunes it with on-policy RL against a composite search reward — a retrieval term (NDCG plus an LLM rubric judge) and a trajectory term (an LLM judge rewarding natural-sentence queries and the right exploration depth). A small trained agent given a strong search tool beat much larger models with default tools (top-1 on Snowflake's DocQA with Gemini 2.5 Flash as the answer model), reinforcing that task-specific training plus the right tools can outperform raw model scale — the trajectory reward, which specifically shapes *how the agent searches*, is what closes the query-quality gap that a bigger general model does not.

RL Nabors (Arize) gives the applied, per-feature procedure that the efficiency and right-sizing threads above imply: "prototype big, deploy small." Rather than reading a leaderboard or taking a peer recommendation, prove a feature is possible on the largest model, freeze its behavior as a golden dataset of success criteria, run a capability eval that benchmarks candidate small models against that baseline, and select the SAGE ("small and good enough") model — the smallest one whose outputs are acceptable for your inputs. In her summarization case the measured winner (Llama 3.2 3B, ~90% accuracy at low latency) beat both a slower Gemma 4 5B and the model most engineers recommended, and the remaining gap closed with per-variant prompt engineering plus deterministic harness post-processing rather than a bigger model. This is the same "not overpaying for scale you don't need" conclusion the Pareto-front and small-specialized-model concepts reach, arrived at from the product-eval side and paired with an on-device deployment target (Chrome's Gemini Nano, Pixel-class SLMs).

Vasant Kearney (Onlay) supplies the deployment-side corollary of that same rejection, from a production claims system: "you can't just replace the model and assume it's going to be better. It's different." A model that wins "on certain evals … as measured by these different metrics" need not be better for your situations "because of the way you've designed your system," so a swap means redoing evals, testing, and validation from scratch rather than bumping a dependency — the concrete case behind [treating model and prompt upgrades as regulated migrations](../concepts/treat-model-and-prompt-upgrades-as-regulated-migrations.md). He pairs it with the cost side of model selection this topic's right-sizing thread argues from evals: an overpowered, over-expensive model on "routine things that need to be done a thousand times a day" defeats the cost-reduction goal the system exists to serve.

Thariq Shihipar (Anthropic) adds a model-behavior framing for reasoning about a new release: "the models are grown, not designed," so a new model should be treated "closer to a biology than a physics" — empirical and organic, with rules not fully known (he points to Anthropic's "Biology of a Large Language Model" paper). The practically important property is that capability arrives *spiky*, not uniformly, so there is a [capability overhang](../concepts/capability-overhang-tools-decide-which-model-spikes-you-reach.md): the model knows every Pokémon but can't name the ones ending in "aw" until a tool lets it filter, and much of a new model's real gain is unlocked at the harness rather than read off a benchmark. This complements this topic's efficiency/right-sizing thread from the other direction — those conclusions are about *not overpaying* for scale you don't need, while capability overhang is about *not underusing* the scale you already have because the tools don't reach its spikes; both reject "the leaderboard number is the model's value."

Domain speech models show a different specialization path than fine-tuning a text LLM. Hippocratic AI's recognition stack is a decoder-only *audio* LLM rather than a speech-to-text function: an open-source Whisper V3 large turbo encoder fine-tuned on millions of clinical conversations, a conformer projector that compacts audio into language-model tokens while preserving prosody so "the model hears not just the what, but also the how," and then conversation state and domain knowledge supplied as context alongside the audio — the basis for [conditioning ASR on conversation context and domain vocabulary](../concepts/condition-asr-on-conversation-context-and-domain-vocabulary.md). Two model-level lessons generalize. Contextual biasing can be *trained in* as well as prompted: millions of synthetic entities (patient addresses, phone numbers) run through training so utterances like "1100 Boulevard" survive. And the accuracy that matters is domain accuracy — a fine-tuned open encoder plus context conditioning cut medical word error rate by over 50% against off-the-shelf models while measuring 3x faster at P99, which is the concrete case for owning the model when the deployment vocabulary is finite and the errors are expensive.

Ayush Bhardwaj (Allos AI) adds a domain-shaped ceiling to the capability picture, and it is a claim about corpora rather than about architecture or scale. In finance and pharma, [high-value vertical data is withheld by design](../concepts/high-value-vertical-data-is-withheld-by-design.md): institutional managers over $100 million in qualifying US equities must file holdings quarterly and see returns fall once competitors reverse-engineer them, so the reasoning stays private; clinical-trial disclosure is legally required yet "30% of the funds, which is nearly 1/3 of firms, never do," with the FDA publicly reminding roughly 2,000 sponsors in 2026. Since the withheld material is exactly "the data which helps your LLM actually reason through these complex and niche industries," his conclusion for model selection is that "neither OpenAI nor Anthropic has this data" — waiting for the next base model is not a plan in a domain whose corpus was never published. The same absence explains why he treats reinforcement learning from verifiable rewards as a boundary rather than a template: it "is really good at math and code because you have answer keys," and those verticals have none. His post-training note qualifies this wiki's fine-tuning-readiness material with an operating cost: fine-tune one open model and "Alibaba Cloud or let's say DeepSeek will release a newer model, then you have to fine-tune that too as well. So there is a cost. It's not cheap."

Chaitanya Asawa (Abridge) answers the question Bhardwaj's ceiling raises — if you do hold data the labs cannot get, when is training your own model actually the right move — and his answer separates two cases that this topic usually blurs. Where "the quality is already maxed out," post-training is a pure efficiency play with no bet attached: you train to cut cost and latency. Where quality is *not* maxed out, the usual objection applies ("oh, the frontier model would just steamroll you"), and the counter is a claim about derivatives rather than levels: "we can actually potentially beat the rate of change on the frontier model if we have the right to win by having the right data that they may not have and the focus on a problem that they may not be focusing on." Both conditions are load-bearing — unique data without narrow focus loses once a lab decides to care, and narrow focus without unique data loses to the next release — which is what makes [a right to win](../concepts/train-your-own-models-only-where-you-have-a-right-to-win.md) a usable test rather than a slogan. Abridge's asset is the complement of Bhardwaj's: where his corpora are defensible because publishing them destroys their value, Abridge's is a renewing byproduct of deployment at scale, "a hundred million medical conversations a year" that "as far as we know, no one else has." The cash-out is structural rather than heroic: [decompose the deliverable and post-train a model per section](../concepts/decompose-the-deliverable-and-post-train-a-model-per-section.md), because a clinical note is really history of present illness, past medical history, and assessment and plan, and "health care is actually many specific workflows. You don't need … frontier level intelligence for every problem." That is the practical answer to where the narrow tasks come from in this topic's small-model thread — read the structure of the artifact rather than hunting for a capability to isolate. The honest limit is that the rate-of-change claim is stated as a bet, with no measurement of the two curves and no stated trigger for retiring a post-trained model when a frontier release catches up.

Krea's Krea 2 talk supplies the image-model counterpart to that post-training thread, and its most transferable claim is about what the stages are for rather than what diffusion is. Once the architecture is locked, Sangwu Lee treats the ladder as directly borrowed from LLM practice — [run the LLM post-training ladder on diffusion models](../concepts/run-the-llm-post-training-ladder-on-diffusion-models.md): a 256→1K resolution curriculum where low resolution teaches semantics and high resolution teaches structure and detail, then mid-training and SFT on curated illustration, graphic design, photography, and cinematics "to kind of mold your distribution" (a pre-trained diffusion model, like a pre-trained LLM, is "just basically auto complete"), then preference optimization on A/B pairs where "we get a little bit more opinionated," then GRPO-style RL against reward servers targeting text rendering and anatomy. Two additions are diffusion-specific: a separately trained prompt expander that rewrites short user prompts into long ones that sit closer to the training distribution, and current work on multi-expert on-policy distillation that merges capability-specialized experts into a single student. The stated reason for borrowing is engineering economy rather than theory — prefer "methods that have like low number of hyper parameters" and steal from LLM research "so that I can just reuse their kernels and… research and… literature" — which is the same reuse argument this topic makes for open-model ecosystems, applied to research tooling. Where the analogy stops is the input: for media models the differentiating asset is not a private corpus of workflows but the *filtered* public one, and Lee's ranking of levers puts data above methods on durability grounds — "methods can change… but data is like eternal."

The infrastructure half of the same Krea 2 project, presented separately by Gabriel Jorge Menezes, is what the research half omits and it changes the cost picture of "train from scratch." Krea 2 was pre-trained with no base checkpoint on thousands of InfiniBand-connected GPUs, and the reported constraint was not compute budget but uptime: crashes scale with cluster size, many are silent (NCCL timeouts while every dashboard reads healthy), and their runs lasted far less than a published Meta failure-rate estimate would predict — short enough that "doing large-scale pre-training on runs that last less than 8 hours, it is a problem." The practices that made the run finish are generic to from-scratch training rather than to diffusion: [instrument tensor cores and the fabric rather than GPU utilization](../concepts/measure-tensor-core-utilization-not-gpu-utilization.md), because the utilization number reads 100% while the cluster is underused and because DCGM exports no InfiniBand counters even though cross-node communication caused most of their failures; and [let training crash and checkpoint against a fast filesystem](../concepts/let-training-crash-and-checkpoint-against-a-fast-filesystem.md), because identical machines running identical code go an hour and then twenty-four, so the cheap answer is threshold-based hardware replacement plus checkpoints frequent enough to make a crash cost minutes. One detail links the two halves directly: the resolution curriculum Lee describes as a training-method choice is visible in Menezes's dashboards as rising tensor core utilization from 128 up to 1024 pixels — the same decision seen as arithmetic intensity. Read together, the two talks say the from-scratch decision buys architecture and data control at the price of an operations practice, and the research talk's "fast-iteration infrastructure" line item is the thing that has to be built first.

Real-time interactive video is arriving as its own model family, and Reactor's Ahmed Ahres gives it a working taxonomy rather than a capability claim: [pick a real-time world-model class by what the user steers](../concepts/pick-a-realtime-world-model-class-by-what-the-user-steers.md). He first narrows "world model" — "a little bit of a marketing term," read by some through Gaussian splatting — to video that is infinite, interactive, and fast enough to steer, then splits the field three ways by the control surface: the scene through mid-generation prompts (Veo/Sora-shaped but live; his platform example is ByteDance's Helios), a character inside a generated world (Genie 3-shaped, which is also what robotics labs use to manufacture unlimited training data), and live avatars, which by his own account "hasn't actually been cracked." Two adjacent shapes fill the gaps: a multi-shot film model where prompts supplied in advance hold a consistent story, and a video-to-video editing model used for VFX on footage generated elsewhere. For model selection the useful part is that maturity differs sharply per class and that several product names in this space are ASR-damaged in the captions, so verify them against vendor documentation before committing.

LemonSlice's Sidney Primas fills in the third class of that taxonomy — live avatars — with the model-training detail Ahres's platform talk does not have, and it turns two general model-design questions concrete. The first is a build-versus-narrow decision: rather than a purpose-built talking-head model, LemonSlice [points a general world model at a narrow domain](../concepts/point-a-general-world-model-at-a-narrow-domain.md), accepting that it is "harder to get the initial model working… harder to train… harder to deploy" because the domain's long tail — full body movement, hands, object interaction, scene physics, micro-expressions — then arrives "more for free" rather than as enumerated features. The decision rule generalizes past media: a general model amortizes when the requirement set is open-ended, and loses to a specialist when it is closed. The second is the training-time change that converts a video model into a streaming one. Batch video models are bidirectional; an interactive one cannot see the future because the user has not spoken it yet, so LemonSlice [trains with a causal attention mask and budgets for the error accumulation it creates](../concepts/make-video-models-causal-and-budget-for-error-accumulation.md) — matching training conditions to inference conditions rather than masking a bidirectional model at serving time, and paying for it with error that compounds block over block across sessions measured in hours. Two smaller model-level findings travel well: expressiveness in this architecture is carried by the audio embedding, so [an audiobook-trained audio encoder caps how emotional the generated face can be](../concepts/audiobook-trained-audio-encoders-flatten-generated-emotion.md) no matter how good the video model is; and Primas expects the eventual shape to be a [split between an end-to-end EQ layer and a separate IQ model](../concepts/split-an-embodied-agent-into-an-eq-layer-and-an-iq-model.md), where the interaction model is explicitly not the intelligent one — a different decomposition from both the monolithic multimodal model and the tool-calling agent stack.

Amazon AGI Lab's Gaurav Mishra puts a boundary on this topic's most-repeated post-training story — RL with verifiable rewards produced strong coding models, so point it at everything else. His restatement of the recipe matches the wiki's: RL beats SFT when tasks are cheap to generate but demonstrations are not, when many paths reach a verifiable outcome and imitation would "narrow down the model to following a few patterns only," and when the domain is reasoning-heavy enough that only the outcome should be judged; the task needs a difficulty window, the environment needs a safe sandbox, and the verifier ladder runs from string equality up to rubric-graded agent judges. "Coding fits this paradigm perfectly." The boundary is that computer use does not, in two separable ways. First the reward: once actions touch real accounts, a verified outcome is no longer sufficient, because an agent that files the expense *and* mails a resignation letter passes the check — hence [scoring the path with a process reward model](../concepts/penalize-dangerous-steps-with-a-process-reward-model.md) and [training calibrated confidence](../concepts/teach-calibrated-confidence-so-an-agent-knows-when-to-hand-off.md) rather than maximizing autonomy. Second the capability: "one of our biggest bets is that coding abilities are not sufficient to do well on computer use," so the model itself needs [screen-perception primitives](../concepts/train-screen-perception-primitives-beyond-coding-ability.md) — grounding, semantic understanding, change detection over a growing screenshot history, and reconciliation of observation sources that are each incomplete (the DOM misses image-baked text, the screenshot misses what needs scrolling). Both fixes are model-side by design: the lab's position is that the guardrail layer around the model is temporary and [thins as the model absorbs its jobs](../concepts/keep-the-harness-thick-early-and-thin-it-as-the-model-improves.md), which is the training-lab counterpart to the runtime-first claims in [Agents](agents.md).

Dhruv Batra (Yutori) argues the same model-side position as a scaling claim, and states it in the field's own idiom: [per-site scaffolding is the bitter lesson for web agents](../concepts/per-site-scaffolding-does-not-generalize-to-the-long-tail.md) — "the more you end up writing scaffolds around existing websites, it doesn't actually generalize to the long tail of the web. The thing that generalizes is the thing that it was designed for, which is the most general solution: just pixels in." The premise under it is a fact about the artifact rather than about models: because a browser is a rendering engine and much of what a page shows is computed rather than stored, [the document does not contain the answer](../concepts/rendered-state-is-not-in-the-html.md), so "machines will need vision." Two qualifications keep this from being a purity argument. Vision is a floor, not a ceiling — "just because for the long tail you need to have a capability does not mean that is the only way you should do it" — so the next model version writes JavaScript in the page when that is faster and checks the result on screen. And the model that results is deliberately small: at accuracy "within statistical noise" of Opus 4.7 and GPT-5.5 on browser-use benchmarks, its case rests on [latency per step and cost per task](../concepts/compete-on-latency-and-cost-per-task-when-computer-use-accuracy-ties.md) against "trillion-parameter-plus models," which is this topic's right-size-the-model argument arriving in the computer-use setting.

On continual learning, Shlok Khemani's contribution is to point out that the consumer version already shipped and nobody called it that. A running user profile that shapes every conversation, absorbs what those conversations reveal, and gets rewritten on a schedule is [continual learning outside the weights](../concepts/profile-synthesis-is-continual-learning-outside-the-weights.md) — a closed loop that improves a model's behavior toward one person without touching a parameter. His reason for expecting the weights version to lag is not capability but arithmetic: enterprise training amortizes across employees and customers, while per-user personalization has a denominator of one, which leaves "who pays for this" as the open question rather than "can it be done." That sits directly beside this topic's weights-versus-context material: the text loop is available now and its cost is a design choice you control, whereas the parameter loop needs an economic argument no architecture supplies.

LangChain's Vivek Trivedy adds the operational version of this topic's model-selection material, and the sequencing is the contribution. Open models "have basically hit an inflection point in intelligence" such that his team does not reach for a frontier model per use case, asking instead "what is the minimum level of intelligence that I need to do any given task." The frontier model still gets used, but only to establish a waterline: "we start with Opus, we start with 5.5 because we just want to know if the task is even possible," and then "we look back at those traces" to see whether an open model can match it. What happens in between is the reusable move — [read the frontier model's traces to harness-engineer its cheap replacement](../concepts/read-frontier-traces-to-harness-engineer-a-cheap-replacement.md), because seeing how Opus reasons tells you what guidance the weaker model is missing, which is a different operation from freezing the big model's outputs as a golden bar ([prototype big, deploy small](../concepts/right-size-models-with-prototype-big-deploy-small.md)) or putting its trajectory into weights ([distillation](../concepts/distill-reasoning-traces-into-small-models.md)). The reported result is a Harvey legal-benchmark engagement where open-model trace judging matched Opus at one to two orders of magnitude lower cost — a single vendor-reported number with no published methodology, whose mechanism stands without it.

Past that ceiling, the talk gives two rungs and an ordering rule. Fine-tuning targets a narrow vertical rather than general capability, since customers "don't really care about the entire variance of tasks," and can take a base model "to reach and then also go beyond frontier performance" on that slice — but [when to climb that rung is decided by feedback speed](../concepts/sequence-harness-engineering-and-finetuning-by-feedback-speed.md), since harness engineering answers in about two minutes and fine-tuning does not, and the sequence is a sandwich rather than a graduation. It is worth noting that the recommendation to stop at the harness comes from a company selling fine-tuning as a service. Alongside it sits a second economic switch this topic shares with Inference: [moving from token costs to hardware costs](../concepts/decide-open-model-ownership-by-capability-hardware-latency-and-cost-thresholds.md) for very high inference workloads, where the point is not just price but accounting unit — a cluster you can saturate and then spin down, rather than a per-million-token meter.

Yu Su pushes the same descend-after-proving instinct into a claim about where scaling should go next. His framing is that raw intelligence and accumulated expertise are roughly orthogonal, so a model scaled on capability alone yields "the world's smartest novice" that "doesn't accumulate expertise" ([separate intelligence from expertise](../concepts/separate-intelligence-from-expertise-when-diagnosing-agents.md)). The provocation is [unbounded expertise from bounded intelligence](../concepts/scale-expertise-once-intelligence-is-abundant.md): if a continual-learning algorithm is strong enough, then past some capability threshold "we don't need a stronger intelligence anymore," and the question stops being whether to train larger models — "maybe they're already good enough. What we're missing is just like better continual learning algorithms." Read next to this topic's measured material, prototype-big-deploy-small and trace-mined harness guidance are the specific instances; the threshold claim is the conjecture. Two supporting positions matter for model planning: he argues [parametric and non-parametric learning are both needed](../concepts/reliability-and-plasticity-conflict-in-continually-learning-agents.md) and leaves their combination unspecified, and he places [the next internet-scale data opportunity inside private worlds](../concepts/private-microworlds-are-the-next-training-data-opportunity.md) — specialized agents learning in situ and channeling that learning back to the general model, on the stated premise that public pretraining data is exhausted. Both the exhaustion premise and the channel-back mechanism are asserted rather than shown, and the speaker is COO of a company positioned exactly there.

Jack Morris turns that same question — where should scaling go next — into a structural argument about which axes are still open, and his talk is the wiki's clearest statement of why private-domain depth is hard rather than merely unfinished. The frame is Terence Tao on breadth against depth: AI "knows like every single public mathematical topic" and can bridge literature gaps "in a way that no human even can know," but lacks what a graduate student gets from five years in one area. The reason is that all three scaling axes — more data, longer training, bigger models — run on public material, and so does the layer bought from annotation vendors, which is "still by definition creating publicly available data because it's something that the model could tell to a user" ([Post-Training Data Is Public by Construction](../concepts/post-training-data-is-public-by-construction.md)). Against your own corpus, two axes are gone before you start — you cannot manufacture more of your emails and will not train from scratch on them — so [only the compute axis is available](../concepts/only-the-compute-axis-is-available-on-your-own-corpus.md). The rest of the talk is a map of what people spend that compute on and where each one stops. Naive continued training reaches a loss of ~0.0001 and collapses on generation, which makes [a perfect training loss on your corpus](../concepts/a-perfect-training-loss-on-your-corpus-is-not-knowledge.md) the wrong success signal — it looks best exactly when the behavior is worst. [KV compaction](../concepts/kv-compaction-reaches-only-what-already-fits-in-context.md) "only applies to things that are in context" and skips gradients entirely. On-policy distillation works but needs a teacher that does not exist yet, so the real design decision is that you [distill behaving as if the corpus were in context](../concepts/distill-behaving-as-if-the-corpus-were-in-context.md) rather than distilling documents. And [continued pre-training on a private corpus owes a post-training debt](../concepts/continued-pretraining-on-a-private-corpus-owes-a-post-training-debt.md) that most teams cannot pay, because they hold an instruct checkpoint rather than a base model.

The contribution that outlives the individual techniques is the ceiling they share. "Whatever you do, you have to define the data set, and then you train on the data set, and eventually things saturate… unless your model is under parameterized, eventually it will learn all the data" — [a synthetic data wall](../concepts/the-synthetic-data-wall-caps-every-define-then-train-loop.md) with none of pre-training's scaling behavior, after which "you have to do it again" and the unsolved question is what that second stage is. This bounds rather than overturns the wiki's existing advice to expand a small corpus into diverse synthetic data: that repair fixes generalization and does not create an unbounded axis, so a first adaptation pass should be budgeted as a project with a stopping point rather than as a curve. Two escapes are named. The algorithmic one is [the AlphaGo property](../concepts/seek-the-alphago-property-so-added-compute-keeps-buying-depth.md) — getting better must make the training questions harder — which Morris offers as a target after reporting that Engram's own early curves plateaued, and which the talk does not show anyone achieving. The cheaper one is to stop believing the premise: [treat the corpus boundary as negotiable](../concepts/treat-the-corpus-boundary-as-negotiable-not-fixed.md), because a person studying a textbook finds other textbooks, searches, and asks people who know. Read the whole talk with its provenance attached — it is a framing talk by a researcher at a startup selling this problem's solution, it reports no results for any method including his own, and its only Engram datapoint is a negative one.

Sara Hooker, speaking at the same event, makes the complementary claim about the axis Morris's argument takes away from you: it is running out for everyone. "Pre-training size in particular is not your most lucrative axis of scale" because "our architecture is saturated," and the predictive form is that "no frontier AI lab is going to [supersize] their model again for pre-training" — [pre-training size is no longer the most lucrative scaling axis](../concepts/pretraining-size-is-no-longer-the-most-lucrative-scaling-axis.md). Two pieces of evidence support it and they are unequal: the observation that recent size increases "haven't provided the same stepwise change… as their predecessors," and the Open LLM leaderboard's daily best-under-13B submission beating larger models, a ratio she says "totally flips" — which is a self-selected sample of what people chose to submit rather than a controlled size comparison. Her explicit non-claims matter as much as the claim: "size does matter… I'm not advocating everyone use a 0.8B," distillation from large teachers is "helpful," and extra pre-training compute is argued to still pay for the long tail of the distribution. The claim is that the *playing field at the top* is more equal, not that scale is irrelevant, and the whole thing is conditional on the architecture holding — "if someone comes out with a new architecture, that's totally different."

Where the lever moves instead is the useful part for a model roadmap. Inside pre-training: "data quality in general means you use capacity a lot more," so "instead of the size people are just moving post-training further back." Outside it: "where the most returns for performance are now are on a broader action space," which she treats as good news for access because those are "new places where the barriers to entry are much more nimble, and where recipe and algorithm and research matters again." Her company's answer to who writes the recipes is an automated training search, and its two disclosed engineering facts are more durable than its headline. First, [co-optimize data with the model or the search does not pay](../concepts/co-optimize-data-with-the-model-or-the-search-does-not-pay.md): most auto-research projects let the agent decide whether to generate data, and "we did not get the returns… until you control for data quality." Second, [automated training search beats staff by not carrying architecture priors](../concepts/automated-training-search-beats-staff-by-not-carrying-architecture-priors.md) — staff "ha[ve] experience with certain model types" while the search ranges over sizes and dense-versus-MoE, and it moves hyperparameters in combinations "humans are much more wary about changing all at once." What the search absorbs is tacit: [frontier-training know-how is apprenticeship, not literature](../concepts/frontier-training-know-how-is-apprenticeship-not-literature.md), held by "probably less than 5,000 in the world at scale." She extends the same factorization argument to harnesses — [automating harness design requires co-optimizing the model](../concepts/automating-harness-design-requires-co-optimizing-the-model.md) — which bounds how far a harness *searcher* can go against a frozen model. Read all of it as a founder's account of an unpublished system: "outperforms research staff" names no benchmark, and the win rates on the slide are [a stopping rule, not a ceiling](../concepts/a-budget-stopping-rule-can-masquerade-as-a-capability-ceiling.md), a fact she volunteers herself.

Sam Denton's talk from the same event is the operational counterpart to those two arguments: if the interesting compute has moved to post-training and adaptation, what does adapting a customer's model actually look like? His organizing device is a grid whose value is that it splits a word the field uses as one thing. [Place a continual-learning setup on two axes](../concepts/place-a-continual-learning-setup-on-the-trace-and-hint-axes.md) — how on-policy the *traces* are (a one-time production dump, a daily batch, or "this sort of unified engine of putting inference and training together," which he calls the holy grail) and where the *hint* comes from (a static prior, or one constructed against the rollout just produced). The two axes have different prerequisites, which is the planning payoff: the trace axis needs infrastructure, the hint axis needs only that you look at each rollout before writing the hint. Underneath both sits a constraint the wiki's other post-training pages mostly assume away — [distill without a golden answer by giving the teacher privileged information](../concepts/distill-without-a-golden-answer-using-privileged-information.md). The teacher here is not a bigger model; it is the same policy with a hint in its context, which is the third way this wiki has now seen of manufacturing a teacher when none exists (the others being reasoning traces from a stronger model, and stuffing a corpus into the window).

Two results carry it, and both are more interesting as mechanisms than as numbers. On SWE-bench, a Qwen thinking model taking up to 80 turns to submit was pushed to wrap up by turn 40: task-complete tool-call rate from about 22% to 60%, base test pass rate flat. The mechanism is that [a teacher can install a tool call by moving the reasoning path, never the call tokens](../concepts/move-the-reasoning-path-not-the-target-tokens.md) — the rollout was conditioned on an old trace that never called the tool, so there were no target tokens to imitate and the teacher shifted the deliberation instead. A behavior absent from the entire corpus was installed from its precursor. The second is a customer whose harness required an unusual hyperlink format: [when rewards and SFT both degrade the base model, hint against the rollout](../concepts/hint-against-the-rollout-when-rewards-and-sft-degrade-the-base-model.md), since both standard approaches cost general coding ability while a rollout-specific hint went from about 15% to 80% — and the same instruction applied uniformly to every rollout "climb[ed] the behavior a little bit, but far less," which isolates specificity rather than content as the active ingredient. Three implementation practices follow, and they are all the same move at different scales: [buy on-policyness with a single rollout step](../concepts/buy-on-policyness-with-a-single-rollout-step.md) on a stale trace, [let a judge place the hint and distill only nearby steps](../concepts/let-a-judge-place-the-hint-and-distill-only-nearby-steps.md) because the KL signal decays with distance, and [mask irrelevant teacher tokens](../concepts/mask-irrelevant-teacher-tokens-before-learning-from-them.md) because "the teacher model has preferences of certain connector words that are not really relevant to actually what we're trying to teach the student." Read together they say the default distillation objective is far too broad for a targeted behavior change. The provenance is heavy in the usual vendor way — every number is from unpublished internal runs with no seeds, sample counts, or variance, the two failed baselines are reported without magnitude, and the strongest-sounding claim (one on-policy step beats fully offline) is delivered against a chart with no numbers at all.

Parth Asawa's talk, from the same event, asks the question those two skip: whether the *checkpoint* is the right substrate for any of it. His framing is that today's continual-learning work inherits a shape nobody chose on purpose — [continual learning bolted onto a frozen checkpoint is a sunk-cost choice](../concepts/continual-learning-bolted-onto-a-frozen-checkpoint-is-a-sunk-cost-choice.md). Pre-training, mid-training, and post-training all terminate in weights that are then frozen and shipped, and every memory layer, notepad, and adapter is built on top of models that "were never designed to be continual learners in the first place." The alternative he sketches is a different phase boundary rather than a different algorithm: "you have one phase of training which is training for continual learning and then everything after that is deployment." He offers no method and no evidence that it is achievable, and the honest reading is that this is a research direction stated as one, not a result. It sits in productive tension with his own leaderboard, where the least invasive approach — appending experience to the context of an off-the-shelf model — beat the elaborate ones.

The modelling constraint that survives regardless of whether that direction pans out is a criterion on tasks, not on architectures. A benchmark that is supposed to measure learning has to have [headroom, shared structure, and a signal](../concepts/a-learning-benchmark-needs-headroom-shared-structure-and-a-signal.md), and the headroom requirement is stricter than the usual "models don't saturate it": the task must require adaptation *online*, at deployment time, rather than being fixable by more offline training. That is a sharp test to apply to any claim that a capability needs continual learning at all — if a larger pre-training run or another post-training pass would close the gap, the observed gap is not evidence about learning. It also implies the negative result about weight-based state that this wiki has not yet resolved: the [gain metric](../concepts/measure-learning-as-gain-over-a-memory-wiped-rerun.md) is defined by rerunning a system with its state wiped, which is well-defined for context and notes and much less obvious for a system whose state is a set of updated weights.

Ronak Malde's talk at the same event is the second independent account of Denton's method, and the first that says what breaks. Its most portable piece is a comparison device rather than an algorithm: [score a post-training algorithm on four properties](../concepts/score-post-training-algorithms-on-four-properties.md) — is the task distribution online, is sampling on-policy, is parallelism one, is the reward per token. SFT holds parallelism and per-token signal but trains on a curated dataset; RLHF gains the online distribution and drops back to sequence-level reward; GRPO is "a Fouian [Faustian] bargain" that maxes on-policy sampling while exploding parallelism into environments that must be "one-to-one copies of the real world" and collapsing feedback into one scalar — "imagine you were trying to write an essay and your teacher just gave you a score of 87 out of 100." Two rows of that scorecard settle arguments the wiki has been having across pages: the parallelism row is where RL's environment bill comes from, and the per-token row is the claimed reason self-distillation keeps climbing. The mechanism behind the second is worth stating precisely, because it is the only part of the ceiling argument that is mechanical rather than promotional — [optimize the whole vocabulary, not the token you sampled](../concepts/optimize-the-whole-vocabulary-not-the-sampled-token.md). Matching the teacher's full distribution at every position can move probability onto a token the student never produced, so the update is "not just taking now a distribution like RL and slightly sharpening it, but… actually shifting entire distributions." Its testable corollary needs none of the vendor's numbers: reward-driven runs grow their reasoning budget, and this one is claimed to shrink it.

The failure half of that talk is what the wiki did not previously have, and it changes how the localization tricks on the Applied Compute pages should be read. Above a threshold — the 120B range with "50 or 100" tool calls rather than one or two, where eval accuracy is "all over the place" and the model stops honoring its instruction-tuned tool format — [long-horizon self-distillation collapses into hedging](../concepts/long-horizon-self-distillation-collapses-into-hedging.md). The student drifts, the teacher course-corrects "every single time it gets a chance," and the favored-token cloud fills with *wait*, *but*, and *maybe* until the model parks between two divergent distributions. The proposed fix is to [weight distillation steps by student/teacher divergence](../concepts/weight-distillation-steps-by-student-teacher-divergence.md) — KL as a per-step multiplier on token weight rather than a penalty on the objective, so a step that has already parted contributes little and a trajectory that recovers is still learned from. That is the same quantity Applied Compute uses to justify a short distillation window, arrived at independently and used continuously instead of as a cutoff, which suggests both teams' "efficiency" measures are really drift defenses. The second failure is [hint leakage, the reward hacking of self-distillation](../concepts/hint-leakage-is-the-reward-hacking-of-self-distillation.md): a hint carrying the answer produces "Oh, actually, I know what the solution is. It's 000. So, let me go back and put that into my reasoning trace," a behavior that cannot occur in deployment because no hint exists there. Two mitigations, one cheap and one structural — an LLM that rewrites raw environment records into "something reasonable that they should have known," and [blending a partial-hint teacher](../concepts/blend-a-partial-hint-teacher-to-bound-the-distribution-shift.md) with the full-hint one, whose gap doubles as an unsupervised measure of how far out of distribution a hint pushes. Read against the wiki's strongest hint result, where rollout specificity took formatting from ~15% to ~80%, these give the missing constraint: specific enough to name the error, restrained enough to withhold the conclusion.

None of that is reported with a number. The whole talk contains no measured value — the LiveCodeBench claim that "GRPO saturates around sonnet level" while self-distillation reaches "brand new territory," and the claim that the scaled system "has even surpassed RL," are both stated bare, which is a conspicuous omission from a talk whose own diagnosis of that regime is "run-to-run variance is extremely high." The two arguments that survive without numbers are the scorecard and the failure modes; the results do not. The most useful sentence in it is the one that undercuts its own vision slide: asked how continual the learning is, Malde answers that [today's continual learning is batch updates and a model re-upload](../concepts/todays-continual-learning-is-batch-updates-and-a-model-reupload.md) — "pseudo continual learning" — and that merging "10,000 rollouts going out in a product" into one update is unsolved, "partly an infrastructure question… partly still an algorithmic question." Two vendors selling weight-level improvement now independently place the deployed state at the batch rung, which means a continual-learning program today inherits release discipline, not memory-system semantics.

A separate line of post-training work is about what the optimizer does to the *served* model rather than to the loss, and it produces the most transferable numerical result in this topic. Modal's cross-datacenter RL talk asks why consecutive rollout weight versions are nearly identical and answers with a comparison of two magnitudes. The floor: a rollout engine reads a quantized view whose spacing at magnitude θ is roughly θ/128 in BF16, and an update must cross the nearest rounding boundary at about half a ULP — "roughly theta over 256 for weight around one," an absolute 0.0039. The push: ignoring weight decay, an Adam step is the learning rate times a normalized direction, bounded at a constant times the learning rate, and "a typical Adam step here is around 3 millionths." The step is therefore "more than a thousand [times] smaller than the boundary," so the master weight moves and the value the engine would serve does not — [Adam absorption](../concepts/adam-absorption-hides-most-weight-updates-from-the-served-model.md), with the reported consequence that ~99% of served weights are bit-identical per step. The plot is worth carrying: the floor scales with θ and the push does not, so small weights keep moving while large ones freeze.

Two corollaries matter beyond the systems use. First, and stated on stage as a correction, [a sparse served-weight delta is not gradient sparsity](../concepts/a-sparse-served-weight-delta-is-not-gradient-sparsity.md): "the gradients are dense. About 99% of the parameter gets non-zero gradients. The FP32 master update is also dense. It's just small." The sparsity lives in the instrument — a BF16 or FP8 cast — not in the learning signal, which means it licenses no trainer-side skipping and can be destroyed by a change of learning rate, optimizer, or serving dtype rather than by a change of data. LoRA is kept separate for the same reason: "full parameter delta is small by absorption and the LoRA updates are small by construction." Second, the effect runs the counterintuitive way with precision — the floor is roughly θ/2^(mantissa+1), so [lower serving precision shrinks the weight-sync patch](../concepts/lower-serving-precision-shrinks-the-weight-sync-patch.md) and FP8 or FP4 rollout serving changes fewer weights per step than BF16, with group-scaled formats (INT4, MXFP4, NVFP4) asserted to follow the same rationale through different encodings. The scope limit is the one Jiang raises himself: all of it holds for Adam, and "a lot of model providers such as Moonshot and also DeepSeek… are adopting Muon in their post training." The supporting evidence is second-hand — the Adam bound and the ~99% figure are attributed to a paper the talk never names — and the single first-party measurement is one internal run serving GLM 4.7 Air in FP8, which changed 0.15% of weights on its first high-learning-rate step and settled near 0.05%.

A selection question this topic has treated as a cost decision turns out to be a quality decision too. Sonar scores each new model on roughly 4,000 coding tasks against correctness, complexity, solve rate, maintainability, reliability, and security, and the two tiers of one vendor family land differently across those axes: Claude Sonnet 4.6 is "quite good from a correctness standpoint, from… solving tasks," while "if you're requiring higher levels of maintainability or higher levels of security, if you're trying to get a lower complexity out of your code, you might benefit from switching to Opus" ([Route Between Model Tiers by Quality Dimension, Not Only Cost](../concepts/route-between-model-tiers-by-quality-dimension-not-only-cost.md)). The framing is what makes it useful: the comparison is stated against the toggle teams already operate to control token burn, so a downshift made for cost is silently trading some quality dimensions and possibly improving others. This is the intra-family case of the wiki's [leaderboard caution](../concepts/do-not-trust-a-single-leaderboard-for-model-selection.md) — tiers are marketed and priced as one capability ladder, which is exactly why per-dimension divergence within a family gets assumed away — and it amends [cheapest-sufficient routing](../concepts/route-each-request-to-the-cheapest-sufficient-model-by-difficulty.md) with the point that "sufficient" is per-dimension, so difficulty alone under-specifies the route. Caveats: a vendor board scored on the vendor's own product metrics including a proprietary complexity measure, no numbers spoken for either tier, "4,000 or so coding tasks" as the only sample figure, and the earlier Sonar talk describing its dataset as Java assignments, so language generality is unestablished. Rankings of this kind also expire with each release. The talk's own conclusion from its board is the durable part: "None of these models are ever going to be perfect. You're always going to have some kind of need for verification in the loop."

Vendor boards and public leaderboards both answer "which model," and neither answers "did this generation change what I can hand off." Denys Linkov (WiseDocs) describes the smallest instrument that does: keep one hard task you already solved yourself, re-run it on each release, and read the result in units of your own effort. The recurring case is a single refactor from his pipeline consolidation — o3 in Cursor took "3 hours of back and forth… but it made 10 major mistakes," Sonnet 4.6 needed "one additional iteration," and Opus 4.8 "was basically able to one-shot this problem," so the same work now takes "around 1/5 of the time" ([Re-Run One Remembered Hard Task on Each New Model](../concepts/re-run-one-remembered-hard-task-on-each-new-model.md)). The cost side gets stated rather than hidden: "even though the model execution was a little bit more expensive, it was a lot less manual" — the newer generation buys human hours with tokens, which is the exchange rate a per-token comparison cannot show. A second reading comes from the trajectory shape: "before with O3, there weren't substantial tool calls on certain categories. And then as we moved into Sonnet 4.6 and Opus, we see now that in modern harnesses, we get sub-agents, we get some of those plan calls, we get different shell commands, and we get different verifications." That is also the method's central weakness. Linkov says plainly that "models are getting significantly better along with harnesses," the o3 run was in Cursor and the later harness is never named, and there is one attempt per model with no repetition — so the ratio is a joint measurement of model and harness, not a model result. Treat it as a personal operating-model update rather than a capability figure to quote, and note that Linkov's other reading recommendation applies to the vendor curves in this topic as well: quote time horizons at 80/90/99% rather than 50%, because that is the threshold at which handing a task off unattended is rational ([Read the Task-Length Curve at the Success Rate You Would Actually Delegate At](../concepts/read-the-task-length-curve-at-the-success-rate-you-would-delegate-at.md)).

Saoud Rizwan (Cline) argues the open-weights question from the releasing lab's side rather than the adopter's, which is the direction this topic has less of. His frame is Facebook's Open Compute Project: publish the layer you do not intend to win on, the industry standardizes on it, and the publisher gets the cheaper supply chain plus the interface everyone builds against ([Commoditize the Layer You Do Not Win On](../concepts/commoditize-the-layer-you-do-not-win-on.md)). Applied to models, the claim has a specific shape worth separating from the advocacy: weights and research are different releases. Publishing weights lets others "extract the traces and train your copycat models on them more easily, but not in a way that can leapfrog," while the research is what he says holds the lead — "I don't mean we need to open source our research." If that bound holds, distillation from released weights is a way to close a gap and never a way to open one, which is also a fair description of what this topic's trace-mining and harness-engineering material actually achieves. On the adoption side he reports Coinbase halving spend by pointing its gateway's default at open-weight models, and an N-of-1 head-to-head on a real bug in Cline's repository where GLM "verified that the build compiled before completing" and Opus "broke the production build" — his reading being that GLM "was trained to spend more tokens verifying its output," which is a training-objective difference no capability ranking reports.

The provenance limits are heavy enough to state before quoting any of it. This is a founder keynote three days after launching an open-weights subscription; the head-to-head is one bug with one run per model and self-described as anecdotal; the cost projections ($3 trillion of capex, over 100 gigawatts by 2030, inference on a trillion-parameter model 90% cheaper) are unattributed; and the no-leapfrog bound is asserted rather than measured, and is contested.

A held-out test of where frontier competence comes from arrives from an unlikely direction: multi-GPU kernel generation, which uses the same language and tooling as single-GPU kernel work but has far less public code behind it. The framing question was explicit — "do they generalize well to these problems, or are we benchmaxed on benchmarks of the past which are more single GPU centric?" — and the answer is that [model successes concentrate in the patterns the internet already contains](../concepts/models-solve-the-parallelism-patterns-the-internet-already-contains.md): collective primitives, tensor-parallel GEMMs, and Ulysses-style context parallelism, while the mechanisms with thinner coverage, such as register-level transfer instructions and tensor memory acceleration, go unused. The failures are not syntax; with retries models "can often compile the kernels," and what remains is the design reasoning. The result that constrains interpretation most is that handing the models a hand-distilled set of the governing principles did not help — "models do not currently understand how to reason through these trade-offs even when we provide them in context" — which rules out the missing-information explanation and leaves training or method. GPT 5.5 was the best model benchmarked and DeepSeek V4 Pro the comparison point; both drop off quickly as the required speedup threshold rises.

A newer model is not automatically better informed about your product. Jarmak reran a generative-engine-optimization prompt set on a newer Claude release specifically expecting improvement, and the assistant recommended a retired Sourcegraph product *more* than the older model had. The mechanism proposed is compounding rather than lag: superseded models have been publishing text onto the internet, and later models read it, so an error about you can be better attested in a newer corpus than in an older one. The practical consequence is that model upgrades cannot be treated as a remediation plan for stale claims — the remedy is fresh, authoritative, retrievable content, plus a standing count of mentions per model version, measured through the agents' web-search path rather than through anything that would have to land in a pretraining run.

An environment can be its own training factory when execution supplies the label. DSGym generates trajectories by running data-science agents against curated tasks and keeps only those verified by executing the agents' code, then fine-tunes small open-source models on the survivors — reported as best-in-class open-source performance on these tasks at sizes that run on a laptop. Execution verification is what supplies the target term a raw trace corpus lacks: the trajectory is kept because the code produced the right result, not because a judge liked the reasoning. The specifics are absent — no base model, parameter count, score, or comparison set — so treat the shape as transferable and the result as unverified. The prerequisite the same work makes explicit is that a defective task set is worse here than in evaluation alone, since an environment reused as a data generator writes its shortcuts into weights: the team found 20 to 50 percent of tasks in three popular data-science benchmarks solvable without the data, and rebuilt the set before using it for either purpose.

## Open Questions

- What do execution-verified trajectories actually buy a small model? Zou reports fine-tuned open-source models that are "best in class" on DSGym tasks and laptop-runnable, naming no base model, size, score, or comparison, so the wiki has the recipe without any evidence of its magnitude. ([Zou](../sources/20260825_mMNkdYnIVC4.md), 14:26-15:06)

- Is distributional competence on specialist engineering tasks a training-data property or a reasoning ceiling? Supplying the governing tradeoffs in context did not help on multi-GPU kernels, which rules out simple ignorance but not the possibility that the principles need to be trained in rather than read. No source in this wiki reports the experiment that would separate the two — post-training a model on an expert-derived primitive set and re-running the same benchmark. ([Arora](../sources/20260827_pOvWgX7IJsc.md), 21:42-22:05, 29:11-29:17)

- Can a model distilled from released weights actually surpass its source? The argument for publishing weights leans on a bound — copycats get close, never ahead — and nothing in this wiki tests it. Every distillation result recorded here targets matching a teacher at lower cost, which is consistent with the bound but does not establish it, and the one path that would falsify it (distilled base plus independent post-training or RL on a domain the teacher was not optimized for) is not examined anywhere. The claim is load-bearing for a release decision and is currently held on the word of parties who benefit from it in both directions.
- Do models differ systematically in how much of their output goes to self-verification, and is that reported anywhere? A single head-to-head here turned on one model compiling the build before declaring completion and the other not, attributed to training rather than prompting. If that is a real and stable difference, it is a selection criterion no benchmark score, model card, or price-per-token comparison exposes — and if it is run-to-run variance on one bug, it is exactly the kind of anecdote that gets generalized. One task, one run per model.
- How much of a reported generation-over-generation gain is the model, and how much is the harness? Every practitioner comparison in this wiki runs the new model through a newer harness — sub-agents, plan calls, more shell commands and verifications appearing alongside the model change — and the one source that names the confound directly ("models are getting significantly better along with harnesses") does not control for it. No source reports a re-run with the harness version pinned, so figures like "1/5 of the time" bound the pair, not the weights.

- Do a model family's tiers diverge by quality dimension on anyone else's benchmark? The only evidence in this wiki is one vendor's board, scored on that vendor's own product metrics, spoken over a slide with no numbers. Whether Sonnet-over-Opus on correctness and the reverse on maintainability reproduces on an independent suite — or is an artifact of how those metrics are defined — is unestablished, and it is the kind of claim a routing decision would rest on.
- Does the served-weight sparsity survive Muon? Every step of the absorption argument depends on Adam's normalized, bounded update, Jiang names Moonshot and DeepSeek as moving to Muon in post-training, and no source in this wiki characterizes Muon's step-size distribution against a serving format's rounding boundary. Systems built on the Adam result are betting on an optimizer choice.
- At what learning rate does absorption stop paying? The quoted margin is ~1000×, and the one measured run changed three times as many weights on its first high-learning-rate step as in its stable regime — so the effect is weakest exactly during warmup or aggressive schedules. Nobody reports a curve of changed-weight fraction against learning rate, which is the measurement that would turn a rule of thumb into a design constraint.
- Does the paradigm extend past RL to pre-training, mid-training, and SFT? Jiang closes by asking this and offers nothing beyond the question. Learning rates and step counts differ substantially across those phases, and the argument's whole content is a ratio between step size and rounding boundary.
- How do you merge thousands of concurrent production rollouts into one weight update? Malde names this as the blocker between batch redeploys and anything deserving the name continual learning, calls it "partly an infrastructure question… partly still an algorithmic question," and offers no candidate mechanism. Every single-trajectory account of hint-based distillation — including both of the wiki's — describes one rollout, one hint, one update, and is silent on reconciliation across conflicting lessons.
- What does on-policy self-distillation actually cost relative to GRPO? "Parallelism of one" describes rollouts, not FLOPs, and matching a teacher's full distribution requires teacher forward passes with logits retained at every position. Neither talk on this method offers a total-cost comparison, so the infrastructure saving is asserted on one axis and unpriced on another.
- At what point does the hedging collapse set in, and is it driven by trajectory length or model size? The only report moves both together (120B *and* 50-100 tool calls), gives no frequency, and evidences the failure with a word cloud. Nobody has published the step at which a run turns, or an ablation of the divergence-weighting fix against unweighted self-distillation.
- How would a production pipeline detect hint leakage? The failure is described from a single rollout excerpt, the mitigation is "works decently well," and no detector, rate, or evaluation of the LLM hint filter is given. Since a leaked hint improves the training-time metric being watched, the absence of a detector is the gap that matters.
- What would "training for continual learning" as a distinct phase actually optimize? Asawa proposes replacing the freeze-then-adapt pipeline with one phase of training for continual learning followed only by deployment, but names no objective, no data, and no evidence that a checkpoint trained that way exists or would be better. It is a stated research direction, and the wiki has no counterexample and no supporting result for it.
- How do you compute gain for a system whose state lives in weights? The memory-wiped rerun is well-defined for context, notes, and retrieval stores; for a system that fine-tunes as it goes, the stateless control is the original checkpoint, which makes the comparison depend on what the checkpoint's training already contained. The talk's own examples are all context or memory systems, so this case is untested.
- What does the second stage of private-corpus training actually look like? Morris names it as the missing component — "how do you do it again?" — says any of the existing techniques could fill it, and gives no criterion for choosing or sequencing them.
- Where would the difficulty signal and the correctness signal come from in an AlphaGo-style loop over unstructured documents? Self-play has an opponent and a game result; a corpus of emails has neither, and the talk asserts that "more sophisticated things" exist without describing them.
- How large is the bounded return of a first adaptation pass, in advance? The synthetic-data-wall argument says the pass terminates but offers no way to estimate where, which is exactly the number a team needs before committing budget.

- Is there actually a capability threshold past which a better learning loop beats a better model, and where is it? Su states the escape case as a "what if," names no threshold, proposes no algorithm, and gives the picture a caveat of its own — the slopes assume "a given time horizon and the experience horizon," which means a low-volume deployment may never accumulate enough experience for the trade to exist.
- How would learning acquired inside one customer's environment be channeled back to a general model without conflicting with that customer's interest in owning the resulting capability? Su argues both positions in the same talk — private worlds as the next training-data opportunity, and companies staying "in charge of their means of production" — and reconciles neither.
- Where exactly is the harness-engineering ceiling, and can it be detected before you hit it? Trivedy describes it as a felt threshold ("if I keep tweaking this prompt, I'm not going to get too much more out of it") and no source gives a measurable stopping criterion, which is what a team needs before committing to a training run.
- What would make per-user continual learning pay for itself? Khemani names the blocker as amortization — enterprise training spreads its cost across employees and customers, individual personalization does not — and leaves three questions open: whether each person eventually gets a self-learning model, what data is needed to start the process and how it is generated, and who pays.

- A process reward model needs a danger judgment at every step, which is a far larger grading surface than a terminal verifier. No source in this wiki says what produces that per-step signal at scale — a learned classifier, a rubric-graded judge, or human labeling — or what it costs relative to the outcome verifier it supplements.
- Do the three real-time world-model classes converge into one model family, as Ahres expects when avatars are combined with steerable scenes and controllable characters, or do their control surfaces keep them separate?
- Where is the boundary between a general model narrowed to a domain and a domain-specific model? LemonSlice reports the emergent-capability payoff qualitatively and never names the specialist approaches it beat, so the trade has no measured form in this wiki.
- Which parts of the LLM post-training ladder actually transfer to diffusion because the stage is doing the same job, and which are being copied because the tooling exists?
- What is the real entry cost of training a media model from scratch? The two Krea 2 talks together give an ingredients list — thousands of InfiniBand GPUs, a filesystem sustaining ~1 TB writes in under 30 seconds, custom fabric telemetry, 30-40 data filters over billions of images — but no source states GPU-hours, headcount, or wall-clock, so the build/adapt decision stays qualitative.
- What retires a post-trained specialist model? The right-to-win argument is a bet on outpacing the frontier's rate of change, but no source describes the measurement or the trigger that says a frontier release has closed the gap and the fine-tuning line item should be dropped.
- How should tokenizer decisions change when a model must support mixed modalities or mixed domains rather than a single constrained corpus?
- Which lightweight generated-sample checks complement train/validation loss for tiny local model runs?
- When is a modular set of fine-tuned tiny models preferable to one larger model with prompting or skills?
- Which small-model failures should be fixed with architecture, post-training data, runtime tools, or product task narrowing?
- Which interactive tasks have reward signals clear enough to justify building an RL environment rather than collecting more SFT examples?
- Which private workflow benchmarks have enough measurable ROI and repeated use to justify enterprise RL instead of prompting, RAG, or ordinary fine-tuning?
- How much policy staleness can a given language-model RL algorithm tolerate before asynchronous throughput gains stop improving useful learning?
- How should teams evaluate sparse MoE, effective on-device, and dense long-context models against the same agent workflow without hiding deployment cost differences?
- When should a team fine-tune an open model directly, start from a domain variant, or rely on a hosted API model for maximum raw capability?
- What evaluation suite is sufficient before promoting a weight-updated long-tail model over RAG or full-context prompting?
- When does adding reasoning effort improve model judgment, and when does it simply make accommodation of a bad premise longer?
- Which media-generation failures should be fixed through data curation, latent representation design, sampling settings, distillation, or explicit controls?
- How should media model training account for codec artifacts that are invisible to some users but visible to metrics or downstream models?
- Which non-language tasks should be handled by specialized frontier models instead of routed through a general LLM?
- Which quantization formats preserve enough quality while improving local model responsiveness for each hardware class?
- Which coding-eval time windows best separate memorized benchmark behavior from genuine current model capability?
- Which scaffold perturbations best predict whether a coding-agent model will transfer across real harnesses and tool APIs?
- Which model advances are blocked by research ideas versus the engineering systems needed to test and scale them?
- How can VLMs use high-fidelity vision-only features while preserving language alignment and real-time detection performance?
- Which interpretability-derived feature controls are stable enough across prompts, model versions, and deployment environments to use as production levers?
- What evidence would distinguish "the architecture is saturated on size" from "the field's effort moved to small models"? The leaderboard exhibit is consistent with both, and the difference decides whether waiting for a larger base model is a losing plan or merely an unfashionable one.
- If post-training keeps "moving further back" into pre-training, where does the boundary end up, and which of the two budgets should a team without a base checkpoint be planning against?
- Does an automated training search still beat experienced staff once the data is controlled *for both arms*? The reported comparison is a search with co-optimized data against staff whose data handling is undescribed, which leaves the credit split between the search and the data work unresolved.
- How far can a reasoning-path nudge reach? Applied Compute installed a tool call the traces never contained, but the target was an action the policy could already emit; nothing yet distinguishes "the model would not choose it" from "the model cannot produce it," and that boundary decides whether the technique is a behavior lever or a capability one.
- What does the online-hint loop cost per improvement? It runs a placement judge, a masking judge, and a teacher pass per rollout, and no source in this wiki prices that against the offline path it is said to beat.
- Does token-level relevance masking generalize beyond self-distillation to ordinary teacher-student distillation and SFT, where the same connector-word transfer presumably occurs unmeasured?
