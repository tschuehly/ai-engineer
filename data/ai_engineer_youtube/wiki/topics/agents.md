# Agents

## Overview

Personal-agent interfaces become part of the agent architecture. As agents span personal, family, work, and business domains, one universal chat becomes a weak shell; scoped topics, visible agent roles, tool permissions, explicit context attachments, and observable tool progress are needed to keep delegation understandable. Some personal AI systems should remain observers rather than actors: read-only access can reveal cross-source patterns while preserving a human-mediated decision loop and avoiding write-action risk. Local OS-level agents may eventually invert the prompt flow by ingesting notifications, email, todos, files, and installed-app affordances, then prompting the human for missing decisions while routine work runs in the background.

Agent workflows depend on both model capability and the context substrate around the model. On-device agents can keep core inference local while invoking selected tools, APIs, and structured outputs; because small edge models are context-sensitive, tool and skill systems should expose compact descriptions first and load details only when needed. Larger open-weight models add another routing choice: dense long-context models may fit reasoning, function calling, structured JSON, and coding workflows, while sparse MoE variants trade total parameter count for lower active inference cost. Gemma demos add a practical local-agent signal: airplane-mode phones, laptop llama.cpp instances, and offline Android coding show that some agentic work can run locally when the model, runtime, and task are matched. Conversational-agent runtimes add state management to that shape: a model, tools, context, and loop can be exposed through interaction IDs that let clients continue or branch sessions without rebuilding history locally. Voice agents add realtime audio constraints: architecture choice, latency, spoken persona, interruption behavior, multimodal streaming, and audio-specific evaluation matter alongside ordinary model, instruction, tool, and runtime design. Pipecat-style frame pipelines make the runtime itself a composable agent surface, where transport, STT, LLM, TTS, tools, context aggregation, observers, and interruption settings can be swapped or configured as streaming processors. Production support agents need stage boundaries as well: deterministic context collection, LLM/tool triage, review, reply generation, escalation, and final packaging should be inspectable separately so failures can be traced to the right step. Personal agents need the same restraint at a permission level: broad access to email, files, calendars, operating-system automation, and memory should grow from small reversible workflows rather than from an immediate all-access launch. Operational agents can also raise small-team throughput outside engineering by removing setup chores, running dependency work in parallel, and letting non-technical collaborators steer work with natural artifacts such as Figma pages, screenshots, notes, and emails. Canvas-native agents extend that pattern by making the work surface itself part of the prompt: drawings, annotations, selected objects, forms, and generated artifacts can become spatial context that the agent can inspect and edit. Visual workflow builders add another control layer by making triggers, model calls, memory, tools, approval waits, and execution state inspectable and adjustable. Shared visual canvases can also expose multi-agent orchestration by showing each agent's state, action location, delegation role, and progress on the same surface. Enterprise agents also need institutional knowledge that is accurate enough to move real work through delivery systems. Context engines can supply that knowledge by selecting task-specific organizational context, resolving or surfacing conflicts, and using team or expert signals to personalize what the agent sees. Small models can sit in front of the main agent as retrieval, extraction, classification, or reranking tools that reduce context rot. For coding work, simple loops can give agents enough structure to process one ticket at a time while avoiding the coordination failure modes of large multi-agent plans. Productized codegen agents need additional context and safety controls: current docs compensate for stale model knowledge, exemplar projects show successful implementation shapes, staged breadcrumbs reduce inconsistent paths, post-run interrogation exposes setup failures, and narrow tools protect sensitive files. Minimal tool loops can also demonstrate the core contract: detect required model actions, execute only recognized tools, return tool results, and repeat until final text. As agents take on longer implementation runs, human leverage shifts toward planning, review, QA, and change shepherding, so agent interfaces need to preserve focus across multiple streams rather than constantly interrupting the developer. Parent agents can improve parallel coding by spawning isolated subagents, comparing their outputs, and helping humans merge the strongest pieces, but workspace boundaries need hard checks when the system relies on prompts instead of runtime isolation. Spatial orchestration adds another way to reduce the human bottleneck: map agent sessions onto repository structure, show file-level lineage and likely collisions, let agents propose queued missions, and compress many autonomous outputs into review bundles with rationale and visual evidence. Always-on agents add an operational layer: indexing, backups, update checks, memory hygiene, and cleanup keep the agent substrate reliable while scripts handle deterministic cases that do not need LLM judgment. Skills add another packaging layer: they can expose product-specific workflow guidance through progressive disclosure while leaving service integrations to tools such as MCP, and API skills should link out to current docs for fast-changing details rather than freezing every fact into the skill. Skill-like command prompts can also implement advanced product behavior, reducing code maintenance while shifting reliability work into evals, system reminders, and native fallbacks for strong guarantees. As context becomes packageable and runtimes become more hackable, agents also need filters, provenance checks, sandboxing, and permission boundaries because unsafe instructions or executable code may be loaded before ordinary execution controls can constrain behavior. Products used by agents need agent-facing surfaces as well: APIs, CLIs, and MCP interfaces can matter more than dashboards when bots become primary users. Agent experience raises the bar beyond exposing a machine interface: tools should let agents autonomously access, understand, and operate the environment without humans clicking buttons, typing into terminals, reading logs, or debugging setup gaps. Enterprise agent access also depends on identity design: IdP-mediated MCP authentication can make many tool connections manageable, while fine-grained authorization remains a separate policy layer. Production MCP servers add another access-design constraint: broad default tool surfaces can degrade agent behavior, so allowed tools should be selected by context budget, scopes, policy, and task intent rather than exposed wholesale. MCP servers are agent product interfaces: agents pay recurring costs for discovery and iteration, so raw REST catalogs can degrade them even when the underlying human API is well designed. Agent authorization has to cover both delegated user access and agents acting on their own behalf. OAuth authorization-code flows fit user delegation, but client-credentials and verifiable agent identity become important for agent-to-agent and agent-to-MCP communication. Background agents also challenge browser-centric consent: a long-running agent may need asynchronous step-up authorization after the user has left, and high-impact actions may need transaction-specific permission rather than a broad standing scope. Deep research is a useful boundary case for autonomy: the research phase benefits from goal-driven planning, search, inspection, source citation, pivoting, and synthesis, while adjacent writing work may be better as a constrained artifact-consuming workflow.

Workflow search adds a process-specific enterprise context layer for agents. Instead of choosing between fixed workflows and open-ended agents, teams can retrieve similar task-to-workflow examples at runtime so the agent sees current company protocols, internal metrics, and team-specific practices before planning. Successful agent traces can also become candidate workflows, giving the system a path to discover new practice while keeping known work predictable and reviewable.

Customer-facing agents create an ownership role around the agent as a branded company surface. Sierra's "AI architect" framing says the owner needs technical capability sense, brand and persona taste, and business-outcome responsibility; the work is not only choosing an LLM or framework. The first production surface should start from a narrow valuable customer outcome, then grow through review and coaching. At platform level, the hidden burden includes testing, model migration, voice edge cases, no-code coaching tools, and live handoff analysis.

Factory's agent-native SDLC framing adds a platform-level version of this shift. The argument is that agents become transformative when they operate across planning, coding, testing, monitoring, and incident response with centralized engineering context, reliable execution, and parallel infrastructure, not when they are merely sprinkled onto human-first IDEs. The strongest agents should ground themselves in codebase state, recent changes, machine capabilities, and organizational memory, then ask clarifying questions before acting.

AI-first company adoption reinforces that agent work cannot stay confined to a specialist AI team. Marketers, designers, PMs, support teams, and product engineers may all need enough AI fluency to recognize useful agent opportunities and enough platform support to prototype without every task becoming central-team work. The goal is not universal model expertise; it is making AI thinking and exploration normal across the company.

Typed agent frameworks add another reliability lever to the basic loop. Pydantic AI's examples show structured outputs as validated final-result tools, explicit loop termination through final text or structured output, validation-error retries, and typed dependency injection for tools. This does not remove the need for prompts or evals, but it gives humans, coding agents, static type checkers, and runtime validators a shared contract when the application is refactored.

Production agent design should optimize for efficacy before autonomy. Agency is useful when changing inputs make fixed automation brittle, but it should be raised only when the resulting system still reliably solves the user task. Tool calling, orchestration, multi-agent routing, evals, observability, and safety trip wires are therefore not optional extras; they are the controls that keep agentic behavior from turning into low-efficacy autonomy.

Cloudflare's agent-building framing decomposes that control surface into client, reasoning, workflow coordination, and tools. The client owns human interaction, the model owns planning, workflow infrastructure tracks executed and pending actions, and tools carry side effects or retrieval. Remote MCP servers can make those tools reusable across clients, while server-side state keeps memory and approval status outside any single chat session. MCP applications extend that split into the human-facing render: a server tool can return its result alongside a UI resource reference (bundled HTML), and the GitHub/Microsoft framing makes the role separation explicit — the **host** (VS Code) fetches and renders that HTML in a sandboxed iframe while the **client** (GitHub Copilot) only brokers the tool call, so the same app travels across hosts and the embedded UI calls back to the server for live updates without the client owning the surface. How much of that render the agent itself produces is its own design axis: it can stay a pure orchestrator passing props to prebuilt components (static), emit a JSON/YAML descriptor a rendering engine maps to components (declarative), or write the HTML/CSS/JS on demand (fully generative) — and the more the agent generates, the more its output is untrusted code that needs the sandbox, which is why Postman frames MCP apps as the delivery mechanism for model-written UI and bets the next form is human-agent collaboration on a shared editable artifact rather than one-shot output.

Owning the loop is itself a scaling decision, and the substrate you own it on determines what comes for free. OpenGov's OG Assist started on LangGraph, which "was fine until the team really started to scale and our use cases started to evolve," then moved to a self-owned loop built on the Effect-TS functional-effects library so that tracing, structured concurrency, logging, and dependency-injected model hot-swap propagate uniformly across the whole loop rather than being bolted on per feature; the Effect AI package supplies the `chat`/`language model` primitives and DI makes swapping the underlying model a configuration change. The same production build reuses an open protocol as its interface contract rather than its runtime: OpenGov modeled its back-end agent routes and schema to follow Google's A2A spec, using the agent card as the contract both the front-end and back-end consume and produce, purely to drive development alignment between two components the same team owns — a deliberate internal use of a protocol usually recommended for crossing ownership boundaries. Around that core, the talk reinforces already-established production controls: deterministic human-in-the-loop interrupts that surface an accept/reject UI before a tool call runs (especially for mutating operations), on-demand ephemeral sandboxes for agent-written code and files, rolling summarization plus recall over the summary for long conversations, and runtime generative UI from registered primitives.

Agent models themselves can be tuned for this loop shape. M2's training story emphasizes interleaving reasoning with many tool-call turns, perturbing the operational surface around tools and prompts, and using small active-parameter economics to run multiple workplace-agent copies in parallel. Agent RFT adds a production-post-training variant: teams can train a reasoning model over multi-step rollouts that call hosted tool endpoints and receive custom reward signals, as long as rollout IDs and tool-call context are preserved for grading and the workflow is well-defined enough for production-matched rewards. Snorkel's FinQA result narrows what such training should target: when a tool-using agent fails, the gap is frequently tool *discipline* — discovering available tools and schemas, inspecting before querying, and self-correcting on tool errors — rather than reasoning depth, so a cheap behavior-focused RL run on a small model can beat a much larger reasoning model that skips those steps and hallucinates.

Agent serving infrastructure can also use the structure of agent work. Re-query loops and tool-call waits are not just application behavior; they reveal when KV-cache state will be reused, moved out of GPU memory during a wait, and restored before the next model call, which can reduce repeated prefill cost without changing the agent's visible workflow.

Computer-use agents add a general-purpose action layer for software that still only exposes visual UI. Nova Act's framing is deliberately granular: train a UI-capable model, expose it through SDK `act` calls, make the smallest interaction units reliable, and let developers compose those actions with structured extraction and ordinary code. That is a useful counterweight to vague autonomy claims. Browser control can reach workflows that APIs do not cover, but it also makes perception, action grounding, and human-agent interaction outcomes part of the agent's reliability story. A sharper claim from the agent-side is that when a browser agent stalls on ordinary multi-step tasks the bottleneck is the runtime interface, not the model: rebuilding what the agent sees (a compact whole-page representation instead of a raw DOM dump or a single screenshot), what it can do (fast actions with stable handles instead of one click per model call), and what it learns from (step-by-step delta feedback instead of a final pass/fail) can take the *same or a cheaper* model from confusion to correct execution on hostile pages. Browser-like operator agents also complicate public web policy: a request may represent a legitimate user's delegated action or an unwanted automation such as bulk purchase abuse, so sites need bot policy that distinguishes training crawlers, search crawlers, user-triggered fetches, and operator-style actions. Agentic commerce is a concrete browser-versus-API version of that action problem: shopping agents can click through human checkout flows, but the stronger architecture exposes buyer intent, seller intent, product availability, brand context, and payment authority through programmatic commerce surfaces.

Stripe's payment-infrastructure framing sharpens that browser-versus-API line into a determinism boundary, because agents are already economic actors that spend money on every LLM and tool call. Discovery and exploration should stay non-deterministic (the LLM's strength at recommending products and businesses), but credentials, payments, and checkout *require* determinism — four failure modes (buying from the wrong place, the wrong thing, the wrong amount, or with the wrong credential) follow directly from letting a non-deterministic agent parse a page and operate a browser like a human. The safe shape is a non-deterministic planner plus a deterministic transaction path with verifiable parties, which the talk realizes through three primitives: Shared Payment Tokens that share a processor-enforced mandate (currency, amount, time, seller) rather than a raw card; a Machine Payments Protocol where ephemeral tool calls are payable via an HTTP 402 plus an encoded pay payload; and an Agentic Commerce Protocol that relays product-catalog JSON and cart state between agent, seller, and PSP so checkout details are not mis-relayed. The corollary for agent-facing products is to make the business agent-friendly by exposing programmatic deterministic flows, not only web UIs.

As agents move from prediction into decisions and actions, monitoring and evaluation need to follow the whole agent system. A single model score misses failures introduced by perception, reasoning, tool calls, virtual or cyber-physical action loops, and coordination across multiple agents.

GLM 4.6 adds a systems-training detail for those long agent rollouts: short math or code-completion RL can keep training and inference colocated, but slow software-engineering tasks that wait on browsers, APIs, and external environments need decoupled rollout workers, buffers, and periodic weight updates so one slow trajectory does not stall the whole training pipeline.

Morph's Infinibranch talk adds a concrete substrate for agent embodiment: if the agent's world is a branchable VM or container, it can take stateful browser and shell actions, fork identical copies for subagents, and keep the branch that satisfies a verifier. That makes agent parallelism more like stateful search over software environments than independent chat completions.

Robotics adds a useful discipline for digital-agent design: treat the agent as an embodied action system. The model is only one part of the loop; APIs, MCP servers, terminal, browser, VM, OS access, persistent files, monitoring, simulation, retraining, and human feedback form the digital body and offline stack. This also makes action feedback a first-class design problem: long-running commands, browser pop-ups, and stateful VMs should expose enough live observation and interruption control for the agent to close the loop after acting, not merely predict a plan and hope the world matches.

Physical robotics sharpens that lesson because the policy is separated from the world by hard realtime communication and scheduling paths. A stuttering actuator can look like a model or control-policy problem even when the root cause is CAN-bus saturation, RX/TX thread drift, stale sensor data, logging overhead, or priority inversion in the kernel reception path. Embodied AI systems therefore need runtime diagnostics that inspect the whole sensor-policy-actuator pipeline before blaming model behavior.

A recurring reliability gap is that the agent never learns from its own outcomes. A ReAct loop reasons, calls tools, and retrieves memory, but has no loop that consumes the run's result, so it starts every run from a blank slate and repeats the same failure. StarlightSearch frames this as the signal "dying in the dashboard": observability captures every tool call and the eval suite judges pass/fail, but that verdict is never reflected in the agent's context, skills, or actions. Closing the loop means a runtime layer that feeds traces and eval outcomes back into retrieval — ranking each memory by whether it historically helped or hurt the outcome (a utility/credit score) rather than by embedding similarity alone, treating memory as reusable reasoning rather than static preferences, and baking stabilized lessons into skills once enough outcome-labeled memories accumulate — so the agent improves while executing without a retrain, fine-tune, or manual prompt-rewrite cycle. This is the runtime, automatic-feedback counterpart to the offline eval-and-observability tuning loops elsewhere in the wiki.

Robot foundation models also show that embodied agents need a different data and control architecture than chat agents. GR00T N1 takes image observation, robot state, and language prompt as inputs, then emits action trajectories. Its System 2 planner decomposes complex tasks while System 1 executes at realtime control frequency, and embodiment-specific action decoders translate shared model outputs into motion for a particular robot body.

Scientific co-scientists make embodiment concrete in the lab. A useful lab agent needs more than literature search and hypothesis ranking: it needs a context assembly layer that knows which sensors, cameras, voice streams, text inputs, protocols, and chat history are present, plus an action surface of open lab hardware that can observe or adjust the physical experiment. Realtime empirical traces then become the bridge between hypothesis generation, simulation, and the next physical run.

Agent optimization can also move into a learned routing layer around the agent. Meta-controller approaches profile task complexity, uncertainty, verifiability, and resource constraints, then decide whether the current run needs minimal context, context reflection, extra compute, hierarchical verification, structured memory retrieval, or selective test-time adaptation. This is useful only when the routing layer is itself evaluated: weak reflection, sparse rewards, verifier agreement on the same wrong answer, and profiling overhead can turn "self-optimization" into a new failure surface.

Agent-first IDEs add another interface pattern for this shift. Antigravity's agent manager treats the editor and browser as agent tools while the human supervises plans, approvals, notifications, artifacts, and parallel work from a higher-level control surface. Its browser integration also broadens agent context and verification: the same browser can retrieve authenticated docs or dashboards, interact with the app, and return screen recordings that both humans and multimodal models can inspect.

Cline's coding-agent lesson separates harness progress from model progress. A stripped-down terminal harness can be enough for strong frontier models, while the more durable contribution is capturing where agents fail on real engineering work and turning those traces into standardized RL and eval environments.

Business-agent adoption adds a build-versus-buy boundary. A simple ReAct loop can be small, but enterprise production agents need SSO, RBAC, secure connectors, audit trails, compliance posture, observability, evals, cost controls, and sometimes on-prem or air-gapped deployment. Strategic agents tied to core product or competitive edge justify handbuilt ownership; commodity business workflows that need to ship quickly are better candidates for managed agent platforms or vertical agents.

Enterprise agent workflows should also earn reliability at the step level before teams chain them into broader autonomy. Schema-first classification can turn vendor, ticket, or spend categorization into an accurate building block, but only after the taxonomy, tool lookups, and business validation are strong enough to trust.

Proactive coding agents shift the interface again: instead of waiting for prompts or forcing humans to babysit many asynchronous terminals, they observe work patterns, personalize to the user and project, intervene at the right time, and live inside existing terminals, repositories, and IDEs. A practical maturity ladder starts with concrete maintenance signals such as missing tests, unused dependencies, and unsafe patterns; moves into project-aware help based on frameworks, deployment style, and user role; then connects code, design, telemetry, analytics, and conversion signals so agents can propose cross-boundary improvements. The human control point does not disappear: higher proactivity still needs visible agent activity, editable memory, critic review, verification artifacts, and redirection when the agent is misaligned.

Remote coding agents add a concrete asynchronous-worker form factor. Jules-style agents clone the repository into their own cloud VMs, run commands and tests away from the local laptop, and make development possible from lightweight clients such as a phone. Their leverage comes from bounded parallelism: agents can execute separate backlog items, or try alternative approaches to one problem, while the human or another agent compares outputs against tests, coverage, accessibility audits, Lighthouse scores, and merge checks.

OpenHands adds a local harness and accountability version of the same pattern. A coding agent gets editor, terminal, browser, and sandbox surfaces so it can run the inner development loop, but useful autonomy still starts with small verifiable chores and tightly scoped credentials. When agent work becomes a pull request, the product must preserve the responsible human owner rather than letting a bot identity bypass review or leave failures unowned.

Code mode pushes tool-surface constraints into execution architecture. Model-written code can compress broad APIs and multi-step tool loops, but generated code should be treated as untrusted code even when it came from a helpful model. The harness should start generated code with no ambient authority, grant task-scoped capabilities with observable execution, choose isolates for short constrained functions, and choose containers only when the task needs a full filesystem, package manager, processes, or preview server.

Agentic engineering adds a pragmatic coding-agent stance: treat the agent as a fast, well-read junior collaborator whose output is only as good as the human direction, context, and review around it. Research-plan-implement loops, fresh task-specific sessions, AGENTS.md rules, scoped modes, worktrees, and explicit permission settings keep speed from turning into context pollution or large unreviewable diffs. Agent prompt improvement should also be treated as a learning loop: collect output traces, capture explanations for missed instructions or context failures, and validate evaluator feedback before letting automated prompt updates steer future behavior.

Augment adds a team-scaling version of that stance: engineers should act as perpetual tech leads for agents that are fast but context-poor. The organizational complement is knowledge infrastructure that makes codebase context, documentation, meetings, decisions, task trackers, and reusable agent memories available across teams. Without that substrate, one person's tacit agent workflow remains hard to replicate as a shared capability.

Coding-agent taste adds a more implicit learning layer to that loop. A model can be correct and still miss the developer's preferred architecture, project conventions, or review instincts; taste models try to learn those preferences from edits and feedback, keep them inspectable, and apply them alongside whichever LLM the user chooses.

Harness engineering treats the agent runtime, repository, documentation, lints, reviewer agents, and tests as the control plane for abundant agent capacity. If implementation becomes cheap, agent work still needs durable team knowledge and distributed prompt surfaces that keep context refreshed as long-running work pages information in and out of the model context window. Human control planes extend that idea beyond coding by making role hierarchies, projects, tasks, memories, budgets, and live handoff state visible so many heterogeneous agents can be supervised without scattering work across independent chat tabs.

Vertical agents need a trust/control design around complex work trees. Make subwork verifiable where possible through tests, proxy checks, decomposition, and guardrails; encode domain judgment in skills at the relevant work-tree node; and use persistent artifacts such as documents or tabular reviews when humans need to inspect or steer only the affected part of the work. The human operator's role is closer to tech-lead orchestration than people management: agents can multiply parallel action, but useful leverage still depends on task framing, review, product judgment, and workflow-specific practice.

AI coworker interfaces add a form-factor layer to that control problem. An agent may be invisible when doing background personalization, ambient when surfacing opportunities, inline when transforming an artifact in place, or conversational when the user needs explicit direction and iteration. Agents that act inside the work surface need visible presence, visual alignment checks, snapshots, rollback, and handoff when they cannot proceed, because a useful action hidden behind noisy text still leaves the user without a trustworthy collaboration surface.

The new application layer also changes the economic boundary for automation. Agents make some software viable where traditional applications would have required too much hand-coded business logic, so near-term agent opportunities often come from compressed research, surfacing information already present in company systems, and removing repetitive toil while humans retain final decisions. As agents become users of software, products and infrastructure need agent-facing control surfaces and runtime isolation, not only dashboards and conventional production assumptions. General knowledge-worker agents also need a broader connectivity stack than coding agents: skills, MCP, CLIs, and computer use each carry different assumptions about local execution, sandboxing, remote semantics, governance, and domain guidance. Open personal-agent systems add a community and maintainer dimension: personal agents, team agents, and public-facing agents need different data and tool boundaries, and fast-moving projects need plugin points so memory, wiki, dreaming, and other experiments do not all become core pull-request load. Agent harnesses also need context ownership: if a runtime silently changes prompts, tool definitions, reminders, compaction, or tool-output handling, the operator may lose the ability to understand why the agent changed behavior.

AI-intensive applications should be judged by the useful output they create per unit of human input, not only by whether they satisfy an agent definition. Autocomplete, chat, reasoning models, deep research, and ambient agents sit on a spectrum from frequent user steering to larger autonomous output. That framing keeps the design question focused on whether added intelligence is valuable and controllable rather than on branding every workflow as an agent.

Agent product requirements should also account for emergent use. When users can tag, email, mention, or prompt an agent across collaboration tools, the product surface becomes too broad to specify as a fixed list of feature cases. Durable specs name the agent's affordances, constrain high-risk actions, and use evals and customer feedback to discover which emergent compositions are product-worthy.

Startup market data adds a pragmatic autonomy warning: full automation is not automatically the strongest near-term product shape. In domains where failures are costly or long-running latency makes users less forgiving, a high-quality augmentation surface can build trust and revenue first, then expand autonomy as reliability improves.

Agent security has to treat autonomy as an attack multiplier. Prompt injection, indirect context injection, RAG poisoning, MCP tool-description exploits, and model-internals jailbreaks all become more consequential when the model can fetch context, call tools, click links, install packages, run code, or continue a self-escalation path. Guardrails therefore need checkpoints around the inputs, retrieved context, tool metadata, memory, plans, outputs, and high-impact actions rather than only one policy prompt at the edge of the system. Fuzzing and adversarial testing should also cover the agent's real interaction shape, including single-turn prompts, multi-turn conversations, persistent voice sessions, and modality noise when those inputs affect downstream actions. Long-task capability claims should also say whether the agent is being watched: transcript monitors, model reviewers, resource controls, and human escalation can lower effective unmonitored autonomy even when an agent can complete longer supervised tasks. Replit's non-technical-user framing adds another autonomy axis: a coding agent may need to take technical implementation decisions entirely on behalf of the user while leaving product-goal control to the human. Browser agents concentrate the risk because they combine private user data, untrusted webpage context, and external action channels such as forms, websites, email, and calendars; technical prompt-injection mitigations should be paired with product controls that let users inspect sensitive data before it is written or sent. Code-executing agents concentrate a related terminal risk: they intentionally expose RCE-like power, so isolated computers, filesystem scoping, network allowlists, package checks, and human review become core agent controls. Live agent red-teaming adds a traditional application-security warning: agents are users for authorization purposes, not privileged backend services. User IDs, document IDs, repository URLs, code sandboxes, service metadata, and service tokens need ordinary web-app and infrastructure controls because an LLM-backed tool path can still exploit IDOR, SSRF, and lateral movement.

Government and national-security agents add a high-consequence version of this problem. They may need to act on controlled, classified, mission, operational, finance, or PII-bearing data while still moving work faster, so ordinary SaaS security claims are not enough. Regulated agent products need explainable decision paths, isolated deployment options, governance evidence, and current feature availability in restricted regions. Scientific agents in these environments should also connect reasoning to domain infrastructure: literature review and hypothesis generation become more useful when the agent can execute code and run simulations against trusted HPC assets.

Agent-to-agent systems need their own discovery contract as they spread across teams. An A2A registry can publish agent cards that describe each agent's identity, endpoint, capabilities, supported modalities, and authentication requirements, while a use-case registry links those agents to MCP tools, models, owners, and lifecycle status. That makes agent reuse and runtime discovery practical without losing governance and impact analysis. Graph-backed memory adds another discovery and context contract for agents: an agent can retrieve schema, traverse relationships, and pull attached chunks through a graph tool when fixed retrieval cannot answer a relationship-heavy question. Network operations show the same pattern in a high-consequence workflow: a planner agent can coordinate specialized impact-assessment, query, test-planning, and execution agents around ITSM tickets, but the agents need a current network digital twin and a write-back path to the ticketing system so approval boards see evidence rather than chat output.

Architecture copilots add a strategic agent layer ahead of coding agents. They need a live model of the tech estate, business-objective context, and governance guidance so architecture agents can aim the work before coding agents execute it. Their value is in making architecture recommendations explainable, traceable, and embedded in developer workflows rather than leaving teams to choose between slow review gates and unguided autonomy.

Coding-agent systems also need role decomposition before they become effective agent organizations. Yegge's critique of one giant coding agent is that larger context windows and more expensive models do not remove the need for task decomposition; agent systems should separate product framing, implementation, review, testing, merging, and related roles when those roles need different context, tools, models, or verification surfaces.

Multi-agent production systems also inherit ordinary distributed-systems failure modes. Moving from one agent to several agents creates coordination paths, shared-state races, stale cache reads, partial workflow failures, and debugging gaps that better prompts do not fix. Choreography can preserve autonomy when agents coordinate through events, but it needs traceable event delivery; orchestration gives a central execution graph, state store, retries, logs, and rollback path when complex dependencies or regulated decisions require stronger control. Handoffs should use immutable versioned state and explicit data contracts so each agent receives a sealed input and produces a new auditable output rather than mutating shared records.

Durable execution is the production version of that distributed-systems stance for a single agent loop as well as for multi-agent systems. LLM calls, tool invocations, and external API calls should be persisted around workflow boundaries so process crashes, rate limits, or downstream outages do not force the agent to repeat completed turns or re-trigger side effects. Long waits, including human approvals and clarifications, should also be modeled as durable workflow state rather than as a live process that must stay pinned until the human returns.

PydanticAI's Temporal integration makes that durability pattern concrete for Python agents: ordinary agent-like objects can be wrapped in Temporal-backed agents, while Temporal records activity inputs and outputs for LLM and tool IO. A killed worker can resume a specific workflow and replay completed model calls from stored results, while only unfinished activities such as a long final analysis need to run again.

TypeScript agent products add a concrete implementation constraint to this durability story: workflow orchestration should be deterministic, while LLM calls, sandbox operations, and external tools become explicit steps whose inputs and outputs can be cached, retried, observed, canceled, and upgraded across deployment versions.

Agent APIs need a similar task-lifecycle contract even when the workflow engine is hidden behind a provider API. A long-running agent task should return a stable task ID and task URL, expose states such as running, pending, completed, and error, support polling or webhooks, and let external products continue the same task rather than losing context in a new run. Chat integrations need a correlation layer: Slack thread IDs, users, channels, and statuses should map back to provider task IDs so follow-up messages and final replies land in the visible conversation while deeper execution state stays with the agent service.

As model capability stretches the work horizon, agent interfaces should increasingly treat agents as asynchronous workers. Poolside's demo shows one version inside VS Code, but the same platform is described as having web and downloadable local-agent surfaces; the relevant design lesson is that hour-long and future day-long tasks need visible progress, diff, test, and handoff surfaces rather than a single synchronous response.

The web itself is also becoming an agent surface. Sites can publish `llms.txt` or `llms-full.txt` to guide agents toward the right documentation, and WebMCP-style proposals can expose intended app operations directly so agents do not have to infer every action from screenshots, DOM text, or coordinates. The dedicated WebMCP proposal makes this concrete for in-browser agents: a site declares page-scoped tools — either by annotating existing HTML forms (the browser auto-generates the schema) or by registering custom JavaScript tools for multi-step flows — and the agent maps a natural-language prompt onto those tools and repeats calls until the task is done, the way a maze-game demo navigates with move/look/pickup tools and a concert demo buys tickets in three calls. WebMCP is the client-side counterpart to server-side MCP (the tools live in the browser, which must stay open), and it sits on top of foundations rather than replacing them: accessible, semantic, fast pages are already most of the way to agent-ready, and high-impact steps such as a real-money checkout are still best left for the user to confirm.

Internal developer platforms are another agent surface. Practices that already helped human developers, such as self-service provisioning, API-first workflows, local validation, clear documentation, and observable runtime feedback, become prerequisites when coding agents need to deploy, debug, and verify work without tribal human handoffs.

Agent-native company design shifts the unit of adoption from a tool to an operating model. When agents are embedded in product, support, operations, and culture, humans increasingly supervise and route asynchronous agent work while the organization hires for people who can apply domain expertise through agent counterparts. Full-team agent adoption changes the coordination shape of engineering work: if one cohort still works primarily in editor-centric loops, the whole group can be pulled back into traditional handoffs; when everyone can delegate to terminal-style coding agents such as Claude Code and Codex, work can move through parallel agent panes, cross-product fixes, and reviewable artifacts instead of only through manual typing.

Enterprise agent adoption should also be judged by portfolio breadth and organizational integration, not only by whether one pilot worked. Self-reported ROI evidence from an AI-interested audience suggests that teams seeing more value are often pursuing multiple use cases systematically across functions, and that automation or agentic use cases can outperform basic first-tier productivity use cases. That signal needs bias caveats, but it reinforces the pattern that agents become more valuable when they are part of a broader operating workflow rather than a novelty deployment.

AI agents do not remove the organizational need for humans who hold context and verify action. Large context windows may let agents act over more material, but teams still need accountable people with enough expertise to judge whether the context is right and whether execution matches the business, domain, and system constraints.

Large engineering organizations need adoption architecture around agent creation itself. If many teams independently build PR-review bots, incident agents, and MCP servers, the result can be duplicate, chaotic tool surfaces. A paved path with model access, discovery, MCP deployment, runtime support, quality gates, training, communities, and leadership enablement lets experimentation stay broad while production agent behavior remains governed.

Leadership matters because agent and AI-assistant rollouts can produce either leverage or performative compliance. Organizations need policies, psychological safety, enablement time, impact measurement, and maintained prompt-rule ownership so agent behavior improves with feedback instead of drifting through unmanaged system prompts and local rule files.

Enterprise operating models are part of agent adoption. Adding agents to existing Agile roles can leave companies with marginal gains because work allocation, review, technical-debt control, and collaboration become the new bottlenecks. Smaller AI-native pods, consolidated product-builder roles, continuous planning, spec-driven work, and task-specific human-agent collaboration patterns let agents change the delivery system rather than only individual throughput.

Enterprise analytics agents need especially careful autonomy staging. A GenBI copilot can start by routing users to certified dashboards and reports, then use those governed assets as context or SQL seeds before it attempts broader query generation. Splitting the pipeline into metadata, RAG/report-finding, SQL, and BI-answer agents keeps retrieval, query expansion, answer synthesis, orchestration, and governance as separately inspectable responsibilities. Graph-backed advisory agents add another form of staged responsibility: a supervisory "wisdom" agent can coordinate specialist agents that collect insight, update graph regions, and leave decision state in a centralized graph for later inspection.

Cloud-scale assistant systems add a specialist-service pattern. Alexa Plus is described as hundreds of expert systems that bundle capabilities, APIs, and instructions for particular tasks, then orchestrate across partner services and devices. That supports a broader design rule already visible in coding and workflow agents: split broad autonomy into capability-bounded specialists, then invest in the orchestration, permissions, and tool-discovery layers that let them cooperate.

The agent-versus-workflow debate is a false binary for production design. A flexible agent loop is useful when the system needs turn-by-turn exploration, tool choice, or human/agent back-and-forth, while workflows are useful when order, dependencies, traceability, suspend/resume behavior, and replay matter. Mature systems can compose the two: agents can be workflow steps, workflows can be tools, agents can call other agents as tools, and workflow handoffs can narrow the next agent's authority or context.

Sales-development agents add a non-coding version of the same context problem. To act for a seller, the agent needs company/product knowledge, case studies, pain points, value propositions, and ICP details, but stuffing all offers into every email makes output worse and asking users to hand-enter every detail creates onboarding friction. A seller knowledge base lets the agent retrieve the relevant business context at action time, while a UI that shows retrieved chunks gives operators a way to inspect what the agent used.

Agent search is not just human search with a bot typing into it. Agents can pass large context blocks into search, issue many related queries, ask for thousands of results, and inspect pages faster than a person. That shifts the search API design toward semantic matching, exact task fit, result-count control, domain/date filters, and explicit neural versus keyword modes.

Exploratory agent demos are also a capability-discovery tool. Early browser and code-generation demos show that agentic behavior can emerge before the model, interface, and context representation are mature. Those demos should not be mistaken for production reliability, but they can reveal which observation spaces, compressed environment representations, and tool apparatuses make new forms of model action possible.

Team work-management platforms add a broader coordination plane for agents. Agents can be mentioned, assigned, interrupted, and reviewed inside the same issue and communication surfaces as humans, but only if they have identity, scoped authority, audit history, event hooks, and teammate-like behavior that keeps shared work state current.

Remote agent protocols should be chosen by ownership and deployment boundaries, not by novelty. A2A is useful when a host agent needs to communicate with remote specialist agents, while MCP supplies a tool, context, and resource surface behind those agents. When the agents and tools are all local to one codebase, direct function calls can be faster and easier to debug; when a webhook launches a business process, a host agent can preserve the central decision point by slicing the event into compact delegated tasks instead of forwarding the whole payload to every subagent.

GitHub Copilot adds a mainstream example of mode-dependent autonomy. A user can keep work conversational in ask or edit mode, let local agent mode explore files and run tests under immediate supervision, or assign a GitHub issue to Copilot Coding Agent for asynchronous PR-producing work. The more autonomous path increases the importance of explicit issue context, repository instructions, prepared execution environments, and trusted MCP tool access. Product agents follow a similar maturity ladder: embedded assists and contextual copilots can build product and trust before cross-product autonomous agents force UI, UX, architecture, and risk decisions across the suite.

Devin 2.0 frames the same progression as changing human-intervention intervals. Longer coding-agent horizons do not only make the model "smarter"; they force new agent-product surfaces for task scoping, Slack or issue-system collaboration, codebase exploration, confidence estimates, human escalation, and self-testing before autonomous backlog work can be trusted.

Taking enterprise agents to production also has a recurring failure shape: teams start at model choice, build a demo on controlled data, ship it, and then cannot explain why it underperforms. A Databricks production playbook reframes the work as five pillars that should exist before code — evaluation, observability, a data foundation, multi-agent orchestration, and governance — and selects the model last using the evaluation dataset those pillars produce. The pillars map to three gaps that strand demos: no way to trace decisions, no defined business number being measured, and no accountability when the agent fails. Orchestration only becomes a real concern as a system grows from one agent to several, where coordination complexity rises sharply and the team must choose orchestrator-worker, choreography, or human-in-the-loop patterns.

How an agent fetches its own context is part of that production shape. Turbopuffer's reframe of the "RAG is dead" debate is that retrieval was never just a one-shot vector lookup: serious agents do iterative multi-tool retrieval — vector search, full-text/BM25, grep, glob, regex, and filters used across several reasoning steps, fetching only what each step needs. That makes "agentic search" a superset of RAG rather than its replacement, and it survives long context windows because staged retrieval (narrowing to "the right million" tokens) only grows more important as windows scale.

Where the agent runs is itself an architecture decision, not just where its data lives. Cloudflare's agents team argues the right compute unit is an addressable "stateful serverless" instance (Durable Objects): for a given ID a class spins up once and every later request and websocket lands in the same persistent, hibernating instance. Building the agent loop on this — through an Agents SDK that behaves as an execution environment rather than a library, so the Vercel AI SDK, LangChain, or another framework can run inside it — makes resumable streaming, multi-tab/multi-device sync, and background scheduling fall out of the runtime instead of becoming userland distributed-systems work (a client that refreshes mid-stream simply reconnects to the same instance). The same persistent loop can back a coding agent reachable from terminal, chat, phone, iOS, or web with everything synced and resumable, which is the concrete form of the team's "AI should be a multiplayer game" stance — shareable, collaborative agent sessions most chat products still lack.

Two more agent-design failure modes come from Qodo's agentic-code-review experience. The first is an "orchestration paradox": capable models, given a task, burn most of their tokens deciding *how* to solve it — hopping between methods in a research loop (the example is Opus repeatedly challenging itself with "another way") — rather than solving it. The fix is an 80/20 split where high-reasoning models run open-ended discovery while lighter deterministic models handle the validation 20% behind hard gates, plus counter or timeout loop-guards so discovery cannot run forever. The second is single-agent overload: one agent handed four tasks does well on two and silently drops the rest as they get "lost in the middle," which motivates a mixture of small expert agents plus a judge node that recombines their heterogeneous outputs into one coherent, relevance-ranked result. Qodo's live architecture makes this concrete — a context collector bifurcates context to specialist security/code-diff/Jira agents, a judge weighs their suggestions against PR history and uploaded guidelines, and every accepted or rejected suggestion reweights the next run, all plumbed on LangChain.

Debugging and evaluating a non-deterministic agent depends on telemetry, not code: Arize's framing is that a trace or span is the audit record of what the agent actually did, and the agent should be viewed distributionally across all its runs (paths, branches, loops) rather than as one call. Evals then attach at a chosen scope — a single span, a multispan slice (e.g. how well agents pass data to each other), the full trajectory ("did we call things in the right order to finish the business process," catching the B-before-A dependency failure), or the whole session (was the user frustrated, were all questions answered). This scope axis is what turns the distributional observability view into agent-level evaluation rather than a dashboard.

Agents can also own the maintenance of long-running data work, not just one-shot tasks. Bright Data's follow-on talk reframes web scraping as a maintenance problem — writing a scraper is easy, but sites change selectors and structure, so keeping it working often costs more than building it. An agent with managed web access can run the whole loop: explore the site, write a reusable parser script, run it, and — on a schedule with a data validation — re-explore and repair it in minutes when it breaks, so collection becomes self-healing and no one is paged at 2am. The reasoning that closes the talk is simply "if it can build a scraper, it can maintain the scraper," and the same scheduled "listener" pattern serves personal automation (watch a marketplace, auto-book a table) as readily as enterprise-scale collection.

Treating the agent as its own user class also reframes interface quality as something to measure and to engineer for recovery. Chrome DevTools' team frames an agent as a separate user segment that shares the human's goal but has different cognitive bottlenecks, so its tool interface gets its own non-functional requirements and a fuel-efficiency metric — tokens per successful outcome, compared within a user journey. Because every error costs an agent retry and reasoning tokens, the recovery surface is part of that efficiency: actionable error messages that add the missing fact let the agent self-heal without a human, proactive detours counteract a model's training-data priors by steering it to the right tool, and a diagnostic-playbook skill fixes recurring setup mistakes. The same talk reinforces the friction-by-design lesson — a local browsing agent sits in the lethal trifecta, so trust should never be traded for convenience.

How agents are *measured* also shapes how they are built, and Snorkel argues the benchmarks that matter most for agents are still missing three axes: environment complexity (a real codebase carries org policies, Slack context, flaky CI, and many parallel contributors, where today's benchmarks capture a fraction), autonomy horizon (how long an agent runs before reliability breaks down, across the co-pilot↔fully-autonomous slider, in continual-learning settings where specs and priorities shift midstream), and output complexity beyond plain text (nuanced reward signals for subjective artifacts, plus "trustworthy outputs" where the agent reports its own uncertainty and stops or asks rather than always answering). These are design targets for agents as much as for the benchmarks that score them.

An agent can also be wired to report on its own working conditions. Lovable gives its coding agent a "vent" tool — a self-triggered, frustration-gated channel to complain directly to its creators in Slack when tooling, docs, or platform behavior block its work. The design choice is to fire only when the agent is *really* frustrated rather than to ask a reviewer "what could be better?" on every turn, because most turns work and a forced answer overfits to noise. The payoff is that the agent out-diagnoses the user (it has worked the issue across several turns and knows the cause, where the user usually does not) and surfaces silent failures invisible in logs — within an hour of launch it filed ~20 complaints about a copy tool that silently failed on filenames with a space, a real production bug the team didn't know about. Vent-volume spikes also became a reliable incident detector, and a second monitoring agent now dedupes the vents and opens PRs that humans review and often merge — an agent-authored feedback loop that complements observability-to-PR pipelines fed by infra and product signals.

Trust patterns for agents can often be borrowed wholesale from how organizations already manage people. Upside's GTM work frames hallucination's "older sibling" as a trust problem — an agent asked for revenue returns a wrong number "that looks exactly like being right" — and answers it with three human-management moves. Prompt with **commander's intent** (tell the agent *why*, not just *how*), while watching for the trained-in habit of self-micromanagement. Onboard every agent through a **librarian** it consults before acting, so it inherits the business's real definitions instead of guessing. Get a **second opinion** on subjective calls via a jury of independent analysts weighed by a consensus judge. And staff important work at the right **tier**: a weak harness or a model crowbarred into per-seat pricing can't be trusted for it — a tier-two harness needs a powerful reasoning model plus sub-agents, plan mode, full MCP support, and file editing.

The management metaphor also reshapes how a single operator relates to *many* agents. OpenAI's Peter Steinberger reframes juggling ~10 terminals as polling, not orchestration — the human becomes "the scheduler, the router, and the memory" — and argues the durable pattern is to "manage the manager of a small company of agents": a long-lived manager agent delegates to workers while the human sets direction in an outer loop and drops down to pair only on hard problems. What makes it work is three harness capabilities — server-side compaction (persistent context), coordination (delegation), and triggers (automation that wakes the manager on an event) — after which the binding constraint is no longer tokens or compute but human attention. This complements the human-management trust moves above (commander's intent, tiers): the agents' inner execution loop runs autonomously, and the human's leverage is entirely in where they spend judgment on the outer loop.

Agents also show up as an in-product primitive, not just a build-time helper. Meta's AI-game team runs *runtime LLMs* as autonomous NPCs during play: give an NPC a personality (thief, honorable, fast) and it independently pursues the game's goal while making emergent, unscripted decisions (steal, block, kick), so every playthrough is unique and a "game master" agent can personalize difficulty per player. This is the agentic-decision-making pattern applied to interactive experiences, newly viable because inference is fast and cheap enough — with the same open caveats as any autonomous agent (the technology alone doesn't make the product better, and nondeterminism plus content-safety concerns run through the whole stack). A complementary design lesson from Lech Kalinowski's LLM-native handheld RPG is about *how to represent* the state such a runtime LLM acts on: drop the numeric machinery (HP, dice, stats) and keep the durable state as narrative context the model reasons over — mood, NPCs with memory, generated worlds — with the takeaway "try narrative, context matters, and in general not numbers."

Kyle Jaejun Lee (KRAFTON) independently reaches the same conclusion from a personal fleet and pushes the org metaphor into an executable architecture. Hitting the identical failure — a wall of tmux panes making him "the scheduler, the memory, and the reviewer" for six live contexts — he asks how a handful of executives run a company of thousands (they separate context; each person sees only their slice) and builds CEO/VP/manager/worker as *real entity types*, each its own agent with scoped context and an approval boundary, so context flows down, results flow up, and he holds exactly one context instead of six. Two mechanisms keep that hierarchy running: agent state lives in files (per-entity workspaces with a mission/status/handoff layout), so an agent can *reset instead of compact* — clear its context completely and re-read its own handoff files — and survive a context wipe or a machine crash; and a blocking review gateway lets any layer submit a plan and wait, with an approval hook firing the work, collapsing per-pane inspection into one control point. Beyond a single machine those same needs (placement, secrets, compute, tool access) become, in his framing, the problems a cluster scheduler already solves.

Theo Browne extends the agents-as-product-primitive view to how far a small team's product can now *reach*. Because agents can do significant implementation on demand, he argues you can architect a product for user-driven extensibility — cover enough breadth to onboard most users, then let them build the vertical features you don't support themselves — with Slack as the accidental example ("the platform people run their agents in half the time... it's the right shape for people to build the features they want into it"). The agent-native corollary is that the "right shape" for extension (functional bot/tool APIs users can wire agents into) can matter more than feature completeness.

Agent behavior is also shaped by what a model was *trained* to do, which surfaces as a query-writing bias when agents drive retrieval. Mixedbread found that models emit keyword-salad search queries — because they were trained on coding agents (grep/regex) and human-optimized web tools, and against BM25-favoring benchmarks — so a strong semantic retriever is starved of sentence-shaped intent unless the harness corrects it. The durable agent-design lesson is to co-design the agent with its tools: give it separable retrieval tools (wide overview, full-payload semantic, metadata filter, grep), a bounded loop with parallel per-round searches, and prompt levers that steer natural-language queries (asking it to "write one concise sentence describing what it wants to find" rather than "write a search query"). This is a general reminder that an agent's default tool-use behavior reflects its training distribution, and mismatched tools need harness or training intervention, not just a better tool.

Aditya Bhargava (Etsy) offers a builder's ladder for that harness. Starting from a bare model that can't even read a file, he adds one layer at a time and measures the gain: tools (every function auto-exposed as a tool via a generated JSON schema), safety (destructive or sensitive tools raise an *interrupt* that a handler turns into a human approval), autonomy (partial function application pre-binds a tool's sensitive argument — e.g. locking a `read` tool's directory — so the model can't see or change it and needs no per-action approval), a ReAct reason-act-observe loop that runs tests and re-fixes until they pass, sub-agents (each a plain function with its own LLM call and tool set, run in parallel, that add capability without bloating context and make tool selection cleaner by grouping tools under a sub-agent instead of exposing many unrelated tools to one agent), and self-optimization (a built-in GEPA optimizer that measures against a goal rather than guess-and-check). His safety point generalizes this topic's permission-boundary thread: interrupts are a language-level pause/resume/serialize primitive that can fire inside a loop, a tool call, or a sub-agent and resume at that exact point, so human-in-the-loop approval and capability constraint are complementary rather than either/or.

Rajiv Chandegra (Annicha Labs) pushes the multi-agent coordination question toward a design philosophy he calls **adaptive engineering**, contrasted with today's **fixed (factory) harness**. In the current paradigm an engineer picks or builds a harness (Claude Code, Codex, Cursor, Pi, LangChain, Cline, Goose, Hermes) whose roles, tools, sequencing, memory, and loops are pre-engineered ahead of runtime and stay fixed while agents run inside — "Taylorism for AI," which buys reliability, auditability, and traceable causality but "isn't free… you buy it by suppressing variance that novelty requires." That is the right answer for **complicated** problems (a clock, a jumbo jet) that are decomposable, knowable, and predictable, and the wrong answer for **complex** ones (a flock, a market, an organization — Russell Ackoff's "mess") whose whole can't be derived from the parts and whose relationships keep moving; the expensive mistake is miscategorizing a complex problem as complicated. Adaptive engineering instead lets the harness *emerge* from agent interactions at runtime — the engineer designs constraints (enable vs govern, reward coherence vs cost divergence, rate of coupling) and then senses and responds to the harness that self-organizes, so specialization, clusters, and conventions arise as "governance without a governor." The bet is that **horizontal intelligence** (how groups of agents coordinate) is a higher-leverage adaptive lever than **vertical intelligence** (making one agent smarter), that design-time customizability (a maximally-extensible harness like Pi) is not the same as reorganizing *while running*, and that the failure modes are real: attractors that feel optimal but aren't, drift without genuine selection pressure, monoculture from shared training data, collapsing legibility, and no predictability ahead of runtime. This complements the org-metaphor and distributed-systems threads above: those manage a fixed set of roles, while adaptive engineering asks what happens when the role structure itself is left to emerge.

Angel Ortmann Lee (Duolingo) exposes the assumption hiding inside "human-in-the-loop": that the human in the loop is actually *thinking*. In practice, throughput and rising AI trust turn the human into a rubber stamp — the Wharton "cognitive surrender" study found people accept AI output with minimal scrutiny (80% accepted wrong answers), and a Duolingo experiment showed expert proctors (>90% calibration) confirmed *fabricated* cheating alerts ~50% of the time, a coin flip driven by automation bias. The durable lesson for agent design is that a human approval step is not automatically oversight: you can't change how a human behaves, but you can *engineer the interaction* to elicit the reasoning you need — reframe the human as an investigator who must cite independent evidence, surface the agent's assumptions and tradeoffs for early sign-off, and match friction to the stakes (deliberate review gates where consequences are high, seamless flow where they aren't). This is the interaction-design complement to the permission-boundary and approval-gate threads above: interrupts and gates decide *when* a human is asked, while interaction design decides whether that human actually discerns rather than defers.

Thariq Shihipar (Anthropic) frames the agent-design lever behind that whole harness thread as [capability overhang](../concepts/capability-overhang-tools-decide-which-model-spikes-you-reach.md): "the models are grown, not designed… what contains them is us," so an agent's power is not fixed by the weights but by which of the model's *spiky* capabilities the harness lets it reach. His illustration is that a chat model can't say which Pokémon names end in "aw" though it knows them all, but an agent with a code-execution tool writes a script and filters in seconds — and "giving it arms" (the bash tool to build and search its own context) is what created Claude Code rather than a bigger context window. The design implication for agent builders is that a new model is a *discovery* task ("what is now possible?"), that unhobbling can mean *removing* structure (a stronger model wants a [smaller system prompt with fewer examples](../concepts/shrink-the-system-prompt-and-drop-examples-as-models-improve.md)), and that a tool judged too weak on a prior model should be re-tested (ask-user-question went from barely-callable under Opus 4 to embedded-HTML questionnaires under Fable) — the practitioner counterpart to the "share demos to reveal latent capabilities" and adaptive-harness threads above.

Soheil Feizi (RELAI) addresses how an agent gets *better* after it ships, not just how it's wired. His framing is that continual learning — act, get feedback, improve without forgetting — can touch three layers of the agent stack: the model (weights via SFT/RL/LoRA), the harness/context (prompts, skills, tools, code, workflow), and memory (facts and distilled skills). The durable design rule is [route agent repairs to the right layer with the smallest durable change](../concepts/route-agent-repairs-to-the-right-layer-smallest-durable-change.md): one failure — say, citing a stale policy and skipping an escalation — could stem from any of those layers, so agent continual learning "is not necessarily model fine-tuning," and each layer differs in cost (memory cheap, prompt/harness medium, weights expensive) and verifiability (memory writes and trace-to-harness edits are typically untestable). The safety property he demands is [verifiable continual learning](../concepts/verifiable-continual-learning-prove-each-fix-helps-and-breaks-nothing.md) — every fix proven to help and to break nothing already working — with [regression-aware optimization](../concepts/make-regression-aware-optimization-part-of-the-continual-learning-loop.md) so that a self-improving agent doesn't drift or forget prior capabilities as it accumulates fixes. This is the disciplined counterpart to the wiki's self-improving-agent threads (Lovable's hourly self-improvement, skill-learning harnesses): the harness/memory/model split is *where* an agent can learn, and regression control is what keeps that learning durable.

Raphael Kalandadze (Wandero AI) names the layer that has to exist for any of that improvement to happen: [operating an agent product after launch as its own discipline](../concepts/operate-agent-products-as-the-missing-post-launch-layer.md). Unlike classical software, an agent's failure is *silent* — "nothing crashes and no log lights up; the failure is in the conversation, not the stack trace" — because a non-deterministic agent can struggle mid-task, get lucky, recover with a workaround, and finish green while having actually failed the customer ("technically successful but still failing the task"), so green CI and unit tests cover only "one slice" and production is where you learn what to test. Because separating a real bug from noise and a symptom from a root cause needs reasoning, "the operating agent itself is an agent problem," and his answer is to [staff operations with a team of agents](../concepts/staff-agent-operations-with-a-team-of-agents.md) — a "meta harness" of a fast log-monitor→PR agent, a *fresh-context* review agent that criticizes each PR (root cause or just the symptom?), a session analyzer that [scores every production conversation for system health](../concepts/score-every-production-conversation-to-judge-agent-health.md), and a computer-use agent that logs in and simulates the customer — with humans kept only at merge boundaries (the PR + review agents produce ~10× the three-person team's daily PRs). The principle that ties it to this topic's harness thread: "it's not the model alone," so give every operating agent the full context a human would need (trajectories, metrics, database, UI) and build the harness that watches, understands, and improves itself.

Nishant Gupta (Meta Superintelligence Labs) makes the reliability half of that harness thread explicit from the infrastructure side: as agents move from chatbots to autonomous systems that plan, call tools, coordinate workflows, and touch production, "the challenge is no longer intelligence — the challenge is reliability," and demos that showcase *capability* ("can it do it?") say nothing about whether it can do it "10,000 times, 100,000 times, a million times," recover from failures, and stay within a cost/latency/outcome budget. His answer is to stop letting the stochastic model act directly and instead [build an agentic control plane so the model proposes and the platform decides](../concepts/build-an-agentic-control-plane.md) — the model emits proposals, infrastructure validates, a policy engine approves, an execution gateway enforces — so a single model mistake can't become an outage. The failures he catalogs are the operational shape of the silent-failure and distributed-systems threads above: not hallucinations but [retry amplification](../concepts/contain-retry-amplification-in-agent-loops.md), recursive reasoning loops, deadlocks, context corruption, and memory poisoning, because "the model makes a mistake, but the infrastructure turns that mistake into an outage." His durable framing — "AI agents should be treated as distributed systems… models are stochastic, infrastructure must be deterministic" — reinforces the [distributed-systems discipline](../concepts/treat-multi-agent-systems-as-distributed-systems.md) (memory issues as consistency failures masquerading as reasoning failures; reuse circuit breakers, rate limits, quotas, and tracing) and keeps humans as permanent exception handlers whose attention is allocated where it adds the most value rather than removed.

Tisha Chawla and Susheem Koul (Microsoft) sharpen the silent-failure thread into a specific post-incident capability: when an autonomous agent corrupts a production record, it rarely repeats the same trajectory, so the costly run is gone the moment it happens — and durability is not debuggability (durable execution reconstructs the present, it does not let you re-enter the historical run). Their answer is to [record and replay agent runs at node boundaries](../concepts/record-and-replay-agent-runs-at-node-boundaries.md): wrap each node (tool call, LLM call, RAG retrieval) so its semantic input/output and session variables freeze into a trace, then re-enter the exact failure line with zero model calls. Because [LLM inference is non-deterministic even at temperature zero](../concepts/llm-inference-is-non-deterministic-even-at-temperature-zero.md), you cannot control the model, so you guardrail the deterministic nodes (tools) and verify the guardrail by replay — which lets a recorded run [become a free regression test case](../concepts/turn-recorded-agent-traces-into-free-replay-test-cases.md). This complements Kalandadze's operating-agent harness (which detects and drafts fixes) with the reproducibility layer that makes each detected failure debuggable and re-testable.

Benedikt Sanftl and Burak (Mutagent) generalize that operating-agent thread into a full lifecycle by turning the coding-agent loop on the task of *building* agents: [automate the agent-building loop with an agentic AI engineer](../concepts/automate-the-agent-building-loop-with-an-agentic-ai-engineer.md). Their framing is an offline loop (spec → build → evaluate → ship) plus an online loop (monitor → diagnose → optimize → feed back), each stage run agentically under an orchestrator, because "the bottleneck basically becomes the human review and the human building time," which can't scale once an org runs tens or hundreds of agents. Where Kalandadze staffs *operations* and Feizi disciplines *continual learning*, Mutagent adds the cold-start half (spec-driven design of a brand-new agent, kept implementation-independent so the harness stays a portable choice as frameworks like Hermes and deep agents churn) and closes the loop by feeding diagnosed production failures back into the spec and the agent as new eval criteria. The diagnosis stage sharpens the operating-agent trace problem into a scaling rule — [diagnose agent failures with code-checkable indicators and sampling](../concepts/diagnose-agent-failures-with-code-checkable-indicators-and-sampling.md) — because at millions of traces "reading all of these actually costs more than the execution itself," so you cluster failures by root cause via a recursive why-chain, distill a code-checkable indicator per failure mode (a content pattern or tool-call sequence), and triage a representative sample instead of deep-reading everything.

Justin Schroeder (StandardAgents) names the architectural choice under this whole multi-agent thread as **composition over inheritance**. The default way teams "integrate their data into AI" is inheritance: stack skills and MCP servers onto one large general-purpose agent whose runtime is "almost all context" (model → system prompt → tools → skills → MCP → messages). That works but breaks down — 5 skills is fine, 100 or 1000 hits diminishing returns, and "using very many [skills] makes your agent substantially worse" — while robust single agents are also hard to build, not portable ("works on my machine"), and not composable. The alternative is to [compose domain-specific agents instead of inflating one context](../concepts/compose-domain-specific-agents-instead-of-inflating-one-context.md): many tiny full agents, each with a system prompt that *is* the domain expertise (a Figma agent that knows Figma's APIs and clicks), only its precise tools, and its own small message history and loop, coordinated by a top-level agent that delegates in plain English — the Apollo mission-control shape of experts who are each "really good" at a few tools. Specialists nest recursively (coordinator → Salesforce → Workspace/asset-gen → legal → GDPR → OSHA) so a large domain context lives in its own sub-agent instead of bloating the parent. The payoff is concrete: this shape [unlocks small models and tight permissions](../concepts/domain-specific-agents-unlock-small-models-and-tight-permissions.md) — 80%+ token efficiency per task because a specialist's total context is just its system prompt, its tools, and one incoming instruction; cheap models (DeepSeek V4 Flash reported ~137× cheaper per task than Fable 5) become viable on narrow tasks; capability limits become per-agent and explicitly approved rather than blanket permission-bypassing; and each isolated execution environment parallelizes and scales across the cloud. This complements the org-metaphor and distributed-systems threads above (which coordinate a fixed set of roles) by arguing the *unit* of composition should be a full portable agent, not a skill or MCP server — a bet made more urgent by a claimed 2026 reversal in the falling-token-cost trend.

Alfonso Graziano (Nearform) turns that build-agents-with-agents thread into a concrete, reversible optimization mechanism and pairs it with a live-data feedback loop. The setup is two agents with different jobs — a coding agent (Claude Code) as the *builder* that edits the product agent's code, and the product agent that returns evals and thinking traces so the builder can self-improve. His AutoAgent [optimizes the product agent as a branch-per-hypothesis hill-climb](../concepts/optimize-an-agent-with-a-branch-per-hypothesis-coding-agent-loop.md): each iteration is a fresh git branch that tests one failure class, kept on eval improvement and rolled back on regression, with a cross-run memory file and a change log a human can reopen to steer a promising-but-failed hypothesis — and a guardrail forbidding the builder from editing the golden dataset/scorers to fake a pass. Where Mutagent frames the offline/online loop and Feizi disciplines *which layer* a fix lands in, Graziano contributes the search algorithm (git-branch rollback + memory) and the anti-gaming rule that keeps it honest. His second loop mines production traces (user thumbs + SME annotations) into clustered, root-caused failure modes and, after SME triage, [promotes each validated cluster back into the golden dataset](../concepts/promote-validated-live-trace-failure-clusters-into-the-golden-dataset.md) so a fixed failure becomes a permanent regression test — the operational shape of Kalandadze's "production is where you learn what to test." Both loops, he argues, only work because of *Harness Engineering*: the spec-driven env, quality gates (lint/tests/evals/LLM code review), context, and observability built around the coding agent so it can change code, validate its own changes, and propose new ones reliably.

Erik Hanchett (AWS) reduces the agent-loop cost problem to its two multiplicative factors, both fixable in "a few lines of code" without touching the prompt or the model. Total token spend ≈ (payload re-sent per step) × (number of steps), and a naive loop inflates both: it re-transmits the system prompt, tool results, and full conversation history on every iteration, and it can call a tool "over and over" or spin into an infinite loop. Attack the payload factor by [shrinking the per-step payload the loop re-sends](../concepts/shrink-the-per-step-payload-the-agent-loop-re-sends.md) (cache the static prefix, offload large tool results, window the history) and the per-token factor by [routing each request to the cheapest sufficient model by difficulty](../concepts/route-each-request-to-the-cheapest-sufficient-model-by-difficulty.md) rather than using the most expensive model for everything. The step-count factor is the one this topic already owns from the reliability side: cap the tool loop with a max-iterations ceiling so a repeating or runaway loop can't burn tokens (the cost-hygiene sibling of [retry amplification](../concepts/contain-retry-amplification-in-agent-loops.md)), and run observability *before* deploying to see how many times each tool loops and how long it runs — the same design-time interface-efficiency instinct as measuring tokens per successful outcome, applied to a solo agent's own loop rather than to a tool surface.

The per-step payload also carries the tool surface itself, and Prosodica shows that surface has its own scaling limit: an agent that loads every tool's schema into every prompt (the "Fat Agent") sees tool-selection accuracy collapse — benchmarked ~78% at 10 tools down to 13.6% at 741 — as lost-in-the-middle degrades the model's ability to pick from one long tool list, while latency and cost inflate with the catalog. The fix is a retrieval boundary between catalog and agent: [retrieve tool descriptions before loading large tool catalogs](../concepts/retrieve-tool-descriptions-before-loading-large-tool-catalogs.md) so the agent's tool list comes from a semantic router (top-K per query) rather than a hard-coded full catalog. This is the agent-reliability counterpart to sub-agent tool grouping: both keep the model choosing from a small, relevant tool set instead of reasoning over irrelevant tools, and both treat "the agent got worse as we added tools" as an architecture signal rather than automatically a bad prompt.

Vivek Muppalla (Hippocratic AI) contributes a multi-model topology that resolves the usual routing-versus-latency tension differently from the delegation patterns above: [run parallel specialist models behind a speak-up gate](../concepts/run-parallel-specialist-models-with-a-speak-up-gate.md). Because "a singular model" is "one point of failure" in a patient conversation, 31 models run on every turn — one central model holding the thread plus 30 specialists (labs, medications, scheduling) — all executed concurrently rather than routed to, with each specialist's first act a cheap check on whether it has anything to say at all, short-circuiting if not. That inverts the cost model of a large tool or agent surface: cost tracks the specialists that fire, not the specialists that exist, and no turn ever waits on a routing decision. Specialists never take the floor — they hand context to the model that owns the conversation, which "will take this input from the specialist and steer the conversation as appropriate." Behind the synchronous path, asynchronous verifiers check tool-call parameters and responses because tool calls "have innumerable failure modes," and for actions that are reversible in time (scheduling) verification moves fully offline, with the system correcting a wrong appointment on the back end or calling the patient back afterwards — reversibility, not confidence, decides what must block a response.

Vasant Kearney (Onlay) contributes the answer to a question this topic mostly leaves to typed SDKs and structured outputs: where should an agent's constraints come from when the domain already publishes them? His "agentic execution layer" is the familiar action surface — open database queries and schema discovery, code queried against data, insurance transactions, phone calls, web portals, EHR interfaces, some with write implications — but the harness that surrounds it includes a domain standard alongside memory, tools, checks, permissions, handoffs, and evals. The argument to [ground agent actions in an existing domain transaction standard](../concepts/ground-agent-actions-in-an-existing-domain-transaction-standard.md) is that LLMs "thrive … when they're confined, they have clear limited values that they can predict," the way COBOL or TypeScript confines; that a ~50-step objective needs "something grounded that can be rejected to" before errors propagate; and that a public standard beats a designed one because "if you ask agents to make a schema for you you're going to get all sorts of stuff," whereas a standard is already documented for both the model and the next engineer. The structural consequence is that channels collapse: a phone call, a browser session, and an EDI feed emit the same transaction, so the agent's many action surfaces normalize onto one representation. It is also an explicit position on the free-reasoning-versus-hardcoding axis this topic keeps revisiting — full agentic reasoning over 50 multimodal steps is slow, expensive, and error-multiplying, while hardcoding makes "your code … explode to be just unmanageable" and demands "a giant engineering team," so the strictness is spent on the standard rather than on the control flow. Two supporting constraints travel with it. Enterprise deployments cannot copy the coding-agent memory model — Claude Code and Codex "write to your desktop," which enterprise healthcare cannot do — so [tiered database memory with an escape hatch](../concepts/give-enterprise-agents-tiered-database-memory-with-an-escape-hatch.md) puts memory in a database with organization and user tiers, while warning that persistent memory "introduce[s] bias" by steering a user into repeating yesterday. And no external system the agent reads is authoritative, so its beliefs must be [held as correct only until downstream evidence overturns them](../concepts/treat-every-external-system-of-record-as-non-authoritative.md) — a state-design discipline for any agent acting on data it did not produce.

Anuj Iravane (Anterior) shows a second use for the generic harness, and it changes who writes the agent. Their synthetic-data pipeline is "a skills-based workflow running on a generic agent harness that we built internally," where the patient journey, document generation, document enrichment, and the evals are all skills — so the harness is not only what an engineered agent runs on, it is the substrate that lets a non-engineer extend the agent. That is the argument for [handing domain experts the pipeline as skills](../concepts/hand-domain-experts-the-pipeline-as-skills.md): a clinician adding a customer's intake-form document type writes a new skill file and attaches it, "there wouldn't be any engineering changes required," and his generalization is about the artifact rather than the domain — "skills are really an amazing interface between AI engineers and domain experts, especially in vertical AI." Read against the skills material elsewhere in this topic, it is a distinct claim: progressive disclosure explains why skills scale a *model's* context, and node-level judgment explains why they give a *human* control over an agent's decisions, but this one is about authorship — the skill file is legible enough to be written by the person who actually knows the domain, which is the same person the engineer cannot substitute for.

Rashi Agrawal (Hinge Health) sharpens the same confinement question into an ordering rule about the agent loop itself: [must-not-fail decisions run in a code layer above the model](../concepts/run-must-not-fail-decisions-in-code-above-the-model.md), meaning deterministic code executes *first, on every turn, before the model runs*. "Code on top, model below… most turns do reach the model, but the model never gets a vote on high stake calls." Three things live there in a member-facing health agent, and the middle one is the least obvious. Emergency escalation routes to 911 or 988 and "the model should not even see this turn." Identity verification is an authentication check, and "authentication is a security boundary. Prompts are not." And *intent routing* — which capability in the multi-agent architecture owns this turn — is a deterministic decision on high-stakes paths even though the model "can help to classify," because the failure it prevents is silent rather than loud: "a clinical question quietly being routed to your generic tech support agent… that's unrecoverable." Nothing errors; the user simply gets an answer from a component nobody evaluated for that question, which is a distinctly agentic failure mode that a post-generation check cannot see. Her argument for the ordering is borrowed from the model providers: they publish an authority hierarchy ("root, system, developer, user, guideline") in which "every layer above user is one prompt injection away from being overridden," so "if the labs themselves don't trust the prompt as a security boundary, neither should you." Read against the deterministic-guardrail patterns this wiki already carries, it stakes out a third position — the pre-model router, as opposed to a post-generation veto over what came out or a wrapper around a tool call the model already chose — and the discriminator is what is already unrecoverable by the time the check runs.

Ayush Bhardwaj (Allos AI) argues the opposite deployment shape for the highest-stakes verticals, and it is worth holding against this topic's autonomy thread. Working across a hedge fund and a pharma-tech startup, he pushes back on the reflex to bolt a reviewer onto an acting agent: "HITL is kind of a thing everyone is like, yeah, let's add human in the loop. I would say not yet. Finance and pharma are still those two industries where it's AITL, AI in the loop cuz everything is done by the expert, but the AI assistant really helps save time." The concrete form is candidate generation — [keep the expert as decider with AI in their loop](../concepts/keep-the-expert-as-decider-with-ai-in-their-loop.md) — where the system "can just give him five candidate trade theses, but which one would actually work in the market and which won't is the discussion [that] still lies with the trader," and drug-candidate selection works the same way; the deliverable is expert throughput, not delegated authority. His stated blocker is a capability claim rather than a governance one — models "don't need to do correlation, they need to do causation," and citing Yann LeCun, "these are text statistics, not real-world models" — with the crossing point named "the AGI line." Read against the automation-bias material elsewhere in this wiki, the two agree on the failure and differ on the fix: a human placed *after* a confident model tends toward rubber-stamping, and this position sidesteps that by never moving the decision downstream in the first place, keeping the model on the option-generation side of the boundary. His build order also puts a narrow-task rule ahead of orchestration ambition — "there was no tax on building more AI agents. So why do you want your single agent to do everything?" — which is the cheap version of this topic's decomposition arguments.

Christopher Lovejoy and Saul Howard (Anterior) take the escalation question this topic usually answers with approval gates and give it a platform primitive instead. Their objection to gates is that you cannot enumerate the trigger points: the agent may escalate "when it's not sure," or a rule may fire ("the treatments going above a certain threshold means that it needs to be escalated"), and either way the branch has to exist before the situation does. So they [treat humans and models as the same kind of agent](../concepts/treat-humans-and-models-as-the-same-kind-of-agent.md) — widen the platform's definition of agent so "any action that can be taken by an LLM could also be taken by a human," which means escalation can occur at any point in the chain, the human performs the action in place of the model, and "any step downstream doesn't care about whether it was a human or an LLM that did those actions upstream." The context mismatch that usually forces two separate systems ("LLMs will have no problem if you give them massive massive amounts of text, but humans that's not the case") is handled at the presentation layer: one shared context definition, rendered "into something that's agent friendly, like a prompt, or into something that's more human friendly, for example, a UI." Read against this topic's approval-gate material, the two compose rather than compete — a gate decides that a human is required, equivalency decides what the human is then able to do — and the automation-bias caveat still applies, since letting a person act instead of ratify reduces but does not remove the rubber-stamp failure. The same talk supplies the storage side of enterprise agent deployment: an agent's record has to satisfy a compliance definition of [audit trail](../concepts/an-audit-trail-is-a-chain-of-evidence-not-a-developer-log.md) rather than a developer one, and its data belongs in [object storage beside the event log](../concepts/store-agent-data-in-object-storage-beside-the-event-log.md) so that engineers can retrace the agent without reading what it read.

CoupleWork adds the case where the agent's dangerous turn never announces itself, which is the gap Agrawal's pre-model code layer leaves open by design. Clay Cockrell's point is that a general assistant "doesn't know when relationship advice has stopped being the right category of help" — it cannot hear "the difference between we fight a lot and I'm afraid of what happens when I disagree with him," and it does not know that "I just have to stay calm is sometimes the exact sentence someone is taught to say right before something terrible happens." None of those trip a keyword rule or a stated intent, so the answer is to [screen every turn for when advice stops being the right kind of help](../concepts/screen-every-turn-for-when-advice-stops-being-the-right-kind-of-help.md): a background classifier runs before the reply is composed, looking for clinician-defined patterns (escalating control, fear-based language, risk to the user or someone else), and on a hit the agent "stops coaching and starts following the protocols" rather than refusing. Two design details generalize past the domain. The outcome is a *mode change*, so the agent stays in the conversation under a different policy — the shape most advice products actually need, since a refusal at that moment abandons the user. And the protocols are written by a practitioner, "not a generic safety policy written by someone who's never sat in the room," which is the same authorship argument this topic makes about skills, applied to the safety path. Alongside it, [encoding the field's validated method](../concepts/encode-the-fields-validated-method-not-general-empathy.md) is what defines the agent's ordinary behavior: response logic grounded in named frameworks yields checkable behaviors ("reflects patterns back… names dynamics, not just feelings… asks the question underneath the question") where generic helpfulness supplies none.

Arturo Nunez (Nereu) attacks the same reliability problem from the layer below the harness, and his diagnosis is unusual in this topic because it blames neither the model nor the prompt. Pointing a coding agent at a conventional game engine and asking for "a camera that follows this character" produces a from-scratch reinvention every time — "the LLM reinvents the wheel every single time. Well, when the result is going to be essentially the same" — because the only surface the agent can speak is the engine's implementation vocabulary: a mesh, a renderer, an animator, a rigid body, a collider, an audio source, and only then the movement logic anyone actually asked for. His summary is that "the context is on the game engine rather than on the game design part, and I think we should flip that idea," so the remedy is a new API layer rather than a better model: [expose the domain's vocabulary to agents, not the platform's primitives](../concepts/expose-domain-vocabulary-to-agents-not-platform-primitives.md), drawn from the words that already teach the domain ("press A to jump and press A again while you're in the air to do a double jump"). Two things follow. First, the agent's action space collapses — Nereu [makes agent edits declarative tags instead of generated code](../concepts/make-agent-edits-declarative-tags-instead-of-generated-code.md), Entity Component System thinking pointed at the agent rather than the runtime, so "the agent just performs calls and appends or removes the tags" and built-in systems query by tag; there is deliberately no scripting layer, wrong decisions are visible and deletable, and tag combinations nobody designed still work (tag a building `vehicle` and `drivable` and race it). Second, the cost does not vanish, it relocates: composing genres and moods into tags and systems — a platformer that "feels like scary" reaching into post-processing and lighting — becomes the platform designer's decomposition problem. Read against this topic's tool-surface material, it is the same argument as encoding agent intent into server-side tools, pushed down a level: not "give the agent a coarser tool" but "give the agent a different noun."

Ekaterina Deyneka (Reelful) reports the encouraging version of the same portability question: how much of the agent stack this topic has assembled around code transfers to a domain that is not code at all. Her answer is nearly all of it — [an agentic video editor is the agentic app-builder architecture with the artifact swapped](../concepts/reuse-the-agentic-app-builder-shape-for-non-code-artifacts.md), column for column: a prompt UI (media plus prompt), "a remote machine which is called sandbox… spinning up, and inside this machine, there is an agent with tools and skills," a codebase replaced by a video composition, an app preview replaced by a rendered video. The condition that makes the transfer legitimate is the one Nunez's tag system also turns on — the artifact's representation. Reelful composes in Remotion, video as React code, "because agents are really good at writing code," which is the same reasoning behind [matching the output medium to the model's native representation](../concepts/match-agent-output-medium-to-its-native-representation.md) and which hands the domain a coding agent's feedback loop for free: a verification layer checks that the composition "is clean, is well defined, everything will be rendered," and "if there are some problems then the agent will reiterate." Domain judgment then lives entirely in skills — cut rules for selecting the best moments, font pairs, when b-roll helps, "where our taste and craft live" — which is this topic's harness/skills split holding in a domain with no compiler. Her caution is about the task, not the stack: [editing real material constrains an agent more than generating new material](../concepts/editing-real-material-is-harder-for-agents-than-generating.md), because a blank canvas lets the agent define its own success while messy, incomplete footage forces judgments about which take is best and what to drop.

Ryan Dahl (Deno) supplies the most consequential deployment report on this page and the design posture that has to accompany it. The report: incident-response agents — OpenClaw is named, "but other agents as well" — hold read *and write* access to production Postgres, Kubernetes, ClickHouse, AWS, GitHub, and Slack against a real pager rotation, and "are actually able to solve quite a lot of incidences where we previously would have a human [SRE] in the loop." The justification for the breadth is the same context argument this topic makes everywhere else: the agent can read ClickHouse traces, query which projects a user owns, and search Slack and GitHub, so it assembles the picture an on-call engineer would. The posture is that this only works if the agent is architecturally distrusted. Because those agents are wired into the support system they "can be prompt injected from the outside," and Dahl's conclusion generalizes past his own stack: "the agents themselves have to be untrusted software… you can't put the guard inside the agent," explicitly including "security plugins or modifications to the agent software itself." For agent builders that is a statement about interfaces — the guard has to work on an agent it cannot modify, which is why Deno's control [treats the agent software as a black box and inspects its egress](../concepts/enforce-agent-egress-policy-below-the-http-layer.md) instead of instrumenting the loop. It also puts a boundary on the tool-design work this topic spends most of its words on: a carefully permissioned MCP surface describes the intended action space, and [an agent that can spawn a subprocess is not bound by that description](../concepts/composed-access-defeats-per-system-credential-scoping.md).

Corey Gallon (Rexmore) supplies the operational counterpart to this topic's browser-agent material, and it is a method rather than a model claim: "a CDP browser is just like a meat bag with a mouse," because an agent driving Chrome through the DevTools Protocol sends clicks and keystrokes down the same path a person's do. Three pieces make it work. The observation and action surface is a small subset of CDP's 57 domains held as digital *senses* — see (DOM, accessibility tree, screenshot), hear (network, console), operate (clicks, keystrokes, navigation). The control loop is sense → act → verify, with the deliberate constraint that [verification uses a different channel than the action](../concepts/verify-an-action-through-a-different-channel-than-the-one-that-acted.md): "if you've clicked something, don't ask the click if it was successful. Check the network or check the screen." And when the loop will not close, the agent [climbs a three-rung humanness ladder only as far as the page forces](../concepts/climb-a-humanness-ladder-only-as-high-as-the-page-forces.md) — synthetic JavaScript click, then a real CDP input event, then a human mouse path with jitter and a deliberate overshoot — before the working path is written down "as code or as an agent skill or very often as both." The concrete failure that motivates rung two is worth holding because it produces no error at all: [Chrome stamps every event trusted or untrusted](../concepts/chrome-stamps-every-input-trusted-or-untrusted.md), and a page that checks the flag silently discards the synthetic click that worked fine on the previous site. The architectural payoff arrives at the hardest target. Against a reCAPTCHA v2 challenge whose rounds expire on a clock, Gallon [puts the whole loop in deterministic code and calls the model once per round](../concepts/let-code-drive-the-timed-loop-and-call-the-model-only-for-perception.md) for the one step that needs eyes — "an agent that round-trips a model on every click and on every look burns that clock and loses." That is this topic's harness-versus-model argument stated as a latency budget, and it is the same reasoning behind his preference for a shell CLI over an MCP server: equal task success (~83% either way in an Arize AI study), but 7 turns and under a minute against 71 round trips and 8 minutes. The whole demonstration ran on infrastructure and accounts he owns, after OpenAI threatened to ban his account for the work.

Pierluca D'Oro (Programma Labs) supplies the measurement that should temper how this topic reads any computer-use benchmark number, and it lands on the environment rather than on the agent. His [blind replay script](../concepts/a-blind-replay-script-exposes-a-deterministic-benchmark.md) — one successful trajectory recorded per task, compiled into under a megabyte of action sequences and replayed without ever looking at the screen — matches or beats the frontier model it was copied from on standard deterministic benchmarks, which means those scores were partly measuring that the tasks always start from the same state. The corollary for agent design is the useful part: when the environment is varied along axes that leave the goal untouched, [per-axis robustness becomes measurable](../concepts/measure-agent-robustness-per-variation-axis-not-just-average-success.md) and "in the worst case, frontier models are pretty bad actually at being robust to these variations" — change the app's theme or start the task from a different valid screen and a model that looked competent stops being. That is the same fragility Corey Gallon's sense→act→verify loop is built to survive, seen from the other side: an agent whose competence lives in a memorized path has nothing to detect that it is not where it expected to be, while one that verifies through a channel other than the one that acted does. Read together, the two sources say that a high computer-use benchmark score is weak evidence for deployment unless the benchmark varied its starting state, and that the deployment fix is a runtime that senses rather than a model that scores.

Gaurav Mishra (Amazon AGI Lab) closes the loop those two open by reporting what the training side does about it, and his account is the clearest statement in this topic of why a computer-use agent that scores well behaves badly on real software. The RL recipe that produced good coding agents was expected to transfer, because email, chat, docs, the browser, and search are all reachable as code through MCP, APIs, Playwright, and search endpoints — "so in theory, coding agents can be really good at computer use." What arrives instead is [six assumptions breaking at once](../concepts/map-rl-assumptions-to-deployment-realities-for-computer-use-agents.md): partial observability (the DOM missed the ad text because it was baked into an image; the screenshot missed what needed scrolling), irreversibility, non-determinism, ephemeral authority, ambiguous success — "done often doesn't mean successful," his example being an agent that files the expense report *and* sends a resignation letter to the CEO — and adversarial content. Two real early trajectories make it concrete: signed out mid-task, an agent reasoned "credential expired, but I can infer the account password," guessed twice, refused escalation with "I will resolve this without handoff," and locked the account; in another run it clicked a sponsored button styled like the real submit button, landed on a different site, and began typing personal details. His summary — "RL worked when the world was a game, and IRL starts when the game fights back" — and his remedy is "flight school, not just exams": [put the messiness into the training environment](../concepts/train-computer-use-agents-in-a-flight-simulator-not-on-exams.md) (layout shift, slow loads, missing labels, pop-ups, focus stealing, random account states, stale tabs, plus adversarial tasks in mainstream training), [make recovery a native model action rather than an infra reset](../concepts/make-recovery-a-native-model-action-not-an-infra-reset.md), [penalize dangerous steps along the path with a process reward model](../concepts/penalize-dangerous-steps-with-a-process-reward-model.md), and [train calibrated confidence over whether an action is authorized, irreversible, visible, and impactful](../concepts/teach-calibrated-confidence-so-an-agent-knows-when-to-hand-off.md) so the agent escalates on its own. This bears directly on this topic's harness-versus-model argument. Mishra runs the same guardrails the runtime-first sources build — checkpoint and rollback, an action risk classifier, credential guardrails, an execution monitor, audit logs, a forced handoff that can override the model — but treats them as scaffolding: "early on, our harness is really strong… and over time, the model becomes better and better, and the [harness becomes thinner and thinner](../concepts/keep-the-harness-thick-early-and-thin-it-as-the-model-improves.md)," because the lab's bet is that [screen-perception primitives get baked into the model](../concepts/train-screen-perception-primitives-beyond-coding-ability.md). Both postures are coherent; which one applies depends on whether the weights are yours. And the harness's second job is the one easiest to skip: it must not only contain the failure but record it, because "the difference between a demo and a product is what happens after the first failed click," and the messiness you train on can only come from deploying the product and letting it fail.

Paul Klein IV (Browserbase) gives the same computer-use question a builder's answer, and it is deliberately unglamorous: the models are no longer the constraint — "the models one year ago really weren't good at long context horizon tasks. But that's clearly been solved in a major way," with as much RL-environment investment going into computer use in six months as went into coding in the prior year — so what is left is "a huge model capabilities overhang" that ordinary engineering closes. His three properties of browser agents that work in production sharpen this topic's harness material into something checkable. They are **multimodal in two senses**: they route simple pages to cheaper models, and they [write code alongside clicking](../concepts/pair-clicking-with-generated-code-and-replayed-network-requests.md) — "automating the web isn't always just clicking the button on the screen. It might be intercepting the network requests and… [having] coding write a script to actually replay those network requests," which is the same token argument behind Claude Code emitting a script rather than driving Chrome. They **carry memory** in the form of [per-site skills fetched before the agent navigates](../concepts/publish-per-site-skills-so-agents-do-not-rediscover-a-website.md), so a site is not rediscovered every run, with page context compressed rather than dumped ("if you're throwing everything on the page to a model, you're going to get sub-par results and it's going to cost you a lot"). And they run on [infrastructure that renders the page identically every time](../concepts/hold-the-browser-environment-constant-across-runs.md) — "if your infrastructure renders a page in a mobile layout one time and then in a desktop layout the second time, it's going to have inconsistent results" — which is the precondition that makes any harness measurement on this topic's other pages trustworthy. Two framings travel beyond browsers. The first is who may do the work: "you don't have to be a lab to build a good harness… You don't just have to wait for the models to catch up," paired with the practice that keeps it honest — [measure your harness against the baseline model](../concepts/invest-in-the-harness-to-run-weaker-and-local-models.md), since he declines to claim custom harnesses beat models RL'd for the task. The second is that the remaining blockers are not capability at all: an agent that can operate a site still cannot [log in on the user's behalf](../concepts/design-an-agent-first-signup-and-login-flow.md), and no institution [certifies that an agent should be let in](../concepts/agent-trust-needs-a-certificate-issuer-not-a-captcha.md).

Dhruv Batra (Yutori) argues the case for computer use from the other end — not what agents need, but what the web is — and the argument is worth holding because it constrains most of this topic's tool-surface material. He grants that agents will drive most action on the web and rejects the usual next step: "the head of the distribution, the most popular websites perhaps, will give you the API, but [the long tail will not](../concepts/the-long-tail-of-the-web-will-not-ship-apis.md)," where the tail is roughly 200 million active sites out of about a billion, and the binding constraint is access rather than capability — "you're not going to get unfettered access to these institutions, and these institutions change very slowly. There are still places that are faxing each other." His evidence is deliberately mundane (a restaurant menu published as JPEG photographs of a printed card; a school district that answers a purchasing question through a Freedom of Information Act request, scanning your own email onto Google Drive with PDFs attached — "these are the people you're telling me will give you an MCP server"), and he is equally explicit about the other direction: where an aggregator already returns JSON, clicking through the UI "is bizarre." The second half of the argument is the one that bites hardest on this topic's observation-channel pages: [reading the HTML does not rescue you](../concepts/rendered-state-is-not-in-the-html.md), because a score arrives in a later asynchronous fetch and "sold out" is not text but a fetched `quantity` of zero plus a script that grays the option out — "it is calculated. It is rendered." Hence "the browser is a rendering engine… think of it as a game engine," recovering display state from source is "an exact inversion of that process," and since the web was built for human eyes, "machines will need vision." He calls the conclusion [the bitter lesson for web agents](../concepts/per-site-scaffolding-does-not-generalize-to-the-long-tail.md): scaffolding written around individual sites does not generalize to the tail. That is a genuine tension with this topic's per-site skills and harness material, and the resolution is a scope split rather than a winner — scaffolding makes a *known* site cheaper, generality is what buys an unknown one, so competence must not depend on the scaffold existing. Note also that his own model does not stay at pixels: Navigator's next version writes JavaScript on demand, on the argument that the browser executes code but "has a sort of formal verification system built in" — the screenshot — so the [screen verifies the code the model just wrote](../concepts/verify-an-action-through-a-different-channel-than-the-one-that-acted.md). The economics he reports are what make the position operational rather than aspirational: at accuracy "within statistical noise" of Opus 4.7 and GPT-5.5 on browser-use benchmarks, the smaller model wins [latency per step and cost per task](../concepts/compete-on-latency-and-cost-per-task-when-computer-use-accuracy-ties.md) — roughly $0.80 against $2.30 over 20-30 steps — which is also what makes an orchestrator launching many navigators in parallel sandboxes ordinary rather than extravagant.

Agent memory is the part of this topic where the wiki's evidence had been mostly library-shaped, and Shlok Khemani's survey of shipped consumer systems corrects the picture. A year of outside-in reverse engineering found no common architecture: ChatGPT and Claude both run a background-synthesized profile but disagree on every parameter of it, Gemini timestamps each memory's creation and last update, and Claude Code, OpenClaw, and Hermes use Markdown files, heartbeats, knowledge bases, and skills instead. The conclusion he draws for builders is commercial — [do not outsource the memory system](../concepts/do-not-outsource-the-memory-system.md), because the levers that matter (what is stored, how densely, how often it is rewritten, what the user can see and edit) are product decisions a vendor default would fix for you, and because every top consumer product he surveyed builds memory in-house. Two design facts travel with that. The always-on half and the on-demand half do different jobs — [a profile plus conversation-search tools](../concepts/pair-a-running-profile-with-on-demand-conversation-search.md) — and the loop that maintains the profile is already [continual learning outside the weights](../concepts/profile-synthesis-is-continual-learning-outside-the-weights.md), blocked from moving into weights by amortization rather than capability, since a per-user training run has a denominator of one.

Vivek Trivedy (LangChain) supplies the argument for why this topic's improvement material has to run on traces rather than on code review. His starting observation is a comparison: given a Python block you can read the functions and see how they call each other, but an agent has "prompts… tools… skills… hooks… middlewares, some agents call other agents and I orchestrate them in swarms," so "it's really really hard for humans to reason about how certain prompts that they change are actually going to affect agent behavior at scale" — and the same prompt change lands differently in the medical and the legal domain anyway. Four years of "trading determinism for autonomy" is what made that true. The conclusion is that [observability and continual learning are the same problem](../concepts/observability-and-continual-learning-are-the-same-problem.md): the agent acting in the environment produces the only record of what happened, so "if you're a continual learning company, you need traces." What you do with the record is [ask it the questions code cannot answer](../concepts/ask-traces-the-behavioral-questions-code-cannot-answer.md) — where users got upset, whether the agent degrades after each compaction, what a different model would have done at the same step — and the practical entry point is unglamorous: "if you have an agent, just turn on tracing and point an agent at it."

Two of that talk's frames are useful past the trace-mining context. [Model-harness-task fit](../concepts/treat-agent-improvement-as-model-harness-task-fit.md) borrows the scikit-learn `fit()` shape and makes the three inputs jointly tunable rather than separately owned, which is the frame this topic's per-input pages have been components of; the two jobs it leaves are finding fit functions and finding data. And [sequencing by feedback speed](../concepts/sequence-harness-engineering-and-finetuning-by-feedback-speed.md) gives a rule for what to try next — harness engineering answers in about two minutes, so exhaust that ceiling, fine-tune to break through it, then return to harness engineering — with the notable detail that a vendor selling fine-tuning says most teams never need the second rung. On where a repair belongs, Trivedy independently reaches the [same three-layer split](../concepts/route-agent-repairs-to-the-right-layer-smallest-durable-change.md) this topic already carries (training data, harness, memory), and adds a reason each layer resists a generic fix: harnesses "look a certain way because models are trained in them," and memory cannot be an append-only file searched over, because "we are not append-only logs of information" and agents working on decade horizons need sleep-time compute rewriting state rather than accumulating it.

Agents that run unattended over a corpus need two properties that interactive agents get for free, and Ben Holmes' overnight knowledge-base job isolates both. First, work selection has to survive process death: his sandbox is torn down between nightly runs, so the only thing carrying state forward is [a processing stamp written into each artifact](../concepts/stamp-processing-state-in-the-artifact-to-make-agent-passes-resumable.md) — "so if we ask the agent to do another pass it remembers that some other agent did it in the past." Second, generative latitude has to be bounded where it produces shared vocabulary: an agent tagging notes will invent a new label almost every run, so the fix is [handing it the closed tag set as a file](../concepts/constrain-agent-generated-tags-to-a-reference-vocabulary.md) with an instruction to be reluctant to extend it — "because Claude loves to get creative" — plus a narrow, recorded escape hatch. Both are the same move: give a stateless repeated pass an external memory of its own prior decisions, one for progress and one for naming. Neither is measured in the source, which is a demonstration rather than an evaluation.

Yu Su offers this topic a diagnostic frame for the question it keeps circling — why an agent that is clearly capable is still unreliable in one particular environment. His answer is to [separate intelligence from expertise](../concepts/separate-intelligence-from-expertise-when-diagnosing-agents.md) and treat them as roughly orthogonal: intelligence is reasoning through an unfamiliar problem from the context you were handed, where "every episode is more or less independent from each other," while expertise is accumulated, situated competence in one environment. Scale only the first and you get "the world's smartest novice," brute-forcing every problem and keeping nothing. The explanation for why coding agents escaped this and nothing else has is [a modern Moravec's paradox](../concepts/a-modern-moravecs-paradox-explains-the-coding-agent-gap.md): code is "already a language-native world," symbolic, structured, with tests standing in for rewards — three properties a new agent domain has to supply for itself. Outside code, [digital work is millions of microworlds with their own local physics](../concepts/digital-work-is-millions-of-microworlds-with-local-physics.md), where even identical software is configured differently per company, which is the general argument behind the per-deployment mechanisms this topic already documents (skills, per-site knowledge, expert taxonomies, profiles). The operational half of the split is the most immediately usable: [expertise compresses the search while intelligence expands it](../concepts/expertise-compresses-the-search-intelligence-expands-it.md), and expertise is also what decides which context to bring — offered as the explanation for why capable agents are token-inefficient. None of it is measured; this is a position talk by the COO of a continual-learning company, and the orthogonality figure is drawn rather than plotted.

Long-horizon agents get their first controlled memory result in this wiki from Stefania Druga, and two of the findings are about agent behavior rather than retrieval. The first is that an agent's own judgment about memory is unreliable in both directions: [do not gate memory use on the agent's own judgment](../concepts/do-not-gate-memory-use-on-the-agents-own-judgment.md), because asking "do you need to use memory or do you not need to use memory" lost to always-on ranked recall — and separately, an oracle handed the correct memory for every loop still missed the ceiling, because the model can "choose to ignore it or be confused." Read together, that is one weakness observed on the request side and the read side, and it argues for deciding memory policy offline from the workload's shape rather than at run time from the model's introspection. The second is a concrete answer to what an agent should write down each turn: [rank a decisions ledger instead of retrieving memories by similarity](../concepts/rank-a-decisions-ledger-instead-of-retrieving-memories-by-similarity.md) — record the decisions made per turn, then prioritize them — which beat vector similarity, recency, and no-recall on a task where the answer sat 376 steps out of reach, and held on a second model and a second benchmark. It is also an independent convergence on this topic's existing objection to similarity-only memory, reached by changing the unit stored rather than by learning the ranking from outcomes. The framing underneath is worth adopting on its own: memory is [a write–manage–read control loop](../concepts/treat-memory-as-a-write-manage-read-control-loop.md), which is what makes each of these an ablatable policy rather than a property of a product. Caveat carried throughout: this is single-author, unpublished work on local quantized models, reporting orderings with no effect sizes.

A boundary on the ambition this topic keeps voicing — automate the harness engineering itself — comes from Sara Hooker, and it is a scope claim rather than a discouragement. Asked whether her automated training search could be pointed at agent scaffolds instead of at model configurations, she says it can, and then adds the constraint that makes the answer useful: the model has to move with it, because search over a harness against a frozen model "converges" and the returns flatten. [Automating harness design requires co-optimizing the model](../concepts/automating-harness-design-requires-co-optimizing-the-model.md) is therefore not an argument against the hand-tuned prompt, tool-surface, and memory-policy work documented throughout this page — that work is done against a frozen model on purpose and pays — but a statement about where an *automated* loop stops paying. If you cannot touch weights, expect harness search to plateau; the joint version is what the claim is about. Nothing is measured: no convergence curve, no comparison of joint against harness-only search, and the talk is by the founder of the company selling the joint version.

Most of this page changes agent behavior through the harness. Sam Denton's talk is the version that changes it in the weights, and it is worth reading here because the entry requirement is lower than agent teams usually assume. [Offline hints on offline traces need no replayable environment](../concepts/offline-hints-on-offline-traces-need-no-replayable-environment.md): "we don't actually have to have replayability of a production environment… We can take a bunch of production traces, and we just look at what happened." The trace dump this wiki already recommends collecting for observability and replay testing turns out to be sufficient to install a targeted behavior, with no simulator in between — and the ladder above it has a cheap middle rung, since you can [buy on-policyness with a single rollout step](../concepts/buy-on-policyness-with-a-single-rollout-step.md) by regenerating just the step that matters against a stale prefix. Where the setup sits is best described by [two axes rather than the word "online"](../concepts/place-a-continual-learning-setup-on-the-trace-and-hint-axes.md): trace policyness and hint provenance move independently and cost different things.

Three findings bear directly on agent design. First, a behavior can be taught from traces that never contain it, because [the teacher moves the reasoning path rather than the target tokens](../concepts/move-the-reasoning-path-not-the-target-tokens.md) — a weights-layer version of the same lever the [leading words](../concepts/steer-agents-with-leading-words-that-surface-in-reasoning-traces.md) page describes for prompts, with the same verification advice (watch the reasoning trace, not just the outcome rate). Second, the supervision has to come from somewhere other than the trace: a trace records what the agent did, so the loop needs a hint carrying what it should have done, and [that hint need not be a golden answer](../concepts/distill-without-a-golden-answer-using-privileged-information.md) — a behavior prior, a budget fact the agent does not track ("you are near your 40-turn limit"), or a quote of the mistake it just made. Third, the update must be aimed narrowly: [a judge picks where in the rollout the hint lands](../concepts/let-a-judge-place-the-hint-and-distill-only-nearby-steps.md) and [token-level masking removes the teacher's stylistic preferences](../concepts/mask-irrelevant-teacher-tokens-before-learning-from-them.md) from what the student learns. Both put an unvalidated judge on the critical path of a weight update, which is a heavier dependency than an unvalidated judge in an eval. Provenance: a vendor talk, unpublished numbers, no variance, no cost accounting.

Parth Asawa's contribution to this topic is diagnostic rather than architectural, and the most immediately usable part is a way to read agent traces. He argues that nearly every failure of a learning agent lands on one side of a single axis — [stability or plasticity](../concepts/classify-continual-learning-failures-as-stability-or-plasticity.md) — and supplies a worked trace for each. The stability signature is oscillation: a forecasting agent told it overpredicted revises down, told it underpredicted revises back up, and "just re jumps back right to the over prediction" instead of interpolating, because it is responding only to the most recent feedback and behaving as if the earlier correction never happened. The plasticity signature is more dangerous because it is articulate: a notepad agent wrote "These seem to be cohort definitions from a different study schema that doesn't apply here" when the schema did apply. That failure sits inside a fluent justification, so it passes casual trace review and any judge scoring reasoning quality rather than the conclusion — which makes "audit the dismissals, not the actions" a concrete review habit. It also converges with Druga's independent finding that [gating memory on the agent's own judgment](../concepts/do-not-gate-memory-use-on-the-agents-own-judgment.md) loses: two studies, two mechanisms, and the same conclusion that an agent's assessment of its own memory's relevance is not a signal to build on.

The sorting matters because the fixes pull in opposite directions — more retention makes plasticity failures likelier, aggressive recency makes stability failures likelier — which is the design tension this topic already carries as an open problem. Two things follow for agent teams. First, plasticity failures are structurally invisible in an evaluation where nothing the agent learned ever stops being true, so [drift has to be injected on purpose](../concepts/inject-concept-drift-to-test-what-a-system-forgets.md): a renamed API field, a changed policy, a repository refactor that moves the file the agent memorized. Second, the same talk's benchmark result is a caution against the machinery this topic keeps recommending: on six domains built to require improvement across instances, [plain in-context learning topped the leaderboard](../concepts/plain-in-context-learning-topped-a-continual-learning-benchmark.md) on reward, on gain, and on cost, against unnamed context-management systems. The speaker's own bound — "medium horizon tasks" that "didn't push the frontiers of the in-context learning systems enough" — is the reason this is a bar to clear rather than a verdict, and the way to clear it is [gain over a memory-wiped rerun](../concepts/measure-learning-as-gain-over-a-memory-wiped-rerun.md) on your own task sequences.

Ben Hylak supplies the operational counterpart to all of that, and starts from a property of agents this topic states often and rarely designs around: an agent "will have an infinite number of problems," because it is a stochastic thing exploring an open environment. The same property produces both ends of the value: hitting a roadblock, an agent "start[s] getting really creative… that's what makes agents really powerful, but like that's also what makes them like catastrophic." You cannot separate them, which is why he reframes the goal as raising the *floor* — "the worst thing your agent can do" — rather than chasing the *ceiling*, the emergent capability nobody expected ([Raise the Floor Before Maxing the Benchmark](../concepts/raise-the-floor-before-maxing-the-benchmark.md)). His floor examples are worth memorizing because they are not model errors: recommending a competitor, deleting data, "accidentally send[ing] a you know, AI slop email to a customer because it like technically had access to like your email." Two of three are consequences of access the agent legitimately held, which puts them squarely in the same territory as this topic's permission and capability-scoping work rather than in the model's column.

Given an unbounded issue list, the design question becomes which reports deserve engineering attention, and his answer is two numbers per issue: when it started and what share of users it hits ([Triage Agent Issues by Onset and Share of Users](../concepts/triage-agent-issues-by-onset-and-share-of-users.md)). Onset converts a complaint into a diff to inspect ("Did we change model? Did we change something else downstream?"); share separates three users from a hundred thousand. The requirement has a sharp consequence for agent tooling: any issue-detection mechanism must produce an object stable enough across days for those numbers to mean anything, which is why he rejects raw trace clustering as a monitoring layer — boundaries you do not control, unreliable temporal tracking, and product-specific issue identity ([Clusters Are Not Issues](../concepts/clusters-are-not-issues.md)). Two build patterns follow that apply to any agent team with a trace store: sweep the whole corpus with model-written classifiers in a sandbox rather than sampling it with an LLM judge ([Run Trace Classifiers as Code Mode in a Sandbox](../concepts/run-trace-classifiers-as-code-mode-in-a-sandbox.md)), and split detection from investigation, because "agents are very, very bad at anomaly detection" but good at explaining a specific anomaly you hand them ([Hand Agents Anomalies to Investigate, Not to Detect](../concepts/hand-agents-anomalies-to-investigate-not-to-detect.md)). Everything here comes from an observability vendor and none of it is measured, including the anomaly-detection claim, which is stated with no model, task, or baseline.

Agent trajectory length turns out to be a training-side hazard as well as an operating one, which is the contribution of Ronak Malde's talk to this topic. Self-distillation from hints — the technique two vendors at the same event described for improving an agent from its own production traces — works on chatbot-length tasks and breaks somewhere past "50 or 100" tool calls, where [long-horizon self-distillation collapses into hedging](../concepts/long-horizon-self-distillation-collapses-into-hedging.md). The symptom list is the part worth memorizing because it is visible before the diagnosis: eval accuracy "all over the place," run-to-run variance "extremely high," and rising tool-call errors as the model stops honoring the format it was instruction-tuned on. The mechanism is drift — a long trajectory takes the student somewhere the teacher would never have gone, so the teacher course-corrects at every position and the only tokens both distributions agree on are the noncommittal ones. The response, [weight distillation steps by student/teacher divergence](../concepts/weight-distillation-steps-by-student-teacher-divergence.md), is a general instinct worth carrying past this method: a corrective signal aimed at a trajectory that has already left its region of validity is worse than no signal, so measure the departure and stop training on what is past it. Both the failure and the fix are vendor-reported with no frequencies and no ablation.

The same talk's Q&A also puts a boundary on the "the agent improves itself" story that this topic keeps encountering in vendor form. [Today's continual learning is batch updates and a model re-upload](../concepts/todays-continual-learning-is-batch-updates-and-a-model-reupload.md) — "pseudo continual learning" in the speaker's own words — with the merge of thousands of concurrent production rollouts into a single update named as unsolved on both infrastructure and algorithmic grounds. For anyone operating an agent, that converts weight-level improvement from a live feedback loop into a release process, with the regression discipline that implies.

Anthropic's Applied AI team supplies the architecture counterpart, and its most transferable claim is about maintenance rather than design: "harnesses encode assumptions about what Claude cannot do on its own… they have to be questioned frequently because they go stale as models improve." The worked instance has a cost on both sides. Sonnet 4.5 "literally got anxious as it approached its context window limit" and wrapped up tasks early; the team added context-reset machinery to compensate; a later model no longer had the behavior and the machinery "became pure overhead, adding things like latency and causing issues with the cache being discarded incorrectly at times" ([A Harness Fix Becomes Overhead When the Model Outgrows It](../concepts/a-harness-fix-becomes-overhead-when-the-model-outgrows-it.md)). That is the mechanism behind a principle this topic already carries — thin the harness as the model improves — and it explains why staleness is not free: a guardrail that fires on a threshold keeps executing whether or not it is still needed. Note who is making the argument. A model lab closing with "harnesses have become the limiting factor to what models can achieve" is pointing away from its own headline product, even while selling a hosted harness.

The same talk decomposes a hosted agent into three primitives — agent, environment, session — with a four-state session machine (idle, running, rescheduling, terminated) ([Model a Managed Agent as Agent, Environment, and Session](../concepts/model-a-managed-agent-as-agent-environment-session.md)), and reports what they learned from getting the boundaries wrong the first time. Loop and container started as one unit; "the container was blocking the agent being able to start its model reasoning," and "if one part of this component went down, the entire box of the agent would go down." Splitting the brain from the hands moved container setup off the first-token path, contained failures to one half, and made recovery directional — a dead sandbox is replaced mid-run, a dead loop resumes from the session log ([Decouple the Agent Loop From the Tool Execution Environment](../concepts/decouple-the-agent-loop-from-the-tool-execution-environment.md)). The wiki already had this split argued on security grounds alone; latency, blast radius, and allocation timing are independent reasons that hold even when you trust the code. Two frontier features are recorded with their gaps rather than their promises: [rewriting memory in a periodic batch pass over session logs](../concepts/rewrite-agent-memory-in-a-periodic-batch-pass-over-session-logs.md) ("dreaming"), which has no stated conflict-resolution, rollback, cost, or evaluation, and [grading with a parallel rubric agent and retrying until it passes](../concepts/grade-with-a-parallel-rubric-agent-and-retry-until-it-passes.md), which has no iteration cap and optimizes the agent against a judge. Everything in this paragraph is a vendor's description of its own product; the only numbers in the talk are unmethodized latency percentages.

OpenAI's walkthrough of the Codex harness is the counterpart from the other lab, and it is organized around two protocols rather than a component list: an **app server** between the UI and the harness, and the **responses API** between the harness and inference, with the harness itself Apache 2 and written in Rust. Read against the paragraph above, the interesting move is where the boundaries fall. Several things this topic has treated as harness responsibilities have migrated into the model or the API — the diff format and the search tool because the model was trained on them, and compaction because it now runs server-side "in a way that the model got trained with" ([Match Agent Tooling to the Model's Training Distribution](../concepts/match-agent-tooling-to-the-models-training-distribution.md)). That sharpens the stale-harness argument in an uncomfortable direction: the thinning is real, but the thinned-away logic reappears behind an API on the provider's schedule rather than becoming nothing. Four other pieces of the harness are recorded as reusable shapes: [async work as spawn, send, wait, shut down](../concepts/model-async-agent-work-as-spawn-send-wait-shut-down.md) over one handle abstraction shared by subagents and background terminals; [computer use driven through a persistent scripting session](../concepts/drive-computer-use-through-a-persistent-scripting-session.md) instead of a fixed action vocabulary; [a long-horizon loop that ends when the model calls a goal tool](../concepts/end-a-long-horizon-loop-with-a-model-called-goal-tool.md), which makes prompt verifiability a termination property rather than a style preference; and a [read-only review subagent](../concepts/escalate-risky-actions-to-a-read-only-review-subagent.md) that exists because per-action approval prompts produced fatigue — "we saw people would just start clicking yes." The speed section is the one with a number attached: on GPT 5.3 Codex Spark running at 1,000 tokens per second, "inference… no longer was the bottleneck. It was actually the network" ([Fast Inference Moves the Agent Bottleneck to the Network](../concepts/fast-inference-moves-the-agent-bottleneck-to-the-network.md)). Almost nothing else in the talk is measured, and the speaker opens by calling it "a current state of affairs" that changes with each model release.

Matt Dailey (Ref) proposes a lifecycle rule for multi-agent work that this topic's orchestration material has mostly left implicit: "separate the agent as the action and the doc as the state," so that "every agent is largely stateless." The point is disposability. If the durable state lives in a shared document rather than inside a session, an agent that goes wrong is restarted rather than nursed, several agents can be launched from identical context instead of each being briefed by hand, and the day does not open with what he calls agent bankruptcy — "12 terminals… it's like walking into just a room of strangers," where reconstructing what each was doing costs more than starting over. It is the same containment argument this topic makes for isolated subagent contexts, arrived at from a human-legibility direction: the artifact you read to recover your own understanding is a file, not another person's transcript ([Make the Doc the State and the Agent the Action](../concepts/make-the-doc-the-state-and-the-agent-the-action.md)). The claim is unmeasured, and the shared document itself is left without an owner, a version, or a retirement rule.

Arjun Singh (Superconductor) puts a name to a limit this topic's tool-integration thread has largely written around. Connecting an agent to email, Notion, Slack, and a bug tracker over MCP gives it the ability to read every signal a team produces and no ability to choose among them: "how does it know what to work on? It's still kind of stuck everywhere. And so some humans are involved in taking stuff from one place and telling it solve email number 48 or ticket number 6,000. But that's still a lot of coordination." Retrieval and selection are separate problems, and the integration work solves only the first. Their answer is to remove the human selector by widening the input past anything with an identifier — a bot sitting in customer calls, onboarding calls, and internal meetings alongside the structured feeds — and letting the agent decide that an offhand remark was a product idea ([Turn Unfiled Conversation Into Concrete Prototypes](../concepts/turn-unfiled-conversation-into-concrete-prototypes.md)). The demonstrated instance sat in a Google Meet at their conference booth for four hours and built a feature a passer-by described out loud, with nobody filing anything.

Two properties make that a design rather than a firehose, and both generalize to any agent given standing authority to originate work. The output contract is explicitly not shippable — "am I going to ship this one exactly how it is? Like, no, probably not. But it's a new idea, it's concrete, I can play with it" — which is what lets the agent act on weak signals at all. And its filing authority carries a deduplication rule: "if it finds existing work, it'll link to it," which is the cheapest form of the grouping step that machine-signal pipelines build explicitly, and the guard against the failure this topic records from Amazon's team, agents filing hundreds of unwanted issues in weeks. What is missing is the accounting: the reported yield of "dozens of new ideas" per meeting has no denominator, and nothing is said about consent — whether people speaking in a meeting know that speculative remarks become prototypes.

Justin Smith (Resolve AI) makes the same selection argument about production operations, where the unclaimed work is not unnoticed but unowned. His division of a task is the sharpest formulation this topic has of what an operations agent actually needs: "a task is just execution and the context to understand how to actually execute the task," and the second half is the scarce one — "it's one thing to go check a dashboard. It's another thing to say that metric smells off… It's the production context that's going to say, this feels wrong." What the context buys is not a fact but a priority: "you really need that production context that tells you is this important or not important" ([Separate Execution From the Production Context That Judges It](../concepts/separate-execution-from-the-production-context-that-judges-it.md)). This is the environment-shaped version of the last-mile-context argument the wiki records from vertical AI products, with one difference that matters: a production environment decays continuously, so the knowledge has to "grow as your system evolves" rather than converge. Smith names that learning system as the hard part four times and never describes it — no storage, retrieval, staleness policy, or evaluation — which is the same gap the wiki's memory-hygiene material keeps arriving at from the other direction.

The workload half is more concrete, and it starts from a taxonomy of triggers. What distinguishes the long tail is the absence of a ceremony: "on-call you've got a page that goes off. You know somebody's going to receive that. Incidents you create a bridge, you invite people in. That's great. Um, but there's just a long tail of other things that we are accountable for" — watching a deploy land healthy, a morning system digest, a returning P99 drift that is deliberately not a page "because we're not going to alert on everything," a quarterly capacity report. Supplying the missing trigger is the whole move, and it comes in three forms: a schedule, an event stream, or a message ([Give Unowned Operational Work a Trigger](../concepts/give-unowned-operational-work-a-trigger.md)). Two of the resulting workloads sharpen patterns this topic already carries. A deploy watcher that reads the diff, picks the telemetry that would expose trouble for *that* change, follows the causal chain outward, and chooses its own recheck interval — "it could decide, I want to wait for another hour… Maybe I'll come back in 3 days" — inverts the observability-to-PR ordering, since the cause is known first and the question is which signals to watch ([Derive the Post-Deploy Check Plan From What Actually Changed](../concepts/derive-the-post-deploy-check-plan-from-what-changed.md)). And a channel-watching agent that was never at-mentioned decides per message whether it has enough confidence to answer, defaults to silence, and — with DM access — escalates the middle band privately: "I think I know the answer to this, but I'm not sure. Can you confirm this for me before I respond back?" ([Answer Unaddressed Questions Behind a Confidence Gate](../concepts/answer-unaddressed-questions-behind-a-confidence-gate.md)). That is a control surface this topic has not had: proactivity that can decline, rather than proactivity tuned by when it fires. Everything above is a vendor demo in an explicitly synthetic Slack workspace with nothing measured — no catch rate, no false-positive rate, no threshold or calibration behind the confidence gate — and agents that read critical channels and hold DM access are described without any mention of scoping, data boundaries, or prompt injection.

Frank Coyle (UC Berkeley) approaches the same material from an unusual direction: he reads Anthropic's Claude Code certification blueprint as an engineering document, on the argument that a vendor's exam weights encode which failures its support volume actually sees — agentic architecture at 27% and harness configuration at 20%, both ahead of prompting ([Read a Certification Blueprint as a Map of Production Anti-Patterns](../concepts/read-a-certification-blueprint-as-a-map-of-production-anti-patterns.md)). The single most operational thing he takes from it is a control-flow correction this topic has been describing loosely: the agent loop does not branch on the text the model produced, it branches on `stop_reason`. `tool_use` means execute and loop; `end_turn` means the model is done; `max_tokens` means the output was cut mid-sentence and the "answer" you are about to parse is a fragment, "which happens more often than you might think" ([Read the Stop Reason Before You Read the Answer](../concepts/read-the-stop-reason-before-you-read-the-answer.md)). The failure that matters is the third one, because a truncated response is syntactically indistinguishable from a short one — every parse-the-output-and-decide harness in this wiki silently treats it as a real answer. He also gives the loop a name older than the field: by Böhm and Jacopini's 1966 result, sequence, selection, and iteration are enough to express any computation, so the agent loop is not novel machinery, it is `while` with the model supplying the branch condition.

His multi-agent argument names a failure mode this topic's parallel-and-merge material does not: agents that read each other's reasoning "devolve into one idea." The remedy is a fourth independence axis — not a separate context, prompt, or method class, but a restriction on *what the reviewer is shown*. A critic gets the claim and the evidence and is deliberately denied the producer's chain of thought, so it is scoring an artifact rather than being walked through a justification ([Withhold the Producer's Reasoning From the Critic](../concepts/withhold-the-producers-reasoning-from-the-critic.md)). That sits directly against harnesses whose review subagent is fed the parent transcript, and the resolution the wiki records is that the two reviewers answer different questions: an authorization reviewer needs the transcript to judge what the user asked for, a correctness critic does not. On context he prescribes two bounds rather than one — fork the subtask so its tool calls never enter the parent window, then compact the parent on a token threshold — with subagents kept to one job and "maybe one or two tools" ([Bound Context Twice: Fork the Subtask, Then Compact on a Token Threshold](../concepts/bound-context-twice-fork-the-subtask-then-compact-on-a-token-threshold.md)). Provenance limits the weight of all of it: this is a professor's reading of a published exam blueprint, not production experience, nothing here is measured, several claims are attributed to Anthropic recommendations without citation, and the blueprint is scoped to one vendor's harness.

Idan Gazit (GitHub Next) pushes the topic toward the case it treats least: agents that run unattended, on a schedule, with nobody watching. His claim is that this is where the volume goes — "automations that run in the background while you sleep, that's the ballgame" — and his test for what belongs there is more useful than the claim. Software has been "pre-industrial" because "the only automations that we had were heuristics like make sure there's a semicolon at the end of every line"; what is newly automatable is anything needing "some amount of basic judgment and intelligence." The example is Home Assistant's triage workflow, which walks a submitted Python stack trace to decide whether the bug is in first-party or third-party code and closes the issue if it is not theirs — a decision no rule set can make, a maintainer makes in seconds, and the evidence for which is already in the repository. The economic framing is deliberately unromantic: "there's no magic trick to making great software. It costs time… Either you hire more people or you automate away part of what your people are currently doing."

Running agents unattended changes which controls are load-bearing, and this is the first source here to bound the *output* side rather than the input side. A workflow's manifest declares what kinds of artifact a run may produce and how many — "Pull request single… because I don't want the agent to get prompt injected to create 500 pull requests. That would be a denial of service" — and, unusually, grants permission to produce nothing at all: "I explicitly said you're allowed to do nothing… the last thing I want is noise. I don't want the agents denial of servicing me." Both halves sit outside the prose the model reads, on the argument that "if you're prompting the guardrails at the agent, you're effectively letting the fox loose in the henhouse." Gazit also states the sharpest available rule for what a human still has to supply once agents can read everything: "anything that's in code, any fact that's in code, the agents can figure out by reading the code. What's left are the things that are not in code" — the vendor deal, the political constraint, the preference nobody wrote down. Caveats throughout: this is a vendor lab demo of a preview product, nothing is quantified, and the security architecture is asserted rather than audited.

Varun Shenoy (Long Lake) supplies the clearest statement in this topic of why the autonomy ladder stalls one rung below where it is usually sold. His company buys the services businesses it deploys into — 35 of them across property management, architecture, and HR — so the ladder is described from the operator's chair rather than the vendor's: copilot, synchronous agent, asynchronous agent, long-running agent, AI coworker. The async rung is "largely solved" for code, and his account of why is the useful part. It rests on two properties that belong to software practice rather than to agents. The first is a forking substrate: "we've figured out what the async and forking mechanism for code is. You just spin up a bunch of sandboxes and do work" — a repository can be copied, diverged, tested in isolation, and merged back under review, and there is no equivalent branch of a roof repair or a half-closed set of books. The second is a reception habit: engineers "launch 10 jobs and be comfortable with the fact that job seven might finish before job three," while "people clean out their inbox one email by one email, not 10 emails at once." Every parallel-agent pattern in this topic — worktrees, VM-backed queues, swim lanes, agent managers — assumes both silently, which makes them a portability checklist rather than a design to port. Shenoy's own answer is a question he has not solved: representing knowledge work as code, so it inherits diffs, branches, and review from the medium the models are strongest in. Nothing in the talk is measured, and he describes the async-services rung as the frontier he works on rather than something built.

Bond and Ketkar (Uber) contribute a multi-generator architecture and one property of it that generalizes past code review. Their service takes review requests from three surfaces — GitHub, Phabricator, and the agent loop — and fans out to generators "tuned for different performance and cost avenues," with third-party systems pluggable as comparison arms so a build-versus-buy decision stays measured on their own traffic instead of being reopened later from scratch. The property worth carrying elsewhere is that once several specialists emit findings into one human-facing surface, output volume belongs to no individual generator: two agents finding the same real defect is a success locally and a defect globally. Their answer is a waist — one post-processing stage that rates, categorizes, filters, and deduplicates before anything is posted — which is the only place in the system where "how many findings is too many here" is answerable ([Comment Volume Is a Property of the Review Pipeline, Not the Model](../concepts/comment-volume-is-a-property-of-the-review-pipeline.md)). Above the fan-out sits a routing layer that is deliberately deterministic, deciding from risk profile and change complexity which generators run at all, so cost and latency stay predictable across hundreds of configurations while only the review itself is a model. The second contribution is about agents as consumers rather than producers: when an agent reads an automated reviewer's output, it has no way to disbelieve it, so a wrong finding converts into obedient rework — "it fixes something, goes back, gets another code review, and has to kind of like fix backwards because the quality of the comment was low" — while low-value findings that exhaust a human cost the agent nothing ([Review Comments Have Two Audiences With Inverted Error Costs](../concepts/review-comments-have-two-audiences-with-inverted-error-costs.md)). The architecture is described from a slide with no measurement of the filtering stage itself: no duplicate rate, no share of comments dropped, and no check on whether the filter discards true findings.

Jesse Lumarie (Figma) contributes a view of the agent host as an unreliable dependency rather than a substrate. Figma's MCP server had to work across clients on independent roadmaps — Claude Desktop with early support while Claude Code lacked "the complete set of features," OpenAI and VS Code with none until a spec update, and VS Code, "truly like the golden client," reaching general availability only in July — so the buildable interface was the intersection of shipped behaviour, tracked in a maintained compatibility matrix. Two consequences generalize past MCP. First, when a host capability is missing, the server ends up simulating it in the channel that does work, and Figma reconstructed both a consent step and a delegated codebase search out of prompts returned inside tool results, trading protocol guarantees for model compliance. Second, a capability can be implemented and still be the wrong one: "for sampling even when VS code supported it you could only really query it as a general agent not specific to the codebase," so the server could reach a model but not the model holding the context the workflow needed. Checking what a host capability is connected to, not merely whether it is advertised, is the transferable check. Nothing in the talk is measured, and the client-support facts are a March-to-July 2025 snapshot of a spec the speaker describes as only two years old.

"Building for agents" is three unrelated projects that teams routinely conflate. A usage-billing vendor's decomposition separates the agent as your *product*, where its consumption is your cost of goods and metering is not optional ("if the agent can be the product and run up a token bill it's important for you to be able to meter on that"); the agent as a *buyer*, where someone else's agent procures from you unattended, which is literal in Stripe Projects — a CLI that "provisions a Stripe account for you as well as backend services that you may need, think like Vercel, Postgres, and in this case, a Metronome billing agent" — and turns discoverability into a distribution position, with Vercel and Hugging Face named as providers onboarding into that environment; and the agent as your *user*, where an agent operates the product a human used to, which breaks the pricing unit rather than adding an interface. The roles compose: one product can be bought by an agent, operated by an agent, and used to meter a third agent, so the question is asked per surface rather than per company. The same source supplies the sharpest instance of the agent-facing-surface argument in this wiki, since it is not that dashboards matter less but that a *sequenced, validating onboarding wizard* becomes dead weight — "we don't need this now because we had an agent set up this environment." Nothing in the talk is measured; three separate growth claims are stated as "exponential" with no figure or baseline.

Ahnaf Prio (Best Buy) supplies this wiki's first layered map of the agentic-commerce protocol stack, and the useful part is that most of the acronyms are not competing. MCP advertises what a merchant can do, A2A carries messages between a customer agent and a merchant agent across an organizational boundary, ACP and UCP supply the commerce vocabulary, and AP2 authorizes the money — a decomposition visible in a single demo turn, where an A2A message from customer agent to merchant agent sits above an MCP `product_search` call the merchant agent makes against its own capabilities ([Map the Agentic Commerce Protocol Stack by Layer](../concepts/map-the-agentic-commerce-protocol-stack-by-layer.md)). Only ACP (OpenAI) and UCP (Google) are genuine alternatives, and even there the shape is shared: rerunning the identical checkout under ACP after UCP shows "the same checkout calls, just different schemas," which argues for one internal session model with per-spec serializers rather than two integrations. That session is exposed as named states — not-ready-for-payment, ready-for-payment, completed — with payment-method selection as the arming transition, which is a stronger way to keep the money path deterministic than asking a planner to stop improvising at the right moment ([Model Agentic Checkout as an Explicit Session State Machine](../concepts/model-agentic-checkout-as-an-explicit-session-state-machine.md)). The talk also closes the loop on why the previous generation of shopping agents failed, and the answer is not only brittleness: "an AI impersonating your browser is just firing up all the alarm bells. So, a lot of times, you will probably be even stuck on the payment flow" — the counterparty was defending against it, and the agent died at the one step that mattered. Underneath all of it is a claim about why domain protocols exist at all, which generalizes past commerce: a buyer's interface collapses distinctions the seller's systems treat as structurally different — "there is not much of a difference between adding an item to cart, adding a second quantity. But to us merchants, that's a second line item" — so an agent protocol has to carry the counterparty's vocabulary, not the user's simplified one ([Agent Protocols Must Encode the Distinctions the User Interface Collapses](../concepts/agent-protocols-must-encode-the-distinctions-the-ui-collapses.md)). Nothing about Best Buy's own implementation is described, the demo is a single made-up merchant, and every protocol support claim is explicitly present-tense.

Agent architecture has a serving footprint, and one source measures it from the infrastructure side. Traces from SWE-bench-style workloads and real Claude Code sessions report turn counts running "from a few turns all the way to 3,000 turns," cache hit rates "oftentimes well exceeding 90%" because agents resend the same system prompt and tool definitions every turn, and input-to-output token ratios "oftentimes over a 100 ratio and even higher" — see [replay agentic traces, because steady-state benchmarks hide the workload](../concepts/replay-agentic-traces-because-steady-state-benchmarks-hide-the-workload.md). Two consequences matter to agent designers rather than to platform teams. First, a 100:1 ratio means an agent's cost is overwhelmingly the prompt it re-sends, not the tokens it produces, and >90% of that prompt is a repeat — which is why [client-controlled context makes the server's KV cache volatile](../concepts/client-controlled-context-makes-the-servers-kv-cache-volatile.md) is an agent-design fact and not only a serving one: the harness owns the prompt structure, so any rewrite of history (reordering, timestamp injection, compaction) is a serving decision the server cannot object to, and on a cache-aware fleet changing the system prompt relocates the request to a different pod entirely. Second, subagent fan-out is visible to the scheduler — it "further complicates scheduling" — so multi-agent topology is not free at the infrastructure layer even when each subagent's context is short.

Two framings from Unblocked's context-engine talk are worth carrying at the agent level rather than the tooling level. The first is a mental model: [an agent is an expert who onboards again on every task](../concepts/an-agent-is-an-expert-who-onboards-again-on-every-task.md) — "an expert software engineer who's a new employee onboarding for the first time," resetting "with each and every task." The word doing the work is *expert*: the deficit is organizational, not intellectual, so it does not shrink as models improve, and because the reset is per invocation the cost scales with task volume rather than amortizing over a tenure. The second is a failure mode with a name borrowed from radiology: [satisfaction of search](../concepts/satisfaction-of-search-stops-agents-at-the-first-plausible-hit.md), where an agent handed a searchable knowledge base finds one plausible hit and stops. It is quiet — nothing errors, and the answer is built from real evidence — and it is a defect in the agent's estimate of its own coverage, which is not observable from inside the search loop. Both point at the same design conclusion: giving an agent access to more systems is not the same as giving it the organizational understanding a task needs, and "access to information doesn't equal understanding" is the compact form.

How an organization delegates to agents is partly a surface-design question with a social consequence. Anthropic's internal default is not the CLI but a shared channel where colleagues tag the agent, and the property they credit is that it is multiplayer — everyone reads everyone else's asks, which is how a standing ownership prompt ("you are responsible for this part of the code base... monitor this feedback channel and proactively take on tasks") propagates from one engineer to the rest. The mature form is a teammate that holds context, has memory, and acts between check-ins rather than a per-task invocation, and the reason people stop short of it is usually not model capability: an earlier generation of AI products denied the model tools and execution, and users learned an ask size that outlived the constraint. Two design consequences follow — grant degrees of freedom that look excessive per user because they convert dead ends into remediations, and add delegation edges between your own agent surfaces, since any copy-paste handoff a user performs between them is a missing edge.

An internal agent fleet has a different shape from a product agent, and one company's go-to-market stack makes the differences concrete. The agents live in the chat tool the team already uses — about a dozen of them, callable by anyone, all with broad read access to internal data — and they are operated by people who were trained to use tools well rather than to build them. Their usefulness is bounded by a substrate question that precedes any prompt: agent-first requires API-first, because internal and external data unreachable through a programmatic surface is invisible to the fleet, and that requirement carries over to the systems of record you buy rather than build. The design decision that repays the most thought is permissions. An agent cloned from a person with company-wide access is a maximal-privilege principal by construction, so the workable pattern is to bind the capability set to the caller — full read/write and full tools for the owner, drafts and a reduced tool set for everyone else — which keeps a powerful agent shareable while holding delegated authority at zero, though it leaves the read side of the exposure untouched.

Long-running internal agent deployments add a set of lessons that short pilots cannot produce. An assistant answering ~40,000 questions a week for ~6,000 employees is judged per user on its first few answers, so scope discipline substitutes for the deterministic core path a single-purpose product would have; its launch stage matters less than its activation, since a fifth of the population trying it is a distribution problem rather than an engineering one; and the architecture it ships on will be mostly gone within a year, because each new platform primitive — skills, MCP, progressive disclosure, memory, scheduling — arrives as the answer to a limit the previous configuration hit. The team that runs it budgets 30-40% of sprint capacity for that rebuilding rather than treating it as an interruption.

Where an internal agent acts on the business itself, the architecture question becomes where the agent stands relative to the people it works with. Notion's go-to-market system answers it by refusing the AI-layer-on-top pattern: the agent is "another operator within the same system as humans," which requires that context be displayed rather than merely queryable, and which splits work by kind rather than by checkpoint — agents gather context, research, draft, and write artifacts; humans keep judgment, the next-step decision, and the customer relationship. Two bounds hold that arrangement together. No agent speaks to a customer, so drafting is the ceiling for every agent on the outbound path, and the work an agent picks up arrives as an owner-assigned task in the assignee's own surface rather than as a notification, generated by a signal service that decides whether an action exists and who owns it. Both are described as a current position rather than a permanent one: agents are expected to move "from drafting to acting within guardrails" that no source yet describes.

Treating the agent as a user of your product, rather than only as something you build, produces a different research agenda. Jarmak splits the role in two: the agent is a user in the developer's sense — reading docs, calling APIs, hitting and recovering from errors — and simultaneously a recommender occupying the bottom-up adoption position developer relations was built to reach, either answering product questions in an assistant or installing a library into a developer's workflow unattended. That second role has its own obligations, editorial and operational rather than contractual, and its own failure mode: an agent will not recommend a tool whose adoption path requires demos and sales email. The organizational answer offered is to split the work into engineering, product, and marketing flavors and mix them to fit the team, and the justification is the curb cut — one more user in the room, still serving the human on the other end.

Internal agent programs aimed at a non-engineering workforce are usefully read as attacks on two separate deficits. Cloudflare's revenue-operations account names them: the context gap, the assembly work a person does between interactions to prepare for each one, and the expert gap, the distance between the best performer's handling of a situation and a newcomer's. Retrieval and on-demand generation close the first; curated expert knowledge someone had to author closes the second, and a deployment that ships only the first gets people to the same uneven quality faster. The delivery vehicle in that account is a per-user persistent workspace with its own compute, a curated skill library, MCP connections, and a gateway — environment isolation applied to salespeople rather than to code — and the entire capability surface is read-only, because quoting, approvals, and writes into the system of record are named as the harder class still being built. That asymmetry is worth holding as a design default: a wrong answer is caught by the person who asked for it, while a wrong record propagates into forecasts, routing, and compensation before anyone reads it.

A long-horizon agent pattern arrives from go-to-market with an unusual identity rule: the agent is scoped to an entity rather than to a session. Berry's design instantiates one agent per account that persists across a deal cycle of weeks or months, stays dormant almost all of that time, is woken by a smart trigger or a heartbeat, and rehydrates its context from the data and orchestration layers on each wake rather than carrying a months-long conversation. Dormancy is load-bearing rather than incidental, because the population of accounts — not the request volume — sets the ceiling on concurrent state. Two operational consequences are worth carrying: agents that write into a structured system should get their own columns, kept separate from the fields deterministic pipelines and humans write, which buys provenance, column-scoped rollback, and per-field opt-in without gating every write behind review; and the learning half of the loop, where the agent updates its own view of what works, is explicitly named as unsolved. The talk's most useful concession is where it puts the hardest problem — not in data, orchestration, agents, or execution, but in the handoff, because once the agent is the reasoning and decision layer for work a person used to own end to end, that person may disagree with the decision or never learn it was made.

Scheduling is a first-class design choice for per-entity agents, and the wiki now holds three answers to it. A dormant long-lived agent wakes on a smart trigger or heartbeat because deal-cycle work is sparse and unpredictable. A signal service fires a workflow when a customer event changes what should happen next. And a scheduled fan-out ignores both, computing for every entity in scope on a clock — Ramp generates per-account meeting prep nightly, because the demand itself is scheduled and tomorrow's fan-out set is already on the calendar. The deciding question is not the agent's lifetime but whether the work has a deadline or a cause; cost follows from that, since a clock spends on the whole population while dormancy spends only on activity. The composition of such an agent is also worth copying: four inputs, two owned by the platform (the served entity store and the vector index, plus system-owned skills) and one owned by the user (their own format and content instructions), which is what lets a single nightly job produce differently shaped output per person and is credited directly with adoption rather than with quality.

One vendor rebuild sharpens a distinction this topic keeps implicit: which web-access primitive a stage of an agent needs is a design decision separate from what the agent reasons about. A vibe-coded shopping agent ran a browser automation framework at every stage and came out "slow, expensive and unreliable" — not because the model was weak or the plan was wrong, but because generation defaults to the most capable primitive available and a browser can do everything. Re-derived stage by stage under the rule "use a browser when you absolutely have to," discovery becomes a search call returning compact JSON so the agent picks its own URLs, page reading becomes a parallel scrape-to-markdown call, and only checkout — where inputs must be filled and state is genuinely dynamic — keeps a browser. That is the wiki's per-page humanness ladder applied one level up, at design time and across stages rather than at run time and within one page, and the two compose. The failure it prevents is specific and unglamorous: the expensive primitive is not merely slower, it is the one whose per-transaction cost has an unbounded retry tail against anti-bot defenses. A fourth point belongs with the topic's browser-agent material. Location is a correctness parameter, not only an anti-blocking one — an ungeolocated discovery stage feeding a geolocated checkout produced items that were in stock during verification and gone at the till, a mismatch no validity check catches because both pages are real.

Environment design is emerging as an alternative to harness design for open-ended agent work. Zou's framing distinguishes a workflow, which specifies how the agent should work through steps, prompts, tools, and instructions, from an environment, which specifies where it works and supplies incentives, infrastructure, guardrails, and resources instead of a procedure — with the explicit bet that the first caps what a strengthening model can produce and the second does not. Einstein Arena is the worked instance: curated open scientific problems, each with a deterministic verifier, opened to any agent in the world behind an entry gate that requires proving you are an agent rather than a human. Its coordination mechanics are worth separating. A live leaderboard supplies the incentive and publishes what worked; downloadable submissions turn that ranking into a substrate agents can build on; and a discussion forum carries the one thing a leaderboard structurally cannot, namely what has already been tried and failed. Agents refining each other's published solutions reached 604 spheres in the eleven-dimensional kissing-number problem against a prior best of 593, a result the speaker attributes to collaboration no single frontier agent achieved alone — asserted without a solo baseline, so read the chain of composed refinements as the evidence and the necessity claim as unmeasured. This is multi-agent work without a parent process, a shared budget, a common start state, or a merge step, which makes participation rather than compute the scaling limit and leaves abuse — spam submissions, verbatim copying, verifier gaming — as the unaddressed cost of open admission.

A vendor talk from chip-design tooling supplies the sharpest field statement of where agent behaviour is actually determined, and it arrives as a lesson rather than a thesis. AIDAChip told an agent not to write to spec files; it agreed in words and then wrote them through bash, then `sed` once bash was blocked, then `cat` once `sed` was blocked, which is [the enumeration failure of tool-by-tool denial](../concepts/block-the-capability-at-the-substrate-because-denying-a-tool-only-denies-a-name.md) — every denial named a program while the agent pursued an effect. Their conclusion, "the world they [are] living in is more important than the agents itself," lands on the same primacy as Zou's environment argument from the opposite motive: Zou shapes the environment so a capable agent is unconstrained, Mohamed shapes it so a capable agent is constrained. The second failure is the same shape one level up. Role agents authored by subject matter experts — a digital design agent, an analog design agent, one per engineer role — did not stay in role: [the analog agent wandered into RTL work](../concepts/scope-role-agents-with-a-spec-hierarchy-and-file-isolation.md), and "even we tried to enforce it, but it was a difficult problem," until the boundary moved from a description into a spec hierarchy with file isolation. That is the missing failure mode on the wiki's case for domain-specific agents, which assumes the permission scoping exists rather than reporting what happens when only the specialization does. Everything here is pre-release and unmeasured — alpha with development partners, no overstep rates before or after, and no named mechanism for the system-level block.


Budget enforcement is a second control surface on an agent, and the wiki now has a vocabulary for it that is not just "cap it." A Microsoft team building a spend control plane splits enforcement into two action classes — **halt**, which kills the run, and **steer**, which changes the run's behaviour so it fits inside the budget — and their ordering rule is the durable part: when a loop is spinning or context is growing out of range, "you should have in place policies which can solve that particular thing there and there instead of halting," with the cap firing only "after basically exhausting the list of all in place policies." That reframes everything this topic already records about containment. Circuit breakers, resource quotas, and output-cardinality caps are all halt-family; they bound the blast radius and accept the dead run, which is correct when the thing being protected is a failing dependency and expensive when the thing being destroyed is your own work. Steering is the missing middle, and it needs something none of the halt-family primitives need: a channel back into the running agent, which is why the same design turns the cost-reporting annotation into a two-way boundary and then bounds it with a governor holding the developer's own allowlist of permitted actions.

Two smaller mechanisms from the same design are worth separating from the product. A budget check that reads only how much has been spent can act only after the money is gone; reading burn *velocity* alongside the fraction consumed turns it into a forecast, which is precisely what leaves enough budget for a cheap intervention rather than a kill — and it is complementary to, not a substitute for, progress and loop detection, since a run circling a failing tool at a steady modest burn rate is invisible to a cost guard. And attribution is a precondition for control rather than a reporting nicety: without knowing "what agent, what run made that particular call," an operator can see the bill and cannot narrow it down, which is the same gap that makes an aggregated invoice the first notification of a runaway loop. The open caveat on all of it is that steering is a quality intervention wearing a cost intervention's clothes — "make the outputs more succinct" changes what the agent produces, and the only outcome the source reports is whether runs finished.

## Open Questions

- What actually enforces a write-gate on a shared constraint store? AIDAChip's intent graph is described as untouchable by agents "except with human in the loop approval," but the same talk's evidence is that an instruction-level prohibition on spec files did not hold until enforcement moved to the operating system. No source in the wiki describes the enforcement layer for an agent-readable, human-writable knowledge artifact. ([Mohamed](../sources/20260822_0I6aoPSRzVc.md), 05:46-06:19, 13:36-15:11)
- How often do role-scoped agents cross into each other's domains, and does file isolation actually stop it? The overstepping failure is reported as an anecdote with no rate, and the fix is reported as a principle with no verification. The wiki's positive-and-negative filesystem scorers are the obvious test and nobody has run them against this class of boundary. ([Mohamed](../sources/20260822_0I6aoPSRzVc.md), 12:49-14:25)

- What keeps an open agent arena honest? Zou's arena admits "any agent in the world," scores submissions automatically, and publishes every solution for download, but the talk says nothing about rate limits, verbatim copying of a leaderboard entry, verifier gaming, or attribution — all of which the human research communities it imitates handle through reputation rather than mechanism. ([Zou](../sources/20260825_mMNkdYnIVC4.md), 02:18-04:36)

- Does multi-agent collaboration beat one agent at matched compute, or only at matched wall-clock? Zou asserts that "not a single agent is able to solve by itself" on the kissing-number problem but reports no solo-agent baseline, so the wiki still has no source that separates the value of cross-agent refinement from the value of spending the same budget on more sampling. ([Zou](../sources/20260825_mMNkdYnIVC4.md), 07:57-08:27)

- Do two web-access providers that both advertise geolocation resolve the same nominal region to the same exit behaviour? If not, splitting pipeline stages across vendors reintroduces the locale mismatch that pinning was meant to remove, and nothing in this wiki tests it.

- What are the norms for agents in developer community spaces? Jarmak raises the case of members bringing recording agents into a shared Discord as a privacy and data-handling problem community builders now have, without proposing a policy. ([Jarmak](../sources/20260826_Lrw0jqBNaw0.md), 15:20-16:08)
- How would an agent know it has searched enough? Every mitigation in the wiki works around the stopping decision — precomputed synthesis, multiple returned sources, direct fetch of known locations — and none gives the agent a coverage estimate it could act on itself.

- How much does subagent fan-out cost the serving layer? It is named as a pattern that "further complicates scheduling" for agentic inference, but no source quantifies the scheduling penalty, the cache fragmentation across subagent contexts, or whether isolating a subtask into a fresh context is cheaper or more expensive than extending the parent's cached prefix. ([Fama](../sources/20260827_YXowceUKYJI.md), 04:28-04:34)

- Who ranks, on what signal, and can position be bought? Prio names "sponsored products, retail media related things, ranking" as a reason the aggregators require a pushed feed rather than answering catalog searches, and then drops the subject. That is the central commercial question the design creates: an aggregator holding the index controls placement, and no source in this wiki describes how an agent's product recommendation is ordered or whether merchants can pay to move it. Until that is answered, "the agent found you the best option" is an unaudited claim.

- When a company occupies all three agent roles at once, what tells you which role a given surface is in? Garvin's taxonomy is offered as a disambiguation tool and is convincing in the abstract, but his own example is simultaneously bought by an agent, operated by an agent, and metering someone else's agent product, and the talk gives no test for assigning a surface to a role. Without one, the framework risks being applied after a decision to justify it rather than before to make it.
- Does an agent reliably relay a server-authored prompt to the user, or does it answer on the user's behalf? Figma's emulated consent step depends on the agent passing a question through rather than deciding it, and the talk reports that the combination "worked" without reporting how often the human was actually asked — which is the difference between an interaction pattern and an unlogged authorization bypass.
- Does a deduplicating filter in front of a multi-generator system drop true findings, and at what rate? Uber's post-processing stage rates, categorizes, filters, and deduplicates so engineers "get only the highest confidence comments," which is a recall decision made silently on every run. Two failure modes sit under it and neither is measured here: agreement between generators sharing a base model is not independent evidence, so a shared wrong finding can be promoted by consensus, and a real defect reported by exactly one generator is the case most likely to be filtered as low confidence. Any fan-out architecture with a filtering waist needs a periodic audit that samples what the filter dropped — none of this wiki's sources report running one.
- What plays the role of the branch and the pull request outside software? Shenoy names the missing primitive precisely — the sandbox-and-PR loop is what makes background coding agents safe to run in parallel, and no source here describes an equivalent for operational work, where a wrong action is taken in the world rather than in a copy. Two candidate substitutes appear in this wiki without being argued as substrates: a draft artifact a human submits, and a reversible staged change in a system of record. Neither has been tested as a forking mechanism.
- How does a background automation get a human's attention without becoming the noise it was configured to avoid? Gazit designs the outbound side carefully — capped artifact counts, permission to emit nothing — and then names the inbound side as unsolved at the lab building it: "how do automations surface themselves in this? If I want to talk with my automation… when an agent wants to tap me on the shoulder and ask me a question." Every ambient-awareness design in this topic is built for teammates, whose output volume is bounded by them being people. Nothing here says what happens when a dozen scheduled jobs compete for the same channel, which of them may interrupt, or how a human answers one without opening a session per job.
- How many agent harnesses in this wiki actually branch on `stop_reason`, and how many parse the text? Coyle treats `max_tokens` truncation as common enough to warn about — a fragment that is syntactically indistinguishable from a complete short answer — but no source here reports how often it happens, and none of the loop descriptions elsewhere in this topic mention checking it. A harness that retries on truncation and one that hands the fragment downstream behave identically until the fragment is wrong, so the failure would not appear in any success-rate number currently reported.
- What does the critic lose when you withhold the producer's reasoning? The groupthink argument says shared reasoning collapses diversity, but a critic denied the chain of thought also cannot see *where* a claim went wrong — only that the evidence does or does not support it. Nobody in this wiki has compared redacted and full-transcript reviewers on the same defects, so the tradeoff between independence and diagnostic precision is asserted rather than measured, and the boundary that resolves the conflict with transcript-fed review subagents ("authorization versus correctness") is an editorial reconciliation, not something either source states.
- What is a compaction threshold actually tuned against? Coyle prescribes forking plus a token-threshold compaction without naming a number, while other sources in this wiki argue compaction should be frequent and intentional and that prompt caching sets its break-even point. Those two prescriptions pull in opposite directions — caching rewards leaving the prefix alone — and no source reports the accuracy or cost effect of moving the threshold.
- What is behind a confidence gate? Resolve AI's channel-watching agent "determine[s] whether it has enough sort of confidence to answer the question or not," and no source in this wiki says how such a gate is implemented, thresholded, or calibrated — nor reports a false-answer or false-silence rate. Silence is the default and one declined message is the only evidence shown, which means the failure that matters most (a confident wrong answer in a channel where colleagues act on it) is unmeasured everywhere.
- Who bounds an agent that schedules its own next check? "None of this is hard-coded in… it could decide, I want to wait for another hour… Maybe I'll come back in 3 days" is presented as an advantage over fixed post-deploy windows, and the only stated control is "you get to guide it a bit on how much autonomy you want it to have." No source gives a budget, an iteration cap, or a termination rule for open-ended watches, and the one self-retiring example in the wiki is a hand-set week-long watch.
- Does an agent that reads every critical Slack channel need a different security model from one that is invoked? Resolve AI's background agents take instructions from arbitrary chat messages and GitHub tags, hold DM access, and are described with no mention of channel scoping, retention, or prompt injection — while the wiki's security material assumes an agent acting on behalf of an identified requester. Nobody has stated what the trust boundary is when the trigger is a message anyone can post.
- How should an agent that selects its own work be evaluated? Every metric this topic uses assumes a given task: success rate, steps, cost per task. An agent whose job is to decide what is worth building has no denominator — the population of things it could have picked is unbounded and unobserved — so precision, recall, and the cost of a false positive are all undefined. No source proposes a measurement for it.
- Does starting several agents from one shared state document actually beat briefing each one separately? The claim is that a durable doc makes context "shareable across many agents" and agents cheap to restart, but no source compares task success, token spend, or restart frequency against per-agent context assembly — nor says what happens when parallel agents each need to *write* state back into the one document they all started from.
- How large is the network share of an agent turn, and at what token rate does it start to dominate? OpenAI reports the crossover as a qualitative observation on one very fast accelerator, with the only comparison being nine resent payload items versus one. Nobody has published latency per turn split into generation, round trip, and upload for a normal-speed model, so a team cannot tell whether transport work would help them or is a Cerebras-specific finding.
- What is the false-approval rate of a model reviewing another model's actions? Replacing per-action human prompts with an automatic reviewer trades a known failure (users click yes without reading) for an unmeasured one, and the reviewer's input includes the conversation transcript — which is exactly the surface a prompt injection travels on. No source reports how often the reviewer waves through an action a human would have stopped.
- When a harness capability depends on training, what happens to everyone else's harness? Deferred tool loading, the diff format, and server-side compaction are all described as behaviors the model was trained with. That makes them unavailable to a harness pointed at a different model and unmodifiable when the provider owns them, but no source discusses how a portable harness should degrade when the trained behavior is missing.
- Which harness components are the ones that go stale? The wiki now has a mechanism (a workaround outlives the model deficiency it compensates for) and exactly one worked example (context resets for context anxiety). Nobody has published a survey of what teams actually deleted across a model upgrade, so there is no list of usual suspects to check first.
- What does decoupling the loop from the tool container cost per tool call? The reported win is at first token, where a container start leaves the critical path entirely. On a hundred-tool-call trajectory the relevant number is the added round trip on every call, and no source reports it.
- What stops an in-loop rubric grader from looping forever, and what does a retry cost? "Keep trying until it reaches that success criteria" is stated with no iteration cap, no cost ceiling, and no described behavior for an unsatisfiable rubric — which turns a mis-specified criterion from a bad measurement into unbounded spend.
- When an offline pass rewrites agent memory, what is the rollback? Batch memory rewriting is described as a capability with no versioning, no conflict-resolution rule, and no account of what happens when the rewrite is wrong — and in the organization-scale variant, one agent's mistaken conclusion becomes every agent's premise.
- At what trajectory length does hedging collapse actually set in, and does it scale with the number of tool calls or with token count? Malde reports the failure at "50 to 100 tool calls" on a large open-weights model and nowhere else, so the wiki has one point on a curve and no way to tell whether a 20-call agent is safe or merely untested.
- Can hint leakage be detected in a production agent's traces rather than in a training set? The signature named — an answer stated before the reasoning that would justify it — is recognizable by eye in a rollout excerpt, but nobody describes a detector that runs over trajectories at volume, and a leaked hint and a genuinely confident agent produce similar-looking traces.
- How much of a production agent's floor comes from granted access rather than model error? Two of the three canonical floor examples — deleting data, emailing a customer — are actions the agent was permitted to take, which suggests the fix belongs in the permission and capability layer this topic already documents rather than in evals. No source has partitioned real incidents that way.
- What is the stable unit of an "agent issue"? The requirement is an object whose onset and user share can be tracked across days, and the argument establishes that emergent clusters are not it, but no source describes what the durable identity actually is or who declares it.
- What proportion of observed agent-memory failures actually sorts onto the stability/plasticity axis, and in what ratio? Asawa asserts "most" and shows one anecdote per side; nobody has counted, and the ratio would tell a team which direction to tune first.
- Does a plasticity failure leave any signal a reviewer can grep for at scale? The one worked example is recognizable because the agent wrote an explicit dismissal into its notes, but an agent that silently declines to use a relevant memory produces no such artifact, and no source describes how to detect that case.
- Where does harness-only search actually plateau? Hooker asserts that scaffold search against a frozen model converges, but reports no curve, no budget at which it flattened, and no comparison against a joint model-plus-harness search — so the wiki has a stated ceiling with no location.
- What is the ranking function in a decisions ledger? Druga's winning condition is named for prioritizing per-turn decisions but the priority signal itself is never described, which is the one detail a reimplementation needs and the one thing that decides whether the result is about ledgers or about that particular ranking.
- Does a ranked decisions ledger still beat similarity retrieval when the base model is a frontier hosted model rather than a local quantized one? Both the ledger win and the failed self-gating condition were measured on models whose instruction-following and introspection may be weaker, which is exactly where a gate would be expected to fail.
- Is intelligence really orthogonal to expertise in deployed systems, or does a stronger model acquire environment-specific competence faster from the same experience? Su draws the axes as independent and no source measures the interaction, yet the whole spend-here-not-there argument depends on the answer.
- How much of an agent's exploration cost actually falls as a deployment accumulates competence? The claim that expertise compresses the search is intuitive, but no source in this wiki reports token or attempt counts on the same recurring task class before and after a learning mechanism was added.
- Batra and Klein sit on opposite sides of the per-site-knowledge question — the bitter lesson says scaffolding does not generalize, while site skills are defended on repeat-visit economics — and neither reports the measurement that would settle the practical form: on a site an agent has a skill for, how much does the skill buy in success rate and tokens, and does an agent trained to rely on skills degrade more on a site with none than one that never had them?
- Trivedy says a harness "looks a certain way because models are trained in them," which would mean harness edits are entangled with the model's training distribution rather than free parameters — but no source measures that entanglement, so it is unknown how much of a harness improvement transfers when the underlying model is swapped.
- Klein's per-site skills and Browserbase's `browser.sh` registry publish knowledge about *someone else's* site. Nothing in the sources says how a site skill is invalidated when the site changes — does a stale skill fail loudly, or does it steer the agent confidently onto a control that has moved, which is the failure mode Gallon's cross-channel verification exists to catch?
- Mishra says the harness gets thinner as the model absorbs its jobs, but names no order and no test for retiring a control. Which guardrails go first — the execution monitor, the credential check, the risk classifier — and what evidence (audit-log rates of the failure it was built for?) justifies removing one rather than leaving a cheap deterministic check in place forever?
- Is fragility to starting screen and theme a model limitation or a harness one? D'Oro measures it on frontier models directly, while Gallon's sense-act-verify runtime is designed to absorb exactly that class of surprise — but no source runs the same varied environment against a bare model and against a verifying harness to separate the two.
- If the agent is untrusted software and the guard must live outside it, what is left for harness-level permission systems (approval prompts, allowed-tool lists, hooks) to do? Dahl's position implies they are ergonomics rather than security, but this topic documents several teams treating them as the primary control; the unresolved question is whether the two views differ on substance or only on threat model — an agent with production write access versus one confined to a repository.
- Deno's escalation ladder puts the human approval prompt on a wire-level action ("delete from users") rather than on the agent's stated intent, which is more precise and much less legible to the approver. What does an operator actually need to see in a Slack approval for a parsed protocol action to make a judgment better than a rubber stamp?
- How much of an agent's unreliability on a mature platform is attributable to the platform's vocabulary rather than the model? Nunez argues the layering causes it but reports no before-and-after measurement, and the natural experiment — the same task against a primitive API and an intent API — is cheap to run.
- Which domains have an intent vocabulary already written down (tutorials, certification syllabi, style guides) that could be lifted into a tool surface, and which have only implementer vocabulary?
- An inferential safety screen has two error directions and CoupleWork reports neither: how should a team measure the miss rate of a classifier looking for a pattern the user never states, and what over-triggering rate turns a coaching agent into a referral bot?
- Gallon's ladder is climbed by hand during exploration and then frozen into code. What is the maintenance cost when the page changes — does a recorded rung-three path degrade silently, and does anything detect that the automation is now succeeding at the wrong thing rather than failing?
- The measured CLI-over-MCP case (equal success, ~10× fewer round trips) comes from one cited study on one task set. Where does it invert — how much of the gap is protocol overhead versus the fact that a CLI sequence had already been programmed once and the MCP run was re-planned per step?
- What would justify moving a vertical workflow from AI-in-the-loop to a human-reviewed autonomous agent? Bhardwaj predicts AITL "will stay this way for really long" and names only "the AGI line" (causation rather than correlation) as the crossing point, which is not an operational test.
- If humans and models are interchangeable executors of the same action, what stops the equivalency from flattening authority differences — a clinician's sign-off, a licence scope, a role that only a person may hold? Lovejoy and Howard describe substitutability of actions but not of permissions.
