# Retrieval

## Overview

Retrieval gives agents access to institutional systems such as Confluence, Jira, SharePoint, GitHub, Slack, knowledge graphs, and file-backed knowledge bases. The useful retrieval layer is not the one with the most connectors, but the one that provides accurate, task-relevant context and exposes gaps when the source knowledge is missing, stale, contradictory, or unavailable to the current user. Personal Markdown knowledge bases can play the same role at individual scale when saved links, notes, tasks, and project records are indexed, tagged, connected, and resurfaced when relevant. Read-only personal retrieval can also synthesize emails, journals, tasks, browser history, notes, and relationship records into reflection without granting mutation rights. Context engines add a reasoning layer over retrieval by personalizing results to the task, team, permissions, and source relationships. Small models can improve this layer by embedding, reranking, extracting entities, filtering inputs, or building structured knowledge targets. Omnimodal embeddings extend the retrieval target beyond text: one semantic vector can represent text, audio, video, and documents so agents can retrieve, query, and compare concepts without lossy modality handoffs. Dimension-adaptive embeddings add an infrastructure lever by letting retrieval start with cheaper coarse vectors and expand when higher expressiveness is needed.

Retrieval is also an LLM security boundary. Poisoned chunks can steer an answer when they are retrieved for the target query and ranked high enough to look useful, so retrieval systems need provenance, corpus hygiene, and safety checks before retrieved text becomes model context. Embeddings themselves should also be protected as sensitive derived data: storing vectors without source text does not make the corpus safe to expose if a reconstruction model can recover source-like content.

Search-engine fundamentals still matter inside RAG. A retrieval engine is not only a vector store: lexical search depends on analyzers, tokenization, offsets, positions, inverted indexes, and ranking statistics that are built at ingestion time. BM25 remains a useful baseline because exact names, brands, identifiers, and short keyword queries often need literal matching, while dense vectors need enough surrounding context and a model that understands the corpus. Hybrid retrieval should therefore be treated as a composition problem: keyword, learned sparse, dense vectors, filters, RRF, and rerankers each solve different candidate-generation or ordering failures.

RAG systems benefit from reusable baselines, but not from a single fixed recipe. Document parsing, chunking, embedding choice, hybrid lexical/vector search, metadata filters, and query-time agent loops all need to be tuned against the actual corpus and user questions. Fast query-document evals make that tuning empirical: if each local query has an expected document, teams can compare top-k recall across embedding models and chunking strategies before re-embedding a corpus or trusting a public benchmark. Synthetic queries can help when real traffic is unavailable, but they should be calibrated against realistic user specificity so the eval does not become cleaner than the production task. Real-time web search needs an even fresher benchmark loop: dynamic eval sets should generate current grounding documents and evidence-backed question-answer pairs, because static QA datasets can miss source changes, subjective timing, and user-context ambiguity. Generic embeddings can be too global for a specialized corpus, so contextual or domain-adaptive embedding approaches may improve retrieval before a team reaches for model weight updates. Structure-aware ingestion is especially important for messy source formats: preserving document hierarchy, tables, images, OCR output, and modality-specific extraction gives retrieval cleaner chunks than plain text extraction. Choosing *how* to extract is itself a tiered cost/determinism/scale decision, not a single tool pick: a naive parser is cheap on CPU but linearizes tables and drops images; a frontier VLM is high quality but expensive (~$30/M output tokens), non-deterministic, and brittle to model deprecations; and a local structure-aware library (Docling) is the middle ground — deterministic, air-gappable, GPU-optional, and ~50× cheaper at scale (Hugging Face's FinePDFs was built on CPU with Docling + OCR). Extraction accuracy is not cosmetic: a column-merge OCR error produced a nonexistent term now cited across ~20 scientific papers, showing how ingestion mistakes compound downstream. Once a document is parsed into faithful structure, retrieval can sometimes skip the vector store entirely: "chunkless"/agentic RAG treats the document's Markdown section outline as the whole retrieval index, and an agent iterates over section summaries, pulls the relevant section's full text, and answers — no chunker, embedding model, or vector database (demonstrated over a 418-section annual report). This is a document-scoped specialization of agentic retrieval, appropriate when per-document query volume is low. The parser's operational surface matters for production: a Pydantic document enables programmatic table→DataFrame and structured field extraction, a layout model can strip PII before extraction, VLMs can enrich images into retrievable descriptions, and the pipeline can be served as a REST microservice or exposed to coding agents through an MCP server. For image-heavy or scanned PDFs, the retrieval unit itself may need to shift from extracted text chunks to page images: ColPali-style systems embed visual page patches so the retrieved evidence preserves layout, embedded text, forms, and images together. Hybrid indexes add another control point by combining vector similarity, keyword search, filters, aggregations, and embedding-model migration paths. Graph retrieval adds a distinct lever when questions depend on entity relationships: teams can combine vector retrieval with knowledge-graph traversal, but only when the ontology and extracted triplets are reliable enough to justify the extra compute and latency. KAG makes that choice more advisory: when the answer needs exact values, function calls, and strategic recommendations, the graph should expose structured evidence and decision relationships rather than only similar passages. Graph-backed context can also become an agent memory surface rather than only a search backend: nodes, relationships, properties, embeddings, and access overlays make long-term memory traversable and inspectable, while agentic GraphRAG can let a model inspect schema, issue graph queries, and pull related chunks iteratively when a fixed retrieval path is too shallow.

RAG technique choice should follow query-set loss analysis. Start with the product outcome, a launch bar, easy and hard query sets, and the simplest viable baseline, then inspect failures before adding layers. Small corpora may work with in-memory context until attention or window limits break; explicit keyword queries may only need BM25; paraphrased intent can justify vector retrieval; conflicted candidate sets can justify cross-encoder reranking; and vertical domains may require custom vocabulary or product-ranking signals. As queries become more ambiguous, the retrieval layer may need to fan out across supplementary backends, but product UX should also degrade gracefully when the system cannot confidently infer intent.

Agent-facing web search has a different target shape than human search. Human search engines are optimized for short keyword queries, click-worthy pages, and a few links a person can inspect; agents can submit paragraph-length context, run many searches, ask for high-recall result sets, and process retrieved pages quickly. Neural web search extends the retrieval substrate by embedding documents and queries so semantic constraints, negation, and long-form intent can be represented directly. Agentic search APIs should therefore expose controls such as result count, domains, dates, and neural versus keyword mode instead of hiding all retrieval policy behind one opaque search box.

Open-web retrieval also has an adversarial reliability problem that is distinct from relevance tuning. A large fraction of the public web actively resists automation: a default agent fetch cannot reach roughly 20% of sites that block AI crawling, and some defenses now poison rather than block by feeding detected bots fake data. The dangerous part is that the failure is silent. A blocked, empty, challenged, or poisoned page is usually not surfaced by the model; because LLMs are tuned to please, they fall back to stale training data or fabricate, producing dead 404 citations and invented links and prices that look like grounded answers. The practical fix is to keep the agent from getting blocked so real content reaches it: managed web-access infrastructure pairs residential-quality IPs, human-like browser fingerprints, automatic CAPTCHA solving, scrape-to-markdown, batch search, and parallel sessions, plus pre-collected public datasets the agent can filter when fresh-to-the-minute data is unnecessary. This means web grounding should be treated as access-layer engineering and verified with retrieved-evidence checks, not assumed from the model claiming it searched. A follow-on talk from the same provider details that layer further — a curl-any-URL "web unlocker" returning HTML with correct headers/cookies and a solved-CAPTCHA token, ~500 pre-built per-site APIs that return structured JSON, and geo-targetable remote browsers that mimic human input — and notes the access matters most on the ~20% of "juiciest" domains behind Akamai/DataDome/Cloudflare, with the legal footing ("public data is public data") tested in won lawsuits against Meta and X.

Document extraction for enterprise retrieval often needs a domain-operated template layer before chunks become trusted structured data. BlackRock's knowledge-app sandbox treats field source, type, required status, validations, dependencies, labels, embeddings, and business tags as configurable retrieval and extraction metadata, so operators can compare runs and refine evidence before downstream systems consume the output.

Operational graphs add a schema-normalization burden before retrieval even starts. Network agents may need controllers, devices, telemetry, SIEM data, and configuration files normalized into an agent-readable graph so queries hit the right layer of production state; when the schema and query workload are stable, a specialized graph-query agent can be trained on schema and example queries to reduce token-heavy exploration.

Private research agents can treat connectors and uploads as complementary retrieval inputs. A connector such as Notion or Microsoft 365 provides durable organizational context, while uploaded receipts, PDFs, screenshots, or task files provide local evidence for the current run. The workflow becomes more useful when the agent can compare both layers and write results back to the right internal page or record. Enterprise deep research applies the same private-context idea to larger document-heavy corpora: the agent runs multi-step or parallel investigation over internal sources, reflects on retrieved evidence, and synthesizes a cited report. That raises the retrieval bar because multimodal ingestion, hybrid search, metadata, reranking, access control, hallucination checks, deployment boundaries, and observability all affect whether the research output can be trusted.

Enterprise RAG can also become a bridge to licensed APIs, not only a search box over uploaded files. Large data-room RAG is useful when it handles mixed file formats and huge corpora, but some facts sit behind third-party databases or internal APIs. Embedding or otherwise exposing API specs to the LLM lets the retrieval workflow call those sources directly; teams still need to design multi-step workflows for broad questions because ordinary RAG does not automatically reason across every document.

Product work graphs are another retrieval target. A product-intelligence pipeline can combine hybrid search, query rewriting, reranking, deterministic rules, and relationship explanations so issues retrieve related issues, likely owners, duplicates, projects, and customer-feedback clusters. That turns retrieval into coordination infrastructure: the agent does not only need relevant chunks, it needs the work relationships that tell it where an issue belongs and who should act.

Workflow search treats prior enterprise processes as retrieval units. A task can retrieve similar task-workflow examples and pass their steps to the agent as dynamic prompt context; this is especially useful when the desired behavior depends on current company protocols, team practice, or executive metrics. The retrieval layer needs ordinary similarity signals plus authoritativeness signals such as who created the workflow, whether it succeeded, and whether trusted coworkers discussed it.

Retrieval freshness is also an operational reliability concern, not only a quality dial. A Databricks production case shows the failure mode concretely: after a bank changed its interest-rate policy, the new policy document was never re-embedded into the vector database, so the RAG agent confidently served stale answers and customer satisfaction dropped until tracing localized the cause. The durable lesson is that the retrieval index is part of a data foundation that needs an embedding-refresh and lineage plan; metadata such as table, column, and PII descriptions further helps agents query enterprise data correctly.

What you embed matters as much as which model embeds it, especially when the corpus is not uniform. PostHog found that off-the-shelf embedding models cluster heterogeneous product signals (errors, logs, Slack messages, session replays) by structural similarity rather than meaning, so all errors land in one region of embedding space and all chat messages in another, and cross-format signals describing the same problem never group together. The fix is an indexing-side rewrite: instead of embedding the raw signal, ask an LLM what the signal is about, generate a short query or description, and embed that meaning-bearing surrogate so clustering reflects semantics. This is the indexing counterpart to query rewriting, and it underlines that normalization is a prerequisite for clustering when source formats differ.

Context-supply strategy is itself a retrieval decision when the goal is to avoid dumping a whole corpus. Qodo frames it as a menu chosen by developer-input cost and scaling because models drop the middle of a long prompt: a ranking context engine (a "bouncer" that builds search patterns and ranking logic, but whose indexing becomes unpredictable past ~600-700 repositories), per-file/folder hierarchical summarization (high upfront LLM cost and re-mapping on every change), a knowledge graph (very high setup, but it "works wonders" for cross-file and cross-repo logical dependencies), iterative retrieval (a low-setup index that acts as a "library card" the agent follows into the code, the recommended default when you are not building a context product), or self-correction with a critic node. These map onto the retrieval techniques this topic already covers — summarization, graph traversal, and agentic iterative search — but ranked here by setup cost rather than query shape.

The "RAG is dead" discourse is best read as a definitional confusion rather than a real obsolescence claim. Turbopuffer's framing splits retrieval-augmented generation back into its parts: retrieval is not a single vector-search call but vector search, full-text/BM25, grep, glob, regex, and filters used iteratively by an agent, which is exactly what "agentic search" already means — so agentic search is a superset of RAG, not its replacement, and Google search volume for "RAG" hit a new inflection point in mid-2025 even as the Twitter narrative said the opposite. The sharper engineering frame is that embeddings and semantic search are *cached compute*: whether to build a persistent index or rediscover context per session is a query-volume decision, not a correctness one. Claude Code's grep-read-assess-repeat discovery pays the cost every run (one sub-step can cost ~6,000 tokens, and the same question is rediscovered across many developers and days), while Cursor pays a one-time parse/chunk/embed cost and then answers cheaply with a lightweight runtime tool; neither is wrong, they are opposite tradeoffs. The upfront index becomes cheaper to maintain when near-duplicate working copies share most of their content: Cursor uses Merkle-tree diffing to copy an existing index and re-embed only changed files across a team, and its measured semantic-search gains (almost 24% answer-accuracy on the composer model, plus retention and satisfaction deltas) show why the cache is worth building. Long context does not retire any of this — Jeff Dean's "you don't need a trillion at once, you need the right million" frames staged retrieval as more important as windows grow, not less.

Retrieval quality, not reasoning, is increasingly the bottleneck for knowledge work, and Mixedbread makes that measurable with the *Oracle gap*. Model reasoning has grown roughly exponentially (GPT-3.5 → GPT-5) while search has crept forward for ~20 years, and since retrieval tools are the main access pattern reasoning uses to reach real knowledge (legal, finance, deep research), the divergence — their "knowledge gap" — makes retrieval the limiter. The diagnostic: score a model when handed the correct documents (Oracle: 93% on BrowseComp Plus, 64% on FinanceQA Pro) versus over the real noisy corpus (Codex with default tools drops to single digits), and the delta is retrieval loss recoverable at the tool layer — their late-interaction search brought GPT-5 within ~3 points of Oracle on BrowseComp and nearly closed FinanceQA Pro, with no change to the answer model. Crucially, a stronger retriever is not enough: models default to keyword-salad queries (a real emitted query was pure keyword gibberish) because they were trained on coding agents (grep/regex), on human-optimized web tools, and against BM25-favoring "caveman-style" benchmark queries (BEIR/NanoBEIR), so they guess keywords to maximize lexical overlap instead of expressing intent. The fix is to co-design agent and retriever: a harness with separable tools (wide summary-only overview search over up to 50 chunks, full-payload top-10 semantic search, a metadata-facet filter, and grep), a short loop of ≤4 rounds with parallel per-round searches, an initial semantic preview plus facet hints, intent split into ≤4 aspect queries each routed to the best tool, deduplicated chunks for context hygiene, and a submitted final ranking — plus prompt levers that steer sentence-shaped queries (notably asking the model to "write one concise sentence describing what it wants to find" rather than "write a search query"). On top of the harness they distill a small fast agent (SFT from a teacher, then on-policy RL) against a composite search reward that scores both the ranked output (NDCG plus an LLM rubric judge) and the trajectory (an LLM judge rewarding query naturalness and the right exploration depth), reaching NDCG@10 of 0.4 on an OpenCongress-style benchmark (vs 0.18 for the best paper baseline) and top-1 on Snowflake's DocQA with Gemini 2.5 Flash as the answer model. This reframes the query-quality half of retrieval as a training/harness problem, not only a retriever-choice problem.

A benchmark from the same Turbopuffer speaker sharpens both the payoff and the limits of code semantic search. Measured on ContextBench — which scores the agent's *trajectory* (did it read the right files, lines, and symbols) rather than whether it solved the task — adding a semantic-search tool to Claude Code raised file precision from a 65% baseline to 87%, i.e. wasted file reads fell from 1-in-3 to 1-in-5 (windowed grep) to 1-in-8 (windowed grep + semantic). But the gain is conditional and uneven. First, grep and semantic search win *different* query shapes: grep wins import tracing where the keyword is present, while semantic search wins behavior-adjacent tasks where related files share no keywords (e.g. ORMs across libraries) — the same lexical-vs-vector split this topic already documents, now confirmed on code. Second, the tool only helps as much as the model knows when to call it: bolted onto Claude Code as "just another tool in the list," semantic search underperformed the ~24% gains Cursor's trained-in Composer achieves with the identical capability. And the index quality itself depends on bridging the query↔code format gap — "semantic search is just similarity search," so good inline comments, synthetic comment injection, or parent-child (natural-language description ↔ raw code) chunking make the embedded code more findable.

Seller-facing agents show a product-specific version of retrieval as onboarding. Instead of asking users to manually prefill product offers, value props, pain points, case studies, and ICP fields, the product can ingest seller materials once and retrieve only the relevant chunks at message-generation time. That makes parsing and chunking part of the user experience: decks, websites, screenshots, calls, and videos need to become structured text before retrieval can help the agent write grounded outbound messages. Because this retrieval directly shapes customer-facing output, the workflow should expose retrieved chunks in the UI and then benchmark parsing accuracy, completeness, hallucinations, hybrid search, and cost once real usage exists.

Expert-domain RAG adds another layer of corpus and query modeling. Legal retrieval may need to work across on-demand uploads, project vaults, and global law or regulation corpora, while a single query can combine semantic intent, jurisdiction, dates, named directives, multiple provisions, and domain abbreviations. Dense retrieval alone is not the architecture; the system needs domain experts to shape representation, preprocessing, categorization, sparse and dense matching, filters, reranking, and evaluation.

Tax explanation systems add a regulated consumer version of expert-domain retrieval. Static summary explanations can use prepared prompts over known user state, while dynamic tax Q&A may need RAG or GraphRAG over yearly IRS changes, proprietary tax knowledge, and internal tax engines. The retrieval layer is still subordinate to product usefulness and deterministic correctness: GraphRAG can improve response quality for relationship-heavy tax knowledge, but personalized answers and authoritative numbers matter more than adding graph traversal by default.

## Open Questions

- How should retrieval systems route between source-of-truth systems and curated context blocks when they disagree?
- Which retrieval steps benefit from hot-swappable small models rather than a single general embedding or reranking service?
- How should Graph RAG or graph summarization systems preserve permission boundaries when summaries cross source scopes?
- Which graph-traversal depths, graph-acceleration libraries, and RAG evaluation metrics produce the best relevance-latency balance for each corpus?
- Which operational graph schemas are documented enough for LLM agents to use reliably without repeated schema rediscovery?
- How should personal retrieval distinguish durable notes from stale bookmarks and noisy saved material?
- What status metadata should retrieval systems use to demote closed PRDs and historical planning artifacts?
- When should cross-modal retrieval use one omnimodal embedding space instead of separate modality-specific indexes plus fusion?
- For heterogeneous-signal clustering, when is embedding an LLM-generated description better than fine-tuning an embedding model on the mixed corpus?
- When should visual-document RAG preserve page images instead of extracting OCR text and structured table/image chunks?
- Which RAG pipeline changes should be exposed as user-facing filters, operator settings, or internal LangFlow-style flow edits?
- Which private corpora are too sensitive to expose through third-party or loosely protected embedding stores?
- Which advisory tasks need graph-backed quantitative computation, and which should remain simple vector lookup?
- How much synthetic-query calibration is enough before real query logs exist?
- What evidence should a seller-agent UI expose so operators can debug whether generated outreach used the right retrieved context?
- Which domain constraints belong in query planning, filters, rerankers, or corpus preprocessing for expert legal and regulatory RAG?
- Which RAG failures should be fixed through retrieval engineering, and which should be punted to UX clarification or broader result selection?
- Which query shapes should route to lexical-only, vector-only, hybrid, or reranked retrieval in a given corpus?
- Which AI search providers expose enough retrieved-document evidence to support reference-free quality metrics at production scale?
- Which agent search tasks need high-recall semantic web search, and which are better served by keyword search plus reranking or filters?
- At what query-volume and corpus-churn threshold does a persistent semantic index beat per-session grep-read-assess discovery for a given codebase or document set?
