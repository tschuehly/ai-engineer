# Voice Agents

## Overview

Voice agents add realtime audio constraints to the usual agent stack of model, instructions, tools, and runtime. The central architecture choice is whether to chain speech-to-text, text reasoning, and text-to-speech components or use a speech-to-speech model that preserves conversational semantics and reduces latency. Cascaded stacks remain useful when teams need explicit monitoring, provider/model choice, RAG, function calling, and language-control tools, but they need tight placement of audio and LLM services to keep latency tolerable. The operational target is voice-to-voice latency: the full path from the user stopping speech to the first returned audio, not only model response time. Stateful streaming APIs extend that decision into a runtime shape: audio buffers, visual frames, transcriptions, realtime events, and tool calls may all flow over one session. Low-latency consumer products may prioritize expressiveness and responsiveness, while customer-service workflows often need stronger accuracy, integrations, and guardrails even if the experience is less fluid. For open-source realtime TTS, serving must also be measured in audio-token throughput: codec-token voice models need enough generated tokens per second to keep up with playback, and generated leading silence wastes the same latency budget even when filtered before the user hears it. Frameworks such as Pipecat make that runtime explicit as a frame pipeline: transports, STT, LLMs, TTS, native speech models, tools, recording, transcription, and observers can be composed as streaming processors instead of hidden inside one monolithic bot. Pipecat's deployment framing adds that production voice agents also need a realtime session layer around the pipeline: cold starts, autoscaling, global routing, telephony/WebRTC endpoints, data residency, and inference-server placement affect whether a caller hears the agent quickly and gets sub-second responses. Realtime media transport is part of the agent architecture: WebRTC should carry browser, native, and edge-to-cloud audio/video streams when packet freshness, jitter handling, bandwidth adaptation, and observability matter more than TCP-style in-order delivery. WebRTC topology can also match the product shape, from local peer-to-peer devices to cloud AI servers to multiparty agents in meetings. Voice AI can also become a hardware and developer ecosystem: app editors, dev kits, open source, and custom hardware form factors let assistants move from smart speakers into robots, toys, appliances, and home automation. Voice can also be a presentation layer over explicit retrieval workflows: a visual-document RAG agent can retrieve page images, construct multimodal answer prompts, and then speak the grounded answer. Contact-center voice intelligence adds a data-pipeline shape: preserve speaker channels, tune STT with domain vocabulary and normalization, extract structured JSON, mask PII before LLM processing, and verify CRM-bound summaries before durable updates. Multilingual agents need explicit language detection and switching policies rather than treating language as only a transcription feature, especially when official-language requirements or mixed-language conversations affect user comfort. Production voice systems should keep the conversational agent's tool surface small, delegate complex tasks to specialist agents or models, and preserve context through summarized handoffs. Slow tools need spoken waiting states, bounded timeouts, or queued follow-up paths so unavoidable backend latency does not become dead air. Turn-taking is itself a production behavior: fixed VAD and silence timeouts are too blunt for pauses, backchannels, and culture- or speaker-specific response timing, so semantic end-of-turn detection should use conversation context, transcript meaning, syntax, prosody, and acoustic cues. Background audio is another production behavior, not just a transcription detail: speech-like noise can trigger interruptions and pseudo-transcripts that cause downstream inference at the wrong time. Full-duplex speech models point to a different path where listening, silence, speech, and backchannels are learned from raw audio, but cascaded pipelines may remain preferable when products need stronger control over pronunciation, brand terms, instruction following, tool integration, and evaluation. Evaluation needs traces, labeled conversations, transcript-based checks, audio-specific judgments, synthetic conversations, turn-taking benchmarks, release evals across realtime provider services, and guardrails that fit within the timing of spoken responses. Autonomous voice-agent evals should also borrow from self-driving simulation: run many multi-turn conversations, measure failure probabilities, calibrate realism to the behavior under test, and feed production bugs back into regression suites and monitoring dashboards. Generated voice safety also requires platform controls beyond model behavior: consent checks for cloning, moderation for restricted speech, and provenance signals such as watermarking help respond to fraud and impersonation. A frontier multimodal model can also collapse parts of the audio stack: one call with a response schema can return a rich structured profile of a recording — diarization with speaker names, timestamps, per-segment language detection with translation, emotion, and a summary — instead of chaining ASR, diarization, language-ID, and emotion models, useful when speaker channels are not separable. The same audio understanding changes speech generation: rather than filtering a large voice catalogue, a small set of base voices is steered by a natural-language director's note (audio profile, scene, performance guidance) so accents and personas are synthesized on demand, with the caveat that a directed accent can bleed across languages. Native sound-to-sound real-time models (e.g. Gemini 3.1 Flash Live) push this further by ingesting text/audio/video over a WebSocket with thinking baked into the model rather than cascaded through a text LLM, and they can orchestrate generative media by calling a media-generation model (such as Lyria 3 for music) as a tool, letting the conversation gather the creative brief before generating. Underneath "rich transcription" sits speaker diarization — "who speaks when" — a distinct, still-unsolved task with its own pipeline (voice activity detection → segmentation/overlap → speaker assignment), its own difficulties (unknown speaker count, permutation-invariant labels, overlapping speech, very short turns), and its own metric (diarization error rate = confusion + false alarm + missed detection over total speech), where the conversation-understanding ladder rises from "what was said" to who said what, *when* (interruptions, backchannels, pauses), and *how* (laughter, stress, prosody). Speaker-attributed transcription is harder than a timestamp join: STT is mostly single-speaker-trained, boundary words straddle two turns, and the two models' timestamps disagree, so production stacks reconcile them with an STT-agnostic orchestration layer (an "exclusive diarization" trick that, on overlap, picks the single most-likely speaker for the STT) — the architectural opposite of collapsing everything into one multimodal call. Above the architecture sits an interaction-design layer that good ASR/TTS does not solve: a viral "talk to a statue" build (ElevenLabs Voice Design API → an agent → a phone call in ~30 seconds) surfaced that voice is a strong *input* channel for dumping raw intent but a weak *output* channel for dense information, so the better shape is single-stream voice input paired with parallel high-density multimodal output (text, diagrams, generative UI) rather than symmetric voice-in/voice-out; concise speech "sounds rude" where concise text does not, voice can deliver companionship and motivation rather than facts, and "skim listening" (jump forward by concept, not sentence) is still missing. Turn-taking is as much a UX problem as a detection one: people are too polite to interrupt, so push-to-talk beats unreliable barge-in detection, an "agent-wants-to-interject" nudge can signal *which topic* it wants to raise, and because platforms generate the full text before TTS, a mid-speech interruption can be handled by using audio-playback timestamps to truncate the transcript so the model "forgets" what it generated past the interruption. Hardware form factors extend the same goal of removing the screen so the agent does not feel "tacked on" — a statue or red phone booth with an embedded mic/speaker you talk to directly — and raise the question of deriving an object's voice from its provenance. At the engineering layer, building voice agents "at scale" is an "and problem": low latency, baseline intelligence/tool-calling, natural voice, and reliability across thousands of concurrent calls must all hold at once. Two production levers tie the pipeline together. First, the LLM dominates the shared latency/cost budget (then TTS, then STT), so its size is set by a time-to-first-token target (~200-300 ms) that pins it to an ~8-30B sweet spot — larger blows the budget, smaller breaks tool calling — with use-case fine-tuning to recover tool-calling quality in a small model. Second, total latency is engine latency (model compute) *plus* network latency (data-center hops), and once engine latency is optimized the biggest remaining win is co-locating every model and the orchestrator: dropping a ~75 ms cross-region hop to ~5 ms is a ~30% cut even in an already-optimized pipeline, which is the latency case for self-hosting an open model near the agent rather than calling a distant managed API. Around this, classifiers route before the LLM and guardrails run after generation but before TTS (spoken audio cannot be unsaid), the "thinker-talker" pattern lets a small conversation model emit immediate filler and delegate hard work via a single tool call to a bigger model, and autoscaling must be aggressive on the way up but drain stateful long-lived sessions on the way down.

- [Realtime multimodal models should plan over specialized local actuators](../concepts/realtime-multimodal-models-should-plan-over-specialized-local-actuators.md) - realtime multimodal models can interpret speech or vision while specialized components execute embodied actions.
- [Choose voice-agent architecture by latency, accuracy, and semantics](../concepts/choose-voice-agent-architecture-by-latency-accuracy-and-semantics.md) - architecture should match whether the product prioritizes responsiveness, semantic preservation, deterministic control, or system integration.

- [Design voice agents around voice-to-voice latency budgets](../concepts/design-voice-agents-around-voice-to-voice-latency-budgets.md) - spoken UX depends on the full speech-input-to-speech-output path fitting conversational timing.

- [Remove Head-Of-Line Silence From Voice Models](../concepts/remove-head-of-line-silence-from-voice-models.md) - leading generated silence can waste compute and latency before any useful audio reaches the user.

- [Realtime multimodal agents use stateful streams for audio, vision, and tools](../concepts/realtime-multimodal-agents-use-stateful-streams-for-audio-vision-and-tools.md) - live audio agents can include visual context, streaming events, transcriptions, and tools in the same session.

## Open Questions

- Which voice-agent workflows should accept extra latency for chained control rather than use a lower-latency speech-to-speech model?
- What audio-specific eval rubrics reliably measure brand fit, pacing, interruption handling, and conversational comfort?
- What benchmark data can evaluate turn-taking across pauses, incomplete thoughts, backchannels, barge-ins, and speaker-specific response timing?
- How should teams evaluate multimodal voice agents when the relevant context includes screen frames or camera input as well as transcript content?
- When is voice output enough over a visual-RAG backend, and when does the product need a fully realtime speech-to-speech architecture?
- Which contact-center fields can be auto-confirmed safely, and which always require operator validation before CRM sync?
- Which voice-device capabilities should be exposed through app editors and dev kits, and which should remain fixed platform behavior?
- How should teams set thresholds for semantic end-of-turn models so interruption behavior balances latency with the user's need to pause and think?
- Which voice products can tolerate prototype WebSocket transports, and which need WebRTC before user testing is meaningful?
- How should multilingual voice products decide when to auto-switch language, ask for confirmation, or constrain mixed-language turns?
- Which long-running enterprise voice tasks should stay synchronous with spoken status updates, and which should become queued follow-up work?
- What provenance and consent controls are sufficient for generated-voice features in high-risk domains?
