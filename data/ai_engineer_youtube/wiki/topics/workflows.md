# Workflows

## Overview

Personal-agent workflows need domain separation and proactive task flow once they move beyond one recurring pain. A single chat can collapse unrelated work and life contexts; multi-topic workspaces preserve context boundaries, show tool progress, and let the agent ask the human for decisions or missing artifacts while background work continues. Read-only observer workflows are a lower-authority alternative for high-stakes personal domains: they gather signals, produce reflection artifacts, and leave outreach, scheduling, and writing decisions to the user.

Agent workflows become more reliable when they expose a tight loop between work execution, failure observation, missing-context discovery, and documentation updates. Demand-driven context uses that loop to grow enterprise context from real tasks rather than from speculative upfront curation. Production AI application workflows add another loop: stage the agent, trace it, evaluate it on golden cases, deploy managed prompts/tools/scores, monitor production traces, replay failures, and rerun regression checks before promoting fixes. Personal-agent workflows apply the same idea to permissions and trust: start from one recurring pain, add one simple workflow, watch it fail or succeed, then add guardrails before expanding autonomy. Human-in-the-loop automations make those guardrails concrete by pausing sensitive actions for explicit approval, keeping credentials scoped, and logging waiting or resumed executions. Voice-agent workflows need a similar staged design: start with a narrow realtime conversation path, add tools sparingly, preserve context across handoffs, and validate both transcript behavior and audio delivery before expanding coverage. Coding-agent loops apply the same principle to implementation work: keep each run small, make progress observable, and feed defects or process lessons into the next prompt or skill. Product codegen workflows can reduce variation by breadcrumbing the agent through discovery, candidate event design, shared vocabulary, and then implementation, and can use post-run self-interrogation to discover missing tools or contradictory context. AI-amplified product work also needs explicit quality routines: recurring quality reviews train engineers to find small regressions, and zero-bug policies turn defect inflow into immediate triage rather than postponed cleanup. For agentic software work, workflow design should deliberately trade upfront planning against later review effort, should make feedback speed and review capacity the limit on change size, and should use parallel queues only when the interface preserves human focus around completed work. Harness-oriented workflows turn repeated review lessons into durable context, lints, reviewer agents, and PR comments so non-functional requirements are refreshed throughout long-running agent work instead of relying on one initial prompt. Workflows should also reintroduce friction where it carries judgment: database migrations, permission changes, dependency additions, architecture, and reliability decisions need explicit human gates even when mechanical bugs can be sent back to the agent automatically. Parent-agent comparison workflows can run multiple models or strategies in isolated workspaces, then help the user review, rank, and combine the results. Spatial orchestration workflows add filesystem visibility, collision heat maps, agent-discovered quest queues, containerized decomposition, and evidence-rich review bundles so many agent runs can be supervised without constant babysitting. When that workflow is encoded as prompts rather than runtime code, its eval loop must verify both desired work and absence of forbidden side effects. Outside coding, agents are useful when they shorten feedback cycles for collaborators who can hand over natural artifacts, and when they absorb the prerequisite work that otherwise blocks progress. Canvas-native workflows strengthen that artifact handoff by letting users draw, annotate, select, and revise directly on the same surface the agent reads and edits. Multi-agent canvas workflows can also make shared state, leader/follower delegation, overlapping work, and completion review visible rather than hidden in logs. Context-engine workflows should also surface unresolved source conflicts, recompute from current sources when answers may be stale, and route clarification back into durable context. Skill and context-package workflows should be developed like library workflows: define expected behavior, package guidance, evaluate changes, distribute reusable context, observe use through logs and review, then update shared packages when the workflow changes. Ambient-agent workflows add a maintenance loop: overnight indexing, backups, memory refreshes, update validation, cleanup, and notification filtering keep the system ready without forcing the user to watch every operation.

Designing a production AI application is itself a workflow, and the reusable shape is requirements-first and four-phased: product requirements → system design → evaluation and monitoring → optimization. Because AI can now write the code, the leverage is in the earlier decisions, and most systems fail in production from bad choices made there rather than from bad code. The requirements phase quantifies a *solution-agnostic* business problem (user-specific, current state, quantified pain, no prescribed architecture), gathers business and performance constraints up front as design inputs, classifies the role of AI (critical vs complementary, reactive vs proactive, autonomy level), and states a SMART success metric. System design then works out a per-source data strategy (residence, update cadence, processing, retrieval technique), maps the request flow, and composes the *simplest* set of AI design patterns — RAG, control flow, LLM-as-router, human-in-the-loop, fine-tuning — instead of jumping to an agent, because the common failure mode is over-engineering before knowing what is actually failing. The discipline is to start simple, evaluate, find gaps, and iterate, which is the same "add structure where reliability fails" logic applied at whole-system scope.

Sustainable solo-developer workflows treat the human, not the agents, as the scaling bottleneck. Because agents can loop infinitely until they hit your verification criteria while human attention degrades under load, a personal workflow should be built to conserve attention rather than to maximize agent throughput. WorkOS's stack illustrates four reusable layers: a signal layer where an agent reads Slack and Linear on a loop, deduplicates asks, and surfaces only the real high-priority work so the developer is never pulled off task; voice-first dictation (~184 wpm) that enables driving several agent windows in parallel; remote control of a session that runs on the dev machine but is driven from a phone over LTE, so diffuse-mode insight is captured and PRs are reviewed away from the desk; and a scheduled retrospective over locally stored JSONL conversation history that finds struggle and churn patterns and generates the missing skills or MCP servers. "Speed requires safety" governs how far the human can step away: a verification ladder escalates from lint/build/unit-test hooks, to agent browser click-through, to a constitutional critic agent. The advice is to add one layer at a time and reinvest the recovered margin in time away from the keyboard, because the default path with these tools is faster burnout while the intentional path keeps the human responsible for quality, review, and shipping.

Complex vertical workflows add another design dimension: make ambiguous work more verifiable through decomposition, proxy checks, and guardrails; when uncertainty remains, let agents record reversible decisions instead of blocking on low-context chat questions. Artifact-native surfaces help humans review the specific branch of the work tree where their judgment is needed. Deep-research-to-writing pipelines show the same principle in a content workflow: keep exploratory evidence gathering agentic, then hand a `research.md` artifact to a tighter writing workflow with guidelines, few-shot examples, reviewer loops, and versioned drafts. AI adoption workflows should also avoid Goodharted usage goals: visible token counts, spend leaderboards, and top-down usage mandates can reward performative usage, while effective adoption requires hands-on experimentation against real work, clear augmentation intent, and enough psychological safety for engineers to report where tools fail. Measurement should be open about why data is collected and should connect utilization to quality, speed, and cost instead of treating adoption itself as the finish line. Workflow products should also bring domain context to the user instead of asking every user to prompt from scratch: the "Cursor for X" pattern is to know the user's job well enough to collect context automatically, orchestrate multiple models or tools, and present outputs in the review surface where the work already happens.

Domain-native LLM workflows need a production-to-expert-to-engineering loop. Live outputs should flow into an expert review surface that includes the source evidence, policy or guideline context, AI reasoning, correctness labels, failure-mode labels, and suggested domain knowledge. A domain-expert PM can then prioritize the failure sets that most affect customer metrics, ask engineering to hit explicit thresholds, and decide whether measured improvements should go live.

Enterprise AI operating models should change the workflow shape, not only the tool list. AI-native software work can move from quarterly planning toward continuous planning, from story-driven handoffs toward spec-driven work, and from uniform Agile ceremonies toward work-type-specific collaboration: agent factories for high-context but well-defined modernization, iterative co-creation for feature discovery, and workflow-specific squads for bug fixes or greenfield development. Expectations, hands-on coaching, bring-your-own-code practice, first-sprint habit formation, incentives, and outcome measurement need to move together or usage can rise without impact.

A 30-day roadmap-pause sprint is one concrete version of that reserved-capacity cadence. Automattic's "Radical Speed Month" paused the roadmap, put people in two-person pairs with full autonomy, and asked them to ship something real — and it changed individual workflows, not just output. Two shifts generalize. For design work, the coded prototype replaces the high-fidelity mockup as the primary artifact of iteration: the old loop was start in Figma and stay until very high fidelity, the new loop is plan → build the prototype/product in code (iterate on the live product directly) → return to Figma only later for a mood board and UI fine-tuning. Running exploration "as a Cloud Code project folder where all of the chats and ideas were recorded into a file system" was reported to "significantly speed up collaboration as well as build" and became a retained daily practice. For team composition, once non-engineers contribute in code, the strongest specialist's best use of time is enabling and teaching teammates rather than doing more of their specialty. The transferable operating rule is that a large org changes process by shifting human behavior — access, enablers and champions, space to experiment, and agency to break habits.

AI-first SaaS transformation adds an operating cadence around uncertainty itself. Instead of treating AI exploration as isolated spikes, teams can reserve planning-cycle capacity for experiments, hackathons, learning forums, and MVPs that validate direction. Process should remain subject to outcome review: if a new ritual does not create clarity, unblock teams, or improve decision speed, it should be changed or removed before it becomes transformation overhead. Dynamic-product workflows add a staged product-integration path: crawl by embedding AI into existing workflows, walk by adding contextual and personalized surfaces, and run only when cross-product agentic behavior justifies rethinking UI, UX, and application architecture.

Compressed research is a lower-risk operations pattern: keep the business event and human decision in place, but let an agent gather, classify, route, or summarize the evidence that made the work slow. This is especially useful when the source information already exists in company systems but is not available in the right place at decision time. Enterprise deep research is the document-centric version of that workflow: it fits tasks such as RFP responses, onboarding guides, and investment memos where the hard part is searching many private sources, choosing the right evidence, and synthesizing a cited artifact that a human can review or adapt.

Scientific and government workflows show a higher-consequence version of compressed research. An agent can read papers, discover adjacent literature, propose a hypothesis, generate executable code, and hand the result to domain simulation infrastructure, but regulated deployment adds a parallel workflow for pilot governance, risk classification, data-boundary review, SBOMs, patching plans, continuous monitoring, and restricted-region or self-hosted availability.

Realtime co-scientist workflows add a live experiment loop to that pattern: enumerate available sensors, cameras, outputs, safety constraints, and measurement goals; define the experiment protocol; assemble the active multimodal context for each model call; record traces and CSVs; analyze condition changes and outcomes; then feed traces into simulations or the next physical run. The smallest useful workflow is bounded by what can be safely measured and acted on, not by the model's ability to write a plausible hypothesis.

Open-source agent workflows have their own bottleneck: AI can generate more reports, PRs, and fixes than maintainers can safely absorb. Projects need triage loops, contribution boundaries, foundation or company support for sustained maintenance, extension points so experiments can happen without turning every idea into core-review load, and human-effort filters that require concise contributor context before maintainers spend review time.

Org-chart agent workflows add a business-operations control surface: assign work through roles, keep plans and tasks visible, route completion through reviewer and approver agents, and convert repeated prompts into scheduled or manually parameterized routines. They should grow from the smallest useful agent set because role behavior, skill use, budgets, model cost, and concurrency all need validation before fan-out.

Repository-local web-agent workflows can make implementation, verification, preview sharing, and handoff rules part of the repeatable routine. Skills can teach the agent how to inspect issues, run browser QA, record evidence, create a public preview tunnel, notify a reviewer, and wait for confirmation before closing work.

High-assurance agent workflows should make risk analysis and verification separate from code generation. A practical flow can ask one agent context to implement, another prompt or model to write tests and safety cases, and deterministic or formal tools to check critical properties; the workflow should also prefer trusted libraries for behavior that would be expensive to re-verify if generated from scratch.

Agentic payment workflows show where that determinism boundary should fall when money moves. Stripe's framing is that discovery and exploration should stay non-deterministic (the LLM finds what to buy), but credentials, payments, and checkout should shift to exclusively deterministic flows, because a non-deterministic transaction path produces the four failure modes of buying from the wrong place, the wrong thing, the wrong amount, or with the wrong credential. The reusable workflow shape is a non-deterministic planner feeding a deterministic, constrained execution path with verifiable parties and structured negotiation — for example a back-and-forth between agent, seller, and PSP that relays cart state on each step so the agent proxy cannot mis-relay tax, quantity, or shipping into a dispute. This is the commerce-specific instance of the broader rule that mandatory, sensitive, or irreversible steps belong outside the model's free-form reasoning.

Multi-agent workflows need explicit coordination and recovery choices. Event-driven choreography works when agents can act independently and the system can trace every event; centralized orchestration works when dependencies, state, rollback, or auditability matter more than autonomy. Large refactor workflows make the dependency problem concrete: scan or visualize the code graph, form PR-sized batches, dispatch fixers only when upstream dependencies are ready, review and merge small outputs, then repeat as new batches unblock. Durable workflows should pass immutable state versions through data-contract validation and wrap agent calls with circuit breakers, graceful degradation, and compensation so partial failures do not leave hidden side effects.

Durable workflow engines also address the single-agent production loop. Agent frameworks may provide the fixed loop that calls the LLM, executes requested tools, and feeds results back, but production workflows need persisted turns, retry policy, timeout behavior, and resumable waits around that loop. Human-in-the-loop steps are a useful stress test: the workflow should pause as logical state, release active process resources when needed, and resume when a human response arrives. Workflow-like automations can still justify an agent harness when the middle of the process requires flexible exploration, repository cloning, Docker runs, tests, and structured output rather than only known deterministic steps.

Agentic workflow design should start simple and add autonomy only when it beats the simpler structure. A single chain or branching tree is cheaper, easier to measure, and more reliable when it fits the task; a freer agent loop becomes attractive when chains and trees become too complex to maintain. Hard business rules and side effects should still sit in deterministic state and validation steps, while the model handles enrichment, interpretation, and action selection inside bounded authority.

Python agent workflows can keep ordinary imperative structure while becoming durable. PydanticAI's Temporal demo wraps agents, keeps non-IO orchestration deterministic, places LLM and tool calls behind activity boundaries, and uses normal `TaskGroup`-style parallelism for search branches. That matters for deep research and similar workflows because a crash after planning and search should not require paying for those steps again before final analysis resumes.

Unattended content pipelines are a workflow shape with their own QA economics. TNG's chess channel runs a nightly loop — pull source data, agent-analyze it against grounding tools, emit a structured intermediate artifact, render to narrated video, auto-upload — and once volume exceeds what a human can hand-review, the reliability strategy shifts from gating to sampling: at a low, recoverable per-item error rate (~1-in-20) the operator publishes and takes down mistakes afterward rather than pre-reviewing every asset, treating errors as learning signal about missing tool calls. Two reusable structure choices sit underneath: decoupling the reasoning stage from the rendering stage via a machine-readable intermediate format, and letting the agent own presentation decisions (highlights, arrows, emphasis) instead of a downstream template. The tradeoff — accept a small, reversible defect rate to unlock scale and personalization — is the generate-and-publish analogue of the coding-agent principle that mechanical defects can be sent back automatically while only irreversible steps deserve a human gate.

Pydantic AI's shorter typed-agent demo adds the non-durable inner-loop contract: model calls can produce structured final-result tool calls, Pydantic validation can reject invalid output, and the harness can return the validation error to the model for a corrected retry. The same workflow benefits from observability: traces reveal the model exchanges, tool arguments, validation retries, cost, and latency that explain why a run failed or passed.

Workflow-backed TypeScript agents should keep orchestration deterministic and put LLM calls, sandbox commands, and external APIs behind step boundaries. That makes the running agent easier to inspect through step spans, easier to connect to a resumable UI stream, and easier to control through scheduling, cancellation, and run-version operations when it waits beyond one request.

API-backed agent workflows should be hardened only after their task shape is understood. A practical path is to prototype the repeated work in the provider's web UI, observe which context, files, connectors, and permissions make the run succeed, then encode that stable shape as an API task lifecycle with polling or webhooks. When the workflow starts in a channel such as Slack, store the thread-to-task mapping explicitly so follow-up messages continue the same task and final results return to the user's original conversation.

Contact-center voice workflows show a concrete human-in-the-loop automation pattern: shift after-call documentation from manual memory work into a streamed extraction pipeline, but keep operators responsible for quick validation before the generated summary updates CRM fields. The workflow is only as strong as the early audio and transcript stages; speaker separation, domain STT, masking, grounded JSON extraction, and schema mapping all happen before the final human confirmation.

Platform workflows should be shaped for agent loops as well as human onboarding. Agents need local validation, clear task and success definitions, and callable platform feedback so they can iterate before remote CI or deployment; when agents contribute back to platform code, policy guardrails and repository instructions should separate hard safety boundaries from workflow guidance.

For AI app reliability work, build evals at the start of the workflow rather than after a demo already feels good. A practical loop is to define scenario-level criteria from user outcomes, generate realistic persona and wording variants, inspect failures one by one, and then use the benchmark to compare model, prompt, RAG, logic, or agentic changes while watching for regressions and cost or latency tradeoffs.

Application eval workflows should also map the product domain before optimizing. The team should gather real prompts and feedback, identify in-bounds and out-of-bounds work, keep the data set stable, vary the task logic under test, and run simple debuggable scores in CI so prompt, model, RAG, or preprocessing changes reveal both improvements and regressions.

Metric-building workflows should start from a simple product behavior, then iteratively turn coarse judgment into a scoring system. Teams can begin with a system prompt, examples, or explicit criteria, generate good and bad cases, inspect failures, add correlated signals, and calibrate against human and user behavior. As the scorer matures, it can move from offline spreadsheets and notebooks into online candidate scoring, prompt optimization, synthetic-data filtering, and training loops.

AI application improvement workflows should also inspect both inputs and outputs. Input-side retrieval checks should run quickly enough to support repeated experiments on embedding models, chunking, and top-k choices. Output-side conversation analysis should extract structured fields from chats and agent traces, cluster similar work, and compare KPIs across those clusters so teams can decide whether to add tools, build routers, change prompts, educate users, or refuse unsupported categories. Product discovery workflows need a similarly fast loop: name the real users, show them a concrete artifact such as a PRFAQ, launch post, prototype, or API outline, capture high-bandwidth feedback, and ship a small improvement quickly enough that the loop can run daily.

AI product reliability workflows can turn chaotic model behavior into bounded improvement loops. Teams should continuously inspect app data, define explicit and implicit signals, cluster those signals with user intents, and turn high-priority intents into semi-deterministic workflows. The useful workflow is broad enough to serve many similar cases but narrow enough to be reliable, attributable, and changeable without spilling behavior changes into unrelated workflows.

DSPy-style workflows separate program shape from prompt shape: teams can define signatures and modules, route inputs through ordinary control flow, select adapters for model-facing format, and then optimize the resulting program with datasets and metrics. This is most useful when the task has known examples and quality criteria, not when the workflow is too open-ended to score. Prompt-learning workflows should likewise be made explicit: start from examples with feedback, choose sample size and train/test split, run bounded generate/evaluate/refine loops, and review whether evaluator feedback is trustworthy enough to drive the next prompt.

For coding agents, this workflow can be attached directly to rule files: run the agent on benchmark issues, collect test and judge feedback, use a meta-prompt to draft rule changes, diff the resulting prompt context, and rerun the benchmark before adopting the rules. Shared prompt context also needs ownership: a gatekeeper group can receive feedback on system prompts, Cursor rules, or agent Markdown and keep organization-wide instructions aligned with current frameworks and practices. AI-native products need a related model-behavior workflow: broaden ideation through in-product tools, dogfood ideas with real context, collect evals to clarify requirements, hill-climb through code and prompt changes, and route feedback back into the behavior system after shipping. The same workflow pressure applies to DevEx basics: fast local validation, written external context, clear turn-taking in review, and assigned review ownership keep agent iteration from becoming slow CI loops and rubber-stamped PRs.

OpenHands adds a simple workflow rule for early delegation: start with chores whose outcome is visible, give the agent concrete frameworks, TDD preferences, files, or function names, and discard far-off attempts instead of preserving bad generated context. Agent-created PRs should enter ordinary ownership and review queues so failing checks have a person responsible for follow-up.

Anti-slop workflows should separate quality from provenance. Human and AI work can both be low-quality, inaccurate, or insecure, so the workflow should ask for evidence instead of accepting line count, engagement, or autonomous runtime as progress. AI can still be part of the anti-slop loop when it helps curate what is worth attention, creates code maps that improve codebase understanding, operates development tools through computer use, or sends commoditized work through asynchronous agents while humans keep clear design boundaries.

Production vibe-coding workflows should make safe change the unit of work. A useful loop starts with a Markdown plan or rules file, reviews that context before implementation, runs the agent against a scoped task, uses fast tests and linters for feedback, then spends human attention on review questions that automation cannot settle: whether the change is supportable, secure, production-safe, and aligned with the system's intended direction. For bug-finding work, the prompt surface should be narrower than "find bugs": rules should name specific defect classes, preserve diffs and key files, ask for a component inventory when cross-file reasoning matters, and require tests or other validation before accepting a fix.

Agent-native organizational workflows start with supervision, dispatch, and review of agent work as a normal daily rhythm. This only works when the organization also adapts hiring and onboarding: employees need enough AI fluency to turn domain expertise into agent instructions, review artifacts, and role-specific agent setup. Inside an AI-native engineering organization, the daily workflow can compress into plan, delegate, assess, and codify. Cheap agentic code also changes product persuasion: instead of writing a memo or deck for every weird idea, a team can build a prototype quickly enough that stakeholders can experience it and decide from the artifact.

AI coworker workflow design should choose interaction mode deliberately. Background personalization can stay invisible, workspace scanning can be ambient, artifact transformation can be inline, and app-building or ambiguous direction can remain conversational. The workflow should also leave room for bounded play: realistic prototypes can reveal when an agent should combine inputs, create follow-up artifacts, or escalate missing information back to a human instead of pretending to complete the task.

AI product workflows can deliberately go wide before they narrow. When AI coding assistance makes feature experiments cheap, teams can test many templates, edit paths, chat surfaces, and hidden automations with different user groups, but the workflow must include a cut-back phase. The useful pattern is to pick the user group with strongest evidence, remove unused or confusing controls, and collapse overlapping AI affordances into the simplest validated job flow.

Computer-use workflows should be composed around reliable action primitives when the product surface is a browser UI. Nova Act's example shows a useful pattern: let the agent navigate and extract from the screen, bind outputs to a schema, use ordinary code for helper lookups and parallelism, and use data tooling for final comparison. This keeps the model in the perception/action role while deterministic program structure handles repetition, tabulation, and orchestration.

AI-intensive workflows can also be modeled as many model calls organized around one user-facing artifact. SPADE captures a reusable loop: synchronize input sources, plan the work, analyze in parallel, deliver a reduced artifact, and evaluate the result. This is a stronger design unit than a single prompt/response when the product repeatedly scrapes, researches, summarizes, transforms, or publishes from many inputs.

Proactive coding workflows try to remove the prompt/wait/repeat loop without removing human alignment. The useful shape is not a wall of parallel terminals; it is background observation, repository indexing, candidate task discovery, critic review, Playwright-style verification artifacts, editable memory, and just-in-time context that lets the agent handle friction while the human keeps creative and product judgment. Proactivity should be staged: start with bounded maintenance and best-practice work, then move toward system-level proposals only when the agent can connect code, design, telemetry, and outcome signals.

Enterprise AI research workflows can be made fundable by turning each uncertain phase into a small productizable bet. For GenBI, the useful pattern is to work with production-like but controlled data, involve expert users early, ship six-week deliverables such as metadata enrichment or report discovery, and preserve stop/go decision points so leadership can keep funding tied to measurable value instead of sunk cost.

Enterprise knowledge-app workflows need the same separation between expert iteration and deployment. BlackRock's pattern gives investment-operations experts a sandbox for extraction templates, prompts, field dependencies, QC checks, model strategies, and run comparisons, then sends approved definitions into an app factory for downstream integration. That keeps the fast learning loop close to domain experts while leaving distribution, access control, cost controls, and regulated human review in the production workflow.

AI coding workflows should also separate easy generation from simple system design. Nations' three-phase approach turns one long coding conversation into research, planning, and implementation artifacts with human checkpoints between them. Gallon's framework adds a more granular make-it-work sequence: capture a master project specification, extract and categorize features, develop atomic feature specifications, build a dependency matrix, then produce an implementation plan that sequences phases and binary validation criteria. That structure keeps review at the speed of generation: humans validate the research and plan before the agent produces a diff, then review implementation against a known plan rather than reverse-engineering whatever the chat invented.

Product workflows need the same discipline before generated code or copy enters the loop. A launch workflow should ask whether the marketing artifact has a plausible reason to be shared, whether first use reaches one aha moment before nonessential questions, and whether feature work is building durable primitives rather than one-off surfaces that power users will outgrow.

Backlog.md turns that sequence into a terminal and repo workflow. A human or agent creates a Markdown task, the human checks description and acceptance criteria, the agent writes an implementation plan from the task and codebase, the human reviews direction, and only then does the agent implement and move the task to done when the definition of done is met. Independent tasks can run in parallel through Git worktrees when dependencies are clear.

Preference-learning workflows add a feedback path that runs during normal coding. When a developer edits generated code to change library choice, file structure, parameter shape, test framework, or design details, that correction can become learned taste for later agent runs. The workflow is valuable when it reduces repeated steering without hiding the preference surface from the developer or team.

Architecture-copilot workflows put an aiming step before coding-copilot execution. The recommended rollout is incremental: pick one portfolio area, build live visibility, generate recommendations tied to business outcomes, pilot autonomous guidance with one team, and scale only after the ROI and adoption path are proven.

Frequent intentional compaction adds a context-window version of the same workflow. Research, plan, and implementation are useful because each phase can compact the previous phase into a smaller, reviewed artifact: codebase truth, then implementation intent, then executable change. The workflow should scale with task difficulty rather than become ceremony; a small button change may need direct prompting, while hard brownfield work needs enough compaction and review to keep the agent out of stale or noisy context.

Agent-first IDE workflows make those artifacts live inside the working surface. Antigravity uses the agent manager as a queue and review control plane, lets the model decide when to create a plan, task list, diagram, screenshot, recording, or walkthrough, and lets the user batch comments on text or image artifacts while execution continues. Its dogfooding loop also turns real product use into research feedback about model, tool, and harness gaps.

Outcome-based delivery workflows add an organizational layer around AI-accelerated engineering. A roadmapping phase can turn client goals into product requirements, architecture design documents, and story-pointed tickets, while acceptance gates determine when output becomes compensable. This creates a workflow incentive for AI leverage only if scoping, QA, and customer approval remain separate from the person paid for implementation throughput.

Leadership-led AI workflows should start from the actual SDLC constraint. Code completion is not automatically the highest-leverage target if reverse engineering, onboarding, incidents, context switching, meetings, compliance uncertainty, or missing runbook context dominate delivery. Useful rollouts identify that bottleneck, choose AI use cases that reduce it, then measure whether system outcomes changed. Leadership learning workflows should also avoid learning from only one segment of the market: a cross-segment convening can help AI transformation leaders compare frontier lab direction, startup product velocity, academic framing, consulting patterns, and large-enterprise deployment evidence before turning strategy into a tactical roadmap for their own company.

AI-team workflows need the same bottleneck discipline. An AI mandate should be translated into inner loops for daily execution and outer loops for differentiation, then staffed or upskilled around the weakest loop. Functional prototypes, domain-expert-authored evals, engineer/customer calls, and weekly learning cadences keep product, model, serving, and domain knowledge moving together instead of turning AI work into isolated research, engineering, or product handoffs.

Enterprise AI adoption workflows should then turn isolated pilots into a portfolio. A useful pattern is to classify use cases by impact category, record current ROI separately from expected future ROI, and keep explicit caveats around self-reported or self-selected data. The workflow should also look for movement from first-tier time savings toward automation, agentic workflows, risk reduction, new capabilities, and revenue or product-line impact, because these categories can require different governance, rollout, and measurement loops.

Enterprise engineering adoption also needs workflow scaffolding after the first demo. Bloomberg's rollout suggests starting with broad experimentation, then redirecting scaled effort toward mature-codebase work such as uplift patches and incident response, while using onboarding, training, guilds, inner-source, visiting engineers, and leadership workshops to turn individual tool use into organization-level capability.

Support-led coding workflows add a practical backlog pattern for products with many integrations or other constantly changing surfaces. Zapier's Scout Agent starts from live support issues, runs diagnosis and routing, kicks off an asynchronous GitLab pipeline with plan, execute, and validate phases, attaches a merge request back to Jira, and lets support request another pass inside GitLab before engineering review.

Prompt-to-app workflows can sit before implementation as a product ideation loop. A team can turn a screenshot, rough feature idea, or desired interaction into a runnable UI, inspect alternate interaction patterns, then decide whether to move into a heavier IDE or full-stack runtime. The same workflow needs verification once it crosses from front-end demos into stateful or multiplayer behavior: generated lobbies, collisions, readiness gates, storage, payments, and API integrations should be tested as real runtime behavior rather than accepted as prompt output.

Vibe engineering turns agentic coding into a supervised review workflow rather than a slot-machine loop. A practical pattern is to let the agent produce a change, inspect the running UI, voice-dump observations and bugs, inspect the code, then feed back technical patterns and context through rules, docs, commands, and memories. Loose prompting is acceptable for disposable scripts or one-off tools, but durable code needs enough cleanliness and context structure for future agent runs to continue safely.

Mentoring-oriented coding-agent workflows make delegation explicit before implementation starts. The human supplies the outcome, context, constraints, and boundaries, then lets agents explore or execute in the background while the human preserves focus for critical-path decisions. At team scale, the same workflow captures decisions, meeting outputs, task lists, and successful memories so later agents and teammates inherit the lesson rather than rediscovering it.

Yegge and Kim's adoption framing makes production practice part of the workflow. A leader or senior engineer who ships one bounded feature with an agent learns the real context, review, maintenance, and safety constraints in a way that a training session or usage dashboard cannot show. The same source also reframes small valuable work: when an issue can be safely bounded and owned, agentic coding can remove backlog grooming, persuasion, and staffing delays, but the resulting artifact still needs maintainership after the prototype lands.

AI code quality workflows should cover the whole SDLC rather than only generation. Qodo's framing treats testing, review, context, executable standards, and secure validation environments as workflow surfaces that must keep learning as generated-code volume grows. Confident vibe coding adds another workflow shape: use the command line to compose specialized coding agents, and move review, coverage, and best-practice feedback earlier than PR-time inspection.

Brockman's workflow advice is to challenge inherited constraints by first principles rather than by blanket rule-breaking. The Stripe bank-integration story compresses a slow external process by pairing implementation with parallel test-script work and keeping the certifier engaged, but the stated lesson is narrower: find overhead attached to constraints that no longer apply in the specific situation. For AI-assisted workflows, that means converting speedups into better process design, not pretending every safety, testing, or coordination step is obsolete. Copilot's VS Code workflow adds another practical path from ad hoc prompting to team practice: begin with a fast prototype, then stabilize the workflow through starter templates, `.github/copilot-instructions.md`, custom modes such as TDD, configured tasks and tests, MCP integrations, browser feedback, and scoped approval settings.

Cloud-scale agent workflow can still start with local iteration. The Strands pattern is to define a prompt and tools in code, test locally, then deploy the same model-tool shape into cloud infrastructure when the workflow is ready. For very large tool catalogs, the workflow adds a retrieval step before tool selection so the model sees task-relevant tools instead of every possible integration.

Branchable cloud workspaces create a workflow primitive for stateful agent exploration. A human or orchestrator can declare a starting snapshot, hand it to multiple agents, let branches mutate independently, and pass the successful branch into later workflow steps. This works best when the branch outcome is verifiable and the workspace can be moved between humans, agents, and other agents without losing provenance.

Agentic workflows should be designed as composable primitives, not as allegiance to one framework shape. Use agent loops where the task needs flexible turns and tool decisions; use workflow structure where dependencies, traceability, branching, retries, or human waits need to be explicit. The practical move is often local: find the unreliable LLM call, overloaded tool surface, or opaque handoff and add enough workflow structure there without removing useful agent exploration elsewhere.

Business workflows also need an ownership decision before implementation. Core or differentiating workflows may justify handbuilt agents, while commodity workflows often benefit from managed platforms that already provide connectors, permissioning, auditability, observability, notifications, and hosting. The workflow decision should include risk assessment for sensitive data, SLAs, deployment model, and whether engineers should spend time on business logic or platform plumbing.

Enterprise productivity workflows should start from the shape of the engagement. In advisory and investigation work, AI often pays off first by ingesting, normalizing, classifying, retrieving, and extracting across the whole corpus so experts can spend more time on the recommendation. Those steps should become validated workflow components, not one-off demos: taxonomy classification needs business review, RAG needs stepwise design, and extraction needs confidence and validation surfaces for human review.

Knowledge-base onboarding workflows can move domain setup from manual forms into source ingestion. A practical seller-agent flow lets the user upload decks, websites, images, calls, and videos; stores the raw artifact; parses asynchronously by source type; chunks and embeds the parsed Markdown; updates the UI; retrieves relevant chunks at generation time; and shows the retrieved evidence beside generated messages for review.

Durable workflow engines are also an agent observability boundary. When the workflow records signals, queries, activity calls, retries, and state transitions, teams can inspect how an agent crossed LLM calls, tools, user input, and long-running waits instead of reconstructing behavior from scattered logs.

Approval-gated tool execution adds a concrete state-machine requirement to agent workflows. If a model proposes a sensitive action such as issuing a card, the workflow should defer the actual tool call, send the approval through the right notification channel, route the approval event back to the correct agent instance, resume only after approval, and persist enough status to prevent duplicate side effects from repeated or out-of-order events.

Work-management platforms can host the agent workflow itself. An agent should acknowledge triggers, state what it understood, move issues through normal status, continue in threads, ask for clarification before acting, and keep output useful enough that the shared workspace remains a coordination surface rather than a dumping ground for model text.

Eval workflows can be staged the same way as software test workflows: start with component checks, then integration and end-to-end checks, and automate the suite in CI/CD as prompts, models, data, and production behavior evolve. This keeps evals tied to real release decisions instead of one-off benchmark exploration.

Dagger's agent workshop shows a lighter-weight delivery workflow with the same principle: package build/test functions, source directories, containers, and LLM calls into workflow code, then run that code locally or through GitHub Actions. The trace view becomes part of the workflow feedback loop because it shows which prompt, environment, and tool call failed before the team changes the tool description or implementation.

Webhook-backed business workflows can use a host agent as the orchestration and context-slicing layer. The host reads the incoming event, decides which specialist agents or tools are needed, sequences dependent work when one output is required by the next step, and sends small task payloads rather than all source context. This keeps external agents focused while preserving a central control point for retries, routing, context budget, and cross-tool decisions.

Devin-style coding-agent workflows evolve with task horizon. Repeatable migrations can be driven by playbooks and memory; isolated tasks need prepared repositories with lint, CI, reload, and rollback; broader tasks need an exploration-and-planning phase with codebase search or wiki context; backlog-scale workflows need issue-system integration, confidence thresholds, human escalation, and self-testing before PR handoff.

High-quality coding-agent workflows can prevent defects before generation by forcing plans before implementation, researching existing solutions, and keeping specs, docs, and strict style guides in the active agent context. The same workflow should watch for stale or conflicting specs so the agent does not code against intent that humans have only kept in side channels.

Enterprise-aware agent workflows can be compiled from agent traces themselves. When an agent successfully completes a novel task, the trace can become a candidate workflow; when a future task resembles it, workflow search can retrieve that process and steer the agent toward known company practice. This creates a feedback loop where agents discover workflows, humans edit or approve them, and retrieval keeps the current process available without turning every workflow into fixed code or retrained weights.

Customer-facing agent workflows should be narrow before they are broad. Sierra's rollout pattern starts from one valuable customer journey, models the path in code, preserves flexibility for topic shifts, makes compliance language deterministic when needed, and then uses pre-launch simulations plus post-launch conversation review to expand capability. The organizational workflow also changes: CX and support teams may become agent coaches who review conversations and update behavior rather than only handling escalations.

Healthcare revenue cycle workflows add a financially measurable version of the same pattern. Late failures such as denials should not only trigger faster appeal generation; they should feed upstream checks for missing data, prior authorization gaps, policy changes, and registration errors. When a denial becomes a clinical-necessity dispute, the workflow should assemble patient records, guidelines, and payer policies for GenAI drafting while preserving expert approval before submission.

Production AI also needs a defined incident workflow, not ad hoc firefighting. A Databricks playbook connects the production pillars into one loop: detect on the eval dashboard (for example a customer-satisfaction drop), diagnose with tracing (such as a policy document never re-embedded into the vector store), contain by rolling back a versioned prompt or applying saga, compensation, and circuit-breaker fault tolerance, fix from the LLM-judge reports and eval-set library, then add the case back so the living test set grows. This response loop should integrate with the organization's existing ITSM alerting so the right person is paged and downstream systems are protected. The same engagement also inverts the usual build order — evaluation, observability, and data foundation come first, and the model is chosen last from the eval dataset — which is why the playbook can localize regressions instead of guessing.

A signal-to-PR workflow extends the incident loop all the way to a code change. PostHog's pipeline ingests heterogeneous product signals (errors, logs, Slack messages, session replays, experiments), drops malicious public-source signals with an LLM safety classifier, normalizes each into a weighted schema, groups them into reports that promote past a weight threshold, runs a research agent that diagnoses the problem and picks a reviewer via Git blame, gates on actionability, and finally dispatches an execute agent that opens a PR and iterates a snapshotted sandbox until CI is green. Two workflow-design lessons generalize beyond this product. First, gate dispatch on problem specificity: a coding agent will fix *something* for any input, so under-specified reports must be re-pooled for more evidence or routed to a human inbox rather than turned into noisy PRs. Second, sequence cost optimization last: while building the pipeline, run agents liberally to find the solution shape ("tokens are free" during experimentation), then collapse a proven expensive step into a one-shot call or a small trained model — over-indexing on per-stage cost early in the workflow hides whether the pipeline can work at all.

A self-serve internal-question workflow can break the recurring "explain question, wait for an engineer, get an answer, realize it needs one more join, repeat" loop. WorkOS's Studio lets any employee ask a business question in natural language and either get an answer or have the LLM compile a reusable widget: declarative code that calls the data sources directly so later runs are deterministic, cheap, and LLM-free. The leverage is that one-off questions are answered by the asker while recurring ones become shared widgets, so a platform or data team never has to keep building and modifying dashboards; a support team self-serves per-customer lookups in Slack. The widget pattern is the inverse of leaving probabilistic logic in the prompt — the agent emits frozen code once and any change requires re-invoking the model.

A data-collection workflow can be made self-maintaining rather than fragile. Bright Data's pipeline talk reframes scraping as a maintenance problem — sites change selectors and structure, so a hand-written scraper costs more to maintain than to build — and hands the whole loop to an agent: explore the site, write a reusable parser script once, run it, and re-run on a schedule with a data validation that triggers the agent to re-explore and repair the scraper in minutes when a field goes missing. The token economics are what make the deterministic script the production runtime rather than the LLM: building the parser once saves roughly a million tokens versus LLM-parsing every page (~62% on a structured demo site), and re-running the built script costs ~60-100 tokens against ~10,000 to walk the JSON with the model. This is the same collapse-the-proven-step pattern as PostHog's pipeline, with a scheduled self-healing loop bolted on so the workflow keeps running without a human.

Splitting a workflow by determinism is also how Qodo defuses the "orchestration paradox," where capable models waste most of their tokens deciding *how* to solve a task instead of solving it. The 80/20 design gives high-reasoning models the open-ended discovery 80% (which tool, which plan, the next action) and routes the validation 20% to restricted, deterministic steps behind hard gates such as "if I get X results I want Y," which "lowers down" the unbounded research from the discovery phase. Because the discovery phase can still loop, the workflow needs explicit stop conditions — a counter (work with the last result after 4-5 iterations) or a timeout (take the last decision after ~5 minutes, then retry only if results are bad). This is the multi-agent counterpart to keeping orchestration deterministic while reasoning stays flexible: the deterministic validation gate is a workflow step, not another open-ended agent.

A one-person, many-agent workflow can be managed as a factory floor rather than an orchestration framework. OpenClaw's "dark factory" practice organizes 15-20 concurrent coding sessions into typed swim lanes (CI, test refactors, features, bugs, triage) and supervises each lane to a different depth — stable lanes run fire-and-forget while risky lanes get a live conversation — so the human's scarce input is attention, not tokens. The process is deliberately minimal ("in harness we trust": no plan or spec mode), the supervision signal is the agent's own reasoning narration (waffling means cut the lane), and the input queue is shaped by deduplicating a large issue backlog with semantic embeddings so convergent pressure decides what to feed the lanes next.

Safe Intelligence's "capturing decisions" workflow shows the opposite discipline: a single agent kept on-policy for hours by a loop built out of git hooks, CI, linters, and skills rather than prompt instructions. The loop is generic — do work, push, get rejected at the commit, get linked back to the architecture-decision record, read it, fix it, iterate — but skills change its *focus* (an ADR skill, a PRD skill, a UI loop that skips checks for fast browser iteration, a test skill that runs only the tests implicated by coverage and file changes, a goal-execution skill that records decisions for review). Two enforcement choices keep the loop from depending on the prompt: the rules survive 20–50 context compacts because they live outside the prompt and the agent re-looks-them-up, and the most reliable rules are structural — lint module imports so a failure class is impossible (templates can't touch the database → no N+1 ever) rather than detectable, because "what you cannot find, you cannot enforce." Verification is carried by executable, human-readable BDD/Cucumber scenarios linked to PRDs and critical user journeys, and the decision documents (ADRs capturing why and how-to-enforce, light PRDs capturing why/problem/goal/journey) serve both the agent and "you 6 weeks from now."

Lovable runs two parallel continuous-improvement workflows aimed at "make a mistake once, then never again" at ~200,000 projects/day. The first is a demand-driven knowledge loop: an LLM judge detects stuck→solved transitions, the system captures and clusters the fix into a generalized entry, eval-verifies it, and a lightweight model injects it just-in-time into future runs — with each entry A/B-ranked by a blank-injection holdout and pruned as it goes stale, so the workflow stays at the frontier of what is solvable. The second is an agent-authored incident-to-PR loop: the coding agent uses a frustration-gated "vent" tool to report tooling/platform friction to Slack, a second monitoring agent dedupes the vents and opens PRs for human review and merge, and vent-volume spikes serve as the incident-detection trigger. Both are the same detect → fix → continuously-review-and-eval shape as PostHog's signal-to-PR pipeline and the Databricks incident playbook, with the distinguishing twist that the *agent's own experience* is one of the signal sources, not just infra metrics and product events.

Geoffrey Litt (Notion) adds a set of *understanding* workflows for the human side of the loop, treating "how do I keep up with what my agents wrote" as an education problem rather than a review-throughput problem. Three reusable patterns: have the agent write a literate explainer doc for its own change (background first, intuition before details, tasteful interactive figures, prose-ordered diffs — the `explaindiff` skill); append a short comprehension quiz and refuse to promote code until you pass it, a "speed regulator" that catches the self-fooling of thinking you understood; and have the agent build ephemeral microworlds (a scrubbable debugger, a click-through migration "game") so you *feel* how a system works. These are the counterpart to the on-policy and continuous-improvement loops above: those keep the *agent* aligned and improving, while these keep the *human* understanding-rich enough to stay a creative participant across loops rather than accumulating cognitive debt — and the collective version (multiplayer human+agent threads, commentable documents) extends the same discipline to a team's shared understanding.

Alex Volkov (ThursdAI) frames the review step of those loops as a routing decision rather than an all-or-nothing policy. His Z/L Continuum reframes "read every line vs. code is free" as a per-task question — "what proof does this specific change need?" — and gives a routing table: read every line yourself of authentication, money movement, permissions, and irreversible data; decompose long PRs into atomic reviewable ones; verify with traces, evals, and shadow mode; separate the writer from the reviewer/tester; and engineer rails, observability, and rollback so reading spends attention once. This is also where the emerging "loops" primitive gets a caution: a scheduled agent that discovers a task, plans, executes, and grades its own work looks like it removed review, but a builder that grades itself has only *hidden* it — so self-verifying loops raise the stakes on where you place independent judgment rather than eliminating the need for it (Addy Osmani: relying entirely on automated loops to fix code produces "a downward spiral"). Capability drift moves *where* the proof belongs (outputs → task direction → loops) but never removes the requirement for proof.

Kyle Jaejun Lee (KRAFTON) turns that organizational shape into a concrete review workflow for a personal fleet. Instead of walking into each tmux pane to catch plan drift as work flows down a CEO/VP/manager/worker hierarchy, he runs a **review gateway**: any layer that wants to act submits its plan and then blocks — "Nothing runs until I approve. And the second I approve, a hook fires the work off automatically" — collapsing many panes into one web inbox and one control point. As the fleet grows across machines, every machine sends its review requests over SSH into a single main gateway hosted on an always-on box, because "your one point of control can't be a thing that falls asleep." The gateway itself was built by an infra team of agents inside the fleet — "agents building the tools that run the agents." This is the human-in-the-loop, plan-first counterpart to the self-verifying-loops caution above: rather than let a builder grade itself, the workflow inserts one deliberate approval boundary at the point where plans could drift.

OpenAI's Peter Steinberger gives the loop an organizational shape. Running many agents by hand across ~10 terminals is not orchestration — "I was polling. I was the scheduler, the router, and the memory." The scalable workflow is to manage one long-lived manager-of-agents that delegates to workers while the human works an outer loop (set direction, decide) and drops down to pair only on tricky work. Three harness capabilities constitute the loop: server-side compaction (persistent context that makes long-running tasks reliable), coordination (one thread creates and steers projects), and triggers (automation that wakes the same manager on an event). The canonical instance is automated open-source issue resolution: an issue arrives → the manager wakes, reads it against the project's goals/notes/vision, decides fit, and spins a worker; the worker investigates, implements, and tests; another agent reviews; and only when it needs you does it return a PR plus the original issue, the diff, and maybe a video or a running build to VNC into — you review once, note, approve, and it lands after checks pass. As with the review-routing view above, this shifts *where* judgment goes rather than removing it, and its named limit is that the bottleneck keeps moving to human attention, so "the future is not 20 terminals. It's better loops."

Talha Sheikh (Checkout.com) closes the loop with an automated enforcement step. Left alone, the human is the enforcement layer: the agent reports "task completed," but "when you actually try to run it… something else failed," so you keep hand-issuing "fix this, fix that." His harness moves that check into the workflow itself — a deterministic verification gate wired to the agent's completion event (a Claude Stop hook) that runs a config of test cases and loops "try again" back into the agent until they pass. Unlike the self-verifying loops caution above, this is *deterministic* verification: capability ≠ reliability and instructions ≠ verification, so a better model does not remove the need for a check, and the same gate should run at every level (in-conversation, conversation-end, pre-commit, multi-agent, async, plus optional LLM-as-judge) as a language-agnostic, bring-your-own-enforcement contract. It is the workflow embodiment of this topic's recurring theme — value has moved from "the code that we create" to "the verification that we design," so "work on the harness, not on the code."

Theo Browne pushes the "better loops" idea to its minimal form: a whole class of former standing services can collapse to a "markdown file on a cron." His PR-triage service is now one markdown file that instructs an agent to read open PRs across several repos, assess status, prioritize, then write a static HTML report to S3 and return the URL — piped to Codex/Claude and fired by a 9 a.m. cron so his work list is ready by ~9:15. The durable point for this topic is that executable natural language on a schedule is now a legitimate workflow tier below a coded service, and it belongs to the same tier-collapse logic that lowers the scope of every buildable artifact as models improve.

Iris ten Teije (Differ) pushes the loop past the build step and into distribution: [the frozen-artifact pipeline was a cost constraint, not a law](../concepts/frozen-artifact-pipeline-is-a-cost-constraint-not-a-law.md), so "when the agent is the runtime… development and distribution stop being two phases" and the freeze-verify-ship-once workflow that CI, packagers, and registries encode is no longer forced. The workflow that replaces it is to [deploy a canonical stem plus bounded per-user divergences](../concepts/deploy-a-canonical-stem-plus-bounded-per-user-divergences.md) and treat coordination differently: with a million per-user versions you "don't merge code, merge intent, merge outcome" — everyone converges on the same goal through their own path rather than the same commit. This shifts the review/verification burden this topic keeps circling: correctness must now be reasoned about across "the stem and every possible divergence," provenance means every divergence stays "immutable, inspectable, attributable" back to the signal that produced it, and the harder step is *desirability* (was a correct change actually an uplift), which is the runtime-distribution analogue of the deterministic verification gates and review-routing patterns above — generation is the easy 80%, and "observability, validation, coordination… is the entire business."

Rajiv Chandegra (Annicha Labs) questions the fixed shape of the workflow itself. Every loop, review gate, and orchestration graph above is *pre-engineered* before the run — a **fixed (factory) harness** whose roles, sequencing, and handoffs are decided up front, "Taylorism for AI," reliable because reliability is bought "by suppressing variance that novelty requires." That is the right workflow for **complicated** problems (decomposable, knowable, predictable) and the wrong one for **complex** ones (a flock, a market, an organization — Ackoff's "mess" of moving relationships) where "you don't analyze and plan… you probe and sense and respond." His **adaptive engineering** proposal is to stop authoring the workflow structure and instead [let the harness emerge at runtime](../concepts/let-the-agent-harness-emerge-at-runtime-adaptive-engineering.md) from agent interactions under designed constraints (enable vs govern, reward coherence vs cost divergence, rate of coupling), so the workflow becomes an output that self-organizes, specializes, and dissolves rather than an input fixed ahead of time. It is the far end of this topic's agent-versus-workflow spectrum — deliberately *not* "a swarm with no roles," but a bet that the durable design question moves from wiring the graph to [matching the harness to whether the problem is complicated or complex](../concepts/match-the-harness-to-complicated-vs-complex-problems.md), with the caution that emergent workflows lose legibility and predictability ahead of runtime.

Thariq Shihipar (Anthropic) contributes a concrete pre-run workflow for the spec-and-review discipline this topic keeps circling: at high model capability the binding constraint is the human's ability to match intent to reality, so [use the agent to surface your own unknowns](../concepts/use-the-agent-to-surface-your-own-unknowns.md) before generation. The spec is a *map* and the codebase the *territory*; every gap the agent guesses at is an "unknown," organized in a knowns matrix (known knowns, known unknowns, unknown knowns, unknown unknowns). The reusable moves each target a quadrant: a **blind-spot pass** (point the agent at the module, git diff, or Slack for gotchas — and at whole unfamiliar fields), **prototype variants** ("four widely different design decisions so I can react to them") to elicit know-it-when-you-see-it taste, an **interview** ("prioritize questions that would change the architecture"), a **reference codebase or HTML mock-up passed in as another map** instead of a prose spec, **implementation-note logging** of deviations during the run, and a **comprehension quiz** afterward so the human can represent the work at PR time. This is the discovery front-end that precedes structured spec-driven development, and it dovetails with the "being unreasonable" mindset — demand good/fast/cheap at once and [rescope ambition up](../concepts/rescope-ambition-down-a-tier-as-models-improve.md), while remembering that "building is easier, but generating value is still hard."

Raphael Kalandadze (Wandero AI) adds the *post*-launch workflow this topic mostly leaves implicit: after shipping an agent, [staff its operations with a team of agents](../concepts/staff-agent-operations-with-a-team-of-agents.md) arranged as an explicit pipeline — a fast loop (log-monitor over a rolling window → drafts a PR with mermaid/ASCII/HTML artifacts and a static-analysis pass → a *fresh-context* review agent that criticizes it, scores root-cause-vs-symptom, and requests changes or closes it → human merge) and a slower zoom-out loop (a session analyzer scoring live conversations for health). It is a concrete instance of this topic's reviewer/approver and independent-validation patterns, with two twists: the reviewer runs in a deliberately fresh context because agents are "eager to send the PR" and biased toward their own fix, and the human is kept only at the merge boundary because the PR + review agents "send 10 times more PRs than the three of us every day." The staging rule he draws — "close the loop first" (make yourself the bottleneck, then remove yourself) — is a workflow-sequencing decision, and the meta-harness principle (give each operating agent all the context a human would need: trajectories, metrics, database, UI) is why the pipeline's fixes "depend on the real problem" rather than a symptom.

Vaidas Razgaitis (Higharc) narrows the aperture to the *research-to-production* handoff — the workflow that moves a frontier-ML prototype into a customer-ready feature — and frames it as a systems-and-process problem with three levers. The first is a documentation move: [bridge ML research to production with a taxonomy handoff document](../concepts/bridge-ml-research-to-production-with-a-taxonomy-handoff-document.md), a software-engineering technical design doc / RFC adapted for ML (ML-specific domain-context and business-goal sections up front, then conventional type-contract, persistence, architecture, and decompose sections) that makes a researcher's prototype legible to the platform/back-end engineers and PMs who must productionize it — the same spec-before-building discipline this topic circles in spec-driven development and [using the agent to surface your own unknowns](../concepts/use-the-agent-to-surface-your-own-unknowns.md), here aimed at a human-to-human baton pass rather than a human-to-agent one. The third lever is a decomposition workflow: slice the proven monolithic prototype along its dependency graph and land it as **Graphite stacked diffs** for asynchronous subject-matter-expert review, a concrete instance of this topic's dependency-aware batching and route-each-change-to-the-proof-it-needs threads (the code-structure lever it pairs with is [structuring the ML codebase as decoupled per-researcher microservices](../concepts/structure-the-ml-codebase-as-decoupled-per-researcher-microservices.md)). His closing diagnostics turn each lever into a health check: ambiguity about where new staff should concentrate signals a legibility gap, fighting old abstractions signals a repo-structure gap, and inability to estimate timelines or name reviewers signals a decomposition gap.

Benedikt Sanftl and Burak (Mutagent) generalize both the post-launch pipeline and the "better loops" thread into a single end-to-end agent-building workflow: [automate the agent-building loop with an agentic AI engineer](../concepts/automate-the-agent-building-loop-with-an-agentic-ai-engineer.md). The workflow is two connected loops — an offline loop (spec → build → evaluate → ship) and an online loop (monitor → diagnose → optimize → feed back) — with every stage run agentically under an orchestrator, because run by hand "the bottleneck basically becomes the human review and the human building time," which can't scale once an org rolls out hundreds of agents. Its exit condition generalizes Talha Sheikh's deterministic verification gate: eval-driven development supplies an eval suite as the termination gate ("when is an agent good enough?"), the agent iterates until the suite is green, then auto-ships. Like Theo Browne's markdown-on-a-cron and Kalandadze's operating pipeline, the human is pushed to the boundary — you design the loops with a clear eval gate and the sub-agents (spec, build, evaluate, diagnose, monitor, optimize) do the leg work — and the diagnosis stage keeps the loop affordable at scale via [code-checkable indicators and representative sampling](../concepts/diagnose-agent-failures-with-code-checkable-indicators-and-sampling.md) rather than reading every trace.

Angie Jones (Block) supplies the *organizational* workflow for getting a large engineering org to adopt these loops, which this topic mostly assumes rather than sequences. Her starting observation reframes what "adoption" measures: ~90% of 3,500 engineers used coding agents yet shipped no faster, so she [stages adoption with a delegation maturity model](../concepts/stage-agentic-engineering-adoption-with-a-delegation-maturity-model.md) (Stage 0–5, ranking each engineer's delegation/orchestration relationship with agents) to locate the org and name the target. The rollout mechanism is a leverage play rather than a mandate: instead of upskilling everyone, [drive adoption through champions and AI-ready repos](../concepts/drive-org-wide-agentic-adoption-through-champions-and-ai-ready-repos.md) — a hand-picked ~1% cohort (1-9-90 rule) from the most critical repos embeds AI assets (context/rules files, slash commands and skills, an AI reviewer, PR attribution) into the *shared* repos so delegation becomes native for the 90%. This is the change-management counterpart to this topic's operating-loop patterns: the champions then wire hands-off delegation into where requirements already live (Jira/Linear/GitHub/Slack), add a Codex auto-fix review loop and isolated cloud workspaces when parallel output overwhelms review, and build a Builder Bot orchestrator over a machine-readable 25,000-repo world model — but the durable workflow insight is that the substrate work (readable repos, a capability ladder, bottom-up per-team convergence) is what lets the org, not just the power users, run these loops. The closing caveat — the autonomy push preceded layoffs — is the human-outcome question the pipeline framing tends to leave out.

Paul Iusztin and Louis-François Bouchard add a research-and-knowledge-work workflow that precedes most of the build loops above: before you delegate, decide *how durable and how owned* the research needs to be. Their tool-selection ladder — [choose the research tool by reuse and ownership, not just speed](../concepts/choose-the-research-tool-by-reuse-and-ownership.md) — routes a throwaway answer to Google/ChatGPT, a one-off change to Codex/Claude Code, revisitable content to NotebookLM, production scale to a RAG/vector-DB pipeline, and a personalized, inspectable, compounding store to a self-owned file wiki. Their operating pattern then turns research into work with a clean split: the immutable "second brain" is the research and each project (an article, a course, a new harness) scopes its own wiki via a deep-research pass — "the project is the work, and your second brain is the research." It is the individual-scale companion to Angie Jones's org-level substrate work below, and the ladder is a reusable decision node this topic's build loops can sit on top of.

Jared Joselowitz (Ufonia) narrows one stage of these build loops — the "improve the prompt" step — into a workflow with a hard prerequisite. Given that "formatting changes alone have been seen to swing benchmarks by 76 percentage points" and reordering few-shot examples "flips a model from near random… to near state-of-the-art," hand-tuning is not a workflow at all: it is "very subjective, it's not reproducible, and very importantly, it's extremely time-consuming." The replacement is to [optimize prompts against an asymmetric cost matrix](../concepts/optimize-prompts-against-an-asymmetric-cost-matrix.md) with GEPA, which drops iteration from hours-or-days to 30-60 minutes and leaves an audit trail — but only if the objective encodes the real damage function rather than a dataset average, since a missed red flag is catastrophic where an over-called one is "mildly annoying." Two consequences matter for how a team organizes around the loop. The work relocates rather than disappearing: "it's mainly focused on the data, how to make your data right, the feature engineering, and you define the actual metric along with the clinicians" — the same shift Graziano's branch-per-hypothesis hill-climb makes when it forbids the coding agent from touching the scorers. And the objective becomes a swappable parameter, so a domain expert who wants a different tradeoff need only "recompile the prompt," which is what turns prompt optimization into something a non-engineer can steer. In Ufonia's full flywheel the optimizer sits between the data (real calls plus manufactured edge cases) and a simulation safety gate, with a gated deploy last — the eval-as-termination-gate pattern this topic already uses, with the gate raised to a hazard-level safety case.

Dan Feng (Maven Clinic) works one level above the build loops and asks what happens to *planning* when the loops make implementation nearly free. His claim is a cost inversion: long requirement phases existed because "implementation can be really expensive" and getting it wrong later was costly, but "with AI, building is super fast… Argument is really expensive one." So Maven [commits at sprint scale](../concepts/commit-at-sprint-scale-when-implementation-is-cheap.md) — a one-year view kept as direction only, on the deliberate assumption that "AI models can do anything you want in one year"; a two-to-four-week window as the only real commitment, with reversal built in ("if at the end of this sprint, they say, 'No, what we decided two weeks ago is wrong.' It's totally okay"); PRDs and TDDs cut to one or two pages that "serve as communication, so we can iterate on it"; and the three-to-six-month plan written off as close to unplannable, because "I don't know what AI models will be capable in three months. There may be multiple releases already." The same inversion shows up in their tool-adoption workflow — start on the lowest-risk, easiest-to-verify tasks (unit tests, documentation), use that window to "construct our own rules, skills, and build our barriers," then push to the whole team and treat a refusal as a signal to investigate rather than a policy violation — which is the individual-team version of Angie Jones's champions-and-substrate rollout above. The horizon question is the durable one: this topic's loops assume a target worth hill-climbing toward, and Feng's answer is that the target is only trustworthy two to four weeks out.

Anuj Iravane (Anterior) contributes a generation workflow with an unusual ownership arrangement. The pipeline itself follows a rule worth lifting out of its domain: to synthesize a long structured artifact, [build it coarse to fine by emulating how it was actually produced](../concepts/build-synthetic-records-coarse-to-fine-by-emulating-their-source-process.md). Because real medical documentation "is really generated" only during provider encounters, the pipeline models exactly that — patient invariants, then an ordered *patient journey* of events and providers, then a document plan per encounter, then a fan-out that hydrates the documents against the plan and the preceding history. One-shotting is rejected on the same grounds you would reject it for prose ("you wouldn't ask an LLM to write a novel for you in one shot"), and the layering doubles as the token-efficiency mechanism: payloads stay small on input and output, and a longer journey scales by fanning out further rather than by growing a context window. Parallel fan-out then forces its own reconciliation step — a refinement loop whose evals include "an LLM based check for consistency between all documents," because the branches were written independently. The workflow also declines an obvious step: generation stays in markdown rather than rendering to PDF, since "state of the art PDF parsers" already collapse the real documents back into text, so fidelity is spent on structure rather than on scan artifacts. The ownership half is the part that generalizes furthest: [hand domain experts the pipeline as skills](../concepts/hand-domain-experts-the-pipeline-as-skills.md). Every stage — patient journey, document generation, enrichment, evals — is a skill file on a generic internal agent harness, so a clinician adding a customer's intake-form type "could easily just make a new skill file for it, attach it to the pipeline," with no engineering change, on top of human-in-the-loop steering at any generation step. The justification is an admission rather than a convenience argument — "no AI engineer would" know what a good medical record looks like — and the claimed payoff is that domain experts, not engineers, "drive towards a recursive self-improvement."

Ayush Bhardwaj (Allos AI) offers a build order for vertical AI whose interesting feature is a deliberate stop. Seven steps: formulate a narrow problem, identify proprietary data, model the problem as a prompt written "after the person who you are trying to replace," add observability — and then "you don't iterate yet, you hire the user." The pause is the whole argument, because the first four steps "fit one screen" and produce something that looks shippable while nobody on the team can tell whether it is any good. Once the expert is on staff, the loop this topic normally starts with becomes runnable, and its rungs are specific: the expert narrows prompts, curates sources (a practitioner "knows which sources are more reliable than the other," the way an engineer distinguishes credible venues from influencers), encodes ordering — "if you follow five steps to solve a problem, you just cannot do it in any random order. There has to be a logical flow" — and only then judges, so that a career's worth of judgment "is now turning into agents." That is [hiring the user to own the judgment loop](../concepts/hire-the-user-to-own-the-judgment-loop.md), and it sits one step earlier than Anterior's expert-review tooling and skill-file authorship: those arrangements hand a pipeline to experts the company already employs, whereas this one is about a team that has none and must buy the judgment before any loop exists. The loop's byproduct is the asset the company started without — "at this point you're kind of generating your own data… that exercise itself is generating a crazy data set of what works and what does not work" — and the improvement ladder is explicitly cost-ordered, with error analysis over observability logs as the cheapest, highest-ROI rung and fine-tuning carrying a treadmill cost, since each new base model release means fine-tuning again.

Generative-media authoring supplies a workflow shape this topic has not carried: a two-tier loop where the cheap tier makes the decision and the expensive tier makes the artifact. Keegan McCallum (uRun) describes today's video-creation loop as a slot machine — a prompt, maybe some keyframes, "about $10 a minute to try and get the shot that you want" — and the replacement as [steering in real time and then rendering the chosen shot at full fidelity](../concepts/steer-in-real-time-then-render-the-chosen-shot-at-full-fidelity.md): sub-second steering while the model generates, then a slower high-fidelity render of the result you converged on. The generalizable part is not video-specific. Whenever attempts are paid and quality is only knowable after the fact, moving the intervention point *inside* the attempt converts a gamble into a search — and the pattern's load-bearing assumption is that the cheap tier is representative of the expensive one, which is the thing to test before adopting it. The same live surface has a second use in this topic's supervision thread: "piloting an agent that you're able to look over its shoulder and see what it's generating in real time," which is streamed agent progress applied to media instead of tool calls.

Ankit Jain (Aviator) supplies a loop shape for the case where the human can no longer inspect the work product itself: relocate the review surface instead of removing the reviewer. The pipeline is session → acceptance criteria → test plan → verification against a live preview, and the interesting structural choices are three. First, the loop's input is the *interaction*, not the artifact — [the coding session is the intent record](../concepts/capture-the-coding-session-as-the-intent-record.md), and deriving the verification plan from the diff instead would let the producer define its own passing grade, this topic's self-grading failure in a new place. Second, the loop's output is [intent plus evidence as the review surface](../concepts/make-intent-and-evidence-the-review-surface.md): a plan in English that product managers and designers can read, and screenshots plus database snapshots that show the behavior happened, with the human keeping "governance and the review part." Third, execution follows an explicit ordering rule — "deterministic where it can be, but LLM where you must" — which is this topic's inspectable-steps discipline stated as a default rather than a preference. The reusable generalization beyond code: when output volume outruns inspection capacity, the durable move is to find the artifact that still fits in a human's attention (here, a page of criteria and a folder of evidence) rather than to sample the unreviewable one.

LangChain's Vivek Trivedy proposes an improvement loop for agents themselves, and its shape is worth reading as a workflow rather than as tooling advice. The four steps are: ship the agent, collect its traces, mine the corpus, and run data-driven experiments — with the claim that the first step is the cheap one and the loop only starts on contact with users. What makes it a workflow question rather than an observability question is his framing that [observability and continual learning are the same problem](../concepts/observability-and-continual-learning-are-the-same-problem.md): "there's a very tight coupling between what observability is and what continual learning is… if you're a continual learning company, you need traces." The loop's second half is a sequencing rule this topic can use directly. [Order harness engineering and fine-tuning by feedback speed](../concepts/sequence-harness-engineering-and-finetuning-by-feedback-speed.md): a prompt or tool change tells you whether it worked in "maybe 2 minutes," a training run in hours or days, so exhaust the fast lever first, and expect to return to it after the model changes — "a lot of teams are happy with harness engineering" and stop there legitimately.

The mining step has a constraint that changes who does the reading. A trace corpus is too large to fit any context window — the cost of a naive pass is "the input token cost times the number of traces times how big each trace is on average" — so [agents read the traces and the corpus is queried as an external object](../concepts/mine-trace-corpora-with-agents-because-they-do-not-fit-in-context.md) rather than loaded. The reframing that ties the whole loop together is [model-harness-task fit](../concepts/treat-agent-improvement-as-model-harness-task-fit.md): borrowing scikit-learn's `fit()`, the thing being fitted is the triple of data, harness, and model together, which means "which model should we use" is a term inside the optimization rather than a decision made before it. Note the two jobs this leaves — finding a good fit function and finding good data — and his own warning about the first: "agents are pretty good at making that number go up. They might cheat a little bit."

A recurring agent job over a corpus you own needs three decisions the interactive case never forces, and Ben Holmes' nightly knowledge-base pipeline makes all three explicit. Where does it run: a local scheduler is simpler but "means your laptop has to be cracked open when it runs," so anything that must actually happen nightly belongs in [a cloud sandbox that syncs the corpus down, runs the skill, and syncs it back](../concepts/run-recurring-knowledge-jobs-in-a-cloud-sandbox-with-sync-down-sync-back.md) — and the reason to schedule at all is latency, since "it can take time for an agent to go generate these things," not convenience. How does it know what is left to do: [stamp processing state into each artifact](../concepts/stamp-processing-state-in-the-artifact-to-make-agent-passes-resumable.md), which makes the corpus its own checkpoint store — necessary here because the sandbox is torn down between runs, so nothing else survives. And what does the human get: a review artifact rather than a notification — "I wake up to a perfectly fresh wiki that I can review. It's like the daily paper, but it's your own" — with the run itself still viewable afterward, which is what makes a silent failure detectable. The unglamorous gaps are worth designing before adopting: nothing in the source handles a human editing a file while the sandbox edits the same file, or what a half-finished run leaves behind on sync-back.

Ben Hylak describes the operational loop from the other end — not a scheduled job over a corpus you curated, but a standing process over the traces a shipped agent throws off — and its most useful contribution is a set of requirements the loop's components must satisfy. Two numbers per issue are the whole triage interface: "you need to know when it actually started, and you need to know how many people it affects." Onset converts a complaint into a diff to inspect ("this issue started yesterday… suddenly like your mind starts turning and you're like, 'Oh, what did I do?… Did we change model?'"); share decides whether to act at all, since "three users versus 100,000 users just is critical" when "agents will have an infinite number of problems" ([Triage Agent Issues by Onset and Share of Users](../concepts/triage-agent-issues-by-onset-and-share-of-users.md)). Those requirements are what disqualify the obvious default. Clustering every trace is conceded as good one-off error analysis but rejected as the monitoring layer for three structural reasons — cluster identity does not stay stable across runs, you do not control the boundaries, and what counts as "the same issue" is product-specific — with the worked example of a "price issues" bucket that merges a wrong quote and a wrong refund calculation, two problems with "extremely different root causes," one owner, and one meaningless trend line ([Clusters Are Not Issues](../concepts/clusters-are-not-issues.md)). This qualifies rather than cancels the wiki's clustering pages: [promoting a validated cluster into the golden dataset](../concepts/promote-validated-live-trace-failure-clusters-into-the-golden-dataset.md) survives precisely because its human validation step converts the cluster into a named artifact with stable identity.

What replaces it is a division of labor. Detection should be deterministic and cheap — "pull out as many deterministic things as you can like keyword frequency" — and the detector is allowed to be wrong, because its job is to produce "something more tangible tractable that you can have an agent actually investigate," not to be right: "don't ask your agent to find anomalies. Ask it to investigate anomalies you've already found" ([Hand Agents Anomalies to Investigate, Not to Detect](../concepts/hand-agents-anomalies-to-investigate-not-to-detect.md)). The natural detector layer is [code mode transplanted from MCP tool calling to traces](../concepts/run-trace-classifiers-as-code-mode-in-a-sandbox.md) — the model writes a classifier, a sandbox runs it "at production scale" — which also happens to be what makes onset and growth computable, since a named, versioned classifier re-run over last month's data yields a comparable series. On the offline side, the same talk argues the eval layer of the loop has a depreciation schedule: evals are written against a harness, so "you switch to like Claude Code CLI and now 80% of your evals suck," with the honest test being whether you would actually "delay it 2 weeks to update your evals" before a model upgrade ([A Harness Switch Invalidates Most of an Eval Suite](../concepts/a-harness-switch-invalidates-most-of-an-eval-suite.md)) — and that the assertions belong in the repo as tests rather than in a hosted playground, because "the prompt is actually like the whole thing now. It's your whole harness" ([Keep Evals in the Repo as Tests, Not in a Prompt Playground](../concepts/keep-evals-in-the-repo-as-tests-not-in-a-prompt-playground.md)). Which half of the loop you can lean on is set by scale before anything else ([Match the Quality Method to Your User Count](../concepts/match-the-quality-method-to-your-user-count.md)). Caveat on all of it: a vendor talk selling the production-detection half, with no measurement anywhere — the 80% is an explicit estimate, the anomaly-detection claim names no model and no task, and no failure rate is offered for clustering.

Aditya Khandelwal runs the same close-the-loop idea inside an engineering org rather than over a product's traces, and reports what breaks first. His three principles are prompt-inject the codebase, close the loop ("you got to make a self-healing system cuz slop is inevitable… a pipeline and a way to close the loop to remove the slop, to detect it"), and keep iterating, with the loop wired through issues and boards, CI/CD, agentic reviews, and a nightly code gardener whose rubric is repo-specific because "what does correct organization mean will depend on your code base." The failure is the part worth carrying: giving agents a tracker without deciding which agents may file produced 400–500 issues in a couple of weeks, "so many like different agents all trying to create issues cuz they've not been wired correctly" ([Wire Issue-Filing Authority Before Giving Agents a Tracker](../concepts/wire-issue-filing-authority-before-giving-agents-a-tracker.md)). It is the internal-facing version of the caution above that [clusters are not issues](../concepts/clusters-are-not-issues.md) — in both cases a detector's output was handed straight to the artifact humans are supposed to work from, and the missing step is the same one: something has to convert a finding into an item with an owner, an identity, and a reason to exist. Its natural counterpart is an exemption lane, since a loop that files against experiment code generates work nobody intends to do ([Let Prototypes Opt Out of Codebase Standards](../concepts/let-prototypes-opt-out-of-codebase-standards.md)).

Two further pieces belong to this topic's rollout thread rather than its trace-loop one. The adoption workflow he recommends is not a platform build but a single skill: find the work everyone dislikes, automate it end to end, and let that be the demonstration — theirs, `ship it`, carries a change from code-done to PR-ready, and complaints about it are routed back into the skill rather than answered, which is the [prompt-and-skill improvement cycle](../concepts/feedback-turns-coding-agent-loops-into-prompt-and-skill-improvement-cycles.md) used as a change-management tool ([Invest in One High-Value Skill to Convert Agent Skeptics](../concepts/invest-in-one-high-value-skill-to-convert-agent-skeptics.md)). And the maintenance discipline is stated as a standing budget line rather than a project: a fraction of IC time goes to iterating on the shared setup, work that "is not going to lead to like meaningful PRs like up front, but it's useful and it's worth it" ([Own Agent Adoption at the Leadership Layer Because the Fixes Are Shared](../concepts/own-agent-adoption-at-the-leadership-layer-because-the-fixes-are-shared.md)), with a fear × utilization map and a five-symptom checklist as the instruments for deciding whether it is working ([Map Agent Adoption on Fear and Utilization Axes](../concepts/map-agent-adoption-on-fear-and-utilization-axes.md), [Uneven Agent Adoption Loads Review Onto the Slowest Adopters](../concepts/uneven-agent-adoption-loads-review-onto-the-slowest-adopters.md)). None of it is measured: one team of about ten over a few months, no before/after on throughput, review latency, or incident count, and no figure for what the gardener or the review agents caught.

Sonar's ACDC loop — Guide, Verify, Solve — is already in this topic from the May 2026 talk; its second appearance changes where the loop's verification step sits and why. The argument for checking during generation rather than at PR time is no longer feedback latency but propagation: issues found as the agent writes "can then be fixed immediately by the agent so they don't propagate into future agentic loops that are going to run in order to fully build out the software project" ([Fix Defects Inside the Agent Loop Before They Become Foundation](../concepts/fix-defects-inside-the-agent-loop-before-they-become-foundation.md)). Latency argues for a faster check anywhere; propagation argues specifically for inside the loop, and it is the argument that survives if CI ever becomes fast. The workflow shape that follows has three parts. The verifier's verdict becomes the turn's exit condition — the agent "will not proceed until it actually is able to get a passing grade" — which makes verification a precondition for advancing rather than a report it may ignore. Remediation belongs to the agent, "allowing the agent to have the agency to do so itself," because findings routed to a human queue do not stop propagation while the agent keeps building. And the same regime runs again in the outer loop: "the verification needs to run in both the inner agentic loop and also in the outer loop for CICD," where an LLM review produces findings and a computational review "assigns grades" and blocks the PR. Only the second of those is reproducible, which is the practical reason to let it be the one that blocks ([Choose Verification Layers by Defect-Class Coverage](../concepts/choose-verification-layers-by-defect-class-coverage.md)).

The Guide half is where this topic's context-and-standards material gets an explicit list of what must be written down before any of it executes: desired architecture and its constraints, acceptable coding standards and patterns, the allowed and disallowed dependency list, syntax standards, logging and observability practices, and the security/quality/maintainability thresholds themselves — "you need to basically write that down and encode it." The same talk reverses the earlier Sonar position on how that context reaches the agent: not the whole codebase up front, because "it's going to spend a lot of time thrashing and exploring and burning tokens," but served per task. Two cautions travel with all of this. Nothing in the talk is measured — no defect rate, no false-positive rate, no latency or cost for in-loop verification, and a pre-recorded demo. And the loop's autonomy ramp has no criterion: the review agent defaults to findings-and-dialogue and escalates to writing, approving, and merging its own fixes "as you use it more and more and gain confidence," which is elapsed usage, and which retires the method independence that justified the layer in the first place ([Verify Generated Code With a Method the Generator Does Not Share](../concepts/verify-generated-code-with-a-method-the-generator-does-not-share.md)).

Matt Dailey (Ref) argues that the workflow most teams are running has one layer too few. Once agents own implementation, what remains above them is not the front end of coding but a **decision layer** with inverted requirements — "creative and collaborative" where implementation was "individual" and "heads down" — and the failure mode is running both in one tool and one posture. The concrete tell is drift inside a single session: "when you drift from the planning phase into the polish phase and is your tool serving you," since an IDE built for individual implementation is the wrong instrument for a shared design conversation, and chat is worse still ("chat is a is a brain off medium… built for execution"). He is explicit that plan mode and spec-driven development already point this way and that neither goes far enough — plan mode is "a chat conversation that eventually just leads into agentic implementation," spec-driven development is "a full-on factory" that assumes you already know what to build ([Separate the Decision Layer From the Implementation Layer](../concepts/separate-the-decision-layer-from-the-implementation-layer.md)). Without that layer the symptom is **velocity sickness**: a PR backlog that breaks the merge queue, work sprinting in incompatible directions, agent bankruptcy at the start of each day, and — the one he ranks first — decisions being made by the agent rather than the engineer ([Velocity Sickness Is Output Without Impact](../concepts/velocity-sickness-is-output-without-impact.md), [Ceding a Critical Decision Transfers Ownership of the Code](../concepts/ceding-a-critical-decision-transfers-ownership-of-the-code.md)).

Two consequences are worth carrying into workflow design regardless of what tool you use for the decision layer. First, the review point moves: "if you have a colleague at work and you agree on how something's going to be built, the code review that comes afterwards becomes much simpler" — the same conclusion this topic reaches from throughput ([Review Research and Plans Before They Multiply Into Code](../concepts/review-research-and-plans-before-they-multiply-into-code.md)), arrived at from alignment instead, with the practice being to hand the plan to a teammate before handing it to an agent. Second, the success signal is not completion. Dailey reports that teams adopting a decision layer "start to plan and then not implement their plan… this is actually like a really good sign," because prioritization then happens after exploration rather than being forced by **prototype gravity** — "once you have a prototype, it's really hard to throw that away" ([Unimplemented Plans Signal a Working Decision Layer](../concepts/unimplemented-plans-signal-a-working-decision-layer.md)). That reframes an abandoned plan from waste into evidence, and it is the one claim in the talk most in need of a counter-metric, since nothing distinguishes exploration from avoidance. Nothing in the talk is measured; it is a founder's argument for the category his product occupies.

Arjun Singh (Superconductor) attacks the coordination residue this topic keeps circling: the human who carries work between systems. His first target is the agent's reachability — a session addressable from Slack, an app, and GitHub rather than a bot per surface, so that "your team and your agents can work together and don't have to like context switch and copy context back and forth" ([Make One Agent Session Reachable From Every Interface](../concepts/make-one-agent-session-reachable-from-every-interface.md)). His second is the triage step, and the diagnosis is precise about what MCP already solved and what it did not: the signals "already exist… people hook them together with MCPs. So now your coding agent can check the email or check Notion," but "how does it know what to work on? It's still kind of stuck everywhere. And so some humans are involved in taking stuff from one place and telling it solve email number 48 or ticket number 6,000." Retrieval was solved; selection was left to a person. The answer is to let the agent watch the raw conversation stream — a meeting bot in Meet, Zoom, or Teams alongside Sentry and bug-tracker feeds — and decide for itself what is new work ([Turn Unfiled Conversation Into Concrete Prototypes](../concepts/turn-unfiled-conversation-into-concrete-prototypes.md)). The demonstrated case had no ticket behind it at all: a passer-by at their booth said out loud that agents should have clear completion criteria, and the bot filed and built it.

Two design choices are what make that survivable, and both are transferable. The output contract is loosened from mergeable to reactable — "am I going to ship this one exactly how it is? Like, no, probably not. But it's a new idea, it's concrete, I can play with it" — which is what makes an unrequested prototype cheap to reject. And filing authority carries a deduplication rule stated in one sentence: "if it finds existing work, it'll link to it," the cheap guard against the failure another team in this topic reported directly, agents filing hundreds of unwanted issues. The precondition for all of it is environmental rather than procedural: the codebase must run in an isolated cloud environment, which is also what removes the queue-and-triage path for non-engineers — "without that, they'd have to put it in linear and linear would eventually pick it up and a PM would triage it" ([Environment Isolation Is What Lets Non-Engineers Trigger Real Work](../concepts/environment-isolation-is-what-lets-non-engineers-trigger-real-work.md)). What none of it prices is the other side: "dozens of new ideas that are prototyped" after every meeting, plus support-triggered fixes, all landing on the same human review gate the team says it never relaxes.

Justin Smith (Resolve AI) describes the operations-side counterpart, and the contrast is instructive. Superconductor's problem is that nobody noticed the work; Smith's is that everybody knows about the work and nothing fires for it. His examples are all named and understood — watching a deploy land healthy, a morning system digest, a returning P99 drift, a quarterly capacity report — and they persist on memory alone because they have no ceremony: "on-call you've got a page that goes off. You know somebody's going to receive that. Incidents you create a bridge, you invite people in… but there's just a long tail of other things that we are accountable for that doesn't have sort of a thing that's going to show up in your sort of job description." The P99 case names why paging is not the fix: "this may not be paging, right? Because we're not going to alert on everything." Automating this class starts by supplying the missing trigger, which comes in exactly three forms — a schedule, an event stream, or a message ([Give Unowned Operational Work a Trigger](../concepts/give-unowned-operational-work-a-trigger.md)) — atop a runtime that does not depend on anyone's laptop: "Always runs. It's in the cloud… Runs inside of a sandbox, so it has kind of a file system underneath it."

Two of the resulting workloads are reusable beyond operations. Verification triggered by a *change* rather than a symptom reads what the diff touched, picks telemetry that would expose trouble for it, walks the causal chain to downstream systems, and sets its own recheck interval — an hour, three days — which covers the paths a pipeline never sees: "a feature flag or maybe some infra changes… which maybe don't get any monitoring at all. And you're sort of just trusting that an alert might fire and an on-caller will wake up and say, 'Who changed what?'" ([Derive the Post-Deploy Check Plan From What Actually Changed](../concepts/derive-the-post-deploy-check-plan-from-what-changed.md), [Watch the Change Paths That Bypass Your Deployment Pipeline](../concepts/watch-the-change-paths-that-bypass-your-deployment-pipeline.md)). And the tuning loop for a standing job runs in the thread the job's own output landed in: replying "this is too verbose. Verbose. Make it shorter" updates the recurring task itself, "so that the next time it fires, it's not going to be as verbose," with creation working the same way — the agent explores the environment, asks a few clarifying questions, and stands up a testable draft before it is shared with the team ([Amend a Recurring Agent Task by Replying to Its Output](../concepts/amend-a-recurring-agent-task-by-replying-to-its-output.md)). The caveat that applies to all of it: an explicitly synthetic demo environment, two segments that did not finish on stage, and no measurement of anything — no catch rate, no false-positive rate, no cost for an agent that keeps re-checking for three days.

Denys Linkov (WiseDocs) contributes a selection workflow with a specific step worth protecting when it gets compressed. His team spent "around 2 months evaluating orchestrators for our AI pipeline," reviewing five open-source projects by hand against "17 different criteria that we came up with," then building proofs of concept "with a team of three to make sure that we actually got the right results." The agentic redesign is faster by an estimated 90% and keeps the same three structural properties: a criteria list written before the search, a fan-out of "sub-agents for each of these criteria and products" instead of one prompt for the whole comparison, and a build step at the end. The build step is the one that must survive the speed-up, because the failure it catches is invisible from inside the document: "it's very easy to undergo AI psychosis, where you look at a deep research report that's 20 pages long and you say, 'Wow, this looks good.' And then those features don't actually exist in the product, and you've set yourself back" ([Validate a Research Report by Building the Thing It Recommends](../concepts/validate-a-research-report-by-building-the-thing-it-recommends.md)). The corpus a research agent reads — docs, changelogs, announcements — describes intended capability; the Q&A's example of a hidden assumption is exactly that gap, "you thought an open-source library had this feature, but it was actually in a beta." The fixed criteria list is also what makes the outcome auditable afterwards: "we got 15 out of 17 requirements right when we were going ahead with the refactor." Two things are unmeasured — the 90% figure is a counterfactual estimate rather than a re-run, and the talk never says how much POC work is enough.

The same talk frames the larger decision this topic keeps meeting in pieces: whether to do a cleanup now or wait for models to make it cheaper. Linkov argues it on business return rather than capability forecasting, and treats partial isolation as a first-class option — "the AI delivery system is a layered approach. You can isolate different parts of your codebase to avoid a full refactor, but there's so many components that you need to keep in mind" ([Audit a Refactor Against Having Waited for Better Models](../concepts/audit-a-refactor-against-having-waited-for-better-models.md)). Two workflow details from the six-month rebuild are worth carrying: plan mode was adopted partway through and became the entry point for each batch of work, and every pull request stayed human-reviewed, with skills used as local checks rather than as reviewers. The unpriced part is the same one that limits the whole talk — no engineer-months, token spend, or account of what did not ship while the rebuild ran.

Frank Coyle (UC Berkeley) supplies the smallest piece of workflow structure this topic has, and an argument that it is not new. Reading Anthropic's Claude Code certification blueprint, he reduces the agent loop to sequence, selection, and iteration — Böhm and Jacopini's 1966 result that those three constructs suffice to express any computation — with the model supplying the branch condition through the API's `stop_reason` field. A workflow step is therefore not "call the model and parse what comes back" but a switch: `tool_use` executes and loops, `end_turn` exits, and `max_tokens` means the step's output was cut off mid-sentence and should not be treated as a result at all ([Read the Stop Reason Before You Read the Answer](../concepts/read-the-stop-reason-before-you-read-the-answer.md)). Any pipeline that feeds one stage's text into the next inherits that third case silently, because a truncated stage output is indistinguishable from a terse one. He adds two operational notes for pipelines specifically. Running a coding agent in CI with interactive mode left on is a named anti-pattern — the agent stops to ask for permission with nobody present, so the approval decision has to move into configuration ahead of time rather than being deferred to a person ([Permission-stable command wrappers reduce approval friction](../concepts/permission-stable-command-wrappers-reduce-approval-friction.md)). And any batch of work that does not need an answer today can go through the batch API at half the token cost for a result "in at least 24 hours," which makes scheduling an inventory question — which of your workflows are actually interactive ([Treat Token Spend as a Strategic Axis](../concepts/treat-token-spend-as-a-strategic-axis.md)). None of this is measured; it is a reading of a vendor exam blueprint by someone teaching from it.

Idan Gazit (GitHub Next) demonstrates a concrete answer to a question this topic keeps deferring: what artifact *is* an agentic workflow, and who can edit it. GitHub's Agentic Workflows put the whole thing in one Markdown file in the repository — prose instructions in the body, a YAML front-matter manifest of permissions, allowed tools, allowed network destinations, permitted writes, and capped outputs — and compile it into a GitHub Actions workflow. The contract is that the compiled form is a build artifact: "the markdown is the source code. The YAML is like a compiled artifact… If you don't like the way that the automation works, just edit the English. It gets recompiled… You never look at it." Authoring, correspondingly, looks like messaging a colleague. His dependency-upgrade job started as roughly three lines — "every day I want you to check if there's a new release, look at the change log… come up with a plan for the upgrade, and then create a PR" — and expanded, codebase-aware, into a full playbook: "because it sees my codebase, it was able to infer what it even needs to check." The demonstrated run took a personal site across two major Astro versions, fixed the broken call sites, verified the build, and separately listed the manual steps it could not perform.

Two consequences are worth separating from the product. First, the split inside the file is a trust boundary, not a formatting choice: the prose is elaborated and rewritten freely, while the manifest binds capabilities before the agent starts, on the argument that "if you're prompting the guardrails at the agent, you're effectively letting the fox loose in the henhouse. It's not actually a guardrail." That is the same position this topic's deterministic-gate material reaches from other directions, applied to scheduled CI. Second, a workflow that is one readable document is forkable, which is what makes a starter library plausible — an issue triager, a CI doctor, a Repo Assist swarm, daily team and repo status — and what carries the pitch past engineers to "product managers whose job it is to look at information over here and summarize those tickets over there." The unpriced cost is in the contract itself: an artifact nobody reads is an artifact nobody reviews, and the talk offers no account of how a bad compile would be noticed.

This topic's contribution-quality material assumes a receiving workflow that stays open and gets better filters. Saoud Rizwan (Cline) reports the cases where maintainers stopped assuming that. Zig banned AI-assisted contributions, with the reasoning stated as a preference between two things a project accumulates — they "value contributors more than they do the contributions"; curl considered shutting down its bug bounty under the volume of AI-generated reports; tldraw closed all pull requests outright ([Closing the Contribution Channel Is Where Slop Filtering Ends](../concepts/closing-the-contribution-channel-is-where-slop-filtering-ends.md)). GitHub's third-party-pull-request toggle makes the last step a setting rather than a policy. The workflow lesson is the direction of travel: templates, required reproduction steps, effort gates, and triage rotations each raise the cost of submitting, they raise it for careful contributors and careless ones alike, and none of them reduces the incoming volume that motivated them — so the sequence escalates one way and terminates in a channel that accepts nothing from outside. What that costs is the apprenticeship path, since a first pull request is how most people enter a project, and it is the part with no replacement proposed. Rizwan's own position is that maintainers are entitled to close the door, which sits oddly beside his argument that agents should write most code; both are worth holding. No submission volumes, acceptance rates, or attribution method for identifying agent-generated work are given anywhere in the talk.

Eyal Blum's Figma report puts two workflow claims beside each other that are usually argued separately. The first is that planning, not prompting, is where the human's craft now lives: he describes a week spent writing a detailed plan and aligning three other teams on it, then one overnight agent run producing roughly twenty pull requests of ten to a hundred lines — work he self-estimates at six weeks pre-AI, delivered in one. The plan document is what carries that, and it has structural requirements rather than stylistic ones: a "why" at the top the agent is not permitted to rewrite, phases sized to a pull request the author would review in one sitting, a validation gate on each phase so that a written-but-unvalidated first stage does not become the foundation for four more, and enough detail per phase to hand it to a subagent that will see nothing else. The rules are deliberately loop-agnostic — "once you have the plan, you can use whatever loop you want" — which is what separates them from this topic's process pages. The second claim is about communication rather than code. Documents, Slack messages, and emails have grown three to four times longer while saying the same thing, and the cues that used to tell a reader where to concentrate no longer work; his team's answer is a convention, not a tool, opening each pull request description with a short passage a human actually typed and marking the generated text below it as the part to be suspicious of. He also declines to standardize the personal loop, finding "diminishing return[s] in trying to centralize everybody on one thing" as long as colleagues can still iterate with each other's setups. None of it is measured, and the speaker describes the org as mid-journey with its automation story unfinished.

Varun Shenoy (Long Lake) argues that two workflows this topic treats separately — improving an agent from production data, and getting people to use it — are one loop, and that the seam between them is an org chart. Continual learning, "whether it's in the prompt or in the weights," is owned by research and platform engineering; enablement is owned by growth, deployment, or customer experience; the two are "usually pretty siloed, not much interaction between the two." His merge is mechanical rather than cultural: "the agent only improves if people actually use it. And people only use the agent if it's worth adopting." That makes adoption the rate limiter on the improvement program rather than a downstream concern, and it means a continual-learning roadmap in a low-usage deployment is starved by construction. The loop also has no seed, which he calls the elephant: "everyone assumes the usage just shows up… It never does. Getting a 100-year-old firm to change its processes is hard. You could have the best AI coworker on Earth. And if the person who's closed the books for the last 20 years continues to do things the same way, nothing changes." His remedy borrows Jensen Huang's "extreme hardware software co-design" as extreme software–service co-design: lower the activation energy by embedding into Excel, the ERP, the 3D design software, or Outlook, and gather the requirements in person, because "you cannot co-design software with the services business over Zoom or over a support ticket." The physical list is specific — a lunch and learn, a cotton-candy stand at their trade conference, questions asked on a mountain bike — and its common property is that none of them is a meeting the customer prepared for. This is one operating model argued from the inside, with nothing measured and no comparison against a remote-first deployment.

Bond and Ketkar (Uber) describe what it takes to let hundreds of teams customize one shared workflow without a central curator, which is a governance problem this topic usually meets in smaller form. The authoring step turned out to be nearly free — a team asks a model to read its past pull-request reviews and emit a review skill — so the cost moved entirely to operating the result: binding rules to the ownership model the company already has rather than a parallel registry, co-locating them next to the code so their refresh rate stays high, routing deterministically so which team gets which review with which model is computable, and returning per-rule telemetry to the rule's author so bad rules are retired by the person who wrote them ([Distributed Rule Authoring Is a Platform Problem, Not an Authoring Problem](../concepts/distributed-rule-authoring-is-a-platform-problem.md)). The counter-force bounds how much may be delegated: security and compliance checks stay centrally mandated, because "we can't rely on teams hoping to run the code review skill that happens" — a rule living in a coding agent's own configuration is advisory, since whether it ran depends on how somebody invoked the agent. Two workflow-shaping details travel with this. Volume is a property of the pipeline rather than of any generator, so the place to decide how many comments a reviewer sees is a single post-processing waist that rates, categorizes, filters, and deduplicates across all of them ([Comment Volume Is a Property of the Review Pipeline, Not the Model](../concepts/comment-volume-is-a-property-of-the-review-pipeline.md)). And their guardrails are a negative turn budget rather than a step cap — "tell the agent what not to waste turns doing" — because review carries a deadline and a review that arrives after the author has moved on is worthless regardless of content. Nothing about the platform is measured beyond the aggregate figures: no rule count, no per-rule cost, and no rate at which authors actually retire rules after seeing the feedback.

Imad Touil (QuantumBlack) attacks the question of where a workflow's organization-specific content actually lives, and answers it by elimination. A workflow holds four authorable things, and three cannot carry knowledge: hooks "trigger on events," MCP servers are consumed from vendors rather than written ("who actually build a lot of MCPs? We just use MCP tools… so we don't really own"), and sub agents exist "just to minimize the context window." What remains is skills, so "all of your know-how is actually at the skills level. And if you don't have the right structure of your skills, then you're not really having a deterministic workflow." Three consequences follow for this topic. A missing skill produces no defect and no ticket — it is paid for as steering iterations and tokens by each engineer who needs it, which makes cost per task class the leading indicator of a library gap rather than a request queue. Composability across independently authored skills cannot be retrofitted by a catalog, because two overlapping skills are both findable and both owned and still conflict when loaded together; the domain carve and named human owners come first, which is where "technology stop solving the problem." And a self-improving skill loop, "the next hype," writes into whichever library already exists, so it multiplies the governance regime rather than supplying one. He also insists the specify-plan-task-implement loop most coding agents implement is a single step of an organization's lifecycle — "probably 10, 20%" of it — and that organizations run many such lifecycles rather than one, so the catalog argument applies one level up, to workflows themselves. Nothing in this talk is measured: the fifteen-team, six-month illustration is a simulation Touil wrote and parameterized himself, and the prescribed end state is also the kind of transformation work his firm sells.

The clearest workflow lesson from DoorDash's eval platform is what its team stopped building. Annotation work varied enough across use cases — grading restaurant menus, annotating images, manual testing — that "it's almost hard for a platform team to build like a UI specific for each use case," so instead of one configurable generic screen they shipped stable APIs and had strategy-and-operations staff point Codex or Claude Code at those endpoints and generate whatever interface their use case needed. The precondition is stated explicitly and is the part that travels: "the underlying patterns were similar" — the variation lived in the presentation, not in the data model. That decision is the third stage of a progression the team narrates directly, from UI first (the domain experts were not engineers), to API first (the platform team had become the queue), to workflow first (coding agents turned non-engineers into API consumers), with the stages accumulating rather than replacing one another. Judge calibration went the other way and got a first-party self-serve UI, because that workflow was too intricate to leave to a generated app and its output has to be reviewed before it is promoted. Nothing here is measured, and the talk never says who maintains an operator-built app after an endpoint changes.

Formal verification changes the shape of a spec-driven workflow in a way worth recording next to this topic's existing spec material. Varun Pant enters through the same door — spec-driven development, "for example, with Kiro" — but the destination differs: the specification is written directly in Lean or written in natural language and auto-formalized, the coding agent "implements from the specification," and "the formal verification tool proves that the implementation matches the specification," so reviewing the implementation stops being a human step. What replaces it is a step the prose version never made obvious. "Now, this is really important. You then validate the specification. So, either the human reviews it, or you test that it holds on some inputs," because "the specification is upstream. It's a living, breathing artifact that the builder interacts with. You want this to be correct. Everything else is downstream from this." Auto-formalization adds a second link to the chain — natural language to formal spec to code — and the verifier certifies only the second, so a mistranslation produces a perfectly valid proof of the wrong statement. The workflow's inner loop is also newly agent-shaped: proof search is tactic-by-tactic tree traversal with backtracking "when for some goals, you're not able to prove it," terminated by a checker that rejects immediately and cannot be argued with — the labour that historically made proof assistants expensive is precisely the part an agent absorbs. Nothing here is measured, and the talk offers no criterion for when a specification has been validated enough.

Human supervision does not have to be distributed through an agent's loop; it can be concentrated at a single handoff, provided the run is cheap, reversible, and produces one inspectable artifact. Stripe's billing demo is that shape in its clearest form: the agent works unattended from a one-sentence instruction and the entire human contribution sits at the boundary between a sandbox and the production account. What makes the pattern safe is not restraint during the run but the design of what comes out of it — a rendered draft invoice, split into build, plan mode, cloud, and AI gateway credit pools, at the level of detail where a person can recognize whether the intended pricing model was actually built. That output does not exist by default, which is the workflow lesson: the vendor's skills file instructs the agent to flow synthetic usage through the system during setup so the derived artifact materializes, because a provisioned customer and a configured credit rule look identical whether or not they interact correctly. Two guardrails frame the run rather than interrupt it, and the division between them is worth copying — anything the agent could not have known belongs in the skill, and anything only the runtime can detect belongs in a deliberately verbose error. The limit of the pattern is stated by its own preconditions: it degrades as the artifact grows large enough that reviewing it costs what writing it would have.

The workflow change that Amazon's pilot teams credit for their gains is mostly about where the human sits in the loop. A conversational back-and-forth serializes the engineer on 30-second turns, and a serialized engineer cannot occupy a second loop — "it's very difficult to clone yourself into multiple agents" — so the ceiling is roughly one regardless of model quality, and faster models only shorten the wait. The substitution is a different payload rather than a different tool: send the task *and* the criteria the agent can validate itself against, so it returns only when the work runs, compiles, passes tests, is testable, and has coverage; then promote those criteria into the steering file so they recur without prompting. That contract only buys unattended time if the checks are fast and local, which is why the same teams replaced live-service integration tests with locally-run deterministic mocks — loop count is the currency, and more loops per hour is what makes an hours-long self-correcting run possible. Two further workflow moves complete the set: settle ambiguous intent in a document first, because iterating with a model on a specification is cheaper than iterating on code spread across a codebase when the intent itself was wrong; and treat the context file as a two-way artifact, adding what the agent was missing at each failure while pruning workarounds that newer models have stopped needing. Escaping the inner loop does not make the work free — it relocates the constraint to attention, terminal-tab switching, and the review of several parallel outputs at once — and once the engineering loop is fast, the constraint can leave engineering altogether, landing on decision and launch-approval processes that were rounding errors when builds took the better part of a year.

Three operational patterns come out of Unblocked's context-engine demo, and each is a workflow rather than a model choice. First, responses that carry their sources do two jobs at once: [they are a correction surface for the human and a continuation pointer for the agent](../concepts/attach-sources-as-a-correction-surface-and-a-continuation-pointer.md) — a wrong answer becomes a fixable knowledge-base entry, and "the sources come back to Claude and then Claude knows exactly where to jump to next." The correction half only works if the knowledge base is writable, otherwise citations convert a silent wrong answer into a visible recurring one. Second, review guidance mined from PR history is [ranked by the author's seniority or expertise](../concepts/weight-mined-review-guidance-by-the-authors-expertise.md), using the same review-relationship graph that projects onto the codebase as an expert-coverage map — one structure, two consumers. Third, a debugging loop that ends in a self-explaining pull request: an engineer noticed the review agent's flagged-issue count had dropped, traced it conversationally, and an internal cloud agent produced a PR that "not only generates the fix, it also is able to relate it to all the conversations that were happening" — with [the causal explanation resolving to a Slack thread](../concepts/a-model-swap-moves-agent-output-metrics-and-the-reason-lives-in-chat.md). That is the incident-to-PR pattern with a conversation corpus substituted for telemetry: easier to retrieve, harder to verify, and reviewable because the reviewer can check the reasoning rather than only the diff.

Delegation surfaces have a social property that is easy to miss when comparing them on capability: a private CLI hides the org's best prompts, while a shared channel where colleagues tag the agent turns every good delegation into a demonstration. Anthropic reports that as the transmission mechanism for ambition — one observed ask ("you are responsible for this part of the code base... monitor this feedback channel and proactively take on tasks") moved a former chief product officer's own ceiling — and the end state is a standing participant that holds context, has memory, and acts between check-ins, rather than a per-task invocation. Two operating disciplines sit underneath. Instrument before you have the question, because a metric first recorded during an incident has no history and cannot say whether the number is normal, and build runtime knobs as a first-class surface because AI systems are made of tradeoffs you will want to move without a deploy. And pace the team against the cycle rather than the day: a news cycle that refills before Wednesday makes burnout the default outcome, so being offline for a couple of days has to be explicitly permitted and the inability to go offline treated as a system defect.

A workflow layer over customer or account data is best modelled as an event stream on state transitions rather than as a report anyone reads on a schedule. The transition set worth encoding includes an entity event, a positive rate change, a watchlist match, and — the one most alerting systems cannot express — a stop, which produces no rows and therefore has to be detected against expected activity instead of observed activity. The output contract stays modest: the system routes attention to a human or an agent and does not decide. The staffing analogue is a group that both runs the operational work and builds the systems it runs on, which shortens the loop between noticing a workflow gap and closing it, and which is reported as working at small scale without a claim that it survives growth.

Rolling an agent out to a large population is itself a workflow with stages that answer different questions. A pilot staffed with self-selected enthusiasts can only certify that the answers are right; a 10% beta reveals workflow fit by where feature requests concentrate and exits on weekly-active retention rather than satisfaction; general availability is the first cohort containing people with no interest in the product, which is why trial rate only becomes measurable — and binding — there. What follows GA is not a maintenance phase but two ongoing workloads: months of activation work that can consume most of the owner's time, and a standing share of engineering capacity spent rebuilding onto platform primitives that did not exist at launch.

A business-process instance shows what a workflow layer looks like when the spec comes from watching people rather than from a document. Notion's team reduced every go-to-market workflow to four questions — what do we know, what should happen next, how do we execute that safely, did it work — and built one layer per question, with safety inside the decomposition rather than added at review time. The act layer is derived by shadowing the strongest reps for the most repetitive part of the job, on the argument that "if you encode a mediocre process you get a mediocre agent" and that the first workflow to encode is the most legible one, meaning documented and repeated. Each signal becomes a durable Temporal workflow whose run touches enrichment, web search, and draft generation, and the property named as decisive is per-item isolation: one malformed transcript cannot take down the batch. Above it, eligibility and segmentation rules are pulled out of the individual tools into one shared rule set with a single routing classifier, which is what stops two subsystems from contacting the same customer twice.

A recurring generated artifact is a workflow shape worth separating from the agent-loop cases. Cloudflare's weekly go-to-market summary runs as a fixed chain — fetch pre-shaped data, draft through MCP reads, check the draft's veracity against the data, then rewrite for tone so risks and opportunities land with equal weight — with per-call observability across all three model stages. Two design choices generalize. First, the deterministic work is pushed out of the model entirely and into the transform layer, so the filters and aggregations that decide the answer are engineered once rather than re-derived per run; the model composes prose over a small table it cannot reorganize. Second, one of the three roles has an objective no correctness check can express: a factually accurate summary can still bury the bad news, so framing gets its own stage, specified by exemplars rather than rules. The acceptance procedure matched the artifact's cadence — a human read every single run for two to three months — which is affordable at roughly a dozen runs and is a burn-in rather than an eval, since it produced a decision to trust and no recorded defect taxonomy to carry forward.

## Open Questions

- Does a public delegation surface raise ask quality, or mainly raise ask volume and performative delegation? The multiplayer claim is reported from inside a company that builds the models and is not measured against a private-CLI baseline. ([Krieger](../sources/20260827_qqrk7CtkuIw.md), 09:02-09:39)
- How does an expertise-weighted guidance corpus avoid calcifying? Boosting by seniority preserves outdated rules along with durable ones, and no source in this wiki describes a decay, expiry, or contest mechanism for mined review guidance.

- Liguori's self-validation contract — return only when the work runs, compiles, passes tests, is testable, and has high coverage — is stated as a prompt and steering-file convention with no report of how often agents return without meeting it. What is the false-completion rate against a criteria list the agent can read? ([Liguori](../sources/20260828_pqlWNihgdjI.md), 12:09-12:31)
- At what artifact size does single-handoff supervision stop working? The sandbox-then-review pattern depends on the output being small enough to check by looking at it — one draft invoice is, a hundred provisioned entities across four services is not. No source in this wiki states the threshold, or offers a way to keep the review cost sublinear as the agent's unattended stretch grows, which is the variable that decides whether this pattern scales past a demo.
- Does adding a verifier reduce net human time in a spec-driven workflow, or move it? Reviewing the implementation becomes mechanical, but validating the specification becomes a mandatory step with no stated method and no sufficiency criterion, and the specification now has to be maintained in a formal language. No source in this wiki reports the net change for a team that made the switch. ([Pant](../sources/20260828_lRa9sPaMyy4.md), 01:11-02:10)
- What happens to an operator-generated annotation app when the API underneath it changes? DoorDash's whole argument rests on "very stable APIs that our team owns," which is a promise with a shelf life. The talk never says who owns the generated apps afterwards, whether any have been rebuilt, or whether a deprecation has yet been tested against them.
- Does the four-component elimination survive in an organization that authors its own MCP servers? Touil's argument that skills are the only home for know-how rests on "we just use MCP tools" — but this wiki also carries the case for in-house servers that carry domain vocabulary, which would give knowledge a second place to live and change where governance effort should go.
- Which changes qualify for automatic approval, and who decides? Bond states both that Uber sees "a short path in the near future to a percentage of our code landing automatically, having automatic approvals" and that the human role expands upward into architecture and product judgment, without naming the boundary between the two populations. Every mechanism this topic carries for that decision — risk-based routing, defect-class coverage, human gates on high-impact actions — describes how to route a change to more scrutiny, not how to certify that a change needs none. The missing artifact is an explicit, auditable qualification rule and a record of what the automatically-landed population actually did in production afterwards.
- Does in-person co-design beat a disciplined remote discovery process, or only beat a passive one? Shenoy's claim is stated as an impossibility — "you cannot co-design software with the services business over Zoom or over a support ticket" — and the mechanism he offers is real: a ticket is written by someone who already framed their problem as a feature request, so the channel selects for articulated needs. But the comparison is against organizations that were waiting for tickets, not against teams running structured remote observation, and no source here measures the difference. The travel cost is also unstated, which matters because it decides whether this is a method or a description of what a well-funded operator can afford.
- How far does workflow pluralism go before it stops composing? Blum reports "diminishing return[s] in trying to centralize everybody on one thing, but as long as it works for their flow and other people can iterate with them," which cuts against this topic's champion-and-standard-repo material without contradicting it — the plausible split is that the repo-side substrate every agent hits should be shared while the personal loop should not. Neither source offers a threshold, a failure case where divergent loops stopped interoperating, or a cost for the divergence, so the line between substrate and loop is currently drawn by judgment alone.
- What replaces the first pull request as an entry path into a project? Every filter this topic recommends against low-effort submissions falls hardest on someone who has contributed nothing yet, and the terminal case — a closed contribution channel — removes the path entirely. No source here proposes a substitute: not a sponsored-newcomer track, not a separate queue with different acceptance rules, not a trusted-referrer mechanism. Until one exists, "value contributors more than contributions" describes a preference the closure itself makes impossible to act on.
- What is the review surface for a workflow whose executable form nobody reads? "You never look at it" is stated as a feature, and for a build artifact it usually is — but a compiler for English into CI configuration is not a deterministic one, and the talk shows no failure case, no compile-fidelity measurement across many workflows, and no description of what a bad compile looks like. A reviewer approving a pull request sees a diff of sentences and has to trust that the recompile preserves the manifest's denials. This topic elsewhere argues that the enforceable layer should be hand-written and covered by tests; here it is machine-generated and unexamined, and no source reconciles the two.
- Which agent workloads can actually tolerate a 24-hour turnaround? A 50% discount for batch submission is the only cost lever in this wiki that trades nothing but wall-clock, yet no source reports what share of a real team's token spend is genuinely non-interactive. Evaluation sweeps, backfills, and scheduled reports are obvious candidates and interactive coding obviously is not, but the middle — nightly review passes, documentation regeneration, dependency triage — is unclassified everywhere.
- How much proof-of-concept work is enough when the research step gets 90% faster? The manual version paid for "a team of three" building POCs against five candidates, and the compressed version still ends in a build step — but nothing says whether one throwaway integration per finalist is sufficient, or which of the seventeen criteria a POC can actually falsify. The check that makes the speed-up safe is the one part with no sizing guidance.

- When does a standing agent job stop? Every recurring workload in this topic is created and none is retired, apart from one hand-set week-long watch that "can sort of stop [its] job" when the worry that motivated it expires. A team that adopts trigger-per-unowned-task accumulates jobs whose owners change and whose reasons lapse, and no source describes a review, expiry, or ownership-transfer mechanism — which turns the automation into a second unowned long tail.
- Does amending a task by replying to its output need a permission model? A recurring report shared with a team can be reshaped by anyone who replies in its thread, and nothing is said about who may amend, whether amendments are versioned or reversible, or how an instruction is distinguished from ordinary discussion of the report. The one demonstration was not shown completing on stage.
- What fraction of agent-originated prototypes is noise, and who absorbs the cost of finding out? "Dozens of new ideas that are prototyped" and "at least a few shippable PRs" per meeting is a yield claim with no denominator, no definition of shippable, and no merge count. The number that would make the pattern evaluable — reviewer time spent per idea that survived — is not reported by any source that recommends this shape.
- Should an agent be allowed to originate work from a conversation nobody chose to file? Not filing something is a decision, and a bot that treats every remark in a meeting as candidate work removes it. No source discusses consent, minuting, or whether participants know that speculative remarks become prototypes — nor what an organization does when the agent builds something a customer said in a sales call.
- What tool actually serves a decision layer, and how would you know? Dailey rules out the IDE (built for individual implementation), chat (a "brain off" execution medium), plan mode (a chat that slides into implementation), and spec-driven development (a factory that presumes the decision is already made) — but the positive requirements he names, "creative and collaborative," are not testable, and the only vendor with an answer here is his own. No source offers a comparison, a trial, or even a checklist that would let a team evaluate a candidate.
- How do you tell a healthy unbuilt plan from an avoided one? If plans written and not implemented are the success signal, the failure mode with the identical signature — endless exploration that never commits — has no stated counter-metric anywhere in this wiki.
- What does running verification on every agent loop cost, and when does it stop paying? The propagation argument says a defect caught during generation saves every later loop that would have built on it, but no source gives a per-call latency, a token cost, or a false-positive rate — and a check that fires on every turn is the one most exposed to all three. The comparison that would settle it (in-loop plus PR-gate versus PR-gate only, same tasks) exists nowhere in this wiki.
- What converts a detector's finding into a tracked item with an owner and a stable identity? Two independent failures in this topic — raw clustering as a monitoring layer, and unscoped agent filing into a tracker — have the same shape, and neither source describes the missing conversion step.
- How much of an engineering team's time should go to maintaining the shared agent setup, and how would you know it was too much? Khandelwal is explicit that the work "is not going to lead to like meaningful PRs" and equally explicit that it never ends, but names no fraction and no signal for the boundary.
- If clusters cannot serve as the issue-tracking primitive, what does? Hylak states the requirements an alternative must meet — stable identity across days, controllable boundaries, product-defined sameness — but the talk describes no mechanism that produces them, and stops short of saying whether his own product's answer is classifier-based, human-named, or something else.
- How much of an operational trace loop should be deterministic sweep versus agent reading, and how would you tell you had the split wrong? Both halves are recommended and neither is measured, so the allocation is left to taste.
- How should a scheduled sandbox job and a live human editing the same files resolve a conflict? Sync-down/sync-back is presented as "super simple," and it is — until both sides write the same note on the same night.
- What does the ship-trace-mine-experiment loop cost to run per cycle? Trivedy gives the ingredients of the arithmetic (traces × average trace size × input token price) but no worked example, so the point at which mining a corpus costs more than the improvement it buys is unquantified.
