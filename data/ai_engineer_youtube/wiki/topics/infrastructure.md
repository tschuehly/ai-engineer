# Infrastructure

## Overview

Cursor Composer shows that model training itself can become an infrastructure problem once the target behavior is a real coding-agent loop. Matching training and inference required trainer, inference, and environment servers; rollout orchestration with Ray; cloud VM sandboxes that looked like the product environment; load balancing for uneven rollout lengths; and low-precision custom kernels to make large MoE training practical. The useful boundary is not just model versus app: tool schemas, tool responses, sandbox fleets, semantic-search indexes, and deployment kernels all shape what the model can learn and how fast users can interact with it. Browser-agent runtimes make the same point at the observation layer: the runtime interface — how the page is represented, how actions are dispatched, and how change is fed back — is a bigger reliability lever than the model, and a well-built interface lets a cheaper model succeed on tasks where a stronger model stalls.

AI infrastructure spans local training environments, edge deployment, server-side inference operations, observability systems, identity systems, and the product systems that meter expensive AI usage. Edge AI needs a path from model conversion through quantization, runtime integration, accelerator selection, and fleet validation; CPU/GPU deployment can use a shared artifact, while NPU deployment may require ahead-of-time vendor compilation behind a consistent app API. Apple local inference adds a native runtime path: MLX Swift LM can integrate Hugging Face-hosted MLX weights into iOS, iPadOS, and macOS apps, but product infrastructure still needs curated model catalogs and model-download planning. Desk-side local AI workstations add a different infrastructure tier: when they run the same serving stack used in production, they can reduce shared-infrastructure queueing for privacy-sensitive or latency-sensitive prototyping while preserving a path to later data-center or cloud scaling. Server-side small-model inference needs model-aware runtimes plus routing, queueing, autoscaling, observability, and GPU provisioning so many specialized models can run efficiently in production. Agentic long-context inference adds context-platform infrastructure: memory tiers for KV-cache storage have to balance capacity, write speed, fetch speed, cache TTL, and GPU blocking behavior so repeated prompt and tool tokens become usable cache hits. Model-family access also becomes infrastructure: downloadable open weights support local/self-hosted deployment, while hosted playgrounds and managed endpoints let teams prototype larger reasoning models before owning serving operations. Open model infrastructure also depends on ecosystem fit: permissive licensing, Hugging Face or Ollama-style distribution, llama.cpp, MLX, vLLM, Unsloth, and product integrations determine whether teams can fine-tune, quantize, self-host, or run locally without rebuilding their stack. Team capability is part of the infrastructure decision: improving open-source and commercial platforms can reduce the need to build custom serving systems, while product-specific domain complexity can raise the need for people who understand the deployed workflow. Enterprise self-hosting adds a build-or-buy platform boundary: runtime and GPUs need reliability engineering, fast scale-up, crash recovery, observability, lifecycle controls, and audit surfaces before open models can carry mission-critical traffic. Production AI applications also need managed prompts, tools, scoring functions, trace metadata, and online scoring automation so local prototypes can become monitored systems. Eval and observability infrastructure for agents must handle production traces that are text-heavy, semi-structured, large, and high velocity, then make those traces usable for offline replay, online scoring, aggregate failure clustering, and systematic tuning of prompts, tools, memory, agent counts, and orchestration patterns. Local training work adds a smaller-scale infrastructure lesson: choose a setup that can run on MPS, CUDA, CPU, or Colab, and keep the model, tokenizer, and batch sizing proportional to the available memory. AI monetization adds a billing-infrastructure lesson: usage caps, threshold notifications, top-ups, rate limits, detailed metering, and pricing simulations protect customers and providers when AI calls can burn spend unexpectedly or change economics before launch. Enterprise MCP deployments need identity infrastructure as well: centrally managed cross-app trust can reduce local standing credentials and make agent tool access revocable through SSO. Gateways extend this into a broader MCP control plane: one trusted platform can provide auth, authorization, observability, secure connectivity, routing, deployment, and credential primitives while individual teams build domain-specific servers. Remote MCP infrastructure also needs ordinary horizontal-scaling discipline: session storage, observability, policy-derived tool surfaces, and stateless request handling keep large tool-call volumes from depending on one stateful server process. As APIs become agent-facing surfaces, infrastructure also needs compact API exposure mechanisms such as generated SDK types and code-mode execution, plus sandboxes, network controls, secret boundaries, and rate limits so model-written code cannot turn broad API access into an abuse path. Large enterprises may also need internal AI engineering platforms around monorepos, service discovery, on-call systems, and code review because their context and workflow boundaries are too specific for generic agents.

Open-model ownership is also an infrastructure-economics decision, not only an availability one. Owning the weights buys sovereignty (no loss-of-service exposure, proprietary data kept on owned hardware, free customization) and, when the license is permissive, removes the procurement and legal review that blocks sovereign and regulated deployment. Whether a given workload should run hosted, on a single owned GPU, or on the edge is a threshold call across capability, hardware fit, latency budget, and cost — where rising agentic token generation is the pressure tipping toward ownership, on-device cost is measured in energy rather than tokens, and the serving tradeoff is uptime control against maintenance, ongoing, and upfront capex spend. Intelligence-per-size matters here too: a near-top open model that runs on a single GPU instead of four or five changes the capex side of the calculation, and an enterprise can scale a 300B-class multi-GPU workload down to a single H100/A100 or even an L4.

Physical AI devices push the self-hosting boundary all the way to a pocket terminal, and the infrastructure lesson is to split the device from the model. Lech Kalinowski's Vault handheld runs only a tiny firmware on an ESP32-S3 microcontroller — I/O plus fixed-buffer one-bit rendering, deliberately with no markdown engine and no `malloc` on the MCU — and offloads all inference and agent work to a dependency-free self-hosted Python backend that serves an open-source ~120B model (gpt-oss:120b) via NVIDIA TensorRT-LLM behind an OpenAI-style proxy. The proxy is itself an infrastructure fix: not every open model matches the OpenAI API shape, so an adapter layer is what lets the firmware target one stable interface while the backend model swaps. "Keep the model off the metal" is the durable framing — the device owns interaction and rendering, the backend owns compute — and graceful degradation across independent surfaces and inputs (OLED/e-paper, keyboard/encoder, Wi-Fi/local shell) falls out of keeping the device thin.

Stateful remote MCP adds a serverless memory variant to that infrastructure. Cloudflare's Agents SDK uses Durable Objects-style state for MCP servers, so preferences, approval status, and workflow memory can live with the server endpoint and remain available when different clients connect. That reduces separate database plumbing for small stateful agent services, but it also makes idempotency and webhook routing part of the infrastructure contract.

The same Durable Objects primitive is also a candidate compute unit for the agent itself, not just its MCP memory. In Cloudflare's "stateful serverless" model, a given ID maps to one addressable instance that spins up once and receives every later request and websocket, hibernates when idle, persists state in the compute unit, and answers at ~15ms edge latency (inside a 60fps animation frame). Building an agent on this makes resumable streaming, multi-tab/multi-device sync, and background scheduling emergent properties — a client that refreshes mid-stream reconnects to the same instance instead of needing a database, replication, and sticky sessions — so the runtime absorbs the distributed-systems work that would otherwise live in userland. The cost framing is that this is cheap not because of subsidy but because of architecture: ISP-adjacent hardware and bulk bandwidth rather than mega data centers. The same talk reinforces the code-mode/Dynamic-Workers stack already in this topic: generated code runs in a zero-authority isolate ("eval++") that only gets explicitly granted capabilities, and code mode collapses Cloudflare's 2,600 API endpoints to ~1,000 tokens.

Commerce data creates another agent-facing API layer. Retailers and marketplaces may need to abstract product catalogs, inventory representations, brand data, and checkout operations behind cohesive APIs or MCP servers so agents can retrieve current products and complete transactions without scraping websites or negotiating separate feeds for every merchant.

GPU marketplaces add a supply-allocation layer to AI infrastructure. Compute scarcity is not only a data-center construction problem: fragmented providers, idle enterprise GPUs, long grid interconnect waits, and changing training/inference demand can waste capacity even when accelerators already exist. A useful marketplace needs orchestration over heterogeneous clusters, flexible spot/on-demand/reserved commitments, resale or release paths for idle capacity, and a trust layer of provider ratings, benchmarks, provisioning, and reliability signals.

Training clusters invert several of these defaults, and Krea's infrastructure account of pre-training Krea 2 on thousands of InfiniBand-connected GPUs is the wiki's most concrete look at that regime. Its first argument is that the standard observability stack points at the wrong things: GPU utilization "is a lie" — it reads 100% straight through a pre-training run that is nowhere near well used, because it measures time spent doing work rather than useful arithmetic — so tensor core utilization is the honest proxy, validated by watching it climb as the resolution curriculum stepped 128 → 1024 pixels. Worse, the counters that mattered most are ones nothing exports: most of their failures were cross-node communication failures, DCGM ships no InfiniBand metrics (and no NVLink error counters), and the fix was to build the collection themselves, which he reports was easy. The second argument is that at this scale failures are a rate, not incidents: crashes are frequently silent (NCCL timeouts while every dashboard stays green), the same nodes running the same code and data will go an hour and then twenty-four, and the economical posture is replacement plus checkpoints rather than diagnosis — pull any GPU above 78 °C without investigating it, and checkpoint every 20-30 minutes against a filesystem fast enough to write a terabyte in under 30 seconds so the checkpoint never delays training. Their first storage choice, Ceph, failed that trust test. The third argument is scheduling policy: training and production share one cluster and *training holds the higher priority*, on the explicit ground that a GPU-hour spent training is worth more than one spent serving. What makes that survivable is a virtual-kubelet fake node that turns "rent capacity from an external provider" into ordinary pod scheduling, a Prometheus-driven taint that decides whether new pods land in-cluster or outside, and a descheduler that walks them back gradually once local GPUs free up — deliberately not a NoExecute taint, which would evict everything at once and take the site down. The whole scheme rests on a hardware-tiering asymmetry — [inference tolerates degraded GPUs that training cannot](../concepts/inference-tolerates-degraded-gpus-that-training-cannot.md) — because their single-node diffusion-transformer serving runs happily on GPUs that are hot, flaky, or "falling out of the bus," precisely the cards a synchronous training run has to eject.

Data-center inference adds another allocation layer inside the model-serving fleet. NVIDIA Dynamo-style deployments treat serving as a token factory with an application-specific Pareto point across quality, latency, and cost. The infrastructure has to split and balance prefill and decode workers, route around KV-cache locality and queue depth, preserve KV state across structured agent waits, and autoscale specialized worker pools when user traffic shifts from one input/output sequence length distribution to another.

Large RAG systems create their own infrastructure ladder. Broad fan-out and supplementary retrieval can improve recall for ambiguous queries, but more backends, more queries, cross-encoder reranking, and LLM post-processing raise serving cost and latency. Distillation becomes an infrastructure option only after the full stack proves valuable but too slow or expensive: the target is to hold the observed quality bar while reducing model size or response time.

Browsers are becoming an infrastructure layer for both development and runtime AI. Chrome DevTools MCP can expose live web-app diagnostics to agents through structured tools, while browser-native Web AI APIs can put a downloaded local model behind summarization, proofreading, prompt, image, and audio APIs. That shifts some inference, debugging, storage, token accounting, and compatibility concerns into the client browser, and because these APIs are experimental, production use needs capability checks and graceful fallbacks.

Agent-built applications add a deployment boundary: the harness that plans and controls work should not be treated as the same trust domain as generated code. Infrastructure for the new application layer needs sandboxes and execution separation so agent-written software can run without giving that code direct authority over the agent runtime.

Private AI serving adds a confidential-compute boundary for sensitive inference. Apple PCC-style architecture treats the remote AI server as untrusted until the client can verify stateless computation, code-enforced limits, non-targetability, no privileged runtime access, and transparency evidence. Remote attestation can bind encrypted payloads to signed hardware and software claims, while transparency logs let reviewers and clients compare runtime attestations against public signed binary records. The tradeoff is operational: removing SSH, disks, detailed logs, and user-identifying telemetry improves privacy guarantees but makes debugging, billing, latency management, and trust in the platform operator's supply-chain and key-management behavior more explicit.

Public web traffic is also becoming AI infrastructure. Sites that serve dynamic pages, database-backed content, or large assets need admission controls for automated clients because search crawlers, training crawlers, user-triggered AI fetchers, and browser-like operator agents impose different costs and benefits. Practical defenses layer cooperative policy, user-agent and crawler verification, IP reputation, economic challenges, request signatures, fingerprints, and rate limits; no single signal is stable enough on its own when clients can spoof headers, rotate IPs, or route through residential proxies.

Full-stack app-generation runtimes add an inference-to-infrastructure boundary. When a user asks for a multiplayer app, persistent storage, ecommerce, or API-connected product, the builder can infer backend services, packages, server wiring, payments, and third-party integrations, but the generated runtime behavior still needs validation under realistic concurrency and state.

Code-mode infrastructure should also treat capability grants as part of the runtime contract. Generated programs should start with no authority, receive only the APIs or network paths required for the task, and leave enough execution trace to explain high-impact actions later. AI-generated code is still untrusted code: it can crash through hallucinated loops, expose secrets through over-helpful environment inspection, or exfiltrate data after prompt injection. Infrastructure should default-deny network access, proxy authenticated calls through trusted application code, isolate tenants by sandbox, cap CPU and memory, clean up idle sandboxes, and log what ran.

Code-executing agent infrastructure has a related but more interactive shape: the agent may inspect a repository, run tests, install dependencies, read external docs, and produce a PR. The safer default is a dedicated container, VM, or OS sandbox with scoped filesystem access and no broad ambient network. When internet access is needed, the runtime should expose configurable allowlists, method restrictions, and package-safety checks rather than giving the agent arbitrary outbound reach. Agent-native runtimes add product requirements on top of isolation: fast startup, API-controlled lifecycle operations, preloaded headless tools, declarative environment builds, reusable data volumes, and branch or fork primitives let agents use sandboxes as their own computers rather than as human-operated containers.

Agent code sandboxes need the same suspicion even when the interface looks narrow. A tool that can write a Python file and read files can still discover app internals, overwrite enforcement code, query metadata services, recover service tokens, and move laterally into data platforms. Sandboxes should therefore be hardened infrastructure products or deeply reviewed isolation layers, not ad hoc helper containers built beside the agent.

Sandbox technology should match the workload. V8-style isolates are useful for short-lived tool calls, plugins, skills, data transformations, and code interpreters when filesystem, process, and arbitrary-binary access are intentionally absent. Containers are heavier, but they are the right shape when generated work must clone repositories, install packages, run builds, start dev servers, expose preview URLs, or otherwise need real operating-system features.

Emerging MCP protocol work adds production-infrastructure concerns beyond ordinary tool schemas. Stateless transport can make MCP servers easier to deploy like ordinary stateless services, server discovery through well-known URLs can make agent-facing services easier to find, and asynchronous tasks plus extension mechanisms can support richer long-running or UI-backed agent interactions.

Production MCP deployment has a sharp security cliff between local stdio and remote streamable HTTP. Local stdio works as a single-user development surface, but shared remote servers need OAuth, token lifecycle management, TLS, CORS, rate limits, governance, and horizontal-scaling discipline. API-key passthrough is a weak bridge because keys are often long-lived, unscoped, rarely rotated, shared, and vulnerable to confused-deputy patterns. OAuth 2.1 with PKCE, token exchange, and CIMD moves remote MCP toward short-lived scoped access and stronger client identity, but enterprise readiness still requires tool/resource-level RBAC, data masking, interaction logging, and end-to-end traces. It also needs standard enterprise SaaS plumbing around SSO, lifecycle management, provisioning, audit logs, abuse prevention, input validation, and DLP. Public MCP servers also need local hardening when used in products: curation, description wrapping, pre-invocation validation, and deterministic setup execution make the integration a controlled infrastructure layer instead of a pass-through server registration. Dynamic client registration and background-agent authorization make this more than an ordinary hosting problem because app-management systems and service accounts must represent which client or workload has which authority.

OAuth infrastructure for agents should keep MCP servers in the resource-server role. When an MCP server only verifies incoming tokens, identity providers and authorization servers can own login, consent, token issuance, refresh, central policy, and client identity. That separation becomes more important as agents start acting on their own behalf, asking for transaction-specific authority, attesting the runtime or LLM that will see data, and passing authority through MCP-to-API or agent-to-agent chains.

The network can itself become the identity and policy plane for agent infrastructure. Tailscale's Aperture treats a WireGuard identity network as the substrate: every connection (container, GPU server, CI runner, laptop) carries verified identity — user, SCIM-synced group, or tag — so access control moves off the host and onto the connection, and a GitHub Actions runner authorizes via federated OIDC by joining the tailnet and receiving a tag on spin-up rather than shipping a secret. An LLM gateway deployed as a node on that network holds the only real provider key and hands the sandboxed agent a placeholder, which makes the gateway a single chokepoint for both policy and observability: cross-provider budgets and quotas ("here's just a thousand dollars, decide how to use it"), webhooks guaranteed to fire on each tool call, and complete tool-call/bash/MCP visibility without in-container instrumentation, because every model call must traverse it. The reusable infra primitive is open-sourced as tsnet (a Go library), so teams can build internal identity-aware MCP servers or API endpoints on the same identity rather than exposing a service to everyone — a network-layer counterpart to the gateway and cross-app-trust patterns already in this topic, and a complement to the capability-grant model where the sandbox starts with no authority.

Guardrails are an infrastructure layer, not just a prompt. Production systems need low-latency classifiers or policy checks at input, output, retrieval, MCP, memory, and plan boundaries, and the serving path must account for added latency. ModernBERT-style encoder discriminators are one concrete option when a self-hosted safety layer needs millisecond-scale classification rather than seconds of LLM-as-judge delay.

Regulated public-sector infrastructure adds deployment and governance constraints that ordinary SaaS launches can avoid. If a tool must operate on controlled, classified, mission, operational, finance, or PII-bearing data, the infrastructure conversation expands to NIST SP 800-53, FedRAMP, DoD cloud requirements, CNSSI 1253, continuous monitoring, restricted regions, self-hosting, SBOMs, dependency patching, and feature freshness in federal environments. Scientific-agent infrastructure also needs domain execution paths: an agent that proposes a physics design should be able to run code and simulations on appropriate HPC assets rather than stopping at a plausible explanation.

Lab co-scientist infrastructure adds a realtime, lower-cost version of that domain-execution path. A browser app can gather WebUSB sensor readings, webcams, voice, text, protocols, and chat history, assemble the active context for a model API call, and connect the loop to open-source lab hardware such as mobile object-tracking cameras, motion platforms, and bioreactors. The infrastructure problem is not just model access; it is synchronized empirical context, hardware availability, safety constraints, and a path from recorded traces into simulation.

Voice infrastructure has an upstream data-quality layer before any model call. Contact-center pipelines should preserve raw channel fidelity, apply denoising and level normalization, run early PII masking, tune STT with domain vocabulary and inverse text normalization, and map structured LLM outputs through an API gateway into CRM schemas. Each added privacy or verification layer can increase latency, so architecture decisions must balance low-latency extraction with compliance and durable-record accuracy. Realtime voice agents add another deployment layer: long-running sessions, cold starts, non-HTTP autoscaling, global media endpoints, data residency, and inference-server placement all affect conversational latency. Together AI's voice talk sharpens the placement point into a separable budget: total latency is engine latency (model compute) plus network latency (data-center hops between orchestrator and models), and once the engine side is optimized the dominant remaining win is co-locating every model and the orchestrator — dropping a ~75 ms cross-region hop to ~5 ms is a ~30% cut even in an already-optimized pipeline, which is the latency rationale for self-hosting an open model near the agent rather than calling a distant managed API (a London agent calling US-hosted OpenAI pays a trans-Atlantic round trip). Autoscaling for these sessions is asymmetric: scale up aggressively because backed-up requests are the worst outcome, but scale down by draining stateful long-lived connections rather than killing pods mid-conversation. Background audio should also be filtered before inference because speech-like noise can trigger interruptions and pseudo-transcripts even when STT is robust.

Computer vision adds a similar latency-and-locality constraint for real-world perception. If a system must perceive motion or act on camera input, it often needs multiple frames per second and edge execution rather than a single centralized inference hub. That makes the model choice, visual backbone, accelerator path, and benchmark target part of infrastructure, not just research accuracy.

Self-service AI platforms are also cultural infrastructure. They let product and engineering teams prototype and ship AI-powered features without making every experiment depend on deep central AI-team involvement, while enablement rituals help non-specialists understand what is safe, useful, and worth building.

Enterprise AI registries are another infrastructure layer between experimentation and production. A model gateway can centralize model access, authentication, budget erosion, and request analytics, while registries track MCP servers, A2A agents, models, ownership, environments, costs, and use-case lineage. The practical deployment pattern is to give teams template repositories and CI/CD flows that publish both runtime artifacts and registry metadata, so governance stays aligned with what is actually deployed.

Enterprise analytics infrastructure needs a governed data and metadata layer before an agent writes or executes arbitrary queries. A GenBI stack can separate metadata understanding, certified-report retrieval, SQL expansion, business-answer synthesis, orchestration, trust controls, and contextual UI. That lets teams package the report finder, metadata enrichment, and data-pivoting pieces independently while retaining the benchmarks and catalog improvements even if the end-to-end agent changes.

Multi-agent orchestration is also infrastructure once workflows leave the demo stage. A production system needs a workflow engine, state store, contract registry, serving layer, observability layer, and recovery controls around agent calls. Immutable append-only state versions make handoffs replayable; schema contracts catch malformed or low-confidence outputs at boundaries; circuit breakers, timeouts, rate limits, and compensation methods keep one failing agent or API from cascading through the full workflow.

Business-agent platforms add ordinary enterprise infrastructure requirements to the agent loop. SSO, RBAC, secrets handling, secure connectors, audit logs, SOC 2-style compliance, observability, token and runtime accounting, and regulated deployment modes can dominate the work even when the agent logic is a short reason-act loop. Build-versus-buy decisions should price token cost, infrastructure cost, and engineering cost together.

Durable execution infrastructure can wrap even a single agentic loop. Treat LLM calls, tool invocations, and external APIs as workflow activities with configured retry and timeout behavior, and persist successful results so crash recovery does not repeat token spend or side effects. For human-in-the-loop agents, the infrastructure should support logical waits that can leave active memory and later rehydrate state when approval or clarification arrives.

PydanticAI's Temporal path adds a Python-specific implementation: wrap agents in Temporal-backed agents, keep IO in activities, and use Logfire to inspect workflow IDs, model calls, nested tool activities, parallel branches, costs, and cached replay behavior. The key infrastructure boundary is not only "can the process restart"; it is whether completed LLM calls and tool calls can replay instantly while unfinished activities rerun normally.

Durable agent infrastructure also needs a deterministic orchestration boundary. Workflow code should be rerunnable and side-effect-free, while steps perform LLM calls, tool calls, sandbox commands, and external API work; observability then attaches to the step/event log, and lifecycle controls manage cancellation, scheduling, and deployment-version changes for in-flight runs.

Self-healing infrastructure adds an operations-to-code workflow on top of that durable boundary. Railway Autofix uses scheduled workflows to fetch application architecture, resource metrics, HTTP metrics, service logs, build logs, and deployment logs, then passes an analyzed repair plan to a headless coding agent that opens a pull request. The infrastructure lesson is that agent repair needs machine-readable observability and code-execution tools, but the merge boundary can stay human-reviewed.

Developer-platform infrastructure also needs to be consumable by agents. Self-service provisioning, API/CLI/MCP access, standardized development environments, local validation, machine-readable observability, and layered contribution guardrails let agents work against internal platforms without relying on informal human escalation paths. Agent-ready infrastructure should prefer fast local checks over slow CI-only loops because agents will repeatedly run whatever feedback path is available.

Enterprise AI engineering platforms should also reduce duplicate tool building. A model gateway can provide experimentation, visibility, and model-fit guidance; an MCP discovery hub can reveal existing servers before another team builds one; and a standardized deployment/runtime platform can handle authentication, SDLC, and production quality controls while leaving room for easy proofs of concept.

Knowledge-app factories add the same platform pattern for enterprise document workflows. A sandbox can let domain experts configure extraction templates, validation rules, model strategies, and transformations, while a cloud-native factory packages the resulting definition into an application with distribution, access control, cluster choice, downstream integration, and cost controls. The infrastructure value is not only faster app creation; it also keeps regulated deployment and human-review requirements attached to what leaves the sandbox.

Graph-backed retrieval becomes infrastructure when relationship traversal is on the production path. Large knowledge graphs need graph construction pipelines, traversal-depth controls, latency budgets, acceleration paths such as cuGraph or NetworkX-backed graph algorithms, and evaluation that checks both retrieval quality and generated answers. In operational environments, graph infrastructure also includes ETL from live systems into a canonical schema, layered graph access for different test types, and executable tools around the graph so agents can validate proposed changes against a digital twin.

AI-generated kernels turn low-level optimization into an infrastructure workflow. A useful system needs a supervisor that accepts source code, target hardware, and human guidance; synthesis agents that search optimization ideas; and a verification agent that executes candidates on actual hardware with strict correctness and timing checks. This infrastructure is most valuable when heterogeneous agentic inference workloads need to move across CUDA, Triton, Metal, Pallas, or new device generations faster than scarce kernel experts can hand-port every path.

Morph's Infinibranch talk adds branchable cloud state as infrastructure for agent reasoning. If full VM or container workspaces can be snapshotted, branched, replicated, rehydrated, and moved with low overhead, agents can treat stateful computer-use actions as reversible branches, run many parallel attempts from the same starting state, and promote only verifier-passing results.

Compiler pipelines can also be infrastructure for model portability, not only for optimization. Muna's Python-to-native path treats model-serving code as an artifact that can be traced, typed, lowered, compiled, and loaded through FFI, then exposed through an OpenAI-compatible client. LLMs fit this pipeline best when they generate bounded operation lowerings that the compiler can compose and verify, not when they replace representation, typing, compilation, and runtime packaging.

SGLang's deployment pattern reinforces that model serving infrastructure is partly a packaging problem and partly a runtime-configuration problem. A server command can be bundled with dependencies into a deployment artifact, exposed through an OpenAI-compatible endpoint, and benchmarked from a separate client, but production quality depends on hardware-aware settings such as CUDA graph max batch size and speculative decoding parameters rather than only on whether the server starts.

RL training infrastructure has a similar systems-modeling requirement. Synchronous RL wastes accelerator capacity when long-tail samples keep the whole step waiting, while asynchronous pipeline RL keeps sampling and training workers busy through queues and in-flight weight updates. The infrastructure problem is to allocate GPUs between sampling and training so production and consumption rates match, KV-cache memory is respected, and policy staleness stays within the algorithm's tolerance.

Serverless compute reshapes that training infrastructure from the elasticity side. Modal's "what lies beneath the API" framing argues that serverless GPU — usually associated with inference — is also a strong fit for the bursty, parallel shape of training, and offers a middle ground between a frontier API (no algorithm control) and full in-house training (a big cluster isolated from production, infra engineers, "massive responsibility for the entire stack"). Two training shapes benefit: hyperparameter search becomes fan-out where "every minute on your cluster isn't sacred" — spin up many on-demand containers and kill the unpromising ones, almost a meta-evolutionary search — and RL rollouts, which are "massively embarrassingly parallel," scaling to 50,000–100,000 sandboxes just for rollout (enabled by a unified API over sandboxes and GPU containers/clusters). This is the elasticity counterpart to the async-RL allocation view above (where the problem is balancing fixed sampling and training pools) and to the GPU-marketplace and pods-vs-serverless views (supply contracts and dev-vs-prod modes): here the unit is the on-demand sandbox you summon and discard. With open-source libraries reducing supervised fine-tuning and RL to ~300 lines of Python, the remaining work is data and evals rather than owning a cluster, and serving the trained model (vLLM, SGLang, Triton, or custom Python, auto-scaled to traffic) is the inference counterpart.

Robotics contributes a broader infrastructure lesson for agents: the offline stack can be the development accelerator. Production agents need monitoring, logs, simulation, counterfactual replay, retraining paths, and human-feedback loops around the online model. Stateful VMs and persistent files make this harder because the infrastructure must capture the world state that shaped the agent's action, not only the prompt and final answer.

Realtime robotics adds a lower-level version of the same infrastructure problem. A 2 ms control loop can be dominated by CAN-bus transmission time, and pipelining RX, policy execution, and TX can recover throughput only if synchronization, logging, and process priorities are designed as part of the control path. Observability itself needs isolation or budget: a log flush, UART write, or dropped-packet log can become the failure mechanism it is trying to explain.

Robotics data infrastructure can be as important as robot inference infrastructure. Physical Intelligence's VLA pipeline treats data collection as an operated system: teleoperation runtimes, leader-arm capture, scheduled collection sessions, metrics, cloud annotation, filtering, and training ingestion form the loop that turns scarce successful episodes into model capability.

Agent optimization infrastructure can include a meta-controller that routes budget across context, compute, verification, memory, and temporary parameter adaptation. That controller needs telemetry for task outcomes, per-strategy contribution, compute, latency, memory, and confidence calibration, plus efficient profiling so the optimizer does not spend more on deciding than it saves through adaptive execution.

Coding-agent harnesses are another infrastructure layer when teams want products to survive rapid model and API churn. The harness absorbs model-facing details such as tool loops, compaction, sandboxing, permissions, MCP support, parallel tool calls, port forwarding, and image handling. A stable SDK boundary can let product teams integrate the harness into IDEs, CI/CD, GitHub Actions, or product agents while leaving model/harness maintenance to a shared provider.

High-assurance agent infrastructure includes reusable verified components and proof-capable toolchains, not only model hosting. When generated code touches critical behavior, infrastructure can route agents toward trusted libraries, typed languages, static verification, model checking, theorem provers, and proof-carrying languages such as Dafny or SPARK, while keeping the specification-to-code boundary explicit.

Web and mobile coding agents add a remote-compute version of that harness problem. When the user starts work away from a local terminal and returns later, the platform needs secure sandboxed execution, container orchestration, and session persistence so generated code can run without depending on the user's machine.

Architecture-copilot infrastructure needs a live system model before recommendations are credible. The described pattern ingests cloud, Kubernetes, service, logging, dependency, and drift signals into a normalized digital twin, then uses that model to support explainable recommendations and workflow-embedded governance.

Brockman's AI infrastructure framing adds a fleet-shape constraint at frontier scale. AGI-scale work is not only model software; it can require massive physical infrastructure, and the workloads split between long compute-heavy jobs and low-latency realtime interactions. A fleet can use different accelerator shapes for each mode, but the ratio matters: if planning overestimates one mode, expensive capacity can become idle or mismatched.

Realtime voice infrastructure adds a smaller but concrete version of that constraint. Development and production depend on live network transport, low-latency provider calls, VAD or semantic turn detection, synchronized audio/text events, and release evals that exercise real services end to end. WebRTC is the preferred transport layer for realtime audio/video streams because it can prioritize fresh media under packet loss and jitter, adapt bandwidth, and expose stats without forcing each app to rebuild media networking on top of TCP.

Open-source realtime TTS adds another concrete serving layer to voice infrastructure. If each voice clone is a LoRA adapter over a shared model, the fleet needs batch inference, adapter-aware routing, quantization that preserves realtime audio-token throughput, and sticky session placement so long-running streams stay near the GPU memory state they need.

Remote MCP infrastructure can reuse ordinary cloud primitives when the local stdio assumption no longer fits. A simple MCP server can be wrapped behind Lambda and API Gateway with streamable HTTP, an authorizer or Cognito, and DynamoDB-backed session state; the client can then list remote tools and pass them into an agent. This does not remove the need for gateway, authorization, and context-budget design, but it gives teams a serverless path from local MCP demos to shared cloud endpoints.

Remote MCP gateway infrastructure can also standardize internal agent integration before teams agree on one network transport. Anthropic's pattern returns a normal MCP SDK client session from a simple client-library call, while the gateway handles URL-based routing, credentials, OAuth flow helpers, rate limiting, observability, and policy hooks. The message protocol remains stable even if internal traffic runs over websockets, gRPC, Unix sockets, or another stream carrier.

LLM evaluation infrastructure also needs a CI/CD shape. Manual workshop runs are useful for learning tools, but production teams should turn serving benchmarks, factual checks, formatting checks, safety and bias tests, and custom product evals into repeatable gates that run when prompts, models, data sets, or production use cases change.

Dagger-style agent delivery infrastructure packages that feedback path as portable workflow code. Containers, source directories, repositories, LLM calls, build functions, and test functions can share one runtime and cache, so the agent gets the same tool surface locally and in GitHub Actions. That reduces environment drift and makes the CI path a continuation of the local agent workflow rather than a separate automation.

The data foundation is often the largest hidden infrastructure layer for production agents. Because agents return wrong answers confidently when fed bad data (unlike forgiving humans who correct a wrong report), data quality can consume roughly 60% of an enterprise project. It splits into question data (what the agent answers from) and tracking data (the traces), and the tracking data needs its own schema and a centralized collection layer because enterprises run multiple frameworks (CrewAI, LangChain) and clouds. A lakehouse pattern (cloud storage, a Delta Lake table layer, then a catalog such as Unity Catalog) centralizes permissions and, crucially, metadata: table and column descriptions plus PII tags give agents the context they need to query data correctly, while one trace store can serve dashboards, health monitoring, text-to-SQL, and automated judges. Observability is the paired layer: tracing every agent decision is not only a debugging aid but a regulatory precondition in Europe, and a stale embedding (a policy document never re-embedded after a change) is the kind of failure only tracing can localize. Arize's account of that layer is OTel-first: everything is OpenTelemetry, so a one-line auto-instrumenter on a framework or SDK emits the traces and spans that audit what an agent did — telemetry, not code, does the auditing — and that single trace store feeds dashboards, evals, and experiments. The deployment shape can stay light: Arize Phoenix runs as a single open-source container deployable locally with no Kubernetes layer, while the enterprise tier (Arize AX) adds the AI/agent layer over the same telemetry.

Serverless GPU clouds add a developer-loop layer to that infrastructure. The slow path for GPU iteration is commit → push → Docker-build → registry-pull → server-load → GPU-allocate before any test, and RunPod's Flash SDK collapses it to a `@flash.endpoint` decorator on an async Python function: only the decorated function runs on the GPU cloud while the surrounding orchestration runs locally, and hot file reload pushes any edit immediately so a model swap is a one-line change rather than a container rebuild (`flash run` exposes a local FastAPI dev server to POST against). The same platform's commitment shape is a workload-phase decision: reserved/persistent pods (or a low worker count) fit experimentation when you only need one or two GPUs, while autoscaling serverless workers fit variable production load that needs hundreds of GPUs across data centers — serverless costs a premium for the scaling but bills only per second of running request time and scales to zero when idle. This complements the GPU-marketplace and worker-autoscaling views: the marketplace argument is about supply allocation and reservation contracts, while the Flash view is about deployment ergonomics and the dev-vs-prod product mode. The same platform's "under five minutes to a deployed endpoint" demo exposes the operational counterpart of scale-to-zero — a cold-start tax: deploying an open model from a hub listing (a GitHub repo whose preconfigured Dockerfile options pass through as `vllm serve` flags) gives a provisioned HTTP endpoint quickly, but the first request to a fresh or idle serverless endpoint still spends ~41s creating a container, downloading the model, and initializing before steady-state ~1.5s execution, so warm always-on workers are the only way to remove that first-request latency, at the cost of paying for idle capacity.

Long-context training adds a memory-engineering layer to that GPU infrastructure. Together AI's "road to 5M tokens" work shows that fitting a multi-million-token training run onto a fixed node is an incremental stacking problem, not a single setting: a standard LLaMA 3B at a 3M-token context out-of-memories on an 8×H100 node before any activations exist, and the fix is to layer FSDP (shard parameters), DeepSpeed Ulysses context parallelism (distribute attention heads, keep Flash Attention), activation checkpointing (recompute in the backward pass), CPU offloading of transformer-block inputs (prefetch on backprop, first done by Unsloth), and Arctic-style chunked sequence training (tile loss and MLP computation so no buffer is millions of tokens wide). Reaching 5M needs a deeper context-parallelism optimization, "Untied Ulysses," which chunks attention heads and reuses one smaller activation buffer across iterations because a single head-group already saturates GPU compute, matching the most memory-optimized training baselines at 8B and 32B with negligible throughput cost. The operating lesson mirrors the RL-fleet and KV-cache views in this topic — profile where memory goes (the PyTorch profiler) before optimizing, because the binding constraint appears where you least expect — and the chunk-size knob trades activation memory against throughput much like the RL sampling/training allocation trades staleness against utilization.

Running an agent fleet across machines is an infrastructure problem that converges on cluster scheduling. Kyle Jaejun Lee (KRAFTON) reports scaling a personal coding-agent fleet from one machine to three (a sleeping MacBook plus two always-on headless Linux boxes) and watching single-machine assumptions break: orchestrators do the work themselves instead of dispatching (fixed by a CLI harness where dispatch is the only path), worker panes crowd out `tmux capture-pane`, stacked Claude/MCP processes exhaust memory and swap, credentials collide across workspaces (fixed with a fully separated environment per workspace), and a laptop dying mid-job loses all in-flight work. His durable coordination moves are deliberately boring distributed-systems hygiene: move context between machines over git (commit/push, then `tmux send-keys` over SSH to trigger a pull) with per-machine directories for machine-specific state and shared state changed only through a pull request; collapse per-machine approval gateways into one main gateway on an always-on box because "your one point of control can't be a thing that falls asleep"; and keep all entity state in files so one `overlord boot` command rebuilds the fleet after a crash. The punchline is an infrastructure claim: the four remaining unsolved problems (consistency, abstracting local-only tools, secure credential handoff, resource management) all reduce to "an agent should declare what it needs, not where it runs" — orchestration/review/hierarchy on top, compute/secrets/tools underneath, a scheduler placing work — which is "the exact questions Kubernetes already answers," so the build stance is to stack a cluster scheduler underneath and build only the agent-specific orchestration layer on top.

Coding-agent evaluation at scale is its own infrastructure layer, not a measurement script. Nebius's SWE-rebench treats every benchmark task as a 1-10 GB Docker image with dependencies installed so the project's tests run, then evaluates ~30 models monthly — so the binding work is execution reliability. The durable infra lessons: prefer a minimalistic agent on strong infrastructure over an over-engineered agent on weak infrastructure; define a retry policy that separates model errors (too-long context, too many tool calls) from infrastructural/provider errors and decide which exit statuses are rerun; minimize infrastructural noise (tests that reach external resources, or a default 1970 container clock, silently invalidate runs); validate the harness against an external benchmark (SWE-bench, Terminal Bench) so your numbers match the reported ones before experimenting; and budget for caching (~4x cost efficiency for the simple agent, though token-hungry harnesses stay expensive even with caching and Haiku sub-agents). The same filtering pipeline (GitHub Archive/API → interactive-agent Docker build → LLM filtering → manual verification) that powers the leaderboard also produces RL-training environments, and Nebius ships a Harbor adapter so one terminal-base format runs either evaluation or training.

The distribution stack itself may be the next infrastructure layer to change shape. Iris ten Teije (Differ) argues that CI, packagers, registries, container images, and app-store review exist to solve exactly one problem — move a *frozen artifact* to every machine "safely, reproducibly, once" — and that [the frozen-artifact pipeline was a cost constraint, not a law](../concepts/frozen-artifact-pipeline-is-a-cost-constraint-not-a-law.md): "one version for everyone" was the direct consequence of a correct change taking skilled humans hours or days, so you froze it and shipped it once. As change-production cost collapses toward zero and can happen at runtime on the server, client, or in the user's live session, "when the agent is the runtime… development and distribution stop being two phases," and the guarantees that used to flow from a single immutable artifact (reproducibility, previewability, rollback, provenance) have to be rebuilt as infrastructure. Differ's answer is to [deploy a canonical stem plus bounded per-user divergences](../concepts/deploy-a-canonical-stem-plus-bounded-per-user-divergences.md): one shared stem plus per-user divergences that are immutable, isolated, and individually reversible, so the blast radius of a change is one user context and any divergence "can roll back live with no deploy." This reframes several infrastructure primitives — the source of truth becomes "the stem plus all the immutable divergences" and identifying "what is this user running and why?" becomes a graph query rather than a version number; correctness testing must reason about the stem and every divergence; and coordination is "don't merge code, merge intent, merge outcome." It is a per-user, runtime-generation counterpart to the branchable-workspace and reversible-snapshot patterns already in this topic (there the reversible unit is an agent's exploration; here it is a shipped user's live software), and it sharpens the standing lesson that with AI, generation is the easy 80% while observability, validation, provenance, and coordination "are the entire business."

Autonomous agents also force a new foundation layer onto the infrastructure stack. Nishant Gupta (Meta Superintelligence Labs) frames the shift from chatbots to agents as a move where "the challenge is no longer intelligence — the challenge is reliability": agents are stateful, long-running, decide dynamically, and may run different workflows for the same input, so they violate nearly every assumption of infrastructure built for short-lived deterministic microservices ("the great mismatch"). His central architecture move is to [build an agentic control plane so the model proposes and the platform decides](../concepts/build-an-agentic-control-plane.md) — never let a probabilistic model directly control production, but instead have it emit proposals that infrastructure validates, a policy engine approves, and an execution gateway enforces, so the system stays reliable even when the model stays stochastic. The control plane is the emerging analog to Kubernetes (for containers) and service meshes (for microservices), owning scheduling, memory coordination, policy enforcement, evaluation, monitoring, and workload routing — "an operating system for autonomous AI." The failure modes it exists to contain are infrastructural rather than hallucinations: [retry amplification](../concepts/contain-retry-amplification-in-agent-loops.md) (an agent regenerating slightly different but still-invalid requests until a minor API error becomes an exponential compute incident — "one of the biggest risks in agentic systems"), recursive reasoning loops, workflow deadlocks, context corruption, memory poisoning, and cost explosions, where "the model makes a mistake, but the infrastructure turns that mistake into an outage." His durable engineering claim is that most of these are not new — [treat agents as distributed systems](../concepts/treat-multi-agent-systems-as-distributed-systems.md) and reuse the primitives (circuit breakers → tool isolation, rate limits → agent limits, retries → controlled recovery, resource quotas → cost governance, observability → agent tracing), while remembering that "many multi-agent failures are actually consistency failures masquerading as reasoning failures." Layered defense-in-depth safety, permanent human exception handlers, causal (multi-dimensional) observability of planning decisions and tool calls, and elastic GPU scheduling (inference "becomes a resource orchestration problem") round out the layer — and the closing bet reframes competitive advantage: as prompts and models commoditize, "the future of AI won't be won by better prompts — it will be won by better systems."

Dominik Tornow (Resonate) applies the same "better systems" bet to how infrastructure itself gets built and distributed. His thesis is that coding agents will retire general-purpose platforms by making them unnecessary: a durable-execution vendor's product stops being the implementation and becomes an abstract, target-agnostic *specification*, from which agents [synthesize many bespoke implementations](../concepts/treat-the-specification-as-the-product-and-derive-bespoke-implementations.md) as minimal extensions of infrastructure already in place (a reference server, a Postgres server, a NATS.io server built with a partner). This is a distribution-model shift adjacent to Differ's frozen-artifact argument — reuse moves upstream to the protocol, and the goal is to *repeatedly synthesize trusted* servers from one spec rather than hand-maintain a port per backend. Two infrastructure enablers make it work: minimalism (three years shrinking the protocol to two objects — a durable promise and a durable task, the primitives behind [durable execution for production agent loops](../concepts/use-durable-execution-for-production-agent-loops.md)), and expressing that protocol using only the *target platform's* primitives (NATS queues, a versioned KV store, delayed messages) while remaining correct under the target's real consistency model (legal stale reads, optimistic-concurrency write failures), not just convenient behavior.

Vaidas Razgaitis (Higharc) adds the codebase-shape layer for a multidisciplinary AI/ML shop moving frontier research into production. His answer is to [structure the ML codebase as decoupled per-researcher microservices](../concepts/structure-the-ml-codebase-as-decoupled-per-researcher-microservices.md): a Python mono repo kept separate from the core product repo, made of cleanly isolated, fully decoupled microservices at roughly one microservice per researcher (a custom transformer, a diffusion pipeline), each a standalone layered FastAPI app (services → controllers → API routers) fronted by a gateway on one Docker bridge network, with each service root carrying its own Dockerfile, dependencies, and poetry/UV lock files, and a shared substrate underneath (GitHub Actions CI, Modal for GPU compute, a tooling CLI, and agent-navigable specs). The design goal is not raw scale but *receiving prototypes fast*: a consistent skeletal backbone plus a decomposition step (slice the proven monolith along its dependency graph, land it as Graphite stacked diffs for asynchronous SME review) so research lands on software-engineering best practices without fighting old abstractions. It is the repo-and-serving counterpart to this topic's other "structure for reliability" moves, upstream of the handoff artifact it pairs with — [a taxonomy handoff document](../concepts/bridge-ml-research-to-production-with-a-taxonomy-handoff-document.md) whose mapped types, persistence, and architecture inform where each prototype slots into the mono repo.

The substrate an agent runs on also decides how much observability is free rather than built. OpenGov's OG Assist team owns its agent loop on the Effect-TS functional-effects library, and Gabe De Mesa's "you can't scale what you can't see" framing is concrete: because Effect functions auto-tag with spans that feed traces, they get end-to-end latency profiling, bottleneck detection, and cross-service failure correlation "out of the box," which matters most in an agentic system integrating with many teams and APIs. It is the same reliability-through-primitives instinct as treating agents as distributed systems and reusing observability/tracing — but here the win comes from choosing a runtime where tracing, structured concurrency, and logging propagate uniformly once the loop is self-owned, rather than instrumenting each call by hand.

Where the workload touches regulated data, the data plane has its own version of the "choose the substrate that makes the property free" instinct — except the property being bought is the *absence* of a capability. Hinge Health's Rashi Agrawal argues that most healthcare AI safety failures "are architectural decisions that were made before even a single token was generated," and the PHI layer is the clearest case: [make the failure architecturally impossible](../concepts/make-regulated-data-failures-architecturally-impossible.md) by stripping PHI at the pipeline boundary at ingestion, "before it ever reaches the data lake," rather than redacting it when a log reaches a dashboard. The downstream redaction requirement then has nothing to act on — "a developer opens a dashboard, there's nothing to redact. The PHI was never there." Two supporting decisions have the same shape: production and non-production with "no pipes in between, because even a single pipe is all that it takes for member data to leak into a dev environment," and access scoped by role *and* geographic region, since PHI clearance is "a policy that is applied to specific regions only" and distributed teams are the norm. Compliance is treated as a design input rather than an overlay — "you cannot slap on HIPAA on top of an underlying system or an architecture. You start with it and let the architecture grow around it" — and she is explicit that the cost is real ("building guardrails first is slower than bolting them on later"), which is what makes the pattern a scoping decision rather than a universal default: a field stripped at ingestion is also gone from every future debugging session and every future model input.

Anterior takes the opposite branch of that scoping decision — its agents must reason over the regulated record, so the data cannot be deleted at ingestion — and arrives at a data plane built from two separated stores. Saul Howard's selection rule is the same one running through this topic, stated as a design method: "taking your constraints very seriously and thinking about what you want to be simple within the system and then choosing the trade-offs for that." What they want simple is the compliance answer, so the source of truth becomes an append-only, timestamped event log, and [auditability falls out of the storage model](../concepts/an-audit-trail-is-a-chain-of-evidence-not-a-developer-log.md) instead of being reconstructed — with the event-sourcing bill stated rather than hidden ("writes become very easy… reads become more difficult because you have to read through all of the events"). The second store is the one that makes the first usable: [schema-driven object storage sits beside the log, not inside it](../concepts/store-agent-data-in-object-storage-beside-the-event-log.md), with events holding only references to immutable blobs. The shape of the data drives that choice (non-hierarchical, mixed structured and unstructured, individual records "over a megabyte in size or … much more," under role-based access control, sometimes forbidden from leaving the customer's VPC), and the separation buys three things a single store cannot: engineers retrace an agent "without having access to the personal health information itself" while still seeing its schema-described shape, every read passes one point where zero-trust tokens are checked at the point of use, and the exfiltration leg of the lethal trifecta becomes an architectural question — "is it possible within my architecture for the agent to be also accessing data over here?" — rather than a prompt-hardening one. The generalizing claim is that little of this is new engineering: "there are patterns that have worked very well within finance, within defense, within big tech," with the finance transaction log as the borrowed primitive, recombined for agents.

Generative media reaches the same "this is a different workload, not a faster one" conclusion once it goes real-time, and Reactor's Ahmed Ahres states the divergence as three simultaneous breaks with the batch playbook: [serve real-time video as stateful streaming sessions, not batch jobs](../concepts/serve-realtime-video-as-stateful-streaming-sessions.md). The unit of work stops being a request that "gives you back a file" and becomes a pixel stream to the client; every session is long-lived and carries model state that has to be maintained, since the visible failure of current world models is that "the character can look back and then will not remember what's going on"; and the latency bar dictates topology rather than tuning — "sub-100 millisecond latency anywhere you are" means a user in India or Japan is routed to a nearby GPU, and without worldwide compute "the experiences are not real time anymore and it breaks completely the medium." That last point is worth separating from ordinary p95 goals this topic tracks elsewhere: missing the budget does not degrade a score, it removes the product's reason to exist. The stateful-session pattern is the same one the voice-agent deployment page derives from conversational latency, arrived at from generated video instead of audio, and the remaining model-side dial is familiar — asked how to move 16 FPS to 30, Ahres answers with multi-GPU serving, weight optimization, and quantization rather than a new model. A second inference provider in the same category reaches the identical conclusion without sharing the argument: Keegan McCallum (uRun) closes on "the models are here and the frontier is really in how we serve them," and his checklist fills in what Ahres leaves abstract — GPUs positioned globally *and* a routing decision about "where you're connecting the users to," WebRTC with ICE and TURN named as the transport, several models "wired together in continuous streaming workflows" so the interesting workloads are pipelines rather than one model streaming, and control synchronization specified per frame rather than per session. Both vendors also converge on the same packaging, which is the part to copy regardless of platform choice: a thin client surface (a drop-in React component, or "maybe 10 lines of code") over a programmable server-side runtime that owns the pipeline graph — and, at uRun, a CLI and MCP server shipped alongside it, because "in 2026 we don't just need platforms, we need software factories and ways for agents to interact with these."

The web-data layer that feeds live retrieval is its own infrastructure tier, and Oxylabs' Patricija Žemaitytė supplies the wiki's most concrete account of operating it. Three lessons generalize past scraping. First, the dependency is adversarial, so the usual confidence ladder breaks: a sub-second search API that hit ~650 ms P90 in under two weeks got blocked live on the client demo call, which is her framing that "a system that works in development, a system that works in a test, and a system that actually survives reality" are three different systems — and because targets, layouts, and detection keep changing, that is a standing operational load rather than a one-time hardening cost ("not a build-once business… an adapt-forever business"). Second, throughput numbers need a stated unit of work: scaling a proxy-integrated unblocker from 10,000 to 60,000 requests per second in under two months sounds like HTTP volume, but one request is the end-to-end job (routing, rendering, proxy handling, browser execution, parsing, retries, normalization, delivery), which is why "even adding up additional 2,000 servers doesn't solve the problem" and why 400 million → ~6 billion daily requests is described as a change in operating model — cost, observability, failure domains — rather than growth. Third, the limiting constraint showed up in load testing rather than an outage, and it was epistemic: at ~20,000 rps the system worked, but nobody could tell whether it would go further, because synthetic traffic is easy and organic-looking traffic is not, and at that volume "the telemetry itself becomes a part of the load." Their resolution — scale gradually and accept that the real test is production traffic — is the honest version of the observability-at-scale problem this topic already treats from the training-cluster side.

Browser-agent runtimes are a third tier of that same web-facing infrastructure, and Paul Klein IV (Browserbase) names its distinctive requirement: not throughput but *reproducibility of rendering*. "When your agent is running across a website multiple times, you want it to see the same inputs and outputs, the same page layout, the same size. If your infrastructure renders a page in a mobile layout one time and then in a desktop layout the second time, it's going to have inconsistent results." That makes [holding the browser environment constant across runs](../concepts/hold-the-browser-environment-constant-across-runs.md) the base layer beneath the harness and the model rather than an optimization — a harness improvement measured on a substrate that varies underneath it is measuring noise. The anti-pattern he names is instructive because it works at n=1: when OpenClaw shipped, teams bought Mac minis to run at home and SSH into, where a residential IP makes CAPTCHAs easy, and the two walls that stop it are throughput ("thousands of agents for customers in production") and audit ("I've yet to see a SOC 2 compliant Mac mini setup at scale") — the second having no incremental path. The rest of his platform checklist folds into the wiki's [managed web-access page](../concepts/ground-agents-with-managed-web-access-infrastructure.md): serve one agent and thousands, stay model-agnostic so the agent can move as models change, broker identity with the anti-bot vendors, and capture screen recordings, logs, and network activity as feedback the agent consumes rather than as dashboards a human reads.

Underneath every one of these tiers is a fact about compute shape that Sara Hooker turns into a claim about market structure: [distributable compute lowers the barrier to frontier work](../concepts/distributable-compute-lowers-the-barrier-to-frontier-work.md). "Pre-training compute typically has to be co-located… large volume to accommodate for redundancy. Inference compute and other places where you actually apply compute, typically you can have much more… distributed. It's also much more higher return given the amount of flops." The asymmetry itself is uncontroversial and is visible all over this topic — a from-scratch run needs a contiguous InfiniBand fabric held through silent NCCL failures, while [inference tolerates degraded GPUs that training cannot](../concepts/inference-tolerates-degraded-gpus-that-training-cannot.md), [idle supply can be aggregated through marketplaces](../concepts/aggregate-idle-gpu-supply-through-compute-marketplaces.md), and [commitments should match workload lifecycle](../concepts/match-gpu-commitments-to-workload-lifecycle.md). What Hooker adds is the inference that if returns have moved off pre-training size, the buying pattern changes with them: agentic and post-training compute "does not require the same type of… hoarding of GPUs," which is "very different compute purchasing dynamics." She is candid that the level has not changed — RL and fine-tuning on large models remain GPU-intensive, and frontier models "are still pretty large" — only the trend. Read the argument as conditional on her [scaling claim](../concepts/pretraining-size-is-no-longer-the-most-lucrative-scaling-axis.md) and coming from a founder whose beta ships free GPUs; the planning-relevant residue is that a team that will post-train and serve but never pre-train can build on heterogeneous, preemptible, geographically split capacity, and should stop treating a reserved homogeneous cluster as the price of entry.

Sam Denton's talk names the infrastructure endpoint that this topic's training and serving tiers are converging on, and prices the rungs below it. The endpoint is "this sort of unified engine of putting inference and training together" — a model serving production traffic, producing a trace, learning from it, and serving the next request — which he calls "the holy grail of continual learning" and expects to raise capability ceilings on its own "as the infra collapses between serving and training." That is the zero-staleness limit of the same asynchronous loop this topic already documents under [pipeline RL](../concepts/pipeline-rl-trades-policy-staleness-for-gpu-throughput.md), from the same company eight months earlier. What makes the talk useful for planning is that it does not treat the endpoint as the entry price. [Place a continual-learning setup on two axes](../concepts/place-a-continual-learning-setup-on-the-trace-and-hint-axes.md) — trace policyness and hint provenance — and only the first is an infrastructure question. At the bottom, [offline hints on offline traces need no replayable environment](../concepts/offline-hints-on-offline-traces-need-no-replayable-environment.md) at all: a stored trace dump plus a static behavior prior. In the middle sits a rung this topic did not have, where you [buy on-policyness with a single rollout step](../concepts/buy-on-policyness-with-a-single-rollout-step.md) — replay the stored prefix, generate exactly one step "without actually having to interact with the environment," and write the teacher's hint against it. Staleness there is a supervision-quality problem rather than a throughput one, and the reported remedy costs one forward pass instead of an environment. The claim that this beats the fully offline setup is delivered against an unlabeled chart, so treat the rung as a cheap experiment rather than a settled result; the ladder itself — dump, one-step replay, replayable environment, live training on served traffic — is the durable planning artifact.

There is a smaller piece of infrastructure this topic has treated only as a tool-calling concern that Ben Hylak puts underneath production trace analysis: a sandbox that runs model-written code at corpus scale. His recommendation is to write classifiers with a model and "run them in a sandbox… at production scale" over every trace rather than sampling traces into a model's context ([Run Trace Classifiers as Code Mode in a Sandbox](../concepts/run-trace-classifiers-as-code-mode-in-a-sandbox.md)). Two infrastructure consequences follow. The cost curve inverts — the model call moves from once-per-trace to once-per-question, and the per-trace cost becomes compute rather than tokens, which is what makes full coverage affordable instead of statistical. And the containment requirement is the one this topic already documents for [agent-written API code](../concepts/run-agent-written-api-code-inside-programmable-sandboxes.md) and [sandboxed code execution](../concepts/sandboxed-code-execution-turns-model-reasoning-into-inspectable-computation.md), except that here the untrusted program has broad read access to production traffic, which is usually the most sensitive corpus a company holds. Nothing in the talk addresses that; no isolation model, redaction step, or access scoping is described, and no cost figure is given for either side of the comparison.

Ronak Malde's talk supplies the line item that makes the training tier expensive and names who is paying it. His [four-property scorecard](../concepts/score-post-training-algorithms-on-four-properties.md) for post-training algorithms has one row that is purely an infrastructure question — parallelism — and it is the row that decides whether you need environments at all. Group-based RL "requires huge amounts of infrastructure to make sure our environments are one-to-one copies of the real world," which is the same requirement this topic already documents as [RL environments being software artifacts with a lifecycle](../concepts/build-rl-environments-as-software-artifacts.md) and as the reason long agent trajectories force [decoupled rollout workers and buffers](../concepts/use-hybrid-rl-system-design-for-agent-trajectories.md). The useful move is to notice that this bill follows from one algorithmic choice rather than from RL in general: a method whose parallelism is one deletes the line rather than optimizing it. Read alongside the ladder above — dump, one-step replay, replayable environment, live training on served traffic — it means the environment tier is a decision you make when you pick the training method, not a fixed cost of doing post-training. The same talk's argument for where the data comes from is also an infrastructure argument: [train on inference exhaust instead of scaling benchmarks](../concepts/train-on-inference-exhaust-instead-of-scaling-benchmarks.md) rests on manufactured evals and environments costing engineer-days per task while production traffic accrues for free as a byproduct of serving, which turns trace capture and retention into the substrate spend.

The same talk's Q&A also puts the current state of the streaming endpoint in plainer terms than the vision slides do. [Today's continual learning is batch updates and a model re-upload](../concepts/todays-continual-learning-is-batch-updates-and-a-model-reupload.md) — "pseudo continual learning," in the speaker's own phrase — and the blocker he names is specifically an infrastructure one alongside an algorithmic one: what to do when "you have 10,000 rollouts going out in a product" and they must be merged into a single update. That merge is invisible in every single-trajectory walkthrough of these methods, including his own, and it is unbuilt. For planning, it means a continual-learning program inherits the release discipline of a model deployment — regression gates, rollback, and a policy for traffic between batches — rather than the operational shape of a memory system. Note the direction of the evidence: this is a vendor describing the limits of the field he sells into, offered unprompted, which makes it the more credible half of the talk. No cost figure, cadence, or fleet size appears anywhere in it, and no measured number appears in the talk at all.

Anthropic's Applied AI team describes the serving-side counterpart — what it takes to run someone else's agent — and the most reusable artifact is a checklist rather than an architecture. Six things production forces on you regardless of which surface you build on: hosting and scaling, session management, filesystem, execution isolation, credentials, and observability ([Decide the Agent Buy Boundary With Six Production Questions](../concepts/decide-the-agent-buy-boundary-with-six-production-questions.md)). Scoring a candidate platform on which of the six it answers, and which it answers in a way you would have to undo, is a sharper build-versus-buy test than comparing feature lists — and the two most often missing from a prototype are session durability and observability, because a demo runs to completion in one process. The object model that goes with it is agent, environment, session ([Model a Managed Agent as Agent, Environment, and Session](../concepts/model-a-managed-agent-as-agent-environment-session.md)), where the environment is a *definition* instantiated per session, so policy like an egress allowlist attaches once and every session instance inherits it.

The architecture lesson is one this topic can use directly, because Anthropic shipped the wrong version first. Agent loop and tool container ran as one unit until "the container was blocking the agent being able to start its model reasoning" and "if one part of this component went down, the entire box of the agent would go down." Splitting them ([Decouple the Agent Loop From the Tool Execution Environment](../concepts/decouple-the-agent-loop-from-the-tool-execution-environment.md)) took container start off the first-token path — a reported "60% faster time to first token for P50" and "over 90%" at P95, internal figures with no methodology — and made failure recovery directional: a dead sandbox is replaced and the run continues, a dead loop resumes from the session log. That second half depends on [keeping the session log separate from the context window](../concepts/keep-the-session-log-separate-from-the-context-window.md), which is the durability primitive underneath both recoveries. The split also creates the precondition for [decrypting credentials only at tool execution time](../concepts/decrypt-agent-credentials-only-at-tool-execution-time.md), and for placement choices that keep data where it belongs: self-hosted sandboxes in the customer VPC, and [outbound-only tunnels to private MCP servers](../concepts/reach-private-mcp-servers-with-outbound-only-tunnels.md) so no inbound path into the protected network is required. Every claim here is a vendor's account of its own platform, with the latency percentages the only numbers offered and no per-tool-call cost of the added network hop reported anywhere.

RL post-training gives this topic its sharpest current example of a capacity problem that turns out to be an architecture problem. Modal's framing is that the default loop demands four things at once — "enough GPU, same region, fast fabric, and available now" — and "any of these is manageable, but all four of them are pretty hard to get at the same time," against a supply that actually exists as a bazaar of different providers, regions, prices, and availability ([RL Post-Training Demands Four Scarce Compute Properties at Once](../concepts/rl-post-training-demands-four-scarce-compute-properties-at-once.md)). The asymmetry that makes this permanent rather than a one-time purchase is that "training capacity is not elastic in the way the inference capacity is": a synchronous job's size is fixed at the start of the run, so anything colocated with it inherits its procurement constraint for the duration. The remedy is to cut the loop, and the seam Jiang names is not "training versus inference" but the presence of a collective — back-propagation stays on fast fabric, while the movable unit is a [rollout serving island](../concepts/the-rollout-serving-island-is-the-movable-unit-of-an-rl-run.md), "a coherent endpoint or maybe a local group of endpoints… serving one policy version," because there is no all-reduce across islands and there is one inside them. That is a more precise boundary than the wiki's existing decoupled-rollout pages draw, and it explains both why an island may sit in another region and why it may not be shattered into individual GPUs.

Cutting there leaves exactly one link, and the rest of the design is about shrinking it. A frontier-scale checkpoint is ≈500 GB and takes "multiple minutes to hours" to move, while even fully async training "still want[s] weight update latency to be as low as possible, like within seconds" — so [the checkpoint is the wrong unit of synchronization](../concepts/synchronize-rollout-weights-with-a-bitwise-lossless-patch.md), and what crosses the wire instead is a patch of the *served view*: changed positions plus replacement bits, encoded as overrides or XOR so it is "not a floating point addition… no additive delta drift," reconstructing the target version bitwise. Around that sit two operational pieces worth lifting on their own. [Publishing immutable weight versions to a bulletin board](../concepts/publish-immutable-weight-versions-to-a-bulletin-board.md) converts weight distribution from a push to a pull, so an engine that started ten seconds ago joins by fetching and one that died is forgotten; the engine "choose[s] how to load and shard it. It does not choose a different serve[d] version," and requests carry both a target version and an acceptable range while responses carry the version served plus log probs and router-replay metadata. [A version-aware sidecar](../concepts/make-a-rollout-engine-version-aware-with-a-sidecar.md) then adds the only missing state to an unmodified vLLM or SGLang server with three cases — proxy, catch up, or "not ready" — the third being the one that keeps a stale worker from silently poisoning a training batch. The claimed payoff is that "scattered inference capacity became one elastic rollout fleet… inference capacity can now become RL capacity," which is the same asymmetry [inference tolerates degraded GPUs that training cannot](../concepts/inference-tolerates-degraded-gpus-that-training-cannot.md) reaches from hardware health, extended from *quality* tolerance to *locality* tolerance. Read it as a design with one measured input: this is a vendor talk for Modal's own implementation (Stitch), the mechanism's evidence is attributed to an unnamed paper, and the only first-party number is one internal FP8 run — no cross-region latency, no patch-construction overhead, no end-to-end run, and no threat model for weights sitting on other providers' hardware.

A much smaller-scale bottleneck report from the same week points at a different link entirely. OpenAI shipped GPT 5.3 Codex Spark on Cerebras at 1,000 tokens per second and found that for an agent — which spends its life in tool-call round trips rather than one long generation — "inference… no longer was the bottleneck. It was actually the network" ([Fast Inference Moves the Agent Bottleneck to the Network](../concepts/fast-inference-moves-the-agent-bottleneck-to-the-network.md)). The fix is transport rather than serving: a persistent WebSocket carrying the responses API, plus stateful context so a turn ships only the changed item instead of the whole conversation — nine payload items per turn became one in their demo. The structural reason this bites agents first is that a stateless protocol makes turn *n* re-upload *n* items, so upload volume grows quadratically against a linearly growing conversation. Nothing here is measured beyond the item count: the effect is reported as "quite significantly," the live demo crashed and was replaced by a recording, and no latency figures, workload, or baseline accompany it. The same talk's sandboxing section is a reminder that infrastructure choices do not always live in a datacenter — [Codex isolates local execution with whatever the operating system provides](../concepts/sandbox-primitives-are-per-operating-system.md), which for Windows meant writing one.

Justin Smith (Resolve AI) argues the operational side of infrastructure is where the AI coding wave lands next, and his framing is a coverage argument about change. The premise is that the bottleneck was never authoring — "70% of the time from an engineer is actually not focused just on writing code. It's actually spent on actually running the code that is actually shipped into production," covering platform maintenance, scaling, on-call, hot fixes, runbooks, restorations, and escalations — and that coding agents enlarge that half: "AI is creating a lot more issues in production… it's not clear we have the right sort of structures in place to deal with the amount of kind of changes that are coming through." The figure is attributed only as "this was a survey study done," with no publisher or sample. What makes the argument concrete is where he locates the gaps. CI/CD is granted as "tried and true" and is not the target; the two failures named are that its standard checks are "good baselines, but… not exhaustive based on the type of changes that are going in," and — the more interesting one — that whole change classes never enter the pipeline: "a feature flag or maybe some infra changes… which maybe don't get any monitoring at all. And you're sort of just trusting that an alert might fire and an on-caller will wake up and say, 'Who changed what?'" ([Watch the Change Paths That Bypass Your Deployment Pipeline](../concepts/watch-the-change-paths-that-bypass-your-deployment-pipeline.md)). Detection after impact, by someone who was not involved in the change, is the current control on those paths.

The proposed coverage triggers on the change event and derives its own checks: read what the diff touched, choose the telemetry that would expose trouble for it, walk the causal chain outward — "the checkout replaces currency service, we're monitoring the checkout latency and the error rates. Well, let's take a look at the Kafka pipeline cuz that's sort of involved" — and re-check on an interval the agent picks rather than a configured window, up to "come back in 3 days and say, is this deploy still kind of healthy? Are we seeing the change in the effect that I expected to see out of this?" ([Derive the Post-Deploy Check Plan From What Actually Changed](../concepts/derive-the-post-deploy-check-plan-from-what-changed.md)). That last question is an assertion no merge-time gate can make. The stated posture is additive — "our goal is not to sit here and say, 'We're going to replace an entire CI/CD pipeline'" — and the counterfactual being priced is a person: "it would be great if you had a single engineer just focused on like watching all the things on every release, but that's really expensive." Underneath sits the runtime assumption this topic already carries from other sources: cloud-resident, laptop-independent, with a sandbox filesystem the agent uses to organize its own work. The whole talk is a vendor demo in a self-described "fake environment" with nothing measured — no deploy count, catch rate, false-positive rate, baseline comparison, or cost for open-ended re-checking.

Denys Linkov (WiseDocs) reports a repository-layout finding that belongs here rather than under codebase hygiene, because what changed is where the cost lands. The standard agent-side argument for consolidating repositories is comprehension, and he says that premise has expired: "models are much better at navigating multiple repos. So, if you put it into a higher-level folder, right, they could navigate the file directory. But, for doing that end-to-end testing and verification and deployment, it's still much harder to do with multiple repos" ([Multi-Repo Cost Has Moved From Navigation to Verification](../concepts/multi-repo-cost-has-moved-from-navigation-to-verification.md)). The second half is infrastructure work, and it has a per-task price that scales with parallelism: "if you're building a sandbox environment to run sort of a full AI factory, it also takes more time to clone repos and get everything set up." Every isolated environment pays clone-and-provision again, so a distributed repository estate raises the fixed cost of every agent run and every eval task, exactly in the many-agents regime that isolation is meant to enable. The asymmetry is what makes this durable: better navigation weakens the comprehension argument with each model release, while the cost of standing up a coherent test-and-deploy environment across N repositories does not fall as models improve. Read against Jellyfish's measured drag from highly distributed repository layouts, this is the same observation with a different mechanism attached — and the remedies do not overlap, since documentation and cross-repo retrieval fix context and do nothing for verification. The evidence is thin on its own terms: a three-minute Q&A answer, no clone or provisioning timings, no before-and-after on end-to-end test setup, and no statement of the repository count the claim was tested at.

The LLM gateway is by now a standard piece of this stack — one routing API in front of many providers, the natural place to put observability, budgets, and fallbacks — and Saoud Rizwan (Cline) reports what happened when one of them was compromised. LiteLLM, at "3.5 million downloads a day," was published from a GitHub app that attackers gained publishing rights to; for about three hours the released packages carried a credential harvester and a remote-code-execution backdoor ([An AI-Infrastructure Package Is a High-Yield Credential Target](../concepts/an-ai-infrastructure-package-is-a-high-yield-credential-target.md)). The infrastructure lesson is about who installs it. Self-hosting a gateway is the recommended posture in most of this topic's material — it is how teams keep keys in one place, meter spend, and avoid handing traffic to a hosted router — and that is exactly what made the victim population dense in credentials: "enterprise customers and developers that have their own internal gateways." Centralizing keys to control them and centralizing keys to lose them are the same act, distinguished only by whether the centralizing component stays trustworthy. Nothing here argues against the gateway pattern; it argues that the gateway inherits the blast radius of everything routed through it, which is a reason to treat its release channel, its install-time execution, and the lifetime of the credentials it holds as first-order infrastructure decisions rather than dependency hygiene. Relayed second-hand in a keynote, with no incident report cited and no count of affected installs.

Figma's MCP server adds a deployment ordering to this topic's remote-first material. Before the March 2025 spec revision introduced OAuth there was no authorization story to build against, and rather than wait or invent one, Figma put the server inside an asset it already shipped: the Electron desktop app runs figma.com in its front end, an IPC bridge reaches a Node process holding the user's own file permissions, and a local server-events endpoint lets MCP clients connect on the machine. An installed desktop app supplies three things a web-only product would have had to build — an authenticated session, a file-access model inherited from the OS, and a distribution channel — and the enterprise objection answers itself, since customers "kind of like the idea of our data not being sent anywhere." The stated motive was learning speed: "this architecture was our fastest path to getting something into the hands of users to understand product market fit and what kind of tools and use cases folks had." It is a sequence rather than a choice — remote work began "as soon as we launched," shipped in September, and both servers reached general availability in October 2025 — and the bill for local is reach, since nothing running in CI, a cloud sandbox, or on a phone can connect. The launch checklist is worth copying for one unusual item: alongside speed, a security bar, and file permissions sits "respect our pricing [and] packaging so we didn't have abuse vectors," making entitlement enforcement a control class in its own right. The transport lesson is cautionary in the other direction: weeks into the build "a new version of the spec dropped uh deprecating the support type that we were going to use which was server events."

DoorDash's GenAI platform files evaluation as a peer of its routing and auth primitives rather than as something downstream of them: an LLM gateway for switching between models, an agent gateway that centralizes "authentication, agent identity and other things in a central place which our security team can bless," open-weights model hosting paired with the gateway because "cost is a number one concern these days," and then "the fourth pillar is eval." The eval layer itself is two planes — a telemetry layer of traces, scores, and observations reachable through MCP, an SDK, or the APIs, and a workflow layer where operations and product staff set annotation tasks, review golden datasets, and calibrate judges — with both reading the same primitives, because "all your API access including SDK access is basically powered by this single plane." API stability is what makes the platform's most unusual property possible: non-engineers generate their own operational tooling against those endpoints with a coding agent, so the platform team's product is the endpoint rather than the screen. Two costs go unpriced in the talk — maintenance of operator-built apps across API changes, and the per-annotation spend reduction that is claimed without a number.

AWS's formal-verification work supplies this topic with a production architecture it does not otherwise have on file: a system that maintains two implementations on purpose. Cedar, the open-source authorization policy language behind AWS Verified Permissions and Verified Access, keeps "the specification of Cedar… written in Lean" while "the production code runs in Rust," and the two are held together operationally rather than by discipline — "about 100 million differential random tests run nightly. No version ships until this is satisfied." The executable specification is what makes that possible, since differential testing needs a reference to differ against, and it is worth being precise about the resulting claim: the proofs are about the Lean model, and the shipping binary's conformance to that model is sampled at high volume rather than proved. The rest of the talk is an infrastructure map for teams that cannot put the prover's language in production. Verus discharges inline `requires` and `ensures` conditions with the Z3 solver, and the specification is "a static check… enforced by the verifier and erased at runtime," so it costs nothing in the deployed artifact. Aeneas consumes Rust's mid-level intermediate representation and translates it to Lean automatically. And AWS's work-in-progress Strata generalizes the move: author a dialect for your language, lower it to Strata core — "this is written in Lean" — and "dispatch it to any of the engines… the Lean proof… or the very powerful calculator, SMT solvers, or model checkers." The bet is that a shared verification IR, not any one prover, is the durable asset; it is a plan with no reported adopters, and no cost, latency, or defect data accompanies any of it.

Kanish Manuja's LLM-gateway talk supplies the operational counterpart to those platform checklists, and its frame is a trade rather than a list: "right at the heart of the gateway is a fight between four things. It's availability, latency, your guardrails and costs. In case of a degradation, you cannot maximize all four." That yields the design instruction this topic had been missing — a gateway should [expose the trade as a lever to its callers](../concepts/an-llm-gateway-cannot-maximize-availability-latency-guardrails-and-cost.md) rather than pick one answer for every use case, since the traffic behind one gateway spans embeddings under a second and reasoning calls that run for a minute. Three of his conclusions cut against reflexes this topic records elsewhere. First, the standard unreliable-dependency remedy is wrong here: retrying "eats into your latency budget really fast," blind retries "multiply your cost and your tail latencies," and opening a circuit breaker "when you have another perfectly fine model provider to route to doesn't make sense," so the primitive is [per-request fallback](../concepts/prefer-per-request-fallback-to-retries-and-circuit-breakers-for-llm-calls.md) with the breaker demoted to a minutes-scale cool-down. Second, the backup path is where teams under-invest exactly backwards — [the fallback provider needs more headroom than the primary](../concepts/your-fallback-provider-is-under-tested-and-under-provisioned.md), because it absorbs the whole load at the worst moment, and "OpenAI API compatible" still hides differences in "tool calling schemas, token limits, stop reasons" that need a normalization layer. Third, the gateway is itself a dependency in every caller's request path, which is why he argues to [decentralize the gateway and centralize the governance](../concepts/decentralize-the-gateway-centralize-the-governance.md): a company-wide deployment "is a single point of failure," while cost tracking and rate-limit management — what teams asking for one actually want — can travel as plugins or shared code. The supporting operational details are ordinary distributed-systems hygiene applied to a new dependency: API keys "segregated per route, per use case" against noisy tenants, bounded web-server queues, load shedding rehearsed in game days because "you cannot simply scale out services that is under a retry storm," and traffic prioritization so the important routes survive the shed. None of it is measured — the talk reports no availability, latency, or cost figure anywhere — so read it as a checklist for finding unexamined decisions, not as evidence about their outcomes.

Distributed inference gives this topic a concrete instance of the declare-what-you-need principle, and one hardware line that is not negotiable. llm-d is CNCF-hosted and Kubernetes-native (now also running off-Kubernetes), and it adds only the domain-specific pieces above the scheduler: a router with pluggable endpoint-picker plugins that continuously probe each vLLM pod's metrics — running and waiting requests, KV-cache utilization, prefix-cache availability — plus LeaderWorkerSet and DisaggregatedSet workload APIs for multi-node model execution, autoscalers watching "capacity bounds and real-time traffic mixes," and a cache layer offloading to NVMe SSD, XFS, and KV-centric stores such as Mooncake with session pinning as an eviction policy. The instructive part is that default Kubernetes scheduling is the *baseline* in their own concurrency sweep and domain-aware routing visibly beats it: a scheduler with no model of KV-cache locality places requests correctly by accident. The non-negotiable line is the fabric — [disaggregation needs a fabric, and pays off in the middle concurrency band](../concepts/disaggregation-needs-a-fabric-and-pays-off-in-the-middle-band.md), because the decode worker pulls the KV cache across the network on every request, so "you must possess an advanced high-speed network fabric like RDMA or RoCE" and its absence is named "the biggest point" in favour of staying aggregated. That makes prefill/decode disaggregation a procurement decision before it is a configuration one, which is unusual among the serving levers this wiki records.

Simran Arora's multi-GPU kernel work adds the layer beneath everything else this topic records, and it comes with the number that explains why the layer is now the constraint: from the A100 in 2020 to the B200 in 2024, BF16 tensor core throughput improved 7.2x while intra-node communication improved 3x and inter-node communication 2x. The consequence at the top of the stack is that "communication is increasingly consuming the majority of the runtime and yields low model FLOP utilization at scale," and the consequence at the bottom is measurable headroom — across 87 real multi-GPU problems, a PyTorch-plus-NCCL baseline sits [below 50% of its communication-aware roofline](../concepts/measure-multi-gpu-headroom-against-a-communication-aware-roofline.md) on most of them. Her survey of the three standard routes is the useful part for anyone choosing an approach, because each fails differently: collective libraries are "tuned for bulk transfers for large contiguous chunks" and break down on fused or fine-grained collectives; distributed DSLs cannot track hardware churn, with Triton-distributed "originally tuned around 8 H800 GPUs" failing "to adapt efficiently to other architectures like H100s"; and hand-tuned operators reach peak but take "five or six months to scale [a design] to another precision." What worked instead was [adding a small primitive set directly into an existing single-GPU kernel](../concepts/add-multi-gpu-primitives-to-a-single-gpu-kernel.md) at a cost of roughly a dozen lines, in production at Together AI and Cursor. Two decisions inside that kernel are the ones worth carrying into any distributed-kernel review: [which transfer mechanism moves the data](../concepts/choose-the-inter-gpu-transfer-mechanism-by-message-size-and-resource-cost.md) — copy engine, TMA, or register-level `multimem` instructions, which differ in message-size sweet spot, register and SM cost, and whether they can reach NVSwitch's in-network reductions — and [whether compute and communication overlap within one SM or across SMs](../concepts/overlap-communication-with-compute-intra-sm-or-inter-sm.md), which turns on whether the two consume the same data. A caution this topic should carry forward: matmul units and memory hierarchies look similar across vendors, but "the networking stack is something that is really different across vendors still," so communication-side optimization is the least portable work in the stack.

Two operating disciplines from pre-AI web scaling transfer without modification, and Mike Krieger restates both for AI systems. Instrument ahead of the question: "pre-measure everything that you think you might even remotely need because the worst thing is an outage where you're like, well, is this number normal or is it high?" The loss when you skip it is not the missing number but the missing baseline, which makes the metric uninterpretable for the duration of the incident that prompted it. And build runtime control as a product surface — feature flags, ramps and rollouts, and dynamic config changeable in seconds — because AI systems are unusually knob-dense (model choice, reasoning level, retrieval depth, guardrail placement, context budgets) and those knobs are exactly what you want to move under degradation without a deploy.

Where an agent platform serves non-engineers, the consequential infrastructure decision may be upstream of the agent entirely. Snowflake's internal go-to-market assistant rests on a deliberate consolidation — first-party, third-party, CRM, and call-transcript data landed in one governed store — and the payoff its owner names first is authorization rather than query performance: agents inherit role-based access control from the store instead of each implementing it, which is what makes no-code deployment by business teams defensible and lets the platform curate which sources an agent may reach. The tradeoff against the alternative shape, where systems stay in place behind programmatic interfaces, is where the per-integration cost lands: consolidation pays once at ingestion and inherits one permission model, and the ingestion work is not small — 60% of that system's data arrived in the six to seven months after launch. This is also the platform vendor describing its own product.

Agent-serving infrastructure inherits a familiar split when the context is a company's own data. Notion ingests every go-to-market vendor feed into a warehouse that runs daily — and in some cases real-time — transforms into a small set of modeled, versioned entities, then publishes them to a key-value store as a denormalized, key-addressable profile precisely because an agent turn cannot afford a multi-table join. Generated artifacts are persisted beside the facts under the same keys, which makes one read sufficient and leaves an unanswered invalidation question. The rest of the stack is rented on a per-layer decision: durable orchestration (Temporal, chosen for retries, dedupes, resume-at-failure, and batch isolation), email, CRM, and enrichment all come from vendors, while the context layer is kept for representational fit and debuggability. The failure the design targets is stated plainly — "every vendor added a hop and this lag was causing us to act on stale data" — which makes consolidation a latency and freshness decision before it is a governance one.

When a context layer is assembled from purchased data rather than produced internally, its economics change shape. Berry's account of a go-to-market data layer makes three properties structural: coverage is achieved by waterfalling multiple providers because none covers a field for the whole population, with provider evals deciding the order; freshness is a budget rather than a schedule, because "it's incredibly expensive to update data all the time, especially if you're purchasing it," so refresh is chosen per field and ranked by how fast that field actually moves; and entity resolution across disagreeing vendor representations is an admission requirement for the layer, not a cleanup pass over it. The waterfall inherits a familiar hazard — the later rungs serve exactly the records the earlier rungs missed, a biased and rarely monitored slice — which is why the eval has to be run on the population each provider actually serves.

The store an agent reads its entity context from is a live architectural disagreement, not a settled question. Two go-to-market teams building the same kind of joined customer model chose opposite serving layers for opposite reasons: Notion publishes a denormalized, key-addressable profile from DynamoDB so an agent turn never pays for a join, while Ramp backs the same layer with Postgres precisely to keep "transactional guarantees, referential integrity between the entities that exist… between your CRM, between your product, between third parties," plus provenance columns recording where each value came from and when. Both put heavy batch compute behind the serving layer — Snowflake and dbt on one side, Snowflake, dbt, and reverse ETL back into the same store on the other — and both converge multiple write paths onto one read surface so the agent reads a single place. What they disagree about is what the serving layer owes the reader: denormalization buys latency and pays with duplicated, eventually-consistent copies; a relational store keeps one authoritative relationship graph and pays with joins on the read path. Neither source reports a latency, volume, or entity-count figure, so the boundary between them is undrawn, and the honest reading is that the choice follows from which failure hurts more — a slow agent turn, or a rep shown a contact attached to the wrong account.

A shopping-agent rebuild adds a specific reading of "the missing layer" to this topic: below the agent runtime sits an access layer — stealth, exit location, block detection, and the decision of whether a browser is in the loop at all — and it fails differently from the runtime levers this wiki already documents. Observation format and action vocabulary degrade an agent that is at least receiving the page; this one determines whether a real page arrives. It is also the layer most often bought rather than built, which turns several design questions into procurement questions and introduces a dependency whose failure rate you cannot observe directly. Two consequences are worth carrying. Outsourcing a brittle step is a third option beside scripting it and leaving it in the loop: pushing a browser behind a REST call that renders dynamic pages server-side keeps the brittleness in the system while removing it from the agent's cost, latency, and retry envelope — at the price of depending on someone else's render fidelity with no per-fact provenance. And a protocol boundary at the browser makes the provider replaceable, though drop-in compatibility describes the wiring rather than the results: a different browser build, proxy pool, and exit location render and are treated differently, which invalidates anything calibrated against the old environment.

An environment can be a hosted multi-tenant service rather than a runnable package, and that changes what it distributes. Einstein Arena has no installable artifact: it hosts curated problems, each with its own deterministic verifier, scores submissions live, and lets any admitted agent download every other participant's solution. Against a package registry, which lets you run and modify an environment on your own compute, the hosted arena lets you contribute without owning infrastructure and makes every rival's work visible — prior submissions as downloadable state are what turn a leaderboard into a substrate rather than a ranking. The design's reusability shows up in a retarget: pointing the same arena at GPU kernel optimization changed only the backend, from a mathematics checker to compile, benchmark, test, and time, and produced kernels reported at over 2x and adopted into production at Together AI. That puts the cost model plainly — a new problem class costs a verifier — while understating it where the verifier is a hardware-in-the-loop measurement rig with tolerance, warmup, and timing policy to get right, none of which the source describes. On the execution side, DSGym makes parallel sandboxing part of the environment's contract rather than the trainer's: agents spin up many Docker containers and run experiments concurrently through one interface, which is what lets a single artifact serve both evaluation and trajectory generation.

A routing product from the same period puts a concrete surface on the gateway tradeoffs this topic records. Where a gateway operator's advice to designers is to expose availability, latency, guardrails and cost "as levers to your callers and customers" rather than hard-coding one answer, DigitalOcean ships three of those four as declared fields — "you describe what matters for your workload, costs, latency, quality, preferred models or hard rules" — plus decision-tree rules layered over natural-language task descriptions ([declare routing preferences so a bad route is fixable](../concepts/declare-routing-preferences-so-a-bad-route-is-fixable.md)). The fourth axis is simply absent: guardrails, filters and governance are never mentioned, so the router is an optimization layer and not a policy layer, and anything a gateway enforces still has to sit somewhere else. The operationally interesting piece is that failover stops being a global gateway setting: [give each task a model pool with an explicit selection policy](../concepts/give-each-task-a-model-pool-with-an-explicit-selection-policy.md) puts the backup model in the same config line as the primary, per task, which does not test or provision the fallback path but does remove the most common precondition for neglecting it — not knowing what the backup is. Two cautions carry over unchanged. A declared preference is not an enforcement mechanism: saying latency matters biases a per-request choice whose matching step is itself nondeterministic, so a degradation still forces the four-way choice. And the OpenAI-compatible proxy that makes adoption a base-URL change ("zero application code changes needed") hides cross-model differences in tool-calling schemas, token limits and stop reasons only to the extent someone has built the normalization — which the router makes more pressing, since models now change under the call site without anyone having chosen to switch.

## Open Questions

- What does an arena's kernel verifier actually measure? The wiki's kernel-evaluation guidance enumerates tolerance policy, representative shapes, warmups, cache clearing, and ordering effects; Zou reports "over 2x" against unnamed prior state-of-the-art kernels with none of that stated, and the strongest evidence offered is adoption into production rather than a measured margin. ([Zou](../sources/20260825_mMNkdYnIVC4.md), 08:57-10:54)

- How do you monitor an outsourced access layer's real failure rate, given that its whole value proposition is returning clean results? Per-success billing gives the vendor an incentive to classify honestly, but it gives the buyer no independent measurement, and no source in this wiki proposes one.

- How is a communication-aware roofline actually computed, and does the below-50% result survive outside its own benchmark? The claim that a PyTorch-plus-NCCL baseline leaves more than half its analytic bound unclaimed is the strongest argument this topic has for investing in custom communication kernels, and the bound's derivation is deferred to a paper. Without it, a team cannot tell whether their own workload has the same headroom or whether 50% is simply what a general-purpose collective library costs. ([Arora](../sources/20260827_pOvWgX7IJsc.md), 12:03-12:32)

- What does KV-cache-aware routing cost the platform? The endpoint picker continuously probes every serving pod's metrics to score it, and no source quantifies the probe overhead, the staleness window between probe and placement, or the behaviour when the cache-richest pod is also the most loaded — the scoring function is described only as balancing the two. ([Fama](../sources/20260827_YXowceUKYJI.md), 06:28-07:12)

- What does the decentralized-governance alternative actually cost to operate? The argument against a single company-wide gateway is a blast-radius argument, and it is convincing; the replacement — plugins or shared code enforcing common policy across many deployments — is asserted with no account of upgrade lag, config drift, or how a cost-tracking plugin scattered across a fleet produces a complete picture. No source in this wiki reports running either shape at scale, so the choice currently rests on which failure you find easier to imagine. ([Manuja](../sources/20260828_zrZ1amZBSPw.md), 14:34-15:42)
- What does the input generator behind a differential-testing gate look like? "About 100 million differential random tests run nightly" is the only figure this topic has for such a gate, and the distribution those inputs are drawn from is unreported — which is precisely what decides whether the number means broad coverage or a hundred million near-duplicates. A structure-aware generator running a thousand times fewer cases may be the stronger gate. ([Pant](../sources/20260828_lRa9sPaMyy4.md), 06:36-06:58)
- Does filing eval next to the gateways as a fourth pillar survive the fact that its users are not services? Routing, auth, and model hosting are consumed by code; the eval layer is consumed by operations staff, product managers, and apps those people generated, which implies a different support, access-control, and backward-compatibility profile than the other three pillars carry.
- What is the maintenance cost of running local and remote MCP servers permanently side by side? Figma GA'd both and kept both, and every capability added afterwards — read and write among them — has to land twice under different trust, transport, and permission models. No source here reports what that duplication costs over time.
- Should the credentials an LLM gateway holds be long-lived at all? Every gateway description in this topic assumes provider API keys sit in the gateway's configuration, and the LiteLLM compromise is the case where that assumption is priced. No source here discusses short-lived or broker-issued provider credentials for the gateway itself, per-route key scoping, or what a rotation actually costs when the gateway fronts every model call a company makes — so teams have no basis for choosing between "rotate on incident" and a design where there is little to steal.
- What does sandbox provisioning actually cost per agent task, and how much of it is repository layout? "It also takes more time to clone repos and get everything set up" is the only account in this wiki of the fixed cost every isolated run pays, and it carries no seconds, no cache strategy, no image-warming approach, and no comparison between a monorepo and an N-repo checkout. For teams choosing between more parallel agents and fewer, that number is the budget.

- What does an agent-derived post-deploy check actually catch that the pipeline does not? The argument for per-change telemetry selection is stated entirely from first principles — every rollout is unique, so uniform checks under-cover — with no catch rate, no false-positive rate, and no comparison against the baseline CI/CD checks it is meant to complement. A team cannot tell whether this replaces one alert per quarter or one per week.
- How much does continuous change-watching cost to run? An agent that decides to re-check in an hour, and again in three days, is a long-lived compute and token consumer per release, feature flag, and infra change. The one source describing the pattern also observes that "unlimited tokens is… coming to an end… prices are going up," and offers no cost figure for its own workload.
- Where is the crossover between generation time and network time for an ordinary serving stack? The observation that the network becomes the bottleneck comes from one 1,000-token-per-second deployment, with no per-turn breakdown into generation, round trip, and upload. Teams on conventional hardware have no way to tell whether transport work is their next win or a finding specific to that accelerator.
- What does stateful server-side conversation state cost the provider, and what happens when it is lost? Sending only the delta requires the server to hold the conversation, which turns a stateless request path into a session with a lifetime, a memory footprint, and a failure mode nobody describes — including what a client must resend after a dropped connection.
- What does it cost to build and store the weight patches, and how long must versions be retained? Producing one requires casting the full parameter set to the serving dtype and diffing it against the previous version every step, and a lagging engine can only "apply the missing transition[s]" if the board still holds them. Neither the trainer-side overhead nor the retention policy appears in the only source that describes the design.
- Does cross-region rollout actually pay once the trajectories are counted? The 500 GB → 500 MB figure covers weights flowing out; for long agentic rollouts the trajectories, log probs, and router-replay metadata flowing back may be the larger volume, and no source reports that side, nor any egress cost.
- What is the security posture of a globally distributed rollout fleet? Publishing weight versions to a board that engines at arbitrary providers pull from is the point of the design, and the source offers no threat model, encryption, attestation, or access-control story for weights and trajectory data on hardware the trainer does not control.
- What does an unbounded session log cost to keep? Making the session a durable resource is what buys resumption and slice-back, and no source states a retention policy, a size limit, or a storage cost for a long-running agent — nor addresses that a complete transcript of everything the agent saw is itself a sensitive artifact.
- Where does the added network hop land once the loop and the container are separate processes? The reported latency win is entirely at first token; a trajectory with a hundred tool calls pays a round trip on each, and no source reports that side of the ledger or the failure modes it introduces (partial results, a sandbox alive but unreachable).
- What does a nightly batch pass over all session transcripts cost, and does it pay? Offline memory rewriting is described as a periodic process over accumulated transcripts with no compute figure, no cadence guidance, and no evaluation that rewritten memory improves the next day's runs.
- How are thousands of concurrent production rollouts merged into a single weight update? Malde names this as jointly an infrastructure and an algorithmic problem and says the field is "nowhere close" — batching, averaging, and arbitration between conflicting lessons are all plausible and none is described by any source in the wiki.
- What does a self-distillation update actually cost in FLOPs against a GRPO one? "Parallelism of one" removes the environment fleet but adds teacher forward passes over the full vocabulary at every token; the talk that makes the comparison never prices the second side, so the infrastructure saving is directional and unquantified.
- What isolation does a corpus-scale trace-classifier sandbox need? Model-written code sweeping production traces is untrusted code with broad read access to user data, and the source that recommends the pattern describes no isolation model, no redaction step, and no access scoping.
- What does the "unified engine" of serving and training actually require — weight-swap latency on a live serving fleet, rollback path, and per-request attribution? Two Applied Compute talks now name it as the goal and neither describes the system.
- Where should the placement judge and teacher forward pass run in an online-hint loop, and what do they add to serving cost per request? No source in this wiki prices the online corner against the offline one it is said to beat.
- What is the right checkpoint interval as a function of observed mean time between failures and checkpoint write time? Krea's 20-30 minutes is reported as what their filesystem allowed, not as an optimum derived from their crash rate.
- Which storage systems actually sustain a training cluster's checkpoint burst? Ceph is reported to have failed on trust rather than throughput, and the recommendation ("go with something paid") names no replacement, so the wiki has a gap between the required numbers (~1 TB in under 30 seconds) and any product that meets them.
- How much of Krea's failure rate is workload-specific? The speaker concedes it may be "skill issue on our part, maybe our cluster," and their runs lasted far less than Meta's published estimate, so no source here establishes what an expected failure rate at a given GPU count should be.
- What does the training-outranks-production policy cost in serving quality? The talk reports no latency, error-rate, or utilization numbers for the periods when inference is running on external providers.
- Render consistency and eval-side environment variation pull in opposite directions and no source runs both. If production pins the viewport and browser build while the benchmark deliberately varies theme and starting screen, which distribution does a deployment decision use — and does a fleet that renders one canonical layout make agents that break the first time a customer's site is served differently?
- What does the event log's read cost become when the writer is an agent rather than a transaction processor? Anterior accepts "reads become more difficult" and points at caching and snapshots, but agent runs emit far more events per unit of business work than the finance systems the pattern was borrowed from, and no source quantifies where projection rebuilds stop being affordable.
